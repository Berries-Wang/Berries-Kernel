==========================================
 drm/i915 Intel GFX Driver(Intel GFX 驱动)
==========================================

The drm/i915 driver supports all (with the exception of some very early
models) integrated GFX chipsets with both Intel display and rendering
blocks. This excludes a set of SoC platforms with an SGX rendering unit,
those have basic support through the gma500 drm driver.
(drm/i915 驱动支持所有（除了一些非常早期的型号之外）同时具备 Intel 显示与渲染
模块的集成 GFX 芯片组。这不包括带有 SGX 渲染单元的一批 SoC 平台，那些平台通过
gma500 drm 驱动获得基本支持。)

Memory Management and Command Submission(内存管理与命令提交)
============================================================

This sections covers all things related to the GEM implementation in the
i915 driver.

Intel GPU Basics(Intel GPU 基础)
--------------------------------

An Intel GPU has multiple engines. There are several engine types:
(一个 Intel GPU 拥有多个引擎。引擎类型有以下几种：)

- Render Command Streamer (RCS). An engine for rendering 3D and
  performing compute.
  (渲染命令流（RCS）。用于渲染 3D 与执行计算的引擎。)
- Blitting Command Streamer (BCS). An engine for performing blitting and/or
  copying operations.
  (块传输命令流（BCS）。用于执行块传输（blitting）和/或复制操作的引擎。)
- Video Command Streamer. An engine used for video encoding and decoding. Also
  sometimes called 'BSD' in hardware documentation.
  (视频命令流。用于视频编码与解码的引擎。在硬件文档中有时也称为 'BSD'。)
- Video Enhancement Command Streamer (VECS). An engine for video enhancement.
  Also sometimes called 'VEBOX' in hardware documentation.
  (视频增强命令流（VECS）。用于视频增强的引擎。在硬件文档中有时也称为
  'VEBOX'。)
- Compute Command Streamer (CCS). An engine that has access to the media and
  GPGPU pipelines, but not the 3D pipeline.
  (计算命令流（CCS）。可以访问媒体与 GPGPU 流水线、但不能访问 3D 流水线的
  引擎。)
- Graphics Security Controller (GSCCS). A dedicated engine for internal
  communication with GSC controller on security related tasks like
  High-bandwidth Digital Content Protection (HDCP), Protected Xe Path (PXP),
  and HuC firmware authentication.
  (图形安全控制器（GSCCS）。一个专用引擎，用于在安全相关任务上与 GSC 控制器
  进行内部通信，例如高带宽数字内容保护（HDCP）、受保护的 Xe 路径（PXP）以及
  HuC 固件认证。)

The Intel GPU family is a family of integrated GPU's using Unified
Memory Access. For having the GPU "do work", user space will feed the
GPU batch buffers via one of the ioctls `DRM_IOCTL_I915_GEM_EXECBUFFER2`
or `DRM_IOCTL_I915_GEM_EXECBUFFER2_WR`. Most such batchbuffers will
instruct the GPU to perform work (for example rendering) and that work
needs memory from which to read and memory to which to write. All memory
is encapsulated within GEM buffer objects (usually created with the ioctl
`DRM_IOCTL_I915_GEM_CREATE`). An ioctl providing a batchbuffer for the GPU
to create will also list all GEM buffer objects that the batchbuffer reads
and/or writes. For implementation details of memory management see
`GEM BO Management Implementation Details(GEM BO 管理实现细节)`_.
(Intel GPU 家族是使用统一内存访问的集成 GPU 家族。要让 GPU "干活"，用户空间会
通过 ioctl DRM_IOCTL_I915_GEM_EXECBUFFER2 或 DRM_IOCTL_I915_GEM_EXECBUFFER2_WR
之一把批缓冲喂给 GPU。大多数这样的批缓冲会指示 GPU 执行工作（例如渲染），而该
工作需要有可读和可写的内存。所有内存都封装在 GEM 缓冲对象中（通常通过 ioctl
DRM_IOCTL_I915_GEM_CREATE 创建）。一个为 GPU 提供批缓冲的 ioctl 还会列出该批
缓冲要读和/或写的全部 GEM 缓冲对象。内存管理的实现细节参见
`GEM BO Management Implementation Details(GEM BO 管理实现细节)`_。)

The i915 driver allows user space to create a context via the ioctl
`DRM_IOCTL_I915_GEM_CONTEXT_CREATE` which is identified by a 32-bit
integer. Such a context should be viewed by user-space as -loosely-
analogous to the idea of a CPU process of an operating system. The i915
driver guarantees that commands issued to a fixed context are to be
executed so that writes of a previously issued command are seen by
reads of following commands. Actions issued between different contexts
(even if from the same file descriptor) are NOT given that guarantee
and the only way to synchronize across contexts (even from the same
file descriptor) is through the use of fences. At least as far back as
Gen4, also have that a context carries with it a GPU HW context;
the HW context is essentially (most of at least) the state of a GPU.
In addition to the ordering guarantees, the kernel will restore GPU
state via HW context when commands are issued to a context, this saves
user space the need to restore (most of at least) the GPU state at the
start of each batchbuffer. The non-deprecated ioctls to submit batchbuffer
work can pass that ID (in the lower bits of drm_i915_gem_execbuffer2::rsvd1)
to identify what context to use with the command.
(i915 驱动允许用户空间通过 ioctl DRM_IOCTL_I915_GEM_CONTEXT_CREATE 创建上下文，
该上下文由一个 32 位整数标识。用户空间应当把这样的上下文粗略地类比为操作系统的
CPU 进程概念。i915 驱动保证：提交到同一固定上下文的命令会按顺序执行，使得先前
发出的命令的写入能被后续命令的读取看到。在不同上下文之间发出的动作（即使来自
同一个文件描述符）则没有这种保证，跨上下文同步（即使来自同一文件描述符）的唯一
途径是使用 fence。至少从 Gen4 起，上下文还携带着一个 GPU HW 上下文；HW 上下文
本质上（至少大部分）就是 GPU 的状态。除了顺序保证之外，当命令被提交到某个上下文
时，内核会通过 HW 上下文恢复 GPU 状态，这为用户空间省去了在每个批缓冲开始时恢复
（至少大部分）GPU 状态的需要。非弃用的批缓冲提交 ioctl 可以传递该 ID（在
drm_i915_gem_execbuffer2::rsvd1 的低位中）来标识命令要使用的上下文。)

The GPU has its own memory management and address space. The kernel
driver maintains the memory translation table for the GPU. For older
GPUs (i.e. those before Gen8), there is a single global such translation
table, a global Graphics Translation Table (GTT). For newer generation
GPUs each context has its own translation table, called Per-Process
Graphics Translation Table (PPGTT). Of important note, is that although
PPGTT is named per-process it is actually per context. When user space
submits a batchbuffer, the kernel walks the list of GEM buffer objects
used by the batchbuffer and guarantees that not only is the memory of
each such GEM buffer object resident but it is also present in the
(PP)GTT. If the GEM buffer object is not yet placed in the (PP)GTT,
then it is given an address. Two consequences of this are: the kernel
needs to edit the batchbuffer submitted to write the correct value of
the GPU address when a GEM BO is assigned a GPU address and the kernel
might evict a different GEM BO from the (PP)GTT to make address room
for another GEM BO. Consequently, the ioctls submitting a batchbuffer
for execution also include a list of all locations within buffers that
refer to GPU-addresses so that the kernel can edit the buffer correctly.
This process is dubbed relocation.
(GPU 有自己的内存管理与地址空间。内核驱动为 GPU 维护内存转换表。对于较老的 GPU
（即 Gen8 之前），只有一张全局的转换表，即全局图形转换表（GTT）。对于较新的
代次，每个上下文都有自己的转换表，称为每进程图形转换表（PPGTT）。需要注意的是，
虽然 PPGTT 名为 per-process，它实际上是按上下文划分的。当用户空间提交批缓冲时，
内核会遍历批缓冲使用的 GEM 缓冲对象列表，并保证不仅每个 GEM 缓冲对象的内存是
驻留的，而且它也存在于（PP）GTT 中。如果 GEM 缓冲对象尚未放入（PP）GTT，则会被
分配一个地址。这样做有两个后果：内核需要修改提交的批缓冲，在 GEM BO 被分配 GPU
地址时写入正确的 GPU 地址值；并且内核可能会把另一个 GEM BO 从（PP）GTT 中逐出，
以为另一个 GEM BO 腾出地址空间。因此，提交批缓冲执行的 ioctl 还会包含缓冲区内
所有引用 GPU 地址的位置的列表，以便内核能正确修改缓冲区。这一过程被称为重定位
（relocation）。)

Locking Guidelines(加锁准则)
----------------------------

.. note::
   This is a description of how the locking should be after
   refactoring is done. Does not necessarily reflect what the locking
   looks like while WIP.
   (这里描述的是重构完成之后加锁应当是什么样子。并不一定反映 WIP 期间的加锁
   现状。)

#. All locking rules and interface contracts with cross-driver interfaces
   (dma-buf, dma_fence) need to be followed.
   (必须遵守所有加锁规则以及与跨驱动接口（dma-buf、dma_fence）的接口契约。)

#. dma_resv will be the outermost lock (when needed) and ww_acquire_ctx
   is to be hoisted at highest level and passed down within i915_gem_ctx
   in the call chain
   (dma_resv 将是最外层的锁（在需要时），ww_acquire_ctx 应提升到最高层，并在
   调用链中通过 i915_gem_ctx 向下传递。)

#. While holding lru/memory manager (buddy, drm_mm, whatever) locks
   system memory allocations are not allowed
   (持有 lru/内存管理器（buddy、drm_mm 等）锁时，不允许进行系统内存分配。)

#. Do not nest different lru/memory manager locks within each other.
   Take them in turn to update memory allocations, relying on the object’s
   dma_resv ww_mutex to serialize against other operations.
   (不要把不同的 lru/内存管理器锁相互嵌套。应轮流获取它们来更新内存分配，依靠
   对象的 dma_resv ww_mutex 来与其他操作串行化。)

#. The suggestion for lru/memory managers locks is that they are small
   enough to be spinlocks.
   (对 lru/内存管理器锁的建议是：它们应当小到可以做成自旋锁。)

#. All features need to come with exhaustive kernel selftests and/or
   IGT tests when appropriate
   (所有功能都需要配上穷尽的内核自测，并在适当时配以 IGT 测试。)

#. All LMEM uAPI paths need to be fully restartable (_interruptible()
   for all locks/waits/sleeps)
   (所有 LMEM uAPI 路径都必须完全可重启（所有锁/等待/睡眠都用 _interruptible()）。)

	* Error handling validation through signal injection.
	  Still the best strategy we have for validating GEM uAPI
          corner cases.
	  Must be excessively used in the IGT, and we need to check
	  that we really have full path coverage of all error cases. (通过信号注入进行错误处理验证，仍是我们验证 GEM uAPI 边角情形的最好策略。必须在 IGT 中大量使用，并且我们需要检查确实对全部错误情形有完整路径覆盖。)

	* -EDEADLK handling with ww_mutex (使用 ww_mutex 处理 -EDEADLK)

Microcontrollers(微控制器)
==========================

Starting from gen9, three microcontrollers are available on the HW: the
graphics microcontroller (GuC), the HEVC/H.265 microcontroller (HuC) and the
display microcontroller (DMC). The driver is responsible for loading the
firmwares on the microcontrollers; the GuC and HuC firmwares are transferred
to WOPCM using the DMA engine, while the DMC firmware is written through MMIO.

i915 DRM client usage stats implementation(i915 DRM 客户端使用统计实现)
=======================================================================

The drm/i915 driver implements the DRM client usage stats specification as
documented in :ref:`drm-client-usage-stats`.
(drm/i915 驱动实现了 :ref:`drm-client-usage-stats` 中记录的 DRM 客户端使用统计
规范。)

Example of the output showing the implemented key value pairs and entirety of
the currently possible format options:

::

      pos:    0
      flags:  0100002
      mnt_id: 21
      drm-driver: i915
      drm-pdev:   0000:00:02.0
      drm-client-id:      7
      drm-engine-render:  9288864723 ns
      drm-engine-copy:    2035071108 ns
      drm-engine-video:   0 ns
      drm-engine-capacity-video:   2
      drm-engine-video-enhance:   0 ns

(以下输出示例展示了已实现的键值对，以及当前所有可能的格式选项。)

Possible `drm-engine-` key names are: `render`, `copy`, `video` and
`video-enhance`.
(可能的 drm-engine- 键名有 render、copy、video 与 video-enhance。)
