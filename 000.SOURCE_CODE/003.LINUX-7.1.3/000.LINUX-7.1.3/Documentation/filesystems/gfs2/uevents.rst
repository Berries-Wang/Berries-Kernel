================
uevents and GFS2
================

(uevent 与 GFS2)

During the lifetime of a GFS2 mount, a number of uevents are generated.
This document explains what the events are and what they are used
for (by gfs_controld in gfs2-utils).
(在一个 GFS2 挂载的生命周期内，会生成若干 uevent。本文档解释这些事件是什么以及它们的用途(由 gfs2-utils 中的 gfs_controld 使用)。)

A list of GFS2 uevents
(GFS2 uevent 列表)
======================

1. ADD
(1. ADD)
------

The ADD event occurs at mount time. It will always be the first
uevent generated by the newly created filesystem. If the mount
is successful, an ONLINE uevent will follow.  If it is not successful
then a REMOVE uevent will follow.
(ADD 事件在挂载时发生。它总是由新创建的文件系统生成的第一个 uevent。如果挂载成功，随后会有一个 ONLINE uevent。如果不成功，则随后会有一个 REMOVE uevent。)

The ADD uevent has two environment variables: SPECTATOR=[0|1]
and RDONLY=[0|1] that specify the spectator status (a read-only mount
with no journal assigned), and read-only (with journal assigned) status
of the filesystem respectively.
(ADD uevent 有两个环境变量：SPECTATOR=[0|1] 和 RDONLY=[0|1]，它们分别指定旁观者(spectator)状态(一个未分配日志的只读挂载)以及只读(已分配日志)状态。)

2. ONLINE
(2. ONLINE)
---------

The ONLINE uevent is generated after a successful mount or remount. It
has the same environment variables as the ADD uevent. The ONLINE
uevent, along with the two environment variables for spectator and
RDONLY are a relatively recent addition (2.6.32-rc+) and will not
be generated by older kernels.
(ONLINE uevent 在成功挂载或重新挂载之后生成。它拥有与 ADD uevent 相同的环境变量。ONLINE uevent 以及 spectator 和 RDONLY 这两个环境变量是较新加入的(2.6.32-rc+)，较旧的内核不会生成它们。)

3. CHANGE
(3. CHANGE)
---------

The CHANGE uevent is used in two places. One is when reporting the
successful mount of the filesystem by the first node (FIRSTMOUNT=Done).
This is used as a signal by gfs_controld that it is then ok for other
nodes in the cluster to mount the filesystem.
(CHANGE uevent 在两个地方使用。其一是报告第一个节点成功挂载该文件系统时(FIRSTMOUNT=Done)。gfs_controld 将其用作信号，表示此时集群中的其他节点可以挂载该文件系统了。)

The other CHANGE uevent is used to inform of the completion
of journal recovery for one of the filesystems journals. It has
two environment variables, JID= which specifies the journal id which
has just been recovered, and RECOVERY=[Done|Failed] to indicate the
success (or otherwise) of the operation. These uevents are generated
for every journal recovered, whether it is during the initial mount
process or as the result of gfs_controld requesting a specific journal
recovery via the /sys/fs/gfs2/<fsname>/lock_module/recovery file.
(另一个 CHANGE uevent 用于通知文件系统的某个日志的日志恢复已完成。它有两个环境变量，JID= 指定刚刚被恢复的日志 id，RECOVERY=[Done|Failed] 表示操作是否成功。这些 uevent 会为每个被恢复的日志生成，无论是在初始挂载过程中，还是作为 gfs_controld 通过 /sys/fs/gfs2/<fsname>/lock_module/recovery 文件请求特定日志恢复的结果。)

Because the CHANGE uevent was used (in early versions of gfs_controld)
without checking the environment variables to discover the state, we
cannot add any more functions to it without running the risk of
someone using an older version of the user tools and breaking their
cluster. For this reason the ONLINE uevent was used when adding a new
uevent for a successful mount or remount.
(由于 CHANGE uevent 曾被使用(在早期版本的 gfs_controld 中)时不检查环境变量来获知状态，我们无法在不冒风险的情况下向其添加更多功能——风险是有人使用旧版本的用户工具并破坏其集群。因此，在为成功挂载或重新挂载添加新 uevent 时，使用了 ONLINE uevent。)

4. OFFLINE
(4. OFFLINE)
----------

The OFFLINE uevent is only generated due to filesystem errors and is used
as part of the "withdraw" mechanism. Currently this doesn't give any
information about what the error is, which is something that needs to
be fixed.
(OFFLINE uevent 仅因文件系统错误而生成，并作为 "withdraw" 机制的一部分使用。目前它不提供任何关于错误是什么的信息，这是需要修复的问题。)

5. REMOVE
(5. REMOVE)
---------

The REMOVE uevent is generated at the end of an unsuccessful mount
or at the end of a umount of the filesystem. All REMOVE uevents will
have been preceded by at least an ADD uevent for the same filesystem,
and unlike the other uevents is generated automatically by the kernel's
kobject subsystem.
(REMOVE uevent 在一次不成功的挂载结束时或该文件系统一次 umount 结束时生成。所有 REMOVE uevent 之前都至少有针对同一文件系统的一个 ADD uevent，并且与其他 uevent 不同，它由内核的 kobject 子系统自动生成。)


Information common to all GFS2 uevents (uevent environment variables)
(所有 GFS2 uevent 共有的信息(uevent 环境变量))
=====================================================================

1. LOCKTABLE=
(1. LOCKTABLE=)
--------------

The LOCKTABLE is a string, as supplied on the mount command
line (locktable=) or via fstab. It is used as a filesystem label
as well as providing the information for a lock_dlm mount to be
able to join the cluster.
(LOCKTABLE 是一个字符串，在挂载命令行上(locktable=)或通过 fstab 提供。它既用作文件系统标签，也为 lock_dlm 挂载提供加入集群所需的信息。)

2. LOCKPROTO=
(2. LOCKPROTO=)
-------------

The LOCKPROTO is a string, and its value depends on what is set
on the mount command line, or via fstab. It will be either
lock_nolock or lock_dlm. In the future other lock managers
may be supported.
(LOCKPROTO 是一个字符串，其值取决于在挂载命令行上或通过 fstab 设置的内容。它将是 lock_nolock 或 lock_dlm。将来可能会支持其他锁管理器。)

3. JOURNALID=
(3. JOURNALID=)
-------------

If a journal is in use by the filesystem (journals are not
assigned for spectator mounts) then this will give the
numeric journal id in all GFS2 uevents.
(如果文件系统正在使用日志(spectator 挂载不分配日志)，那么这将在所有 GFS2 uevent 中给出数字形式的日志 id。)

4. UUID=
(4. UUID=)
--------

With recent versions of gfs2-utils, mkfs.gfs2 writes a UUID
into the filesystem superblock. If it exists, this will
be included in every uevent relating to the filesystem.
(在 gfs2-utils 的较新版本中，mkfs.gfs2 会将一个 UUID 写入文件系统超级块。如果它存在，这将包含在与该文件系统相关的每个 uevent 中。)
