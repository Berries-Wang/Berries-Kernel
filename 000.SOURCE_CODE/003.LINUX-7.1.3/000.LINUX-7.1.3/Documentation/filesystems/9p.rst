=======================================
v9fs: Plan 9 Resource Sharing for Linux
=======================================

(v9fs：面向 Linux 的 Plan 9 资源共享)

About
(关于)
=====

v9fs is a Unix implementation of the Plan 9 9p remote filesystem protocol.
(v9fs 是 Plan 9 9p 远程文件系统协议的一个 Unix 实现。)

This software was originally developed by Ron Minnich <rminnich@sandia.gov>
and Maya Gokhale.  Additional development by Greg Watson
<gwatson@lanl.gov> and most recently Eric Van Hensbergen
<ericvh@gmail.com>, Latchesar Ionkov <lucho@ionkov.net> and Russ Cox
<rsc@swtch.com>.
(本软件最初由 Ron Minnich <rminnich@sandia.gov> 和 Maya Gokhale 开发。后续开发由 Greg Watson <gwatson@lanl.gov> 完成，而最近的开发者则是 Eric Van Hensbergen <ericvh@gmail.com>、Latchesar Ionkov <lucho@ionkov.net> 和 Russ Cox <rsc@swtch.com>。)

The best detailed explanation of the Linux implementation and applications of
the 9p client is available in the form of a USENIX paper:
(关于 Linux 实现以及 9p 客户端应用的最佳详细阐述，以一篇 USENIX 论文的形式提供：)

   https://www.usenix.org/events/usenix05/tech/freenix/hensbergen.html

Other applications are described in the following papers:
(其他应用在以下论文中有所描述：)

	* XCPU & Clustering
	  http://xcpu.org/papers/xcpu-talk.pdf
	  (XCPU 与集群)
	* KVMFS: control file system for KVM
	  http://xcpu.org/papers/kvmfs.pdf
	  (KVMFS：用于 KVM 的控制文件系统)
	* CellFS: A New Programming Model for the Cell BE
	  http://xcpu.org/papers/cellfs-talk.pdf
	  (CellFS：面向 Cell BE 的一种新编程模型)
	* PROSE I/O: Using 9p to enable Application Partitions
	  http://plan9.escet.urjc.es/iwp9/cready/PROSE_iwp9_2006.pdf
	  (PROSE I/O：使用 9p 来启用应用分区)
	* VirtFS: A Virtualization Aware File System pass-through
	  https://kernel.org/doc/ols/2010/ols2010-pages-109-120.pdf
	  (VirtFS：一种支持虚拟化的文件系统直通)

Usage
(用法)
=====

For remote file server::
(用于远程文件服务器：)

	mount -t 9p 10.10.1.2 /mnt/9

For Plan 9 From User Space applications (https://9fans.github.io/plan9port/)::
(用于 Plan 9 From User Space 应用程序(https://9fans.github.io/plan9port/)：)

	mount -t 9p `namespace`/acme /mnt/9 -o trans=unix,uname=$USER

For server running on QEMU host with virtio transport::
(用于在 QEMU 宿主机上运行、使用 virtio transport 的服务器：)

	mount -t 9p -o trans=virtio <mount_tag> /mnt/9

where mount_tag is the tag generated by the server to each of the exported
mount points. Each 9P export is seen by the client as a virtio device with an
associated "mount_tag" property. Available mount tags can be
seen by reading /sys/bus/virtio/drivers/9pnet_virtio/virtio<n>/mount_tag files.
(其中 mount_tag 是服务器为每个导出的挂载点所生成的标签。每个 9P 导出在客户端看来都是一个带有关联 "mount_tag" 属性的 virtio 设备。通过读取 /sys/bus/virtio/drivers/9pnet_virtio/virtio<n>/mount_tag 文件可以看到可用的挂载标签。)

USBG Usage
(USBG 用法)
==========

To mount a 9p FS on a USB Host accessible via the gadget at runtime::
(要在运行时通过 gadget 在可访问的 USB 主机上挂载 9p 文件系统：)

	mount -t 9p -o trans=usbg,aname=/path/to/fs <device> /mnt/9

To mount a 9p FS on a USB Host accessible via the gadget as root filesystem::
(要把 9p 文件系统经由 gadget 挂载为 USB 主机可访问的根文件系统：)

	root=<device> rootfstype=9p rootflags=trans=usbg,cache=loose,uname=root,access=0,dfltuid=0,dfltgid=0,aname=/path/to/rootfs

where <device> is the tag associated by the usb gadget transport.
It is defined by the configfs instance name.
(其中 <device> 是由 usb gadget transport 所关联的标签。它由 configfs 实例名定义。)

USBG Example
(USBG 示例)
============

The USB host exports a filesystem, while the gadget on the USB device
side makes it mountable.
(USB 主机导出一个文件系统，而 USB 设备一侧的 gadget 使它可以被挂载。)

Diod (9pfs server) and the forwarder are on the development host, where
the root filesystem is actually stored. The gadget is initialized during
boot (or later) on the embedded board. Then the forwarder will find it
on the USB bus and start forwarding requests.
(Diod(9pfs 服务器)和转发器位于开发主机上，根文件系统实际就存储在那里。gadget 在嵌入式板上于启动期间(或稍后)被初始化。随后转发器会在 USB 总线上找到它，并开始转发请求。)

In this case the 9p requests come from the device and are handled by the
host. The reason is that USB device ports are normally not available on
PCs, so a connection in the other direction would not work.
(在这种情形下，9p 请求来自设备端，由主机处理。原因在于 USB 设备端口通常在 PC 上并不可用，因此反方向的连接将无法工作。)

When using the usbg transport, for now there is no native usb host
service capable to handle the requests from the gadget driver. For
this we have to use the extra python tool p9_fwd.py from tools/usb.
(在使用 usbg transport 时，目前还没有能够处理来自 gadget 驱动程序请求的原生 usb host 服务。为此，我们必须使用 tools/usb 中额外的 python 工具 p9_fwd.py。)

Just start the 9pfs capable network server like diod/nfs-ganesha e.g.::
(只需启动一个支持 9pfs 的网络服务器，例如 diod/nfs-ganesha：)

        $ diod -f -n -d 0 -S -l 0.0.0.0:9999 -e $PWD

Optionally scan your bus if there are more then one usbg gadgets to find their path::
(可选地，如果有不止一个 usbg gadget，可以扫描你的总线以找到它们的路径：)

        $ python $kernel_dir/tools/usb/p9_fwd.py list

        Bus | Addr | Manufacturer     | Product          | ID        | Path
        --- | ---- | ---------------- | ---------------- | --------- | ----
          2 |   67 | unknown          | unknown          | 1d6b:0109 | 2-1.1.2
          2 |   68 | unknown          | unknown          | 1d6b:0109 | 2-1.1.3

Then start the python transport::
(然后启动 python transport：)

        $ python $kernel_dir/tools/usb/p9_fwd.py --path 2-1.1.2 connect -p 9999

After that the gadget driver can be used as described above.
(此后就可以如上文所述那样使用 gadget 驱动程序了。)

One use-case is to use it as an alternative to NFS root booting during
the development of embedded Linux devices.
(一个用例是在嵌入式 Linux 设备的开发过程中，用它来替代 NFS 根文件系统启动。)

Options
(选项)
=======

  ============= ===============================================================
  trans=name	select an alternative transport.  Valid options are
  		currently: (选择一种替代的 transport。当前有效的选项如下：)

			========  ============================================
			unix 	  specifying a named pipe mount point (指定一个命名管道挂载点)
			tcp	  specifying a normal TCP/IP connection (指定一个普通的 TCP/IP 连接)
			fd   	  used passed file descriptors for connection
                                  (see rfdno and wfdno) (使用传入的文件描述符进行连接(参见 rfdno 和 wfdno))
			virtio	  connect to the next virtio channel available
				  (from QEMU with trans_virtio module) (连接到下一个可用的 virtio 通道(来自带有 trans_virtio 模块的 QEMU))
			rdma	  connect to a specified RDMA channel (连接到指定的 RDMA 通道)
			usbg	  connect to a specified usb gadget channel (连接到指定的 usb gadget 通道)
			========  ============================================

  uname=name	user name to attempt mount as on the remote server.  The
  		server may override or ignore this value.  Certain user
		names may require authentication. (尝试在远程服务器上以某个用户名进行挂载时所用的用户名。服务器可能会覆盖或忽略该值。某些用户名可能需要身份验证。)

  aname=name	aname specifies the file tree to access when the server is
  		offering several exported file systems. (aname 指定当服务器提供多个导出文件系统时要访问的文件树。)

  cache=mode	specifies a caching policy.  By default, no caches are used.
		The mode can be specified as a bitmask or by using one of the
		preexisting common 'shortcuts'.
		The bitmask is described below: (unspecified bits are reserved) (指定一种缓存策略。默认情况下，不使用任何缓存。该模式可以用位掩码来指定，也可以使用现有的常用'快捷名称'之一。位掩码描述如下(未指定位为保留位)：)

			==========  ====================================================
			0b00000000  all caches disabled, mmap disabled (禁用所有缓存，禁用 mmap)
			0b00000001  file caches enabled (启用文件缓存)
			0b00000010  meta-data caches enabled (启用元数据缓存)
			0b00000100  writeback behavior (as opposed to writethrough) (回写行为(与直写 writethrough 相对))
			0b00001000  loose caches (no explicit consistency with server) (松散缓存(不与服务器显式保持一致))
			0b10000000  fscache enabled for persistent caching (启用 fscache 以进行持久缓存)
			==========  ====================================================

		The current shortcuts and their associated bitmask are: (当前的快捷名称及其对应的位掩码如下：)

			=========   ====================================================
			none        0b00000000 (no caching) (无缓存)
			readahead   0b00000001 (only read-ahead file caching) (仅预读文件缓存)
			mmap        0b00000101 (read-ahead + writeback file cache) (预读 + 回写文件缓存)
			loose       0b00001111 (non-coherent file and meta-data caches) (非一致的文件与元数据缓存)
			fscache     0b10001111 (persistent loose cache) (持久松散缓存)
			=========   ====================================================

		NOTE: only these shortcuts are tested modes of operation at the
		moment, so using other combinations of bit-patterns is not
		known to work.  Work on better cache support is in progress. (注意：目前只有这些快捷名称是经过测试的工作模式，因此使用其他位模式组合能否工作尚不可知。更好的缓存支持工作正在进行中。)

		IMPORTANT: loose caches (and by extension at the moment fscache)
		do not necessarily validate cached values on the server.  In other
		words changes on the server are not guaranteed to be reflected
		on the client system.  Only use this mode of operation if you
		have an exclusive mount and the server will not modify the
		filesystem underneath you. (重要：loose 缓存(以及目前与之相伴的 fscache)不一定会在服务器上验证缓存值。换句话说，不保证服务器上的更改会反映到客户端系统上。只有在你的挂载是独占的、且服务器不会在你脚下修改文件系统时，才使用这种工作模式。)

  debug=n	specifies debug level.  The debug level is a bitmask. (指定调试级别。调试级别是一个位掩码。)

			=====   ================================
			0x01    display verbose error messages (显示详细的错误消息)
			0x02    developer debug (DEBUG_CURRENT) (开发者调试(DEBUG_CURRENT))
			0x04    display 9p trace (显示 9p 跟踪)
			0x08    display VFS trace (显示 VFS 跟踪)
			0x10    display Marshalling debug (显示编组(Marshalling)调试信息)
			0x20    display RPC debug (显示 RPC 调试信息)
			0x40    display transport debug (显示 transport 调试信息)
			0x80    display allocation debug (显示分配调试信息)
			0x100   display protocol message debug (显示协议消息调试信息)
			0x200   display Fid debug (显示 Fid 调试信息)
			0x400   display packet debug (显示数据包调试信息)
			0x800   display fscache tracing debug (显示 fscache 跟踪调试信息)
			=====   ================================

  rfdno=n	the file descriptor for reading with trans=fd (用于 trans=fd 进行读取的文件描述符)

  wfdno=n	the file descriptor for writing with trans=fd (用于 trans=fd 进行写入的文件描述符)

  msize=n	the number of bytes to use for 9p packet payload (用于 9p 数据包有效载荷的字节数)

  port=n	port to connect to on the remote server (要连接到的远程服务器端口)

  noextend	force legacy mode (no 9p2000.u or 9p2000.L semantics) (强制使用传统模式(没有 9p2000.u 或 9p2000.L 语义))

  version=name	Select 9P protocol version. Valid options are: (选择 9P 协议版本。有效选项如下：)

			========        ==============================
			9p2000          Legacy mode (same as noextend) (传统模式(与 noextend 相同))
			9p2000.u        Use 9P2000.u protocol (使用 9P2000.u 协议)
			9p2000.L        Use 9P2000.L protocol (使用 9P2000.L 协议)
			========        ==============================

  dfltuid	attempt to mount as a particular uid (尝试以某个特定的 uid 进行挂载)

  dfltgid	attempt to mount with a particular gid (尝试以某个特定的 gid 进行挂载)

  afid		security channel - used by Plan 9 authentication protocols (安全通道——由 Plan 9 身份验证协议使用)

  nodevmap	do not map special files - represent them as normal files.
  		This can be used to share devices/named pipes/sockets between
		hosts.  This functionality will be expanded in later versions. (不映射特殊文件——把它们表示为普通文件。这可以用来在主机之间共享设备/命名管道/套接字。此功能将在后续版本中得到扩展。)

  directio	bypass page cache on all read/write operations (在所有读/写操作上绕过页缓存)

  ignoreqv	ignore qid.version==0 as a marker to ignore cache (不把 qid.version==0 当作忽略缓存的标记)

  noxattr	do not offer xattr functions on this mount. (在此挂载上不提供 xattr 功能。)

  access	there are four access modes. (有四种访问模式。)
			user
				if a user tries to access a file on v9fs
			        filesystem for the first time, v9fs sends an
			        attach command (Tattach) for that user.
				This is the default mode. (如果某个用户第一次尝试访问 v9fs 文件系统上的文件，v9fs 会为该用户发送一条 attach 命令(Tattach)。这是默认模式。)
			<uid>
				allows only user with uid=<uid> to access
				the files on the mounted filesystem (只允许 uid=<uid> 的用户访问已挂载文件系统上的文件)
			any
				v9fs does single attach and performs all
				operations as one user (v9fs 执行单次 attach，并以一个用户的身份执行所有操作)
			clien
				 ACL based access check on the 9p client
			         side for access validation (在 9p 客户端一侧进行基于 ACL 的访问检查以验证访问权限)

  cachetag	cache tag to use the specified persistent cache.
		cache tags for existing cache sessions can be listed at
		/sys/fs/9p/caches. (applies only to cache=fscache) (使用指定持久缓存的缓存标签。现有缓存会话的缓存标签可以在 /sys/fs/9p/caches 处列出。(仅适用于 cache=fscache))
  ============= ===============================================================

Behavior
(行为)
========

This section aims at describing 9p 'quirks' that can be different
from a local filesystem behaviors.
(本节旨在描述 9p 的一些可能与本地文件系统行为不同的'怪癖'。)

 - Setting O_NONBLOCK on a file will make client reads return as early
   as the server returns some data instead of trying to fill the read
   buffer with the requested amount of bytes or end of file is reached.
   (对文件设置 O_NONBLOCK 后，只要服务器返回了一些数据，客户端的读取就会尽早返回，而不是试图把读缓冲填满所请求的字节数，也不必等到到达文件末尾。)
