==========================================================================
Kernel Guidelines for Tool-Generated Content(内核对工具生成内容的指导原则)
==========================================================================

Purpose(目的)
=============

Kernel contributors have been using tooling to generate contributions
for a long time. These tools can increase the volume of contributions.
At the same time, reviewer and maintainer bandwidth is a scarce
resource. Understanding which portions of a contribution come from
humans versus tools is helpful to maintain those resources and keep
kernel development healthy.
(内核贡献者使用工具来生成贡献内容已经很久了。这些工具可以增加贡献的
数量。与此同时，审查者和维护者的精力是一种稀缺资源。弄清一项贡献中
哪些部分出自人类、哪些出自工具，有助于守护这些资源并保持内核开发的
健康运转。)

The goal here is to clarify community expectations around tools. This
lets everyone become more productive while also maintaining high
degrees of trust between submitters and reviewers.
(本文的目标是澄清社区对工具的期望。这让每个人都能更具生产力，同时
在提交者与审查者之间保持高度的信任。)

Out of Scope(不适用范围)
========================

These guidelines do not apply to tools that make trivial tweaks to
preexisting content. Nor do they pertain to tooling that helps with
menial tasks. Some examples:
(这些指导原则不适用于对既有内容做琐碎微调的工具，也不涉及帮助完成
杂务的工具。一些例子：)

 - Spelling and grammar fix ups, like rephrasing to imperative voice
   (拼写和语法修正，比如改写为祈使语气)
 - Typing aids like identifier completion, common boilerplate or
   trivial pattern completion
   (打字辅助，例如标识符补全、常见样板代码或琐碎的模式补全)
 - Purely mechanical transformations like variable renaming
   (纯机械变换，例如变量重命名)
 - Reformatting, like running Lindent, ``clang-format`` or
   ``rust-fmt``
   (重新格式化，例如运行 Lindent、``clang-format`` 或 ``rust-fmt``)

Even whenever your tool use is out of scope, you should still always
consider if it would help reviewing your contribution if the reviewer
knows about the tool that you used.
(即便你的工具使用不在上述范围内，你仍然应当始终考虑：如果审查者
了解你所使用的工具，是否会有助于审查你的贡献。)

In Scope(适用范围)
==================

These guidelines apply when a meaningful amount of content in a kernel
contribution was not written by a person in the Signed-off-by chain,
but was instead created by a tool.
(当内核贡献中有相当数量的内容并非由 Signed-off-by 链条上的人所写，
而是由工具生成时，这些指导原则即适用。)

Detection of a problem and testing the fix for it is also part of the
development process; if a tool was used to find a problem addressed by
a change, that should be noted in the changelog. This not only gives
credit where it is due, it also helps fellow developers find out about
these tools.
(发现问题以及测试对它的修复也是开发过程的一部分；如果使用了工具来
发现某项修改所解决的问题，应当在变更日志中注明。这不仅让功劳归于
应得之人，也能帮助其他开发者了解这些工具。)

Some examples:
(一些例子：)
 - Any tool-suggested fix such as ``checkpatch.pl --fix``
   (任何由工具建议的修改，例如 ``checkpatch.pl --fix``)
 - Coccinelle scripts
   (Coccinelle 脚本)
 - A chatbot generated a new function in your patch to sort list entries.
   (聊天机器人在你的补丁中生成了一个对链表条目排序的新函数。)
 - A .c file in the patch was originally generated by a coding
   assistant but cleaned up by hand.
   (补丁中的某个 .c 文件最初由编程助手生成，随后经人工清理。)
 - The changelog was generated by handing the patch to a generative AI
   tool and asking it to write the changelog.
   (变更日志是把补丁交给生成式 AI 工具并让它撰写而生成的。)
 - The changelog was translated from another language.
   (变更日志是从另一种语言翻译过来的。)

If in doubt, choose transparency and assume these guidelines apply to
your contribution.
(如有疑问，请选择透明，并假定这些指导原则适用于你的贡献。)

Guidelines(指导原则)
====================

First, read the Developer's Certificate of Origin:
Documentation/process/submitting-patches.rst. Its rules are simple
and have been in place for a long time. They have covered many
tool-generated contributions. Ensure that you understand your entire
submission and are prepared to respond to review comments.
(首先，阅读开发者来源证书：Documentation/process/submitting-patches.rst。
它的规则很简单，而且已经实行了很长时间，早已覆盖了许多由工具生成的
贡献。请确保你理解自己的全部提交内容，并准备好回应审查意见。)

Second, when making a contribution, be transparent about the origin of
content in cover letters and changelogs. You can be more transparent
by adding information like this:
(其次，在提交贡献时，要在附信和变更日志中公开内容的来源。可以通过
添加如下信息来提高透明度：)

 - What tools were used?
   (使用了哪些工具？)
 - The input to the tools you used, like the Coccinelle source script.
   (你所使用工具的输入，例如 Coccinelle 源脚本。)
 - If code was largely generated from a single or short set of
   prompts, include those prompts. For longer sessions, include a
   summary of the prompts and the nature of resulting assistance.
   (如果代码主要由一条或少数几条提示词生成，请附上这些提示词。对于
   更长的会话，请附上提示词的摘要以及所得帮助的性质。)
 - Which portions of the content were affected by that tool?
   (内容中哪些部分受到了该工具的影响？)
 - How is the submission tested and what tools were used to test the
   fix?
   (提交是如何测试的？测试修复时使用了哪些工具？)

As with all contributions, individual maintainers have discretion to
choose how they handle the contribution. For example, they might:
(与所有贡献一样，各位维护者可自行斟酌如何处理该贡献。例如，他们
可能会：)

 - Treat it just like any other contribution.
   (像对待其他贡献一样对待它。)
 - Reject it outright.
   (直接拒绝。)
 - Treat the contribution specially, for example, asking for extra
   testing, reviewing with extra scrutiny, or reviewing at a lower
   priority than human-generated content.
   (对该贡献做特殊处理，例如要求额外测试、以更严格的标准审查，或以
   低于人工生成内容的优先级进行审查。)
 - Ask for some other special steps, like asking the contributor to
   elaborate on how the tool or model was trained.
   (要求其他特殊步骤，例如要求贡献者详细说明该工具或模型是如何训练
   出来的。)
 - Ask the submitter to explain in more detail about the contribution
   so that the maintainer can be assured that the submitter fully
   understands how the code works.
   (要求提交者更详细地解释该贡献，使维护者能够确信提交者完全理解
   代码的工作原理。)
 - Suggest a better prompt instead of suggesting specific code changes.
   (建议一个更好的提示词，而不是建议具体的代码修改。)

If tools permit you to generate a contribution automatically, expect
additional scrutiny in proportion to how much of it was generated.
(如果工具允许你自动生成贡献，那么生成部分越多，预期受到的额外审查
就越严格。)

As with the output of any tooling, the result may be incorrect or
inappropriate. You are expected to understand and to be able to defend
everything you submit. If you are unable to do so, then do not submit
the resulting changes.
(与任何工具的输出一样，结果可能不正确或不合适。你应当理解并能够为
你提交的一切内容辩护。如果你做不到，就不要提交这些修改。)

If you do so anyway, maintainers are entitled to reject your series
without detailed review.
(如果你执意提交，维护者有权不经详细审查就直接拒绝你的补丁系列。)
