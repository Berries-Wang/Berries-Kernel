How the development process works(开发过程如何运作)
===================================================

Linux kernel development in the early 1990s was a pretty loose affair,
with relatively small numbers of users and developers involved.  With a
user base in the millions and with some 2,000 developers involved over the
course of one year, the kernel has since had to evolve a number of
processes to keep development happening smoothly.  A solid understanding of
how the process works is required in order to be an effective part of it.
(上世纪 90 年代初的 Linux 内核开发是相当松散的事务，涉及的用户和开发者数量
相对较少。如今用户基数达数百万，一年当中约有 2,000 名开发者参与，因此内核
不得不演化出一系列流程来保持开发顺利进行。要有效地参与其中，必须对开发过程
的运作方式有扎实的理解。)

The big picture(总体图景)
-------------------------

The Linux kernel uses a loosely time-based, rolling release development
model.  A new major kernel release (which we will call, as an example, 9.x)
[1]_ happens every two or three months, which comes with new features,
internal API changes, and more. A typical release can contain about 13,000
changesets with changes to several hundred thousand lines of code. Recent
releases, along with their dates, can be found at `Wikipedia
<https://en.wikipedia.org/wiki/Linux_kernel_version_history>`_.
(Linux 内核采用松散的基于时间的滚动发布开发模型。一个新的主内核版本 (举例
来说，我们称之为 9.x) [1]_ 每两三个月发布一次，带来新特性、内部 API 变更等。
一个典型的版本可以包含约 13,000 个变更集，涉及数十万行代码的改动。近期版本
及其日期可在 `Wikipedia
<https://en.wikipedia.org/wiki/Linux_kernel_version_history>`_ 查到。)

.. [1] Strictly speaking, the Linux kernel does not use semantic versioning
       number scheme, but rather the 9.x pair identifies major release
       version as a whole number. For each release, x is incremented,
       but 9 is incremented only if x is deemed large enough (e.g.
       Linux 5.0 is released following Linux 4.20).
       (严格来说，Linux 内核并不使用语义化版本编号方案，9.x 这一对数字是把
       主版本作为一个整体编号来标识。对于每个版本，x 递增；只有当 x 被认为
       足够大时 9 才递增 (例如 Linux 4.20 之后发布的是 Linux 5.0)。)

A relatively straightforward discipline is followed with regard to the
merging of patches for each release.  At the beginning of each development
cycle, the "merge window" is said to be open.  At that time, code which is
deemed to be sufficiently stable (and which is accepted by the development
community) is merged into the mainline kernel.  The bulk of changes for a
new development cycle (and all of the major changes) will be merged during
this time, at a rate approaching 1,000 changes ("patches," or "changesets")
per day.
(对于每个版本的补丁合入，遵循的是一套相对明确的纪律。在每个开发周期开始时，
"合并窗口" (merge window) 被称为打开。此时，被认为足够稳定 (且为开发社区所
接受) 的代码会被合入主线内核。新开发周期的大部分改动 (以及所有重大改动) 都
会在这段时间内合入，速度接近每天 1,000 个变更 ("补丁" 或 "变更集")。)

(As an aside, it is worth noting that the changes integrated during the
merge window do not come out of thin air; they have been collected, tested,
and staged ahead of time.  How that process works will be described in
detail later on).
(附带一提，值得注意的是，合并窗口期间合入的改动并非凭空而来；它们早已被
收集、测试并提前排好队。这一过程的运作方式将在后文详细描述。)

The merge window lasts for approximately two weeks.  At the end of this
time, Linus Torvalds will declare that the window is closed and release the
first of the "rc" kernels.  For the kernel which is destined to be 9.x,
for example, the release which happens at the end of the merge window will
be called 9.x-rc1.  The -rc1 release is the signal that the time to
merge new features has passed, and that the time to stabilize the next
kernel has begun.
(合并窗口持续约两周。在这段时间结束时，Linus Torvalds 会宣布窗口关闭，并
发布第一个 "rc" 内核。例如，对于注定成为 9.x 的内核，合并窗口结束时发布的
版本将被称为 9.x-rc1。-rc1 发布是一个信号：合入新特性的时间已经过去，稳定
下一个内核的时间开始了。)

Over the next six to ten weeks, only patches which fix problems should be
submitted to the mainline.  On occasion a more significant change will be
allowed, but such occasions are rare; developers who try to merge new
features outside of the merge window tend to get an unfriendly reception.
As a general rule, if you miss the merge window for a given feature, the
best thing to do is to wait for the next development cycle.  (An occasional
exception is made for drivers for previously-unsupported hardware; if they
touch no in-tree code, they cannot cause regressions and should be safe to
add at any time).
(在接下来的六到十周内，只有修复问题的补丁才应提交到主线。偶尔也会允许更
重大的改动，但这种情况很少见；试图在合并窗口之外合入新特性的开发者往往会
受到不友好的对待。一般而言，如果错过了某个特性的合并窗口，最好的做法是等
下一个开发周期。(对以前不支持的硬件的驱动偶尔会有例外；如果它们不触碰树内
代码，就不可能造成回归，在任何时候添加都应该是安全的。))

As fixes make their way into the mainline, the patch rate will slow over
time.  Linus releases new -rc kernels about once a week; a normal series
will get up to somewhere between -rc6 and -rc9 before the kernel is
considered to be sufficiently stable and the final release is made.
At that point the whole process starts over again.
(随着修复进入主线，补丁速率会随时间放缓。Linus 大约每周发布一个新的 -rc
内核；一个正常的系列会走到 -rc6 到 -rc9 之间的某处，内核才被认为足够稳定
并发布最终版本。到那时，整个过程又从头开始。)

As an example, here is how the 5.4 development cycle went (all dates in
2019):
(例如，下面是 5.4 开发周期的过程 (日期均为 2019 年)：)

	==============  ===============================
	September 15	5.3 stable release(5.3 稳定版发布)
	September 30	5.4-rc1, merge window closes(5.4-rc1，合并窗口关闭)
	October 6	5.4-rc2
	October 13	5.4-rc3
	October 20	5.4-rc4
	October 27	5.4-rc5
	November 3	5.4-rc6
	November 10	5.4-rc7
	November 17	5.4-rc8
	November 24	5.4 stable release(5.4 稳定版发布)
	==============  ===============================

How do the developers decide when to close the development cycle and create
the stable release?  The most significant metric used is the list of
regressions from previous releases.  No bugs are welcome, but those which
break systems which worked in the past are considered to be especially
serious.  For this reason, patches which cause regressions are looked upon
unfavorably and are quite likely to be reverted during the stabilization
period.
(开发者如何决定何时结束开发周期并创建稳定版本？使用的最重要指标是自先前
版本以来的回归 (regression) 列表。没有 bug 是受欢迎的，但那些破坏了过去
正常工作的系统的 bug 被认为尤其严重。因此，导致回归的补丁不受待见，并且在
稳定期内很可能被回退。)

The developers' goal is to fix all known regressions before the stable
release is made.  In the real world, this kind of perfection is hard to
achieve; there are just too many variables in a project of this size.
There comes a point where delaying the final release just makes the problem
worse; the pile of changes waiting for the next merge window will grow
larger, creating even more regressions the next time around.  So most kernels
go out with a handful of known regressions, though, hopefully, none of them
are serious.
(开发者的目标是在发布稳定版本之前修复所有已知回归。在现实世界中，这种完美
很难达到；这个规模的项目变量太多。到了某个节点，拖延最终发布只会让问题更
糟糕：等待下一个合并窗口的改动堆积会越来越大，下一次制造出更多回归。所以
大多数内核发布时都带着少量已知回归，不过希望它们都不严重。)

Once a stable release is made, its ongoing maintenance is passed off to the
"stable team," currently consists of Greg Kroah-Hartman and Sasha Levin. The
stable team will release occasional updates to the stable release using the
9.x.y numbering scheme.
(稳定版本发布后，其后续维护工作移交给 "稳定团队"——目前由 Greg
Kroah-Hartman 和 Sasha Levin 组成。稳定团队会使用 9.x.y 编号方案为稳定版本
发布不定期更新。)

To be considered for an update release, a patch must (1) fix a significant
bug, and (2) already be merged into the mainline for the next development
kernel. Kernels will typically receive stable updates for a little more
than one development cycle past their initial release. So, for example, the
5.2 kernel's history looked like this (all dates in 2019):
(要被考虑作为更新版本发布，补丁必须 (1) 修复一个重要的 bug，并且 (2) 已经
被合入下一个开发内核的主线。内核通常会在初始发布之后的一个多开发周期内
持续收到稳定更新。例如，5.2 内核的历史如下 (日期均为 2019 年)：)

	==============  ===============================
	July 7		5.2 stable release(5.2 稳定版发布)
	July 14		5.2.1
	July 21		5.2.2
	July 26		5.2.3
	July 28		5.2.4
	July 31  	5.2.5
	...		...
	October 11	5.2.21
	==============  ===============================

5.2.21 was the final stable update of the 5.2 release.
(5.2.21 是 5.2 版本的最后一个稳定更新。)

Some kernels are designated "long term" kernels; they will receive support
for a longer period.  Please refer to the following link for the list of active
long term kernel versions and their maintainers:
(一些内核被指定为 "长期" (long term) 内核；它们将获得更长时间的支持。当前
活跃的长期内核版本及其维护者的列表请参阅以下链接：)

	https://www.kernel.org/category/releases.html

The selection of a kernel for long-term support is purely a matter of a
maintainer having the need and the time to maintain that release.  There
are no known plans for long-term support for any specific upcoming
release.
(选择某个内核进行长期支持，纯粹取决于维护者是否有维护该版本的需求和时间。
对于任何具体的即将发布的版本，目前没有已知的长期支持计划。)


The lifecycle of a patch(补丁的生命周期)
----------------------------------------


The lifecycle of a patch
------------------------

Patches do not go directly from the developer's keyboard into the mainline
kernel.  There is, instead, a somewhat involved (if somewhat informal)
process designed to ensure that each patch is reviewed for quality and that
each patch implements a change which is desirable to have in the mainline.
This process can happen quickly for minor fixes, or, in the case of large
and controversial changes, go on for years.  Much developer frustration
comes from a lack of understanding of this process or from attempts to
circumvent it.
(补丁不会直接从开发者的键盘进入主线内核。相反，存在一个 (虽然不那么正式但)
颇为复杂的过程，旨在确保每个补丁都经过质量审查，并且每个补丁实现的改动是
主线所想要的。对于小修复，这个过程可能很快；而对于大型且有争议的改动，则
可能持续数年。开发者的许多挫败感来自于对这一过程缺乏了解，或试图绕过它。)

In the hopes of reducing that frustration, this document will describe how
a patch gets into the kernel.  What follows below is an introduction which
describes the process in a somewhat idealized way.  A much more detailed
treatment will come in later sections.
(为了减少这种挫败感，本文档将描述补丁是如何进入内核的。下文是一个以 somewhat
理想化的方式描述该过程的介绍。更详细的论述将在后面的章节给出。)

The stages that a patch goes through are, generally:
(补丁通常要经历以下几个阶段：)

 - Design.  This is where the real requirements for the patch - and the way
   those requirements will be met - are laid out.  Design work is often
   done without involving the community, but it is better to do this work
   in the open if at all possible; it can save a lot of time redesigning
   things later.
   (设计。在这里列出补丁的真正需求——以及满足这些需求的方式。设计工作常常
   在不涉及社区的情况下完成，但只要可能，最好公开进行；这可以节省日后重新
   设计的大量时间。)

 - Early review.  Patches are posted to the relevant mailing list, and
   developers on that list reply with any comments they may have.  This
   process should turn up any major problems with a patch if all goes
   well.
   (早期审查。补丁被张贴到相关邮件列表上，该列表上的开发者会回复他们可能
   有的任何意见。如果一切顺利，这个过程应当能发现补丁的任何重大问题。)

 - Wider review.  When the patch is getting close to ready for mainline
   inclusion, it should be accepted by a relevant subsystem maintainer -
   though this acceptance is not a guarantee that the patch will make it
   all the way to the mainline.  The patch will show up in the maintainer's
   subsystem tree and into the -next trees (described below).  When the
   process works, this step leads to more extensive review of the patch and
   the discovery of any problems resulting from the integration of this
   patch with work being done by others.
   (更广泛的审查。当补丁接近可以合入主线时，它应当被相关的子系统维护者
   接受——尽管这种接受并不保证补丁最终会进入主线。补丁将出现在维护者的
   子系统树以及 -next 树中 (见下文)。当这一过程运转良好时，这一步会带来对
   补丁更广泛的审查，并发现该补丁与他人的工作集成后可能产生的问题。)

-  Please note that most maintainers also have day jobs, so merging
   your patch may not be their highest priority.  If your patch is
   getting feedback about changes that are needed, you should either
   make those changes or justify why they should not be made.  If your
   patch has no review complaints but is not being merged by its
   appropriate subsystem or driver maintainer, you should be persistent
   in updating the patch to the current kernel so that it applies cleanly
   and keep sending it for review and merging.
   (请注意，大多数维护者也有本职工作，因此合并你的补丁可能不是他们的头等
   优先级。如果你的收到的反馈是关于需要做的修改，你要么做出这些修改，要么
   说明为什么不应当做。如果你的补丁没有受到审查方面的抱怨，却没有被相应的
   子系统或驱动维护者合并，你应当坚持不懈地把补丁更新到当前内核，使其能够
   干净地套用，并持续提交以供审查与合并。)

 - Merging into the mainline.  Eventually, a successful patch will be
   merged into the mainline repository managed by Linus Torvalds.  More
   comments and/or problems may surface at this time; it is important that
   the developer be responsive to these and fix any issues which arise.
   (合入主线。最终，成功的补丁会被合入由 Linus Torvalds 管理的主线仓库。
   此时可能出现更多意见和/或问题；开发者对这些做出回应并修复出现的任何
   问题非常重要。)

 - Stable release.  The number of users potentially affected by the patch
   is now large, so, once again, new problems may arise.
   (稳定发布。该补丁可能影响的用户数量现在很大，所以同样可能出现新问题。)

 - Long-term maintenance.  While it is certainly possible for a developer
   to forget about code after merging it, that sort of behavior tends to
   leave a poor impression in the development community.  Merging code
   eliminates some of the maintenance burden, in that others will fix
   problems caused by API changes.  But the original developer should
   continue to take responsibility for the code if it is to remain useful
   in the longer term.
   (长期维护。开发者当然可能在合并代码后就把它抛在脑后，但这种行为往往
   会给开发社区留下不好的印象。合并代码消除了部分维护负担，因为其他人会
   修复由 API 变化引起的问题。但如果代码要长期保持有用，原作者应当继续
   对它负责。)

One of the largest mistakes made by kernel developers (or their employers)
is to try to cut the process down to a single "merging into the mainline"
step.  This approach invariably leads to frustration for everybody
involved.
(内核开发者 (或他们的雇主) 犯下的最大错误之一，是试图把整个过程压缩成单一
的 "合入主线" 一步。这种做法必然让所有相关者都感到挫败。)

How patches get into the Kernel(补丁如何进入内核)
-------------------------------------------------

There is exactly one person who can merge patches into the mainline kernel
repository: Linus Torvalds. But, for example, of the over 9,500 patches
which went into the 2.6.38 kernel, only 112 (around 1.3%) were directly
chosen by Linus himself. The kernel project has long since grown to a size
where no single developer could possibly inspect and select every patch
unassisted. The way the kernel developers have addressed this growth is
through the use of a lieutenant system built around a chain of trust.
(有且只有一个人能够把补丁合入主线内核仓库：Linus Torvalds。但是，例如，在
进入 2.6.38 内核的 9,500 多个补丁中，只有 112 个 (约 1.3%) 是 Linus 本人
直接挑选的。内核项目的规模早已增长到没有任何单个开发者能够独自审查并挑选
每一个补丁的地步。内核开发者应对这种增长的方式，是使用一个围绕信任链构建
的副官 (lieutenant) 体系。)

The kernel code base is logically broken down into a set of subsystems:
networking, specific architecture support, memory management, video
devices, etc.  Most subsystems have a designated maintainer, a developer
who has overall responsibility for the code within that subsystem.  These
subsystem maintainers are the gatekeepers (in a loose way) for the portion
of the kernel they manage; they are the ones who will (usually) accept a
patch for inclusion into the mainline kernel.
(内核代码库在逻辑上被分解为一组子系统：网络、特定架构支持、内存管理、视频
设备等。大多数子系统都有指定的维护者——一位对该子系统内的代码负全责的开发
者。这些子系统维护者是 (松散意义上的) 其所管理部分的守门人；他们就是通常
会接受补丁以合入主线内核的人。)

Subsystem maintainers each manage their own version of the kernel source
tree, usually (but certainly not always) using the git source management
tool.  Tools like git (and related tools like quilt or mercurial) allow
maintainers to track a list of patches, including authorship information
and other metadata.  At any given time, the maintainer can identify which
patches in his or her repository are not found in the mainline.
(子系统维护者各自管理自己的一份内核源码树副本，通常 (但肯定不总是) 使用 git
源码管理工具。git 之类的工具 (以及 quilt、mercurial 等相关工具) 让维护者
能够跟踪补丁列表，包括作者信息和其他元数据。在任何给定时刻，维护者都可以
识别出其仓库中哪些补丁不在主线中。)

When the merge window opens, top-level maintainers will ask Linus to "pull"
the patches they have selected for merging from their repositories.  If
Linus agrees, the stream of patches will flow up into his repository,
becoming part of the mainline kernel.  The amount of attention that Linus
pays to specific patches received in a pull operation varies.  It is clear
that, sometimes, he looks quite closely.  But, as a general rule, Linus
trusts the subsystem maintainers to not send bad patches upstream.
(当合并窗口打开时，顶层维护者会请求 Linus 从他们的仓库 "pull" (拉取) 他们
挑选出来用于合并的补丁。如果 Linus 同意，补丁流就会向上流入他的仓库，成为
主线内核的一部分。Linus 对 pull 操作中收到的特定补丁的关注程度各不相同。
显然，有时他看得非常仔细。但作为一般规则，Linus 信任子系统维护者不会向上游
发送坏的补丁。)

Subsystem maintainers, in turn, can pull patches from other maintainers.
For example, the networking tree is built from patches which accumulated
first in trees dedicated to network device drivers, wireless networking,
etc.  This chain of repositories can be arbitrarily long, though it rarely
exceeds two or three links.  Since each maintainer in the chain trusts
those managing lower-level trees, this process is known as the "chain of
trust."
(子系统维护者反过来也可以从其他维护者那里 pull 补丁。例如，网络树是由先在
网络设备驱动、无线网络等专用树中积累的补丁构建的。这条仓库链可以任意长，
不过很少超过两三环。由于链上的每个维护者都信任管理更低层树的人，这个过程
被称为 "信任链" (chain of trust)。)

Clearly, in a system like this, getting patches into the kernel depends on
finding the right maintainer.  Sending patches directly to Linus is not
normally the right way to go.
(显然，在这样的系统中，让补丁进入内核取决于找到正确的维护者。直接把补丁
发给 Linus 通常不是正确的做法。)


Next trees(-next 树)
--------------------


Next trees
----------

The chain of subsystem trees guides the flow of patches into the kernel,
but it also raises an interesting question: what if somebody wants to look
at all of the patches which are being prepared for the next merge window?
Developers will be interested in what other changes are pending to see
whether there are any conflicts to worry about; a patch which changes a
core kernel function prototype, for example, will conflict with any other
patches which use the older form of that function.  Reviewers and testers
want access to the changes in their integrated form before all of those
changes land in the mainline kernel.  One could pull changes from all of
the interesting subsystem trees, but that would be a big and error-prone
job.
(子系统树链引导着补丁流入内核，但它也引出一个有趣的问题：如果有人想查看
正在为下一个合并窗口准备的所有补丁怎么办？开发者会关心其他哪些改动悬而未
决，以便了解是否有需要担心的冲突；例如，改变核心内核函数原型的补丁会与
任何使用该函数旧形式的补丁冲突。审查者和测试者希望在所有这些改动落入主线
内核之前，能以其集成后的形式获取它们。可以从所有感兴趣的子系统树 pull
改动，但那将是一项庞大且容易出错的工作。)

The answer comes in the form of -next trees, where subsystem trees are
collected for testing and review.  The older of these trees, maintained by
Andrew Morton, is called "-mm" (for memory management, which is how it got
started).  The -mm tree integrates patches from a long list of subsystem
trees; it also has some patches aimed at helping with debugging.
(答案的形式是 -next 树——收集各子系统树以供测试和审查的树。其中较老的一棵
由 Andrew Morton 维护，称为 "-mm" (得名于内存管理，它正是由此起步的)。
-mm 树整合来自一长串子系统树的补丁；它还包含一些旨在辅助调试的补丁。)

Beyond that, -mm contains a significant collection of patches which have
been selected by Andrew directly.  These patches may have been posted on a
mailing list, or they may apply to a part of the kernel for which there is
no designated subsystem tree.  As a result, -mm operates as a sort of
subsystem tree of last resort; if there is no other obvious path for a
patch into the mainline, it is likely to end up in -mm.  Miscellaneous
patches which accumulate in -mm will eventually either be forwarded on to
an appropriate subsystem tree or be sent directly to Linus.  In a typical
development cycle, approximately 5-10% of the patches going into the
mainline get there via -mm.
(除此之外，-mm 还包含由 Andrew 直接挑选的大量补丁。这些补丁可能张贴在邮件
列表上，也可能适用于内核中没有指定子系统树的部分。因此，-mm 充当一种最后
手段的子系统树；如果一个补丁没有其他明显的路径进入主线，它很可能最终进入
-mm。累积在 -mm 中的杂项补丁最终要么被转发到合适的子系统树，要么直接发给
Linus。在典型的开发周期中，进入主线的补丁约有 5-10% 是经由 -mm 到达的。)

The current -mm patch is available in the "mmotm" (-mm of the moment)
directory at:

	https://www.ozlabs.org/~akpm/mmotm/

Use of the MMOTM tree is likely to be a frustrating experience, though;
there is a definite chance that it will not even compile.
(当前的 -mm 补丁可在 "mmotm" (-mm of the moment，当下 -mm) 目录中获取。
不过，使用 MMOTM 树很可能是一段令人沮丧的经历；它完全有可能连编译都通不过。)

The primary tree for next-cycle patch merging is linux-next, maintained by
Mark Brown.  The linux-next tree is, by design, a snapshot of what
the mainline is expected to look like after the next merge window closes.
Linux-next trees are announced on the linux-kernel and linux-next mailing
lists when they are assembled; they can be downloaded from:
(用于下一周期补丁合并的主要树是 linux-next，由 Mark Brown 维护。linux-next
树按设计就是下一个合并窗口关闭后主线预期模样的快照。linux-next 树在组装
完成时会在 linux-kernel 和 linux-next 邮件列表上宣布；可以从以下位置下载：)

	https://www.kernel.org/pub/linux/kernel/next/

Linux-next has become an integral part of the kernel development process;
all patches merged during a given merge window should really have found
their way into linux-next some time before the merge window opens.
( linux-next 已成为内核开发过程中不可或缺的一部分；在给定合并窗口中合并的
所有补丁，其实都应当在合并窗口打开之前的某个时刻就已经进入 linux-next。)


Staging trees(staging 树)
-------------------------


Staging trees
-------------

The kernel source tree contains the drivers/staging/ directory, where
many sub-directories for drivers or filesystems that are on their way to
being added to the kernel tree live.  They remain in drivers/staging while
they still need more work; once complete, they can be moved into the
kernel proper.  This is a way to keep track of drivers that aren't
up to Linux kernel coding or quality standards, but people may want to use
them and track development.
(内核源码树中包含 drivers/staging/ 目录，许多正在走向被加入内核树之路的
驱动程序或文件系统的子目录就驻留在这里。当它们还需要更多工作时，会留在
drivers/staging 中；一旦完成，就可以移入正式的内核。这是一种跟踪未达到
Linux 内核编码或质量标准的驱动程序的方式，不过人们可能想使用它们并跟踪其
开发。)

Greg Kroah-Hartman currently maintains the staging tree.  Drivers that
still need work are sent to him, with each driver having its own
subdirectory in drivers/staging/.  Along with the driver source files, a
TODO file should be present in the directory as well.  The TODO file lists
the pending work that the driver needs for acceptance into the kernel
proper, as well as a list of people that should be Cc'd for any patches to
the driver.  Current rules require that drivers contributed to staging
must, at a minimum, compile properly.
( staging 树目前由 Greg Kroah-Hartman 维护。仍需改进的驱动程序发给他，每个
驱动在 drivers/staging/ 中有自己的子目录。除了驱动源码文件之外，目录中还
应当有一个 TODO 文件。TODO 文件列出该驱动在被正式内核接受之前尚需完成的
工作，以及针对该驱动的任何补丁都应当抄送 (Cc) 的人员列表。现行规则要求，
贡献到 staging 的驱动至少必须能够正确编译。)

Staging can be a relatively easy way to get new drivers into the mainline
where, with luck, they will come to the attention of other developers and
improve quickly.  Entry into staging is not the end of the story, though;
code in staging which is not seeing regular progress will eventually be
removed.  Distributors also tend to be relatively reluctant to enable
staging drivers.  So staging is, at best, a stop on the way toward becoming
a proper mainline driver.
( staging 可以是让新驱动进入主线的一条相对容易的途径，运气好的话，它们会
引起其他开发者的注意并快速改进。不过，进入 staging 并不是故事的结束；
staging 中没有持续进展的代码最终会被移除。发行版也往往不太愿意启用 staging
驱动。所以 staging 充其量只是通往成为正式主线驱动路上的一站。)


Tools(工具)
-----------


Tools
-----

As can be seen from the above text, the kernel development process depends
heavily on the ability to herd collections of patches in various
directions.  The whole thing would not work anywhere near as well as it
does without suitably powerful tools.  Tutorials on how to use these tools
are well beyond the scope of this document, but there is space for a few
pointers.
(从上文可以看出，内核开发过程严重依赖把成堆补丁往各个方向驱赶的能力。没有
足够强大的工具，这一切远不能像现在这样良好运转。如何使用这些工具的教程
远超本文档的范围，但还有空间给出几点指引。)

By far the dominant source code management system used by the kernel
community is git.  Git is one of a number of distributed version control
systems being developed in the free software community.  It is well tuned
for kernel development, in that it performs quite well when dealing with
large repositories and large numbers of patches.  It also has a reputation
for being difficult to learn and use, though it has gotten better over
time.  Some sort of familiarity with git is almost a requirement for kernel
developers; even if they do not use it for their own work, they'll need git
to keep up with what other developers (and the mainline) are doing.
(到目前为止，内核社区使用的主导源码管理系统是 git。git 是自由软件社区正在
开发的若干分布式版本控制系统之一。它非常适合内核开发：处理大型仓库和大量
补丁时性能相当好。它也有难学难用的名声，尽管随着时间的推移已经有所改善。
某种程度上的 git 熟悉度几乎是内核开发者的必备要求；即使他们不在自己的工作
中使用它，也需要 git 来跟上其他开发者 (以及主线) 的动向。)

Git is now packaged by almost all Linux distributions.  There is a home
page at:
(现在几乎所有 Linux 发行版都打包了 git。它的主页在：)

	https://git-scm.com/

That page has pointers to documentation and tutorials.
(该页面提供了文档和教程的指引。)

Among the kernel developers who do not use git, the most popular choice is
almost certainly Mercurial:
(在不使用 git 的内核开发者中，最受欢迎的选择几乎可以肯定是 Mercurial：)

	https://www.selenic.com/mercurial/

Mercurial shares many features with git, but it provides an interface which
many find easier to use.
( Mercurial 与 git 共享许多特性，但它提供的界面被许多人认为更易用。)

The other tool worth knowing about is Quilt:
(另一个值得了解的工具是 Quilt：)

The other tool worth knowing about is Quilt:

	https://savannah.nongnu.org/projects/quilt/

Quilt is a patch management system, rather than a source code management
system.  It does not track history over time; it is, instead, oriented
toward tracking a specific set of changes against an evolving code base.
Some major subsystem maintainers use quilt to manage patches intended to go
upstream.  For the management of certain kinds of trees (-mm, for example),
quilt is the best tool for the job.
( Quilt 是一个补丁管理系统，而不是源码管理系统。它不跟踪历史演变；相反，
它面向的是针对一个不断演进的代码库跟踪一组特定改动。一些主要的子系统维护
者使用 quilt 管理打算发往上游的补丁。对于某些类型树的管理 (例如 -mm)，
quilt 是完成这项工作的最佳工具。)


Mailing lists(邮件列表)
-----------------------


Mailing lists
-------------

A great deal of Linux kernel development work is done by way of mailing
lists.  It is hard to be a fully-functioning member of the community
without joining at least one list somewhere.  But Linux mailing lists also
represent a potential hazard to developers, who risk getting buried under a
load of electronic mail, running afoul of the conventions used on the Linux
lists, or both.
(大量 Linux 内核开发工作是通过邮件列表完成的。如果不在某处加入至少一个
列表，很难成为社区中完全发挥作用的一员。但 Linux 邮件列表对开发者而言也
是潜在的危险源：他们可能被电子邮件的洪流淹没、触犯 Linux 列表上的约定，
或两者兼有。)

Most kernel mailing lists are hosted at kernel.org; the master list can
be found at:
(大多数内核邮件列表托管在 kernel.org 上；总列表可在以下位置找到：)

	https://subspace.kernel.org

There are lists hosted elsewhere; please check the MAINTAINERS file for
the list relevant for any particular subsystem.
(也有托管在其他地方的列表；请查阅 MAINTAINERS 文件以找到与任何特定子系统
相关的列表。)

The core mailing list for kernel development is, of course, linux-kernel.
This list is an intimidating place to be; volume can reach 500 messages per
day, the amount of noise is high, the conversation can be severely
technical, and participants are not always concerned with showing a high
degree of politeness.  But there is no other place where the kernel
development community comes together as a whole; developers who avoid this
list will miss important information.
(内核开发的核心邮件列表当然是 linux-kernel。这个列表是个令人生畏的地方：
每天的信息量可达 500 封，噪音很大，讨论可能非常技术化，参与者也不总是
注意保持高度礼貌。但没有任何其他地方能让内核开发社区作为一个整体汇聚在
一起；回避这个列表的开发者会错过重要信息。)

There are a few hints which can help with linux-kernel survival:
(有几点提示可以帮助你在 linux-kernel 上存活：)

- Have the list delivered to a separate folder, rather than your main
  mailbox.  One must be able to ignore the stream for sustained periods of
  time.
  (把列表投递到单独的文件夹，而不是你的主邮箱。人必须能够长时间忽略这股
  洪流。)

- Do not try to follow every conversation - nobody else does.  It is
  important to filter on both the topic of interest (though note that
  long-running conversations can drift away from the original subject
  without changing the email subject line) and the people who are
  participating.
  (不要试图跟进每一段对话——没有别人这么做。重要的是既按感兴趣的主题过滤
  (不过注意，旷日持久的对话可能偏离原主题而不改变邮件主题行)，也按参与的
  人过滤。)

- Do not feed the trolls.  If somebody is trying to stir up an angry
  response, ignore them.
  (不要给喷子喂食。如果有人试图挑起愤怒的回应，无视他们。)

- When responding to linux-kernel email (or that on other lists) preserve
  the Cc: header for all involved.  In the absence of a strong reason (such
  as an explicit request), you should never remove recipients.  Always make
  sure that the person you are responding to is in the Cc: list.  This
  convention also makes it unnecessary to explicitly ask to be copied on
  replies to your postings.
  (回复 linux-kernel 邮件 (或其他列表的邮件) 时，为所有相关人员保留 Cc:
  头。在没有充分理由 (例如明确要求) 的情况下，绝不应当移除收件人。始终
  确保你回复的人位于 Cc: 列表中。这一约定也使得无需显式请求他人把你抄送
  在对你发帖的回复中。)

- Search the list archives (and the net as a whole) before asking
  questions.  Some developers can get impatient with people who clearly
  have not done their homework.
  (提问之前先搜索列表归档 (以及整个网络)。对于明显没有做功课的人，一些
  开发者会失去耐心。)

- Use interleaved ("inline") replies, which makes your response easier to
  read. (i.e. avoid top-posting -- the practice of putting your answer above
  the quoted text you are responding to.) For more details, see
  :ref:`Documentation/process/submitting-patches.rst <interleaved_replies>`.
  (使用交错式 ("inline") 回复，这让你的回应更易读 (即避免顶端发帖 (top
  posting)——把你的回答放在你所回应的引文之上的做法)。更多细节参见
  :ref:`Documentation/process/submitting-patches.rst <interleaved_replies>` 。)

- Ask on the correct mailing list.  Linux-kernel may be the general meeting
  point, but it is not the best place to find developers from all
  subsystems.
  (在正确的邮件列表上提问。linux-kernel 或许是全体集合点，但它不是找到所有
  子系统开发者的最佳场所。)

The last point - finding the correct mailing list - is a common place for
beginning developers to go wrong.  Somebody who asks a networking-related
question on linux-kernel will almost certainly receive a polite suggestion
to ask on the netdev list instead, as that is the list frequented by most
networking developers.  Other lists exist for the SCSI, video4linux, IDE,
filesystem, etc. subsystems.  The best place to look for mailing lists is
in the MAINTAINERS file packaged with the kernel source.
(最后一点——找到正确的邮件列表——是新手开发者常犯错误的地方。在
linux-kernel 上提出网络相关问题的人，几乎肯定会收到礼貌的建议，让他改到
netdev 列表上提问，因为那是大多数网络开发者常去之地。SCSI、video4linux、
IDE、文件系统等子系统也各有列表。查找邮件列表的最佳位置是随内核源码一起
打包的 MAINTAINERS 文件。)


Getting started with Kernel development(开始内核开发)
-----------------------------------------------------


Getting started with Kernel development
---------------------------------------

Questions about how to get started with the kernel development process are
common - from both individuals and companies.  Equally common are missteps
which make the beginning of the relationship harder than it has to be.
(关于如何着手内核开发过程的问题很常见——个人和公司都会问。同样常见的是
一些失误，它们让这段关系的开端变得比本必要的更加艰难。)

Companies often look to hire well-known developers to get a development
group started.  This can, in fact, be an effective technique.  But it also
tends to be expensive and does not do much to grow the pool of experienced
kernel developers.  It is possible to bring in-house developers up to speed
on Linux kernel development, given the investment of a bit of time.  Taking
this time can endow an employer with a group of developers who understand
the kernel and the company both, and who can help to train others as well.
Over the medium term, this is often the more profitable approach.
(公司常常希望雇用知名开发者来启动开发团队。这确实可以是一种有效的手段。
但它往往代价高昂，而且对扩大有经验内核开发者的队伍帮助不大。投入一点
时间，是有可能让内部开发者熟悉 Linux 内核开发的。花这段时间可以为雇主
带来一群既懂内核又懂公司、还能帮助培训其他人的开发者。从中期来看，这往往
是更有利可图的方式。)

Individual developers are often, understandably, at a loss for a place to
start.  Beginning with a large project can be intimidating; one often wants
to test the waters with something smaller first.  This is the point where
some developers jump into the creation of patches fixing spelling errors or
minor coding style issues.  Unfortunately, such patches create a level of
noise which is distracting for the development community as a whole, so,
increasingly, they are looked down upon.  New developers wishing to
introduce themselves to the community will not get the sort of reception
they wish for by these means.
(个人开发者往往 (可以理解地) 不知从何入手。从大型项目开始可能令人生畏；
人们常常想先用更小的东西试试水。于是一些开发者就在这里一头扎进修复拼写
错误或次要编码风格问题的补丁创作中。遗憾的是，这类补丁制造的噪音会分散
整个开发社区的注意力，因此它们越来越受到轻视。希望向社区介绍自己的新
开发者，靠这些手段是得不到他们期望的接待的。)

Andrew Morton gives this advice for aspiring kernel developers

::

	The #1 project for all kernel beginners should surely be "make sure
	that the kernel runs perfectly at all times on all machines which
	you can lay your hands on".  Usually the way to do this is to work
	with others on getting things fixed up (this can require
	persistence!) but that's fine - it's a part of kernel development.

(Andrew Morton 给有志于内核开发的开发者提出了如下建议：)

(https://lwn.net/Articles/283982/).

In the absence of obvious problems to fix, developers are advised to look
at the current lists of regressions and open bugs in general.  There is
never any shortage of issues in need of fixing; by addressing these issues,
developers will gain experience with the process while, at the same time,
building respect with the rest of the development community.
(在没有明显可修复的问题时，建议开发者去查看当前的回归列表以及一般性的
未决 bug。需要修复的问题从不短缺；通过解决这些问题，开发者将在积累过程
经验的同时，赢得开发社区其余成员的尊重。)
