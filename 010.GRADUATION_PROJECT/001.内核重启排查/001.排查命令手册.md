# 重启原因排查命令手册

> 适用：Linux（以 Ubuntu／systemd 为例）。按第 1、2 节顺序执行，拿到结局后进入第 3 节对应分支。
> 原理背景见 [README.md](./README.md) 第 3 节：dmesg 只覆盖本次启动，证据只可能在**上一次启动日志尾部、审计记录、崩溃转储、带外通道**四处。
> dmesg / journalctl 的完整用法与场景见 [../dmesg命令手册.md](../dmesg命令手册.md) 与 [../journalctl命令手册.md](../journalctl命令手册.md)（另附 [journalctl man 中文版](../journalctl.man.中文版.md)）。

## 1. 定位：何时重启、重启过几次

```bash
uptime -s                              # 本次开机时刻
who -b                                 # 同上（last boot，读 wtmp）
last -x reboot shutdown | head -20     # 历史 reboot/shutdown 记录
                                       # ★ reboot 条目没有紧邻的 shutdown 条目配对 → 那次是异常断电/崩溃
journalctl --list-boots               # journal 视角的启动记录列表（含时间区间，负数编号往回数）
```

## 2. 核心：上一次启动的「临终日志」

```bash
journalctl -b -1 -n 100 --no-pager    # ★★ 最关键的一条：上一次启动的最后 100 行
journalctl -b -1 -e                   # 等效：直接跳到上一次启动日志的末尾
journalctl -b -1 -p err -n 50         # 只看上一次启动的 error 级及以上
journalctl -b -1 --no-pager | grep -inE 'panic|oops|bug:|call trace|mce|hardware error|out of memory|general protection'
```

若 `journalctl --list-boots` 只有本次一条（journal 未持久化，重启前的日志已随 `/run` 消失）：
- 本次只能靠第 5 节的崩溃转储和第 6 节的带外通道；
- 事后补救：`/etc/systemd/journald.conf` 里 `Storage=persistent`（Ubuntu 默认 auto，有 `/var/log/journal` 即已持久化）。

## 3. 结局判读

| 上一次启动日志的尾部形态 | 结论 | 进入 |
|-|-|-|
| systemd `Stopping ...` 序列 ＋ `Reached target Reboot/Power-Off` ＋ `reboot: Restarting system` | 主动 reboot（人/定时任务/包管理器） | 第 4 节 |
| `Kernel panic`／`Oops`／`BUG:`／`Call Trace`／`Out of memory`／MCE | 内核崩溃 | 第 5 节 |
| 正常业务输出**戛然而止**，无任何收尾 | guest 未及反应：断电/宿主机强制重启/迁移（虚拟机常见于宿主维护） | 第 6 节 |

补充佐证（虚拟机）：本次启动 dmesg 里 virtio 盘若出现 `Power-on or device reset occurred`，说明经历过掉电/复位周期；EXT4 根分区挂载**无** `recovery complete` 字样，则提示上次是干净卸载（偏向正常 shutdown）。

## 4. 找到 reboot 的发起者（结局＝正常重启时）

```bash
journalctl -b -1 -u systemd-logind | grep -iE 'power|reboot|shutdown'
                                       # logind 事件：Power key pressed（宿主 ACPI 关机）等
journalctl -b -1 _COMM=sudo --no-pager | grep -iE 'reboot|shutdown'
                                       # 谁执行了 sudo reboot/shutdown
journalctl -b -1 -u unattended-upgrades -u apt --no-pager | tail -30
                                       # 无人值守升级常伴随重启
last -x | head                         # shutdown 记录的时间与操作者（wtmp）
```

## 5. 崩溃转储（结局＝内核崩溃时）

```bash
ls -la /var/crash/                    # Ubuntu/apport 崩溃转储目录
ls /var/crash/*/vmcore-dmesg.txt 2>/dev/null && cat /var/crash/*/vmcore-dmesg.txt | tail -50
                                       # kdump 落盘的崩溃时 printk 快照（无需解析 vmcore）
systemctl status kdump-tools 2>/dev/null || systemctl status kdump
                                       # kdump 服务是否在跑（崩溃转储的前提）
```

无转储时检查跨重启幸存通道：

```bash
ls -la /sys/fs/pstore/ && cat /sys/fs/pstore/console-ramoops* 2>/dev/null
                                       # pstore/ramoops：掉电前最后的 printk
dmesg | grep -i pstore                # 本次启动是否注册了 pstore 后端（efi-pstore/ramoops）
```

## 6. 带外通道（结局＝戛然而止时）

- **云主机/虚拟机**：厂商控制台的维护公告、事件中心、工单邮件；宿主机热迁移/宿主机重启/配额强停都会表现为 guest 无预警断流。
- 云厂商串口控制台（serial console）历史——本机 cmdline 就带 `console=ttyS0,115200`，带外侧往往留有落幕输出。
- 物理机：BMC/IPMI SEL 事件日志（`ipmitool sel list`）、RAID 卡/NVRAM 日志。

## 7. 事前部署（让下一次崩溃不再丢证据）

```bash
# ① 持久化 journal（用户态日志跨重启）
grep -r Storage /etc/systemd/journald.conf           # 确认为 persistent/auto 且 /var/log/journal 存在

# ② kdump（内核崩溃转储）
#    内核 cmdline 加 crashkernel=256M，然后：
apt install kdump-tools && systemctl enable --now kdump-tools

# ③ netconsole（实时把 printk 吐到远端，panic 当场可见）
modprobe netconsole netconsole=6666@本机IP/eth0,514@远端IP/远端MAC

# ④ pstore/ramoops（物理机/支持的固件上，跨重启保留最后的 printk）
```

## 附：决策树

```
journalctl --list-boots ──► 确认上一次启动的日志存在
        │
        ▼
journalctl -b -1 -n 100          ← 临终日志
        │
        ├─ 结尾有 systemd 关机流程 ──► 正常重启 ──► 第 4 节找发起者
        │                                          （sudo？logind？unattended-upgrades？）
        ├─ 结尾有 panic/Oops/OOM ────► 内核崩溃 ──► 第 5 节 /var/crash、kdump、pstore
        │
        └─ 日志戛然而止 ────────────► guest 无预警 ──► 第 6 节 last -x 无配对 shutdown 佐证
                                                  ＋ 云厂商面板/BMC 日志
```
