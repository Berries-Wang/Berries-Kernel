# 高负载 D 状态排查命令手册

> 适用：Linux，「负载（Load Average）很高但 CPU 空闲 / 进程 `kill -9` 杀不掉」的现场。按第 1～3 节顺序拿到 D 状态清单；第 4 节按等待路径分支；第 5 节用内核日志定责；第 6、7 节是止损与恢复验证。
> 原理背景见 [README.md](./README.md) 第 2 节：load 统计含 `nr_uninterruptible`，信号唤不醒 `TASK_UNINTERRUPTIBLE`。

## 0. 铁律（动手前先读）

- 只读采证优先；故障期间**不要**为装工具改生产节点——缺 `sysstat` 就用 `/proc`、`ps`、`vmstat` 和日志。
- 不要反复 `kill -9`：对 D 状态无效，只会让恢复更混乱。
- 不要无边界扫描历史日志 / 抓全量堆栈：故障节点资源紧张，先限定时间窗。
- 一切写操作（cordon/drain/umount/重启）先存证据、留回退路径、明确停止条件。

## 1. 固定现场元信息（~1 分钟）

```bash
date -Is                             # ★ 绝对时间：后续所有日志/指标都按这个时间窗对齐
hostnamectl                          # 主机名+系统版本（无此命令用 hostname）
uname -r                             # 内核版本（决定 PSI 可用性、内核栈函数名）
cat /etc/os-release
getconf _NPROCESSORS_ONLN            # 核数：load 要除以它才有意义
ps --version | head -n 1             # 工具版本：不同版本字段有差异
iostat -V 2>&1 | head -n 1
```

## 2. 判断负载来源：CPU 短缺还是任务阻塞

```bash
uptime                               # 1/5/15 分钟负载；恢复期看趋势，不看单点
cat /proc/loadavg                    # 同上 + 最近运行的 PID
vmstat 1 10                          # ★★ 核心判读在此
```

`vmstat` 字段与含义：

| 字段 | 含义 | 本场景关注点 |
|-|-|-|
| `r` | 运行+等待 CPU 的任务数 | 高 → 真 CPU 不足（另行容量排查） |
| `b` | 被阻塞的任务数 | ★ 与 load 同向增长 → 阻塞型负载 |
| `us`/`sy` | 用户态/内核态 CPU | — |
| `id` | CPU 空闲 | ★ 高 + load 高 = 典型 D 状态堆积 |
| `wa` | I/O wait | 仅佐证；**低不能排除 I/O 问题**（远端存储/设备超时未必计入） |
| `si`/`so` | 换入/换出 | 排除内存压力方向 |

PSI（Pressure Stall Information，内核 ≥4.20 且启用才有此文件，没有就跳过）：

```bash
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io                 # some=至少有任务因 I/O 停顿; full=所有非空闲任务同时被卡
                                      # avg10/60/300=窗口内停顿时间占比，不是单次 I/O 延迟
                                      # 只回答"停了多久"，不回答"卡在哪个设备"
```

## 3. 找出 D 状态任务与等待通道（本手册核心）

```bash
ps -eLo state,pid,tid,ppid,wchan:32,comm | awk 'NR == 1 || $1 ~ /^D/'
                                      # ★★ 线程级（-L）：进程级 ps 会漏掉多线程程序内部卡住的线程
                                      # PID=线程组进程号, TID=线程号, wchan=内核等待位置
ps -eLo state= | awk '$1 ~ /^D/ {n++} END {print n+0}'
                                      # D 状态线程计数：恢复期反复执行看趋势
```

对清单回答**三问**：

1. D 状态是否集中在**同一个业务进程**？
2. 多个线程的 `wchan` 是否**相同**（如都落在 nfs/rpc/块设备/文件系统路径）？
3. 异常线程是否访问了**同一个设备、文件系统或远端存储**？

注意：`wchan` 显示 `0` 或 `-` 可能是权限/内核配置/安全限制所致，**不能据此认定没有阻塞**。

拿到代表性线程后读内核栈（root，只读；输出含内核符号，脱敏后再进工单）：

```bash
sudo cat /proc/<PID>/task/<TID>/wchan
sudo cat /proc/<PID>/task/<TID>/stack     # ★ 直接指明卡在哪个子系统（如 rpc_wait_queue）
```

## 4. 沿等待路径分支（按第 3 节的栈指向二选一或都做）

### 4a. 本地块设备

```bash
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
iostat -xz 1 10                          # ★ 第一组是开机以来累计均值，丢掉，看后续采样
                                          # 看: await(请求完成时间)、队列长度、%util
                                          # await 升+队列涨=恶化; %util≈100% ≠ 达到吞吐上限
                                          # (NVMe/存储阵列/虚拟块设备并行能力强)
```

### 4b. NFS / 远端存储

```bash
findmnt -t nfs,nfs4 -o TARGET,SOURCE,FSTYPE,OPTIONS   # 挂载来源与参数(hard/soft、超时)
nfsstat -m                                            # 各挂载点详细参数
nfsiostat 1 5                                         # ★ RPC 积压、重传、往返时间、操作完成时间
                                                      # 与故障前基线对比; 字段名随版本变化，看表头判读
```

## 5. 内核日志定责（限定时间窗，覆盖告警前几分钟）

```bash
journalctl -k --since "2026-10-08 13:40:00" --until "2026-10-08 14:20:00" --no-pager
# 重点搜（可接 grep -iE）:
#   not responding | timed out | I/O error | reset
#   blocked for more than | nvme | scsi | nfs
```

三条旁证一起做：**健康节点对照**（同版本应用访问同一数据是否正常）＋ **核对告警前变更记录**（路由/防火墙/挂载参数）＋ 与负载/超时的时间窗对齐。文章案例即由「路由策略变更」+ `nfs: server 10.0.18.24 not responding, still trying` 定责。

## 6. 止损（Kubernetes 环境；每步先留档再操作，均可回退）

```bash
kubectl config current-context                       # 先确认操作的是目标集群
kubectl get node <node> -o wide
kubectl get pod -A --field-selector spec.nodeName=<node> -o wide
kubectl get pdb -A                                   # PDB（PodDisruptionBudget）驱逐预算：确认剩余容量接得住

kubectl get node <node> -o yaml > node-before.yaml   # ★ 操作前存档
kubectl get pod -A --field-selector spec.nodeName=<node> -o wide > pods-before.txt

kubectl cordon <node>                                # ★ 只挡新调度，不驱逐现有 Pod
kubectl uncordon <node>                              #   回退=cordon 的逆操作
```

需要迁移现有工作负载时，先预览再受限驱逐（先确认剩余容量、PDB、无控制器的 Pod、`emptyDir`、本地持久卷）：

```bash
kubectl drain <node> --ignore-daemonsets --dry-run=client    # 预览
kubectl drain <node> --ignore-daemonsets --timeout=10m       # 受限驱逐
```

- **故意不用** `--force`（可能删除无控制器接管的 Pod）与 `--delete-emptydir-data`（丢本地临时数据）。
- **D 状态会让 Pod 无法按时终止**：drain 一旦超时，停手重新评估，不要继续加码强制操作。
- 已驱逐的 Pod 不会因 `uncordon` 自动搬回；完整回退要结合副本数、流量入口和发布系统。

根因修复禁忌：NFS 故障优先恢复服务端/网络路径，勿对繁忙挂载点强制 umount；勿把挂载 `hard` 改 `soft` 来「让进程能被杀」（长等待变应用错误，且有数据完整性风险）；无厂商指导勿删块设备/重置控制器/分离云盘；重启节点仅作为证据保存后的兜底。

## 7. 恢复验证（先小流量，稳定后再放量）

```bash
uptime                                               # load 滑动回落中即可，不苛求立即归零
vmstat 1 10                                          # b 下降、id 正常
ps -eLo state= | awk '$1 ~ /^D/ {n++} END {print n+0}'   # ★ D 计数应为 0 或持续下降
cat /proc/pressure/io
iostat -xz 1 10
```

同时观察业务错误率、延迟分位数、存储重传、设备队列与内核新日志。任一复现（错误率回升 / D 再堆积 / 存储超时增加）→ 立即停止放量，节点重新摘除或 `cordon`，回退上一版网络/挂载/设备配置。
