## 1. 4.1 文件:命名、类型、属性、操作

- **命名**:UNIX 把扩展名当**约定**而非 OS 义务(对比 CP/M 及 Windows 强制);`file.gz` 是两个后缀;
- **结构**:UNIX 视文件为无结构字节序列(对比记录式);"UNIX treats files as sequences of bytes... the operating system does not care"(大意,书页 264);
- **类型**:普通文件(ASCII/二进制) + 目录 + 特殊文件(块/字符设备)——**设备也是文件**;
- **属性/操作**:图 4-13 属性表(protection/时间/owner/size…);图 4-14 操作表(create/delete/open/close/read/write/lseek/getattr/setattr/rename…);

## 3. 4.3.1 磁盘布局:MBR → GPT

图 4-10(经典布局)重绘:

```text
 整个磁盘:  [ MBR(含分区表) │ 分区0 │ 分区1 │ ... ]
 每个分区:  [ Boot block │ Superblock │ Free space mgmt │ I-nodes │ Root dir │ Files & dirs ]
                 ↑           ↑                ↑                ↑
               引导块     魔数/块数等关键参数   位图或链表        每文件一个
                          (启动/首触时读入内存)   (空闲块管理)
```

> The first one is the superblock. It contains all the key parameters about the file system and is read into memory when the computer is booted or the file system is first touched. Typical information in the superblock includes a magic number to identify the file-system type, the number of blocks in the file system, and other key administrative information.（第一个是超级块。它包含关于文件系统的全部关键参数,在计算机启动或文件系统首次被访问时读入内存。超级块中的典型信息包括标识文件系统类型的魔数、文件系统的块数以及其他关键管理信息。）<sup>[Modern Operating Systems 5th, 书页 278–279(PDF 307–308)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=307)</sup>

- "New School":UEFI + GPT——`Block 0 留给 legacy MBR 标记("No MBR here!")、Block 1 起是 GPT、盘尾备份 GPT、ESP 分区放 FAT 文件系统 + PE 程序`(图 4-11,书页 279–280);与 §1.3.6 呼应;
- 7.1.3 落点:`struct ext4_super_block` <sub>[/fs/ext4/ext4.h:1329](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/ext4/ext4.h)</sub>;引导流程见 [029.内核启动](../029.内核启动)。

## 4. 4.3.2 文件的实现:四种分配方案

全章核心表(图 4-12~4-15 的浓缩):

| 方案 | 思想 | 优点 | 缺点 |
|-|-|-|-|
| 连续分配 | 文件占连续块 | 实现简单(记首块+块数)、顺序读满带宽 | 磁盘碎片化;创建须预知文件长度("录像程序问你视频多大") |
| 链表分配 | 块内前几字节作 next 指针 | 无外部碎片、随用随取 | 随机访问 O(n);指针占数据空间;一块坏链条断 |
| 内存表(FAT) | 链表搬进内存 FAT 表 | 随机访问快;FAT 即"文件分配表" | 整表须常驻内存——"The table must be in memory all the time"(书页 284),盘大表大 |
| **i-node** | 每文件一个 index-node 记属性+块地址 | 只需为**打开的文件**留内存 | 固定地址数 → 间接块 |

i-node 方案的关键引文(为什么它赢了):

> Given the i-node, it is then possible to find all the blocks of the file. The big advantage of this scheme over linked files using an in-memory table is that the i-node needs to be in memory only when the corresponding file is open.（拿到 i-node,就能找到该文件的所有块。与使用内存表的链式文件相比,这一方案的最大优点是:只有对应文件被打开时,i-node 才需要驻留内存。）<sup>[Modern Operating Systems 5th, 书页 284–285(PDF 313–314)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=313)</sup>

> In contrast, the i-node scheme requires an array in memory whose size is proportional to the maximum number of files that may be open at once. It does not matter if the disk is 500 GB, 500 TB, or 500 PB.（相比之下,i-node 方案要求的内存数组大小只与"同时最多打开多少文件"成正比,与磁盘是 500 GB、500 TB 还是 500 PB 无关。）<sup>[Modern Operating Systems 5th, 书页 285(PDF 314)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=314)</sup>

图 4-15(i-node)重绘——`属性 + 块 0..12 地址 + 三级间接`:

```text
   i-node                          数据块
 ┌────────────────┐
 │File Attributes │
 │ addr[0..11] ───┼────────────► 直接块 ×12
 │ single ind. ───┼──► 间接块 ──► 数据块…
 │ double  ind. ──┼──► 间接块 ──► 间接块 ──► 数据块…
 │ triple  ind. ──┼──► …(三层)
 └────────────────┘
```

ext2/ext4 的落地与上限数字见 [010.MOS5-10.6 §4](./010.MOS5-10.6-Linux文件系统精读.md);ext4 用 extent 解决"间接块链长"问题。

## 6. 4.3.4 共享文件:硬链接与符号链接

图 4-18:目录树变 **DAG**。两种实现及各自缺陷:

1. **硬链接**(UNIX i-node 方案):目录项只存 i-node 号,多个目录项指同一 i-node——"This is the approach used in UNIX (where the little data structure is the i-node)."(书页 288)。缺陷:计数回收、跨文件系统不行;若目录也硬链接会成环,故 UNIX **禁止目录硬链接**;
2. **符号链接**:"The new file contains just the path name of the file to which it is linked."(书页 289)——TYPE=LINK 的小文件。缺陷:多一次路径解析、目标可悬空。

> Each of these methods has its drawbacks.（每种方法各有其缺点。）<sup>[Modern Operating Systems 5th, 书页 289(PDF 318)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=318)</sup>

展开对照见 [007.符号链接和硬链接.md](./007.符号链接和硬链接.md)。

## 7. 4.3.5 日志结构文件系统(LFS)

把整盘当**日志**写:写时归段、随机写变顺序写;代价是 periodic **cleaner** 段回收与 inode 位置不定(inode map)。书页 291–296。它是 §4.3.6 日志文件系统的思想源头——"Log-structured file systems are an interesting idea in general and one of the ideas inherent in them, robustness in the face of failure, can also be applied to more conventional file systems."(书页 292)。

## 8. 4.3.6 日志文件系统:WAL 的教科书定义 ★

本小节是任务"WAL 机制"的书本依据,完整展开见 [012.WAL](./012.WAL预写日志在Linux文件系统中的实现-ext4与JBD2.md),这里只录三段原文:

**先写日志、再干活:**

> What the journaling file system does is first write a log entry listing the three actions to be completed. The log entry is then written to disk (and for good measure, possibly read back from the disk to verify that it was, in fact, written correctly). Only after the log entry has been written, do the various operations begin. After the operations complete successfully, the log entry is erased.（日志式文件系统所做的,是先写一条日志条目,列出将要完成的三步操作。然后这条日志被写到磁盘上(为保险起见,还可能从磁盘读回来验证确实写对了)。只有当日志条目写好之后,各步操作才开始。操作成功完成后,日志条目被擦除。）<sup>[Modern Operating Systems 5th, 书页 293(PDF 322)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=322)</sup>

**幂等性要求:**

> To make journaling work, the logged operations must be idempotent, which means they can be repeated as often as needed without harm.（要让日志机制成立,被记录的操作必须是幂等的——即无论重复多少次都无害。）<sup>[Modern Operating Systems 5th, 书页 293(PDF 322)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=322)</sup>

**原子事务:**

> For added reliability, a file system can introduce the database concept of an atomic transaction. When this concept is used, a group of actions can be bracketed by the begin transaction and end transaction operations. The file system then knows it must complete either all the bracketed operations or none of them, but not any other combinations.（为进一步提高可靠性,文件系统可以引入数据库中原子事务的概念。使用这一概念时,一组操作可以用 begin transaction 和 end transaction 括起来。文件系统据此知道自己必须完成括号里的全部操作,或者一个也不做,不能是其他组合。）<sup>[Modern Operating Systems 5th, 书页 293(PDF 322)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=322)</sup>

还有删除文件三步的顺序灾难(目录项/i-node/数据块,先删哪个崩了都出事,书页 292–293)——正是 WAL 要消灭的"崩溃中间态"。

## 9. 4.3.7 闪存文件系统 + 4.3.8 VFS

- **F2FS 类**(4.3.7):针对 NAND 的 erase-before-write、FTL 磨损均衡;与 LFS 思想一脉相承;
- **VFS**(4.3.8)重绘图 4-21:

```text
  用户进程 ── POSIX(open/read/write/close) ──► 虚拟文件系统(VFS)
                                                  │ VFS interface(几十个函数指针)
                             ┌────────────────────┼────────────────────┐
                           FS 1 (ext4)         FS 2 (NFS)         FS 3 (FAT)
                             └────────── Buffer cache(统一页缓存) ──────┘
```

> The key idea is to abstract out that part of the file system that is common to all file systems and put that code in a separate layer that calls the underlying concrete file systems to actually manage the data.（关键思想是:把所有文件系统共有的那部分抽象出来,放进一个独立的层,由它调用底层的具体文件系统去真正管理数据。）<sup>[Modern Operating Systems 5th, 书页 298(PDF 327)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=327)</sup>

VFS 的三个对象(superblock/v-node/directory)+ mount 表;书中 v-node 在 Linux 里即"generic i-node"。7.1.3 落地见 [010.MOS5-10.6 §3](./010.MOS5-10.6-Linux文件系统精读.md) 与 [002.虚拟文件系统](./002.虚拟文件系统)。

## 10. 4.4 管理与优化

### 4.4.1 块大小与空闲空间

- 空间效率 vs 时间效率的折中:"if the allocation unit is too large, we waste space; if it is too small, we waste time. The block size of 4 KB is considered a reasonable compromise."(书页 302);
- 空闲块管理:链表 vs 位图;图 4-26 位图;ext2 选位图(MINIX 遗产);
- 磁盘碎片整理(4.4.5)、压缩去重(4.4.6)、安全删除与加密(4.4.7)各一小节,略。

### 4.4.2 备份与 4.4.3 一致性(fsck)

fsck 的两张计数表(图 4-29):每块的"在文件中出现次数"与"在空闲表中出现次数",一致态 = 每块恰好一处为 1;崩溃后可能出现 missing(0,0)/duplicate(2,2)——fsck 补链/去重:

> If the file system is consistent, each block will have a 1 either in the first table or in the second table, as illustrated in Fig. 4-29(a).（如果文件系统是一致的,那么每个块要么在第一张表中、要么在第二张表中计 1,如图 4-29(a) 所示。）<sup>[Modern Operating Systems 5th, 书页 313(PDF 342)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=342)</sup>

日志文件系统免 fsck 的原因:"...are designed such that they do not require administrators to run a separate file system consistency checker after a crash, because they can handle most inconsistencies themselves."(书页 313)。

### 4.4.4 性能:buffer cache、预读、30 秒 sync ★

图 4-30(哈希表+LRU 双向链)重绘:

```text
 Hash table              Front (LRU)                     Rear (MRU)
 ┌────┐   ┌──────────────────────────────────────────────┐
 │ h0 ├──►│ bh ── bh ── bh ── bh（冲突链 = 同哈希值）    │
 │ h1 ├──►│ bh ── bh（冲突链）                           │
 └────┘   └──────────────────────────────────────────────┘
              ▲ 另有一条贯穿全部 bh 的双向链(图中未画出):按使用
                时间排序,LRU 在 Front 端、MRU 在 Rear 端;命中→摘
                下挪到 MRU 端;缓存满→从 LRU 端取(脏块先回写再复用)。
```

书中对"严格 LRU 反而不对"的讨论(书页 316–317):i-node 块等**关键块**脏了应**立即**写盘,不按 LRU 拖;数据块也不能留太久——于是引出 30 秒:

> The UNIX way is to have a system call, sync, which forces all the modified blocks out onto the disk immediately. When the system is started up, a program, usually called update, is started up in the background to sit in an endless loop issuing sync calls, sleeping for 30 sec between calls. As a result, no more than 30 seconds of work is lost due to a crash.（UNIX 的办法是提供一个系统调用 sync,强制把所有修改过的块立即写到磁盘上。系统启动时会拉起一个通常叫 update 的后台程序,它坐在一个无限循环里发 sync 调用、两次调用之间睡 30 秒。其结果是:崩溃至多损失 30 秒的工作。）<sup>[Modern Operating Systems 5th, 书页 317(PDF 346)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=346)</sup>

→ 这与 §10.5"every 30 seconds"、§10.6 ext4 的"up to 30 sec"三处同源;现代对应 `dirty_expire_interval = 30*100` centisec <sub>[/mm/page-writeback.c:110](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/mm/page-writeback.c)</sub>,写回机制见 [000.块设备 §9-§13](../052.INPUT_OUTPUT/000.块设备/000.块设备的操作.md)。
