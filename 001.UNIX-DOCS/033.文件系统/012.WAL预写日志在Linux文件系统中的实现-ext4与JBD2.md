## 0. 结论速览

| 问题 | 一句话回答 |
|---|---|
| WAL 是什么 | **先把"将要做什么"写进日志并落盘,再动真格的数据**;崩溃后靠重放日志恢复到"全部做完"或"全都没做"的一致点 |
| WAL 解决几个问题 | **两个**:①正确性——"先写日志"是顺序规则,保证崩溃原子性(§1.1-1.2);②性能——把随机元数据写**顺序化**并移出前台关键路径(§1.4)。只答对一半是常见误读 |
| Linux 里谁来实现 | **ext4(及 ocfs2)用 JBD2**(`fs/jbd2/`,通用日志块设备层):ext4 只负责"记什么",JBD2 负责"怎么记、怎么提交、怎么恢复"。ext3 用前身 JBD v1;xfs/btrfs 自带日志(xfs_log/树日志),**不用 JBD2** |
| WAL 中的"W"写在哪个盘区 | 日志区:ext4 保留 inode 8(`EXT4_JOURNAL_INO`,[ext4.h:320](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/ext4/ext4.h))或外部日志设备;环形缓冲,循环覆写 |
| "Write-Ahead"体现在哪 | 事务提交时,元数据先**写入日志区**(descriptor+数据拷贝),写完 **commit 记录**(带 `REQ_PREFLUSH`+`REQ_FUA` 屏障)之后,才允许 checkpoint 把这些元数据写到**最终位置**——写日志永远先于写终点 |
| data=ordered/journal/writeback 差别 | ordered(默认):元数据进日志,数据不进日志但**先于元数据提交刷盘**;journal:数据也进日志;writeback:数据随时刷,只有元数据有日志 |
| 与书 §4.3.6 的对应 | "先写日志条目→再执行→成功后擦除"= JBD2 的 descriptor+commit→checkpoint;"幂等操作"= 基于 tag 的块重放天然幂等;"begin/end transaction"= `handle_t`(原子操作句柄),事务 = `transaction_t` |

## 1. WAL 定义与"为什么必须如此"

### 1.1 书本定义(§4.3.6)

> What the journaling file system does is first write a log entry listing the three actions to be completed. The log entry is then written to disk (and for good measure, possibly read back from the disk to verify that it was, in fact, written correctly). Only after the log entry has been written, do the various operations begin.（日志式文件系统所做的,是先写一条日志条目,列出将要完成的操作。然后这条日志被写到磁盘上(为保险起见,还可能从磁盘读回来验证确实写对了)。只有当日志条目写好之后,各步操作才开始。）<sup>[Modern Operating Systems 5th, 书页 293(PDF 322)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=322)</sup>

配套两原则(原文与分析见 [011.MOS5-第4章 §8](./011.MOS5-第4章-文件系统精读.md)):**幂等性**("the logged operations must be idempotent")与**原子事务**("bracketed by the begin transaction and end transaction operations")。

### 1.2 WAL 要消灭的问题:崩溃中间态

删除文件的三步(目录项 → i-node → 数据块位图)任何一步之后断电都会留下"既不在文件里、也不在空闲表里"或"两文件共享同一块"的中间态(书页 292–293 的顺序灾难分析)。WAL 的答法:

```text
 无 WAL:  步骤1 ──✓── 步骤2 ──✗ 断电     → 步骤3 永远没做,系统处于中间态
 有 WAL:  [日志:1,2,3] ──✓落盘── 步骤1,2,3(任意进度)断电
              ▼ 重启时
          重放日志:已 commit → 重做全部三步(幂等,多做无害)
                    未 commit → 丢弃,三步当作从未发生 → 恢复到一致点
```

### 1.3 磁盘上的两个世界:日志区与最终位置

```text
                    ┌────────── 日志区(JBD2 管理,环形) ──────────┐
                    │ superblock │ T1:desc│data…│commit │ T2:… │…│
                    └─────▲──────────────────────────────────────┘
   ext4 元数据修改 ──先写──┘(W 的"write-ahead")
                    之后 checkpoint 再把同一份元数据 ──► ┌──────────────┐
                                                        │ 文件系统最终  │
                                                        │ 位置(位图/    │
                                                        │ inode/目录块) │
                                                        └──────────────┘
```

### 1.4 常见误读:"WAL 不就是避免随机 IO 吗?"——它只答对一半

WAL 的两个目的**载体不同、缺一不可**:

| 目的 | 载体 | 没有它会怎样 |
|---|---|---|
| **正确性**(write-ahead 本义) | "先写日志、后写数据页"这条**顺序规则** + commit 块作持久化边界 | 重放不安全——崩溃恢复无法区分"改了一半"和"没改"(§1.2) |
| **性能**(顺序化随机写) | 日志区**连续布局** + j_head 顺序推进 + 批量提交 | 元数据散布全盘,每次修改都是随机寻道(§1.2 的三步删文件,位图/i-node/目录块三个地方) |

性能这半,书在两处各给了一段原文。**§4.3.5 LFS 是纯性能动机的极端版**:

> From this reasoning, the LFS designers decided to reimplement the UNIX file system in such a way as to achieve the full bandwidth of the disk, even in the face of a workload consisting in large part of small random writes. The basic idea is to structure the entire disk as a great big log.（基于这一分析,LFS 的设计者决定以这样一种方式重新实现 UNIX 文件系统:即使工作负载主要由小的随机写构成,也要达到磁盘的全部带宽。基本思想是把整个磁盘组织成一个巨大的日志。）<sup>[Modern Operating Systems 5th, 书页 291(PDF 320)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=320)</sup>

> Measurements given in the papers cited above show that LFS outperforms UNIX by an order of magnitude on small writes, while having a performance that is as good as or better than UNIX for reads and large writes.（上述论文给出的测量表明,LFS 在小写场景下比 UNIX 快一个数量级,而读和大写的性能与 UNIX 相当或更好。）<sup>[Modern Operating Systems 5th, 书页 292(PDF 321)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=321)</sup>

**§10.6 则把两个目的合在同一段里**——顺序写在前、崩溃重放在后:

> By sequentially writing out changes to the file-system data or metadata (i-nodes, superblock, etc.), the operations do not suffer from the overheads of disk-head movement during random disk accesses. Eventually, the changes will be written out, committed, to the appropriate disk location, and the corresponding journal entries can be discarded.（通过顺序地写出对文件系统数据或元数据(i-node、超级块等)的变更,操作就不会承受随机磁盘访问中移动磁头的开销。最终这些变更会被写出、提交到合适的磁盘位置,相应的日志条目即可丢弃。）<sup>[Modern Operating Systems 5th, 书页 781(PDF 810)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=810)</sup>

但"避免随机 IO"要精确成三句话,否则会以偏概全:

1. **前台(提交关键路径)是顺序的**:元数据经 `jbd2_journal_next_log_block()` 从 j_head **顺序分配**日志块 <sub>[/fs/jbd2/journal.c:815](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/jbd2/journal.c)</sub>,提交时 `blk_start_plug()` 批量下泄 <sub>[/fs/jbd2/commit.c:579](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/jbd2/commit.c)</sub>,整个事务**只在 commit 块上打一次 `REQ_PREFLUSH\|REQ_FUA` 屏障**(§4.1)——随机寻道被挤出了 fsync 的等待时间;
2. **后台(checkpoint)仍是随机写**:§5 的 checkpoint 最终还是把元数据写回全盘各处的最终位置——随机 IO 没有**消失**,只是被移出关键路径、可排序合并、由 kjournald2 异步慢慢做;
3. **默认模式只顺序化元数据**:`data=ordered`(§7)下数据块根本不进日志、直接写到最终位置(该随机还是随机);只有 `data=journal` 才把数据也并入顺序流,代价是数据写两遍。

所以准确表述是:**WAL 用"前台顺序写日志 + 后台异步随机写回"替换"前台随机写"**——正确性靠 write-ahead 顺序规则,性能靠日志布局与批量提交;二者在 ext4/JBD2 里是同一套结构(§2.2 环形缓冲)的两个侧面,也是它比"影子分页"(只要正确性)和"F2FS/LFS"(只要顺序化,正确性内建于追加写)更通用的原因。

## 2. JBD2 的三大结构与磁盘布局

### 2.1 三层数据结构(与书中 §10.6 的 log record / atomic handle / transaction 对齐)

```c
/* include/linux/jbd2.h:112,122-123 —— 日志块的"类型魔数" */
#define JBD2_MAGIC_NUMBER 0xc03b3998U
#define JBD2_DESCRIPTOR_BLOCK	1     // 描述块:后随 N 个 block tag(每 tag=一个数据块落日志)
#define JBD2_COMMIT_BLOCK	2         // 提交块:见它=事务持久化了

/* include/linux/jbd2.h:131-136(journal_header),185-191(tag3) —— 块格式 */
typedef struct journal_header_s {      /* 所有日志块的公共头 */
	__be32		h_magic;               /* JBD2_MAGIC_NUMBER */
	__be32		h_blocktype;           /* descriptor/commit/... */
	__be32		h_sequence;            /* 事务序号 */
} journal_header_t;

typedef struct journal_block_tag3_s {
	__be32		t_blocknr;	/* The on-disk block number —— 该份拷贝属于盘上哪一块 */
	__be32		t_flags;
	__be32		t_blocknr_high;
	__be32		t_checksum;	/* crc32c(uuid+seq+block) */
} journal_block_tag3_t;
```

- **log record(日志记录)** = 日志区里一个数据块拷贝 + 它的 tag(`t_blocknr` 声明"这是块 X 的影子");
- **atomic operation handle** = `handle_t` <sub>[/include/linux/jbd2.h](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/jbd2.h)</sub>(`h_ref`/`h_credits`),ext4 一次元数据修改的"括号";
- **transaction** = `transaction_t`,`t_state` 状态机:

```c
/* include/linux/jbd2.h:589-599(t_state 状态机) */
	enum {
		T_RUNNING,      /* 接受新 handle */
		T_LOCKED,
		T_SWITCH,
		T_FLUSH,
		T_COMMIT,       /* 元数据写日志中 */
		T_COMMIT_DFLUSH,
		T_COMMIT_JFLUSH,
		T_COMMIT_CALLBACK,
		T_FINISHED      /* commit 记录落盘,等待 checkpoint */
	}			t_state;
```

### 2.2 journal_s 的关键游标

```c
/* include/linux/jbd2.h:923,931,1116(节选,注释为源码原文) */
	unsigned long		j_head;   /* Journal head: identifies the first unused block in the journal. */
	unsigned long		j_tail;   /* Journal tail: identifies the oldest still-used block in the journal. */
	unsigned long		j_commit_interval; /* What is the maximum transaction lifetime before we begin a commit? */
```

环形缓冲与提交节奏:

```text
 j_tail(最老未 checkpoint)                          j_head(下一个空位)
          ▼                                           ▼
 ┌──────┬──────────┬──────────┬──────────┬──────────┬─────────────┐
 │super │T5        │T6        │T7        │T8        │空闲(可覆写) │
 │block │commit*   │commit*   │commit*   │写入中    │             │
 └──────┴──────────┴──────────┴──────────┴──────────┴─────────────┘
   ◄─── 已 commit,待 checkpoint(T5–T7) ───► ◄T8 写入中► ◄空闲►
 提交周期:j_commit_interval = HZ * JBD2_DEFAULT_MAX_COMMIT_AGE   jbd2.h:48
        = fs/jbd2/journal.c:1558  journal->j_commit_interval = (HZ * JBD2_DEFAULT_MAX_COMMIT_AGE);
        默认 5 秒;可被 fsync/空间压力提前触发
```

## 3. 写路径:ext4 怎么把元数据"记进括号"

### 3.1 事务句柄的生与死

ext4 任何元数据修改(建文件、改 i-node、分配块……)都包在 `ext4_journal_start`/`ext4_journal_stop` 之间:

```c
/* fs/ext4/ext4_jbd2.h:225-227 */
#define ext4_journal_start(inode, type, nblocks)			\
	__ext4_journal_start((inode), __LINE__, (type), (nblocks), 0,	\
			     _RET_IP_)

/* fs/jbd2/transaction.c:466(jbd2__journal_start 节选) */
handle_t *jbd2__journal_start(journal_t *journal, int nblocks, int rsv_blocks, ...)
{
	...
	nblocks += DIV_ROUND_UP(revoke_records,
				journal->j_revoke_records_per_block);
	handle = new_handle(nblocks);          /* 句柄=nblocks 个信用:预计改几个块 */
	...
	err = start_this_handle(journal, handle, gfp_mask);  /* transaction.c:312,把 handle 挂到
	                                                        当前 T_RUNNING 事务(满了就开新的) */
```

```c
/* fs/jbd2/transaction.c:1883(jbd2_journal_stop 节选) */
int jbd2_journal_stop(handle_t *handle)
{
	...
	if (--handle->h_ref > 0) { ... }       /* 嵌套 handle:引用计数-1 即返回 */
	...
```

- `handle` 只是**记账**:声明本次要动几个块(credits),JBD2 据此保证事务里日志空间够用;
- 书中"begin/end transaction"的内核实体就是这两个调用;`__ext4_journal_start` 出错时转 `ext4_handle_error`(只读降级)。

### 3.2 元数据进日志的时机

修改执行中,每个被改的元数据 buffer 经 `do_get_write_access` **冻结快照**进事务;提交时 `jbd2_journal_write_metadata_buffer` <sub>[/fs/jbd2/journal.c:325](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/jbd2/journal.c)</sub> 把快照拷进日志块(开头是 `JBD2_MAGIC_NUMBER` 的数据要"escape"替换首字,恢复时还原——源码注释见该处)。**此刻起,这块元数据有了日志里的影子,但它还在内存,没到最终盘位**——这正是 WAL 的"write-ahead"。

data=journal 模式连**数据块**也走这条路(`ext4_block_write_begin` 里对每块 `do_journal_get_write_access`):

```c
/* fs/ext4/inode.c:1374-1378 */
	if (!ret && ext4_should_journal_data(inode)) {
		ret = ext4_walk_page_buffers(handle, inode,
					     folio_buffers(folio), from, to,
					     NULL, do_journal_get_write_access);
	}
```

## 4. 提交(commit):WAL 的事务边界与磁盘屏障

### 4.1 提交时序全图

```text
 kjournald2 线程(fs/jbd2/journal.c:160,线程名 "jbd2/sda1-8")
   │ j_commit_interval(5s)到期 / fsync 强制 / 空间压力
   ▼
 jbd2_journal_commit_transaction(journal)                     fs/jbd2/commit.c:377
   │
   ├─[T_LOCKED] 锁定事务,新 handle 转投新事务
   ├─[T_FLUSH ] (commit.c:561)
   │    "Now start flushing things to disk, in the order they
   │     appear on the transaction lists. Data blocks go first."   commit.c:573
   │    journal_submit_data_buffers()                      commit.c:575
   │      └ data=ordered:把事务里的数据 inode 下发写盘(jbd2_submit_inode_data, commit.c:181)
   ├─[T_COMMIT] 元数据写日志区(commit.c:590)
   │    descriptor block(tag1..tagN) + 数据拷贝块
   ├─ journal_finish_inode_data_buffers()                  commit.c:767
   │      └ 等 ordered 数据 IO 真正完成(jbd2_wait_inode_data, commit.c:198)
   ├─ (日志与文件系统不同设备时)blkdev_issue_flush(j_fs_dev)  commit.c:807
   ▼
 journal_submit_commit_record()                              commit.c:114
   ├ bh = jbd2_journal_get_descriptor_buffer(..., JBD2_COMMIT_BLOCK)   commit.c:130
   └ if (journal->j_flags & JBD2_BARRIER && !async_commit)
         write_flags |= REQ_PREFLUSH | REQ_FUA;              commit.c:154
     submit_bh(write_flags, bh);                             commit.c:156
    ▼
 等 commit 块 IO 完成(journal_wait_on_commit_record, commit.c:165)
   ── 到此"事务已提交":崩溃后恢复会重放它 ──
   ▼
 [T_FINISHED] 唤醒等待者(jbd2_log_wait_commit 等 tid_geq(j_commit_sequence))  journal.c:652
   ▼
 之后(异步):checkpoint 把元数据从日志写到最终位置(§5)
```

**三个要点**:

1. **ordered 模式"数据先于元数据"**:数据块虽不进日志,但 `journal_submit_data_buffers` 先下发、`journal_finish_inode_data_buffers` 在写 commit 记录**之前**等它完成——保证 commit 记录落盘时,它声明的数据已在盘上;
2. **commit 记录是持久化边界**:`REQ_PREFLUSH|REQ_FUA` 让设备把 cache 清掉再写 commit 块且不落易失缓存——"写日志先于写终点、commit 是唯一裁决点"由**磁盘屏障**落实;
3. **幂等重放**:重放只是"把日志里的块拷回 `t_blocknr`",覆盖式写,多做无副作用——满足书 §4.3.6 的 idempotent 要求。

### 4.2 事务状态机(源码序)

```text
 T_RUNNING ──锁定──► T_LOCKED ──flush数据──► T_FLUSH ──元数据写日志区──► T_COMMIT
                                                                │ commit 记录落盘
                                                                ▼
                                  T_COMMIT_DFLUSH / T_COMMIT_JFLUSH
                                                                │ 全部等待者处理完
                                                                ▼
                                        T_COMMIT_CALLBACK ──► T_FINISHED
                                                                │ checkpoint 完成
                                                                ▼
                                                    (j_tail 前移,日志空间回收)

 注:新事务由 jbd2__journal_start() 新建一个 transaction_t 进入 T_RUNNING,与上一
    事务的状态流转无关;同一 journal 同时至多一个 running + 一个 committing 事务
   (jbd2_journal_commit_transaction 开头的 J_ASSERT 即保证这一点)。
```

## 5. checkpoint:把"影子"落到最终位置

commit 只是"日志持久";元数据还在日志区,必须再写到**最终位置**才算完(JBD2 称 checkpoint):

```c
/* fs/jbd2/checkpoint.c:154(jbd2_log_do_checkpoint 节选) */
int jbd2_log_do_checkpoint(journal_t *journal)
{
	...
	/*
	 * First thing: if there are any transactions in the log which
	 * don't need checkpointing, just eliminate them from the
	 * journal straight away.
	 */
	result = jbd2_cleanup_journal_tail(journal);    /* 先回收已完全 checkpoint 的事务(挪 j_tail) */
```

```text
 commit ──► T_FINISHED(日志安全)──checkpoint──► 元数据写入最终位置 ──► __jbd2_journal_drop_transaction
                                                                      j_tail 前移,日志空间回收
 崩溃窗口分析:
   崩在 checkpoint 之前 → 重放日志恢复(commit 过的事务重做到最终位置,幂等)
   崩在 checkpoint 之后 → 重放发现事务已被 cleanup(超级块 j_tail 前移)跳过,无副作用
```

**这就是 WAL 的完整闭环**:"先写日志 → commit(带屏障) → 写最终位置 → 擦日志条目",与书 §4.3.6 "Only after the log entry has been written, do the various operations begin. After the operations complete successfully, the log entry is erased." 逐句对应。

## 6. fsync:应用可见的 WAL 边界

## 8. 崩溃恢复:三遍扫描

挂载时 ext4 触发恢复(`ext4_load_journal` <sub>[/fs/ext4/super.c:6080,6162](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/ext4/super.c)</sub> → `jbd2_journal_load`;super.c:5592 注释:"The jbd2_journal_load will have done any necessary log recovery"):

```c
/* fs/jbd2/recovery.c:282-312(jbd2_journal_recover 节选) */
int jbd2_journal_recover(journal_t *journal)
{
	...
	/*
	 * The journal superblock's s_start field (the current log head)
	 * is always zero if, and only if, the journal was cleanly
	 * unmounted. ...                           ← 干净卸载:j_tail=0,无需恢复
	 */
	if (!journal->j_tail) { ... return 0; }

	err = do_one_pass(journal, &info, PASS_SCAN);     /* 第一遍:找最新有效 commit 点 */
	if (!err)
		err = do_one_pass(journal, &info, PASS_REVOKE);  /* 第二遍:收集"作废块"记录 */
	if (!err)
		err = do_one_pass(journal, &info, PASS_REPLAY);  /* 第三遍:逐 tag 把日志块写回最终位置 */
```

```text
 恢复三遍(do_one_pass, recovery.c:40):
  PASS_SCAN   从 j_tail 向后扫,校验 descriptor 块 CRC/序列号,锁定最后一个 commit 块
              → commit 块之后的不完整事务(没写完 commit)直接作废 —— 事务原子性由"commit 记录在最后"保证
  PASS_REVOKE 收集 revoke 记录(某块已被后续事务删除/重分配,不许重放旧拷贝)
  PASS_REPLAY 对每个完整事务:按 descriptor 的 tag 把日志数据块拷回 t_blocknr(幂等覆盖写)
 结束:sync_blockdev + blkdev_issue_flush(日志设备/文件系统设备),重置 j_head(=info.head_block)
```

replay 的落点:`do_one_pass` 中 descriptor 块分支——"A descriptor block: we can now write all of the data blocks. Yay, useful work is finally getting done here!" <sub>[/fs/jbd2/recovery.c:744-745](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/jbd2/recovery.c)</sub> → `jbd2_do_replay()`。

## 9. WAL 与 redo/undo 日志的关系(理论定位)

| 维度 | 经典 WAL(数据库,如 ARIES) | JBD2/ext4 |
|-|-|-|
| 日志内容 | undo/redo 记录(逻辑或物理) | **物理 redo**(整块拷贝)+ revoke 记录 |
| 写终点前必须先写日志 | ✓ | ✓ 元数据:descriptor+数据拷贝先于 checkpoint |
| 提交点 | commit LSN 落盘 | **commit 块**(带 `REQ_PREFLUSH\|REQ_FUA`)落盘 |
| 重做规则 | 按 LSN 比较、幂等重放 | 按 tag 覆盖写回 `t_blocknr`,天然幂等(书 §4.3.6 要求) |
| 回滚 | undo 记录 | 无 undo——未 commit 的事务直接**丢弃**(日志区可覆写),旧位置数据未动即等价 undo |
| 数据是否进日志 | 由 DB 决定 | 由 data= 模式决定(§7) |

一句话:JBD2 是**物理 redo 日志 + 无 undo + 磁盘屏障提交**的 WAL 特化,把"事务原子性"问题简化成"commit 块最后写"这一条铁律。

## 10. arm64 平台注脚

- **commit 的屏障语义在 arm64 上同样成立**:`REQ_PREFLUSH|REQ_FUA` 最终由块层转成 NVMe Flush/FUA 或 SCSI SYNCHRONIZE CACHE 命令,作用于设备的易失写缓存;arm64 服务器(NVMe 盘 + SMMU/DMA 路径见 [../052.INPUT_OUTPUT/006.DMA](../052.INPUT_OUTPUT/006.DMA))与 x86 无差别;
- **非一致 DMA 平台的补充代价**:若日志区所在存储控制器不与 CPU 缓存一致,数据拷入日志块后还要 `arch_sync_dma_for_device`(clean)才能交给设备 <sub>[/arch/arm64/mm/dma-mapping.c:15-22](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/mm/dma-mapping.c)</sub>——WAL 的顺序性在"CPU cache → 设备"这段路上靠 **clean/invalidate + 屏障指令**延续,原理与 [DMA 笔记](../052.INPUT_OUTPUT/006.DMA/002.arm64下CPU数据访问优先级通常低于DMA的原因.md) 的软件一致性一节相同;
- fast commit(`ext4_fc_commit` <sub>[/fs/ext4/fast_commit.c:1185](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/ext4/fast_commit.c)</sub>)只针对 inode/dentry 级细粒度变更做轻量提交,不支持时 `fallback` 回全量 commit(fast_commit.c:1264-1266)。

## 11. 小结(记忆钩)

- WAL 四步:**记括号(handle)→ 写影子(日志区)→ 盖章(commit 块+屏障)→ 落地(checkpoint)后擦除**;
- 两个目的:**正确性 = write-ahead 顺序规则**(先日志后数据页,重放才安全),**性能 = 前台顺序化**(j_head 顺序分配 + plug 批量 + 单屏障 commit),checkpoint 把随机写移到后台——"避免随机 IO"只说中了后半句(§1.4);
- 两个数字:**5 秒**事务提交周期(`j_commit_interval`,jbd2.h:48)、**30 秒**脏页过期(`dirty_expire_interval`)——后者是页缓存层的兜底,前者才是崩溃一致性的硬边界;
- 三种模式记法:**ordered=元数据有日志+数据先刷**、**journal=全都进日志**、**writeback=只有元数据有日志**;
- 恢复三遍:**SCAN 定 commit、REVOKE 收作废、REPLAY 覆盖写**——commit 块"最后写"这一条铁律,同时买来了原子性(dump 未完成事务)与幂等性(整块覆盖);
- 对照书:§4.3.6 的"log entry→operate→erase"三段 = JBD2 的"descriptor+commit → checkpoint → drop transaction"。
