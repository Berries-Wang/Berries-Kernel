**本节问题**：8.1.2 说 SMP 要"给临界区配 mutex"——但在多处理器上，mutex 本身怎么造出来？答案是一层层往下挖：关中断不行 → 要原子指令 → 原子指令要锁总线 → 自旋浪费总线 → 缓存救不了还添乱（抖动）→ 于是出现四个优化：先读后锁、指数退避、每 CPU 私有锁（MCS，图 8-11）、自旋 vs 切换的抉择。

# Part 1 书中理论

## 1.1 为什么单处理器的招数全部失效

单处理器上保护临界表只需**关中断**：内核关中断后不会被打断，可以从容访问。
多处理器上**关中断只影响执行关中断的那一个 CPU**，其他 CPU 照常跑、照常摸这张表 → 互斥失效。必须用**所有 CPU 都遵守的锁协议**。

## 1.2 TSL 指令与"锁总线"（图 8-10）

- **TSL（Test and Set Lock）**：一条指令完成"读内存字到寄存器 + 同时向该字写 1"，是所有实用锁协议的心脏。它占**两个总线周期**（一次读一次写）。
- **图 8-10 的失败序列**（锁字 1000 初始为 0）：
  1. CPU 1 读到 0；
  2. CPU 2 抢在 CPU 1 写回之前也读到 0；
  3. CPU 1 写 1；
  4. CPU 2 也写 1。
  两个 CPU 都拿到 0 → **双双进入临界区，互斥失败**。
- **正确做法**：TSL 先**锁定总线**（按总线仲裁协议申请总线，然后拉高一根专用总线线直到两次访存完成），期间其他 CPU 不被授予总线 → TSL 成为不可分割的整体。早期总线没有这套硬件 → 只能诞生纯软件的 **Peterson 协议**。

![图 8-10 TSL 失败序列](./999.IMGS/fig-8-10.png)

## 1.3 自旋锁的代价与缓存抖动（cache thrashing）

- 正确实现的 TSL 自旋锁**保证互斥**，但请求 CPU 原地死循环测试 → 浪费自己的时间 + **猛烈冲击总线/内存**，拖慢所有其他 CPU。
- **直觉错误**：以为加缓存就能救（锁字读进 cache，之后本地循环）。**救不了**，因为：
  1. 缓存按 32/64 字节**块**操作，锁字旁边的字通常是锁持有者要用的数据；
  2. **TSL 是写操作**（要写 1）→ 必须拿到包含锁字的缓存块的**独占权**；
  3. 于是每次 TSL 都把持有者 cache 里的该块**作废**、把块搬到请求者；持有者一碰旁边的字，块又被搬回去……
  4. **整个缓存块在锁主与锁客之间来回穿梭，比单纯读锁字的总线流量还大**——这就是缓存抖动。

## 1.4 书中四个优化

1. **先读后 TSL（read-before-test）**：先**纯读**锁字，只有看到空闲才做 TSL 真正去抢。多数轮询变成纯读；若持有者只读同一块里的变量，双方可以各持**共享只读副本**，缓存块不再来回搬。释放时持有者写 0 → 远端副本作废 → 请求者下次读重新加载。
   - **正确性关键**：纯读"看到空闲"只是**提示**（好时机），不保证抢到——可能两个 CPU 同时看到空闲同时 TSL，但 TSL 原子，只有一个赢，**正确性始终由 TSL 保证**。
2. **二进制指数退避**（借自以太网，Anderson 1990）：轮询间插入延迟循环，1→2→4→…条指令翻倍封顶。上限低：释放时响应快但抖动多；上限高：抖动少但发现空闲慢。可与"先读后锁"组合。
3. **每 CPU 私有锁变量（图 8-11，Mellor-Crummey & Scott 1991）**：每个等待者在**自己独享的缓存块**里放一个私有锁变量并自旋于它；抢锁失败的 CPU 把自己挂到等待链表尾；持有者退出临界区时**释放链表首那个 CPU 正在自旋的私有锁**——那个 CPU 进临界区；它退出时再放行它的后继……协议略复杂（避免两个 CPU 同时挂到表尾），但**高效且无饥饿**（FIFO）。→ 专篇：[005.专题-图8-11](./005.专题-图8-11多锁避免缓存抖动.md)。
4. **自旋还是切换（spin vs. switch）**：
   - 有时**只能自旋**：CPU 空闲、要拿就绪队列锁挑下一个进程——此时无处可切换（切换也要摸就绪队列）。
   - 有时可选：等文件系统 buffer cache 锁，可切到别的线程。**切换也不免费**：保存/加载状态、拿就绪队列锁、挑线程、重装 TLB 与缓存（两次上下文切换 + 一堆 cache miss）。
   - 经验法则：**锁平均持有 50μs、上下文切换一来一回各 1ms（共 2ms）→ 自旋划算；持有 10ms → 两次切换划算**。
   - 自适应策略：**记录该锁最近几次的实际自旋时长做预测**——前三次平均 200μs 就再自旋一会儿；上次自旋总是顶满上限 → 这次立即切换。
   - **MONITOR/MWAIT（x86）**：MONITOR 圈定监视地址区间，MWAIT 阻塞直到有人写该区间——"自旋而不烧 CPU"，还省电（笔记本友好）。

## 2.1 "关中断只影响本 CPU"——arm64 的代码证据

```c
// arch/arm64/include/asm/irqflags.h:71
static __always_inline void arch_local_irq_disable(void)
{
	if (system_uses_irq_prio_masking())
		__pmr_local_irq_disable();   // 写 ICC_PMR_EL1（中断优先级掩码）
	else
		__daif_local_irq_disable();  // 置 PSTATE.DAIF 中的 I/F 位
}
```

DAIF/PMR 是 **per-CPU 的 PSTATE/系统寄存器**——写它只屏蔽**当前核**的中断，其他核不受影响。这正是书中论断的硬件根源，也是为什么 `spin_lock_irqsave()`（关中断+锁）只用于**本核中断也会碰这把锁**的场景，而**核间互斥必须靠锁本身**。

## 2.2 现代"TSL"：arm64 的原子指令（原子性的来源变了）

书中 TSL 靠"锁总线"；真实硬件早已进化：**原子性由缓存一致性协议保证**——同一缓存行同一时刻只允许一个 CPU 持有"独占（脏/修改）"状态，对它的原子操作天然互斥（x86 的 LOCK 前缀从"锁总线"变成"锁缓存行"；ARM 走 LL/SC 与 LSE 两条路）。arm64 两种实现**编译期生成两份、启动时按 CPU 能力打补丁**：

```c
// arch/arm64/include/asm/cmpxchg.h:21 —— 以 xchg 为例
#define __XCHG_CASE(w, sfx, name, sz, mb, nop_lse, acq, acq_lse, rel, cl)   \
	asm volatile(ARM64_LSE_ATOMIC_INSN(                                  \
	/* LL/SC 路径：独占监视器（local exclusive monitor）*/               \
	"	prfm	pstl1strm, %2\n"                                     \
	"1:	ld" #acq "xr" #sfx "\t%" #w "0, %2\n"   /* 独占读 ldxr */     \
	"	st" #rel "xr" #sfx "\t%w1, %" #w "3, %2\n" /* 条件写 stxr */   \
	"	cbnz	%w1, 1b\n"     /* 写失败（line 被别人动过）→ 重试 */     \
		" " #mb,                                                           \
	/* LSE 路径：一条指令硬件保证原子 */                                  \
	"	swp" #acq_lse #rel #sfx "\t%" #w "3, %" #w "0, %2\n" /* swpal */\
	...

// arch/arm64/include/asm/lse.h:23 —— 运行时按 ARM64_HAS_LSE_ATOMICS 选择
#define ARM64_LSE_ATOMIC_INSN(llsc, lse)                                    \
	ALTERNATIVE(llsc, __LSE_PREAMBLE lse, ARM64_HAS_LSE_ATOMICS)
```

- **LL/SC（Load-Exclusive/Store-Exclusive）**：`ldxr` 对该地址登记**独占监视器**（本质是缓存一致性协议给的 line 独占权 + 本地监视状态）；`stxr` 只有监视器仍有效才写成功，否则失败重试。**没有显式的"锁总线"，但对 line 的独占让"读+写"序列不被打断**——这就是图 8-10 故障的解法在 ARM 上的形态。
- **LSE 原子指令**（ARMv8.1+，如 `swpal`、`casal`、`ldaddal`）：单条指令完成交换，硬件内部保证原子——**最接近书中理想 TSL**。
- 自旋锁快路径用的 `cmpxchg`（比较交换）同出一门：`arch/arm64/include/asm/cmpxchg.h:107` `__cmpxchg_case_*`。

## 2.3 spinlock_t 的真身与三层结构

```
spinlock_t                      // include/linux/spinlock.h：API 与调试封装
 └─ raw_spinlock_t              // include/linux/spinlock_types.h：PREEMPT_RT 下与 spinlock 分家
     └─ arch_spinlock_t = struct qspinlock   // include/asm-generic/qspinlock_types.h（arm64 经
                                              // Kconfig:70 ARCH_USE_QUEUED_SPINLOCKS 选用）
```

`struct qspinlock` 是**一个 32 位字**，被切成四段（NR_CPUS<16K 时）：

```text
 31        18 17 16 15    9  8      0
┌────────────┬──────┬───────┬───────┬────────┐
│  tail cpu  │ idx  │ 未用   │pending│ locked │
│  (cpu+1)   │(2bit)│       │ (8bit)│ (8bit) │
└────────────┴──────┴───────┴───────┴────────┘
  排队者是谁          入队层级          乐观位    锁定字节
```

- **locked（1 字节）**：0=空闲，1=被持有。单独占一个字节是为了让"置 1/清 0"可以按字节原子操作；
- **pending（1 字节）**：第一个抢锁失败者的"乐观等待位"（见 2.5）；
- **tail（cpu+1 与层级 idx）**：MCS 等待队列的队尾指针（压缩编码，详见专篇）。

## 2.4 无竞争快路径：一条原子指令

```c
// include/asm-generic/qspinlock.h:107
static __always_inline void queued_spin_lock(struct qspinlock *lock)
{
	int val = 0;
	if (likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL)))
		return;                          // 0 → (0,0,1)，一条 cmpxchg 拿锁
	queued_spin_lock_slowpath(lock, val); // 有竞争才进慢路径
}

// include/asm-generic/qspinlock.h:123 —— 解锁只是一条带 release 语义的普通字节写
static __always_inline void queued_spin_unlock(struct qspinlock *lock)
{
	smp_store_release(&lock->locked, 0);   // 远端缓存副本被一致性协议自动作废
}
```

要点：**快路径没有"循环"**——书中 2-25 图那种 TSL 自旋只出现在慢路径；解锁甚至不是原子指令，只是一条 store（x86 上就是普通 MOV）。无竞争时一把自旋锁的开销 = 1 条原子指令 + 1 条 store。

## 2.5 慢路径 `queued_spin_lock_slowpath()`：书中所有优化的一次性落地

`kernel/locking/qspinlock.c:130`，状态机注释（:114-128）：

```text
              fast     :    slow                              :    unlock
uncontended  (0,0,0) -:--> (0,0,1) ----------------------------:--> (*,*,0)
pending               :    (0,1,1) --> (0,1,0) --> (0,0,1)     :
queue                 :    (n,x,y) --> (n,0,0) --> (*,0,1) ----:
```

**① pending 乐观自旋（书中"先读后锁"）** `qspinlock.c:167-206`：

```c
val = queued_fetch_set_pending_acquire(lock);  // 原子置 pending 位并取旧值
...
if (val & _Q_LOCKED_MASK)
	smp_cond_load_acquire(&lock->locked, !VAL); // ★ 只对 locked 字节做【纯读】轮询
clear_pending_set_locked(lock);                 // 持有者释放后，(0,1,0)→(0,0,1) 拿锁
```

- 只有一个竞争者时（队列还没建立），它**不排队**，先置 pending 位，然后**纯读** locked 字节等持有者走——**这就是书中"先读探测再原子抢"**：轮询是读，持有者只读自己临界区数据时双方缓存行可共享，不再来回搬；
- 更贴切的"先读后原子抢"形态还有 `queued_spin_trylock()`（`include/asm-generic/qspinlock.h:90`）：先 `atomic_read` 纯读，**非零直接放弃（零原子开销）**，读到 0 才尝试 cmpxchg——与书中伪代码逐句对应；
- arm64 上这个等待循环被架构覆写成 **WFE 等待**（见 2.7）：`smp_cond_load_acquire` → `__cmpwait_relaxed` = `sevl; wfe; ldxr…`——读到值没变就**睡在事件寄存器上**，持有者写 locked 字节触发一致性事件把 WFE 惊醒。**= 书中 MONITOR/MWAIT 的 arm64 等价物**。

**② 有界等待（退避思想的残余）**：`qspinlock.c:150-154` 对 `val == _Q_PENDING_VAL` 的中间态只轮询 `_Q_PENDING_LOOPS` 次（generic=1，`kernel/locking/qspinlock.h:27`；x86 定义为 512）保证前进，不做无限指数退避——Linux **用"排队"根治了退避要缓解的问题**（见专篇）。

**③ MCS 排队（图 8-11）** `qspinlock.c:212-380`：两个以上竞争者后建队列，每个等待者自旋在**自己的 per-CPU 节点**上（一行独占缓存行）——完整分析独立成篇：**[005.专题-图8-11多锁避免缓存抖动.md](./005.专题-图8-11多锁避免缓存抖动.md)**。

## 2.6 spin vs switch：mutex 的乐观自旋（adaptive spinning 的工程版）

书中"记录最近自旋时长、不行就切换"，Linux 对**睡眠锁**（mutex/rwsem）的标准答案是 **optimistic spinning**：

```c
// kernel/locking/mutex.c:460（设计说明，节选）
/* We try to spin for acquisition when we find that the lock owner
 * is currently running on a (different) CPU and while we don't
 * need to reschedule. The rationale is that if the lock owner is
 * running, it is likely to release the lock soon.        ← 判据不是历史时长，
 *                                                          而是"持有者此刻正在 CPU 上跑"
 * The mutex spinners are queued up using MCS lock so that
 * only one spinner can compete for the mutex.             ← 自旋者也要先排 MCS 队，
 *                                                          防止 N 个 CPU 同时空转冲击锁字
 */
static __always_inline bool
mutex_optimistic_spin(struct mutex *lock, ...)          // mutex.c:474
{
	if (!mutex_can_spin_on_owner(lock)) goto fail;   // need_resched 或 owner 不在跑 → 直接睡
	if (!osq_lock(&lock->osq)) goto fail;            // 排进乐观自旋队列（MCS 变体）
	for (;;) {
		owner = __mutex_trylock_or_owner(lock);      // 反复试拿
		if (!owner) break;
		if (!mutex_spin_on_owner(lock, owner, ...))  // 盯 owner 字段：
			goto fail_unlock;                       //   owner 睡了/被抢占了/我该调度了 → 放弃
		cpu_relax();
	}
	osq_unlock(&lock->osq); return true;
	...
fail:
	if (need_resched()) { __set_current_state(TASK_RUNNING); schedule_preempt_disabled(); }
	return false;                                    // → 慢路径：挂到等待队列去睡
}
```

与书中逐条对应：

| 书中 | mutex 实现 |
|-|-|
| "持有者还在跑就快释放了" | `mutex_spin_on_owner()`（mutex.c:385）盯 `owner->on_cpu`（任务的 owner 字段存在锁里，`atomic_long_t owner`，mutex.c:53 osq 挂其上）；`vcpu_is_preempted` 检测虚拟化下持有者 vCPU 被抢的情形（arm64 恒 false：`arch/arm64/include/asm/spinlock.h:22`）|
| "我该让 CPU 了就别自旋" | 循环里反复查 `need_resched()`——IPI 投递 RESCHEDULE 会把它置位并惊醒 WFE 等待（osq_lock.c:142-145 注释）|
| "切换的成本高（两次切换+缓存全凉）" | 失败路径才 `schedule()` 睡觉；醒来时缓存/TLB 已凉——正是书中算的那笔账 |
| 防止自旋风暴 | 自旋者们先经 `osq_lock()`（`kernel/locking/osq_lock.c:93`）排队，**同一时刻只有一个 spinner 真正在盯锁** |

配置：`CONFIG_MUTEX_SPIN_ON_OWNER`（mutex.c:52）。rwsem（`kernel/locking/rwsem.c`）有对应的同一套乐观自旋。

## 2.7 省电等待：arm64 的 WFE = 书中的 MONITOR/MWAIT

书中 x86 的 MONITOR/MWAIT，arm64 上由三件套实现：

```c
// arch/arm64/include/asm/cmpxchg.h:214 —— 等待原语：sevl 预置事件 + wfe 睡等 + ldxr 读
asm volatile(
"	sevl\n"                          // 发一个本地事件，先跳过第一次 wfe（值可能已变）
"	wfe\n"                           // 睡在事件寄存器上，几乎不耗电
"	ldxr" #sfx "\t%" #w "[tmp], %[v]\n"  // 独占读目标字
"	eor ...\n  cbnz ...\n  wfe\n"    // 值没变 → 继续睡
);

// arch/arm64/include/asm/barrier.h:198 —— 用它覆写通用 smp_cond_load_relaxed：
#define smp_cond_load_relaxed(ptr, cond_expr)          \
	for (;;) {                                          \
		VAL = READ_ONCE(*__PTR);                        \
		if (cond_expr) break;                           \
		__cmpwait_relaxed(__PTR, VAL);  /* ← 上面那个 wfe 序列 */ \
	}
```

**机制**：`WFE` 监听"事件寄存器"；一致性协议发现**本核持有的独占监视器被远端写清除**（或 SEV 广播）时置事件 → WFE 醒来重读。**效果等同 MONITOR/MWAIT：自旋但不烧 CPU**。qspinlock 慢路径、MCS 等待、osq 等待全部经 `smp_cond_load_*` 间接受益。

忙等循环里的 `cpu_relax()` 在 arm64 是 `yield` 指令（`arch/arm64/include/asm/vdso/processor.h:10`）——提示超线程/虚拟化环境"我在等人"，把执行资源让给同核的另一个超线程或 vCPU。

## 2.8 书中没写但属于本话题的两个 Linux 实践

1. **持自旋锁禁止抢占**（`include/linux/spinlock_api_smp.h:154`：`__raw_spin_lock` = `preempt_disable()` + 加锁）：直接消灭了书中 8.1.4"时间片到期时线程持自旋锁被调走、其他 CPU 空转干等"的病态——Linux 的解法比书中"设标志宽限"更彻底：**持锁期间根本不会失去 CPU**（PREEMPT_RT 内核则把自旋锁换成可睡眠的 rtmutex，`kernel/locking/spinlock_rt.c`，从另一头解决同一问题）。
2. **读写锁**：书中没展开的"SMP 锁分型"，Linux 有 qrwlock（`kernel/locking/qrwlock.c`：读者计数字节 + 写者用自旋锁）与 per-CPU rwsem（`kernel/locking/percpu-rwsem.c`），思路仍是"把共享拆成 per-CPU 私有 + 少量全局同步"，与本节精神一脉相承。

## 3. 学习小结

- **一根主线**：互斥的基础是"对同一缓存行的原子访问"；一切锁设计都是在**减少对同一行的原子写**（先读后锁 → 退避 → 排队到各自私有的行）。
- **两个分水岭**：竞争人数 0→1（pending 乐观自旋：纯读+WFE，仍是"锁字上的自旋"）、1→N（MCS 队列：自旋点搬到**每 CPU 私有节点**——抖动清零）。
- **三种等待方式**（按费电排序）：纯读轮询（`cpu_relax`=YIELD）< WFE 事件等待（= MONITOR/MWAIT）< 睡眠切换（mutex 慢路径）。Linux 按"持有者在跑吗 / 我该让 CPU 吗"自动选。
- 书中 TSL → x86 LOCK 前缀 → arm64 LL/SC + LSE：**原子性从"锁总线"进化为"锁缓存行"**，但图 8-10 教训不变：原子操作必须不可分割。
