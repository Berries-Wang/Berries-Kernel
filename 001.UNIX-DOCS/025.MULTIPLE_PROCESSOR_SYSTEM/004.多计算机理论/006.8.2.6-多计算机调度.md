## 1. 书中理论

**与多处理器（8.1.4）的对照**就是本节全部要点：

| 维度 | 多处理器 | 多计算机 |
|-|-|-|
| 进程住哪 | 全部进程在同一内存，任何 CPU 原则上可跑任何进程 | 每节点自有内存、**自有进程集**；CPU 1 想跑节点 4 的进程得先费大劲把进程搬来 |
| 单一中央就绪队列 | 可行（图 8-12 的做法，有队列争用缺点）| **不可行**（进程只能在其所在节点的 CPU 上跑）|
| 调度本身 | 难（两维：选谁 + 放哪）| **更容易**（节点内就是单机调度）|
| 真正的难题 | —— | **进程该放哪个节点**（分配比调度重要）→ 交给 8.2.7 |
| 可用的多处理器算法 | 分时/亲和性/空间共享/组调度 | 节点内**任意本地调度算法**都行；**组调度仍可用**——只需初始约定"哪个时间片跑谁" + 各节点时间片对齐启动的方式 |

**一句话**：多计算机把"调度"拆成两层——**节点间分配**（8.2.7）+ **节点内调度**（退化为单机问题）。

## 2. Linux 对照

| 书中概念 | Linux 7.1.3 | 位置 |
|-|-|-|
| 节点内 = 单机调度 | 正是现实：每节点一个独立内核，调度器只管本机（per-CPU rq + 调度域，见 [../002.多处理器理论/004.8.1.4](../002.多处理器理论/004.8.1.4-多处理器调度.md)）| `kernel/sched/` |
| 单一中央就绪队列不可行 | 集群上没有（也永远不该有）跨机全局就绪队列；跨机"派活"= 集群编排层（Slurm/K8s 调度器、用户态）| 用户态 |
| "创建进程时选节点" | 容器/VM 调度：K8s 按 CPU/内存请求选节点；单机内对应 fork 时的 CPU 选择（唤醒路径 `select_task_rq`）| `kernel/sched/fair.c`（`select_task_rq_fair`）|
| 组调度跨节点 | 无内核对应（8.1.4 已述：Linux 无 gang scheduling）；跨节点"时间片对齐"这类全局时钟同步不存在于调度器 | — |
| 进程迁移（"费大劲搬进程"）| 用户态 checkpoint/restore（CRIU）可整进程搬迁；内核无透明跨机迁移 | 用户态 CRIU |

**学习小结**：本节的价值是**坐标系**——它解释了为什么 Linux 内核"看起来完全不处理集群调度"：那不是缺失，而是分工——节点内归内核，节点间归中间件。
