# 8.2.2 底层通信软件（Low-Level Communication Software）

> 书页 562–565（PDF 591–594）。§8.2 逐小节精读之二——**多计算机性能的灵魂：与复制作战**。
> 同目录：[001.8.2.1](./001.8.2.1-多计算机硬件.md)｜[003.8.2.3](./003.8.2.3-用户级通信软件.md)｜[004.8.2.4](./004.8.2.4-远程过程调用RPC.md)｜[005.8.2.5](./005.8.2.5-分布式共享内存DSM.md)｜[006.8.2.6](./006.8.2.6-多计算机调度.md)｜[007.8.2.7](./007.8.2.7-负载均衡.md)

**一句话**：高性能通信的敌人是**多余的复制**。本小节数清楚有几次复制、怎么砍到最少，以及砍复制引出的三个新问题（用户态网卡的安全、DMA 与分页的冲突、RDMA）。

---

## 1. 书中理论

### 1.1 复制账本：最好 3 次，通常 5 次

- **理论最优（3 次复制）**：① 源主 RAM → 源网卡 RAM；② 源网卡 → 目的网卡（线路上）；③ 目的网卡 RAM → 目的主 RAM。
- **现实（网卡只映射进内核地址空间时）= 5 次**：用户进程发包必须**系统调用**陷入内核；内核收/发两侧还要**各多拷一次**到自己的缓冲：
  - 发送侧：避免传输途中**缺页**（网卡 DMA 期间页被换走会传错数据）；
  - 接收侧：内核**不知道包给谁**，得先收下来看过才能决定去向。
- 代价：RAM 搬运是瓶颈时，多出的两次复制让**端到端延迟翻倍、吞吐减半**。

### 1.2 网卡映射进用户空间：快了，但两个新问题

让用户进程直接把包放进网卡，绕过内核——性能救回来了，麻烦跟着来：

1. **多进程争用**：网卡映射给谁？A 映射了，B 要发怎么办？A 的网卡上到了 B 的包怎么办（尤其 A、B 属于不同主人、互不相帮）？映射进所有需要的进程 → 需要**互斥**，但 mutex 假设进程**合作**——多用户环境下有人可以锁住网卡不放。**结论：只有每节点单进程时才真正好用**（或给不同进程映射网卡 RAM 的不同部分）。
2. **内核自己也要网络**（如访问远程文件系统）：内核与用户共享网卡不行（内核包到了用户映射的板子上；用户可以伪装内核发包）。**最简单的解：两块网卡**——一块映射用户态跑应用流量，一块归内核。很多多计算机真这么干。

### 1.3 现代解药：多队列网卡 + 核亲和

- 新网卡常是**多队列（multiqueue）**：16 发 16 收队列，可虚拟化出多个"虚拟端口"。
- 更好：**核亲和（core affinity）**——网卡自带哈希逻辑，对 **TCP 流字段（IP 地址 + 端口号）** 哈希，同流的段进同一队列、由固定 CPU 服务——**同流同核，缓存是热的**；也给每个虚拟机一个独立队列（虚拟化友好）。

### 1.4 节点到网卡：DMA 与分页的冲突

- 网卡板载 DMA 直接从 RAM 拷包最快，但 **DMA 用物理地址**且独立于 CPU 运行（无 IOMMU 时）：
  - 用户进程只知道**虚拟地址**，不知道物理地址；为地址转换做系统调用，又把"避免系统调用"的初衷丢了；
  - **换页灾难**：DMA 发送中操作系统换出该页 → 发出**错数据**；DMA 接收中换出 → 不仅丢包，还**毁掉一页无辜内存**。
- 解法：**pin/unpin 系统调用**把页临时钉住。代价：每包两次系统调用；小包（≤64B）开销不可接受；大包（≥1KB）可容忍；中间看硬件。另加：软件复杂度 + 贪心进程把全部页钉死怎么办（DoS 风险）。

### 1.5 RDMA（Remote Direct Memory Access）

- 一台机器**直接 DMA 读写另一台机器的内存**，两端 OS 都不经手，数据直达应用内存——HPC、高频交易的最爱。
- 三个没说的代价：① 页仍要 pin；② **放置完成不通知**——对端程序不知道数据到了，常见做法是**接收方轮询内存里的一个标志字节**（浪费 CPU）；③ 极端场景（高频交易）直接定制 **FPGA 网卡**，wire-to-wire <1μs——"OS 基本不参与"。

## 2. Linux/arm64 对照

书中每个问题在 Linux 里都有成熟答案，且基本都成了生产标配：

| 书中问题/概念 | Linux 7.1.3 实现 | 源码（已核对）|
|-|-|-|
| 减少 5 次复制：文件→网络 | `sendfile(2)`：文件页直接进 socket，不经用户态 | `fs/read_write.c:1304`（`do_sendfile`）、`:1400`（系统调用）|
| 管道式零拷贝/页聚合 | `splice(2)`/`vmsplice(2)`（页在缓冲间移动指针而非复制）| `fs/splice.c:1616`（splice）、`:1578`（vmsplice）|
| 用户缓冲零复制发送 | `MSG_ZEROCOPY`：pin 用户页，DMA 直接从用户内存发，完成时通知（err 队列）| 标志 `include/linux/socket.h:346`、路径 `net/ipv4/tcp.c:1141`（`tcp_sendmsg_locked` 内分支）|
| 用户态直接收包（网卡映射用户空间）| **AF_XDP**：UMEM 区域注册给驱动，收包零拷贝进用户内存——书中"接口板映射进用户态"的安全版（UMEM 按进程隔离，解决了"多进程争用/伪装内核"）| `net/xdp/xsk.c`、`net/xdp/xdp_umem.c` |
| 异步收发、避免每包系统调用 | **io_uring**（提交/完成双环共享内存）；接收零拷贝 `io_uring/zcrx.c` | `io_uring/`（收发 SQ/CQ 环）|
| pin 页保 DMA 安全 | `get_user_pages()` / `pin_user_pages()`（DMA 场景用 pin 变体，FOLL_PIN 语义）| `mm/gup.c:2644`（gup）、`:3376`（pin_user_pages）|
| 多队列 + 核亲和 | 硬件 RSS（网卡哈希分流）；软件 **RPS/RFS**（按流哈希选核）+ 发送侧 **XPS** | `net/core/dev.c:5107`（`get_rps_cpu`）、`:3053`（`netif_set_xps_queue`）|
| 两块网卡（用户态一块、内核一块）| Linux 无需双卡：**队列级隔离**替代板级隔离（每进程/每 VM 各得队列）；内核流量走内核队列 | 多队列框架 `net/core/dev.c` |
| RDMA | 内核 RDMA 栈（IB/RoCE/iWARP），页 pin 同样走 gup | `drivers/infiniband/core/` |
| "接收完成不通知→轮询标志字节" | AF_XDP 可配置 **need_wakeup** 轮询；io_uring 收完直接写 CQ（中断/轮询可配置，`io_uring` SQPOLL）| `net/xdp/xsk.c`、`io_uring/` |
| DMA 物理地址问题 | **SMMU/IOMMU**：DMA 用 IOVA，页可迁移而映射保持——书中"无 IOMMU 才有换页灾难"的另一解 | arm64 `drivers/iommu/dma-iommu.c`（`arch/arm64/mm/dma-mapping.c` 挂接）|

**两句话抓住本节**：
1. 书中"复制账本"在 Linux 的演化：`write()` 2 次拷贝 → `sendfile` 砍掉用户态往返 → `splice/MSG_ZEROCOPY` 砍到 DMA 直取 → AF_XDP/io_uring 把系统调用也摊销掉——**一路都在做减法**。
2. 书中"安全 vs 速度"的两难（网卡进用户态），Linux 用**隔离的 UMEM/队列 + IOMMU** 兼得了两者——这是教材写作年代（2000 年代方案）到今天的主要增量。
