## 1. 书中理论

**范式**：一切皆**对象**——变量 + 方法捆绑，**禁止直接碰变量**（区别于 Linda 的纯数据元组）。

**CORBA**（Common Object Request Broker Architecture，1991–2012 持续更新）：

- 定位：**异构**硬件/OS/**语言**环境下的 C/S 系统——客户机进程调用（可能远端的）服务器机器上对象的操作。
- **ORB（Object Request Broker）**：插在客户与服务器之间撮合双方，重要性大到系统以它命名。
- **IDL（Interface Definition Language）**：每个对象用 IDL 定义接口（导出哪些方法、参数类型）：
  - IDL → 编译出 **client stub** 进客户库（提前知道要用的对象就链接它）；
  - IDL → 编译出 **server 骨架（skeleton）**在服务器侧；
  - 事先不知道要调谁 → **动态调用**（细节超出本书范围）。
- **ORB 隐藏什么**：服务器**位置**、服务器是二进制还是脚本、服务器硬件与 OS、对象当前是否活跃、两个 ORB 之间怎么通信（TCP/IP？RPC？共享内存？）。
- **硬伤**：**每个对象只存在于一个服务器上**——全球范围的热点对象（人人都调）性能崩溃。实践结论：CORBA 只在**单机 / 一个 LAN / 一个公司**规模可用。

> 与 8.2.4 RPC 的关系：CORBA = RPC（stub/编组，图 8-20 五步）+ 面向对象（接口继承、对象引用）+ ORB 中间层（位置/平台全透明）。四条"草下的蛇"也一并被 IDL 的强类型接口解决。

## 2. Linux 对照

| 书中概念 | Linux/现状 | 说明 |
|-|-|-|
| CORBA | **内核无实现**（本就属用户态中间件）；GNOME 早年 Bonobo/ORBit 已淘汰 | — |
| IDL → stub/skeleton | 用户态同构物遍地：gRPC 的 `.proto`（protoc 生成 stub）、Thrift IDL、Cap'n Proto——**IDL+代码生成**范式胜出，CORBA 本体凋零 | 用户态 |
| ORB 的"隐藏一切" | gRPC 等由**名称服务+服务发现**（etcd/Consul/DNS SRV）承担"隐藏位置"；序列化/传输由库承担 | 用户态 |
| "热点对象崩溃"的当代解 | **无状态服务 + 负载均衡 + 副本**（书 8.3.5 时代的教训变成了微服务第一原则：别把状态钉在一个对象上）；缓存层（Redis/CDN）挡住全球热点 | 用户态 |
| 内核唯一沾边处 | eBPF 的 **BTF**（BPF Type Format）+ `BPF_PROG_TYPE_STRUCT_OPS`：内核里的"接口描述 + 函数指针表注册"，形似 IDL/骨架，但只用于内核内扩展点 | `include/linux/btf.h`、`kernel/bpf/bpf_struct_ops.c` |

**学习小结**：CORBA 教给系统设计两件事——① **IDL 强类型接口**是跨异构通信的正确起点（活到了 gRPC）；② **单点对象承载全球访问必死**（催生了无状态微服务）。内核侧唯一呼应是 BTF/struct_ops 这种"描述接口+注册实现"的形态。
