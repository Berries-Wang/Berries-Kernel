# 001.KVM VM-exit 与 VM-entry：指令级全链路（arm64）

> 回答两个问题：
> 1. **VM → VMM**：guest 里执行了什么指令/发生了什么事件，才会"陷"进硬件虚拟化层（KVM hyp——**KVM 运行在 EL2 的那部分代码**，详见 §1.1 名词速览）？
> 2. **VMM → VM**：硬件虚拟化层用什么指令把 CPU 还给虚拟机？
>
> 只分析 arm64。每一步都标注**具体指令**（`msr`/`mrs`/`eret`/`hvc`/`ldp`…）和**具体寄存器**。

## 1. 速答

| 方向 | 用什么 | 出处（7.1.3） |
| - | - | - |
| **VM-entry**（VMM → guest） | **`eret`** —— 全链路唯一的一条"进入"指令 | `arch/arm64/kvm/hyp/entry.S:88` |
| **VM-exit**（guest → VMM） | **没有专用退出指令**。同步类 = guest 执行某条指令触发异常（`hvc`/`smc`/`msr`/`mrs`/`wfi`/`wfe`/访存 abort…）；异步类 = IRQ/FIQ/SError 被 HCR_EL2 路由到 EL2，与指令无关 | `arch/arm64/kvm/handle_exit.c:376`（EC 分发表） |

```
 EL0    QEMU (VMM 用户态)                                        guest 用户态
        |  ioctl(KVM_RUN)                                          ^
        v                                                          | eret 进入
 EL1    宿主 Linux 内核                                           guest 内核
        |  kvm_arch_vcpu_ioctl_run()                    +----------+----------+
        |  kvm_call_hyp_ret(__kvm_vcpu_run)             |  guest 里执行 hvc/smc/msr/
        |  x0 = SMCCC func id                           |  wfi/访存 abort... 或被
        |  hvc #0 =====================> EL2            |  IRQ/FIQ/SError 打断
        v                                               v

        |  msr hcr_el2 / vbar_el2 / vtcr+vttbr_el2 ...
        |__guest_enter()
        |  eret ----> guest (PC<-ELR_EL2, PSTATE<-SPSR_EL2)
        +                                              VM-exit: 异常自动路由到
                                                       EL2, 落在 KVM hyp 向量表
```

### 1.1 名词速览（KVM hyp 是什么）

| 名词 | 解释 |
| - | - |
| **KVM hyp** | **KVM 中运行在 EL2 的那一部分代码**（源码目录 `arch/arm64/kvm/hyp/`，本文的 `entry.S`/`hyp-entry.S`/`nvhe/`/`vhe/` 都在里面）。KVM 本体是宿主内核里的一个子系统，它分成两半：**大脑**——vCPU 调度、指令/寄存器模拟、MMIO 分发（跑在 EL1 宿主内核里，`arm.c`/`handle_exit.c`/`sys_regs.c` 等）；**hyp**——贴近硬件干重活的部分：保存/恢复寄存器组、切 stage 2 页表、开关陷阱、执行进出 guest 的 `eret`（跑在 EL2）。nVHE 配置下 hyp 是独立装载到 EL2 的小映像（有自己的页表、栈、per-cpu 基址 `TPIDR_EL2`）；VHE 配置下没有独立映像，宿主内核本体就运行在 EL2，hyp 代码直接以内核身份执行（§3.6） |
| 宿主内核（host kernel） | 跑 QEMU 的那个 Linux。nVHE 下在 EL1，VHE 下在 EL2 |
| VMM / QEMU | 宿主上的用户态进程（EL0），KVM 的"用户"：发 `ioctl(KVM_RUN)`、做设备模拟；内核填好 `KVM_EXIT_*` 后回到它 |
| guest / vCPU | 被虚拟出来的机器 / 虚拟 CPU：guest 内核在 EL1、guest 用户态在 EL0；vCPU = `struct kvm_vcpu`（KVM 用它保存每次切出来的寄存器现场，即 §7 的"vcpu 上下文"） |
| nVHE / VHE | KVM 在 arm64 的两种运行模式（硬件 FEAT_VHE + 启动参数 `kvm-arm.mode=` 决定，kernel-parameters.txt:3192 / arm.c:3112）：nVHE = 宿主 EL1 与 hyp EL2 分离（§3.3-3.5）；VHE = 宿主内核直接跑在 EL2（§3.6）。另有 protected 模式（pKVM），本文不展开 |
| **SMCCC** | **SMC Calling Convention**（ARM 规范 DEN 0028 定义的**跨异常层服务调用约定**）：调用方把**功能号放 x0、参数放 x1-x7**，被调方把返回值放 x0-x3；配两条"门铃指令"——`SMC` 打给 EL3 固件、`HVC` 打给 EL2 hypervisor（选哪条 = conduit，见 §4.8）。功能号 x0 的位编码（`include/linux/arm-smccc.h:25-36`）：bit31=fast/yielding 调用、bit30=SMC32/SMC64、bit[29:24]=属主 OEN（标准服务/厂商区等）、bit[15:0]=功能号。PSCI、TRNG、spectre 缓解、KVM PTP 都是定义在 SMCCC 之上的具体服务；KVM 的 `kvm_call_hyp_nvhe`（kvm_host.h:1280）与 guest 的 PSCI 调用都走它 |

关键认知（对应 [../README.md](../README.md) 步骤 1 的"捕捉并下陷"）：

- **进 guest 只有一条指令**：`eret`。它是"异常返回"，KVM 在执行它之前把 ELR_EL2/SPSR_EL2 填成 guest 的 PC/PSTATE，于是"返回异常"就变成了"进入虚拟机"。
- **出 guest 没有专用指令**：CPU 处理的仍然是 guest 的正常指令流，真正把控制权交给 KVM 的是 **异常进入（exception entry）** 这套硬件机制——guest 的指令只是"触发条件"，异步中断则连触发条件都不是指令。

## 2. 硬件地基：异常的进入与返回

KVM 的进/出完全建立在 arm64 异常模型之上。这一节先剥离 KVM，只看硬件（ARM ARM DDI0487M D1.4）。

### 2.1 异常进入：硬件自动做的 4 件事

ARM ARM D1.4.2 "Exception entry"（D1-7093）规定，一条异常被取到 ELx 时硬件自动：

```
 原状态 (如 guest EL1)                        目标状态 (EL2)
 ---------------------                        --------------------------
 PSTATE ───────────────────────────────────>  SPSR_EL2   (保存旧 PSTATE)
 PC(返回地址) ─────────────────────────────>  ELR_EL2    (保存返回地址)
 异常原因 ─────────────────────────────────>  ESR_EL2    (syndrome: EC[31:26]+ISS)
 (访存类) 出错 VA ─────────────────────────>  FAR_EL2
 (stage 2 fault) 出错 IPA ─────────────────>  HPFAR_EL2
                                              PSTATE.{D,A,I,F}=1111 (关中断)
                                              PSTATE.EL = EL2
 PC <─────── VBAR_EL2 + 向量偏移 (硬件跳转, 无软件参与)
```

向量偏移由"异常种类 + 来自哪个 EL + 用哪个 SP"决定（D1.4.1.6，D1-7092）：

```
 偏移      异常来源                       用途（在 KVM 的向量表里）
 ---------------------------------------------------------------------------
 0x000     当前 EL + SP_EL0               (guest EL0 才可能, KVM 不用)
 0x080     当前 EL + SP_EL0  IRQ
 0x100     当前 EL + SP_EL0  FIQ
 0x180     当前 EL + SP_EL0  SError
 0x200     当前 EL + SP_ELx               EL2 自己出的同步异常 (el2_sync)
 0x280     当前 EL + SP_ELx  IRQ
 0x300     当前 EL + SP_ELx  FIQ
 0x380     当前 EL + SP_ELx  SError
 0x400     低一级 EL (AArch64) 同步       ★ guest 陷进来落在这里 (el1_sync)
 0x480     低一级 EL (AArch64) IRQ        ★ guest 的 IRQ exit
 0x500     低一级 EL (AArch64) FIQ        ★ guest 的 FIQ exit
 0x580     低一级 EL (AArch64) SError     ★ guest 的 SError exit
 0x600     低一级 EL (AArch32) 同步       32 位 guest
 0x680/700 低一级 EL (AArch32) IRQ/FIQ
```

### 2.2 异常返回：`eret` 指令

ARM ARM D1.4.4 "Exception return"（D1-7098）+ 伪代码 `AArch64.ExceptionReturn`（J1-15803）：

```
 eret  (在 ELx 执行)
   PC     <──  ELR_ELx      目标 PC
   PSTATE <──  SPSR_ELx     恢复旧 PSTATE (含 EL、中断屏蔽位)
```

- `eret` 本身并不知道"返回给宿主还是 guest"——它只管把 ELR/SPSR 装回 PC/PSTATE。**KVM 正是利用这一点**：进入 guest 前，把 ELR_EL2/SPSR_EL2 填成 guest 状态，`eret` 就成了 VM-entry（§3.5）。
- **非法异常返回**：若 SPSR 携带的目标状态不合法（如从 EL2 返回 EL2、返回 AArch32 Hyp），硬件把 PSTATE.IL 置 1，且 **PSTATE.{EL, nRW, SP} 保持不变**（D1-7099 规则 RVWJHB："PSTATE.{EL, nRW, SP} are unchanged"）——**EL 并不切换**，于是在执行 ERET 的当前异常级，下一条指令立即触发 Illegal Execution State 异常（D1-7100）。这正好解释了 KVM 为何在 `el2_sync`（EL2 自身的 0x200 向量）里检查这个位（§4.3，hyp-entry.S:95-96 查 SPSR bit[20]），并且故意用 IL 位做安全网：恢复 EL2 返回状态时，若发现要把 CPU"还"给高于 EL1 的状态，就主动写一个带 IL 的 SPSR 让 ERET 立即失败（`hyp/include/hyp/sysreg-sr.h:313-325` 的注释与 `pstate = PSR_MODE_EL2h | PSR_IL_BIT`）。

### 2.3 到哪个 EL、用哪张向量表

伪代码 `AArch64.TakeException`（J1-15765/15767）：`BranchTo(VBAR_ELx[]<63:11>:vect_offset<10:0>)`，其中 `VBAR_ELx[] = VBAR_EL[S1TranslationRegime()]`（J1-15942）。结论：

- **异常被取到 EL2 → 用 VBAR_EL2；被取到 EL1 → 用 VBAR_EL1**。
- guest（EL1）的异常被路由到 EL2 → 硬件跳 `VBAR_EL2 + 0x400..0x580`。

VHE（FEAT_VHE，E2H=1）有一层寄存器重定向（D8.13.2，D8-7714 条件 + 表 D8-113）：**在 EL2 且 E2H=1 时，访问 EL1 寄存器编码实际访问的是 EL2 等价寄存器**（表中含 `VBAR_EL1 → VBAR_EL2`）。这层重定向是理解 KVM VHE 代码里"往 `vbar_el1` 写 hyp 向量"的关键，见 §3.6。

## 3. VM-entry 全链路：宿主 → guest

### 3.1 触发：QEMU 的 ioctl

QEMU 调 `ioctl(vcpu_fd, KVM_RUN)`，进入宿主内核的运行循环：

```c
// arch/arm64/kvm/arm.c:1243
int kvm_arch_vcpu_ioctl_run(struct kvm_vcpu *vcpu)
{
        ...
        while (ret > 0) {                       // arm.c:1266  运行主循环
                ...
                /**************************************************************
                 * Enter the guest
                 */
                trace_kvm_entry(*vcpu_pc(vcpu));        // arm.c:1321
                ret = kvm_arm_vcpu_enter_exit(vcpu);    // arm.c:1324
                vcpu->mode = OUTSIDE_GUEST_MODE;
                /* Back from guest */                   // arm.c:1329
                ...
                ret = handle_exit(vcpu, ret);           // arm.c:1408
        }
        ...
}
```

注意这个 `while` 循环：**exit 处理完若返回 >0（已处理，可以继续跑），就原地再走一遍 entry 链**。VM-exit 和 VM-entry 是同一个循环的两半。

### 3.2 最后一跳：`kvm_call_hyp_ret(__kvm_vcpu_run)`

```c
// arch/arm64/kvm/arm.c:1222
static int noinstr kvm_arm_vcpu_enter_exit(struct kvm_vcpu *vcpu)
{
        guest_state_enter_irqoff();
        ret = kvm_call_hyp_ret(__kvm_vcpu_run, vcpu);   // arm.c:1227
        guest_state_exit_irqoff();
        return ret;
}
```

`kvm_call_hyp*` 宏按 VHE/nVHE 分叉（`arch/arm64/include/asm/kvm_host.h:1276-1317`）：

```c
#define kvm_call_hyp_nvhe(f, ...)                       \
        ({                                              \
                struct arm_smccc_res res;               \
                arm_smccc_1_1_hvc(KVM_HOST_SMCCC_FUNC(f), \   // kvm_host.h:1280
                                  ##__VA_ARGS__, &res); \
                WARN_ON(res.a0 != SMCCC_RET_SUCCESS);   \
                res.a1;                                 \
        })

#define kvm_call_hyp(f, ...)                            \
        do {                                            \
                if (has_vhe()) {                        \
                        f(__VA_ARGS__);                 \   // kvm_host.h:1294
                        isb();                          \
                } else {                                \
                        kvm_call_hyp_nvhe(f, ##__VA_ARGS__); \
                }                                       \
        } while(0)                                      // kvm_host.h:1291
```

### 3.3 nVHE：一条 `hvc #0` 下潜到 EL2

`arm_smccc_1_1_hvc` 展开成内联汇编指令 `hvc #0`（`include/linux/arm-smccc.h:548`，SMC 对应 `smc #0` 在 :547）：

```
 宿主内核 EL1                              KVM hyp EL2 (nVHE)
 --------------                            ------------------
 arm_smccc_1_1_hvc()
   |  x0 = KVM_HOST_SMCCC_FUNC(__kvm_vcpu_run)  (SMCCC func id)
   |  x1..x3 = 参数 (这里是 vcpu 指针)
   v
 hvc #0  ──── 异常进入(硬件, 零软件参与):
                SPSR_EL2 ← 宿主 PSTATE      (宿主被打断时的现场)
                ELR_EL2  ← hvc 下一条指令   (返回地址, 已执行类 → 下一条,
                                             D1-7092 RDKWPP)
                ESR_EL2  ← EC=0x16 (HVC64), ISS=imm16(=0)
                PSTATE.EL=EL2, DAIF=1111
                PC ← VBAR_EL2 + 0x400 ─────────────────────┐
                                                           v
                                    VBAR_EL2 = __kvm_hyp_host_vector
                                    (hyp/nvhe/host.S:234, 由 nvhe/switch.c:110
                                     在每次退出 guest 后用 msr vbar_el2 装回)
                                                           |
                                    host_el1_sync_vect (host.S:170):
                                      stp x0, x1, [sp, #-16]!   (:173 存参)
                                      mrs x0, esr_el2           (:174 取 syndrom)
                                      ubfx x0, x0, #EC_SHIFT    (:175 取 EC)
                                      cmp x0, #ESR_ELx_EC_HVC64 (:176)
                                                           v
                                    __host_hvc (host.S:146)
                                      v
                                    __host_exit (host.S:17):
                                      get_host_ctxt x0 (TPIDR_EL2 定位 per-cpu)
                                      stp x2..x17 / save_callee_saved_regs
                                        → 宿主 x0-x29/lr 存进 host_ctxt
                                      bl handle_trap (host.S:61 → hyp-main.c:896)
                                                           |
                                    handle_trap: mrs esr_el2, EC==HVC64 →
                                    handle_host_hcall (hyp-main.c:748)
                                      | 按 x0(func id) 查 HANDLE_FUNC 表 (:704)
                                      v
                                    handle___kvm_vcpu_run (hyp-main.c:198)
                                      v
                                    __kvm_vcpu_run(vcpu) (hyp-main.c:224
                                      → nvhe/switch.c:258)
```

要点：**宿主内核调用 hyp 与 guest 无关**，这条 `hvc #0` 通道（SMCCC 协议——SMC Calling Convention，ARM 定义的"跨异常层服务调用约定"：功能号放 x0、参数放 x1-x7，详见 §1.1）是 nVHE 下宿主↔hyp 的一切调用的唯一入口；guest 的 HVC 走的是另一张向量表（§4.3）。

### 3.6 VHE 的差异：宿主本来就在 EL2，向量表靠 E2H 重定向

VHE（FEAT_VHE，E2H=1）下宿主内核运行在 EL2，`kvm_call_hyp` 不需要 HVC（kvm_host.h:1293-1295 直接调函数）。入口函数变成 `__kvm_vcpu_run_vhe`（`hyp/vhe/switch.c:572`），核心循环与 nVHE 相同（:598-603 的 do-while 调 `__guest_enter`）。

但**寄存器的装载方式完全不同**，这是 VHE 代码最反直觉的地方。先看宏别名（`arch/arm64/include/asm/kvm_hyp.h:29-32`，VHE 编译分支）：

```c
#define read_sysreg_el1(r)   read_sysreg_s(r##_EL12)   // VBAR_EL1 → mrs VBAR_EL12 编码
#define write_sysreg_el1(v,r) write_sysreg_s(v, r##_EL12)
#define read_sysreg_el2(r)   read_sysreg_s(r##_EL1)    // ELR_EL2 → mrs ELR_EL1 编码
#define write_sysreg_el2(v,r) write_sysreg_s(v, r##_EL1)
```

**编码映射表**（VHE，在 EL2 执行时）：

| KVM 源码写法 | 实际指令 | 硬件效果 | 依据 |
| - | - | - | - |
| `write_sysreg(x, vbar_el1)` | `msr VBAR_EL1` | 写 **VBAR_EL2** | D8.13.2 重定向（D8-7714 条件 + 表 D8-113 D8-7715/7716） |
| `write_sysreg_el1(v, SYS_VBAR)` | `msr VBAR_EL12` | 写 **VBAR_EL1**（真） | D8.13.3 别名（VBAR_EL12↔VBAR_EL1） |
| `write_sysreg_el2(v, SYS_ELR)` | `msr ELR_EL1` | 写 **ELR_EL2** | D8.13.2 重定向 |
| `write_sysreg_el1(v, SYS_SPSR)` | `msr SPSR_EL12` | 写 **SPSR_EL1**（真） | D8.13.3 别名 |
| `write_sysreg(v, hcr_el2)` | `msr HCR_EL2` | 写 HCR_EL2（无别名） | — |
| `write_sysreg(v, vttbr_el2)` | `msr VTTBR_EL2` | 写 VTTBR_EL2 | — |

据此，VHE 两条装载路径：

- **guest EL1 组**（含 SP_EL1/ELR_EL1/SPSR_EL1/VBAR_EL1）：在 **vcpu_load 时**经 `_EL12` 编码一次写入真寄存器（`hyp/vhe/sysreg-sr.c:212` `__vcpu_load_switch_sysregs` → `__sysreg_restore_el1_state`（sysreg-sr.h:211-288）；`sysreg-sr.c:151-157` 注释明确"EL1 寄存器只在可能切换到另一个 vCPU 时才需要切换"）。运行循环内不再重复。
- **hyp 向量**：每次进 guest 时 `__activate_traps` 里这一句（`hyp/vhe/switch.c:141`）：

```c
        write_sysreg(__this_cpu_read(kvm_hyp_vector), vbar_el1);
        // msr VBAR_EL1 → E2H 重定向 → 实际写 VBAR_EL2
```

而 EL2 返回状态在每次进 guest 前由 `sysreg_restore_guest_state_vhe`（vhe/sysreg-sr.c:179）恢复：`write_sysreg_el2(pc, SYS_ELR)` = `msr ELR_EL1` → 重定向 → **ELR_EL2**；SPSR 同理。

```
 VHE 下运行 guest 时的两张向量表（带指令）
 =====================================================================
 物理 VBAR_EL1 = guest 自己的向量表
        ^         写入: msr VBAR_EL12 (别名, sysreg-sr.h:252 → kvm_hyp.h:30)
        |         时机: vcpu_load (vhe/sysreg-sr.c:212), 每次换 vCPU 才写
        |
        |  guest 内部异常 (目标 EL1 → VBAR_EL1):
        |    guest EL0 的 svc、guest EL1 的页异常... guest 内核自处理
        |
 guest (EL1)
        |
        |  触发 exit 的指令/事件 (目标 EL2 → VBAR_EL2):
        v
 物理 VBAR_EL2 = kvm_hyp_vector
        ^         写入: msr VBAR_EL1 → E2H 重定向 (vhe/switch.c:141)
        |         时机: 每次进 guest (__activate_traps)
        |  exit 落点: +0x400 el1_sync / +0x480 el1_irq / ...
        |
 VHE 宿主内核(EL2)  --退出 guest 后--> __deactivate_traps:
                     msr hcr_el2 ← HCR_HOST_VHE_FLAGS(RW|TGE|E2H|AMO|IMO|FMO)
                                                     (vhe/switch.c:151)
                     msr vbar_el1 ← 宿主向量表 vectors → 重定向 VBAR_EL2
                                                     (vhe/switch.c:186-188)
```

nVHE 则没有任何重定向：`msr vbar_el2` ← kvm_hyp_vector（nvhe/switch.c:63）、guest EL1 组直接 `_EL1` 编码（kvm_hyp.h:63-66）。

## 4. VM-exit 全链路：guest → VMM

### 4.1 什么会触发 exit：两张表

**第一张：guest 的"指令/事件 → exit"清单**。ESR_EL2 的 EC（Exception Class，`arch/arm64/include/asm/esr.h:14-48`）+ 打开对应陷阱的 HCR_EL2 控制位（`HCR_GUEST_FLAGS`，`arch/arm64/include/asm/kvm_arm.h:100`，在 vcpu reset 时写入 `vcpu->arch.hcr_el2`，kvm_emulate.h:107）：

| 触发源 | 指令/事件 | EC | HCR_EL2 控制位 | 内核处理 |
| - | - | - | - | - |
| 等中断/事件 | `wfi` / `wfe` / `wfit` | 0x01 | TWI / TWE | `kvm_handle_wfx` (handle_exit.c:130)：vcpu 睡眠/让出 CPU |
| hypercall | `hvc #imm`（EL1 执行，目标本来就是 EL2） | 0x12/0x16 | 天然进入 EL2 | `handle_hvc` (handle_exit.c:38)；场景清单见 §4.8 |
| 固件调用 | `smc #imm` | 0x13/0x17 | TSC | `handle_smc` (handle_exit.c:57)；为什么它才需要陷阱位，见 §4.8 |
| 系统寄存器 | `mrs`/`msr`（如读 MIDR_EL1、CNTV_CTL_EL0 等虚拟寄存器） | 0x18 | TID3/TID1/TIDCP/… | `kvm_handle_sys_reg` (sys_regs.c:5297) |
| 系统调用 | `svc` | 0x15 | 仅嵌套虚拟化转发 | `handle_svc` (handle_exit.c:296) |
| 异常返回 | `eret` | 0x1A | 仅嵌套虚拟化 | `kvm_handle_eret` (handle_exit.c:271) |
| 取指/访存 abort | 任何访存指令（stage 2 缺页或 **MMIO**） | 0x20 / 0x24 | HCR_VM（stage 2 使能即陷） | `kvm_handle_guest_abort` (mmu.c:2220)；MMIO 退到 QEMU（mmio.c:257） |
| **异步** | **IRQ / FIQ / SError** | — | **AMO / IMO / FMO** | 无指令参与，硬件直接路由 EL2 |

`HCR_GUEST_FLAGS` 原文（kvm_arm.h:100-103）——TWI/TWE/TSC 等 trap 位 + AMO/IMO/FMO 中断路由位一眼可见：

```c
#define HCR_GUEST_FLAGS (HCR_TSC | HCR_TSW | HCR_TWE | HCR_TWI | HCR_VM | \
                         HCR_BSU_IS | HCR_FB | HCR_TACR | \
                         HCR_AMO | HCR_SWIO | HCR_TIDCP | HCR_RW | HCR_TLOR | \
                         HCR_FMO | HCR_IMO | HCR_PTW | HCR_TID3 | HCR_TID1)
```

> 最常见的两类 exit 直觉化理解：**guest 读一个被虚拟化的寄存器**（mrs 陷入，KVM 用内存里的值回答）和 **guest 访问一块设备内存**（访存 abort 陷入，stage 2 没有映射 → MMIO → 交给 QEMU 模拟）。绝大多数 exit 是这两类和定时器/中断，而非什么"特殊退出指令"。

**第二张：hyp 内的出口分发表**。`arm_exit_handlers[]`（handle_exit.c:376-405）就是上面这张表的内核态版本，按 EC 索引：

```c

        [0 ... ESR_ELx_EC_MAX]  = kvm_handle_unknown_ec,

        [ESR_ELx_EC_IABT_LOW]   = kvm_handle_guest_abort,
        [ESR_ELx_EC_DABT_LOW]   = kvm_handle_guest_abort,
        ...

```

### 4.2 硬件动作：异常自动路由到 EL2

以 guest 执行 `mrs x0, midr_el1`（TID3 打开 → trap）或 guest 收到路由给 EL2 的 IRQ（IMO/FMO）为例，**从触发到进入 hyp 向量表，全部是硬件行为，零软件参与**：

```

   |  HCR_EL2.TID3=1 → 该访问应 trap
```

### 4.3 hyp 向量表：`__kvm_hyp_vector`

nVHE 下 VBAR_EL2 已在 entry 时指向 `kvm_hyp_vector`；VHE 下经 E2H 重定向同样是它（§3.6）。guest 的 exit 落在 `+0x400..0x580` 四个表项（`hyp/hyp-entry.S:181-201`）：

```
 __kvm_hyp_vector (hyp-entry.S:181)
   0x000-0x1FF  EL2t  → invalid (不该发生)
   0x200-0x3FF  EL2h  → el2_sync/el2_error (:93/:113)   ← KVM 自身异常,
   0x400         同步   → el1_sync   (:192)                含"非法异常返回"检测
   0x480         IRQ    → el1_irq     (:193)            ← guest exit 四入口
   0x500         FIQ    → el1_fiq     (:194)
   0x580         SError → el1_error   (:195)
```

**`el1_sync`（hyp-entry.S:44）——同步 exit 的第一站**，里面的指令与寄存器：

```asm
// arch/arm64/kvm/hyp/hyp-entry.S:44
el1_sync:                               // Guest trapped into EL2
        mrs     x0, esr_el2                                   // :46  取 syndrom
        ubfx    x0, x0, #ESR_ELx_EC_SHIFT, #ESR_ELx_EC_WIDTH  // :47  取 EC[31:26]
        cmp     x0, #ESR_ELx_EC_HVC64                         // :48
        ccmp    x0, #ESR_ELx_EC_HVC32, #4, ne                 // :49
        b.ne    el1_trap                                      // :50  非 HVC → 走慢路
        /* spectre workaround 快速路径: SMCCC_ARCH_WORKAROUND_1/2/3 */
        ldr     x1, [sp]                       // guest 的 x0 (func id)   :58
        eor     w1, w1, #ARM_SMCCC_ARCH_WORKAROUND_1
        cbz     w1, wa_epilogue
        ...
wa_epilogue:
        mov     x0, xzr
        add     sp, sp, #16
        eret                                   // :74  不出 hyp, 直接回 guest!
        sb
el1_trap:                                      // :77
        get_vcpu_ptr   x1, x0                  // TPIDR_EL2 定位 host_ctxt → vcpu
        mov            x0, #ARM_EXCEPTION_TRAP
        b              __guest_exit            // :80
el1_irq:                                       // :82
el1_fiq:
        get_vcpu_ptr   x1, x0
        mov            x0, #ARM_EXCEPTION_IRQ
        b              __guest_exit            // :86
```

- guest 的 `hvc` 若只是 spectre 缓解措施调用（guest 内核启动时的固件探测），hyp 认出 func id 后**就地 `eret` 返回 guest**，连寄存器都懒得全存——这是全系统最快的 exit。
- 其余同步 trap → `el1_trap`，置 `ARM_EXCEPTION_TRAP` 退出码（`arch/arm64/include/asm/kvm_asm.h:20-25` 定义了 4 个退出码：IRQ=0 / EL1_SERROR=1 / TRAP=2 / IL=3）。
- `el2_sync`（:93）处理 KVM 自身在 EL2 的异常：`mrs x0, spsr_el2`（:95）后 `tbnz x0, #20`（:96）检查 **SPSR_EL2 bit[20]（IL）**——非法异常返回 → `ARM_EXCEPTION_IL`，最终在 handle_exit.c:474-480 变成 `KVM_EXIT_FAIL_ENTRY`——与 §2.2 的 IL 机制对应。

### 4.4 `__guest_exit`：把 guest 状态打包（每条指令动什么寄存器）

`__guest_exit`（entry.S:121，`__guest_enter` 同文件内的入口标签）反向执行一遍现场保存：

```asm
// arch/arm64/kvm/hyp/entry.S:121 (摘录)
SYM_INNER_LABEL(__guest_exit, SYM_L_GLOBAL)
        add     x1, x1, #VCPU_CONTEXT                    // :127 x1 = guest 上下文
        ALTERNATIVE(nop, SET_PSTATE_PAN(1), ARM64_HAS_PAN) // :129 恢复 PSTATE.PAN
        // Store the guest regs x2 and x3
        stp     x2, x3,   [x1, #CPU_XREG_OFFSET(2)]      // :132
        // Retrieve the guest regs x0-x1 from the stack
        ldp     x2, x3, [sp], #16   // x0, x1            // :135 (向量入口压的栈)
        // Store the guest regs x0-x1 and x4-x17
        stp     x2, x3,   [x1, #CPU_XREG_OFFSET(0)]      // :138
        stp     x4, x5,   [x1, #CPU_XREG_OFFSET(4)]      // :139
        ...                                              // :140-145 (x6..x17)
        // Store the guest regs x18-x29, lr
        save_callee_saved_regs x1                        // :148 x18-x29/lr → ctxt
        save_sp_el0 x1, x2                               // :151 mrs sp_el0 → ctxt
        ...
        // Restore hyp's sp_el0
        restore_sp_el0 x2, x3                            // :166 ldr + msr sp_el0
        // Now restore the hyp regs
        restore_callee_saved_regs x2                     // :169 ← kvm_hyp_ctxt
        set_loaded_vcpu xzr, x2, x3                      // :171 清"当前 vcpu"
        ...                                              // RAS: mrs_s DISR/VDISR
        mrs     x2, elr_el2                              // :196 ┐ SError 窗口:
        mrs     x3, esr_el2                              // :197 │ 暂存 EL2 现场
        mrs     x4, spsr_el2                             // :198 ┘
        msr     daifclr, #4      // Unmask aborts        // :201
abort_guest_exit_start:
        isb                                              // :208 挂起的 SError 在此炸出
abort_guest_exit_end:
        msr     daifset, #4      // Mask aborts          // :212
        ret                                              // :213 回 __kvm_vcpu_run
```

`ret` 回到调用者——即 §3.4 那个 `__kvm_vcpu_run` 的 do-while（nvhe/switch.c:326-334 / vhe/switch.c:598-603）：

```c
        do {
                trace_hyp_exit(host_ctxt, HYP_REASON_ERET_GUEST);   // nvhe/switch.c:327
                /* Jump in the fire! */
                exit_code = __guest_enter(vcpu);      // 进 guest (eret) / 出 guest 回到这里
                /* And we're baaack! */
                trace_hyp_enter(host_ctxt, HYP_REASON_GUEST_EXIT);
        } while (fixup_guest_exit(vcpu, &exit_code)); // 决定: 再进? 还是回宿主?
```

进入循环体判断前，`fixup_guest_exit` 先把硬件留下的 EL2 寄存器捞进 vcpu 结构：`synchronize_vcpu_pstate`（switch.h:892）**`mrs` SPSR_EL2 → vcpu->arch.ctxt.regs.pstate**（:907），`__fixup_guest_exit`（switch.h:915）**`mrs` ESR_EL2 → vcpu->arch.fault.esr_el2**（:919）。

### 4.5 快速路径：在 hyp 里就地消化，立刻再进 guest

`fixup_guest_exit` → `__fixup_guest_exit`（`hyp/include/hyp/switch.h:915`）：先按 EC 查 hyp 自己的处理器表（nvhe/switch.c:194 `hyp_exit_handlers[]` / vhe/switch.c:521），命中则**在 EL2 处理完直接返回 true → do-while 再跑一遍 `__guest_enter` → 又一次 `eret` 进 guest**，宿主内核完全无感：

| 快速路径 | 处理内容 | 代码 |
| - | - | - |

### 4.8 专题：HVC 是谁发的？KVM 需要专门"捕捉"它吗？

先纠正一个常见误解：**KVM 从不修改/替换 guest 代码里的任何指令，也没有为 HVC 设陷阱位**。HVC 的"接住"是纯硬件行为：

```
 guest (EL1) 执行 hvc #0
   |
   |  按架构(无需任何 HCR 开关): HVC 在 EL1 执行 → 生成 Hypervisor Call,
   |  异常打向 EL2 (D1-7134: "If EL2 is implemented and the HVC instruction
   |  is not UNDEFINED, a Hypervisor Call is generated")
   |  (唯一能让它失效的是在 EL0 执行 → UNDEFINED, 同样 D1-7134;
   |   嵌套场景 HCR_EL2.HCD=1 也会把它变 UNDEF — handle_exit.c:45-49)
   v
 异常进入 EL2 (EC=0x16) → VBAR_EL2+0x400 → el1_sync → §4.3 的流程
```

对比 **SMC** 才是真正需要"捕捉"的：SMC 在 EL1 执行时天然目标是 EL3（绕过 hyp 直通真实固件，虚拟化下不可接受），所以 KVM 必须置 HCR_EL2.TSC=1 把它先截到 EL2。一句话记忆：**HVC 天生来 EL2（免捕），SMC 天生去 EL3（要 TSC 截）**。

那 guest 里的 hvc 从哪来？**没有指令替换，只有固件接口约定**：VMM（QEMU）生成给 guest 的 DT/ACPI 里，PSCI 节点带 `method = "hvc"`，guest 内核启动时读这个属性选 conduit（`drivers/firmware/psci/psci.c:287` `get_set_conduit_method` 读 DT 的 `method` 属性 :293，`"hvc"` → `set_conduit(SMCCC_CONDUIT_HVC)` :298-299，存进全局 `smccc_conduit`，`drivers/firmware/smccc/smccc.c:16`）；此后 guest 的所有 SMCCC 调用（含 spectre 缓解）都沿用这个 conduit（`arm_smccc_1_1_get_conduit`，smccc.c:44-49；SMCCC 本身是什么见 §1.1）。也就是说：guest 发 hvc 是它自己"按固件说明书"发的，KVM 只负责在门铃另一头接。

**场景清单**（guest 里一条 hvc 的可能身份，全部收敛到 `handle_hvc` → `kvm_smccc_call_handler`，hypercalls.c:265）：

| 场景 | func id（x0） | 谁发起 / 什么时候 | KVM 处理 |
| - | - | - | - |
| **PSCI**（最大宗） | PSCI_0_2_FN64_CPU_ON / CPU_OFF / SYSTEM_OFF / SYSTEM_RESET / SUSPEND… | guest 内核：SMP 启动副核、CPU 热插、关机/重启/休眠 | `kvm_psci_call` (hypercalls.c:380) 模拟固件，结果写 x0 |
| **Spectre 缓解** | SMCCC_ARCH_WORKAROUND_1/2/3 | guest 内核启动探测 + 每次进入脆弱代码区 | 探测走 hypercalls.c:296/308/331；**热路径在 hyp 里就地 `eret`**（§4.3 的 el1_sync :58-74） |
| **真随机数** | SMCCC_TRNG_VERSION/FEATURES/GET_UUID/RND32/RND64 | guest 内核熵池补充 | hypercalls.c:103-107 → `kvm_trng_call` (trng.c:51) |
| **PV time（steal time）** | SMCCC_HV_PV_TIME_FEATURES / _ST | guest 内核统计被宿主偷走的时间 | hypercalls.c:110-111/343 |
| **KVM PTP 时钟** | SMCCC_VENDOR_HYP_KVM_PTP_FUNC_ID（vendor call） | guest 的 ptp_kvm 驱动 | hypercalls.c:114-118 |
| **SMCCC filter** | 任意 | 任意 | 按 `KVM_SET_SMCCC_FILTER` 用户态配置：转发 QEMU / 拒绝 / 直通 |
| **嵌套虚拟化** | 任意 | L1 guest hyp 的 vEL2 | HCD=1 → 注入 UNDEF，否则转发 L1（handle_exit.c:44-52） |

两个容易混淆的点：

1. **§3.3 那条 `hvc #0` 是宿主内核自己发的**（nVHE 下 `kvm_call_hyp` 调 hyp 服务），与 guest 无关——同一条指令，两张向量表（`__kvm_hyp_host_vector` vs `__kvm_hyp_vector`），两个世界。
2. **"普通 OS 不发 hvc"并不准确**：非虚拟化的 arm64 Linux 在这些情况也会发——PSCI conduit 为 hvc 的平台（DT/ACPI 固件说了算）、spectre 固件缓解调用（conduit=hvc 时）、Xen 半虚拟化 guest 的 hypercall。HVC 在 arm64 里的定位就是"调用更高异常层服务"的通用门铃，KVM 只是众多"门铃另一头"之一。

## 5. 实例走查：guest 里的一次 PSCI `CPU_ON`

guest 内核启动第二个 CPU 时调 PSCI，conduit 是 `hvc`（`drivers/firmware/psci/psci.c:271` `set_conduit` 按设备树选择）：

```c
// drivers/firmware/psci/psci.c:113
__invoke_psci_fn_hvc(unsigned long function_id, ...)
{
        struct arm_smccc_res res;
        arm_smccc_hvc(function_id, arg0, arg1, arg2, 0, 0, 0, 0, &res);  // :119
        // 展开为 hvc #0, x0=function_id, x1..x3=arg0..arg2
        ...
}
```

全程（假设 nVHE）：

```
 guest EL1      psci.c:119  arm_smccc_hvc → hvc #0
                   |  x0 = PSCI func id (如 PSCI_0_2_FN64_CPU_ON)
                   |  EC = 0x16 (HVC64, esr.h:34) → ESR_EL2.EC
                   |  ELR_EL2 ← hvc 下一条指令 (已执行类, D1-7092 RDKWPP)
                   v  (硬件异常进入)
 KVM hyp        __kvm_hyp_vector+0x400 → el1_sync (hyp-entry.S:44)
                   |  mrs x0, esr_el2; EC==HVC64; 但 x0(func id)非 spectre WA
                   v
                el1_trap (:77) → __guest_exit (ARM_EXCEPTION_TRAP)
                   |  guest x0-x29/lr + sp_el0 → vcpu 上下文
                   v
                do-while → fixup_guest_exit: 无快速路径 → 回宿主
                   |  __deactivate_traps → __host_exit → eret (host.S:96)
                   v
 宿主内核 EL1   arm.c:1329 返回, handle_exit → TRAP
                   |  handle_trap_exceptions (handle_exit.c:421)
                   v
                handle_hvc (:38) → kvm_smccc_call_handler (hypercalls.c:265)
                   |  → kvm_psci_call (hypercalls.c:380) — KVM 模拟固件
                   |  结果写入 guest 的 x0 (vcpu_set_reg)
                   v
                返回 1 → while 循环 → 整条 VM-entry 链 → __guest_enter 的 eret
                   v
 guest EL1      回到 hvc 的下一条指令, x0 = CPU_ON 结果
```

对照 SMC：guest 的 `smc #0` 因 HCR_EL2.TSC=1 被 **trap**（不是执行），preferred return address 是 **SMC 指令自身**（D1-7092 RLBLBR），所以 `handle_smc` 里要手动 `kvm_incr_pc` 跳过它（handle_exit.c:57-76 的长注释就是在解释这条 ARM ARM 规则）——同一语义，两种返回地址约定。

## 6. 反方向补充：KVM 如何把异常"注入"给 guest

exit 之后 KVM 有时需要 guest **收到一个同步异常**（比如 guest 执行了未定义指令、需要向 guest 注入外部 abort/SError）。硬件的异常进入动作（§2.1）此时由 KVM 用软件重放（注意：**vIRQ 的投递不在这条路上**——它走 vgic 装载 ICH_LR 后由硬件直接投递，见 004 §3）：

```
 kvm_inject_undefined (inject_fault.c:326)
   └─ inject_undef64 (:171) → kvm_inject_sync (:165):
        vcpu 的 ESR_EL1 ← 构造的 syndrom, 只挂 PENDING_EXCEPTION 标志
        (kvm_pend_exception, kvm_emulate.h:607)
 下次进 guest 前:
 __kvm_adjust_pc (hyp/exception.c:367; 调用点: arm.c:1429 / nvhe/switch.c:304 / vhe/switch.c:593)
   └─ kvm_inject_exception (exception.c:313)
        └─ enter_exception64 (exception.c:85):
             exc_offset 按来源 EL 选 0x200/0x400/0x600 (:93-100)
             vbar ← guest 的 VBAR_EL1 (:104)
             guest ELR_EL1 ← 原 PC (:106)          ← 软件"写 ELR"
             guest PC = VBAR_EL1 + exc_offset + type (:118)  ← 软件"跳向量表"
             guest SPSR_EL1 ← 构造的 PSTATE (:120 起)
             ESR_EL1/FAR_EL1 已由 inject_abt64 等填好 (inject_fault.c:161-162)
   之后 __guest_enter 的 eret 把 guest 带到它自己的向量表
```

`exc_offset` 的取值（CURRENT_EL_SP_ELx_VECTOR=0x200 / LOWER_EL_AArch64_VECTOR=0x400 等，exception.c:93-100）与 §2.1 偏移表完全一致——软件忠实复刻硬件行为。
