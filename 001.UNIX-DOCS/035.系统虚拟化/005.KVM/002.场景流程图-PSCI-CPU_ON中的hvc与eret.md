# 002.场景流程图：guest 启动副核（PSCI CPU_ON）里的每一次 hvc 与 eret

> **场景**：2-vCPU 的 KVM guest（QEMU + KVM，nVHE 模式）。主核 vcpu0 正在跑 guest，guest 内核启动到 `smp_init`，要把副核 vcpu1 拉起来。
> **目的**：用这一条真实链路回答"**什么时候触发 hvc、什么时候执行 eret**"——全场景共 **4 次 hvc + 4 次 eret**（宿主 3 次 hvc：nVHE 下**每一次 VM-entry** 前都要 `hvc #0` 下潜取 `__kvm_vcpu_run`，包括重进和副核首进；guest 1 次 hvc：PSCI CPU_ON。VHE 下宿主的 3 次退化为函数调用，只剩 guest 的 1 次），每一次的触发点、落点、代码都标注在图里。
> 术语（KVM hyp / 宿主内核 / SMCCC / nVHE）见 [001 §1.1](001.VM-exit与VM-entry指令全链路.md#11-名词速览kvm-hyp-是什么)；hvc"免捕"与 SMC"要 TSC 截"的原理见 [001 §4.8](001.VM-exit与VM-entry指令全链路.md#48-专题hvc-是谁发的kvm-需要专门捕捉它吗)。
>
> **图例**：`★hvc` = 触发 HVC 指令；`★eret` = 执行 ERET 指令；①②… = 时序步骤；所有 `文件:行` 均为 7.1.3 树实测。

## 1. 出场角色与初始状态

| 角色 | 异常级 | 初始状态 | 代码身份 |
| - | - | - | - |
| QEMU 主线程 + vcpu0 线程 | EL0(宿主) | vcpu0 线程反复 `ioctl(KVM_RUN)` | `virt/kvm/kvm_main.c` 通用层 |
| 宿主 Linux 内核 | EL1 | KVM 模块已加载，EL2 已被 hyp 占据 | `arch/arm64/kvm/arm.c` |
| KVM hyp | EL2 | VBAR_EL2 = `__kvm_hyp_host_vector`（待命） | `arch/arm64/kvm/hyp/` |
| guest 主核（vcpu0） | EL1 | 跑到 `smp_init()`，要 `cpu_up` 副核 | 同一棵内核树在 guest 里 |
| guest 副核（vcpu1） | — | **从未运行**：`mp_state = STOPPED`，QEMU 线程睡在 KVM_RUN 的等待里 | `kvm_psci_vcpu_on` 的操作对象 |

guest 拉起副核用的"固件接口"是 PSCI，conduit 在 VMM 生成的 DT 里指定为 `hvc`（[001 §4.8](001.VM-exit与VM-entry指令全链路.md#48-专题hvc-是谁发的kvm-需要专门捕捉它吗)），所以接下来 guest 会**自己执行 hvc**——没有人替它改代码。

## 5. 第 3 幕：KVM 处理 CPU_ON（无指令切换，全是内存操作）

```c
// arch/arm64/kvm/psci.c:60 (摘录, 关键 5 步)
static unsigned long kvm_psci_vcpu_on(struct kvm_vcpu *source_vcpu)
{
        cpu_id = smccc_get_arg1(source_vcpu);          // :68  x1 = 目标 MPIDR
        vcpu = kvm_mpidr_to_vcpu(kvm, cpu_id);         // :72  找到 vcpu1

        if (!kvm_arm_vcpu_stopped(vcpu))               // :82  必须"关着"才能上电
                ret = PSCI_RET_ALREADY_ON;             //      (内部还有 PSCI 版本判断, 此处省略)

        reset_state->pc = smccc_get_arg2(source_vcpu); // :93  x2 = secondary_entry 物理地址
        reset_state->r0 = smccc_get_arg3(source_vcpu); // :102 x3 = context_id = 0
        reset_state->reset = true;                     // :104
        kvm_make_request(KVM_REQ_VCPU_RESET, vcpu);    // :105 挂"待复位"请求

        WRITE_ONCE(vcpu->arch.mp_state.mp_state, KVM_MP_STATE_RUNNABLE);  // :113 上电!
        kvm_vcpu_wake_up(vcpu);                        // :114 唤醒 QEMU 的 vcpu1 线程
                                                       //      (kvm_main.c:3794)
}
```

注意：**CPU_ON 在 KVM 里没有执行任何 `msr`/`eret`**——它只是改内存（reset_state、mp_state）并唤醒线程。副核"上电"的指令动作发生在它自己的 KVM_RUN 里（第 6 幕）。

## 6. 第 4 幕：主核重进 guest —— `★eret⑤`

`kvm_psci_vcpu_on` 返回 `PSCI_RET_SUCCESS`(0) → `smccc_set_retval` 写 x0 → `handle_hvc` 返回 1 → `handle_exit` 返回 1 → **`arm.c:1266` 的 while 循环原地再来一轮**：

```
[宿主内核 EL1]  while 下一轮 (arm.c:1266) — exit/entry 是同一循环的两半
                  |  kvm_arm_vcpu_enter_exit (arm.c:1324)
                  |    └─ kvm_call_hyp_ret(__kvm_vcpu_run, vcpu) (arm.c:1227)
                  |         nVHE 下再次下潜: ★hvc #0 ①'  (arm-smccc.h:548)
                  |         （与第 1 幕完全相同的 entry 链: host.S → __kvm_vcpu_run
                  |           铺路 → __guest_enter）
                  ★eret ⑤  (entry.S:88)
                  v
[guest vcpu0]   回到 hvc 的下一条指令 (ELR_EL2 一直是 hvc+4), x0 = 0 = SUCCESS
                  → cpu_psci_cpu_boot 返回 → 副核标记为 online, 主核继续 smp_init
```

**hvc 与 eret 的配对关系在此清晰可见**：guest 的 1 次 hvc 换来 hyp→宿主的 1 次 eret 和宿主重进的 1 次 eret——一次往返 = 2 条 eret。

## 8. 清点：本场景的 4 次 hvc 与 4 次 eret

| # | 指令 | 谁在哪个 EL 执行 | 为什么 | 落点/去向 | 代码 |
| - | - | - | - | - | - |
| ★hvc① | `hvc #0` | 宿主内核 EL1（vcpu0 线程） | nVHE 下调用 KVM hyp 的服务（SMCCC） | `__kvm_hyp_host_vector`+0x400 → 最终跑 `__kvm_vcpu_run` | arm-smccc.h:548；host.S:234 |
| ★eret② | `eret` | KVM hyp EL2 | **VM-entry**：进入 guest 主核 | PC←ELR_EL2=guest 上次退出点 | entry.S:88 |
| ★hvc③ | `hvc #0` | guest 内核 EL1 | PSCI CPU_ON（调"虚拟固件"） | `__kvm_hyp_vector`+0x400 → `el1_sync` → 慢路径 | psci.c:119；hyp-entry.S:44 |
| ★eret④ | `eret` | KVM hyp EL2 | 慢路径 exit：把控制权还给宿主内核去处理 | PC←ELR_EL2=宿主在 hvc 后的返回地址 | host.S:96 |
| ★hvc①' | `hvc #0` | 宿主内核 EL1（vcpu0 线程） | while 下一轮**重进** guest：entry 链重新走一遍，宿主再次下潜 | 同 ① | arm.c:1227/1266 |
| ★eret⑤ | `eret` | KVM hyp EL2 | 主核**重进** guest（hvc 已处理完） | PC←ELR_EL2=hvc+4，x0=SUCCESS | entry.S:88 |
| ★hvc①'' | `hvc #0` | 宿主内核 EL1（vcpu1 线程） | 副核首次 KVM_RUN 的 entry 链下潜 | 同 ① | arm.c:1227 |
| ★eret⑥ | `eret` | KVM hyp EL2 | 副核**首次 VM-entry**（被 CPU_ON 唤醒） | PC←ELR_EL2=secondary_entry | entry.S:88 |

规律总结：

- **hvc 只有两种来源**：宿主内核调 hyp（nVHE 专属，走 `__kvm_hyp_host_vector`）和 guest 调"虚拟固件"（PSCI/SMCCC，走 `__kvm_hyp_vector`）——两张向量表，两个世界（[001 §4.8](001.VM-exit与VM-entry指令全链路.md#48-专题hvc-是谁发的kvm-需要专门捕捉它吗)）。
- **本场景的 4 次 eret 全部由 EL2 上的 KVM hyp 执行**。但注意 eret 并非 EL2 专属——EL1/EL3 同样可以执行（宿主内核、guest 内核从内核态返回用户态就是 EL1 的 eret；嵌套场景下 guest EL1 的 eret 甚至会以 EC=0x1A 陷阱进 EL2，见 [001 §4.1](001.VM-exit与VM-entry指令全链路.md#41-什么会触发-exit两张表)）。真正不变的是：**跨越 VM 边界的那条 eret 永远在 EL2 上**——只有 hyp 同时握着两侧的现场（ELR_EL2/SPSR_EL2 装的是 guest 的 PC/PSTATE）。
- **一次 guest↔宿主的往返 = 恰好 2 条 eret**（回宿主 + 重进 guest；nVHE 下重进前宿主还要再发 1 条 `hvc #0` 下潜），夹在中间的处理越快（如 spectre 快速路径），往返越短——极端情况在 hyp 里就地 `eret`，往返 0 次。

## 9. 本场景刻意避开的分支（对比记忆用）

| 分支 | 若发生会怎样 | 在哪 |
| - | - | - |
| guest 的 spectre 探测 hvc | el1_sync 认出 func id，**在 hyp 里就地 `eret` 回 guest**，不出 hyp、不回宿主 | hyp-entry.S:58-74 |
| guest 执行 `smc #0` | 被 HCR_EL2.TSC 截到 EL2，返回地址是 SMC 自身，`handle_smc` 手动 `kvm_incr_pc` | handle_exit.c:57-76 |

| guest 用户态执行 hvc | UNDEFINED（D1-7134），根本发不出去 | — |
