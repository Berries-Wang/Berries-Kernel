# get_unaligned 与 put_unaligned

> 书中对应原句（附录 A.3，[深入Linux内核架构.pdf](../../007.BOOKs/深入Linux内核架构.pdf) 物理页 917）："在内核中某些地方，可能需要访问非对齐的数据类型。各体系结构必须为此定义两个宏（在 `<asm-arch/unaligned.h>` 中）：`get_unaligned(ptr)`……`put_unaligned(val, ptr)`……这些宏支持将相应的值**复制到另一个内存位置**，并在新的位置进行访问。"
>
> 源码对照: Linux 5.9（[000.SOURCE_CODE/000.LINUX-5.9](../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9)） vs Linux 7.1.3（[000.SOURCE_CODE/003.LINUX-7.1.3](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3)）

书（基于 2.6.24）说"各体系结构必须在 `<asm-arch/unaligned.h>` 中定义两个宏"。这条规矩如今已演变：**入口统一到 `include/linux/unaligned.h`，实现按"硬件是否高效支持非对齐"分流**。本文用 5.9 → 7.1.3 两代源码讲清这次收敛。

---

## 1. 问题的形状：为什么需要这两个宏

```c
void parse(char *pkt)
{
	u32 len = *(u32 *)(pkt + 2);   // ← pkt+2 不保证 4 字节对齐
}
```

以太网头 14 字节，紧随其后的 IP 头就是 2(mod 4) 相位——网络解析代码天天面对这种指针。直接解引用在有的架构是异常（老 ARM/部分 RISC），在 x86/arm64 是"能跑但有代价"。`get_unaligned/put_unaligned` 把"这里**明知**非对齐"显式告诉编译器，让它生成安全且对该架构最优的指令序列。

书中"将相应的值复制到另一个内存位置"描述的正是最通用的实现策略：**按字节搬运 + 本地变量（天然对齐）上再操作**。

## 2. Linux 5.9：`asm-generic/unaligned.h` 的三分支

```c
// (5.9) include/asm-generic/unaligned.h:11
/* Set by the arch if it can handle unaligned accesses in hardware. */
#ifdef CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS
# include <linux/unaligned/access_ok.h>      // 分支A：硬件高效 → 直接解引用
#endif

#if defined(__LITTLE_ENDIAN)
# ifndef CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS
#  include <linux/unaligned/le_struct.h>     // 分支B：__packed 结构体法
#  include <linux/unaligned/be_byteshift.h>  // 分支C：逐字节移位法
# endif
# include <linux/unaligned/generic.h>
# define get_unaligned	__get_unaligned_le
# define put_unaligned	__put_unaligned_le
#elif defined(__BIG_ENDIAN)
	...（对称的 BE 版本）
#endif
```

谁走哪个分支：

```c
// (5.9) arch/x86/Kconfig:172   /  (5.9) arch/arm64/Kconfig:158
	select HAVE_EFFICIENT_UNALIGNED_ACCESS
```

- **x86、arm64**：声明硬件高效支持（Normal 内存上非对齐访存由微架构直接执行）→ **分支 A**，宏退化为普通指针解引用：

```c
// (5.9) include/linux/unaligned/access_ok.h:8
static __always_inline u32 get_unaligned_le32(const void *p)
{
	return le32_to_cpup((__le32 *)p);     // 直接解引用——零开销
}
```

- **其他架构**（老 ARM、部分 RISC）：分支 B 用 [001.自然对齐的定义.md](001.自然对齐的定义.md) §3 的 `__packed` 结构体法（`struct __una_u32 { u32 x; } __packed;`），编译器生成拆分指令；分支 C 用逐字节移位（`p[0] | p[1]<<8 | ...`）。

## 3. Linux 7.1.3：收敛为单一 memcpy 实现

`asm-generic/unaligned.h` 消失，只剩一个头文件 + 一个通用原语：

```c
// include/linux/unaligned.h:13
#define get_unaligned(ptr)	__get_unaligned_t(typeof(*(ptr)), (ptr))
#define put_unaligned(val, ptr) __put_unaligned_t(typeof(*(ptr)), (val), (ptr))
```

```c
// include/vdso/unaligned.h:20
#define __get_unaligned_t(type, ptr) ({					\
	type *__get_unaligned_ctrl_type __always_unused = NULL;		\
	__unqual_scalar_typeof(*__get_unaligned_ctrl_type) __get_unaligned_val; \
	__builtin_memcpy(&__get_unaligned_val, (void *)(ptr),		\
			 sizeof(__get_unaligned_val));			\
	__get_unaligned_val;						\
})

// include/vdso/unaligned.h:38
#define __put_unaligned_t(type, val, ptr) do {				\
	type __put_unaligned_val = (val);				\
	__builtin_memcpy((void *)(ptr), &__put_unaligned_val,		\
			 sizeof(__put_unaligned_val));			\
} while (0)
```

注释点明了选择 memcpy 的理由："Use memcpy to affect an unaligned type sized load **avoiding undefined behavior** from approaches like type punning"。

妙处在于**编译器对定长 `memcpy` 的 lowering**：

- 已知大小（2/4/8 字节）的 `__builtin_memcpy` 会被编译成**一条普通 load/store**；
- 而这条指令的地址来源是 `memcpy` 语义——编译器**知道**它可能非对齐，在 x86/arm64 上直接生成普通 `mov/LDR`（硬件处理），在不支持的架构上自动拆分成字节访问。

于是**一份代码自动获得旧三分支的全部效果**，且规避了 `(__le32 *)p` 这种类型双关（type punning）的未定义行为。`__packed` 结构体法仍保留在 `include/linux/unaligned/packed_struct.h`，供 `__get_unaligned_cpuN` 系列使用。

字节序族（网络/磁盘解析的主力）在同一头文件里：

```c
// include/linux/unaligned.h:16
static inline u16 get_unaligned_le16(const void *p)
{
	return le16_to_cpu(__get_unaligned_t(__le16, p));   // 非对齐读取 + 字节序转换
}
// 同族: get_unaligned_{le,be}{16,32,64}、put_unaligned_{le,be}{16,32,64}、
//       get/put_unaligned_{le,be}24/48（部分协议的 3/6 字节字段）
```

## 4. 5.9 vs 7.1.3 对照表

| | Linux 5.9（书后时代） | Linux 7.1.3（现状） |
|---|---|---|
| 入口头文件 | `asm-generic/unaligned.h`（各 arch 可覆盖） | `include/linux/unaligned.h`（统一） |
| 实现分派 | 编译期三分支：`HAVE_EFFICIENT_UNALIGNED_ACCESS` → 直接解引用；否则 `le_struct`/`be_byteshift` | 单一 `__builtin_memcpy`，由编译器 lowering 适配 |
| 安全性 | `(__le32 *)p` 类型双关（依赖 `-fno-strict-aliasing`） | memcpy 语义，无 UB |
| `HAVE_EFFICIENT_UNALIGNED_ACCESS` | 仍存在于 Kconfig（arm64:158、x86:172） | 保留（arm64:200、x86:238），转用于**代码分派**而非宏实现 |
| 书中 `<asm-arch/unaligned.h>` | 尚有影子 | 已成历史 |

`HAVE_EFFICIENT_UNALIGNED_ACCESS` 并没有退休——它从"选宏实现"变成了"选算法"的开关，最经典的用户：

```c
// include/linux/etherdevice.h:353
static inline bool ether_addr_equal(const u8 *addr1, const u8 *addr2)
{
#if defined(CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS)
	u32 fold = ((*(const u32 *)addr1) ^ (*(const u32 *)addr2)) |   // 2 条访存
		   ((*(const u16 *)(addr1 + 4)) ^ (*(const u16 *)(addr2 + 4)));
	return fold == 0;
#else
	const u16 *a = (const u16 *)addr1;                            // 6 条访存
	const u16 *b = (const u16 *)addr2;
	return ((a[0] ^ b[0]) | (a[1] ^ b[1]) | (a[2] ^ b[2])) == 0;
#endif
}
```

同一个"比较 6 字节 MAC 地址"：硬件能高效处理非对齐的架构敢用 4+2 字节两枪拿下；不行的架构老老实实按 2 字节对齐分三枪。（内核文档 [unaligned-memory-access.rst](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/Documentation/core-api/unaligned-memory-access.rst) 用这个例子讲解"调用者保证 16 位对齐"的责任划分。）

## 5. 使用守则

1. **写**：地址可能非对齐且类型 ≥ 2 字节 → `get_unaligned_le16/le32/be32...`（顺带完成字节序转换，网络解析首选）或 `get_unaligned(ptr)/put_unaligned(val, ptr)`；
2. **读**：看到 `get_unaligned` 就知道作者在声明"这个地址不保证对齐"——报文解析、`__packed` 结构、跨缓冲区的字段访问；
3. **别滥用**：在 x86/arm64 上它近乎零开销（一条普通 load），但在其他架构上是逐字节模拟；热路径上更好的办法是**把数据先搬进对齐缓冲区再解析**（`pskb_may_pull` + `skb_header_pointer` 的思路）；
4. **性能联觉**：`NET_IP_ALIGN`（[003.非对齐访问-高速缓存性能视角.md](003.非对齐访问-高速缓存性能视角.md) §4）的存在说明：**对齐正确的报文布局 + 逐步解析时的 get_unaligned 兜底**是网络栈"快而稳"的组合拳——能在收包时对齐的（IP 头）就对齐，实在对不齐的（头部链深处的字段）用宏安全访问。

## 6. 与书中其余论断的对照小结

| 书中论断（2.6.24 时代） | 7.1.3 现状 |
|---|---|
| "各体系结构必须定义两个宏" | 已收敛：`include/linux/unaligned.h` 统一提供，编译器分流 |
| "将值复制到另一个内存位置再访问" | `__builtin_memcpy` 到本地临时变量——字面意义上的"复制到新位置" |
| "GCC 自动为 struct/union 选择对齐" | 仍然成立（[001.自然对齐的定义.md](001.自然对齐的定义.md) §2），`__packed` 是显式例外 |
| "相关信息在处理器体系结构文档中给出" | 仍然成立：ARM ARM B2.8 对齐规则 + 各 TRM 的 CTR_EL0 字段（见 [002](002.非对齐访问-架构正确性视角.md)/[003](003.非对齐访问-高速缓存性能视角.md)） |
