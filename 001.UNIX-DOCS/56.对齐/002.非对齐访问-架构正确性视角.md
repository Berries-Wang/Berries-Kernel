# 非对齐访问：架构正确性视角 —— "一些体系结构强制要求对齐"

> 学习: [Arm Architecture Reference Manual DDI0487M.a.a](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf) **B2.8 Alignment support**（[vol1 物理页 309-310](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=309)）、**B2.2.1 Requirements for single-copy atomicity**（[vol1 物理页 246-247](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=246)）、SCTLR_EL1.A/SA 位描述（[vol9 物理页 584](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-9001-12000.pdf#page=584)）、ESR_ELx 的 DFSC 编码（[vol12 物理页 1892](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-12001-15000.pdf#page=1892)）；[Learn the Architecture: AArch64 Memory Attributes and Properties](../../007.BOOKs/learn_the_architecture_-_aarch64_memory_attributes_and_properties_102376_0200_01_en.pdf)（p.33/p.37）
>
> 书中对应原句："**一些体系结构强制要求**对特定长度的数据类型进行特定的对齐。"

"强制要求"在架构手册里是精确的规则，不是修辞。本文把 arm64 的规则逐条对上内核源码；x86 的规则正好是对照组——它几乎从不因非对齐报错，但把代价转嫁到了总线上（bus lock）。

## 1. ARM ARM B2.8 的对齐规则全景

ARM ARM（DDI0487M.a.a）B2.8.2 *Alignment of data accesses* 的规则可以画成一棵判定树：

```
访问地址非自然对齐
│
├─ SCTLR_ELx.A == 1 ?  ──────────→ 绝大多数指令 → Alignment fault
│                                    （以 Data Abort 异常上报，ISS.DFSC=0b100001）
│                                    例外（FEAT_LSE2）：非原子 Load-Acquire/Store-
│                                    Release（LDAR/STLR/LDAPR…）的检查放宽为"整体
│                                    落在 16B 对齐块内"，越出 16B 块且 nAA=0 才
│                                    fault（SCTLR_ELx.nAA，bit[6]，B2.8.2 第二段）
│
├─ 目标是 Device 内存？ ──────────→ Alignment fault（位置不支持非对齐则必 fault；
│                                    支持与否由实现决定——B2.8.2；内存属性指南
│                                    p.33 概括为"Unaligned accesses are allowed to
│                                    addresses marked as Normal, but not to Device
│                                    regions"）
│
├─ 普通 load/store（LDR/STR/LDP/STP…，不含 Load-Acquire/Store-Release）
│    └─ A == 0：执行非对齐访问
│         ├─ 无 FEAT_LSE2：除字节级外【不保证单拷贝原子】
│         └─ 有 FEAT_LSE2：若完整落在某个 16B 对齐的 16 字节块内
│                          且为 Normal WB Cacheable(Shareable) → 单拷贝原子
│                          （LDP/STP 整体原子）；否则不保证
│
├─ 非原子 Load-Acquire/Store-Release（LDAR/STLR/LDLAR/STLLR/LDAPR…）
│    └─ A == 0（B2.8.2.1.3 单列条款，最易被归错类）：
│         ├─ 无 FEAT_LSE2：非对齐 → Alignment fault（不是"放行执行"！）
│         └─ 有 FEAT_LSE2：16B 块内且 WB Cacheable → 执行且单拷贝原子；
│                          非 WB Cacheable → CONSTRAINED UNPREDICTABLE（执行或
│                          fault）；越 16B 块且 nAA=1 → 执行但不保证单拷贝原子
│
└─ 独占/原子指令（LDXR/STXR/LDADD/SWP/CAS…）
     ├─ 无 FEAT_LSE2：非对齐 → Alignment fault（即使 A == 0！）
     └─ 有 FEAT_LSE2：落在 16B 对齐块内且 WB Cacheable → 允许且单拷贝原子；
                       否则 CONSTRAINED UNPREDICTABLE（执行或 fault，二选一）
```

三条最要紧的结论（均为 ARM ARM 原文规则的转述）：

1. **A 位是总开关**：`SCTLR_ELx.A=1` 时，除字节访问外一切非对齐都 fault——唯一例外是 FEAT_LSE2 下的非原子 LDAR/STLR：检查放宽为"整体落在 16B 对齐块内"（见判定树第一支）。SCTLR_EL1.A 的寄存器描述原文（DDI0487M [vol9 物理页 584](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-9001-12000.pdf#page=584)）：

   > "A, bit [1] **Alignment check enable**... All instructions that load or store one or more registers have an alignment check that the address being accessed is aligned to the size of the data element(s) being accessed. If this check fails it causes an Alignment fault, which is **taken as a Data Abort exception**."

   注意最后半句——它定义了 Alignment fault 的**上报通道**：走 Data Abort 异常（EC=0b100100/0b100101），故障码记在 ISS 的 DFSC 字段里，**DFSC = 0b100001 (0x21) = Alignment fault**（DDI0487M [vol12 物理页 1892](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-12001-15000.pdf#page=1892) 的 DFSC 编码表；AArch64 自 v8.0 起对齐故障即编码为 0b100001——Linux 5.9 与 7.1.3 的 `fault_info[]` 均把它排在同一下标 33，两代内核未变。勘误见 §2.1）。

2. **原子/独占指令有独立于 A 位的对齐要求**：无 FEAT_LSE2 时，"Load-Exclusive、Store-Exclusive 和 Atomic 指令访问的地址**未对齐到整体访问大小**" → Alignment fault，**无论 A 位是 0 还是 1**（B2.8.2 第一个 bullet + B2.8.2.1.2）。这就是"原子指令要求自然对齐"的架构出处，也是内核spinlock/原子变量绝不能落在非对齐地址上的原因。
3. **非对齐 = 放弃单拷贝原子性**：B2.2.1 规定"单寄存器 load/store 且**对齐到访问大小** → 单拷贝原子"；非对齐访问（A=0 时硬件放行）则"不保证单拷贝原子（除字节级）"。撕裂读（torn read）由此产生——别的核正在写的 8 字节，你可能读到"前 4 字节新值 + 后 4 字节旧值"。

### 1.1 Alignment fault 还有两个"内存类型来源"（D8.15）

除了"指令要求非对齐"，D8.15 *Memory aborts*（DDI0487M [vol6 物理页 1739](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-6001-9000.pdf#page=1739) 的故障优先级表）还列出了由**内存类型**触发的 Alignment fault：

- **跨页边界且两页内存类型（Device/Normal）或 Shareability 不同**的单次访问；
- **Device 访问跨外设边界**（外设不支持该跨度）。

即：一次访问即使满足自然对齐，只要横跨两个属性不同的页，也可能 fault——这再次印证 A.3 那句"相关信息一般会在所述处理器的体系结构文档中给出"：对齐规则的完整判定不止看地址低位，还要看内存属性。

## 1.5 不止数据：PC 与 SP 的强制对齐

架构强制的对齐不止作用于数据访问，还包括两个**寄存器**：

**① PC：A64 指令必须字对齐（4 字节）**——B2.8.1 *Instruction alignment*（[vol1 物理页 309](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=309)）：

> "A64 instructions must be word-aligned. Attempting to fetch an instruction from a misaligned location results in a **PC alignment fault**."

**② SP：以 SP 为基址的访存必须 16 字节对齐**——C6.1.3 *Use of the stack pointer*（[vol1 物理页 1785](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=1785)）：

> "When stack alignment checking is enabled by system software and the base register is SP, the current stack pointer must be initially **quadword aligned**（16 字节）. Misalignment generates an **SP alignment fault**."

SP 检查由 SCTLR_EL1.SA（EL1）/SA0（EL0）开启（位描述见 [vol9 物理页 584](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-9001-12000.pdf#page=584)）。**Linux 主动开启了这两个检查**——`INIT_SCTLR_EL1_MMU_ON` 的宏体开头（`sysreg.h:864-865`）就显式列出了 `SCTLR_ELx_SA | SCTLR_EL1_SA0`（对照 §2 的代码）：栈指针一旦跑偏到非 16B 边界，立即以异常暴露，而不是等到栈数据被非对齐读写才出错。两个 fault 的处理入口：

```c
// arch/arm64/mm/fault.c:995
void do_sp_pc_abort(unsigned long addr, unsigned long esr, struct pt_regs *regs)
{
	arm64_notify_die("SP/PC alignment exception", regs, SIGBUS, BUS_ADRALN,
			 addr, esr);
}
```

（这也是过程调用标准 AAPCS64 要求 SP 在公共接口处保持 16B 对齐的硬件后盾——编译器为此在栈帧里做 padding，是"对齐无处不在"的又一例。）

## 2. Linux/arm64 的选择：SCTLR_EL1.A = 0

Linux arm64 开 MMU 时写入的 SCTLR_EL1 初值**不包含** `SCTLR_ELx_A`（bit 1）：

```c
// arch/arm64/include/asm/sysreg.h:835
#define SCTLR_ELx_A	 (BIT(1))

// arch/arm64/include/asm/sysreg.h:863
#define INIT_SCTLR_EL1_MMU_ON \
	(SCTLR_ELx_M      | SCTLR_ELx_C      | SCTLR_ELx_SA    | \
	 SCTLR_EL1_SA0    | SCTLR_EL1_SED    | SCTLR_ELx_I     | \
	 SCTLR_EL1_DZE    | SCTLR_EL1_UCT    | SCTLR_EL1_nTWE  | \
	 SCTLR_ELx_IESB   | SCTLR_EL1_SPAN   | SCTLR_ELx_ITFSB | \
	 ENDIAN_SET_EL1   | SCTLR_EL1_UCI    | SCTLR_EL1_EPAN  | \
	 SCTLR_EL1_LSMAOE | SCTLR_EL1_nTLSMD | SCTLR_EL1_EIS   | \
	 SCTLR_EL1_TSCXT  | SCTLR_EL1_EOS)
	 // ↑ 列表里没有 SCTLR_ELx_A → A=0：普通内存的非对齐访问由硬件直接执行
```

该值在使能 MMU 时写入：`__cpu_setup` 在 `arch/arm64/mm/proc.S:564` 把它装进 x0，`__enable_mmu` 随后在 `arch/arm64/kernel/head.S:470` 以 `set_sctlr_el1 x0` 写入 SCTLR_EL1。于是：

- 普通 Normal 内存上的非对齐 `LDR/STR` **硬件直接执行**，不陷异常——所以 arm64 和 x86 一样声明了 `select HAVE_EFFICIENT_UNALIGNED_ACCESS`（`arch/arm64/Kconfig:200`、`arch/x86/Kconfig:238`）；
- 但仍有访问会撞上 Alignment fault，走 `do_alignment_fault`：

```c
// arch/arm64/mm/fault.c:846
static int do_alignment_fault(unsigned long far, unsigned long esr,
			      struct pt_regs *regs)
{
	if (IS_ENABLED(CONFIG_COMPAT_ALIGNMENT_FIXUPS) &&
	    compat_user_mode(regs))
		return do_compat_alignment_fixup(far, regs);   // AArch32 用户态：软件修复
	do_bad_area(far, esr, regs);                       // 其余：按坏地址处理 → SIGBUS
	return 0;
}
```

```c
// arch/arm64/mm/fault.c:942（fault 表中的 EC=0x21 项）
	{ do_alignment_fault,	SIGBUS,  BUS_ADRALN,	"alignment fault"		},
```

什么时候真的会 fault？典型场景：①访问 **Device/MMIO** 内存（寄存器必须自然对齐访问）；②**无 LSE2 时原子指令落在非对齐地址**（内核 bug，必崩）；③跨页边界且两页内存类型/Shareability 不同（§1.1）；④**MMU 尚未开启的启动早期**——此时所有访问按 Device 处理，非对齐即 fault（Learn the Architecture: AArch64 Memory Attributes 指南 p.33/p.37："When the MMU is disabled, all accesses are treated as Device. Unaligned accesses to regions…"——head.S 里的早期代码必须自然对齐访问）。用户态 AArch32 程序还有专门的软件修复路径（`CONFIG_COMPAT_ALIGNMENT_FIXUPS`，逐条模拟——正是内核文档说的"exception handler is able to correct the unaligned access, at significant cost to performance"）。

### 2.1 故障编码的源码-架构交叉验证

Alignment fault 的完整编码链路（架构手册 ↔ 内核缺陷表逐一对应）：

| 环节 | 值 | 出处 |
|---|---|---|
| 异常类别 ESR.EC | 0b100100（来自低 EL 的 Data Abort）/ 0b100101（当前 EL） | DDI0487M [vol6 物理页 2531](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-6001-9000.pdf#page=2531) EC 编码表 |
| 故障状态码 ISS.DFSC | **0b100001（0x21）= Alignment fault** | DDI0487M [vol12 物理页 1892](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-12001-15000.pdf#page=1892) DFSC 编码表 |
| 内核查表 | `fault_info + (esr & ESR_ELx_FSC)` → 表项[33] | `arch/arm64/mm/fault.c:58`、表定义 `fault.c:908` 起 |

```c
// arch/arm64/mm/fault.c:58
static inline const struct fault_info *esr_to_fault_info(unsigned long esr)
{
	return fault_info + (esr & ESR_ELx_FSC);   // 用低 6 位 DFSC 索引
}
```

`fault_info[]` 从下标 0（ttbr address size fault）排到 33（alignment fault，即 `fault.c:942` 那一行），后续还有 48 号位 "TLB conflict abort"（`fault.c:957` ↔ DFSC 0b110000）、52 号位 "implementation fault (lockdown abort)"（`fault.c:961` ↔ DFSC 0b110100）——整张表与 ARM ARM 的 DFSC 编码一一对应，是"内核按架构手册精确实现"的直观样本。

> **勘误记录**：本文档初版曾把故障编码写作"ESR.EC=0x21"——混淆了 EC（异常类别）与 DFSC（故障状态码）。正确说法：EC 是 Data Abort（0b100100/0b100101），**0x21 是 ISS 里的 DFSC 值**。0b100001 这一个数字恰好两个位置都合法（EC=0b100001 是 Instruction Abort current EL），更容易记混，特此留档。
>
> **勘误记录（二）**：初版曾写"FEAT_LPA2 引入 level-0 Access flag/Permission fault 后，Alignment fault 的编码从旧版的 0b001001 移到了 0b100001"——有误。DDI0487M DFSC 表中 0b001001 是 **Access flag fault, level 1**；AArch64 的对齐故障编码自 v8.0 起一直是 0b100001（Linux 5.9 与 7.1.3 的 `fault_info[]` 均排在下标 33，无迁移发生），特此留档。

## 3. 单拷贝原子性：对齐换来的"免费午餐"

B2.2.1 的规则（原文摘录，[vol1 物理页 246](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=246)）：

> - A read that is generated by a load instruction that loads a single general-purpose register and is **aligned to the size of the read** is single-copy atomic.
> - A write that is generated by a store instruction that stores a single general-purpose register and is **aligned to the size of the write** is single-copy atomic.

单拷贝原子（single-copy atomicity）的含义：这个读/写在系统看来是**不可分割的一次事件**——观察者要么看到旧值、要么看到新值，不存在中间态。内核大量依赖这条"免费午餐"：

- **无锁读取**：` READ_ONCE()` 读共享计数器、seqlock 的版本号、RCU 指针——代码里只有一条普通 load，没有原子指令。它的正确性完全建立在"对齐的 load 单拷贝原子"上；
- 一旦这个变量被塞进 `__packed` 结构或落在奇数地址，load 变成两次 4 字节拼接 → 撕裂读 → **极难复现的并发 bug**。

这就是"强制对齐"更深一层的含义：**对齐不仅是性能问题，还是无锁算法正确性的隐含前提。** 反过来，错误的对齐比错误的速度更可怕——速度慢 2 倍能测出来，撕裂读一年崩一次。

### 原子指令与 LSE 的联动

按 CLAUDE.md 约定，原子指令以 LSE 为主路径。注意 B2.8.2.1.2 的规则同样作用于 LSE 原子指令（`LDADD/SWP/CAS`）：无 FEAT_LSE2 时非对齐必 fault；有 FEAT_LSE2（Armv8.4+，AGI CPU/Neoverse V3、A725、A520 均具备）时，落在 16B 对齐块内的非对齐原子访问才被允许且保持单拷贝原子。LL/SC（`LDXR/STXR`）同样受此约束——其状态机细节见 [../008.同步原语/001.原子指令/003.LLSC实现原理.md](../008.同步原语/001.原子指令/003.LLSC实现原理.md)。

## 4. 对照组：x86 —— 不报错，但把代价转嫁给总线

AMD EPYC 9996（x86_64）上，普通非对齐 `mov` 从 486 起就由硬件直接执行，永不因非对齐本身 fault（SSE 对齐指令如 `movaps` 是历史例外，要求 16B）。但 x86 有一条自己的红线：

**带 `LOCK` 前缀的原子指令如果跨缓存行 → 总线锁（bus lock / split lock）**。此时处理器要锁住两个缓存行甚至整条总线完成 RMW，代价是千周期量级的延迟，并且**拖慢所有其他核的访存**（这正是把"非对齐"从本核性能问题放大成全机性能问题的唯一场景）。

内核对 Intel 平台提供了检测与惩罚机制：

```c
// arch/x86/kernel/cpu/bus_lock.c:16
enum split_lock_detect_state {
	sld_off = 0,
	sld_warn,       // WARN 一次并限流
	sld_fatal,      // 用户态直接 SIGBUS
	sld_ratelimit,  // 限流警告
};
```

```c
// arch/x86/kernel/cpu/bus_lock.c:141
static void __init __split_lock_setup(void)
{
	if (!split_lock_verify_msr(false)) { ... }
	rdmsrq(MSR_TEST_CTRL, msr_test_ctrl_cache);
	...
	setup_force_cpu_cap(X86_FEATURE_SPLIT_LOCK_DETECT);  // 开启 #AC 检测
}
```

- 检测通过 `MSR_TEST_CTRL` 的 SPLIT_LOCK_DETECT 位开启，split lock 触发 `#AC`（Alignment Check）异常；
- AMD 不实现该 MSR（EPYC 9996 上保持 `sld_off`），但**微架构代价同样存在**——总线锁在所有 x86 上都慢；
- 注意名字："**split** lock"＝"锁跨行了"，本质就是**对齐问题**；ARM 侧对应物是"原子指令非对齐 → 直接 fault"，ARM 用正确性兜底，x86 用性能兜底，殊途同归：**原子操作必须自然对齐**。

## 5. 架构行为光谱（内核文档的四分类）

内核文档 [unaligned-memory-access.rst](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/Documentation/core-api/unaligned-memory-access.rst) 把各架构对非对齐访问的行为归纳为四档，从好到坏：

| 档 | 行为 | 代表 | 结果 |
|---|---|---|---|
| 1 | 硬件透明执行，但有性能代价 | x86、arm64(Normal内存) | 慢，但对 |
| 2 | 抛异常，**异常处理程序能修复**（拆成字节访问） | arm64 的 AArch32 兼容态、部分老架构 | 更慢，但对 |
| 3 | 抛异常，但**信息不足以修复** | 部分老 RISC | 直接错 |
| 4 | 不抛异常，**默默访问了别的地址** | 架构定义的怪癖 | 隐蔽 bug |

结论（内核文档原意）：**按"目标架构要求自然对齐"来写代码，是唯一能在所有架构上既正确又不慢的策略**——这也回应了书中"即使能够处理随机对齐的体系结构，其读写性能也比不对齐要快"的另一半：非对齐代码在最好的架构上也只是"慢"，在最差的架构上是"错"。

## 6. 小结

| 问题 | ARM (arm64) | x86_64 (EPYC 9996) |
|---|---|---|
| 普通 load/store 非对齐 | Normal 内存：硬件执行（Linux 设 A=0）；Device 内存：fault | 硬件执行，不 fault |
| 原子/独占指令非对齐 | fault（无 LSE2）；LSE2 下 16B 块内允许 | 跨缓存行 → 总线锁（千周期级） |
| 单拷贝原子性 | 仅对齐访问保证（B2.2.1） | 对齐访问天然原子（x86 保证对齐的 ≤8B 访问原子） |
| 指令/栈指针对齐 | PC 4B 硬性；SP 16B（SA/SA0 位，Linux 开启） | 指令可从任意字节边界取；SP 16B 仅 ABI 约定（无硬件检查，EFLAGS.AC 例外） |
| 故障上报 | Data Abort（EC=0b100100/0b100101）+ DFSC=0b100001 | #AC（split-lock 检测：无需 CR0.AM，见 §4；经典对齐检查：需 CR0.AM+EFLAGS.AC 且仅用户态）/ #GP（SSE 对齐指令如 movaps） |
| 内核可配置惩罚 | 无（fault 即 bug） | split_lock_detect=warn/fatal（Intel） |
| `HAVE_EFFICIENT_UNALIGNED_ACCESS` | ✅（arm64 Kconfig:200） | ✅（x86 Kconfig:238） |

正确性视角的完整链条：**对齐 → 单次硬件事务 → 单拷贝原子 → 无锁代码正确**。性能视角（双倍缓存行填充、DMA、伪共享）见下篇。
