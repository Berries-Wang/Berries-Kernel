# 非对齐访问：高速缓存性能视角 —— "高效使用处理器高速缓存"

> 学习: [深入Linux内核架构.pdf](../../007.BOOKs/深入Linux内核架构.pdf) 附录 A.3（PDF 物理页 917）；
> [../003.高速缓存/009.缓存行cacheline64字节为什么这是性能优化的圣杯.md](../003.高速缓存/009.缓存行cacheline64字节为什么这是性能优化的圣杯.md)（64B 的由来：DDR burst × 总线宽度）
>
> 书中对应原句："将数据对齐到特定的内存地址，对于**高效使用处理器高速缓存**和提升性能，都很有必要。即使能够处理随机对齐的体系结构，在一定的对齐条件下，其**读写性能**也比不对齐的访问要快速。"

上一篇（[002.非对齐访问-架构正确性视角.md](002.非对齐访问-架构正确性视角.md)）回答了"非对齐为什么会**错**"；本篇回答"非对齐为什么会**慢**"。答案只有一个标尺：**缓存行（cacheline，64 字节）**——CPU 与内存之间数据搬运的最小单位。

---

## 1. 标尺：三平台缓存行都是 64 字节（证据）

按仓库平台规范，三个平台主实例的缓存行大小及其**硬件出处**如下（各层级均为 64B）：

| 平台 | L1/L2 缓存行 | LLC 缓存行 | 硬件证据（CTR_EL0，"Log2 of the number of words"） |
|---|---|---|---|
| **AMD EPYC 9996**（x86_64，Zen 6c，256C/512T） | 64B | 64B（16 CCX × 64MB L3） | CPUID/`/sys/devices/system/cpu/cpu0/cache/index*/coherency_line_size` = 64；内核编译期 `CONFIG_X86_L1_CACHE_SHIFT=6` |
| **Arm AGI CPU SP113012**（Neoverse V3，136C） | 64B | SLC 64B（CMN-700） | [Neoverse V3 TRM](../../007.BOOKs/arm_neoverse_v3_core_technical_reference_manual_107734_0002_06_en.pdf) p.369-370：CTR_EL0 的 TminLine/IminLine/CWG 均 0b0100（log2(16 words) → 16×4B = **64 bytes**）；[CMN-700 TRM](../../007.BOOKs/arm_neoverse_cmn_700_trm_102308_0307_08_en.pdf) p.45：Snoop Filter 按 cacheline 跟踪 RN-F 中的行 |
| **Cortex-A725 / A520**（异构 big.LITTLE） | 64B | DSU-120 L3 64B | [A725 TRM](../../007.BOOKs/arm_cortex_a725_core_trm_107652_0001_04_en.pdf) p.448、[A520 TRM](../../007.BOOKs/arm_cortex_a520_core_trm_102517_0001_04_en.pdf) p.354：DminLine/CWG/IminLine 均 0b0100 = **64 bytes**；[DSU-120 TRM](../../007.BOOKs/arm_dsu_120_trm_102547_0201_07_en.pdf) p.18："Optional unified 16-way set-associative L3 cache... **64-byte cache lines**"；A520 TRM p.79 另证 DC ZVA 清零的也是 64B 对齐块 |

LLC（V3 的 SLC / A725·A520 的 DSU-120 L3）同为 64B 行意味着：**伪共享、RFO、snoop 的最小单位贯穿全缓存层级**——对齐问题不会在某一层"被抹平"。

### 1.1 DminLine ≠ CWG：两个容易混淆的字段（CTR_EL0）

CTR_EL0 里有两个与"行大小"相关的字段，语义不同（DDI0487M [vol12 物理页 1740](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-12001-15000.pdf#page=1740)）：

| 字段 | ARM ARM 语义（原文转述） | 用途 |
|---|---|---|
| **DminLine** [19:16] | "Log2 of the number of words in the **smallest cache line** of all the data caches and unified caches" | 决定**访问粒度**：一次 load/store 最少搬多少 |
| **CWG**（Cache Writeback Granule）[27:24] | "Log2 of the number of words of the **maximum size of memory that can be overwritten** as a result of the **eviction** of a cache entry" | 决定**逐出/无效化粒度**：一次缓存维护操作可能覆写的最大连续内存 |

关键差别：**CWG 可以大于 DminLine**（一条"行"逐出时可能连带写回更宽的块）；且 CWG=0b0000 时架构要求按**最大 512 words（2KB）**假设。内核运行期正是读 CWG 来定缓存维护/DMA 的粒度（`cache.h:72-84`），读不到时退回 `ARCH_DMA_MINALIGN`(128)——这个保守值就是对"CWG 可能比行大"的工程兜底，见 §4。

arm64 内核对这两个字段的运行期读取（用于 `cache_line_size()`，进而喂给 slab/skb/DMA 的对齐决策）：

```c
// arch/arm64/include/asm/cache.h:8
#define L1_CACHE_SHIFT		(6)          // 2^6 = 64B：编译期兜底值
#define L1_CACHE_BYTES		(1 << L1_CACHE_SHIFT)

// arch/arm64/include/asm/cache.h:79
static inline int cache_line_size_of_cpu(void)
{
	u32 cwg = cache_type_cwg();          // 运行期读 CTR_EL0.CWG（写回粒度）
	return cwg ? 4 << cwg : ARCH_DMA_MINALIGN;   // CWG=0 → 按 128B 兜底
}
```

```c
// arch/arm64/kernel/cacheinfo.c:15
int cache_line_size(void)
{
	if (coherency_max_size != 0)
		return coherency_max_size;   // CLIDR 探测出的最大一致性粒度
	return cache_line_size_of_cpu();
}
EXPORT_SYMBOL_GPL(cache_line_size);
```

## 2. 核心代价①：跨行访问 = 双倍缓存事务

一个 8 字节 load 落在缓存行边界上：

```
地址:      0x3C        0x40
            │           │
  ┌─────────┼───────────┼──────────────────────────┐
  │ ......▓▓│▓▓▓▓......│                          │
  └─────────┼───────────┼──────────────────────────┘
  │←─ 行 0 (0x00-0x3F) ─→│←── 行 1 (0x40-0x7F) ───→│
       占 4 字节              占 4 字节

  u64 v = *(u64 *)0x3C;    // 非对齐：横跨两行
```

两次缓存缺失时会发生什么：

| | 对齐（一次访问一行） | 非对齐跨行 |
|---|---|---|
| linefill 次数 | 1 次（64B） | **2 次（2×64B = 128B）** |
| 总线事务 | 1 | 2 |
| 写路径（RMW 视角） | 1 次所有权获取 | **2 次 RFO**（读所有权），两行都要拉进本核缓存独占 |
| 一致性流量 | 1 行的 MESI 流量 | 2 行的 MESI 流量 |

要点：

- **浪费的是带宽，不只是延迟**。搬运的 128B 里有 112B 与本次访问无关。单次访问贵 ~1 倍尚可接受；对带宽敏感路径（报文处理、拷贝、遍历数组）叠加起来是实打实的吞吐损失——缓存行填充占用的总线周期挤占了其他核的带宽。
- **连续非对齐访问会持续双倍付费**：遍历一个落错了相位的 `u64[]` 数组，每 8 个元素中有一个跨行 → 平摊 1/8 概率的 2×linefill，且预取器的跨行模式匹配更差。
- **原子指令跨行是最坏情况**：x86 上退化为总线锁（千周期级，见 [002](002.非对齐访问-架构正确性视角.md) §4）；arm64 上直接 fault。

这也是书中"其读写性能也比不对齐的访问要快速"的微架构翻译：**对齐访问保证落在单个缓存行内，一次访存 = 一次缓存事务**。

### 定量感觉

延迟阶梯（摘自 [009.缓存行cacheline64字节](../003.高速缓存/009.缓存行cacheline64字节为什么这是性能优化的圣杯.md)）：L1 命中 ~4 周期、L2 ~12、L3 ~40、内存 300+ 周期。miss 时跨行访问的两条 linefill 若都到内存，额外开销 ≈ 再付一次完整内存延迟 + 双倍带宽占用——这是"数量级"的差距，不是几个百分点。

## 3. 核心代价②：对象跨行 = 缓存空间与局部性的双重浪费

即使不发生"单次访问跨行"，**对象本身**跨行也有代价。一个 72B 的对象若起始于行中间，将占据 2~3 行；每次分配、释放、扫描都多触碰一行。这就是 slab 分配器提供 `SLAB_HWCACHE_ALIGN` 的原因：

```c
// include/linux/slab.h:83
/**
 * define SLAB_HWCACHE_ALIGN - Align objects on cache line boundaries.
 *
 * Sufficiently large objects are aligned on cache line boundary. For object
 * size smaller than a half of cache line size, the alignment is on the half of
 * cache line size. In general, if object size is smaller than 1/2^n of cache
 * line size, the alignment is adjusted to 1/2^n.
 */
#define SLAB_HWCACHE_ALIGN	__SLAB_FLAG_BIT(_SLAB_HWCACHE_ALIGN)
```

```c
// mm/slab_common.c:128
static unsigned int calculate_alignment(slab_flags_t flags,
		unsigned int align, unsigned int size)
{
	if (flags & SLAB_HWCACHE_ALIGN) {
		unsigned int ralign;

		ralign = cache_line_size();      // 运行期读 CTR_EL0（64B）
		while (size <= ralign / 2)      // 小对象逐步减半对齐，平衡空间浪费
			ralign /= 2;
		align = max(align, ralign);
	}

	align = max(align, arch_slab_minalign());
	return ALIGN(align, sizeof(void *));
}
```

注意 `while (size <= ralign / 2) ralign /= 2;` 的权衡：对齐到整行能保证"对象不跨行"，但对 16B 小对象强制 64B 对齐会浪费 75% 内存——所以**小对象允许半行/四分之一行对齐**（反正也跨不了行）。对齐从来不是越大越好，而是"刚好不跨行"。

## 4. 核心代价③：DMA 缓冲与缓存行"共享"——对齐换正确性+性能

arm64 把 DMA 最低对齐定为 **128 字节**（两倍缓存行），源码注释把动机写得非常直白：

```c
// arch/arm64/include/asm/cache.h:28
/*
 * Memory returned by kmalloc() may be used for DMA, so we must make
 * sure that all such allocations are cache aligned. Otherwise,
 * unrelated code may cause parts of the buffer to be read into the
 * cache before the transfer is done, causing old data to be seen by
 * the CPU.
 */
#define ARCH_DMA_MINALIGN	(128)
```

场景推演（非一致 DMA，RX 方向）：DMA 缓冲若与**别的内核数据共享同一缓存行**——
1. 邻居数据被 CPU 访问 → 整行（含缓冲的尾巴）进入 L1；
2. DMA 直接写内存 → L1 里那部分变陈旧；
3. CPU 读缓冲前必须 `dma_sync_single_for_cpu()` 做失效 → **把无辜邻居一起失效掉**，下次访问邻居再 miss 一次。

对齐到缓存行（此处保守取 128B）后，缓冲独占整行，失效操作不伤及无辜——注释里"old data to be seen by the CPU"说的是正确性，而"邻居反复被失效/回填"就是隐藏的性能税。**对齐让"按行失效"这个粗粒度操作恰好只影响它该影响的数据**，这是"高效使用处理器高速缓存"最实在的一条。

为什么取 128B 而不是刚好 64B？结合 §1.1 的 CWG 语义就能读懂：缓存维护（clean/invalidate）按**写回粒度**工作，而 CWG 允许大于 DminLine（CWG=0b0000 时甚至要按 2KB 假设）。缓冲只对齐到 DminLine(64B) 时，一次 128B 宽的逐出仍可能覆写缓冲相邻的数据；两倍行长的 `ARCH_DMA_MINALIGN` 给这类实现留了裕量。配套接口 `dma_get_cache_alignment` 直接映射到运行期 `cache_line_size()`：

```c
// arch/arm64/include/asm/cache.h:88
#define dma_get_cache_alignment	cache_line_size
```

网络栈对同一问题的另一处权衡注释（`NET_IP_ALIGN`，为什么预留 2 字节把 IP 头推到对齐位置）：

```c
// include/linux/skbuff.h:3274
/*
 * CPUs often take a performance hit when accessing unaligned memory
 * locations. The actual performance hit varies, it can be small if the
 * hardware handles it or large if we have to take an exception and fix it
 * in software.
 *
 * Since an ethernet header is 14 bytes network drivers often end up with
 * the IP header at an unaligned offset. The IP header can be aligned by
 * shifting the start of the packet by 2 bytes. Drivers should do this
 * with:
 *
 *	skb_reserve(skb, NET_IP_ALIGN);
 *
 * The downside to this alignment of the IP header is that the DMA is now
 * unaligned. On some architectures the cost of an unaligned DMA is high
 * and this cost outweighs the gains made by aligning the IP header.
 *
 * Since this trade off varies between architectures, we allow NET_IP_ALIGN
 * to be overridden.
 */
#ifndef NET_IP_ALIGN
#define NET_IP_ALIGN	2
#endif
```

这段注释几乎就是书中那句话的内核版："性能代价可小（硬件处理）可大（异常修复）"，并且展示了**对齐是可权衡的工程决策**（CPU 侧对齐 vs DMA 侧对齐二选一，允许各架构覆写）。配套地：

```c
// include/linux/skbuff.h:256
#define SKB_DATA_ALIGN(X)	ALIGN(X, SMP_CACHE_BYTES)   // skb 数据区按缓存行向上对齐

// include/linux/skbuff.h:3318
#ifndef NET_SKB_PAD
#define NET_SKB_PAD	max(32, L1_CACHE_BYTES)
#endif
// 注释（skbuff.h:3313）：Using max(32, L1_CACHE_BYTES) makes sense (especially
// with RPS) to reduce average number of cache lines per packet.
// get_rps_cpu() for example only access one 64 bytes aligned block:
// NET_IP_ALIGN(2) + ethernet_header(14) + IP_header(20/40) + ports(8)
```

`NET_SKB_PAD` 的注释点破了网络栈的对齐设计目标：**让 RPS 选核时只碰一个 64B 对齐块**（2+14+20+8=44B < 64B）——头部处理的热数据被刻意聚进一行。

## 5. 核心代价④：伪共享——对齐的"反向应用"

前四节是"让数据**进**对的位置"；伪共享是"让**不相关**的数据**分**开"：两个 CPU 各改各的变量，若同处一行，MESI 协议会让这行在两个核之间来回弹跳（写权限独占），性能可劣化 10 倍量级。解法正是对齐到缓存行：`____cacheline_aligned` / `____cacheline_aligned_in_smp`。

这是对齐服务于"高效使用高速缓存"的另一半，且与本文互为正反面，完整展开见 [../003.高速缓存/006.高速缓存伪共享.md](../003.高速缓存/006.高速缓存伪共享.md)，内核宏的实现见 [004.内核对齐工具箱-源码全景.md](004.内核对齐工具箱-源码全景.md) §4。

## 6. 性能收益汇总表

| 对齐手段 | 作用机制 | 直接收益 |
|---|---|---|
| 自然对齐（编译器自动） | 访问不跨行、保证单拷贝原子 | 不触发异常路径；无锁读正确 |
| `SLAB_HWCACHE_ALIGN`（slab 对象按行对齐） | 对象不跨行 | 遍历/分配少触碰行；行内对象密度稳定 |
| `SKB_DATA_ALIGN` / `NET_IP_ALIGN` / `NET_SKB_PAD` | 报文头聚进一个 64B 块 | 每包平均触碰行数下降（RPS 路径 1 行） |
| `ARCH_DMA_MINALIGN=128`（DMA 缓冲对齐） | 缓冲独占缓存行 | 失效不伤邻居；无陈旧数据 |
| `____cacheline_aligned`（结构体按行对齐） | 隔离不同所有者的数据 | 消除伪共享的一致性弹跳 |
| `__read_mostly`（读多写少数据集中） | 热路径只读数据紧凑共处 | 减少关键路径触碰的行数 |

## 附录：Cortex-A725 + A520 异构教学对照

同为 64B 缓存行、同为 Armv9.2-A，两颗核**感受**非对齐代价的方式不同——这解释了为什么"能跑"不等于"跑得好"：

| | Cortex-A725（大核，乱序） | Cortex-A520（小核，顺序） |
|---|---|---|
| 微架构 | 乱序执行，深乱序窗口 | 顺序双发射（in-order） |
| L2 | 每核私有 128KB~1MB | 每 complex（一对核）共享 128~512KB |
| 缓存行 | 64B（TRM p.448） | 64B（TRM p.354；DC ZVA 亦 64B，p.79） |
| 跨行访问的额外延迟 | 可被乱序引擎**部分隐藏**（访存乱序发出，延迟被其他指令填坑） | 直接顶在**流水线关键路径**上：顺序核等不到数据就整核停顿 |
| 代价放大场景 | 带宽敏感路径（两行的事务照付） | 延迟敏感路径（小核频率低、停顿周期更贵） |
| 工程含义 | 大核上测不出的非对齐劣化，**切到 A520 上可能显著**——异构系统性能验证必须覆盖小核 |

对照 AGI CPU（Neoverse V3，服务器同构 136C）：服务器负载吞吐导向，非对齐主要表现为**带宽浪费与一致性流量增加**；终端式 big.LITTLE 上则更多表现为**小核延迟悬崖**。同一句"对齐到特定内存地址对高效使用处理器高速缓存很有必要"，在三类平台上的"痛点画像"不同，但物理根源（64B 行）完全一致。
