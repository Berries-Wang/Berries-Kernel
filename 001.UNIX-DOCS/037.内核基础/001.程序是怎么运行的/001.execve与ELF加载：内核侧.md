# execve 与 ELF 加载：内核怎么把程序装进地址空间

> **定位**："程序是怎么运行的"系列的内核侧半程——从 shell 敲下命令（`fork` + `execve`）到 CPU 即将第一次跳进新程序。主基准 [003.LINUX-7.1.3](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3)，`file:line` 实测；用户态半程（`_start → __libc_start_main → main`）见 [002.从_start到main](./002.从_start到main：用户态的接力.md)，PC 的下一站在 [000.Program Counter 与0x8000](./000.Program%20Counter%20与0x8000.md)。

## 0. 一句话总结

**`execve` = "旧进程的皮，新程序的芯"：地址空间整套作废重建，按 ELF 的 `PT_LOAD` 段逐个 `mmap` 进来，把 `argc/argv/envp/auxv` 摆到新栈上，最后 `start_thread()` 把 `pt_regs.pc` 设成 ELF 入口、`pstate` 设成 EL0t——返回用户态那一刻，CPU 就"已经在"新程序里了。**

## 1. 触发与总分发：exec.c 的调用链

shell 先 `fork` 出子进程，子进程里调 `execve`：

```
 应用(shell 子进程)                    内核
 ────────────────────────────────────────────────────────────────────
 execve("/bin/ls", argv, envp)
   │ (svc #0 陷入 EL1, x8=系统调用号)
   ▼
 SYSCALL_DEFINE3(execve, ...)                       fs/exec.c:1924
   └─ do_execveat_common(AT_FDCWD, ...)             fs/exec.c:1778
        ├─ 打开文件, 检查执行权限
        ├─ prepare_binprm(): 读文件头(BINPRM_BUF_SIZE=256 字节)到 bprm->buf
        │    (struct linux_binprm = 装载上下文: 文件/参数串/栈顶...)
        └─ bprm_execve(bprm)                        fs/exec.c:1724
             └─ exec_binprm(bprm)                   fs/exec.c:1679
                  └─ search_binary_handler(bprm)    fs/exec.c:1645
                       │
                       │  formats 链表(fs/exec.c:88)逐个试:
                       │  list_for_each_entry(fmt, &formats, lh)   :1659
                       │    binfmt_elf  ← ELF 头 \x7fELF 命中(本篇)
                       │    binfmt_script ← #! 命中(转手再 exec 解释器)
                       │    binfmt_misc ...
                       └─► fmt->load_binary(bprm) = load_elf_binary()
```

> `#!` 脚本的"再入 exec"也在这条链上：`binfmt_script` 把解释器路径换进 bprm 后重新走 `search_binary_handler`——这就是脚本也能被执行的原理。

## 2. load_elf_binary：按 program header 装配地址空间

ELF 头与 `load_elf_phdrs()`（[fs/binfmt_elf.c:520](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/fs/binfmt_elf.c)）读出的 program header 是装配图纸：

| phdr 类型 | 内核动作 | 锚点 |
| - | - | - |
| `PT_LOAD`（可执行段） | `elf_map()` → `vm_mmap()` 建立映射（权限→VM_READ/EXEC） | binfmt_elf.c:371 |
| `PT_LOAD`（数据段） | 同上（VM_READ/WRITE）；BSS 尾部 `set_brk` 清零 | binfmt_elf.c:1229 附近 |
| `PT_INTERP` | 读出解释器路径（如 `/lib/ld-linux-aarch64.so.1`），**把动态链接器也当一个 ELF 装进来**，入口改指它 | binfmt_elf.c:969/1254 |
| `PT_DYNAMIC` 等 | 留给运行期（ld.so 读 GOT/重定位），内核不管 | —— |

随后摆栈、建表、设寄存器：

```c
// fs/binfmt_elf.c:1028（栈：从 STACK_TOP 向下铺 argc/argv/envp/auxv）
	retval = setup_arg_pages(bprm, randomize_stack_top(STACK_TOP),
				 executable_stack);
// fs/binfmt_elf.c:1296（把 argc/argv/envp 与辅助向量 auxv 写进新栈）
	retval = create_elf_tables(bprm, elf_ex, interp_load_addr,
				   e_entry, phdr_addr);
```

- `STACK_TOP`（arm64）：[arch/arm64/include/asm/processor.h:90](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/processor.h)，64 位即 `STACK_TOP_MAX`（默认 `DEFAULT_MAP_WINDOW_64`）；
- **auxv（辅助向量）是内核→用户态的"交接清单"**：`AT_PHDR/AT_PHENT/AT_PHNUM`（程序头在哪，ld.so 自重定位要用）、`AT_ENTRY`（`= e_entry`，即 `_start` 地址）、`AT_BASE`（ld.so 基址）、`AT_RANDOM`（栈保护 canary 种子）、`AT_PAGESZ`……ld.so 与 glibc 启动全靠它（见 [002](./002.从_start到main：用户态的接力.md)）。

## 3. 最后一步：start_thread 设定 PC 与 PSTATE

装载完成后，内核不"跳转"到新程序——它只修改当前进程保存的寄存器现场 `pt_regs`，**真正切换发生在系统调用返回的 `eret`**：

```c
// fs/binfmt_elf.c:1379
	START_THREAD(elf_ex, regs, elf_entry, bprm->p);
```

arm64 的实现（两个 inline，几行就说完了）：

```c
// arch/arm64/include/asm/processor.h:302
static inline void start_thread_common(struct pt_regs *regs, unsigned long pc,
				       unsigned long pstate)
{
	/*
	 * Ensure all GPRs are zeroed, and initialize PC + PSTATE.
	 * The SP (or compat SP) will be initialized later.
	 */
	regs->user_regs = (struct user_pt_regs) {
		.pc = pc,          // ← PC 的下一站:ELF e_entry(_start)
		.pstate = pstate,  // ← PSR_MODE_EL0t:返回后处于 EL0(用户态)
	};
	...
}

// arch/arm64/include/asm/processor.h:336
static inline void start_thread(struct pt_regs *regs, unsigned long pc,
				unsigned long sp)
{
	start_thread_common(regs, pc, PSR_MODE_EL0t);
	spectre_v4_enable_task_mitigation(current);
	regs->sp = sp;          // ← 新栈顶(刚铺好 argc/argv/envp/auxv 的地方)
}
```

另外 `ELF_PLAT_INIT`（arm64：[arch/arm64/include/asm/elf.h:159](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/elf.h)）把 `x0` 清零——注意区分**两个时刻的 `x0`**：execve 时刻内核把全部 GPR 清零（含 `x0`）；而 ABI 里"`x0` = rtld_fini 析构回调"说的是**之后 ld.so 完成重定位、跳向程序 `_start` 的那一刻**由 ld.so 装入（静态链接时没人装，`_start` 看到的 `x0` 就是 0；glibc `_start` 把它存进 `x5`，见 [002](./002.从_start到main：用户态的接力.md) §2）。同段上文 `prepare_binprm` 读的文件头长度 `BINPRM_BUF_SIZE=256` 定义在 [include/uapi/linux/binfmts.h:19](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/uapi/linux/binfmts.h)。

## 4. 装载完成时刻的地址空间全景

```
 高地址 ▲                                    (arm64, 小端)
        │  STACK_TOP(processor.h:90)
        │  ┌────────────────────────┐
        │  │ envp/argv 字符串池       │
        │  │ auxv(AT_*) ┐            │
        │  │ envp[]     │ 内核铺好的  │
        │  │ argv[]     │ 启动栈      │  sp ──► bprm->p
        │  │ argc       ┘            │
        │  │          (向下增长)      │
        │  ├────────────────────────┤
        │  │         ...             │
        │  │  [ld.so 的 PT_LOAD 段]  │ ← AT_BASE(动态链接器,interp)
        │  │  [vdso/vvar]           │
        │  │         ...             │
        │  │  [.bss  (匿名,清零)]     │
        │  │  [.data (文件后备,可写)] │ ← PT_LOAD #2
        │  │  [.rodata(只读)]        │
        │  │  [.text (可执行)]       │ ← PT_LOAD #1
        │  │                         │    e_entry 指向这里(动态链接时
        │  └────────────────────────┘    e_entry=ld.so 入口, ld.so 干完活
                                         再按 auxv 的 AT_ENTRY 跳到 _start)
 低地址 ▼
 注:段地址由 mmap 布局(自顶向下/自底向上随机化),页粒度映射;
    文件里相邻段在内存里被页边界分开 —— 这正是"程序头 vs 落地布局"的差异
```

此刻进程：**代码没执行过一行，但 PC 已指向 `e_entry`（静态=`_start`；动态=ld.so 入口）、栈上已摆好参数、全部 GPR 含 `x0` 均为 0、PSTATE=EL0t**。内核从 `execve` 系统调用原路返回，`eret` 一出，用户程序（或先行的 ld.so）开始运行。

## 5. FAQ

**Q：execve 为什么不新建进程？**
A：它只"换芯"——PID、打开的文件（除非 `O_CLOEXEC`）、信号处置等大多保留。shell 的 `fork+execve` 组合里，"新进程"是 fork 干的，"新程序"才是 execve 干的。

**Q：动态链接器的重定位谁做？**
A：内核只负责"装载"，不做用户态重定位——ld.so 自举（借助 auxv 的 `AT_PHDR/AT_BASE`）后替整个程序做 GOT/PLT 填充，这正是 [028.编译原理/000.链接器](../../028.编译原理/000.链接器/README.md) §4 里 `R_AARCH64_ADR_GOT_PAGE` 那条线的运行期归宿。

**Q：与内核自身启动的对照？**
A：同构对照很有趣——内核启动也是"bootloader 装载 + 跳入口"（arm64 `head.S` 的 `_head`，见 [029.内核启动流程](../../029.内核启动/002.内核启动流程/README.md)），只是没有 ELF 加载器，物理放置 + 自重定位（`.rela.dyn`）。
