# Linux 内核启动与设备树

> 分析起点:`init/main.c:839` 的 `start_kernel()`,追踪设备树(Device Tree)**加载 → 解析 → 应用** 的完整过程。
>
> 内核版本:Linux 5.9 (ARM64)

## 整体脉络

```c
start_kernel()                              init/main.c:839
│
├── setup_arch(&command_line)               init/main.c:867  ── 设备树"加载 + 早期解析"
│     └── [arch/arm64/kernel/setup.c:291]
│           ├── setup_machine_fdt(__fdt_pointer)      ← ① 加载 + 扫描
│           └── unflatten_device_tree()               ← ② 展开成 device_node 树
│
├── init_IRQ()                              init/main.c:952  ── ③ 中断控制器(从DT找)
├── time_init()                             init/main.c:973  ── ④ 时钟/定时器(从DT找)
└── arch_call_rest_init()                   init/main.c:1062
      └── rest_init() → kernel_init() → do_basic_setup()
            └── do_initcalls()                           ← ⑤ 平台设备注册与驱动加载
                  └── of_platform_default_populate_init()   (arch_initcall_sync)
```

四个阶段与内核启动日志的对应关系:

| 阶段 | 对应日志 | 说明 |
|------|---------|------|
| ① 加载 | `Machine model: linux,dummy-virt` | fixmap 映射 DTB + 读 machine 名 |
| ② 解析 | `NUMA: Faking a node at [mem ...]`、`Zone ranges:` | 内存信息来自 DT 的 memory 节点 |
| ③④ 应用 | `psci: probing for conduit method from DT.`、`GICv2m: range[mem ...]`、`arch_timer: cp15 timer(s) running...` | PSCI / 中断控制器 / 定时器 |
| ⑤ 应用 | `9000000.pl011: ttyAMA0 at MMIO...`、`pl061_gpio 9030000.pl061`、`rtc-pl031 9010000.pl031` | 设备树节点 → platform_device → 驱动 probe |

## ① 加载:把 bootloader 传的 DTB 映射进内核

bootloader 把 DTB **物理地址**放在 `x0` 寄存器传给内核,`head.S` 的 `preserve_boot_args()` 把它保存到 `__fdt_pointer` 全局变量。

```
setup_machine_fdt(dt_phys)                         arch/arm64/kernel/setup.c:171
│
├─ fixmap_remap_fdt(dt_phys, &size, PAGE_KERNEL)    arch/arm64/mm/mmu.c:1720
│     │  - 校验 MIN_FDT_ALIGN(至少 8 字节对齐)
│     │  - 读 FDT magic 判断是否合法
│     ├─ create_mapping_noalloc(...)  ← 把DTB先映射到 fixmap 的 FIX_FDT 槽位
│     └─ 返回虚拟地址 dt_virt
│
├─ memblock_reserve(dt_phys, size)                  ← 把DTB物理内存保护起来,不再分配
│
└─ early_init_dt_scan(dt_virt)                      ← 进入解析阶段
```

关键点:
- 此时 MMU 刚开启、常规内核映射还没建好,所以用 **fixmap(固定映射区)** 临时映射 DTB。
- 第一块只映射 `SWAPPER_BLOCK_SIZE`(通常是 2M),读出头部的 `fdt_totalsize()` 后,再把整个 DTB 映射完。
- 映射完成后立即 `memblock_reserve()`,防止 DTB 所在物理内存被后续分配器重用。

## ② 解析:两遍扫描

### 第一遍:扁平扫描(flat scan)— `early_init_dt_scan`

```
early_init_dt_scan(params)                       drivers/of/fdt.c:1221
│
├─ early_init_dt_verify(params)                  drivers/of/fdt.c:1183
│     ├─ fdt_check_header(params)         ← 校验DTB头(magic/version/totalsize)
│     ├─ initial_boot_params = params     ← 保存全局DTB指针(后续全靠它)
│     └─ of_fdt_crc32 = crc32_be(...)     ← 计算CRC
│
└─ early_init_dt_scan_nodes()                    drivers/of/fdt.c:1200
      │  (of_scan_flat_dt 逐个节点线性遍历扁平树,见 fdt.c:631)
      ├─ of_scan_flat_dt(early_init_dt_scan_chosen, boot_command_line)
      │      └─ 解析 /chosen 节点                       fdt.c:1047
      │            ├─ early_init_dt_check_for_initrd()  ← initrd 起始地址/大小
      │            ├─ 读 bootargs → 填充 command_line  ← 内核启动参数来自DT!
      │            └─ 读 rng-seed → add_bootloader_randomness()
      │
      ├─ of_scan_flat_dt(early_init_dt_scan_root, NULL)
      │      └─ 解析根节点 #address-cells / #size-cells   fdt.c:958
      │            写入 dt_root_addr_cells / dt_root_size_cells
      │            ★ 这是后续解析所有 reg 属性的"进制位数"
      │
      └─ of_scan_flat_dt(early_init_dt_scan_memory, NULL)
             └─ 遍历 device_type="memory" 的节点           fdt.c:997
                   └─ early_init_dt_add_memory_arch(base,size)  fdt.c:1116
                         └─ memblock_add(base, size)
                               ★ 内存信息全部来自设备树,填进 memblock
```

> **关键点**:此时**还没有** `device_node` 树,只是对扁平 DTB 做线性扫描,提取三个关键信息:
> 1. `/chosen/bootargs` → 内核命令行参数
> 2. 根节点 `#address-cells`/`#size-cells` → 后续 reg 解析的位数依据
> 3. `memory` 节点的 `reg` → 物理内存布局 → `memblock_add()`

### 展开为树(第二遍)— `unflatten_device_tree`

真正的"设备树"树形结构在这一步建立,把扁平 DTB 变成内存中的 `struct device_node` 树,之后才可以用 `of_find_node_by_path()`、`for_each_matching_node()` 等常规 API 遍历。

```
unflatten_device_tree()                          drivers/of/fdt.c:1241
│
├─ __unflatten_device_tree(initial_boot_params, NULL, &of_root, ...)
│                                                  drivers/of/fdt.c:367
│     ├─ unflatten_dt_nodes(blob, NULL, NULL, NULL)   ← 第一趟:只算需要的内存size
│     │        ├─ fdt_next_node() 遍历整棵树
│     │        └─ populate_node() 只做 dryrun,不分配
│     ├─ mem = early_init_dt_alloc_memory_arch(size,...) ← 按算出的size分配内存
│     └─ unflatten_dt_nodes(blob, mem, ...)        ← 第二趟:真正构造节点
│           ├─ populate_node()  → 构造 device_node + property 链表
│           └─ reverse_nodes()  ← 翻转子节点顺序,保持 dts 中的节点顺序
│
├─ of_alias_scan(early_init_dt_alloc_memory_arch)  ← 扫描 /aliases 节点
│     为每个 alias 建立 "别名 → device_node" 的索引表
└─ unittest_unflatten_overlay_base()
```

> 为什么分两趟?因为 device_node 树需要**连续内存块**一次分配,先 dryrun 一趟算出总大小,分配后再真正填充。

`setup_arch` 里,在 `unflatten_device_tree()` 之前/之后还依赖 DT 做了这些事:

```
setup_arch 继续                              arch/arm64/kernel/setup.c
├─ arm64_memblock_init()        setup.c:351  ← 依赖前面DT填好的memblock
├─ paging_init()                setup.c:356  ← 真正建立内核页表
├─ unflatten_device_tree()      setup.c:364  ← 展开device_node树(仅ACPI禁用时)
├─ psci_dt_init()               setup.c:375  ← 从DT找 /psci 节点
│      └─ drivers/firmware/psci/psci.c:563
│            └─ of_find_matching_node_and_match(psci_of_match)
│                  ← compatible 匹配 "arm,psci"/"arm,psci-0.2"/"arm,psci-1.0"
│                  ← 对应日志: "psci: probing for conduit method from DT."
└─ smp_init_cpus()              setup.c:380  ← 从DT的 /cpus 读CPU信息
```

## ③④ 应用:中断控制器、时钟

`start_kernel` 后半段,设备树开始驱动硬件子系统初始化:

```
init_IRQ()                                  init/main.c:952
└─ arch/arm64/kernel/irq.c:63
      └─ irqchip_init()                     drivers/irqchip/irqchip.c:29
            └─ of_irq_init(__irqchip_of_table)   drivers/of/irq.c:479
                  │  遍历DT中带 interrupt-controller 属性的节点
                  │  按"父先子后"的拓扑顺序
                  │  调用各中断控制器驱动的 init 回调(如 GIC、GICv2m)
                  │  → 建立 irq domain,完成中断树
                  └─ 对应日志: "GICv2m: range[mem 0x08020000-0x08020fff]..."

time_init()                                 init/main.c:973
└─ arch/arm64/kernel/time.c:54
      ├─ of_clk_init(NULL)      ← 遍历DT的 /clocks 节点,初始化时钟树
      └─ timer_probe()          drivers/clocksource/timer-probe.c:16
            └─ for_each_matching_node_and_match(__timer_of_table)
                  ← compatible 匹配 timer 节点(如 arm,armv8-timer)
                  └─ 对应日志: "arch_timer: cp15 timer(s) running at 62.50MHz"
```

> 注意 `of_irq_init` 的**父先子后**排序:先找到没有 `interrupt-parent` 的根中断控制器初始化,再逐层初始化引用它的子控制器。详见 `drivers/of/irq.c:479`。

## ⑤ 应用:平台设备注册 + 驱动匹配

在 `start_kernel` 结尾通过 `arch_call_rest_init()` 创建 `kernel_init` 线程,最终在 `do_basic_setup()` 里执行所有 initcall,其中一个就是设备树应用的**总开关**:

```
arch_call_rest_init()                       init/main.c:1062
└─ rest_init() → kernel_thread(kernel_init)
      └─ kernel_init() → kernel_init_freeable()      init/main.c:1412/1493
            └─ do_basic_setup()                     init/main.c:1320
                  └─ do_initcalls()                 init/main.c:1294
                        └─ of_platform_default_populate_init()
                                               drivers/of/platform.c:517 (arch_initcall_sync)
                              ├─ of_platform_default_populate(NULL,...)
                              │     └─ of_platform_populate(root, of_default_bus_match_table,...)
                              │           └─ of_platform_bus_create() 递归遍历整棵树
                              │                 └─ of_platform_device_create_pdata()
                              │                       └─ platform_device_register()
                              │                             ← 每个有compatible的节点 → platform_device
                              └─ → 触发 driver 的 .probe()(靠 of_device_id 匹配)
```

对应的启动日志(设备已实例化并被驱动接管):

```
9000000.pl011: ttyAMA0 at MMIO 0x9000000 (irq = 39, ...) is a PL011 rev1   ← uart-pl011 驱动
pl061_gpio 9030000.pl061: PL061 GPIO chip registered                        ← pl061 驱动
rtc-pl031 9010000.pl031: registered as rtc0                                  ← rtc-pl031 驱动
pci-host-generic 4010000000.pcie: host bridge /pcie@10000000 ranges:         ← pci-host-generic
```

至此,设备树的每个节点都变成了内核设备模型的对象(`device_node` → `platform_device`),再靠 `compatible` 属性与驱动 `of_device_id` 匹配,驱动开始工作。

## 一句话总结

> DTB 由 bootloader 通过 `x0` 传给内核 → `fixmap_remap_fdt` 映射 → 第一遍扁平扫描提取启动参数/内存 → `unflatten_device_tree` 展开成 `device_node` 树 → 各子系统(`psci`/`irqchip`/`clk`/`timer`/`platform`)靠 `compatible` 匹配节点完成硬件初始化 → 最后 `of_platform_populate` 把设备节点实例化成设备并匹配驱动。
