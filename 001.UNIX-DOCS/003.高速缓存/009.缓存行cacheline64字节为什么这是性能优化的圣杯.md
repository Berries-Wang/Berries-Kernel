# 缓存行 CacheLine 64字节 — 为什么这是性能优化的圣杯
> 参考: [Bilibili: 缓存行cacheline64字节为什么这是性能优化的圣杯](https://www.bilibili.com/video/BV1UKRnB3EMg/)

## 摘要

|摘要内容|说明|备注|
|-|-|-|
|- 64 字节缓存行不是软件的随意选择，而是 DDR SDRAM burst 长度（8 拍）× 总线宽度（64bit/8 字节）凑出的硬件天然粒度|-|-|
|- 两个完全独立的变量，CPU0 改一个、CPU1 改另一个，如果恰好挤在同一行 64 字节里，性能可能比单线程还慢 10 倍——这就是**伪共享（False Sharing）**|-|-|
|- 理解 64 字节这个数字，就能看懂为什么 Java 要 `@Contended`、为什么 Rust 要 `repr align`、为什么 spinlock 旁边都加一堆看起来没用的 padding|-|-|
|- 这不是奇技淫巧，是物理边界给软件的硬约束|-|-|

## 为什么是 64 字节，不是 32 也不是 128？

### 硬件公式

```
缓存行大小 = DDR Burst 长度 × 总线宽度
           = 8 拍        × 8 字节（64bit）
           = 64 字节
```

- **DDR SDRAM Burst 长度（8 拍）**：DDR 内存每次激活一行后，可以连续突发传输 8 次数据，这是 DDR 协议的硬件特性
- **总线宽度（64bit = 8 字节）**：CPU 到内存控制器的数据总线宽度，每个时钟周期传输 8 字节
- **一拍 8 字节 × 连续 8 拍 = 64 字节**：一次内存事务恰好填满一行缓存行

Intel、AMD、ARM 主流架构全都统一到 64 字节。多搬会浪费带宽，少搬则不够用——64 字节是 DDR 协议和总线宽度交汇出的"最优传输粒度"。

### 验证方式

```bash
# Linux 上查看缓存行大小
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
# 输出: 64
```

## CPU 三级缓存层次

### 延迟阶梯

```
寄存器          ~1ns     (~1 时钟周期)
L1 缓存         ~1ns     (~4 时钟周期)   32KB-64KB
L2 缓存         ~4ns     (~12 时钟周期)  256KB-512KB
L3 缓存         ~10ns    (~40 时钟周期)  8MB-32MB
主存 (DDR)      ~100ns   (~300+ 时钟周期)
```

- 缓存行是 CPU 和内存之间数据传输的最小单元
- L1/L2 为每个核心私有，L3 为多核共享
- 每次从内存加载数据，至少搬一个缓存行（64 字节）到 L1 缓存

## MESI 缓存一致性协议

### 四态转换

|状态|全称|说明|
|-|-|-|
|**M**|Modified|缓存行被修改，与主存不一致，数据仅在本核心缓存中有效|
|**E**|Exclusive|缓存行未被修改，与主存一致，且仅在本核心缓存中|
|**S**|Shared|缓存行未被修改，与主存一致，可能在多个核心缓存中同时存在|
|**I**|Invalid|缓存行已失效，不可用|

### 伪共享发生的时序

```
时间 →   CPU0                     CPU1                    缓存行状态
        ↓                         ↓
T1:     读变量 A 到缓存行                                   E (CPU0)
T2:                             读变量 B 到同一缓存行       S (CPU0+CPU1)
T3:     写变量 A（修改缓存行）                               M (CPU0), I (CPU1)
T4:                             写变量 B（触发缓存行转移）   I (CPU0), M (CPU1)
T5:     再写变量 A（再次转移）                               M (CPU0), I (CPU1)
```

CPU0 和 CPU1 在 M ↔ I 之间反复切换，每次都是几百个时钟周期的开销。**两个变量完全不相关，但因为挤在同一缓存行，硬件被迫在整个系统里弹跳整行数据。**

## Linux 内核中四类缓存行对齐方案

### 1. `____cacheline_aligned` 宏

```c
// include/linux/cache.h

/* 基础定义：GCC attribute，按 SMP_CACHE_BYTES 对齐 */
#define __cacheline_aligned                                      \
  __attribute__((__aligned__(SMP_CACHE_BYTES),                   \
                 __section__(".data..cacheline_aligned")))

/* SMP 版本：CONFIG_SMP 时生效，UP 时退化为空 */
#ifndef ____cacheline_aligned_in_smp
#ifdef CONFIG_SMP
#define ____cacheline_aligned_in_smp ____cacheline_aligned
#else
#define ____cacheline_aligned_in_smp
#endif
#endif
```

`____cacheline_aligned_in_smp` 在单核（UP）系统上零开销——不生成任何对齐指令，因为单核不存在伪共享问题。

### 2. `struct rq` 运行队列对齐

```c
// kernel/sched/sched.h
DECLARE_PER_CPU_SHARED_ALIGNED(struct rq, runqueues);
```

`DECLARE_PER_CPU_SHARED_ALIGNED` 宏展开后，每个 CPU 的 `runqueue` 结构体按 `SMP_CACHE_BYTES` 对齐，确保不同 CPU 的 rq 不会落在同一缓存行。

### 3. Per-CPU 数据

```c
// include/linux/percpu-defs.h
#define DEFINE_PER_CPU_SHARED_ALIGNED(type, name)                \
    DEFINE_PER_CPU_SECTION(type, name, PER_CPU_SHARED_ALIGNED_SECTION)

// 使用示例
static DEFINE_PER_CPU(struct irqtime, cpu_irqtime);  // kernel/sched/cputime.c
static DEFINE_PER_CPU(struct sugov_cpu, sugov_cpu);  // kernel/sched/cpufreq_schedutil.c
```

Per-CPU 数据从源头消除了共享——每个 CPU 操作自己的副本，根本不需要竞争同一缓存行。

### 4. `__read_mostly` 段

```c
// include/linux/cache.h
#ifndef __read_mostly
#define __read_mostly
#endif

// 使用示例
extern __read_mostly int scheduler_running;
extern __read_mostly unsigned int sysctl_sched_features;
```

`__read_mostly` 将只读热数据集中到独立的段中，避免它们与频繁写入的变量共享缓存行。这样读操作不会因为写操作的缓存行失效而被拖慢。

### 5. 内核中实际使用案例

|文件|结构体|使用方式|
|-|-|-|
|`include/linux/tcp.h`|tcp_sock|`__cacheline_group_begin_aligned(tcp_sock_write_tx)` 分组对齐|
|`include/linux/fs.h`|文件系统结构体|`} ____cacheline_aligned;` 结尾对齐|
|`include/linux/sbitmap.h`|sbitmap_word|`unsigned long cleared ____cacheline_aligned_in_smp;` 字段对齐|
|`include/linux/spinlock.h`|spinlock|内部使用 `__cacheline_aligned_in_smp` 确保自旋锁独占缓存行|
|`kernel/sched/clock.c`|sched_clock_data|`DEFINE_PER_CPU_SHARED_ALIGNED(struct sched_clock_data, sched_clock_data)`|

## 用户态与高级语言的对应方案

|语言/框架|方案|说明|
|-|-|-|
|Java|`@Contended` 注解|JDK 8+，在字段前后填充 128 字节（考虑硬件预取器）|
|Rust|`#[repr(align(64))]`|结构体对齐属性，确保独占缓存行|
|Go|`align64` + padding|`type T struct { _ [cacheline]byte; ... }` 手动填充|
|C/C++|`alignas(64)`|C++11 标准对齐属性，等价于 `__attribute__((aligned(64)))`|

## 线上诊断工具：perf c2c

`perf c2c`（Cache-to-Cache）是 Linux 性能工具中专门用于诊断伪共享（False Sharing）热点的工具。

```bash
# 1. 采集数据
perf c2c record -a ./your_program

# 2. 生成报告
perf c2c report

# 3. 查看热点
# 输出中会标注 HITM（Hit Modified）最高的缓存行
# 这些就是伪共享的候选
```

`perf c2c` 通过监测缓存一致性协议中 MESI 状态转换事件（尤其是 HITM——从 Modified 状态的缓存行读取数据），精确定位哪些缓存行在多核之间频繁弹跳。

## 总结

1. **64 字节不是软件选择，是硬件物理边界**：DDR burst 8 拍 × 64bit 总线宽度 = 64 字节
2. **伪共享是多核并发最隐蔽的性能杀手**：无关变量同处一缓存行，硬件被迫全局弹跳
3. **Linux 内核四类方案**：
   - `____cacheline_aligned` — 对齐至缓存行边界
   - `struct rq` 对齐 — 关键结构体独占缓存行
   - Per-CPU 数据 — 从源头消除共享
   - `__read_mostly` — 只读热数据集中隔离
4. **理解 64 字节，贯通整个并发编程体系**：Java `@Contended`、Rust `repr align`、Go padding、C++ `alignas(64)` 都是同一个物理约束的不同语言表达

> 致敬：Linus Torvalds、Paul McKenney（《Is Parallel Programming Hard》）、Peter Zijlstra、Ingo Molnar——他们把 cacheline 工程化方法论写进了 Linux 内核的每一行代码。
