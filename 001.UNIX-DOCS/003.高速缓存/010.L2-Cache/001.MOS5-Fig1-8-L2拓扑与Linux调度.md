## 问题与原句核验

### Figure 1-8 与原文语境

Figure 1-8 位于 MOS5 §1.3.2 Memory（印刷页 25，PDF 物理页 54），图题为：

> "Figure 1-8. (a) A quad-core chip with a shared L2 cache. (b) A quad-core chip with separate L2 caches."
> （图 1-8：(a) 共享 L2 缓存的四核芯片；(b) 各自独立 L2 缓存的四核芯片。）<sup>[MOS5 §1.3.2，PDF 物理页 54](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=54)</sup>

紧随其后的正文段（印刷页 27，PDF 物理页 56）给出两种放置方式的取舍：

> "On multicore chips, the designers have to decide where to place the caches. In Fig. 1-8(a), a single L2 cache is shared by all the cores. In contrast, in Fig. 1-8(b), each core has its own L2 cache. Each strategy has its pros and cons. For example, the shared L2 cache requires a more complicated cache controller but the per-core L2 caches makes keeping the caches consistent more difficult."
> （在多核芯片上，设计者必须决定把缓存放在哪里。图 1-8(a) 中所有核心共享一个 L2 缓存；相反，图 1-8(b) 中每个核心有自己的 L2 缓存。两种策略各有优劣：例如，共享 L2 需要更复杂的缓存控制器，而每核私有 L2 使保持缓存一致更加困难。）<sup>[MOS5 §1.3.2，PDF 物理页 56](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=56)</sup>

上文（印刷页 24，物理页 53）还有一句铺垫："The multicore chips of Fig. 1-8 effectively carry four minichips on them, each with its own independent CPU. (The caches will be explained later in the book.)"（图 1-8 那种多核芯片实际上等于把四个"小芯片"装在一起，每个都有独立的 CPU；缓存将在书后文解释。）——书里明确把缓存的展开推迟到了后文，所以图 1-8 只回答"谁和谁共享"，不回答"共享关系怎么被软件知道"，后者正是本文用 Linux 7.1.3 源码补齐的部分。

### 一种常见的说法，逐项核验如下

一种常见的说法是：

> 缓存一致性的维护对内核是无感的（硬件搞定），但缓存拓扑结构对内核是有感的——内核会利用这些信息优化调度策略。

把这句话拆成三个分论点，用 7.1.3 源码逐项核验：

| 分论点 | 判断 | 一句话依据（详见后文小节） |
| --- | --- | --- |
| 一致性维护对内核"无感"（硬件搞定） | **部分成立，边界要改** | 只在硬件一致性域内的普通访存成立；离开域的路径内核必须显式维护：非一致性 DMA 的 clean/invalidate（kernel/dma/direct.c:405-432 分支 + arm64 `dcache_clean_poc_nosync`）、指令/数据缓存同步（cacheflush.h:84 → cache.S:55，含 IDC/DIC 能力位裁剪） |
| 缓存拓扑对内核"有感"，内核用它优化调度 | **成立** | PPTT/DT + CLIDR_EL1 → cacheinfo → `llc_sibling` → `sched_domain`（SD_CLUSTER/SD_SHARE_LLC）→ `sd_llc_id`/`sd_share_id` 参与 ttwu、唤醒选核与负载均衡 |
| 内核处理的对象是"L2"这个层级 | **需修正** | 内核从不问"这是不是 L2"；问的是"末级缓存/cluster 的共享集合"（`fw_token`/Cache ID 相等，cacheinfo.c:41-57）。"L2"只是 CLIDR_EL1/固件表里的一个 level 数字，同一层级在不同平台共享范围不同——Figure 1-8 (a)(b) 对比的正是这件事 |

**修订表述**：在由硬件维护一致性的系统（如 arm64 上 DSU/CMN 构成的一致性域）上，内核执行的普通共享内存访问确实不需要任何缓存维护指令，用屏障保证内存顺序即可——"无感"仅在这个范围内成立。离开一致性域的路径都要内核显式补位：非一致性 DMA 的缓存清理/失效，以及指令与数据缓存之间的同步（内核文本补丁、内核写用户代码页、用户执行页 PTE 建立），维护序列还会按 CTR_EL0 的 IDC/DIC 能力位动态裁剪。缓存拓扑则相反，是内核主动消费的信息：固件（ACPI PPTT 或 Device Tree）与 CLIDR_EL1 一起建立 cacheinfo 与 CPU 拓扑，调度器据此构建 sched_domain（SD_CLUSTER/SD_SHARE_LLC 标志）并以 `sd_llc_id`/`sd_share_id` 两个 per-CPU 变量驱动唤醒选核与负载均衡。内核关心的是"哪个 CPU 与我共享末级缓存/cluster"这一**共享范围**，而不是"L2"这个层级名称。

## "内核无感"的边界：一致性之外内核还要动手的三类路径

先把三个容易混在一起的概念分开：

| 概念 | 硬件/软件分工 | 内核需要做什么 |
| --- | --- | --- |
| 缓存一致性（coherence） | 一致性域内由硬件维护（DSU/CMN 侧的监听/目录） | 域内：什么都不做；设备离开域（非一致性 DMA）：显式 clean/invalidate |
| 内存顺序（memory order） | 架构规定的弱序模型 | 用屏障指令（DMB/DSB/ISB）标注顺序要求 |
| 显式缓存维护（cache maintenance） | 全软件 | 按架构指令逐行/逐区执行（DC CVAC/CIVAC/CVAU、IC IVAU 等） |

### 场景一：一致性域内的普通共享内存（真正"无感"的部分）

内核在核间共享的一切普通数据（自旋锁、队列、页表、per-CPU 之外的共享结构）都不做任何缓存维护；核间同步只插入内存顺序屏障，arm64 的 `__smp_mb()` 就是一条 `dmb(ish)`：

```c
// arch/arm64/include/asm/barrier.h:126
#define __smp_mb()	dmb(ish)
```

也就是说：一致性的"硬件搞定"只覆盖**一致性域内的访存**；它保证的是"各核看到的值一致"，不保证"到达顺序"，后者由屏障补足。

### 场景二：非一致性 DMA——进入/离开一致性域时内核代为维护

设备是否在一致性域内由固件描述（ACPI/DT 依设备而定，`dev_is_dma_coherent()` 判定）。一致性设备直连域内，通用 DMA 层不做维护；非一致性设备则每个方向都要内核动 D-cache。7.1.3 中两条分支：

```c
// kernel/dma/direct.c:405（dma_direct_sync_sg_for_device）
		if (!dev_is_dma_coherent(dev))
			arch_sync_dma_for_device(paddr, sg->length,
					dir);
// kernel/dma/direct.c:218（dma_direct_alloc）
	if (!dev_is_dma_coherent(dev)) {
		if (IS_ENABLED(CONFIG_ARCH_HAS_DMA_ALLOC) &&
		    !is_swiotlb_for_alloc(dev))
			return arch_dma_alloc(dev, size, dma_handle, gfp,
					      attrs);
```

arm64 侧的实现就是把 D-cache 维护到一致点 PoC：

```c
// arch/arm64/mm/dma-mapping.c:15
void arch_sync_dma_for_device(phys_addr_t paddr, size_t size,
			      enum dma_data_direction dir)
{
	unsigned long start = (unsigned long)phys_to_virt(paddr);

	dcache_clean_poc_nosync(start, start + size);   // 设备读方向：clean 到 PoC
}

// arch/arm64/mm/dma-mapping.c:23
void arch_sync_dma_for_cpu(phys_addr_t paddr, size_t size,
			   enum dma_data_direction dir)
{
	unsigned long start = (unsigned long)phys_to_virt(paddr);

	if (dir == DMA_TO_DEVICE)
		return;                                  // 设备写方向无需 CPU 侧动作

	dcache_inval_poc_nosync(start, start + size);    // 设备写后 CPU 读：invalidate
}
```

对应的汇编封装在 cache.S：`dcache_clean_poc_nosync`（cache.S:210）、`dcache_inval_poc_nosync`（cache.S:180）、`dcache_clean_inval_poc`（cache.S:111，DC CIVAC）。一致性域内设备则整段跳过：设备初始化时直接记录 `dev->dma_skip_sync = dev_is_dma_coherent(dev)`（kernel/dma/mapping.c:491），后续同步调用被跳过；`dma_pgprot()` 对一致性设备也直接返回原页属性（kernel/dma/mapping.c:541-543）。另外 `arch_setup_dma_ops()` 会检查 CPU 侧缓存行大小（`cls = cache_line_size_of_cpu()`）：非一致性设备上若 `cls > ARCH_DMA_MINALIGN`（CPU 缓存行大于 `ARCH_DMA_MINALIGN`，即 CTR_EL0.CWG 更大）则 WARN_TAINT(TAINT_CPU_OUT_OF_SPEC)（dma-mapping.c:41 起）——非一致性 DMA 还共享"缓存行对齐"约束。

### 场景三：指令与数据缓存同步（自修改代码与执行页属性）

arm64 的 I-cache 不会自动跟踪 D-cache 写入，内核里所有"写了代码再执行"的路径都要显式同步，并按 CPU 能力位裁剪。能力位来自 CTR_EL0：`ARM64_HAS_CACHE_IDC`（"Data cache clean to the PoU not required for I/D coherence"，cpufeature.c:2713-2719）与 `ARM64_HAS_CACHE_DIC`（"Instruction cache invalidation not required for I/D coherence"，cpufeature.c:2720-2726）。核心维护序列：

```asm
// arch/arm64/mm/cache.S:28（caches_clean_inval_pou_macro）
alternative_if ARM64_HAS_CACHE_IDC
	dsb     ishst                     // IDC=1：I/D 硬件相干，D-cache clean 整体降为一条屏障
	b       .Ldc_skip_\@
alternative_else_nop_endif
	mov     x2, x0
	mov     x3, x1
	dcache_by_line_op cvau, ish, x2, x3, x4, x5, \fixup   // 否则逐行 DC CVAU
.Ldc_skip_\@:
alternative_if ARM64_HAS_CACHE_DIC
	isb                               // DIC=1：I-cache 无需失效，一条 ISB 即可
	b	.Lic_skip_\@
alternative_else_nop_endif
	invalidate_icache_by_line x0, x1, x2, x3, \fixup        // 否则逐行 IC IVAU
.Lic_skip_\@:
```

四条实际触发路径如下（各路径行号均为 7.1.3 实测）：

```text
内核文本补丁（jump_label/ftrace/kprobes/BPF 等）
  \-- aarch64_insn_patch_text (patching.c:225) --> __text_poke (patching.c:107)
        \-- flush_icache_range (arch/arm64/include/asm/cacheflush.h:84)
              |-- caches_clean_inval_pou (arch/arm64/mm/cache.S:55)
              |     D-cache clean to PoU（IDC 置位则只做 dsb ishst）
              |     I-cache invalidate PoU（DIC 置位则只做 isb）
              \-- kick_all_cpus_sync (kernel/smp.c:1077) IPI 全核同步取指

内核写用户代码页（ptrace / access_process_vm）
  \-- copy_to_user_page (arch/arm64/mm/flush.c:44)
        \-- flush_ptrace_access: VM_EXEC --> sync_icache_aliases (:32)

用户执行页 PTE 建立或属性变更
  \-- __set_ptes_anysz (arch/arm64/include/asm/pgtable.h:673)
        \-- __sync_cache_and_tags (:436, :697)
              pte_user_exec --> __sync_icache_dcache (flush.c:52, PG_dcache_clean)

AArch32 兼容应用显式请求（sys_cacheflush）
  \-- __do_compat_cache_op (arch/arm64/kernel/sys_compat.c:23)
        \-- caches_clean_inval_user_pou (cache.S:71，用户 VA 上维护)
```

几点补充：

- `flush_icache_range()` 在 7.1.3 的公开封装是 cacheflush.h:84 的 static inline（先 `caches_clean_inval_pou()` 再 `kick_all_cpus_sync()` 给所有在线核发 IPI 强制重取指；KGDB 场景提前返回避免死锁）。老版本内核里位于 cache.S 的 `__flush_icache_range` 符号在本树已不存在，同类能力由 `caches_clean_inval_pou` 及其 `__pi_` 别名承担。
- "页权限变更"场景的精确语义：`__ptep_set_access_flags_anysz()` 修改 access/dirty/write 权限时**不会**触发维护，因为这类变更"the PTE is never changed from no-exec to exec here"（arch/arm64/mm/fault.c:199-206）；真正需要维护的是把页**建立为可执行**（`__set_ptes_anysz` 中 `pte_user_exec()` 判定），维护结果以 `PG_dcache_clean` 位缓存，避免重复维护（flush.c:52-63）。
- 非别名 I-cache（PIPT）下 `sync_icache_aliases()` 退化为 `caches_clean_inval_pou()`；别名 I-cache 则 `dcache_clean_pou()` + 全量 I-cache 失效（flush.c:18-30）。
- AArch64 用户态自修改代码的惯用法（DC CVAU + IC IVAU + DSB + ISB）属 Arm 架构规定、由用户态自理，内核只在 AArch32 兼容层提供 sys_cacheflush 代劳——这也是"域内无感、离开域显式维护"在用户态的镜像（架构指令细节未附 Arm ARM 页码，见"证据与未确认项"）。

## L2 在内核中的处理：按层级还是按共享范围？

**结论**：内核感知缓存的对象是**共享范围与属性**，不是"L2"这个层级。层级数字（level）只是 cacheinfo 叶子的一个描述字段，供 sysfs 呈现；真正驱动内核行为的是三个固件/硬件事实：同一缓存实例的**标识**（Cache ID 或固件节点 `fw_token`）、缓存的**几何参数**（行宽/组数/路数/大小）、以及由此推出的**共享 CPU 掩码**。调度器消费的是掩码与域标志，从不读"level==2"。

### struct cacheinfo：内核缓存叶子的实际字段

```c
// include/linux/cacheinfo.h:50
struct cacheinfo {
	unsigned int id;                 // Cache ID（CACHE_ID 属性位置位时有效）
	enum cache_type type;            // DATA / INST / UNIFIED
	unsigned int level;              // 层级数字（L1=1, L2=2, ...）
	unsigned int coherency_line_size;
	unsigned int number_of_sets;
	unsigned int ways_of_associativity;
	unsigned int physical_line_partition;
	unsigned int size;
	cpumask_t shared_cpu_map;        // 共享该缓存实例的 CPU 集合
	unsigned int attributes;         // 写策略/分配策略/CACHE_ID 等位
	…                                // 此处省略 9 行：CACHE_WRITE_THROUGH 至 CACHE_ID 的 #define（cacheinfo.h:61-69）
	void *fw_token;                  // 指向固件描述节点（DT cache 节点或 PPTT 处理器节点）
	bool disable_sysfs;
	void *priv;
};
```

注意字段名是 `shared_cpu_map` 与 `id`/`fw_token`——cacheinfo 里没有名为 "shareability" 的字段，"共享性"以掩码加标识两个东西表达。

### 共享判定：三种模式，一条规则

两片 cacheinfo 叶子是否属于同一物理缓存，由 `cache_leaves_are_shared()` 判定（drivers/base/cacheinfo.c:41-57）：

```c
// drivers/base/cacheinfo.c:41
static inline bool cache_leaves_are_shared(struct cacheinfo *this_leaf,
					   struct cacheinfo *sib_leaf)
{
	/*
	 * For non DT/ACPI systems, assume unique level 1 caches,
	 * system-wide shared caches for all other levels.
	 */
	if (!(IS_ENABLED(CONFIG_OF) || IS_ENABLED(CONFIG_ACPI)) ||
	    use_arch_info)
		return (this_leaf->level != 1) && (sib_leaf->level != 1);

	if ((sib_leaf->attributes & CACHE_ID) &&
	    (this_leaf->attributes & CACHE_ID))
		return sib_leaf->id == this_leaf->id;

	return sib_leaf->fw_token == this_leaf->fw_token;
}
```

三个模式依优先级排列：无固件可用的兜底（除 L1 外假设全系统共享）、有 Cache ID 时比 ID、否则比对固件节点指针 `fw_token`。"同一物理缓存"的定义就是**同 ID / 同固件节点**，与 level 数字无关——两个 level=2 的叶子 ID 不同就不共享，反之共享关系的载体可以是任何层级。

`cache_shared_cpu_map_setup()`（cacheinfo.c:392-447）随后把判定结果写进掩码：对每片叶子，先置上自己，再对每个在线 CPU 的同 level 同 type 叶子做上述判定，命中则互写 `shared_cpu_map`；末尾还统计全局最大缓存行 `coherency_max_size`（cacheinfo.c:442-443）——arm64 的 `cache_line_size()` 优先返回它（arch/arm64/kernel/cacheinfo.c:15-20），保证跨核取同一口径。整个流程由 CPU 上线时的 `detect_cache_attributes()`（cacheinfo.c:597-635）串起：先 `populate_cache_leaves()` 填几何参数，再 `cache_shared_cpu_map_setup()` 建共享掩码。结果经 sysfs 暴露为 `/sys/devices/system/cpu/cpuN/cache/index*/{level,type,size,shared_cpu_map,shared_cpu_list,...}`（cacheinfo.c:745-756 的 DEVICE_ATTR_RO 组）——lscpu 等工具读到的"缓存共享"即来源于此。

### arm64 叶子从哪来：CLIDR_EL1 与固件合并

arm64 没有自己的大段缓存探测代码，`populate_cache_leaves()` 直接读 CLIDR_EL1 逐层展开（`get_cache_type()` 读 `clidr_el1`，arch/arm64/kernel/cacheinfo.c:24-31；`detect_cache_level()` 最多扫 MAX_CACHE_LEVEL=7 层，:41-56；`populate_cache_leaves()` 为分离 I/D 的层级生成两片叶子，:99-118）。固件的职责是补充 CLIDR 之外的**外部缓存**——内核注释只说 "some external caches not specified in CLIDR_EL1"（arm64 cacheinfo.c:86）、未点名缓存种类；可确定归入此类的例是互连侧 SLC，DSU 簇内 L3 是否在 CLIDR 之外本文未核【未】：`init_cache_level()` 把 CLIDR 数出的层级与固件层级（DT `of_find_last_cache_level` 或 ACPI `acpi_get_cache_info`）取大（cacheinfo.c:68-97），几何属性则由 DT/PPTT 路径回填（见下一节）。

### x86 一句话对照

x86 不走 PPTT/DT，LLC 标识直接来自 CPUID：AMD/Hygon 的 `llc_id` 由 `cacheinfo_amd_init_llc_id()`/`cacheinfo_hygon_init_llc_id()` 得出，路径依家族而定（arch/x86/kernel/cpu/cacheinfo.c:312-348）——Pre-Zen（x86<0x17）LLC 在节点级、取 die_id；Family 17h model≤0x1F 与 Hygon 走专用路径 `llc_id = apicid>>3`（core complex ID＝ApicId[3]，非"兜底"而是该家族段的固定算法）；更新的家族才用 CPUID leaf 4 的 `get_cache_id()`。smpboot 以 `per_cpu_llc_id()` 相等判定同 LLC（arch/x86/kernel/smpboot.c:349/438）。进入调度器之后消费的仍是同一套域标志/掩码机制——差别在拓扑信息来源，不在调度侧。

## 调度器如何使用：域构建、唤醒选核与负载均衡

### 标志与域层级

调度域标志定义在 include/linux/sched/sd_flags.h：`SD_CLUSTER`（"Domain members share CPU cluster (LLC tags or L2 cache)"，sd_flags.h:110-117）与 `SD_SHARE_LLC`（"Domain members share CPU Last Level Caches"，sd_flags.h:119-126，带 SDF_SHARED_CHILD）。**7.1.3 树中已无 `SD_SHARE_PKG_RESOURCES`**：老内核里表达"共享缓存资源"的语义在这棵树上由 `SD_SHARE_LLC`（与 cluster 机器的 `SD_CLUSTER`）承担，查旧资料时需注意换名。

通用域层级自底向上（kernel/sched/topology.c:1807-1821）：

```c
// kernel/sched/topology.c:1807

#ifdef CONFIG_SCHED_SMT

#endif

#ifdef CONFIG_SCHED_CLUSTER
	SDTL_INIT(tl_cls_mask, cpu_cluster_flags, CLS),   // :1776 返回 SD_CLUSTER|SD_SHARE_LLC
#endif

#ifdef CONFIG_SCHED_MC
	SDTL_INIT(tl_mc_mask, cpu_core_flags, MC),        // :1788 返回 SD_SHARE_LLC
#endif
	SDTL_INIT(tl_pkg_mask, NULL, PKG),
	{ NULL, },
```

掩码来自 arch 层：MC 域掩码 `cpu_coregroup_mask()`（arch_topology.c:705-727）取 **NUMA、core_sibling、llc_sibling 三者最小的子集**，并在 CONFIG_SCHED_CLUSTER 下向 cluster_sibling 扩展——"同末级缓存"直接决定 MC 域形状；CLS 域（CLS＝topology.c 对 cluster 层级调度域的命名，即带 SD_CLUSTER 标志的域）掩码 `cpu_clustergroup_mask()`（:732-741）用 cluster_sibling。域构建收尾时 `update_top_cache_domain()`（topology.c:680-712，由 `cpu_attach_domain()` :728 在 :794 调用）挑出**带 SD_SHARE_LLC 的最高域**记为该 CPU 的 LLC 域：

```c

	if (sd) {
		id = cpumask_first(sched_domain_span(sd));   // sd_llc_id = LLC 域首 CPU 号
```

得到两个 per-CPU 快查变量（topology.c:664-671 定义）：`sd_llc_id`（同值 ⇔ 同 LLC 域）与 `sd_share_id`（同值 ⇔ 同 cluster/LLC）。对应的两个谓词在 core.c:

```c
// kernel/sched/core.c:3889
bool cpus_share_cache(int this_cpu, int that_cpu)        // 同 LLC？
{
	if (this_cpu == that_cpu)
		return true;

	return per_cpu(sd_llc_id, this_cpu) == per_cpu(sd_llc_id, that_cpu);
}

/*
 * Whether CPUs are share cache resources, which means LLC on non-cluster
 * machines and LLC tag or L2 on machines with clusters.
 */
bool cpus_share_resources(int this_cpu, int that_cpu)    // core.c:3901：cluster 机器上即"同 L2/LLC tag"
{
	if (this_cpu == that_cpu)
		return true;

	return per_cpu(sd_share_id, this_cpu) == per_cpu(sd_share_id, that_cpu);
}
```

内核自己的注释就是"层级不重要、范围才重要"的直接证据：cluster 机器上"share cache resources"指的是 **LLC tag 或 L2**，非 cluster 机器上才是 LLC 本体。带 SD_SHARE_LLC 的域在构建期还有三处定制：`sd_init` 给这类域设 `imbalance_pct=117`、`cache_nice_tries=1`（topology.c:1737-1739）；同 LLC 域共享一份 `sched_domain_shared`（含 `nr_busy_cpus`/`nr_idle_scan`，构建去重见 :2719-2728）；存在 CLS 域时拉起 `sched_cluster_active` 静态键（:2756-2767）。

### sched_group 与 sched_group_capacity：域内分组与共享统计

调度域之下的负载/统计单位是 sched_group。每个 sched_domain 持有一条 `groups` 环形链表，链上每个 group 覆盖域 span 的一部分：

```c

	/* These fields must be setup */
	struct sched_domain __rcu *parent;	/* top domain must be null terminated */
	struct sched_domain __rcu *child;	/* bottom domain must be null terminated */
	struct sched_group *groups;	/* the balancing groups of the domain */
	unsigned long min_interval;	/* Minimum balance interval ms */
	…
```

```c
// kernel/sched/sched.h:2203
struct sched_group {
	struct sched_group	*next;			/* Must be a circular list */
	atomic_t		ref;

	unsigned int		group_weight;
	unsigned int		cores;
	struct sched_group_capacity *sgc;
	int			asym_prefer_cpu;	/* CPU of highest priority in group */
	int			flags;

	/*
	 * The CPUs this group covers.
	 *
	 * NOTE: this field is variable length. …
	 */
	unsigned long		cpumask[];
};
```

`cpumask[]` 是变长尾数组（`sched_group_span(sg)` 即 `to_cpumask(sg->cpumask)`，sched.h:2223-2226），`sgc` 指向 `struct sched_group_capacity`（sched.h:2186-2201：ref 计数、组容量 capacity/min/max、均衡掩码 `cpumask[]`）——**组掩码描述"这组 CPU 共享什么"，sgc 描述"这组 CPU 合起来有多少算力"**。组与域的关联和构建全在 topology.c：

```c
// kernel/sched/topology.c:1233（get_group 内：组掩码直接取自子域 span）
	if (child) {
		cpumask_copy(sched_group_span(sg), sched_domain_span(child));
		cpumask_copy(group_balance_mask(sg), sched_group_span(sg));
		sg->flags = child->flags;
	} else {
		cpumask_set_cpu(cpu, sched_group_span(sg));
		cpumask_set_cpu(cpu, group_balance_mask(sg));
	}
```

- **组织方式**：`build_sched_groups()`（topology.c:1256-1290，由 `build_sched_domains` 在 :2708 调用）沿域 span `for_each_cpu_wrap` 扫描，每组经 `get_group()`（:1211-1247）取/初始化，最后 `last->next = first; sd->groups = first;`（:1286-1287）闭合成环形链表——函数头注释即自述 "build a circular linked list of the groups … will set each group's ->cpumask correctly, and will initialize their ->sgc"（:1250-1252）。
- **缓存共享关系在其中的角色**：组的 span 是子域 span 的拷贝（topology.c:1234；get_group 上方注释 "the first group of each domain is its child domain"，:1208），而域 span 自底向上正是 `cpu_clustergroup_mask()`/`cpu_coregroup_mask()` 用 `cluster_sibling`/`llc_sibling` 拼出来的（arch_topology.c:705-727/:732-741）。由此，组与缓存共享集合的正确层级归属是：**CLS 域自身的 span ≈ 一个 cluster/L2（或 LLC-tag）共享集合（A520 教学示例中即一个 complex），它的 group 是 SMT span、无 SMT 时为单核；MC 域自身的 span ≈ 一个末级缓存共享集合，它的每个 group ＝ 一个 CLS span，即一个 cluster/L2 共享集合；PKG 域的每个 group ＝ 一个 MC span，即一个末级缓存共享集合**。cluster 机器上的代码级旁证：`select_idle_cpu()` 在 sd_llc 域内优先扫第一个 group 并检查 `sg->flags & SD_CLUSTER`（fair.c:7976-7979）——LLC 域（cluster 机器上即 MC 域）内部的 group 正是 cluster 尺寸。固件描述的缓存共享范围经"掩码 → 域 span → 父域 group"搬运：一个共享集合先撑起一个域自身的 span，该 span 再整体成为父域的一个 group；共享范围决定的是域的形状，组只是它向父域搬运时的切分单位。
- **组内共享统计**：`sg->sgc` 在 `get_group()` 中取自 per-CPU 预分配并 ref 计数（topology.c:1222、:1226-1227），同组 CPU 跨层级复用同一份 sgc；容量初始化为 `SCHED_CAPACITY_SCALE × 组权重`（:1242-1244），`group_weight` 为组 span 的 CPU 数（`init_sched_groups_capacity()`，topology.c:1302-1312）。
- **与 sched_domain_shared 的分工**：域级共享统计是另一个结构 `struct sched_domain_shared`（include/linux/sched/topology.h:66-71：`ref`/`nr_busy_cpus`/`has_idle_cores`/`nr_idle_scan`），只挂到**最高带 SD_SHARE_LLC 的域**上、同 LLC 域的 CPU 共享一份（topology.c:2719-2728 的去重挂接），消费点是 SIS_UTIL 扫描预算（fair.c:7967）与 nohz 唤醒决策（fair.c:12852）；sgc 是每组一份的容量统计。两者都是"共享缓存范围的 CPU 共享一份运行时状态"的体现，粒度分别为组与 LLC 域。

### 路径二：负载均衡

周期/空闲均衡入口：`sched_balance_domains()`（fair.c:12590，tick 触发）与 `sched_balance_newidle()`（fair.c:13181）都调 `sched_balance_rq()`（fair.c:12101）；均衡在域的 groups 环形链表上逐组统计比较，负责挑最忙组的是 `sched_balance_find_src_group()`（fair.c:11645，内部经 `update_sd_lb_stats()` :11373 逐组统计、`calculate_imbalance()` :11443 定量），组即上一小节 `build_sched_groups()` 的产物。名字与之相近的 `sched_balance_find_dst_group()`（fair.c:11134，挑最闲组）是**唤醒慢路径**的选组函数：由 `sched_balance_find_dst_cpu()`（:7753，`select_task_rq_fair()` 在 :8887 调用）的域循环在 :7778 使用，不参与周期/新闲均衡。缓存共享关系在三处参与：

1. **域参数**：SD_SHARE_LLC 域 `imbalance_pct=117`、`cache_nice_tries=1`（topology.c:1737-1739）——同 LLC 域内迁移的"不均衡容忍度"放宽，变相抑制缓存热数据跨 LLC 搬迁。
2. **不均衡计算**：`calculate_imbalance()` 的 group_has_spare 分支，只有**非** SD_SHARE_LLC 域才允许 `migrate_util` 式的"以利用率倒腾空闲容量"（fair.c:11499-11504）；同 LLC 域内宁可少搬，避免把缓存温度当负载挪来挪去。
3. **nohz 唤醒决策**：`nohz_balancer_kick()` 读 LLC 域共享统计 `sds->nr_busy_cpus`（fair.c:12852，由均衡过程在 :12879/:12908 增减）决定要不要唤醒 idle balancer。

### 通用行为 vs 平台相关策略

域层级、SD_CLUSTER/SD_SHARE_LLC 语义、`sd_llc_id`/`sd_share_id` 谓词与上述选核/均衡路径都是**通用行为**；平台相关的是三样：掩码形状（固件表决定）、是否启用 CLS/EAS（CONFIG_SCHED_CLUSTER / 能耗模型与 overutilized 状态）、以及异构容量策略（EAS 找 `find_energy_efficient_cpu()`，fair.c:8640；Arm AGI 同构单线程平台该路径不生效）。本文的异构对照聚焦 L2 共享范围与 CLS 域，见下文"异构对照：Cortex-A725 / A520（教学示例）"小节；AGI 硬件拓扑的证据口径见 [005 文档](../../000.OS学习基座-ARM/005.Arm-AGI-CPU架构核验.md) 的"硬件拓扑小结（含证据级别）"。EAS 的容量/能耗模型细节不在本文与 005 文档的范围内。

### 异构对照：Cortex-A725 / A520（教学示例）

### L2 / cluster / LLC / SLC 概念关系小结

| 概念 | 是什么 | 内核里对应什么 | 适用前提 |
| --- | --- | --- | --- |
| L2 | 层级序号（CLIDR_EL1/固件表中的 level=2），**不含共享范围信息** | cacheinfo 的一个 level 字段值；本身不参与调度决策 | 协议规定（架构层面层级可枚举） |
| cluster（DSU 簇） | 若干核 + 共享 SCU/L2/L3 的硬件容器 | PPTT cluster 容器/DT cpu-map cluster → `cluster_id` → CLS 域 → `sd_share_id` | 平台以 cluster 组织时【IP】 |
| LLC | 该 CPU 视角的末级缓存（层级因平台而异） | 带 SD_SHARE_LLC 的最高域 → `sd_llc_id`/`llc_sibling` | 由固件描述的层级序推出 |
| SLC（系统级缓存） | 位于互连侧、常为厂商命名的一级系统缓存（如 CMN 的 HN-F 内 SLC） | 若固件声明为末级，即 LLC；AGI 上 SLC=LLC【官+IP 合成】 | 具体芯片实现规格 |

Figure 1-8 的 (a) 共享 L2 与 (b) 私有 L2，在内核里分别表现为"L2 叶子的 shared_cpu_map 是一组 CPU"与"单 CPU"，而 LLC 判定只看固件声明的**末级**——图 1-8(b) 那种每核私有 L2 的四核，若还有共享 L3，则其 LLC 是 L3 而非 L2；这正是"内核不认层级名称、只认共享范围"的具体体现。
