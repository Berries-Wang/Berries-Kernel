## 事件
整个文档只围绕这一个事件：

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
connect(fd, ...);
char buf[4096];              /* 用户空间：进程栈上 */
recv(fd, buf, 4096, 0);      /* 没有数据时进程睡在套接字上 —— 事件开始 */
```

## 逐步解读：①~⑪ 到底在干什么
每一步都给出内核源码／官方文档出处（Elixir 是 Linux 内核源码交叉引用站，点击直达函数定义）：

|#|这一步在干什么（人话）|内核依据（源码 / 文档）|课件 P27|
|-|-|-|-|
|①|内核在**内核内存**（不是进程用户空间）申请一块空缓冲（skb），将来网卡收到的包就放这里。首次挂在 [`e1000_open()`](https://elixir.bootlin.com/linux/latest/A/ident/e1000_open)（接口 up 时，**进程上下文**），此后每轮由 ⑩ 在软中断里循环补挂|[`netdev_alloc_skb_ip_align()`](https://elixir.bootlin.com/linux/latest/A/ident/netdev_alloc_skb_ip_align)，由 [`e1000_alloc_rx_buffers()`](https://elixir.bootlin.com/linux/latest/A/ident/e1000_alloc_rx_buffers) 调用|第 1 步|
|②|把这块缓冲的总线地址登记到 RX 描述符（内存里的一张「登记表」），DMA 只认这张表；这个地址就是课件里的「内存地址 X」。`DMA_FROM_DEVICE` 声明「设备将写入」|[`dma_map_single()`](https://elixir.bootlin.com/linux/latest/A/ident/dma_map_single)；方向声明见 [内核 DMA API 文档](https://docs.kernel.org/core-api/dma-api.html)|第 1 步|
|③|CPU 写一下网卡的 RDT（RX Descriptor Tail）寄存器，等于按门铃：不写这一下，网卡永远不知道有新缓冲。这条 store 指令落在网卡 BAR 空间上，就是一次 MMIO 写|[`writel()`](https://elixir.bootlin.com/linux/latest/A/ident/writel)（e1000_main.c 内 `writel(i, hw->hw_addr + rx_ring->rdt)`）|第 1~2 步|
|④|包真的到了：DMA 自己把数据写进 ① 准备好的缓冲，CPU 全程不在场、不知情——这正是用 DMA 的意义。现代 e1000 网卡是总线主控（bus master），自己经总线（PCI／PCI-X／PCIe，视具体型号）直接读写内存，**没有课件里画的「独立 DMA 控制器」**|[e1000 driver](https://elixir.bootlin.com/linux/latest/source/drivers/net/ethernet/intel/e1000/e1000_main.c)|第 3~4 步|
|⑤|DMA 在描述符上留个回执：把 DD 位（Descriptor Done，描述符完成位——每个 RX 描述符 status 字段的第 0 位，DMA 写完该缓冲后**硬件自动置 1**，驱动看到 1 才认账；驱动重挂缓冲时清 0）置 1，意思是「这块缓冲我写完了」|DD 位定义 [`E1000_RXD_STAT_DD`](https://elixir.bootlin.com/linux/latest/source/drivers/net/ethernet/intel/e1000/e1000_hw.h)（值 `0x01`）|第 5 步前奏|
|⑥|网卡发 MSI-X 中断把 CPU 拽回来（落在哪个核由中断亲和性决定，未必是 recv 睡觉的那颗）。MSI 的物理实现就是**一次设备内存写**（往约定地址写 32 位数据），所以「DMA 向 CPU 发起交互」字面成立|[内核 MSI Driver Guide](https://docs.kernel.org/PCI/msi-howto.html)|第 5 步|
|⑦|硬中断 [`e1000_intr()`](https://elixir.bootlin.com/linux/latest/A/ident/e1000_intr) 刻意少干活：读 ICR（中断原因寄存器）确认原因 → 屏蔽本队列中断（`e1000_irq_disable`）→ 调度 NAPI（`__napi_schedule`）——包来得太快时每个包都中断会把 CPU 打爆，所以改成「中断一次、轮询一批」|[内核 NAPI 文档](https://docs.kernel.org/networking/napi.html)|第 6 步|
|⑧|软中断 [`e1000_clean_rx_irq()`](https://elixir.bootlin.com/linux/latest/A/ident/e1000_clean_rx_irq) 轮询收割：看到 DD 位为 1 就收走那个 skb——`dma_unmap_single()` 解除映射，`skb_put(skb, length)` 按收到的帧长框定数据范围。此刻数据早已在内存里，CPU 一个字节都没搬|同上（e1000_main.c）|第 6 步|
|⑨|协议栈接力：`ip_rcv()` → `tcp_v4_rcv()` 把数据挂进套接字接收队列（`tcp_data_queue()`）。**注意：跑这段代码的是软中断上下文，不是 recv 进程**；它最后调 `sk_data_ready()`（→[`sock_def_readable()`](https://elixir.bootlin.com/linux/latest/A/ident/sock_def_readable)）唤醒 recv——但唤醒只是把进程放回运行队列，并不立刻跑|[`tcp_v4_rcv()`](https://elixir.bootlin.com/linux/latest/A/ident/tcp_v4_rcv)、[内核 NAPI 文档](https://docs.kernel.org/networking/napi.html)|第 6 步|
|⑩|驱动补挂一批新缓冲，把环上被消费掉的空位填回来——就发生在 ⑧ 同一个软中断里（攒够 16 个 `E1000_RX_BUFFER_WRITE` 再补）|[`e1000_alloc_rx_buffers()`](https://elixir.bootlin.com/linux/latest/A/ident/e1000_alloc_rx_buffers)|第 1 步（下一轮）|
|⑪|再写一次 RDT 通知网卡——尾声恰好是下一个事件的序章，收包环因此转起来|同 ③|第 1~2 步（下一轮）|

**唤醒之后还有半步**：recv 进程被调度回来，[`tcp_recvmsg()`](https://elixir.bootlin.com/linux/latest/A/ident/tcp_recvmsg) 在**它自己的进程上下文**里执行 `copy_to_user()` 把数据拷进用户 buf——执行 ⑨ 的软中断和最终拷贝数据的 recv 进程，是两段互不相识的执行流，甚至可能在两颗核上。

## 内存归属：① 的缓冲到底在哪？是进程内存吗？
**不是进程内存。** skb 缓冲自始至终活在**内核地址空间**，和 recv 进程的用户地址空间是两个世界：

- **分配者与位置**：[`__netdev_alloc_skb()`](https://elixir.bootlin.com/linux/latest/A/ident/__netdev_alloc_skb) 优先从 per-CPU **页片段缓存**（page_frag，避免每个小包都整页申请）切一块，尺寸不符则退回普通 skb 分配器（slab／伙伴系统）。拿到的页位于内核**直接映射区（线性映射区）**——把全部物理内存线性映射进内核虚拟地址空间的那段（x86_64 从 `PAGE_OFFSET` 开始），不属于任何进程；
- **「登记表」本身也是内核内存**：RX 描述符环不是凭空存在的，`e1000_setup_rx_resources()` 用 [`dma_alloc_coherent()`](https://elixir.bootlin.com/linux/latest/A/ident/dma_alloc_coherent) 分配它——**相干映射**（coherent），CPU 和设备读写都无需显式同步缓存；而 skb 数据缓冲走 `dma_map_single()` 的**流式映射**（streaming），用完要 `dma_unmap_single()` 解除。一环两映射，正是 DMA API 的两种基本类型（见 [内核 DMA API](https://docs.kernel.org/core-api/dma-api.html)）；
- **用户空间什么时候出现**：整个事件只有一次——`tcp_recvmsg()` 里 `skb_copy_datagram_msg()` → `copy_to_user()`，把数据拷进 recv 传进来的 `buf`（它在进程栈上、用户空间）；
- **描述符里写的地址是什么**：`dma_map_single()` 返回**总线地址**（DMA address）——不开 IOMMU 时就是那段内核内存的物理地址；开 IOMMU 时是 IOMMU 重映射出的 IOVA，设备只能访问被显式映射过的地址（这正是 DMA API 的核心职责，见 [内核 DMA API](https://docs.kernel.org/core-api/dma-api.html)）；
- **所以收包至少两次拷贝**：DMA 写内核 skb ＋ skb→用户 buf。想省掉第二次，就是零拷贝技术的战场：`splice()`、packet ring（`mmap`）、`MSG_ZEROCOPY`（主要发包侧）、AF_XDP 等。

## 要点
- **同台演出的是三种上下文**：进程上下文（①②③的**初始**挂缓冲——跑的是触发接口 up 的那个进程，如 systemd／ifconfig，**不是 recv 进程**；recv 进程自己的上下文里只发生最后的 copy_to_user）、硬中断上下文（⑦）、软中断上下文（⑧⑨⑩⑪）——图里用两条 CPU 生命线区分；被唤醒的进程和执行协议栈的软中断不是一回事，甚至可能不在同一个核上。
- **两种内存两个世界**：经典路径下网卡 DMA 只写内核缓冲，用户 buf 只在最后 `copy_to_user()` 时被碰——这条「内核缓冲→用户缓冲」的鸿沟正是零拷贝技术要填的（AF_XDP 是例外：它专门把用户内存映射给网卡 DMA）。
- **两个方向的「对话」本质**：CPU 不能「调用」DMA——没有函数调用这回事，只能**留信息**：往共享内存的描述符里写地址、往网卡的 RDT 寄存器写序号（描述符环本身就是 CPU 与设备共享的内存，这正是两者的通信机制），两次访存就是全部对话；DMA 主动方向就是一次中断（MSI 本身是一次 DMA 写）。
- **CPU 与 DMA 之间的核心同步原语**：描述符 DD 位（Descriptor Done，DMA 说「写完了」）＋ RDT 寄存器（CPU 说「有新缓冲」），一进一出刚好凑成对话。
- **发送路径是镜像**：`send()` → [`e1000_xmit_frame()`](https://elixir.bootlin.com/linux/latest/A/ident/e1000_xmit_frame) 填 TX 描述符＋`writel(TDT)`＝方向一；DMA 发完写回描述符＋中断 → `e1000_clean_tx_irq()`＝方向二。同一个骨架换个方向而已。
