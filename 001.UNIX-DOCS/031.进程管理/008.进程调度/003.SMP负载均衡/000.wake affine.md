## 1. 问题背景: 唤醒时为什么要"选 CPU"

### 1.1 缓存热度与负载均衡的矛盾

进程被唤醒时, 调度器要立刻回答一个问题: **让它在哪个 CPU 上运行?** 两个天然候选是:

- **prev_cpu**: 该进程上次运行的 CPU, 它的 L1/L2(私有)乃至 L3(LLC 共享)里可能还留着这个进程的工作集;
- **wakeup_cpu (this_cpu)**: 正在执行 wake_up_process() 的 waker 所在 CPU, waker 刚刚操作过的数据(锁、管道缓冲、共享队列)在该 CPU 的缓存里是热的。

如果 waker 与 wakee 正在密集交换数据(典型的 producer/consumer、pipeline、RPC 请求-应答), 让两者共享 LLC, 每次唤醒后 warm-up 的成本大幅降低; 反之, "哪里空闲去哪里"的纯负载均衡视角则会把它们拆散到不同缓存域。

**wake affine 就是唤醒路径上偏向缓存亲和的快速决策器**: 只看 this_cpu 与 prev_cpu 两个候选, 快速决定把 wakee 往哪边放。它与周期性负载均衡(见 [017.SMP负载均衡_KERNEL_5.9.md](./017.SMP负载均衡_KERNEL_5.9.md))是分工而非对立关系(见 Q1)。

### 1.2 sync 唤醒: mutex unlock / futex wake

唤醒路径有一类特殊的 `WF_SYNC` 唤醒(kernel/sched/sched.h:2427, "Waker goes to sleep after wakeup"):

- mutex unlock 后唤醒等待者、futex wake、sema up 等: waker 唤醒别人之后自己**马上要睡眠**;
- 此时把 wakee 放到 waker 的 CPU 上不会造成两者争抢同一个 runqueue —— waker 让出的位置恰好由 wakee 接手;
- WF_SYNC 由 [try_to_wake_up()](../../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/sched/core.c) 的调用方传入(core.c:4290 处把 wake_flags 传入 select_task_rq()), 在 select_task_rq_fair() 一进来就被解析(fair.c:8831), 并带 PF_EXITING 抑制条件。

wake_affine_idle() 的 sync 分支、wake_affine_weight() 的 current_load 扣减, 都是为这一场景定制(见第 3、4 节)。

### 1.3 在 Venice 上看: 同一 CCX vs 跨 CCX

AMD 第 6 代 EPYC 9006 "Venice"(Zen 6c): 8 CCD + 2 IOD; 每 CCD 内含 2 个 CCX, 每个 CCX 16 核共享 64MB L3(每路 16 CCX / 1GB L3); SMT2; 支持 NPS1/2/4。**关键差异: Zen 2~5 的 LLC 边界是 CCD, 而 Venice 的 LLC 边界收窄到 CCX**, 因此 Linux 的 MC(LLC)调度域 = CCX。

|核/线程|256 核 / 512 线程(Zen 6c, SMT2)|
|频率|基频 2.55GHz, 加速至 4.1GHz|

wake affine 的收益/代价在这样的拓扑上非常直观:

```
 情形 A: waker 与 wakee 的 prev_cpu 同属一个 CCX (同一 sd_llc, L3 全热)
+---------------------------------------------------+
| CCX3                                              |
|   [CPU9  waker A]        [CPU44 wakee B prev]     |
|    <--------- 共享的 64MB L3, B 的工作集还热 -----|
+---------------------------------------------------+
   affine 到 CPU9 或留在 CPU44: L1/L2 私有换掉, L3 命中, 净收益为正

 情形 B: waker 与 wakee 的 prev_cpu 跨 CCX
+-----------------+                         +-----------------+
| CCX3            |                         | CCX4            |
| [CPU9 waker A]  |   若强行 affine 过来 => | [CPU77 B prev]  |
| L3: 只有 A 数据 |                         | L3: B的数据(热) |
+-----------------+                         +-----------------+
   B 被 affine 到 CPU9 后, L1/L2/L3 全部 miss, 只能从远端/DDR 取数,
   这正是 wake_affine_idle() 要求 cpus_share_cache(this_cpu, prev_cpu)、
   select_idle_sibling() 刻意不跨 sd_llc 扫描的原因
```

三个要点:

1. **wake affine 是"快中选快"**: 候选只有 this_cpu / prev_cpu 两个, 不做全域扫描; 慢速路径 sched_balance_find_dst_cpu()(5.9 时代叫 find_idlest_cpu, 见第 7 节)才会自上而下找"最闲"的 CPU。
2. **"Prefer wake_affine over balance flags"**(fair.c:8870): 一旦某层域的 SD_WAKE_AFFINE 生效并做出决策, 就 `sd = NULL` 直接 break, 不再看更低概率的 balance 标志 —— 唤醒路径上 affine 优先于唤醒均衡。
3. EAS 分支在最前面"截胡": root domain 未 overutilized 时先走 find_energy_efficient_cpu()(fair.c:8640), 找不到(返回 -1)才继续 affine 逻辑; arm64 大小核详见第 6 节。

### 2.2 select_task_rq_fair() 走读

```c
// kernel/sched/fair.c:8829
static int
select_task_rq_fair(struct task_struct *p, int prev_cpu, int wake_flags)
{
	int sync = (wake_flags & WF_SYNC) && !(current->flags & PF_EXITING);
	struct sched_domain *tmp, *sd = NULL;
	int cpu = smp_processor_id();          // cpu = wakeup_cpu (this_cpu)
	int new_cpu = prev_cpu;
	int want_affine = 0;
	/* SD_flags and WF_flags share the first nibble */
	int sd_flag = wake_flags & 0xF;

	if (wake_flags & WF_TTWU) {            // 普通唤醒(而非 exec/fork)
		record_wakee(p);               // 维护 waker/wakee 翻转统计

		if ((wake_flags & WF_CURRENT_CPU) &&
		    cpumask_test_cpu(cpu, p->cpus_ptr))
			return cpu;               // 调用方点名要放本 CPU (如 complete())

		if (!is_rd_overutilized(this_rq()->rd)) {
			new_cpu = find_energy_efficient_cpu(p, prev_cpu);  // EAS
			if (new_cpu >= 0)
				return new_cpu;
			new_cpu = prev_cpu;    // EAS 失败, 回到常规路径
		}

		want_affine = !wake_wide(p) && cpumask_test_cpu(cpu, p->cpus_ptr);
	}

	for_each_domain(cpu, tmp) {            // 从 SMT/MC 自底向上
		if (want_affine && (tmp->flags & SD_WAKE_AFFINE) &&
		    cpumask_test_cpu(prev_cpu, sched_domain_span(tmp))) {
			if (cpu != prev_cpu)
				new_cpu = wake_affine(tmp, p, cpu, prev_cpu, sync);
			sd = NULL; /* Prefer wake_affine over balance flags */
			break;
		}

		if (tmp->flags & sd_flag)
			sd = tmp;
		else if (!want_affine)
			break;
	}

	/* Slow path */
	if (unlikely(sd))
		return sched_balance_find_dst_cpu(sd, p, cpu, prev_cpu, sd_flag);

	/* Fast path */
	if (wake_flags & WF_TTWU)
		return select_idle_sibling(p, prev_cpu, new_cpu);

	return new_cpu;
}
```

逐条说明:

- **8831 行 `sync`**: 仅当带 WF_SYNC 且 waker 不在退出中;
- **8843~8857 行**: 只有 WF_TTWU 类唤醒才统计 wakee、才考虑 EAS 与 affine;
- **8857 行 `want_affine`**: 两个必要条件 —— `!wake_wide(p)`(不是 1:N 唤醒者, 见 2.3)与 waker CPU 在进程亲和掩码内;
- **8860~8872 行**: `for_each_domain()` 从 this_cpu 出发自底向上找**同时覆盖 this_cpu 与 prev_cpu** 且带 SD_WAKE_AFFINE 的最低域; 找到后 cpu == prev_cpu 时无需 affine(本就同 CPU), 否则进入 wake_affine() 裁决;
- **8887 行慢速路径**: 5.9 的 find_idlest_cpu() 在 7.1.3 已更名为 sched_balance_find_dst_cpu(), 内部逐层 sched_balance_find_dst_group()(fair.c:11134) → sched_balance_find_dst_group_cpu()(fair.c:7697)找最闲组最闲 CPU;
- **8891 行快速路径**: wake_affine() 给出的 new_cpu 只是"倾向", 最终落在哪个具体空闲 CPU 由 select_idle_sibling() 决定(第 5 节)。

### 2.3 want_affine 的来源: record_wakee() 与 wake_wide()

wake affine 的经典副作用是"1:N 拥挤": 一个 server 进程(如 Binder、音频服务)反复唤醒大量 client, 若每次都把 client 拉到自己 CPU 上, server 反而会被自己吸引来的任务饿死。Linux 3.12 起(书 §8.3.6)引入 wakee_flips 统计来识别:

```c
// kernel/sched/fair.c:7537
static void record_wakee(struct task_struct *p)
{
	/*
	 * Only decay a single time; tasks that have less then 1 wakeup per
	 * jiffy will not have built up many flips.  (每秒最多衰减一次: 每秒翻转数减半)
	 */
	if (time_after(jiffies, current->wakee_flip_decay_ts + HZ)) {
		current->wakee_flips >>= 1;
		current->wakee_flip_decay_ts = jiffies;
	}

	if (current->last_wakee != p) {   // 这次唤醒的 wakee 与上次不同 => 翻转
		current->last_wakee = p;
		current->wakee_flips++;
	}
}
```

```c
// kernel/sched/fair.c:7571
static int wake_wide(struct task_struct *p)
{
	unsigned int master = current->wakee_flips;   // waker 的翻转数
	unsigned int slave = p->wakee_flips;          // wakee 自身作为 waker 的翻转数
	int factor = __this_cpu_read(sd_llc_size);    // LLC 域内 CPU 个数

	if (master < slave)
		swap(master, slave);
	if (slave < factor || master < slave * factor)
		return 0;                          // 关系稳定, 允许 affine
	return 1;                                  // "海王" waker, 拒绝 affine
}
```

判据(书 §8.3.6 的总结): `wakee->wakee_flips > llc_size && waker->wakee_flips > llc_size * wakee->wakee_flips` 时认为伴侣数超过 LLC 大小, 属于非"一夫一妻"的唤醒关系, wake_wide() 返回 1, want_affine 直接为 0, 唤醒交给均衡路径去摊开。`sd_llc_size` 在 update_top_cache_domain()(topology.c:694)赋值; 在 Venice 的一个 CCX 上(SMT2)该值为 32。

## 3. wake_affine_idle() 走读

wake_affine() 是分发器: 先试 WA_IDLE(只看"当下谁空闲"), 不服再试 WA_WEIGHT(看平均负载)。

```c
// kernel/sched/fair.c:7597
static int
wake_affine_idle(int this_cpu, int prev_cpu, int sync)
{
	/*
	 * If this_cpu is idle, it implies the wakeup is from interrupt
	 * context. Only allow the move if cache is shared. Otherwise an
	 * interrupt intensive workload could force all tasks onto one
	 * node ... (中断上下文唤醒: 仅共享缓存才允许拉过来)
	 *
	 * If the prev_cpu is idle and cache affine then avoid a migration.
	 * ... prev_cpu 空闲且亲和时避免迁移; 从 cpufreq 角度, 单核高利用率
	 *   优于多核低利用率。
	 */
	if (available_idle_cpu(this_cpu) && cpus_share_cache(this_cpu, prev_cpu))
		return available_idle_cpu(prev_cpu) ? prev_cpu : this_cpu;

	if (sync) {
		struct rq *rq = cpu_rq(this_cpu);

		if ((rq->nr_running - cfs_h_nr_delayed(rq)) == 1)
			return this_cpu;
	}

	if (available_idle_cpu(prev_cpu))
		return prev_cpu;

	return nr_cpumask_bits;   // 哨兵: 两个候选都不理想, 交给 weight 判据
}
```

分支逐一说明:

|分支|条件|返回|语义|
|-|-|-|-|
|①|this_cpu 空闲 **且** this_cpu/prev_cpu 共享 LLC(cpus_share_cache, core.c:3886, 比较的是 sd_llc_id)|prev_cpu 也空闲 → **prev_cpu**|prev_cpu 空闲说明它缓存热且没人抢, 原地不动最优|
|①|同上|prev_cpu 忙 → **this_cpu**|this_cpu 空闲说明唤醒大概率来自中断上下文; 只有共享 LLC 才允许把任务拉来, 否则中断风暴(网卡 IRQ 亲和)会把所有任务吸到一个节点|
|②|sync 且 `rq->nr_running - cfs_h_nr_delayed(rq) == 1`|**this_cpu**|waker 唤醒后即睡, runqueue 上"有效任务只剩 waker 自己" → wakee 接管该 CPU 零成本。cfs_h_nr_delayed()(fair.c:7451)扣除 EEVDF 延迟出队任务, 避免被"名义在队实际将走"的任务干扰计数|
|③|prev_cpu 空闲|**prev_cpu**|回到上次 CPU, L1/L2/L3 全热|
|④|都不满足|nr_cpumask_bits|本次 idle 判据弃权, 继续 weight 判据|

```
 wake_affine_idle(this_cpu, prev_cpu, sync)
 |
 +--[1] this_cpu 空闲 且 与 prev_cpu 共享 LLC ?      (cpus_share_cache)
 |       是 --> prev_cpu 也空闲 ?
 |               是 --> return prev_cpu   // 原地不动, 全部缓存热
 |               否 --> return this_cpu   // 中断上下文唤醒, 拉来即跑
 |
 +--[2] sync 且 (nr_running - delayed) == 1 ?        (只剩 waker 自己)
 |       是 --> return this_cpu         // waker 即睡, wakee 直接接班
 |
 +--[3] prev_cpu 空闲 ?
 |       是 --> return prev_cpu         // 回老家, L1/L2/L3 全热
 |
 +--[4] return nr_cpumask_bits          // 弃权 -> wake_affine_weight()
```

在 Venice 上: 分支①的 cpus_share_cache 即比较两个 CPU 的 sd_llc_id; 同属一个 CCX(32 逻辑 CPU)才可能互拉; CPU9(CCX3)与 CPU77(CCX4)之间分支①永远不成立, 只会落到②③④ —— 拓扑本身就把"跨 CCX 拉 idle"这条路堵死了。

## 4. wake_affine_weight() 走读

idle 判据弃权(两边都忙)时, 用 PELT 平均负载做加权比较:

```c
// kernel/sched/fair.c:7628
static int
wake_affine_weight(struct sched_domain *sd, struct task_struct *p,
		   int this_cpu, int prev_cpu, int sync)
{
	s64 this_eff_load, prev_eff_load;
	unsigned long task_load;

	this_eff_load = cpu_load(cpu_rq(this_cpu));      // PELT: cfs_rq_load_avg

	if (sync) {
		unsigned long current_load = task_h_load(current);

		if (current_load > this_eff_load)
			return this_cpu;                  // waker 自己比整队还重: 直接拉来

		this_eff_load -= current_load;            // 扣掉即将睡眠的 waker
	}

	task_load = task_h_load(p);                      // 被唤醒进程的负载

	this_eff_load += task_load;                      // this 侧: 加入 wakee
	if (sched_feat(WA_BIAS))
		this_eff_load *= 100;
	this_eff_load *= capacity_of(prev_cpu);          // 容量归一化 (fair.c:7532)

	prev_eff_load = cpu_load(cpu_rq(prev_cpu));
	prev_eff_load -= task_load;                      // prev 侧: 拿走 wakee
	if (sched_feat(WA_BIAS))
		prev_eff_load *= 100 + (sd->imbalance_pct - 100) / 2;  // 117 -> x108
	prev_eff_load *= capacity_of(this_cpu);

	/*
	 * If sync, adjust the weight of prev_eff_load such that if
	 * prev_eff == this_eff that select_idle_sibling() will consider
	 * stacking the wakee on top of the waker if no other CPU is
	 * idle.  (sync 时 prev+1: 平手偏向 this_cpu)
	 */
	if (sync)
		prev_eff_load += 1;

	return this_eff_load < prev_eff_load ? this_cpu : nr_cpumask_bits;
}
```

公式归纳(以 MC 域 imbalance_pct=117 为例):

```
 this 侧 = [ cpu_load(this_rq) - (sync ? waker 负载 : 0) + wakee 负载 ]
            x 100(WA_BIAS) x capacity_of(prev_cpu)

 prev 侧 = [ cpu_load(prev_rq) - wakee 负载 ]
            x 108(WA_BIAS) x capacity_of(this_cpu) + (sync ? 1 : 0)

            this 侧 < prev 侧  ----> 选 this_cpu (affine 成功)
            否则               ----> 弃权 (nr_cpumask_bits)
```

要点:

- **两边负载互为镜像**: this 侧"加上 wakee 之后的总量", prev 侧"减去 wakee 之后的存量", 比的是迁移后的两边轻重;
- **capacity 交叉相乘**: this 侧乘 capacity_of(prev_cpu), 是把 prev 侧的"1 单位负载"折算到 this 的容量尺度上 —— 大核上 1 单位负载更"贵"(arm64 大小核下尤其明显, 见第 6 节);
- **WA_BIAS**(features.h:123)给 prev 侧多乘 (117-100)/2=8: 把 prev 的存量放大 8%, 等价于 load 相当时**偏向 this_cpu**; sync 再 +1, 保证平手时也倒向 waker 一侧(与代码注释一致: 让 select_idle_sibling 考虑把 wakee "stacking on top of the waker");
- cpu_load()(fair.c:7473)就是 `cfs_rq_load_avg(&rq->cfs)`, 即 5.9 时代 source_load()/target_load() 的裸版本(见第 7 节对比)。

汇总到分发器:

```c
// kernel/sched/fair.c:7670
static int wake_affine(struct sched_domain *sd, struct task_struct *p,
		       int this_cpu, int prev_cpu, int sync)
{
	int target = nr_cpumask_bits;

	if (sched_feat(WA_IDLE))
		target = wake_affine_idle(this_cpu, prev_cpu, sync);

	if (sched_feat(WA_WEIGHT) && target == nr_cpumask_bits)
		target = wake_affine_weight(sd, p, this_cpu, prev_cpu, sync);

	schedstat_inc(p->stats.nr_wakeups_affine_attempts);
	if (target != this_cpu)
		return prev_cpu;      // 两个判据都没选 this_cpu => 留在 prev_cpu

	schedstat_inc(sd->ttwu_move_affine);         // /proc/schedstat 可见
	schedstat_inc(p->stats.nr_wakeups_affine);
	return target;
}
```

注意 wake_affine() 的输出只有两个值: this_cpu 或 prev_cpu —— 它不做第三选择; "在 this_cpu 附近找哪个具体空闲 CPU"是下一步 select_idle_sibling() 的事。

```
 wake_affine()
 |
 +-- WA_IDLE ?   --> wake_affine_idle()
 |                    |-- 命中 ----> target = prev_cpu / this_cpu
 |                    `-- 弃权(nr_cpumask_bits)
 +-- WA_WEIGHT ? --> wake_affine_weight()
 |                    |-- this 侧更轻 -> target = this_cpu
 |                    `-- 否则       -> target = nr_cpumask_bits
 v
 target == this_cpu ?  --是--> new_cpu = this_cpu (affine 生效, 记 ttwu_move_affine)
                      --否--> new_cpu = prev_cpu  (不迁移)
```

## 5. select_idle_sibling() 走读

wake_affine() 给出的 new_cpu 交给 select_idle_sibling()(fair.c:8092): **在 target 的 LLC 域(sd_llc)内找一个真正空闲的 CPU**, 找不到再退而求其次。

### 5.1 主流程

```c
// kernel/sched/fair.c:8092
static int select_idle_sibling(struct task_struct *p, int prev, int target)
{
	bool has_idle_core = false;
	struct sched_domain *sd;
	unsigned long task_util, util_min, util_max;
	int i, recent_used_cpu, prev_aff = -1;
	...
	/* 大小核系统先同步 util, 并用 asym_fits_cpu() 过滤容量不足的 CPU */
	if (choose_idle_cpu(target, p) &&
	    asym_fits_cpu(task_util, util_min, util_max, target))
		return target;                       // ① target 自己就空闲

	/*
	 * If the previous CPU is cache affine and idle, don't be stupid:
	 */
	if (prev != target && cpus_share_cache(prev, target) &&
	    choose_idle_cpu(prev, p) &&
	    asym_fits_cpu(task_util, util_min, util_max, prev)) {

		if (!static_branch_unlikely(&sched_cluster_active) ||
		    cpus_share_resources(prev, target))
			return prev;                // ② prev 空闲且同 LLC -> 回 prev
		prev_aff = prev;                     // cluster 机器: 先记着, 兜底用
	}

	/* per-cpu kthread(如 IO 完成回调) 与 wakee 同 prev 时允许堆叠 */
	if (is_per_cpu_kthread(current) && in_task() &&
	    prev == smp_processor_id() &&
	    this_rq()->nr_running <= 1 &&
	    asym_fits_cpu(task_util, util_min, util_max, prev)) {
		return prev;                         // ③ kthread 场景
	}

	/* Check a recently used CPU as a potential idle candidate: */
	recent_used_cpu = p->recent_used_cpu;
	p->recent_used_cpu = prev;                   // 滚动更新
	if (recent_used_cpu != prev && recent_used_cpu != target &&
	    cpus_share_cache(recent_used_cpu, target) &&
	    choose_idle_cpu(recent_used_cpu, p) &&
	    cpumask_test_cpu(recent_used_cpu, p->cpus_ptr) &&
	    asym_fits_cpu(task_util, util_min, util_max, recent_used_cpu)) {

		if (!static_branch_unlikely(&sched_cluster_active) ||
		    cpus_share_resources(recent_used_cpu, target))
			return recent_used_cpu;       // ④ 最近用过的 CPU 也热
	} else {
		recent_used_cpu = -1;
	}

	/* 大小核: 改用 sd_asym_cpucapacity 域 + select_idle_capacity() */
	if (sched_asym_cpucap_active()) {
		sd = rcu_dereference_all(per_cpu(sd_asym_cpucapacity, target));
		if (sd) {
			i = select_idle_capacity(p, sd, target);  // fair.c:8027
			return ((unsigned)i < nr_cpumask_bits) ? i : target;
		}
	}

	sd = rcu_dereference_all(per_cpu(sd_llc, target));   // LLC = sd_llc
	if (!sd)
		return target;

	if (sched_smt_active()) {
		has_idle_core = test_idle_cores(target);         // ⑤ SMT 感知
		if (!has_idle_core && cpus_share_cache(prev, target)) {
			i = select_idle_smt(p, sd, prev);        // 先试 prev 的 SMT 兄弟
			if ((unsigned int)i < nr_cpumask_bits)
				return i;
		}
	}

	i = select_idle_cpu(p, sd, has_idle_core, target);   // ⑥ LLC 域扫描
	if ((unsigned)i < nr_cpumask_bits)
		return i;

	/* ⑦ cluster 机器兜底: prev_aff / recent_used_cpu 可能跨 cluster 但同 LLC */
	if ((unsigned int)prev_aff < nr_cpumask_bits)
		return prev_aff;
	if ((unsigned int)recent_used_cpu < nr_cpumask_bits)
		return recent_used_cpu;

	return target;
}
```

要点:

- **缓存亲和的判定有两档**: cpus_share_cache()(core.c:3886, 比较 sd_llc_id, 即 LLC)与 cpus_share_resources()(core.c:3898, 比较 sd_share_id, cluster 机器上是 LLC tag / L2 级别的"更近一层共享", topology.c:698 用 lowest_flag_domain(SD_CLUSTER) 赋值)。**cluster 机器(topology.c:674 的 sched_cluster_active 静态钥匙)上, ②④ 即使同 LLC 也要求同 cluster, 否则只作为兜底**;
- **sd_llc 的来历**: update_top_cache_domain()(topology.c:676)用 `highest_flag_domain(cpu, SD_SHARE_LLC)` 取"最高的 LLC 共享域"记入 per-cpu sd_llc/sd_llc_size/sd_llc_id/shared;
- **recent_used_cpu**: 一次唤醒的"记忆", 让 ping-pong 式的两组任务能稳定聚拢。

### 5.2 SMT 感知: select_idle_core / select_idle_smt

LLC 域共享统计放在 sched_domain_shared(include/linux/sched/topology.h:66):

```c
// include/linux/sched/topology.h:66
struct sched_domain_shared {
	atomic_t	ref;
	atomic_t	nr_busy_cpus;   // LLC 域内忙 CPU 数(NOHZ 路径维护)
	int		has_idle_cores; // 域内是否还有整核空闲
	int		nr_idle_scan;   // SIS_UTIL: 允许扫描的 CPU 数上限
};
```

- 空闲时 __update_idle_core()(fair.c:7845)检查 SMT 兄弟全空闲则置 has_idle_cores=1;
- select_idle_core()(fair.c:7872)要求**整核**(SMT 两线程都空闲)才算 idle core —— 让任务优先独占物理核, 避免 SMT 争抢;
- 没有整核空闲时 select_idle_smt()(fair.c:7904)只扫 prev 的 SMT 兄弟(小范围、便宜):
  `for_each_cpu_and(cpu, cpu_smt_mask(target), p->cpus_ptr)`;
- nr_busy_cpus 由 set_cpu_sd_state_busy()/set_cpu_sd_state_idle()(fair.c:12868 / 12897)在 CPU 进出 NOHZ idle 时增减, nohz 均衡 kick 读取它决定是否拉起 ILB(fair.c:12852)。

### 5.3 SIS_UTIL: LLC 扫描的动态限流

select_idle_cpu()(fair.c:7952)从 target+1 绕回扫描整个 LLC 域; Venice 上一个 CCX 32 个逻辑 CPU 全扫代价可观, 因此 7.1.3 用 SIS_UTIL(features.h:95)根据 LLC 总利用率算出扫描上限 nr_idle_scan:

```c
// kernel/sched/fair.c:7952 (节选)
static int select_idle_cpu(struct task_struct *p, struct sched_domain *sd,
			   bool has_idle_core, int target)
{
	...
	if (sched_feat(SIS_UTIL)) {
		nr = READ_ONCE(sd->shared->nr_idle_scan) + 1;   // 空闲扫描配额
		if (nr == 1)
			return -1;                  // LLC 已过载: 直接放弃扫描
	}

	if (!cpumask_and(cpus, sched_domain_span(sd), p->cpus_ptr))
		return -1;                          // 域内无亲和 CPU

	if (static_branch_unlikely(&sched_cluster_active)) {
		struct sched_group *sg = sd->groups;
		if (sg->flags & SD_CLUSTER) {           // cluster 机器: 先扫本 cluster 组
			for_each_cpu_wrap(cpu, sched_group_span(sg), target + 1) {
				...
			}
			cpumask_andnot(cpus, cpus, sched_group_span(sg));
		}
	}

	for_each_cpu_wrap(cpu, cpus, target + 1) {  // 从 target+1 绕回扫 LLC
		if (has_idle_core) {
			i = select_idle_core(p, cpu, cpus, &idle_cpu);  // 整核优先
			...
		} else {
			if (--nr <= 0)
				return -1;              // 配额耗尽
			idle_cpu = __select_idle_cpu(cpu, p);
			...
		}
	}
	...
}
```

nr_idle_scan 的更新在 update_idle_cpu_scan()(fair.c:11298): 以 `nr_scan = llc_weight * (1 - x^2 * pct^2 / ...)` 二次曲线随 LLC 利用率收缩, 利用率达到 85%(对应 imbalance_pct=117 的过载点)时降为 0 —— **LLC 越忙越少扫, 过载直接不扫**, 这与老版本 SIS_PROP(按平均扫描成本/平均空闲时长限流)思路不同(见第 7 节)。

### 5.4 Venice 上的扫描顺序

设 waker(=affine 出的 target)在 CPU3(core1 线程0), wakee 的 prev_cpu=CPU44(同 CCX3), recent_used_cpu=CPU13:

```

 +---------------------------------------------------------------+

 +---------------------------------------------------------------+
   扫描半径刻意限制在 sd_llc = MC 域 = CCX3;

```

## 6. arm64 例子: Arm AGI CPU 上的 wake affine 与 EAS

### 6.1 Arm AGI CPU(SP113012, Neoverse V3)

arm64 平台实例: **Arm AGI CPU(SP113012, 136×Neoverse V3, 双 chiplet, 无 SMT)**。V3 每核**私有 L2(2MB/3MB)**, DSU-120 "Direct connect"(单核簇, 无本地 L3), 全片经 CMN 互连共享 **SLC 系统级缓存** = LLC(依据 [Neoverse V3 TRM](../../../../007.BOOKs/arm_neoverse_v3_core_technical_reference_manual_107734_0002_06_en.pdf), SLC 上报以固件 PPTT 为准)。arm64 的拓扑(cluster_id/core_id/llc_sibling/cluster_sibling)由统一的 drivers/base/arch_topology.c 解析(DT core-id/PPTT; store_cpu_topology() arch_topology.c:961, update_siblings_masks() arch_topology.c:745), 生成默认 SDTL 层次(topology.c:1805): SMT(无)→ CLS(退化)→ MC。

```
 Arm AGI CPU (SP113012), 136 x V3, LLC = SLC (MC 域 = 全片)
 +------------------------------------------------------------------+
 |  MC = sd_llc 域 (CMN SLC, 全片共享, SD_SHARE_LLC)                 |
 |  +------------------------------+  +----------------------------+ |
 |  | CPU0..CPU67 (chiplet0, ~68c) |  | CPU68..CPU135 (chiplet1)   | |
 |  | 每核私有 L2 2MB              |  | 每核私有 L2 2MB            | |
 |  | CLS 退化(单核簇)             |  | CLS 退化(单核簇)           | |
 |  +------------------------------+  +----------------------------+ |
 +------------------------------------------------------------------+
   层次: MC(全片 SLC); 无 SMT/CLS; 单 NUMA 形态下 PKG 未构建(MC span==cpu_map, build 循环 break)
```

- **任意核间唤醒**: SLC 覆盖全片, 任意两个 V3 之间 `cpus_share_cache()` 都为真, SD_WAKE_AFFINE 的最低公共域就是 MC 层; waker 在 CPU0、wakee prev 在 CPU70(跨 chiplet)与同 chiplet 唤醒在**缓存判据上等价**(都共享 LLC), 只差 mesh 距离——比 EPYC 9996"跨 CCX 即 L3 全冷"宽松得多;
- **wake_affine_weight()**: `capacity_of()` 交叉相乘在同构 AGI 上不起筛选作用(两侧都是 1024), 判据回归纯负载比较; 异构大小核上它才是"别把重任务放小核"的守门员(见附录);
- **CLS 域**: V3 Direct connect = 单核簇, CLS 全部退化, `sched_cluster_active` 关闭——cluster 感知分支在 AGI 上全部走默认路径(对照: 成对共享 L2 的小核簇会打开它, 见附录)。

### 6.2 EAS 打开后: find_energy_efficient_cpu() 优先

arm64 大小核通常配 Energy Model, EAS 使能(sched_energy_present, topology.c:393~397)后唤醒路径在 affine **之前**先走 EAS:

```c
// kernel/sched/fair.c:8850 (select_task_rq_fair 内)
		if (!is_rd_overutilized(this_rq()->rd)) {
			new_cpu = find_energy_efficient_cpu(p, prev_cpu);
			if (new_cpu >= 0)
				return new_cpu;   // EAS 直接定 CPU, 不再走 affine
			new_cpu = prev_cpu;
		}
```

- EAS 按"预测能耗增量最小 + 容量 fit"挑 CPU, 目标函数是能耗而非单纯缓存/负载;
- root domain 一旦 overutilized, EAS 弃权, 回到本文的 affine + select_idle_sibling 路径(性能优先);
- 异构大小核(见附录)才有 EAS 的用武之地; 对称服务器上 EAS 一律沉默——EPYC 9996(x86)连 Energy Model 都没有, rd->pd 为空; Arm AGI CPU(arm64)经 cppc_cpufreq 注册了 EM, 但 136 核同构 V3 无 `SD_ASYM_CPUCAPACITY`, `sched_energy_present` 依旧不打开——两者殊途同归, 全部唤醒走 affine 路径。

## 7. 5.9 → 7.1.3: 该路径的演进对比

书 §8.3.5/§8.3.6 的走读基于更早的内核(引用片段是 4.x 风格); 下表给出 5.9 → 7.1.3 的实际变化(行号均为 [Linux 7.1.3](../../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/sched/fair.c) 实测):

|方面|Linux 5.9|Linux 7.1.3|说明|
|-|-|-|-|
|select_task_rq_fair 签名|(p, prev_cpu, sd_flag, wake_flags) 4 参数|(p, prev_cpu, wake_flags) 3 参数|sd_flag 内部自取(wake_flags & 0xF, fair.c:8837)|
|wake_wide() 位置|select_task_rq_fair 的 want_affine 判定|同左(fair.c:8857)|书中所示"wake_affine() 内调用 wake_wide()"为 4.x 旧形态|
|EAS 门控|sched_energy_enabled() 静态钥匙|`!is_rd_overutilized(rd)` + find_energy_efficient_cpu() 内查 rd->pd(fair.c:8850/8640)|EAS 实现整体重写(spare capacity 策略)|
|WF_CURRENT_CPU|无(5.17 引入)|fair.c:8846 命中即返回 this_cpu|complete()(completion.c:35)等同步原语在用|
|慢速路径名|find_idlest_cpu()/find_idlest_group()|sched_balance_find_dst_cpu()(fair.c:7753)/sched_balance_find_dst_group(fair.c:11134)|6.1 起统一改名|
|负载采样|cpu_load(cpu_rq())(本仓库 5.9 树 fair.c:5903, 已无 source_load/target_load)|cpu_load() = cfs_rq_load_avg(&rq->cfs)(fair.c:7473)|source_load()/target_load() 是书中 4.x 旧形态, 本仓库 5.9 树已删除, 语义变为纯 PELT load_avg|
|delayed dequeue|无|cfs_h_nr_delayed(rq)(fair.c:7451)参与 idle 判据|EEVDF(6.6+)引入延迟出队, 7.1.3 计数需剔除|
|SIS 限流|SIS_PROP: avg_scan_cost vs rq->avg_idle|SIS_UTIL: nr_idle_scan 由 LLC 利用率二次曲线决定(features.h:95; fair.c:11298)|LLC 过载(约 85%)时干脆不扫|
|cluster 感知|无(5.16 才引入 SD_CLUSTER)|sched_cluster_active(topology.c:674)分支遍布 ②④⑥⑦|arm64 DynamIQ / 共享 L2 的 cluster 优先|
|任务级统计|p->se.statistics.nr_wakeups_affine|p->stats.nr_wakeups_affine(sched.h:564)|6.8 起 stats 移入 task_struct|
|sched_energy/拓扑标志|SD_SHARE_PKG_RESOURCES|更名 SD_SHARE_LLC(sd_flags.h:126)|语义相同|

wake_affine_idle()/wake_affine_weight()/wake_affine() 三个函数本体自 5.9 以来基本未变, 是唤醒路径里少有的"稳定资产"。

## 8. 调试方法

结合书 §8.3.7(sched_migrate_task 追踪点)与 §9.1.3(kernelshark):

### 8.1 tracepoint

- sched:sched_wakeup / sched_wakeup_new(include/trace/events/sched.h:178/185): 每次唤醒记录 `comm/pid/prio/success/target_cpu`;
- sched:sched_migrate_task(同文件:272): 记录 `orig_cpu → dest_cpu`, 是观察 affine/均衡实际迁移的直接证据。

```bash
# trace-cmd 抓取(书 §8.3.7 原命令)
trace-cmd record -e 'sched_wakeup*' -e sched_switch -e 'sched_migrate*'
kernelshark trace.dat

# 或纯 ftrace
cd /sys/kernel/tracing
echo 1 > events/sched/sched_wakeup/enable
echo 1 > events/sched/sched_migrate_task/enable
cat trace_pipe
```

判读技巧: 同一 pid 的 `sched_wakeup ... target_cpu=X` 与随后的 `sched_migrate_task ... orig_cpu=Y dest_cpu=X`, 就是唤醒路径(WF_TTWU → affine/均衡)做出的搬迁决策。

### 8.2 /proc/schedstat 与 /proc/<pid>/sched

- 域统计: `/proc/schedstat`(show_schedstat, kernel/sched/stats.c:109 起)每个 `domainN <域名> <span位图>` 行的末尾 12 个计数是 alb/sbe/sbf 与 ttwu 系列, 其中最后三个为 `ttwu_wake_remote, ttwu_move_affine, ttwu_move_balance`(stats.c:153~161); **ttwu_move_affine 即 wake_affine() 里 schedstat_inc(sd->ttwu_move_affine)(fair.c:7685)的累计值**, 增长越快说明该域 affine 决策越活跃;
- 任务统计: 需先 `sysctl kernel.sched_schedstats=1`(静态钥匙 sched_schedstats, core.c:4567), 之后 `/proc/<pid>/sched` 可见 `nr_wakeups_affine_attempts` 与 `nr_wakeups_affine`(include/linux/sched.h:564~565), attempts 与 affine 之差就是"试了但没拉成"的比例。

### 8.3 ftrace 函数级跟踪

```bash
cd /sys/kernel/tracing
echo function > current_tracer
echo wake_affine wake_affine_idle wake_affine_weight select_idle_sibling \
    > set_ftrace_filter
echo 1 > tracing_on
# 跑负载后
cat trace
# funcgraph 看开销(LLC 扫描成本是唤醒路径大头时尤其有用)
echo function_graph > current_tracer
echo select_idle_cpu >> set_ftrace_filter
```

### 8.4 运行时开关: sched_features

```bash
# 观察位置: /sys/kernel/debug/sched/features (debug.c:600 注册)
grep WA_ /sys/kernel/debug/sched/features
# 关掉 idle 判据 / weight 判据 / bias, 对比唤醒分布变化
echo NO_WA_IDLE    > /sys/kernel/debug/sched/features
echo NO_WA_WEIGHT  > /sys/kernel/debug/sched/features
echo NO_WA_BIAS    > /sys/kernel/debug/sched/features
```

7.1.3 中 wake affine **没有专属 sysctl**(不存在 wakeup 相关 tunable)。顺带一提: 常被误记为 sysctl 的 `kernel.sched_migration_cost_ns` 在 7.1.3 已不存在, 影响均衡侧迁移代价的变量是 `sysctl_sched_migration_cost`(fair.c:82, 默认 500000ns, task_hot() 判定用, fair.c:9649), 唯一运行时入口是 debugfs 的 `/sys/kernel/debug/sched/migration_cost_ns`(debug.c:612)。

## Q&A

**Q1: wake affine 与负载均衡, 谁赢?**
二者不竞争同一时机。唤醒路径(try_to_wake_up → select_task_rq_fair)里 affine 优先: 一旦 SD_WAKE_AFFINE 的域做出裁决, 代码显式 `sd = NULL` 放弃 balance 标志(fair.c:8870 "Prefer wake_affine over balance flags")。但 affine 只在"唤醒瞬间"生效且只选 this_cpu/prev_cpu 之一; 之后周期性/NEWIDLE 均衡会持续纠正长期不均 —— 不过均衡侧有 task_hot()/migration_cost 的缓存热度豁免, 两边短时间内互相打架造成的颠簸因此受限。真正的仲裁者是 wake_affine_weight() 的负载比较与 wake_wide() 的 1:N 豁免。

**Q2: sync 唤醒到底是什么?**
WF_SYNC(sched.h:2427, "Waker goes to sleep after wakeup")表示 waker 在唤醒后即将阻塞, 典型来源是 mutex unlock、futex wake。语义上"把 wakee 放到 waker 的 CPU"不再是抢占而是交接。代码上有三处兑现: select_task_rq_fair 的 sync 变量(fair.c:8831, 附加 PF_EXITING 抑制)、wake_affine_idle 的 `nr_running - cfs_h_nr_delayed == 1` 分支(fair.c:7617, 队列里只剩 waker 自己)、wake_affine_weight 的 current_load 扣减 + 平手 +1(fair.c:7637~7665)。

**Q3: 什么时候 affine 反而有害?**
① 1:N 唤醒(server 唤醒大量 client): 全部 client 被吸到 server 的 CPU 造成饥饿, 由 wake_wide() 豁免; ② 中断风暴场景: this_cpu 因 IRQ 空闲而 wakeup 密集, 若不共享 LLC 仍拉任务过来, 会把全系统任务吸到 IRQ 所在节点, wake_affine_idle() 分支①的 cpus_share_cache 条件专门堵这个洞; ③ 跨 LLC 拉(如 Venice 跨 CCX): L3 全冷, 迁移纯亏, 分支①与 select_idle_sibling 的 sd_llc 半径都在拓扑层面阻止; ④ 高负载 LLC 内无脑扫描本身有开销, SIS_UTIL 会按利用率收缩 nr_idle_scan 直至放弃。

**Q4: WA_BIAS 的 8% 是什么意思?**
MC 域 imbalance_pct=117, wake_affine_weight() 在 WA_BIAS 开启时把 prev 侧负载乘 `100 + (117-100)/2 = 108`, this 侧乘 100, 相当于承认"迁移有缓存破坏成本, prev 现存负载要重估 8%", 因此负载相当时偏向 this_cpu —— 即让 affine 更容易胜出, 而不是偏向 prev。

**Q5: Venice 上 wake affine 与 NPS1/2/4 有关系吗?**
NPS 改变的是 NUMA 域划分(NPS4 时每 socket 切成 4 个 NUMA 节点, 每节点 2 CCD/4 CCX), 影响的是 SD_NUMA 层与"远 NUMA 剥离 SD_WAKE_AFFINE"的生效范围; 而 wake affine 的主战场 MC=CCX 完全在 socket 内部, 与 NPS 无关。NPS 只决定更上层(跨 CCX/CCD/节点)的均衡行为。

## 附录: Cortex-A725 + A520(DynamIQ/DSU-120)异构实例(教学对照)

> 主文 arm64 实例为 Arm AGI CPU(SP113012, 同构 V3)。本附录保留异构大小核实例——`capacity_of()` 交叉相乘与 `sched_cluster_active` 这两件事只在异构/有簇的系统上有戏, AGI 上都"沉默"。

现代 arm64 大小核: 4×Cortex-A725(大核, **乱序**, 每核**私有 L2**, 128KB~1MB 可配) + 4×Cortex-A520(小核, **顺序**, **每 complex 一对核共享 L2**, 128~512KB 可配), 全部经 DSU-120 共享同一块 L3(依据 [Cortex-A725 TRM](../../../../007.BOOKs/arm_cortex_a725_core_trm_107652_0001_04_en.pdf)/[Cortex-A520 TRM](../../../../007.BOOKs/arm_cortex_a520_core_trm_102517_0001_04_en.pdf))。

```
 Cortex-A725 + A520, 单 DSU-120 (MC/LLC 域 = 全片)
 +------------------------------------------------------------------+
 |  MC = sd_llc 域 (DSU-120 L3, 全片共享, SD_SHARE_LLC)              |
 |  +---------------------------+  +------------------------------+  |
 |  | CPU0..CPU3 (A725, 大核)   |  | CPU4..CPU7 (A520, 小核)       |  |
 |  | 每核私有 L2 (128KB~1MB)   |  | 每 complex(对)共享 L2         |  |
 |  | capacity = 1024           |  | CLS 域 = {4,5} / {6,7}        |  |
 |  | CLS 退化(单核簇)          |  | capacity ≈ 252 (示意)         |  |
 |  +---------------------------+  +------------------------------+  |
 +------------------------------------------------------------------+
   层次: CLS(仅 A520 对, SD_CLUSTER) -> MC(全片 L3); 无 SMT; PKG 未构建(MC span==cpu_map, build 循环 break)
```

- **A520 对内唤醒**: waker 在 CPU4、wakee prev 在 CPU5, 同属一个 CLS 域且共享 L2, `cpus_share_cache()` 为真, wake_affine_idle() 分支①③可用, L2/L3 全热 —— 与 EPYC 9996"CCX 内"同理;
- **任意大/小核间唤醒**: 因为 LLC(DSU L3)覆盖全片, 大小核之间 `cpus_share_cache()` 也为真, SD_WAKE_AFFINE 的最低公共域就是 MC 层; wake_affine_weight() 里 `capacity_of()` 交叉相乘开始起作用: A725 侧容量 1024 vs A520 侧 ≈252, 同样的 PELT 负载折算后轻重立判, 避免把重任务压到小核;
- **CLS 域**: 只在固件把"共享 L2 的核"声明为一个 cluster(DT cluster 节点/PPTT)时存在——A520 对 → CLS={4,5} 存活且 `sched_cluster_active` 被打开, select_idle_cpu()/select_idle_smt() 会优先扫同 cluster 的 CPU; A725 私有 L2 → 单核"簇"退化。这与老式"整簇共享 L2、簇间无 L3"的传统 big.LITTLE(MC=簇、无 CLS)不同。
