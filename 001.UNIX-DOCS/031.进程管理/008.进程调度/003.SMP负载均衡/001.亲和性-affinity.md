## 1. 物理基础：为什么需要亲和性（MOS5 p.552）

亲和性的全部论证建立在一个微架构事实上：**CPU 不是等价的——刚跑过你的那颗 CPU 对你更"值钱"**。

- **缓存半句**：CPU k 的缓存里还装着线程 A 的工作集 → 回 k 重跑，L1/L2（乃至 LLC）命中率高，省掉整个预热重建；
- **TLB 半句**：k 的 TLB 里还留着 A 的页表映射 → 减少 TLB miss（arm64 上对应物：ASID 跟着 mm 走、迁移不换，见 [004.8.1.4 §2.10.3](../../../025.MULTIPLE_PROCESSOR_SYSTEM/002.多处理器理论/004.8.1.4-多处理器调度.md)）；
- **边界**（MOS5 第8章习题14 的追问）：亲和调度减少缓存失效 ✓、减少 TLB 失效 ✓，但**不减少缺页**——页框分配与"上次跑在哪"无关（NUMA locality 是另一维度，Linux 用 `migrate_degrades_locality()` 单独建模）。

## 2. 书里的定义句（逐条原文）

### 2.1 MOS5：affinity scheduling = 尽量回上次跑过的 CPU

> Some multiprocessors take this effect into account and use what is called **affinity scheduling** (Vaswani and Zahorjan, 1991). The basic idea here is to **make a serious effort to have a thread run on the same CPU it ran on last time**. One way to create this affinity is to use a **two-level scheduling algorithm**.<sup>有些多处理机考虑了这一因素，并使用了所谓亲和调度（affinity scheduling）（Vaswani和Zahorjan，1991）。其基本思想是，尽量使一个线程在它前一次运行过的同一个CPU上运行。创建这种亲和力（affinity）的一种途径是采用一种两级调度算法（two-level scheduling algorithm）。</sup>

书中给出的两级调度（顶层按最闲分派 CPU、底层每 CPU 私有就绪队列、空闲时偷任务）带来三个收益：**负载大致均衡／缓存亲和最大化／就绪队列争用最小**。书索引条目：**Affinity scheduling, 552**。

MOS5 的 Linux 节（索引 "Scheduling algorithm → affinity, 552" 同段家族）还总结了 2.6 时代就有的三件套——与两篇笔记的结论完全同构：

> 首先，在多处理器平台上，运行队列数据结构与某一个处理器相对应，**调度器尽量进行亲和调度，即将之前在某个处理器上运行过的任务再次调入该处理器**。第二，为了更好地描述或修改一个选定的线程对亲和性的要求，**有一组系统调用可供调用**。最后，……调度器实现在不同处理器上阶段性地加载平衡，从而保证整个系统的加载是平衡的。<sub>（中文版 epub 的 Linux 小节仍是 2.6 O(1) 调度器内容，为旧版，页码与 5th 不同；5th 英文版同段见 "the Linux scheduler includes special features particularly useful for multiprocessor or multicore platforms"）</sub>

### 2.2 PLKA（《深入Linux内核架构》）：亲合性必须可设置——硬亲和

§2.8.1 SMP调度 给出多处理器调度的三个额外要求，其中第二条就是硬亲和的定义句：

> 进程与系统中某些处理器的**亲合性（affinity）**必须是可设置的。例如在4个CPU系统中，可以将计算密集型应用程序绑定到前3个CPU，而剩余的（交互式）进程则在第4个CPU上运行。……进程对特定CPU的亲合性，**定义在 `task_struct` 的 `cpus_allowed` 成员中。Linux提供了 `sched_setaffinity` 系统调用**，可修改进程与CPU的现有分配关系。

注意两点：① 该书用"亲**合**性"译法；② 它同时点出迁移代价的另一半——"内核必须能够将进程从一个CPU迁移到另一个，但必须谨慎使用……小型SMP系统上CPU高速缓存是最大的问题；真正大型系统上CPU与迁移进程此前使用的物理内存距离可能有若干米"（即 NUMA 距离）。缓存热度 + 内存 locality，正是软亲和与 NUMA balancing 两套机制的分界。

### 2.3 RLK1（Run Linux Kernel Vol.1）：wake affine——唤醒路径的软亲和

§8.3.6 的定义句：

> wake affine特性希望把**被唤醒进程尽可能地运行在 wakeup_cpu 上**，这样可以让一些有相关性的进程尽可能地运行在**具有高速缓存共享的调度域**中，获得一些高速缓存命中带来的性能提升。

书把它讲成一把"**双刃剑**"：Android C/S 模型下 server 反复唤醒大量 client，1:N 唤醒会把所有 client 吸到 server 的 CPU0 → server 被自己吸引来的任务饿死。Linux 3.12 的解法是 `record_wakee()`/`wakee_flips` 统计 + `wake_wide()` 豁免（"海王"唤醒者拒绝 affine）。完整代码走读见 [000.wake affine.md](./000.wake%20affine.md) §2.3/§3/§4。

## 3. 三个层次：硬亲和 / 软亲和 / 唤醒亲和

|层次|谁决定|书中出处|Linux 7.1.3 落点（详见两篇材料）|
|-|-|-|-|
|**硬亲和**|用户/系统调用|PLKA §2.8.1（`cpus_allowed` + `sched_setaffinity`）；MOS5："a set of system calls is available to further specify or modify the affinity requirements"；MOS5 Windows 节："Threads can also be **affinitized** to run only on certain processors"（索引 Affinitized thread, 930）|`task_struct.cpus_ptr/cpus_mask`（include/linux/sched.h:927）、`sched_setaffinity(2)`（syscalls.c:1262）；`select_task_rq()` 先查 `nr_cpus_allowed==1`（core.c:3574）；`can_migrate_task()` 中 `dst_cpu ∉ p->cpus_ptr` 一票否决（fair.c:9780）——**约束**，调度器必须遵守|
|**软亲和**|内核自动（缓存偏好）|MOS5 p.552 命题① + Linux 节"将之前在某个处理器上运行过的任务再次调入该处理器"|唤醒路径回 prev_cpu／`recent_used_cpu`（sched.h:862），候选全圈在 `sd_llc`（LLC 域）内："迁移可以，缓存不许凉透"（fair.c:8092）；均衡路径 `task_hot()` 把"缓存还热"定量成 `<500µs` 的迁移刹车（sysctl_sched_migration_cost, fair.c:82；fair.c:9611）——**偏好**，可被均衡/容量/安全推翻|
|**唤醒亲和**（wake affine）|内核唤醒路径（软亲和特例）|RLK1 §8.3.6（上文 2.3）|`want_affine` → `wake_affine()`（fair.c:7670）二选一裁决 this_cpu vs prev_cpu（`wake_affine_idle` fair.c:7597／`wake_affine_weight` fair.c:7628），`wake_wide()`（fair.c:7571）防 1:N；开关 WA_IDLE/WA_WEIGHT/WA_BIAS（features.h:121~123）|

三层共享同一个物理动机（缓存/TLB 热），但强度不同：**硬亲和是约束，软/唤醒亲和是收益估计**——异构机上算力错配时（`asym_fits_cpu()`）、负载失衡痛过头时（`cache_nice_tries`）、安全 cookie 不匹配时，软亲和都会被推翻，见 [004.8.1.4 §2.10.5/§2.10.6](../../../025.MULTIPLE_PROCESSOR_SYSTEM/002.多处理器理论/004.8.1.4-多处理器调度.md)。

## 4. 同词异义：007.BOOKs 里 affinity 的另外三种用法

### 4.1 中断亲和（IRQ affinity）——《深入Linux内核架构》

> 在多处理器系统中，可使用 **`set_affinity`** 指定CPU来处理特定的IRQ。这使得可以将IRQ分配给某些CPU（通常，SMP系统上的IRQ是平均发布到所有处理器的）。<sub>（该书 `struct irq_chip` 一节；现代内核对应 `irq_chip->irq_set_affinity`，运行时入口 `/proc/irq/N/smp_affinity`）</sub>

这是"**中断与 CPU 的绑定**"：把某个中断源钉在（或偏向）某些核上处理。它与调度亲和互相成就——网卡中断亲和 + wake affine 一起决定"报文→中断→唤醒的 socket 线程"是否留在同一 LLC。

### 4.2 网卡 core affinity —— MOS5（多计算机章，索引 Affinity core, 563）

> Better still, the card often supports **core affinity**. Specifically, it has its own hashing logic to help steer each packet to a suitable process. As it is **faster to process all segments in the same TCP flow on the same processor (where the caches are warm)**, the card can use the hashing logic to hash the TCP flow fields (IP addresses and TCP port numbers) and add all segments with the same hash on the same queue that is served by a specific core.

多队列网卡按流 hash 把同一条 TCP 流固定到同一个核——**硬件版的 wake affine**，思想同源：同流数据在同一核上缓存热。

### 4.3 虚拟化 VP affinity —— MOS5 Hyper-V 节

> The classic scheduler …… allows adjustments such as **setting affinity for VPs to a set of processors**, reserving a percentage of processor capacity and setting limits……

hypervisor 给 vCPU 设亲和，本质是把 4.1/4.2 的"钉住"思想搬到 host 调度层（对照 [004.8.1.4 §2.5](../../../025.MULTIPLE_PROCESSOR_SYSTEM/002.多处理器理论/004.8.1.4-多处理器调度.md) 的 pv_spinlock/定向让渡——虚拟化层级的同一疾病）。

### 4.4 ARM/GIC 的 affinity —— 编址与路由，另一码事（007.BOOKs）

> The **affinity of a PE** is represented as four 8-bit fields: `<affinity level 3>.<affinity level 2>.<affinity level 1>.<affinity level 0>` …… The affinity scheme matches that used in ARMv8-A, with the affinity of a PE reported in **MPIDR_EL1**. …… The **ARE** bits in GICD_CTLR control whether **affinity routing** is enabled.

GIC 文档里的 affinity 是**处理器的层级编号**（Aff0=线程/核内、Aff1=核、Aff2=簇、Aff3=封装级），GIC 用它把中断**路由**到目标核（affinity routing）；Arm ARM 中 `MPIDR_EL1.Aff0~Aff3` 同义。**与调度亲和是两码事**——但两者共享同一套硬件层级：arm64 调度域拓扑（`cpu_topology` 的 package_id/cluster_id/core_id/thread_id、`llc_sibling` 掩码）正是从这个层级体系解析出来的（[004.8.1.4 §2.10.2](../../../025.MULTIPLE_PROCESSOR_SYSTEM/002.多处理器理论/004.8.1.4-多处理器调度.md)）。所以：**GIC 的 affinity 是这套编号的"地址"用法，调度器的 affinity 是这套编号之上的"倾向"用法**。读 Arm/GIC 文档时不要与调度语境混淆。

## 5. 收束

- **定义**：affinity = 任务与 CPU 之间"值得待在一起"的倾向，物理基础是缓存/TLB 的微架构温度（"有些 CPU 更平等"）；
- **谱系**：学术出处 Vaswani & Zahorjan 1991（MOS5 p.552）→ 硬亲和（`cpus_allowed`/`sched_setaffinity`，PLKA §2.8.1）→ 软亲和（per-CPU rq + 回 prev + `task_hot` 刹车）→ wake affine（RLK1 §8.3.6，waker-wakee 共享 LLC）；
- **一句话对账**：硬亲和是用户意志（约束），软/唤醒亲和是调度器对"缓存还热"的估价（偏好）；均衡、算力、安全随时可以推翻这份乡愁——**affinity 的价值由芯片拓扑定价**（EPYC 9996 的 CCX 墙 vs Arm AGI 的全片 SLC，见 004.8.1.4 §2.10.7）。

## Q&A

**Q1: 亲和调度减少了缓存失效，它也减少 TLB 失效吗？缺页呢？**（MOS5 第8章习题14）
TLB 减少——同一批虚拟地址的翻译表项还在 prev CPU 的 TLB 里（arm64 上 ASID 随 mm 迁移不换，遗留表项无害）。缺页**不**减少——页框在物理内存里的位置与上次跑在哪个 CPU 无关；NUMA 系统上"跑得近"能降低**远端访问延迟**，但那是 `migrate_degrades_locality()`（fair.c:9658）建模的另一维度，不是缺页次数。

**Q2: 亲和性是规则还是偏好？**
两派并存：**硬亲和**（`cpus_mask`）是约束——用户意志，`select_task_rq`/`can_migrate_task` 都会先检查它；**软/唤醒亲和**是收益估计——`task_hot()` 的 500µs、"同 LLC 才回 prev"都只是倾向，会被负载失衡（`cache_nice_tries` 次失败后强行搬）、算力错配（`asym_fits_cpu`）、安全 cookie（core scheduling）推翻。书中命题①在异构机上的改写：**"有些 CPU 更平等"不仅因为缓存热，还因为算力大、能耗低——亲和是三者博弈后的最优解，不是无条件的乡愁**（004.8.1.4 §2.10.6）。

**Q3: wake affine 与负载均衡谁赢？**
唤醒瞬间 affine 优先（fair.c:8870 "Prefer wake_affine over balance flags"，`sd = NULL` 显式弃用 balance 标志）；之后的周期性/NEWIDLE 均衡持续纠正长期不均，而均衡侧又有 `task_hot()` 缓存热豁免——两边短兵相接被"热"刹车限制。完整仲裁见 [000.wake affine.md Q1](./000.wake%20affine.md)。

**Q4: GIC 文档里的 affinity 与本文的 affinity 是一回事吗？**
不是。前者是 PE 的层级编号（Aff0~3，MPIDR_EL1），用于**中断路由**（affinity routing）；后者是任务与 CPU 之间的**调度倾向**。但共享同一套硬件层级——调度域拓扑就是从这个编号体系构建的，两者是"同一块地形"上的"地址"与"倾向"（§4.4）。
