## 摘要

|要点|说明|
|-|-|
|平台|Arm AGI CPU（SP113012，136×Neoverse V3，双 chiplet，无 SMT，Armv9.2-A，每核私有 L2 2MB，DSU-120 Direct connect）|
|层级一句话|`线程(无SMT) → 核(私有L1/L2) → "簇"(单核,无共享) → 全片 SLC → DDR5`——**没有 9996 那种"CCX 缓存墙"**，LLC(SLC) 覆盖全片|

|内核映射|SMT 层无；CLS 退化（单核簇）；**MC = 全片 SLC = 136 CPU**；单 NUMA 形态下 PKG/NODE 未构建（构建循环 break）|

## 一、物理层级总览

```
 Socket (封装) x1 —— Arm AGI CPU (SP113012)
 |
 |=====================================================================|
 |   chiplet/DIE 0 (~68 核, 示意)         chiplet/DIE 1 (~68 核)       |
 |                                                                     |
 |  core0  core1 ... core67            core68 ... core135              |
 |  |L1|L2| |L1|L2| ...                |L1|L2| ...                     |
 |  |  每 core: DSU-120 "Direct connect"(单核簇, 无簇级 L3/SCU) |      |
 |  |      CHI RN-F 口 ——> 互连网格 (CMN 家族, 示意)                   |
 |  +--------+------------------+ +--------------------------------+   |
 |           |   mesh: HN-F x N (每 HN-F: SLC 切片+SF) + SN-F |        |
 |           +------------------+--------------------------------+     |
 |                                    |                                |
 |                              DDR5-8800 (每芯片最高 6TB)             |
 |=====================================================================|
  合计: 136 核 = 136 CPU (无 SMT); LLC = 全片 SLC (容量以官方为准)
```

**与 9996 的层级对照（最简记忆）**：

|层级|EPYC 9996|Arm AGI CPU (SP113012)|
|-|-|-|
|线程层|SMT2（512 线程，共享 L1/L2/执行单元）|**无**（1 核 = 1 CPU）|
|核层|256 核，私有 L1/L2|136 核，私有 L1(64K/64K) + L2(2MB)|
|"簇"层|CCX：16 核共享 64MB L3（**一致性墙**）|DSU Direct connect：**单核**，无簇内共享|
|裸片层|8 CCD + 2 IOD（GMI/Fabric）|双 chiplet（跨 die 链路示意）|
|LLC|16 块互不相通的 L3（CCX 各一块）|**全片一片 SLC**（HN-F 分布式切片，硬件统一编址）|
|一致性域|每个 CCX 一个小域 + Fabric 互联|**全片一个大一致域**（Inner Shareable）|

## 二、逐层共享什么

|层|数量|共享内容|不共享/私有|
|-|-|-|-|
|核（V3）|136|—（是最小调度单位）|L1i/L1d 各 64KB、L2 2MB（私有）|
|"簇"（DSU Direct connect）|136 个单核簇|**什么都不共享**（TRM：V3 "supports Direct connect only"，无本地 L3/Snoop Filter/SCU）|—|
|chiplet|2|die 内互连/供电（示意）|跨 die 仍共享 SLC（一致性不因 die 断裂）|
|全片 SLC|1 片（HN-F 切片分布式）|**LLC**：所有核共享；对数据行默认 **exclusive 分配**，检测到共享模式时 **pseudo-inclusive**（CMN-700 TRM 原文）|—|
|DDR5-8800|最高 6TB/芯片|统一编址内存（一致性终点 PoC 之后）|—|

> 关键差异：9996 的"同 CCD 两 CCX"在缓存上互为远端；AGI 的"同 chiplet 两核"与"跨 chiplet 两核"**在缓存层级上等价**——都共享同一片 SLC，只有 mesh 跳数差别（示意）。

## 三、互连与节点类型（CHI 视角）

```
                    CMN 网格 (rectangular mesh, 可配置矩形网格)
   RN-F (Fully coherent Request Node)          每核一个
     core0   core1   core2  ......  core135
       |       |       |              |
   ====|=======|=======|==============|======================== mesh
       |       |       |              |
   +---v---+---------------------+---v---+ .........  +--------+
   | HN-F #0                       HN-F #k |           | SN-F    |
   |  - Snoop Filter (SF) 目录     (按地址 |           | Slave   |
   |  - SLC 切片(容量可配)          哈希归属)|          | Node:   |
   |  - PoS: 序列化点(同一地址的事务 |       |           | DDR5 MC |
   |    在此排队定序)                |       |           +--------+
   |  - PoC: 一致性点(所有核视图在此 |       |
   |    汇合, 脏行最终在此对齐)      |       |
   +--------------------------------+-------+ ......... (示意)
   注: HN-F 最多可到 128 个, RN-F 最多 256 个 (CMN-700 规模上限)
```

- **RN-F**（Request Node, Fully coherent）：V3 核的 CHI master 口（经 DSU Direct connect）；
- **HN-F**（Home Node, Fully coherent）：一致性枢纽——**集成了 PoS 与 PoC**（TRM 原文），自带 SF 目录与 SLC 切片；
- **SN-F**（Slave Node）：通往 DDR5 内存控制器；
- 地址哈希把每条 cache line 归属到某个 HN-F——**目录式（directory）一致性**：SF 记录"哪些核缓存了这行"，探针只发给目录里的核，**不做全核广播**（对比：无目录的总线式/广播式 snoop）。

## 四、缓存一致性：核心内部 / 跨核心 / 跨 socket（重点）

### 4.0 三层战场总图（各自的总线与协议）

```
 +-------------- Socket 0 (AGI CPU, SP113012) -----------------+
 |                                                             |
 |  [核内层]  私有层次, 无需外部协议                           |
 |   LSU <-> L1d(64K,WB) <-> L2(2M,统一,WB)                    |
 |   总线: 核内私有load/store通道(非AMBA)   协议: 无(自一致)   |
 |                                                             |
 |  [全片层]  所有核 + I/O 设备的一致域                        |
 |   RN-F核 --CHI--> XP(交叉点) --mesh--> HN-F(SF+SLC) --> SN-F|
 |   总线: AMBA 5 CHI Issue E over CMN mesh                    |
 |   协议: CHI 目录式(MOESI家族: I/SC/UC/UD/SD, SF 记录持有者) |
 |   I/O: 设备经 HN-I(AXI/ACE-Lite) 入一致域                   |
 |                                                             |
 +------------------- 跨 socket 链路(示意) --------------------+
 |  方案a: 定制 CHI 远链路(专利, 如 Marvell CCPI)              |
 |  方案b: CMN 的 CCG(CXL 网关): CXL.cache/背失效(BI)          |
 |  方案c: 非一致 NUMA: 远端内存走 CXL.mem/PCIe, 不可缓存      |
 +------------------------- Socket 1 --------------------------+
```

### 4.1 核心内部：私有层次，没有"协议"只有"策略"

核内 L1/L2 属于**同一个核**，不存在两个独立代理——一致性问题退化为"维护策略"：

```
        一个 Neoverse V3 核
  +---------------------------------------------------+
  |  LSU(访存单元) --私有通道--> L1d 64KB (WB/WA)       |
  |    |                        |  <-- 核内后备/逐出    |
  |  取指单元 --私有通道--> L1i 64KB                   |
  |    |                   (可与数据侧硬件一致, 见下)    |
  |  L2 2MB 统一(指令+数据), WB                          |
  |    |                                               |
  |  逐出策略(TRM): Unique Clean 行逐出可发              |
  |  WriteEvictFull / Evict(可配置, 原文: "Enables      |
  |  sending WriteEvictFull transactions when Unique    |
  |  Clean cache-lines are evicted")                    |
  +---------------------------------------------------+
     出核 == 进 CHI 世界(RN-F master 口, Direct connect)
```

- **L1d↔L2**：核内逻辑保证（L1 是 L2 的子集视图 + 逐出回写），不需要 CHI 事务；
- **L1i 一致性**：V3 提供 "**Instruction cache hardware coherency**"（TRM §6.5，可配置）——自修改代码场景下 I-cache 与 store 的协调由硬件完成，否则软件需 `IC IVAU` 维护；
- **写策略**：Normal WB（页表 attribute 控制；虚拟化下有 S2FWB 强制回写等特性，V3 支持列表原文）；
- **这一层没有总线仲裁对手，只有流水线**——所以原子操作的"本地监视器"放在核内（见 §5.1）。

### 4.2 跨核心：CHI 目录式协议（全片一致域）

**协议**：AMBA 5 CHI Issue E（CMN-700 支持到 CHI-E，含 MakeReadUnique、带可选数据的写、增强独占事务等——TRM 特性清单原文）。
**总线**：mesh 上的 CHI 链路（RN-F→XP 交叉点→HN-F），地址哈希选 HN-F。

常用 CHI 事务速查（RN-F 发起）：

|事务|用途|典型行状态变化|
|-|-|-|
|`ReadOnce`|只读一次、不驻留（如 DMA 源）|不进 L1/L2|
|`ReadShared`|普通读，要一份可共享副本|→ SC|
|`ReadClean`|读但不接受脏（如页表遍历）|→ SC(净)|
|`ReadUnique`|读且要独占（读-改-写前奏）|→ UC/UD|
|`CleanUnique` / `MakeUnique`|把已持有的行变独占 / 使他核副本失效后独占|→ UC|
|`WriteNoSnpFull` 等|直写不连贯内存|不进一致域|
|`WriteBackFull`|脏行逐出回写|UD → I(行下岗)|
|`WriteEvictFull`|净独占行带数据逐出(TRM 配置项)|UC → I|

行状态（MOESI 家族在 CHI 的记法）：`I` 无效 / `SC` 共享净 / `UC` 独占净 / `UD` 独占脏 / `SD` 共享脏（另有 UCE 净空独占等变体）。

**读 miss 全流程（含 DMT/DCT 优化）**：

```
 core42 读 X: L1d miss -> L2 miss
   |
   | ReadShared (Req)                        [按 X 哈希路由]
   v
 HN-F #k  == X 的 Home (PoS: 同址事务在此定序)
   |
   +--[优化DCT] SF 显示 core7:SC 且数据可直传
   |     HN 让 core7 直接把数据发给 core42 (Direct Cache Transfer,
   |     少一跳 HN 缓存; CHI-E 支持, CMN-700 TRM: "DCT Yes")
   |
   +--[常规] SF 无持有者: 查 SLC 切片
   |     命中 -> 返回 (SLC 是全片共享后备)
   |     未命中 -> [优化DMT] 直接转发 SN-F 读 DDR (Direct Memory
   |     Transfer, 数据不过 HN 缓存)
   |
   +-- 更新 SF: core42 加入持有者集合
   v
 core42 L1d/L2 填充 X (SC); core7 保持 SC   [数据只有一份净本, 可多持]
```

**写路径（先独占，后落笔）**：

```
 core42 要写 X (32字节部分写, 举例)
   |
   +-- 小写优化: WriteUniquePtl(带部分数据的写)
   |     不必先把整行取回来! HN 负责合并 (CHI-E "writes with
   |     optional data", TRM 特性清单)
   |
   +-- 常规 RMW 前奏: CleanUnique / MakeUnique / ReadUnique
         |
         v
      HN-F #k: 查 SF {core7:SC, core90:SC}
         |  SnpUnique 定向探针(只发持有者, 不广播)
         v
      core7/core90 失效副本(I) + Ack; SF -> {core42:UC}
         |
         v
      core42 改写 -> UD; 逐出时 WriteBackFull 落 SLC(exclusive)
      -> 最终 DDR (PoC 保证全局单值)
```

**SF 目录与 SLC 的分工**：

```
 SF(Snoop Filter)条目 = {line 状态, 持有者位图}   <-- "谁有"
 SLC 切片(每 HN-F)   = 数据后备 + 写下沉落点      <-- "数据在哪"
   - SLC 对数据行默认 exclusive(与核缓存不重复)
   - 检测到共享模式 -> pseudo-inclusive(SLC 也留副本,
     让后续探针/转发在 SLC 闭合, 少去 DDR)   [CMN-700 TRM 原文]
   - SF 容量不足时目录逐出 -> 等效于"隐性失效"过量的核副本
```

**I/O 一致性与 DVM（跨核心的另外两个口）**：

- **HN-I**（I/O coherent Home Node）：外设（NIC/加速卡 DMA）经 **AXI/ACE-Lite** 接入 HN-I，从而对一致内存的 DMA 访问自动与 CPU 缓存保持一致（TRM：HN-I "supports AMBA AXI and ACE-Lite protocols"）——设备不需要手动 cache 维护；
- **DVM**（Distributed Virtual Memory，CHI 消息族）：TLB 击落（`TLBI ...IS` 指令）在 CHI 里是 **DVM message** 广播到 DVM 域内所有 RN-F（TRM §3.3.8 "RN entry to and exit from Snoop and DVM domains"、§3.9.4 "DVM messages"）。这是**虚拟地址一致性**：数据一致管 cache line，DVM 管 TLB 项。内核每次 `flush_tlb_mm()`（[tlbflush.h](../../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/tlbflush.h):21 的 `__tlbi()` 宏）最终都是一串 DVM 广播。

### 4.3 跨 socket：三种方案谱系（AGI 未公开，按 Arm 生态示意）

```
 方案a: 定制 CHI 远链路(专利)            方案b: CXL(CCG 网关)
 Socket0 HN-F <==专利CHI==> HN-F Socket0 CMN 的 CCG <==CXL 2.x==> Socket1
 SF 目录跨片延伸(两片的 SF 合成     CXL.cache: 远端可缓存本片内存,
 全局目录); 一致延迟最高但语义完整   背失效(BI)通道负责"对方改了要撤"
 代表(公开资料): Marvell CCPI,      CMN-700 有 CCG/CXL 寄存器组(TRM
 华为 Kunpeng 多路 HIS              4.1.7)——Arm 官方路线

 方案c: 非一致 NUMA
 远端内存走 CXL.mem(Type3)/PCIe, CPU 不缓存远端行(或仅点对点);
 "一致性"退化为软件层的 NUMA 纪律(页只属一个 socket)
```

- AGI CPU 的机架形态（>45000 核/机架，公开资料）必然多片协同，但**选哪条路未公开**——本文按 Arm 生态谱系示意；
- **内核视角**：跨 socket 在 Linux 里只有 NUMA 距离（SRAT/SLIT），硬件是否真一致 kernel 并不区分；方案 a/b 下远端内存页可以正常 cache，方案 c 下远端访问天然慢；
- 与 9996 对照：AMD 用 **xGMI/UPI 类 socket 间一致链路**（IOD-IOD 直连），9996 双路时 SF/探针语义由 IOD 侧扩展到对端——同样是"方案a"思路。

## 五、原子指令实现：两级监视器 + 三条路径（重点）

### 5.1 先搞清"独占监视器"：原子性的基石

```
 两级监视器(架构概念, 各司其职):

 [本地监视器] 每核一个, 纯核内电路
   V3 TRM §7.4 原文: "internal exclusive monitor with a
   2-state, open and exclusive state machine that manages
   Load-Exclusive and Store-Exclusive accesses and Clear-Exclusive"
   LDXR -> Open 变 Exclusive(记 reservation)
   STXR 成功/失败 都回 Open; CLREX 显式清(指令编码见
   insn.h:435)

 [全局监视器] 在一致域边界(HN-F/SF 处), 管 Shareable 内存
   LDXR(Inner/Outer Shareable) -> 请求到达 HN-F, SF 给该行
   打"被监视"标记; 他核对监视行的写入会使标记失效 ->
   STXR 必败  ==> 独占语义跨核成立
```

### 5.2 三条原子路径总览

```
 __________________________________________________________________
 路径A LL/SC:  LDXR x0,[x]; ...; STXR w1,x0,[x]; CBNZ 重试
   依赖: 本地监视器 + 全局监视器(SF 打标)
   独占窗口内任何他核写入 -> STXR 失败 -> 整段重来
   atomic_ll_sc.h:20 注释原文: "We use load exclusive and
   store exclusive to ensure that these are atomic. We may loop"
 __________________________________________________________________
 路径B LSE:   LDADD/LDCLR/LDEOR/LDSET/LDS[MU][MAX|MIN]/
              CAS/CASP(128位)/SWP (+ A/L/AL 语义后缀 =
              acquire/release 变体)
   一条指令, 无重试循环; 内核启动按 HAS_LSE_ATOMICS
   (cpucaps:48) 用 alternatives 把 LL/SC 实现补丁成 LSE
   (atomic_lse.h:62 ATOMIC_FETCH_OPS(add, ldadd))
 __________________________________________________________________
 路径C CHI硬件原子: 核把 Atomic 事务发到 HN-F, 由 HN 在
   SLC/内存处完成 RMW (CMN-700 §3.9.1 Atomics;
   "Enhanced Exclusive transactions"/原子缓冲 NUM_ATOMIC_BUF)
   V3 侧出现的事务名(TRM): AtomicLd / AtomicCAS / AtomicSwap
 __________________________________________________________________
 关键: LSE 指令"走哪条路"是微架构决定 ——
   - 行已在本地缓存(独占): 核内直接 RMW, 最快
   - 行不在/争用: 发 CHI Atomic 给 HN-F (下面的图)
```

### 5.3 争用场景：LSE 原子 offload 到 HN-F（图）

```
 32 个核同时 LDADDAL x1, x2, [lock]  (同一地址!)
 core42 |                                   core135 | ...
    |  L2 miss, 不取行不抢独占                      |
    +-> AtomicAdd(payload=x1) --哈希路由--> HN-F #k
                                                  |
                              PoS 定序: 32 个 Atomic 排队
                              (同址事务全片唯一定序点!)
                                                  |
                              每个 Atomic 在 HN 内:
                                读旧值(SLC 命中? 否则 SN/DDR)
                                RMW(NUM_ATOMIC_BUF 缓冲)
                                AtomicFetch 语义: 旧值返回给核
                                提交: 更新 SLC 行
    v                                           v
 core42 拿到旧值, 32 次原子全部串行正确       (示意)
 亮点: 全程没有任何核"持有"该 cache line —— 没有失效风暴
       对比: 若用 LDXR/STXR, 32 核互踢独占权, 探针风暴+重试
```

### 5.4 LL/SC 失败细节（为什么它在大机器上失宠）

```
 core42: LDXR x0,[X]  --ReadUnique倾向--> {core42:UC} + SF 打"监视"标
                                    ......
 core7 : 写 X --> HN-F#k --> SnpUnique -> core42 失效
         同时 SF 清除"X 被core42监视"标记
                                    ......
 core42: STXR w1,x0,[X] -> 全局监视器无标记 => 必败(w1=1)
         CBNZ 回 LDXR 重来   [争用越凶, 活锁越像, 吞吐越差]
 对策: 内核一律优先 LSE(启动期补丁); 用户态编译器 -march 至少
       armv8.1-a 生成 LSE
```

### 5.5 内存序与屏障（原子的"另一半"）

```
 弱序核心(V3 乱序) + 多核 = 需要显式定序工具:

 全屏障:   DSB (dsb sy / ish ...)   完成屏障, 最重
 双向屏障: DMB (barrier.h:28 一行宏) 挡住前后重排
   域 x 方向组合:  osh/nsh/ish  x  (空)/ld/st
     dmb ish   -- 全片一致域全屏障 (内核 SMP 最常用)
     dmb ishst -- 只约束 store
 单向屏障: LDAR/STLR (acquire/release, 免 DMB 的高效形式)
     STLR: 之前的写在它之前对外可见 (release)
     LDAR: 之后的访问不提前 (acquire)
     LDAPR (FEAT_LRCPC): 更弱的 acquire, 免不必要的 store 排队
 指令流同步: ISB (上下文/指令流改变后)
 一致域=屏障域: Inner Shareable 的边界就是 SF 覆盖的全片
   (页表 SH 位 ↔ dmb ish 互相咬合; Device 内存按 Outer 处理, V3 表)
```

## 六、调度域映射（速览，详见 001 §2.7）

```
 AGI (SP113012, 单 NUMA 固件形态, 示意) 的域链:

 rq(cpuN) --> [MC 域: span=0-135, 全片 SLC] --> NULL
              flags: SD_SHARE_LLC|BALANCE_*|WAKE_AFFINE
   SMT 层: 无(SMT 兄弟不存在)          CLS 层: 单核簇, 退化删除
   PKG/NODE: MC span==cpu_map -> 构建循环 break, 未构建(topology.c:2688)

 调度组环链: MC 域 136 组, 每组 1 CPU (sg->cores=1)
 sd_llc = MC = 全片; sd_llc_size = 136
```

一致性/原子性与调度的交汇点：

- **任意两核 `cpus_share_cache()` 恒真**（全片一个 LLC）→ wake_affine 的缓存判据不设墙，只受 mesh 跳数/负载影响（示意）；
- **任务迁移永不丢 L3**（对比 9996 跨 CCX 全冷）——代价是争用剧烈时 SLC/SF 成为全片热点；
- 无 SMT → `SD_SHARE_CPUCAPACITY` 不存在，调度器无需"整核优先"启发式；
- 高频原子计数器（如记账）在 AGI 上走 CHI 原子集中到 HN-F——若落在少数 HN-F 切片，**热点会沿地址哈希集中**（数据结构按每 CPU 切分仍是最佳实践，如 percpu counter）。

## Q&A

**Q1：为什么 AGI 不用 DSU-120 的簇级 SCU 做一致性？**
V3 "Direct connect only"（TRM）：每个核直连 mesh，把簇内小目录（DSU SCU）这一层整个拿掉，一致性统一交给 HN-F 的 SF——136 核一片域，软件不用再区分"簇内/簇外"（对比 A725/A520 的 DSU 簇模型与 9996 的 CCX 墙）。

**Q2：LSE 原子一定比 LL/SC 快吗？**
无争用时两者都一两次往返；**争用时差距拉开**——LL/SC 的独占窗口反复被打破要整段重试，LSE/CHI 原子在 HN-F 的 PoS 排队定序，一次事务必然完成。内核因此对一切 atomic_* 优先打 LSE 补丁。

**Q3：SLC 的 "exclusive 分配" 是什么意思？**
SLC 默认只收核逐出的行（victim，与核缓存不重复=exclusive）；当 SF 检测到多个核共享同一行时改为 pseudo-inclusive（SLC 也留副本），让后续探针/转发在 SLC 内闭合，少去 DDR（CMN-700 TRM 原文）。

**Q4：.Inner Shareable 的边界在哪？**
= SF 目录覆盖的范围 = 全片（双 chiplet 含在内，跨 die 链路承载 CHI 事务，示意）。页表里标 Inner-Shareable 的 normal memory 的 dmb ish 就以这个域为界。
