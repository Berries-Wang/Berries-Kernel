# EPYC 9996: CCX / CCD / DIE / 核心 层级架构与调度域映射

> 学习：本文是 [001.KERNEL_7.1.3.md](./001.KERNEL_7.1.3.md) 第三章的**展开与放大**——聚焦"物理层级每层共享什么"与"内核调度组/调度域如何逐层对应"。<br/>
> 源码：[000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3](../../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3)（下称 7.1.3）<br/>
> 平台事实：AMD EPYC 9996（第 6 代 EPYC 9006 旗舰，代号 "Venice"，Zen 6c，256C/512T，2026-07 上市）

## 摘要

|要点|说明|
|-|-|
|核心问题|9996 的 物理层级（线程→核→CCX→CCD/DIE→IOD→Socket）各自**共享什么资源**，内核又把每一层映射成哪个**调度域/调度组**|
|最关键的一条|**L3 的边界是 CCX，不是 CCD**——同 CCD 的两个 CCX 各有独立 64MB L3，跨 CCX 迁移 = L3 全冷，调度器"看不出"这两个 CCX 同属一个 CCD|
|第二关键|调度域不感知 CCD：域层次是 `SMT(2线程) → MC(=CCX, 32线程) → PKG/NODE/NUMA`，**没有 CCD 这一层**；CCD 只作为(示意上的)NPS 划分单位出现|
|源码依据|MC 域掩码 = `cpu_llc_shared_mask()`（smpboot.c:754）；LLC ID 由"共享 L3 的线程数"推导（cacheinfo.c:312 起注释原文）|
|退化两条|CLS 域掩码=L2 掩码==SMT 掩码 → 单组退化删除；NPS1 下 PKG span==cpu_map → 构建循环 break，NODE/NUMA 未构建|

**数量速查表**：

|层级|数量|每层包含|共享资源（同层内部）|
|-|-|-|-|
|Socket（封装）|1|2 IOD + 8 CCD|整个封装的供电/散热/Infinity Fabric|
|IOD（I/O 裸片）|2|8×DDR5 通道、PCIe 6.0、SMU|内存控制器、Fabric 仲裁（跨 IOD 访存经 IOD-IOD 互连，示意）|
|CCD（计算裸片 = DIE）|8|2×CCX|**只共享裸片供电与片内互连——不共享 L3**|
|CCX（核心复合体）|16|16 核 + 64MB L3|**L3（LLC）**：16 核共享，一致域；核心间探针在 CCX 内部完成|

|SMT 线程（逻辑 CPU）|512|—|无（是最小调度单位）|

> 注意：DIE 在 9996 上有两种物理形态——**CCD（计算 DIE）**与 **IOD（I/O DIE）**。下文"DIE"如无特指即 CCD。

## 二、逐层详解：每一层共享什么、不共享什么

### 2.1 SMT 线程层（512 个逻辑 CPU）

```
        一个物理核 (Zen 6c)
 +---------------------------------------------+
 |  Thread0 (CPUx)      Thread1 (CPUx+256)     |
 |  +---------+        +---------+             |
 |  | 退出槽/  |        | 退出槽/  |   <- 各自私有 |
 |  | 重命名资源|        | 重命名资源|             |
 |  +----+----+        +----+----+             |
 |       |    共享以下    |                     |
 |  +----v----------------v----+               |
 |  | 前端: 取指/解码/uop 缓存   |  <- 分时共享   |
 |  | 执行单元: ALU/AGU/FPU/VEC |               |
 |  | L1i (32KB) + L1d (32KB)   |  <- 容量按惯例示意 |
 |  | L2 (约 1MB, 私有于核)      |               |
 |  +---------------------------+               |
 +---------------------------------------------+
   调度器视角: thread_sibling = {CPUx, CPUx+256} -> SMT 域
```

- **共享**：取指/解码前端、执行端口、L1、L2——同核两线程**互相争抢**这些资源，因此 SMT 对吞吐有益、对单线程延迟有害；
- 这正是 `SD_SHARE_CPUCAPACITY` 的物理含义：调度器把同核两线程视为"共享计算能力"，SMT 域的 `imbalance_pct=110`（sd_init，topology.c:1731）意味着**几乎不允许两线程间不均**——多一个任务就该往别核跑。

### 2.2 Core 核心层（256 核）

- 每核私有 L1i/L1d + 私有 L2（L2 容量按 Zen c 系惯例示意 ~1MB，以官方数据集为准）；
- 核心间**不共享** L1/L2；同 CCX 内核心通过 L3 交换数据（写回的脏行以 victim 方式落入 L3，供他核命中）。

### 2.3 CCX 层（16 个）——本文最重要的一层

```
                     一个 CCX (核心复合体)
     +----------------------------------------------------+
     |   16 个 Zen 6c 核, 每核 2 线程                     |
     |  core0   core1   core2  ......  core15             |
     |  |L1|L2| |L1|L2| |L1|L2|          |L1|L2|          |
     |  +--V-----+--V-----+--V----......---+--V------+    |
     |    |        |        |                  |     |    |
     |  +--v--------v--------v------------------v-----+   |
     |  |        L3 Cache: 64MB ( slices/ways )        |   |
     |  |  - 16 核共享, CCX 一致域 (探针在本层完成)      |   |
     |  |  - 作为各核 L2 的 victim/缓存后备              |   |
     |  +-----------------------------------------------+  |
     +----------------------------------------------------+
       出了 CCX: 走 Infinity Fabric -> 探针/取数跨 CCX,CCD,IOD
```

- **共享**：64MB L3 = CCX 内 16 核的公共后备缓存与一致域；核心间一致性探针在 CCX 内部即可完成，不过 Fabric；
- **调度意义**：L3 是 Linux 的 LLC——`cpu_llc_shared_mask` 的边界就是 CCX（32 线程），MC 域 = CCX；同 CCX 迁移任务 **L3 全保留**，只丢 L1/L2；
- L3 容量按 CCX 独享：9996 全片 16 CCX × 64MB = 1GB，**不存在跨 CCX 的"共享 L3"**。

### 2.4 CCD 层（8 个 DIE）——最容易误解的一层

```
                一个 CCD (计算裸片)
     +-----------------------------------------+
     |   CCX0                CCX1               |
     | +-----------+      +-----------+         |
     | | 16核      |      | 16核      |         |
     | | 64MB L3(a)|      | 64MB L3(b)|   <-- 两块独立 L3!
     | +-----+-----+      +-----+-----+         |
     |       |   片内互连(示意 GCI)  |           |
     |       +--------+  +---------+            |
     |                |  |                     |
     +----------------|--+---------------------+
                      v  v
                GMI 链路 -> IOD
```

- **共享**：仅裸片级供电、时序域与片内互连；
- **不共享 L3**：同 CCD 的 CCX0/CCX1 各有 64MB，互不透明——CCX0 的核要读 CCX1 缓存的行，一样要过片内互连发起跨 CCX 探针；
- **调度器视角：CCD 这一层在调度域里不存在**。MC(LLC)=CCX、PKG/NODE=NUMA 节点（NPS4 下 1 节点=2 CCD），没有任何域的边界恰好好等于 CCD——"同 CCD"这个概念对调度器**不可见**，跨 CCX（哪怕同 CCD）与跨 CCD 迁移同样都是 L3 全冷；
- Zen3~Zen5（每 CCD 单一 CCX）"MC=CCD"的旧直觉在 9996 上**失效**，这是 9996 拓扑最大的认知更新点。

### 2.5 IOD 层（2 颗）

- Infinity Fabric（片间一致互连的总枢纽）+ 2×8=16 通道 DDR5-8800 + PCIe 6.0 + SMU（频压管理固件）；
- CCD 经 GMI 链路接 IOD（条数/挂接关系为示意图）；访问远端 CCX / 内存控制器都要经过 IOD 仲裁；
- **SMU 在这里**：amd-pstate 写入的 CPPC 请求最终由 SMU 落实为频压（详见 [../005.绿色节能调度器/README.md](../005.绿色节能调度器/README.md)）。

### 2.6 Socket 与 NPS（NUMA Per Socket，按 AMD 惯例推断，示意）

```
 NPS1: 1 个 NUMA 节点                NPS4: 4 个 NUMA 节点(每节点 2 CCD)
 +---------------------------+      +----------+----------+----------+----------+
 | NODE0: 8 CCD, 16 通道交错 |      | NODE0    | NODE1    | NODE2    | NODE3    |
 | (全片统一编址)            |      | CCD0,1   | CCD2,3   | CCD4,5   | CCD6,7   |
 +---------------------------+      | 4 通道   | 4 通道   | 4 通道   | 4 通道   |
                                    +----------+----------+----------+----------+
   NPS1 域链: SMT→CLS(退化)→MC→PKG(=全片)      NPS4 域链: SMT→MC→NODE→NUMA
   (NODE/NUMA 未构建: break)                    (PKG 项被 smpboot.c 清零)
```

## 三、"同层共享什么"速查总表（本文核心）

|迁移目标层级|丢了什么（本地不再热）|保住什么（仍然共享）|域内均衡代价|
|-|-|-|-|
|同核另一线程（SMT 域内）|无（L1/L2/执行单元本来就共享）|一切|最低（imbalance_pct=110，基本不许不均）|
|同 CCX 另一核（MC 域内）|L1、L2|**L3 全热**|低（imbalance_pct=117，cache_nice_tries=1）|
|同 CCD 另一 CCX|L1、L2、**L3 全冷**|仅同一裸片（调度器不可见）|≈跨 CCD，走 PKG/NODE 层均衡|
|跨 CCD（同 NUMA 节点，NPS4）|L1、L2、L3|同一节点内存/Fabric 端口组|中（跨 GMI 链路探针/取数）|
|跨 NUMA 节点（NPS4）|以上全部|仅统一编址|高（远端内存，SLIT 距离示意 12/14）|
|跨 Socket（多路）|以上全部|—|最高（IOD-IOD 互连）|

> 记忆法：**"往下迁=只丢私有缓存；横跨 CCX=丢掉最后一个共享层"**。L3 是 9996 上最后一堵"缓存墙"，墙的砖缝在 CCX 边界。

## 四、一次跨 CCX 读的完整路径（ASCII 流程图）

```
 [CCX0.core3 上的线程] 要读 addr X (X 被 CCX1.core7 的 L2 缓存, dirty)
 |
 v
 L1d miss? --> L2 miss? --> 查本 CCX L3 (64MB) ---miss---+
                                                        |
                                                        v
                                            出 CCX0, 上 Infinity Fabric
                                                        |
                              +-------------------------v-------------------+
                              | IOD: 地址哈希定位 X 的 Home/内存控制器 (示意) |
                              +------------+-------------------------------+
                                           |  发起对 CCX1 的探针 (probe)
                                           v
                              CCX1 L3 命中 X (其核 L2 的后备)
                                           |
                              <============v===============>
                                返回数据 + 一致性处理 (失效/转发)
                                           |
                                           v
                              回到 CCX0.core3 的 L1/L2 (局部化)
 全程: 2 次过 Fabric(去 + 回), 与访问 DDR 同量级延迟(示意)
 ==> 这就是 wake_affine()/select_idle_sibling() 坚持"不跨 sd_llc 放置"的物理动因
```

### 5.2 关键掩码函数（决定每层域的 span）

```c
// arch/x86/kernel/smpboot.c:754
const struct cpumask *cpu_coregroup_mask(int cpu)
{
	return cpu_llc_shared_mask(cpu);   // MC 域 = 共享 L3 的线程 = CCX = 32 线程
}

// arch/x86/kernel/smpboot.c:759
const struct cpumask *cpu_clustergroup_mask(int cpu)
{
	return cpu_l2c_shared_mask(cpu);   // CLS 域 = 共享 L2 的线程 = 同核 2 线程
}                                        //    == SMT 掩码 -> CLS 退化(见 §六)
```

### 5.3 层级标志（sd_init，topology.c:1660 起）

|域|掩码来源|9996 上的 span|flags（7.1.3）|关键参数|
|-|-|-|-|-|
|SMT|`cpu_smt_mask`（thread_sibling）|2 线程|`SD_SHARE_CPUCAPACITY \| SD_SHARE_LLC`|imbalance_pct=110|
|CLS|`cpu_clustergroup_mask`＝L2 掩码|2 线程(==SMT)|`SD_CLUSTER \| SD_SHARE_LLC`|（退化，不存活）|

|PKG|`cpu_node_mask`＝NUMA 节点|NPS1: 512 / NPS4: 项被清零|—（NPS1 存活为顶层）|cache_nice_tries=1, imbalance_pct=117|
|NODE/NUMA|`sd_numa_mask`（按 SLIT 档位）|NPS4: NODE=128, NUMA 层之上|`SD_NUMA`（仅 NUMA 层，NODE 无）|NODE: tries=1；NUMA: tries=2, imbalance_pct=117|

## 六、调度域映射：NPS1 / NPS4 完整域树（带调度组环链）

### 6.1 NPS1（单 NUMA 节点）

```
 每个 CPU 的域链(rq->sd 自底向上), 以 CPU0 (CCX0.core0.thread0) 为例:
 (线程编号: core k = 线程 k 与 k+256, 与 001 图 b-1 同; 实际取决于固件 MADT 顺序)

 rq(cpu0) -> [SMT 域] -> [MC 域] -> [PKG 域] -> NULL
              span={0,256} span=0-15,   span=0-511(=cpu_map)
                             256-271    ^ 构建循环在此 break(topology.c:2688)
                             (CCX0)     NODE 层虽被无条件追加(:2132)但从未构建
 flags: SHARE_CPUCAPACITY|  SHARE_LLC|     BALANCE_*|PREFER_SIBLING
        SHARE_LLC          BALANCE_*|
                            WAKE_AFFINE

 域间关系(父子): SMT 是 MC 的"孩子", MC 是 PKG 的孩子; CCD 无域!

 退化记录:
  CLS: L2 掩码 == SMT 掩码 -> CLS 只有 1 个组 -> sd_parent_degenerate() 判死
  (条件④⑤⑥: span 相同+单组豁免组标志+标志子集, 见 001 文档 §五)
```

### 6.2 NPS4（每 NUMA 节点 2 CCD，按惯例推断）

```
 以 CPU0 为例: (线程编号同上: core k = k 与 k+256; node0 = 64c = 线程 0-63,256-319)

 rq(cpu0) -> [SMT {0,256}] -> [MC CCX0 0-15,256-271] -> [NODE 0-63,256-319] -> [NUMA-1 0-127,256-383] -> [NUMA-2 0-511]
                                                       (2 CCD=4 CCX)       (2 节点)                  (全片)
   PKG: x86_topology[] 中被 build_sched_topology() 清零(smpboot.c:495)
        -> "包内 NUMA 由 NODE/NUMA 层接管" (注释原文意)
   NUMA 域用 build_overlap_sched_groups()(topology.c:1042): 同层各节点的
        "近邻掩码"视角不同 -> 组可重叠(对称 SLIT 也如此, 内核注释的直径 3
        例子即对称); NODE 层无 SD_NUMA, 仍走 build_sched_groups()(互斥组)
   (SLIT 示意 {10,12,14}: 12=相邻节点对, 14=对角 -> 两层 NUMA; 001 图 b-2
    为全互联 {10,12}, 故只有一层 NUMA — 两种都是合法形态)

 CCX/CCD 在域链中的位置(不存在!):
   CCD0{CCX0,CCX1} ... CCD7{CCX14,CCX15}
        ^^^^^^ 没有任何域边界沿 CCD 划分:
        - MC 按 L3(=CCX) 切
        - NODE 按 NPS(=2 CCD) 切, 但那是内存交错域, 不是 CCD 缓存域
```

### 6.3 每层域的调度组环形链表（sched_group, sched.h:2203）

```
 SMT 域 (span=2):   {0} -> {256} -> (环回)    [2 组, 每组 1 线程]
     (SMT 域整体又是 MC 域的一个组, 那个组 sg->span={0,256}; 见下行 MC 域)

 MC 域 (span=32):   组 = 每个子域(SMT 对)一组  [16 组] 每组 sg->span=2 线程
     {0,256} -> {1,257} -> {2,258} -> ... -> {15,271} -> (环回)
     sg->cores = 1   (物理核数; init_sched_groups_capacity, topology.c:1298
                       会剔除 SMT 兄弟再计数)

 PKG 域 (NPS1, span=512): 组 = 每个子域(MC=CCX)一组 [16 组] 每组 32 线程
     CCX0{0-15,256-271} -> CCX1{16-31,272-287} -> ... -> CCX15{240-255,496-511} -> (环回)
     sgc->capacity 修正后 = 32*1024/组(同构)  [get_group(), topology.c:1238]

 NODE 域 (NPS4, span=128): 组 = 每 MC 一组 [4 组: CCX0..CCX3], 互斥组(build_sched_groups)
 NUMA-1 域 (span=256): overlap 组(build_overlap_sched_groups), 对端节点整体作为一个(可重叠)组
```

> 组是**负载均衡的最小搬运单位**：均衡器在 MC 域内只会在"组"(=SMT 对)之间挪任务；在 PKG 域内则在 CCX 之间挪。

## 七、调度器的消费视角：谁在读这套层级

|消费者|读什么|在 9996 上的行为|
|-|-|-|
|周期/空闲负载均衡|逐层 `rq->sd` 向上找最闲组|同 CCX 先平衡 → 仍不均才跨 CCX(MC 内 16 组比) → 再上 PKG/NUMA|
|wake_affine()（fair.c:7670）|`cpus_share_cache(this, prev)`＝是否同 LLC|同 CCX 才有"affine 收益"；跨 CCX 直接放弃 affine|
|select_idle_sibling()（fair.c:8092）|`sd_llc`/`sd_llc_size`（update_top_cache_domain, topology.c:676）|**只在 32 线程的 CCX 内找空闲核**，从不跨 CCX 扫描|
|select_idle_core|`SD_SHARE_CPUCAPACITY` 层的整核空闲判断|整核(2 线程全闲)优先，避免 SMT 争抢|
|fork/exec 均衡|`SD_BALANCE_FORK/EXEC`|新任务优先落同 CCX 空闲核|
|能耗路径|`sched_energy_present`|9996 无 EM、SMT2、同构 → EAS 不启用（三重原因见 EAS 文档）|
|cpufreq(amd-pstate)|policy 与频域|每逻辑核一个 policy（cpufreq.c 初始单 CPU），实际频压由 IOD 的 SMU 在硬件侧协调（示意）|

## 八、频域补充：层级之外的另一个"域"

```
 调度域(缓存拓扑) 与 频压域(供电拓扑) 是两套体系:

 调度域:  SMT(2) -> MC/CCX(32) -> PKG/NODE ...      [由 CPUID/L3 推导]
 频压域:  每逻辑核一个 cpufreq policy -> 请求 CPPC(min/des/max/EPP)
          -> MSR_AMD_CPPC_REQ -> IOD 的 SMU 统一裁决实际 V/F(硬件协调, 示意)

 即: Linux 侧没有"每 CCX 一个 policy"这样的域; SMU 才知道真正的供电划分。
 调度器通过 util(PELT) 给出"要多少算力", SMU 决定"给哪个簇多少伏多少兆"。
```

## Q&A

**Q1：任务从 CCX0 迁到同 CCD 的 CCX1，缓存代价为什么和跨 CCD 一样？**
因为 9996 的两块 L3 是 CCX 各自私有的（§2.4），CCX0 的 L3 内容对 CCX1 完全不可见；调度器的 LLC 判据 `cpu_llc_shared_mask` 也只认 CCX——物理与内核口径一致：**"同 CCD"在缓存与调度两个层面都不存在共享**。

**Q2：为什么 NPS4 下没有 PKG 域？**
`build_sched_topology()`（smpboot.c:483）检测 `topology_num_nodes_per_package() > 1` 即把 PKG 项从 `x86_topology[]` 清零（:495）——包内已有 NODE/NUMA 层按 SLIT 划分，PKG 冗余。

**Q3：SMT 域为什么"几乎不许不均"？**
同核两线程共享执行端口与 L1/L2（§2.1），堆在一起只有争抢没有并行收益，因此 SMT 域 `imbalance_pct=110`（topology.c:1731）：负载比 1.1:1 就触发迁移。

**Q4：MC 域内的调度组是核还是线程？**
组 = 子域 span = **SMT 对**（2 线程一组，`sg->cores=1`）；均衡把任务在"核"间搬运，倾向先占空闲整核（select_idle_core），必要时才同核双线程。

## 附录 A：Chiplet（芯粒）详解

### A.1 是什么：把一颗大芯片"化整为零"

**Chiplet（芯粒）** = 把传统上整片流片的 SoC，按功能**切成多颗小裸片（die）**，每颗 die 独立流片、独立测试，最后在**封装内**通过高速互连拼成一颗完整芯片。9996 的 8 颗 CCD + 2 颗 IOD 就是 10 颗 chiplet 的组合。

```
 传统 Monolithic(整片)                Chiplet(芯粒组合)
 (如手机 SoC / A725 类单 die SoC)      (如 EPYC 9996 / Arm AGI CPU)

 +---------------------------+        +------+ +------+ +------+
 |      一颗 500~800mm²       |        |CCD0  | |CCD1  | | ...  |  <- 小 die
 |      大裸片一次流片        |        |(计算)| |(计算)| |      |     各自流片/测试
 |  CPU | GPU | 内存PHY | IO  |        +--+---+ +--+---+ +------+        |
 |      |     |         |     |           |        |       |             v
 +---------------------------+        +--+--------+-------+---------+  封装内互连
                                      |        IOD(Fabric/MC/IO)   |  (基板走线/
                                      +--------------------------+   中介层/TSV)
 "良率随面积暴跌, 工艺只能一刀切"      "小 die 良率高, 各 die 可用不同工艺"
```

### A.2 为什么：良率与成本的数学（示意计算）

晶圆缺陷近似随机分布，良率随 die 面积**指数级下降**（Poisson 模型示意：`Y ≈ e^(-D·A)`，D=缺陷密度）：

```
 良率                                        同一片 300mm 晶圆(面积约 70700mm²,
 100%|                                      忽略边缘损失, 示意):
     |*                                     - 1 颗 800mm² 大 die:
  90%|   *                                    数量 ≈ 88, 良率 e^(-0.8) ≈ 45%
     |      *                                 => 好 die ≈ 40 颗
  70%|         *
     |            *                         - 8 颗 100mm² 小 die(CCD 规模):
  50%|   (800mm²在此)-----*                   每片晶圆可切 ≈ 707 颗/die,
     |                    *      *            良率 e^(-0.1) ≈ 90%
  30%|                          *   *         => 8 die 合计好 die 数量级百倍于大 die
     |                               *   *
   0%+----+----+----+----+----+----+--->     D=0.1 缺陷/cm² 示意(先进工艺
      100  200  300  400  500  600  800        节点量级), 数字仅示比例
                die 面积 (mm²)
```

> 一句话：**缺陷是按面积收税的，chiplet 把一块大税基拆成十块小税基**。再算上"坏一颗 die 只扔一颗"（KGD, Known-Good-Die：先测好每颗 die 再封装），成本优势进一步放大。

### A.3 其他四个收益

|收益|在 9996 上的体现|
|-|-|
|**工艺混搭**：计算 die 冲最先进制程；I/O die 用成熟工艺（SerDes/模拟电路在老工艺反而更好做）|Zen 6c 的 CCD 用 TSMC N2 冲密度，IOD 用成熟工艺做 16 通道 DDR5 / PCIe 6.0|
|**SKU 派生**：增减 chiplet 即得新型号，不必重新流片|EPYC 9006 一个封装平台派生 31 款 SKU（8 核～256 核，靠屏蔽/裁剪 CCD 实现）|
|**上市速度**：小 die 设计验证周期短，历代可部分复用|EPYC 历代 IOD/CCD 的迭代节奏解耦|
|**良品率救险**：局部缺陷屏蔽成低端 SKU 出售|业界通行做法（示意）|

### A.4 代价：天下没有免费的午餐

- **跨 die 延迟与功耗**：访问"隔壁 die 的缓存/内存"要过 die 间互连（如 GMI），延迟/功耗比 die 内互连高——这是 §2.4"两个 CCX 各自 L3"代价的放大版；
- **封装成本**：多 die 封装需要更精密的基板/中介层/TSV，先进封装本身是大投资；
- **软件复杂度**：硬件不再是"均匀一块"，OS 要靠 CPUID/PPTT 才能发现真实拓扑（本文 §五）；调度器若无视 die 边界，会吃跨 die 互连的暗亏（9996 的"CCD 不可见"正是此问题）；
- **测试复杂度**：KGD 预筛 + 封装后联测两套流程。

### A.5 AMD 服务器 chiplet 谱系（2019 起，公开资料）

|代|年份|结构|核心规模|
|-|-|-|-|
|Rome（Zen 2）|2019|1 IOD(14nm) + 最多 8 CCD(7nm)，每 CCD 2 CCX×4 核|64C（**首颗服务器 chiplet CPU**）|
|Milan（Zen 3）|2021|1 IOD + 8 CCD，**每 CCD 单 CCX**（L3 域=CCD）|64C|
|Genoa（Zen 4）|2022|1 IOD(6nm) + 12 CCD(5nm)，每 CCD 单 CCX|96C|
|Bergamo（Zen 4c）|2023|8 CCD×16 核（Zen 4c 密度核）|128C|
|Turin / 9005（Zen 5/5c）|2024|12 CCD（标准核）；密度核扩展|最高 256C（公开报道）|
|**Venice / 9006（Zen 6c）**|2026|**2 IOD + 8 CCD，每 CCD 2 CCX×16 核（切回双 CCX！）**|**256C（= EPYC 9996）**|

> 历史位置：Zen 3~5 让"每 CCD 单 CCX"维持了三代，**Zen 6c 又把 CCD 切回两个 CCX**——"L3 边界"从 CCD 缩回 CCX，这正是本文 §2.4"MC=CCX 而非 CCD"故事的由来。

### A.6 die 间互连技术谱系（怎么"拼"起来）

```
 封装剖面(示意):                  互连方式从近到远:
                                 +-- 3D 堆叠(TSV 键合): AMD 3D V-Cache
   散热盖                          |   (L3 芯粒叠在 CCD 上, 微米级间距)
 +-------------+                 +-- 2.5D 中介层(interposer): Apple
 | [CCD] [CCD] |  <- die         |   UltraFusion(M Ultra 两颗拼一颗)
 |  ||GMI||    |                 +-- 有机基板走线(最常见; 9996 的 CCD-IOD
 +=============+  <- 基板/互连    |   GMI 即此类, 成本最低)
 |   [IOD]     |                 +-- 标准化: UCIe(2022, die 间互连的
 +-------------+                     行业标准 PHY+协议, 承载 PCIe/CXL/流式)
    PCB 引脚                      不同技术: 距离↑ 带宽密度↓ 成本↓
```

- **GMI**（Global Memory Interconnect）：AMD 的私有 die 间互连（xGMI 则是 socket 间）；9996 每 CCD 的 GMI 条数/挂接为示意（见 §一图注）；
- **UCIe**（Universal Chiplet Interconnect Express，2022）：把"chiplet 之间的接口"标准化，让不同厂商的 die 理论上可混搭——chiplet 从"厂商内部工艺"走向"开放生态"的关键一步。

### A.7 对照三平台

|平台|封装形态|die 间互连|内核如何感知|
|-|-|-|-|
|**EPYC 9996**|10 颗 chiplet（8 CCD+2 IOD）|GMI（私有）|CCD **不可见**；按 L3 推出 MC=CCX；die 只在（示意上的）NPS 划分里间接出现|
|**Arm AGI CPU（SP113012）**|双 chiplet（每 die ~68 核，示意）|跨 die 链路延续一致性（CHI 跨 die，示意）|同样**不感知 die**：MC=全片 SLC；固件可选把 chiplet 映射成 NUMA 节点|
|**Cortex-A725/A520 SoC（单 die）**|monolithic|无|传统小系统：MC=LLC 即接近全片|
|（参考）Apple M Ultra|2 颗 die 经 interposer 拼接|UltraFusion（2.5D）|呈现为单一致域（示意）|

### A.8 内核视角一句话

**chiplet 是封装/成本概念，不是调度域概念**：内核从不解析"die 编号"来建域——它只看两件事：① 谁共享缓存（CPUID/PPTT → LLC/L2 掩码）；② 谁共享内存节点（SRAT/SLIT → NUMA）。die 只有被固件"翻译"成这两种共享关系之一，才会间接出现在调度域里。9996 的教训（§2.4）：**die 与 LLC 边界错位时，调度器"看见"的比硬件"封装"的更细**。
