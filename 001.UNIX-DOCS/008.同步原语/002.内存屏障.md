## 0. 一句话总结

**缓存一致性只保证"对同一个地址，所有观察者看到相同的写入顺序"；跨地址的可见顺序没有任何保证——屏障就是把"跨地址顺序"补上的指令。** arm64 给了三档：`DMB`（保证屏障前后的访存**顺序**，不保证完成）、`DSB`（在顺序之上再保证**完成**）、`ISB`（**上下文同步**：之后的指令重新取指，让之前的系统寄存器/TLB 写入生效）；以及第四种现代形态——**单向屏障 `LDAR`/`STLR`**，把 acquire/release 语义直接焊进访存指令，内核的 `smp_store_release()`/`smp_load_acquire()` 在 arm64 上就是它们。

## 1. 问题：没有屏障，顺序会错成什么样

### 1.1 经典消息传递（Message Passing）litmus

生产者写数据、再立标志；消费者看到标志、再读数据——这是内核里最普遍的同步形状（就绪标志、引用计数发布、RCU、锁的 locked 字段……）：

```
CPU0（生产者）                          CPU1（消费者）
─────────────                          ─────────────
data = 42;        // 普通 store         do { flag = READ_ONCE(f); }
f = 1;            // 普通 store         } while (flag == 0);
                                        d = data;    // 普通 load
问：CPU1 看到 f==1 之后，d 一定 == 42 吗？
答：不保证。架构允许 CPU1 读到 f==1 且 data 仍是旧值。
```

为什么错——两个独立地址（`data`、`f`）之间**没有任何架构保证**：

```
没有屏障时的可见顺序（示意）
──────────────────────────────────────────────────────────────
CPU0 视角(程序序)      CPU1 观察到的全局可见顺序（可能）
  ① str data=42  ──┐    ① str f=1      ← f 先可见
  ② str f=1     ──┘    ② ldr f==1      ← 消费者放行
                       ③ ldr data=旧值 ← ✗ 数据还没"到"
──────────────────────────────────────────────────────────────
缓存一致性（MESI）管的是"同一地址的多次写，所有核看到同一顺序"
（single-copy atomic，见 002.CAS §4.1 前提③）；
①②是两个地址——一致性协议不管跨地址顺序，
这是"有 MESI 为什么还要屏障"的答案。
```

### 1.2 修法：写侧 release + 读侧 acquire，配对出现

```
CPU0                                    CPU1
data = 42;
smp_store_release(&f, 1);              while (smp_load_acquire(&f) == 0)
                                          cpu_relax();          // 或 cmpwait
                                       d = data;   // ✓ 保证读到 42
```

配对规则（内核 memory-barriers.txt 的核心约定）：**release 之前的所有写，对 acquire 之后的读全部可见**。只加一侧不够——写侧 release 保证"data 先于 f 可见"，读侧 acquire 保证"看到 f 才允许后面的 data 读提前发生"。

## 2. 三条 CPU 屏障：DMB / DSB / ISB

ARM ARM B2.6 开篇就把屏障分成三类功能（B2-295）：

> "The memory barriers defined by the Arm architecture provide a range of functionality, including:
> • **Ordering** of load/store instructions.
> • **Completion** of load/store instructions.
> • **Context synchronization**."
>
> Arm 架构定义的内存屏障覆盖三类功能：访存指令的**排序**、访存指令的**完成**、**上下文同步**。

这三类正好对应三条指令，也对应内核里三组场景：

| | DMB（B2.6.2） | DSB（B2.6.9） | ISB（B2.6.1） |
| - | - | - | - |
| 管什么 | **顺序**：屏障前后的访存，观察序不乱 | **完成**：屏障前的访存全部完成后，DSB 才完成 | **取指**：之后的指令在 DSB 之后重新取指 |
| 堵谁 | 只堵**访存**（load/store + 缓存维护指令），不堵其他指令的执行 | 堵**一切**：DSB 之后的任何指令都要等 | 堵**流水线取指**：冲刷预取 |
| 代价 | 一道"重排墙" | 等待全部到达观察点（贵一个量级） | 流水线重启（最贵） |
| 内核典型 | `smp_mb/rmb/wmb`（dmb ish…） | `mb/rmb/wmb`（dsb sy…，MMIO）、TLB/缓存维护后 | 换页表基址 TTBR0/ASID 后、修 SCTLR 后 |
| 手册 | B2-295~296、C6-2157 | B2-298~300、C6-2160 | B2-295、C6-2195 |

关键原文各一句：

> **DMB**："The DMB instruction is a memory barrier instruction that ensures the relative order of memory accesses before the barrier with memory accesses after the barrier. The DMB instruction **does not ensure the completion** of any of the memory accesses for which it ensures relative order."（B2-296）
>
> DMB 保证屏障前后访存的**相对顺序**，但**不保证完成**。

> **DSB**："A DSB instruction is a memory barrier that ensures that memory accesses that occur before the DSB instruction **have completed before the completion of the DSB instruction**. In doing this, it **acts as a stronger barrier than a DMB** and all ordering that is created by a DMB with specific options is also generated by a DSB with the same options."（B2-298）
>
> DSB 保证之前的访存**先于 DSB 本身完成**——比 DMB 强，DMB 能建立的序 DSB 同参数都能。

> **ISB**："An ISB instruction ensures that all instructions that come after the ISB instruction in program order are **fetched from the cache or memory after the ISB instruction has completed**."（B2-295）
>
> ISB 之后的指令在 ISB 完成后才取指——"上下文改变"（改系统寄存器/TLB）之后的代码必须 ISB 才可靠。

三条屏障在流水线上的作用点：

```
        指令流水（一个 PE 的视角）
 ┌────────────────────────────────────────────────────────┐
 │  取指/预取 ──► 译码 ──► 乱序执行窗口 ──► 访存队列 ──► 提交/可见 │
 └────────────────────────────────────────────────────────┘
    ▲ ISB 在这里砍一刀               ▲ DMB 在这里立墙
    （之后的指令重新取，             （墙前墙后的访存不许乱序可见，
     预取作废——上下文                但墙内指令可以继续跑，
     切换语义生效）                   不等"完成"）
                              ▲ DSB 立墙且关门
                                （墙前访存全部"完成"才放行后面的指令）
   "完成" = 到达 ARM ARM 定义的观察点（PoP/PoC，对相应域的观察者可见）
```

### 2.1 DMB/DSB 的参数：域（domain）× 类型（types）

DMB/DSB 都带一个 `<option>` 参数，两位域 × 两位类型决定它管多宽（C6-2157 的 Decode 表）：

```
CRm<3:2> → 域（domain）                    CRm<1:0> → 类型（types）
  00 Outer Shareable (OSH)                   00 全系统+读写（= SY）
  01 Non-shareable  (NSH)                    01 只管读   (LD)
  10 Inner Shareable (ISH)  ← 内核 SMP 用     10 只管写   (ST)
  11 Full System     (SY)                    11 读写都管
```

拼出全部 12 个常用助记符（B2.6.10，B2-300）：

| 域 ↓ / 类型 → | 全 | 只读（LD） | 只写（ST） |
| - | - | - | - |
| Full System | `dmb sy` | `dmb ld` | `dmb st` |
| Outer Shareable | `dmb osh` | `dmb oshld` | `dmb oshst` |
| Inner Shareable | `dmb ish` | `dmb ishld` | `dmb ishst` |
| Non-shareable | `dmb nsh` | `dmb nshld` | `dmb nshst` |

> 域的定义（B2-300）：屏障参数指定"必须在哪个 shareability 域内生效"——Full system / Outer Shareable / Inner Shareable / Non-shareable。域选小了屏障"够不着"目标观察者，选大了白付代价。

**内核的选域逻辑**（一眼看懂 barrier.h 的三组映射）：

- **核间同步**（所有运行内核的 CPU = 一个 Inner Shareable 域）→ `dmb ish` 系；
- **与设备/DMA 打交道**（设备不属于任何 shareability 域，在 Inner Shareable 之外）→ `dmb osh` 系甚至 `dsb sy`；
- **MMIO 寄存器写入要"到达外设"**（完成，不只是顺序）→ `dsb`。

### 2.2 内核三组屏障宏：同一个文件里的三档火力

```c
// arch/arm64/include/asm/barrier.h:63
#define __mb()		dsb(sy)      // 全系统 + 完成语义：设备/体系结构级
#define __rmb()		dsb(ld)
#define __wmb()		dsb(st)

// arch/arm64/include/asm/barrier.h:67
#define __dma_mb()	dmb(osh)     // 与外设/DMA 的顺序：外域，不需要完成
#define __dma_rmb()	dmb(oshld)
#define __dma_wmb()	dmb(oshst)

// arch/arm64/include/asm/barrier.h:126
#define __smp_mb()	dmb(ish)     // 核间：Inner Shareable 就够
#define __smp_rmb()	dmb(ishld)
#define __smp_wmb()	dmb(ishst)
```

三组对照本身就是一条教学主线：**对象越"远"，域越大、屏障越强**——CPU 同伴（ish）→ 设备（osh）→ 全系统完成（dsb sy）。

## 3. 单向屏障：LDAR / STLR（把语义焊进访存指令）

### 3.1 双向墙 vs 单向闸

`dmb ish` 是**双向**墙：墙前墙后的访存互相不许乱。而很多同步场景只需要**单向**约束（release 只约束"之前"，acquire 只约束"之后"），arm64 为此提供了一族专用指令（B2.6.11，B2-301）：

> "Arm provides a set of instructions with **Acquire semantics for loads**, and **Release semantics for stores**. These instructions support the **Release Consistency sequentially consistent (RCsc)** model. In addition, **FEAT_LRCPC** provides Load-AcquirePC instructions. The combination of Load-AcquirePC and Store-Release can be use to support the weaker **Release Consistency processor consistent (RCpc)** model."
>
> Arm 提供带 acquire 语义的 load（LDAR）与 release 语义的 store（STLR），支持 RCsc 模型；FEAT_LRCPC 的 LDAPR 与 STLR 组合支持更弱的 RCpc 模型。

```
        DMB ISH（双向墙）                 STLR / LDAR（单向闸）
  str A          │  str B            str A                    str B
  str C          │  str D            STLR X ←─ 只约束它"之前"的 str A/C
  ───────────────┼────────────       ──────────────────────────────
  墙前{A,C} 与墙后{B,D}              release-store 之前的所有写，
  两两不许乱序可见                    不许排到 STLR 之后可见；
                                      STLR 之后的写不受约束（单向）
                                     LDAR X ←─ 只约束它"之后"的读
                                      acquire-load 之后的读不许提前
                                      （LDAR 自身的读必须先完成）
```

单向的好处：**读写各管一半，比成对的 DMB 便宜且语义更贴**——一次 release-store 同时完成"写变量 + 立半堵墙"，不需要再垫 `dmb ish`。

### 3.2 语义同族：四个层面说的是同一件事

| 层面 | acquire（之后的读不提前） | release（之前的写不落后） | 出处 |
| - | - | - | - |
| 裸指令 | `LDAR`（C6-2222） | `STLR`（C6-2660） | ARM ARM C6.2.191/401 |
| LL/SC 变体 | `LDAXR` | `STLXR` | [003.LLSC实现原理 §5](./001.原子指令/003.LLSC实现原理.md) |
| LSE 后缀 | `LDADDA`/`CASA`…（`A`） | `SWPL`/`CASAL` 的 `L` | [002.CAS §5](./001.原子指令/002.CAS实现原理.md)、[005 §3.5](./001.原子指令/005.LSE内核实现.md) |
| 内核 API | `smp_load_acquire()` | `smp_store_release()` | 本文 §3.3 |

（RCpc 一支：`LDAPR`/`LDAPRB`…与 STLR 配对放宽到 processor-consistent——内核目前主力仍是 RCsc 的 LDAR，一句带过。）

### 3.3 内核实现：`smp_store_release` = STLR，`smp_load_acquire` = LDAR

arm64 直接用单向屏障指令实现这对 API（[barrier.h:130](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)，4 种宽度各发射一条指令，节选 32/64 位两臂）：

```c
// arch/arm64/include/asm/barrier.h:130（节选：case 1/2 为 stlrb/stlrh，同形）
#define __smp_store_release(p, v)					\
do {									\
	typeof(p) __p = (p);						\
	union { __unqual_scalar_typeof(*p) __val; char __c[1]; } __u =	\
		{ .__val = (__force __unqual_scalar_typeof(*p)) (v) };	\
	compiletime_assert_atomic_type(*p);				\
	kasan_check_write(__p, sizeof(*p));				\
	switch (sizeof(*p)) {						\
	case 4:								\
		asm volatile ("stlr %w1, %0"				\
				: "=Q" (*__p)				\
				: "rZ" (*(__u32 *)__u.__c)		\
				: "memory");				\
		break;							\
	case 8:								\
		asm volatile ("stlr %x1, %0"				\
				: "=Q" (*__p)				\
				: "rZ" (*(__u64 *)__u.__c)		\
				: "memory");				\
		break;							\
	}								\
} while (0)

// arch/arm64/include/asm/barrier.h:165（节选：同理，ldarb/ldarh 略）
#define __smp_load_acquire(p)						\
({									\
	union { __unqual_scalar_typeof(*p) __val; char __c[1]; } __u;	\
	typeof(p) __p = (p);						\
	compiletime_assert_atomic_type(*p);				\
	kasan_check_read(__p, sizeof(*p));				\
	switch (sizeof(*p)) {						\
	case 4:								\
		asm volatile ("ldar %w0, %1"				\
			: "=r" (*(__u32 *)__u.__c)			\
			: "Q" (*__p) : "memory");			\
			break;						\
	case 8:								\
		asm volatile ("ldar %0, %1"				\
			: "=r" (*(__u64 *)__u.__c)			\
			: "Q" (*__p) : "memory");			\
			break;						\
	}								\
	(typeof(*p))__u.__val;						\
})
```

`compiletime_assert_atomic_type()` 挡掉非标量/非对齐原子宽度类型——release/acquire 只对"天然原子"的标量有意义。

分发链：体系结构无关层 [asm-generic/barrier.h:172](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/asm-generic/barrier.h) 把 arch 宏包上 KCSAN 检查；没有专用指令的架构退回"普通访存 + `__smp_mb()`"的通用拼法（asm-generic/barrier.h:139 的 `__smp_store_release` 回退实现）——arm64 因为有 STLR/LDAR 而走捷径：

```c
// include/asm-generic/barrier.h:172
#define smp_store_release(p, v) do { kcsan_release(); __smp_store_release(p, v); } while (0)
#define smp_load_acquire(p) __smp_load_acquire(p)          // :176
```

## 4. 编译器屏障与 READ_ONCE / WRITE_ONCE

CPU 屏障之前还有第一层坑：**编译器重排**。三层"乱序源"与各自的对策：

```
乱序源 ①  编译器（为优化调整指令顺序）
   对策：barrier() / volatile / READ_ONCE / WRITE_ONCE
乱序源 ②  CPU 乱序执行与访存队列（多核可见顺序）
   对策：DMB / LDAR / STLR（+ 原子指令的 A/L 后缀）
乱序源 ③  上下文改变（系统寄存器、TLB、代码补丁）取到旧指令
   对策：ISB
```

### 4.1 编译器屏障 barrier()

```c
// include/linux/compiler.h:85
# define barrier() __asm__ __volatile__("": : :"memory")
```

一条空内联汇编骗过编译器：`"memory"` clobber 声明"内存被神秘修改了"，编译器不得不把寄存器里缓存的值写回/作废、且**不许跨过它重排访存**。它**只管编译器**，不生成任何 CPU 指令——UP 内核里 `smp_mb()` 就编译成它（asm-generic/barrier.h:113 `#define smp_mb() barrier()`，单核没有核间可见性问题）。

### 4.2 READ_ONCE / WRITE_ONCE：给"每次访问"上锁

循环等标志为什么必须 READ_ONCE——否则编译器有权把循环里的读**提升到循环外**（读一次、缓存进寄存器），死循环就"看不见"别人写的 1：

```c
// include/asm-generic/rwonce.h:44
#define __READ_ONCE(x)	(*(const volatile __unqual_scalar_typeof(x) *)&(x))

// include/asm-generic/rwonce.h:47
#define READ_ONCE(x)							\
({									\
	compiletime_assert_rwonce_type(x);				\
	__READ_ONCE(x);							\
})

// include/asm-generic/rwonce.h:53
#define __WRITE_ONCE(x, val)						\
do {									\
	*(volatile typeof(x) *)&(x) = (val);				\
} while (0)
```

volatile 挡住"合并/提升"类优化，类型检查（`compiletime_assert_rwonce_type`）拒绝非标量/非对齐原子宽度——保证访问落在架构单拷贝原子范围内（见 [002.CAS §4.1](./001.原子指令/002.CAS实现原理.md) 的 B2-248）。**READ_ONCE 管"这一次读真的发生、读的是当下内存"，不管顺序**——顺序仍是 §2/§3 屏障的事，两者配合才完整。

## 5. 内核屏障 API 全景（arm64 映射，7.1.3 实测）

| 内核 API | arm64 展开 | 语义 | 何时用 |
| - | - | - | - |
| `barrier()` | 空 asm + memory clobber | 只挡编译器 | 纯编译器序（UP、per-CPU 数据） |
| `READ_ONCE/WRITE_ONCE` | volatile 访问 | 单次访问成真 + 防合并撕裂 | 任何被并发访问的共享标量 |
| `smp_mb()` | `dmb ish` | 核间全序（读写都管） | 少用——多数场景单向屏障够 |
| `smp_rmb()` | `dmb ishld` | 核间：读-读序 | acquire 不可用时的配对读 |
| `smp_wmb()` | `dmb ishst` | 核间：写-写序 | release 不可用时的配对写 |
| `smp_store_release()` | `stlr{,b,h}` | 单向：之前的写不落后 | 发布标志/版本号（首选） |
| `smp_load_acquire()` | `ldar{,b,h}` | 单向：之后的读不提前 | 消费标志/版本号（首选） |
| `smp_mb__before_atomic()` / `__after_atomic()` | `dmb ish` | 给 **relaxed** 原子操作前后补序 | `atomic_set`/`atomic_read`、`*_relaxed` 家族（asm-generic/barrier.h:164/168） |
| `mb()/rmb()/wmb()` | `dsb sy/ld/st` | 全系统 + 完成 | MMIO 寄存器序（barrier.h:63） |
| `dma_mb()/dma_rmb()/dma_wmb()` | `dmb osh…` | 外域（设备可见）顺序 | DMA 描述符 vs 数据（barrier.h:67） |
| `io_stop_wc()` | `dgh`（hint #6） | 阻止 Device-GRE/Normal-NC 访问合并 | relaxed MMIO 区结束（barrier.h:71） |
| `isb()` | `isb` | 上下文同步 | 改 TTBR/ASID/SCTLR 后（见 §6.3） |

选型树（按"对手是谁"走）：

```
对手是谁？
 ├─ 编译器 ……………………… barrier() / READ_ONCE / WRITE_ONCE
 ├─ 本核其他上下文（中断/抢占）… local_irq_save / preempt_disable（000 §4）
 ├─ 其他 CPU 核 …………………… smp_*（ish 域）
 │     ├─ 只要"发布/消费" ………… smp_store_release + smp_load_acquire（stlr/ldar）
 │     ├─ relaxed 原子周围 ……… smp_mb__{before,after}_atomic
 │     └─ 全序兜底 ………………… smp_mb
 ├─ 设备/DMA ……………………… dma_*（osh 域）；完成要求 → mb()（dsb sy）
 └─ 取指上下文 ……………………… isb()
```

## 6. 实战走读三例

### 6.1 消息传递的最终形态

§1.2 的修法在 arm64 上的落点——两边的 C 与指令形态：

```
CPU0                                   CPU1
data = 42;                             do {
WRITE_ONCE(data, 42);                      old = smp_load_acquire(&f);   // ldar
smp_store_release(&f, 1);  // stlr       } while (!old);
                                           d = READ_ONCE(data);          // ✓ 必见 42
等价指令序（arm64）：                     等价指令序：
  str  w0, [data]                          1: ldar w1, [f]
  stlr w1, [f]                                cbz  w1, 1b
                                              ldr  w2, [data]
```

### 6.2 自旋锁：acquire/release 的最大规模应用

 queued spinlock 的快慢路径就是"本篇 + [001.原子指令]"的合体（[qspinlock.h:107](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/asm-generic/qspinlock.h)）：

```c
// include/asm-generic/qspinlock.h:107
static __always_inline void queued_spin_lock(struct qspinlock *lock)
{
	int val = 0;

	if (likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL)))
		return;                        // 快路径 = CAS with acquire
	                                   //（LSE: casal/casa, 见 005 §4.1）
	queued_spin_lock_slowpath(lock, val);
}

// include/asm-generic/qspinlock.h:123
static __always_inline void queued_spin_unlock(struct qspinlock *lock)
{
	/*
	 * unlock() needs release semantics:
	 */
	smp_store_release(&lock->locked, 0);   // 慢路径之外的解锁 = 一条 stlr
}
```

为什么锁要这两个方向：**加锁 acquire**——临界区里的读不许提到锁前；**解锁 release**——临界区里的写不许落到锁后。§1 的 MP 配对在锁上被复用为"锁传递临界区的顺序"。

### 6.4 等待也可以省电：smp_cond_load

轮询循环的正确打开方式（[barrier.h:196](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)）——READ_ONCE + 条件 + `__cmpwait_relaxed`（WFE 睡等待，监视器事件唤醒，见 [003.LLSC实现原理 §4.7](./001.原子指令/003.LLSC实现原理.md)）：

```c
// arch/arm64/include/asm/barrier.h:196
#define smp_cond_load_relaxed(ptr, cond_expr)				\
({									\
	typeof(ptr) __PTR = (ptr);					\
	__unqual_scalar_typeof(*ptr) VAL;				\
	for (;;) {							\
		VAL = READ_ONCE(*__PTR);				\
		if (cond_expr)						\
			break;						\
		__cmpwait_relaxed(__PTR, VAL);				\
	}								\
	(typeof(*ptr))VAL;						\
})
```

acquire 变体（barrier.h:209）把 `READ_ONCE` 换成 `smp_load_acquire`——醒来读到目标值时顺便立起 acquire 半墙。

## 7. 常见误区

1. **"有 MESI/缓存一致性就不用屏障"**——错。一致性只约束**同一地址**的可见序；跨地址顺序（§1 的 data/f）屏障才管。
2. **"DMB 保证写完成"**——错，B2-296 原文明确 "does not ensure the completion"；要完成用 DSB（写设备寄存器后 `dsb sy` 才保证到达外设）。
3. **"单核内核不需要内存屏障"**——半对：核间屏障（`smp_*`）在 UP 编译成 `barrier()`，但**编译器屏障永远需要**，且中断/抢占上下文与线程之间的顺序仍要 READ_ONCE + 屏障配对（内核文档 memory-barriers.txt 对此有专门讨论）。
4. **"屏障域随便选大的更保险"**——`dmb sy` 代替 `dmb ish` 功能上没错但付全系统代价；选域要看观察者在哪个 shareability 域（内核核间 = ISH，设备 = OSH）。
5. **"smp_wmb() 之后加 smp_rmb() 就等于 acquire/release"**——方向反了配对就失效：MP 配对是**写侧 release（约束其之前）+ 读侧 acquire（约束其之后）**；单向屏障的"方向"就是它的语义本身（§3.1）。
6. **"READ_ONCE 能防 CPU 乱序"**——不能，它只管编译器层（§4.2）；顺序必须靠本篇的 CPU 屏障或单向屏障指令。
