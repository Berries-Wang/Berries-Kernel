## 0. 一句话总结

**内核把每个原子 API 编译成 LL/SC 和 LSE 两份实现，启动时读 `ID_AA64ISAR0_EL1.Atomic` 探测 CPU 是否有 FEAT_LSE，有则运行期把"选 LL/SC"的分支补丁成"选 LSE"——所以同一个 `atomic_add`，在 5.9 时代的老核上跑 `ldxr/add/stxr` 重试环，在 A725 这类新核上跑一条 `stadd`。** 选路不靠重新编译、不靠 if 慢分支，而靠两类启动期补丁：**分支变 NOP**（atomic/cmpxchg 走的 `alternative_has_cap_likely`）和**指令原地重写**（xchg/percpu 走的 `ARM64_LSE_ATOMIC_INSN`）。

## 2. 能力探测：ID_AA64ISAR0_EL1.ATOMIC

### 2.1 架构侧：一个 4 位字段回答"有没有 LSE"

ARM ARM 对 `ID_AA64ISAR0_EL1.Atomic`（bits [23:20]）的定义（D24-9100）：

> "The value of this field is an IMPLEMENTATION DEFINED choice of: **0b0000** No Atomic instructions implemented. **0b0010** LDADD, LDCLR, LDEOR, LDSET, LDSMAX, LDSMIN, LDUMAX, LDUMIN, CAS, CASP, and SWP instructions implemented. **0b0011** As for 0b0010, plus 128-bit instructions LDCLRP, LDSETP, and SWPP. **All other values are reserved.** FEAT_LSE implements the functionality identified by the value 0b0010. FEAT_LSE128 implements the functionality identified by the value 0b0011. **From Armv8.1, the value 0b0000 is not permitted.**"
>
> 该字段是 IMPLEMENTATION DEFINED 的选择：0b0000 未实现原子指令；0b0010 实现了 LDADD/LDCLR/LDEOR/LDSET/LDSMAX/LDSMIN/LDUMAX/LDUMIN/CAS/CASP/SWP；0b0011 在 0b0010 基础上再加 128 位的 LDCLRP/LDSETP/SWPP；其余值保留。FEAT_LSE 对应 0b0010，FEAT_LSE128 对应 0b0011；**Armv8.1 起不允许 0b0000**。

```
ID_AA64ISAR0_EL1（AArch64 指令集属性寄存器 0）
 63       36 35  32 31  28 27  24 23  20 19  16 15  12 ...
┌──────────┬──────┬──────┬──────┬──────┬──────┬──────┬─────────
│   ...    │ SHA3 │ RDM  │ RES0 │ATOMIC│ CRC32│ SHA2 │  ...
└──────────┴──────┴──────┴──────┴──────┴──────┴──────┴─────────
                                     ▲
                         ┌───────────┴────────────┐
                         │ 0b0000  无（v8.1 起非法）│
                         │ 0b0010  FEAT_LSE       │ ← 内核最小匹配值
                         │ 0b0011  FEAT_LSE128    │   （≥ 0b0010 全算有）
                         │ 其他    保留            │
                         └────────────────────────┘
```

注意两点：

- **0b0010 已经含 CASP**——128 位"比较交换对"是 v8.1 LSE 的原始成员；FEAT_LSE128（0b0011）追加的是 128 位**算术/交换**族（LDCLRP/LDSETP/SWPP，见 §7）。
- `min_field_value = IMP` 的匹配是**无符号数值比较**：0b0011（LSE128）也满足"有 LSE"，这正是想要的语义——LSE128 是 LSE 的超集。

### 2.2 内核侧：cpufeature.c 的能力表项

```c
// arch/arm64/kernel/cpufeature.c:2580
	{
		.desc = "LSE atomic instructions",
		.capability = ARM64_HAS_LSE_ATOMICS,
		.type = ARM64_CPUCAP_SYSTEM_FEATURE,
		.matches = has_cpuid_feature,
		ARM64_CPUID_FIELDS(ID_AA64ISAR0_EL1, ATOMIC, IMP)
	},
```

- `ARM64_CPUID_FIELDS(reg, field, min_value)` 把"匹配条件"编码成"字段值落在 `[min_value, 无符号上限]` 区间"（[cpufeature.c:179](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/cpufeature.c)），即 `ATOMIC ∈ {0b0010, 0b0011}`；
- 字段的位置/宽度来自内核自己的寄存器描述文件，与 ARM ARM 完全同构：

```c
// arch/arm64/tools/sysreg:1875
UnsignedEnum	23:20	ATOMIC
	0b0000	NI
	0b0010	IMP
	0b0011	FEAT_LSE128
EndEnum
```

- `.type = ARM64_CPUCAP_SYSTEM_FEATURE`——LSE 是**系统级**能力（全系统所有 CPU 必须一致）：主 CPU 探测，次级 CPU 上线时 `check_local_cpu_capabilities()`（[smp.c:226](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/smp.c)）只做**校验**，不一致则拒绝上线（`verify_local_cpu_capabilities`）。异构大小核（A725+A520）两族核心都实现 FEAT_LSE（Armv8.1 起强制，A2-97），所以整个能力位天然一致。

### 2.3 探测结果落在哪

`update_cpu_capabilities()` 把命中的能力置进两张 bitmap：`boot_cpucaps`（BOOT 范围）与 `system_cpucaps`（系统范围）。后续所有补丁动作（§5）都查这两张表——**运行期的每条原子指令不读 ID 寄存器，只看启动期改写过的代码**。

## 3. 一个 API，两个后端：atomic.h 的分派

### 3.1 三层展开：从 `arch_atomic_add` 到一条 `stadd`

```c
// arch/arm64/include/asm/atomic.h:19
#define ATOMIC_OP(op)							\
static __always_inline void arch_##op(int i, atomic_t *v)		\
{									\
	__lse_ll_sc_body(op, i, v);					\
}

ATOMIC_OP(atomic_andnot)
ATOMIC_OP(atomic_or)
ATOMIC_OP(atomic_xor)
ATOMIC_OP(atomic_add)
ATOMIC_OP(atomic_and)
ATOMIC_OP(atomic_sub)
```

`__lse_ll_sc_body` 定义在 [lse.h](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/lse.h)——这是整个双路径的**总开关**：

```c
// arch/arm64/include/asm/lse.h:7
#define __LSE_PREAMBLE	".arch_extension lse\n"

// arch/arm64/include/asm/lse.h:17
#define __lse_ll_sc_body(op, ...)					\
({									\
	alternative_has_cap_likely(ARM64_HAS_LSE_ATOMICS) ?		\
		__lse_##op(__VA_ARGS__) :				\
		__ll_sc_##op(__VA_ARGS__);				\
})

/* In-line patching at runtime */
#define ARM64_LSE_ATOMIC_INSN(llsc, lse)				\
	ALTERNATIVE(llsc, __LSE_PREAMBLE lse, ARM64_HAS_LSE_ATOMICS)
```

以 `arch_atomic_add(i, v)` 为例的完整展开（LSE 命中后）：

```
arch_atomic_add(i, v)                          [atomic.h:28 实例化]
 └─ __lse_ll_sc_body(add, i, v)                [lse.h:17]
     └─ alternative_has_cap_likely(ARM64_HAS_LSE_ATOMICS) ?
          │  ← 启动期该分支已被补丁成 NOP（§5.1），永远走到 true 侧
          ├─ true : __lse_atomic_add(i, v)     [atomic_lse.h:27]
          │          └─ asm: "stadd %w[i], %[v]"     ← 一条 LSE 指令
          └─ false: __ll_sc_atomic_add(i, v)   [atomic_ll_sc.h:35]
                     └─ asm: ldxr/add/stxr/cbnz 重试环  ← 死码（补丁后）
```

- 两个后端是**两个完整的 C 函数**（`__always_inline`，编译器在每个调用点各展开一份），运行期只靠那一条被补丁过的分支二选一；
- `alternative_has_cap_likely` 是"编译期存在、启动期变 NOP"的静态分支，普通 `if` 快不了它多少，但它**没有任何运行期探测开销**——细节在 §5.1。

### 3.2 LSE 后端走读（atomic_lse.h）

不返回旧值的"发后即忘"操作用 `ST*` 家族（store-OP，不需要回读旧值，更省）：

```c
// arch/arm64/include/asm/atomic_lse.h:13
#define ATOMIC_OP(op, asm_op)						\
static __always_inline void						\
__lse_atomic_##op(int i, atomic_t *v)					\
{									\
	asm volatile(							\
	__LSE_PREAMBLE							\
	"	" #asm_op "	%w[i], %[v]\n"				\
	: [v] "+Q" (v->counter)						\
	: [i] "r" (i));							\
}

ATOMIC_OP(andnot, stclr)      // ~i 的位清零 → STCLR（按位清）
ATOMIC_OP(or, stset)          // 置位     → STSET（按位置）
ATOMIC_OP(xor, steor)         // 异或     → STEOR
ATOMIC_OP(add, stadd)         // 加法     → STADD（STADD 是 LDADD 的
                              //   "不回读旧值"别名, ARM ARM C6.2.385/C6-2627）
```

需要旧值的操作用 `LD*` 家族，并把内存序后缀直接编进指令名：

```c
// arch/arm64/include/asm/atomic_lse.h:36
#define ATOMIC_FETCH_OP(name, mb, op, asm_op, cl...)			\
static __always_inline int						\
__lse_atomic_fetch_##op##name(int i, atomic_t *v)			\
{									\
	int old;							\
									\
	asm volatile(							\
	__LSE_PREAMBLE							\
	"	" #asm_op #mb "	%w[i], %w[old], %[v]"			\
	: [v] "+Q" (v->counter),					\
	  [old] "=r" (old)						\
	: [i] "r" (i)							\
	: cl);								\
									\
	return old;							\
}

#define ATOMIC_FETCH_OPS(op, asm_op)					\
	ATOMIC_FETCH_OP(_relaxed,   , op, asm_op)			\
	ATOMIC_FETCH_OP(_acquire,  a, op, asm_op, "memory")		\
	ATOMIC_FETCH_OP(_release,  l, op, asm_op, "memory")		\
	ATOMIC_FETCH_OP(        , al, op, asm_op, "memory")

ATOMIC_FETCH_OPS(andnot, ldclr)
ATOMIC_FETCH_OPS(or, ldset)
ATOMIC_FETCH_OPS(xor, ldeor)
ATOMIC_FETCH_OPS(add, ldadd)
```

四处展开对应 LSE 的四个内存序变体（`LDADD/LDADDA/LDADDL/LDADDAL`，ARM ARM C6.2.179/C6-2198）——**内存序不靠额外的 barrier 指令，而是选另一条指令**。

**三个"语义补角"技巧**——LSE 指令族是固定语义集合，内核用 C 层的小变换把 API 全集盖满：

```c
// arch/arm64/include/asm/atomic_lse.h:29
static __always_inline void __lse_atomic_sub(int i, atomic_t *v)
{
	__lse_atomic_add(-i, v);        // 没有 STSUB：减法 = 加负数
}

// arch/arm64/include/asm/atomic_lse.h:81
#define ATOMIC_OP_ADD_SUB_RETURN(name)					\
static __always_inline int						\
__lse_atomic_add_return##name(int i, atomic_t *v)			\
{									\
	return __lse_atomic_fetch_add##name(i, v) + i;			\
}									\
									\
static __always_inline int						\
__lse_atomic_sub_return##name(int i, atomic_t *v)			\
{									\
	return __lse_atomic_fetch_sub(i, v) - i;			\
}

// arch/arm64/include/asm/atomic_lse.h:101
static __always_inline void __lse_atomic_and(int i, atomic_t *v)
{
	return __lse_atomic_andnot(~i, v);   // 没有 STAND：AND(x) = BIC(~x)
}
```

- **返回新值 = 返回旧值 ± i**：LSE 指令一律返回**旧值**，而 `atomic_add_return` 语义要**新值**——加一条免费的寄存器加法补上（比让硬件出 `ADDRETURN` 变体划算）；
- AND 用 BIC（STCLR）按位取反实现、SUB 用加负数实现——这正是 [004 §2](./004.LLSC与LSE的区别.md) 表里"每条指令语义固定"的直接后果：**指令族没有的操作，在 C 层合成**。

### 3.3 LL/SC 后端对照（atomic_ll_sc.h）

同一个 `arch_atomic_add` 的 LL/SC 后端（重试环的完整分析见 [003 §7.1](./003.LLSC实现原理.md)）：

```c
// arch/arm64/include/asm/atomic_ll_sc.h:25
#define ATOMIC_OP(op, asm_op, constraint)				\
static __always_inline void						\
__ll_sc_atomic_##op(int i, atomic_t *v)					\
{									\
	unsigned long tmp;						\
	int result;							\
									\
	asm volatile("// atomic_" #op "\n"				\
	"	prfm	pstl1strm, %2\n"				\
	"1:	ldxr	%w0, %2\n"					\
	"	" #asm_op "	%w0, %w0, %w3\n"			\
	"	stxr	%w1, %w0, %2\n"					\
	"	cbnz	%w1, 1b\n"					\
	: "=&r" (result), "=&r" (tmp), "+Q" (v->counter)		\
	: __stringify(constraint) "r" (i));				\
}
```

对比一下两边的指令条数（这就是 §1 那张全景图在单条 API 上的样子）：

```
      LSE 后端（1 条）                LL/SC 后端（4~5 条 + 环）
  ┌────────────────────────┐    ┌──────────────────────────────┐
  │ stadd  w0, [x1]        │    │ prfm  pstl1strm, [x1]        │
  │  // 旧值都不要，无回读  │    │ 1: ldxr  w0, [x1]            │
  │                        │    │    add   w0, w0, w3          │
  │                        │    │    stxr  w2, w0, [x1]  ──┐   │
  │                        │    │    cbnz  w2, 1b        │   │
  │                        │    │      ▲──────────────────┘   │
  └────────────────────────┘    └──────────────────────────────┘
   无失败态、无重试               STXR 失败重试；ERG 块伪共享
```

| `cmpwait_relaxed`（等待） | **无 LSE 路径** | —— | `sevl/wfe/ldxr`（§4.4） |

### 3.5 内存序后缀：LSE 的 a/l/al vs LL/SC 的 dmb ish

LSE 把内存序做进指令名；LL/SC 只能靠 `LDAXR`/`STLXR` 变体 + **full 屏障时额外贴 `dmb ish`**。[cmpxchg.h:16](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/cmpxchg.h) 的注释把这件事说得很直白：

```c
// arch/arm64/include/asm/cmpxchg.h:16
/*
 * We need separate acquire parameters for ll/sc and lse, since the full
 * barrier case is generated as release+dmb for the former and
 * acquire+release for the latter.
 */
```

即同一个"全屏障"语义：

```
LL/SC 版:  stlxr (release) + dmb ish          两条
LSE 版:    swpal / casal (acquire+release)    一条（ARM ARM B2.6.11 的
                                           RCsc 语义, 见 002 §5）
```

这也解释了 §5.2 里 `__XCHG_CASE` 宏参数为什么有 `mb / nop_lse / acq / acq_lse / rel` 五个——两边拼"全屏障"的材料不一样。

## 4. cmpxchg 家族与三个特殊角色

### 4.1 cmpxchg：CAS + "rZ" 约束

分派层（与 atomic 同一个 `__lse_ll_sc_body`）：

```c
// arch/arm64/include/asm/cmpxchg.h:106
#define __CMPXCHG_CASE(name, sz)			\
static inline u##sz __cmpxchg_case_##name##sz(volatile void *ptr,	\
					      u##sz old,		\
					      u##sz new)		\
{									\
	return __lse_ll_sc_body(_cmpxchg_case_##name##sz,		\
				ptr, old, new);				\
}
```

LSE 后端（16 个实例 = 4 种宽度 × 4 种内存序，下面以 8 位宽为例）：

```c
// arch/arm64/include/asm/atomic_lse.h:248
#define __CMPXCHG_CASE(w, sfx, name, sz, mb, cl...)			\
static __always_inline u##sz						\
__lse__cmpxchg_case_##name##sz(volatile void *ptr,			\
					      u##sz old,		\
					      u##sz new)		\
{									\
	asm volatile(							\
	__LSE_PREAMBLE							\
	"	cas" #mb #sfx "	%" #w "[old], %" #w "[new], %[v]\n"	\
	: [v] "+Q" (*(u##sz *)ptr),					\
	  [old] "+r" (old)						\
	: [new] "rZ" (new)						\
	: cl);								\
									\
	return old;							\
}

__CMPXCHG_CASE(w, b,     ,  8,   )           // 第一族 sfx=b/h/无/x → casb/cash/cas/cas(x)
__CMPXCHG_CASE(w, b, acq_,  8,  a, "memory")   // acq_ 族 → casa…（acquire）
__CMPXCHG_CASE(w, b, rel_,  8,  l, "memory")   // rel_ 族 → casl…（release）
__CMPXCHG_CASE(w, b,  mb_,  8, al, "memory")   // mb_ 族 → casal…（acquire+release）
```

两个细节：

- **`[new] "rZ"` 约束**：允许新值用 `WZR/XZR`（零寄存器）而不是普通寄存器——`cmpxchg(p, old, 0)` 这类极常见的"条件清零"不用占寄存器；
- `old` 是 `"+r"`（输入输出）：CAS 把读到的实际旧值写回同一寄存器（[002 §3](./002.CAS实现原理.md) 的 `X[s] ← oldvalue`），失败路径就靠它判断——CAS 本身**没有状态位**，"失败"只是"读回的旧值 ≠ 期望值"，仍是一次无条件完成的原子 RMW。

### 4.2 cmpxchg128：CASP 与偶寄存器对

```c
// arch/arm64/include/asm/atomic_lse.h:296（__CMPXCHG128 的 asm 主体，节选）
	asm volatile(							\
	__LSE_PREAMBLE							\
	"	casp" #mb "\t%[old1], %[old2], %[new1], %[new2], %[v]\n"\
	: [old1] "+&r" (x0), [old2] "+&r" (x1),				\
	  [v] "+Q" (*(u128 *)ptr)					\
	: [new1] "r" (x2), [new2] "r" (x3), [ptr] "r" (x4),		\
	  [oldval1] "r" (o.low), [oldval2] "r" (o.high)			\
	: cl);								\
```

`CASP` 是 v8.1 LSE 的原始成员（ID 字段 0b0010 已含，ARM ARM C6.2.54/C6-1877），架构要求**比较值/新值各占一对偶数起始的相邻寄存器**（这里固定绑 `x0-x1` 旧值对、`x2-x3` 新值对、`x4` 地址）——所以代码里全是 `register ... asm("x0")` 绑定。这也顺带回答了一个老问题：**128 位原子不需要 FEAT_LSE128 就有**（CASP 一直在），FEAT_LSE128 追加的是 128 位**算术**族（§7）。内核声明 `system_has_cmpxchg128() == 1`（[cmpxchg.h:201](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/cmpxchg.h)），refcount/ticket lock 等因此可用 128 位 CAS。

### 4.3 dec_if_positive：LSE 时代依然存在的"重试环"

`atomic64_dec_if_positive` 语义是"**仅当**当前值 > 0 才减 1，返回新值"——带条件的 RMW（Read-Modify-Write，读-改-写；定义见 [README](./README.md)），LSE 固定语义指令族里**没有**对应单条，于是 LSE 后端自己拼了一个乐观 CAS 环：

```c
// arch/arm64/include/asm/atomic_lse.h:227
static __always_inline s64 __lse_atomic64_dec_if_positive(atomic64_t *v)
{
	unsigned long tmp;

	asm volatile(
	__LSE_PREAMBLE
	"1:	ldr	%x[tmp], %[v]\n"          // 乐观读（普通 ldr，非原子）
	"	subs	%[ret], %x[tmp], #1\n"    // ret = tmp-1，置标志
	"	b.lt	2f\n"                     // tmp <= 0 → 直接返回负值
	"	casal	%x[tmp], %[ret], %[v]\n"  // 期望 tmp，想写 tmp-1
	"	sub	%x[tmp], %x[tmp], #1\n"    // tmp = CAS 读回的旧值-1
	"	sub	%x[tmp], %x[tmp], %[ret]\n"// 减去写进去的值
	"	cbnz	%x[tmp], 1b\n"            // 差 ≠ 0 ⇒ CAS 失败 → 重读重试
	"2:"
	: [ret] "+&r" (v), [v] "+Q" (v->counter), [tmp] "=&r" (tmp)
	:
	: "cc", "memory");

	return (long)v;
}
```

走读（成功路径）：

```
*v = 5
ldr   tmp = 5              （乐观读，可能与并发写竞争）
subs  ret = 4, 5-1 ≥ 0 → 不跳
casal 期望 5 / 写 4：若此刻 *v 仍是 5 → *v=4，tmp 读回 5
      tmp-1 - ret = 4 - 4 = 0 → 退出，返回 ret = 4（新值）✓
失败路径：*v 已被别人改成 7 → tmp 读回 7 → 6-4 ≠ 0 → 回 1 重读
```

> 注意 `[ret] "+&r" (v)`——**返回值复用了指针实参的寄存器**，函数结尾 `return (long)v` 直接把它当新值返回（GCC 内联汇编的老技巧）。

**教学点**：[004 §0](./004.LLSC与LSE的区别.md) 说"LSE = 锁死 + 必成"指的是**每笔原子 RMW 自身**无失败态——不是说所有操作都能单条化。**非固定语义的条件 RMW，LSE 路径仍是"乐观读 + CAS 重试"环**；对比 LL/SC 环，它的优势是每次 CAS 都是一笔保证前进的一致性事务（无 ERG 伪共享、无需前瞻兜底），且重读发生在失败之后而非每次都排他标记（[003 §8](./003.LLSC实现原理.md) 保留地 2 的运行期形态）。

### 4.4 cmpwait：LSE 进不来的地方

等待原语 `cmpwait_relaxed`（`smp_cond_load_*` 的底层）在 7.1.3 里**连 LSE 分支都没有**，纯 LL/SC + WFE：

```c
// arch/arm64/include/asm/cmpxchg.h:213
#define __CMPWAIT_CASE(w, sfx, sz)					\
static inline void __cmpwait_case_##sz(volatile void *ptr,		\
				       unsigned long val)		\
{									\
	unsigned long tmp;						\
									\
	asm volatile(							\
	"	sevl\n"							\
	"	wfe\n"							\
	"	ldxr" #sfx "\t%" #w "[tmp], %[v]\n"			\
	"	eor	%" #w "[tmp], %" #w "[tmp], %" #w "[val]\n"	\
	"	cbnz	%" #w "[tmp], 1f\n"				\
	"	wfe\n"							\
	"1:"								\
	: [tmp] "=&r" (tmp), [v] "+Q" (*(u##sz *)ptr)			\
	: [val] "r" (val));						\
}
```

原因：LSE 没有"等待"类指令，而这里的 `ldxr` 根本不是用来做原子的——它是**事件登记**：把地址挂上独占监视器，远端核写该地址（监视器被清）会产生事件唤醒 `wfe`（机制见 [003 §4.7](./003.LLSC实现原理.md)）。这是 LL/SC 四块保留地（等待 / 非标准 RMW / 128 位 / 基线兼容）中最不可替代的一块，全表见 [003 §8](./003.LLSC实现原理.md)。

## 5. 启动期补丁：两套机制与一个时序

### 5.1 机制一：分支变 NOP（atomic / cmpxchg 走这条）

`alternative_has_cap_likely()` 本体只有十几行：

```c
// arch/arm64/include/asm/alternative-macros.h:226
static __always_inline bool
alternative_has_cap_likely(const unsigned long cpucap)
{
	if (!cpucap_is_possible(cpucap))
		return false;

	asm goto(
#ifdef BUILD_VDSO
	ALTERNATIVE("b	%l[l_no]", "nop", %[cpucap])
#else
	ALTERNATIVE_CB("b	%l[l_no]", %[cpucap], alt_cb_patch_nops)
#endif
	:
	: [cpucap] "i" (cpucap)
	:
	: l_no);

	return true;
l_no:
	return false;
}
```

编译产物里每个调用点只有**一条指令**的判断位：默认是 `b l_no`（跳到 false 分支，走 LL/SC）；启动期若 LSE 命中，回调 `alt_cb_patch_nops` 把这条 `b` **改写成 NOP**——执行直落 `return true`，走 LSE：

```
      补丁前（无 LSE / 补丁完成前）           补丁后（有 LSE）
  ┌────────────────────────────┐        ┌────────────────────────────┐
  │ alternative_has_cap_likely │        │ alternative_has_cap_likely │
  │     b   l_no    ◄─ ALTERNATIVE_CB  │     nop         ◄─ 补丁覆盖 │
  │     return true            │        │     return true            │
  │ l_no:                      │        │ l_no:                      │
  │     return false           │        │     return false（死码）    │
  └────────────────────────────┘        └────────────────────────────┘
        → __ll_sc_atomic_add                  → __lse_atomic_add
```

回调本体（对每条指令写 NOP）：

```c
// arch/arm64/kernel/alternative.c:299
noinstr void alt_cb_patch_nops(struct alt_instr *alt, __le32 *origptr,
			       __le32 *updptr, int nr_inst)
{
	for (int i = 0; i < nr_inst; i++)
		updptr[i] = cpu_to_le32(aarch64_insn_gen_nop());
}
```

### 5.2 机制二：指令原地重写（xchg / percpu / hyp 锁走这条）

`ARM64_LSE_ATOMIC_INSN(llsc, lse)` 是更老的机制：把两段**指令序列**塞进同一个内联 asm，链接期把 LSE 副本放进特殊节，启动期有 LSE 就**整段抄写覆盖** LL/SC 原文。xchg（交换）是代表：

```c
// arch/arm64/include/asm/cmpxchg.h:21
#define __XCHG_CASE(w, sfx, name, sz, mb, nop_lse, acq, acq_lse, rel, cl)	\
static inline u##sz __xchg_case_##name##sz(u##sz x, volatile void *ptr)		\
{										\
	u##sz ret;								\
	unsigned long tmp;							\
											\
	asm volatile(ARM64_LSE_ATOMIC_INSN(					\
	/* LL/SC */								\
	"	prfm	pstl1strm, %2\n"					\
	"1:	ld" #acq "xr" #sfx "\t%" #w "0, %2\n"				\
	"	st" #rel "xr" #sfx "\t%w1, %" #w "3, %2\n"			\
	"	cbnz	%w1, 1b\n"						\
	"	" #mb,								\
	/* LSE atomics */							\
	"	swp" #acq_lse #rel #sfx "\t%" #w "3, %" #w "0, %2\n"		\
		__nops(3)							\
	"	" #nop_lse)							\
	: "=&r" (ret), "=&r" (tmp), "+Q" (*(u##sz *)ptr)			\
	: "r" (x)								\
	: cl);									\
											\
	return ret;								\
}
```

机制要点，对着链接期镜像和补丁后的镜像看：

```
        链接期镜像                                       apply_alternatives_all() 之后
 ───────────────────────────────────────         ───────────────────────────────────────
 .text（正式代码段）                              .text
 661: prfm  pstl1strm, [x1]                       661: swpal  w3, w0, [x1]
      1: ldxr  w0, [x1]                                 nop
         stxr  w2, w3, [x1]                             nop
         cbnz w2, 1b                                    nop
         dmb ish              ← "全屏障"变体            nop
 662:                                                662:（后续指令原样）
 .subsection 1（替换序列的"备件库"）                .subsection 1
 663: swpal w3, w0, [x1]     ← 全屏障变体两侧        （副本还在，但不再被引用）
      nop / nop / nop          各 5 条：LL/SC 侧
      nop                      prfm+环+dmb，
                               LSE 侧 swpal+nop×4
 664:
 .altinstructions（补丁清单节）                    .altinstructions
 ┌──────────────────────────────┐                 ┌──────────────────────────────┐
 │ orig_offset → 661:            │                 │ （表项保留；已应用的能力      │
 │ alt_offset  → 663:            │                 │   记进 applied_alternatives）│
 │ cpucap = ARM64_HAS_LSE_ATOMICS│                 └──────────────────────────────┘
 │ orig_len / alt_len（必须相等）│
 └──────────────────────────────┘
```

- **表项格式**就是 [alternative.h:13](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/alternative.h) 的 `struct alt_instr { orig_offset; alt_offset; cpucap; orig_len; alt_len; }`；
- **两段必须等长**：以全屏障（`_mb`）变体为例，LL/SC 侧五条（prfm/ldxr/stxr/cbnz/`dmb ish`）↔ LSE 侧五条（`swpal` + `__nops(3)` + `nop`，最后那个 `nop` 来自 `nop_lse` 参数）；无屏障变体两侧各四条。补丁循环里 `BUG_ON(alt->alt_len != alt->orig_len)` 强制这一点（[alternative.c:163](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/alternative.c)）；
- **`__LSE_PREAMBLE` 不占字节**：`".arch_extension lse\n"` 是发给**汇编器**的指令——允许这段 asm 里出现 LSE 编码（默认 `-march` 未必含 LSE）。它只存在于汇编期，链接期 663: 处放的纯是 `swpal` 的机器码，抄写覆盖与它无关；
- 执行抄写的正是 [alternative.c:104](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/alternative.c) 的 `patch_alternative()`（逐条从 `alt_offset` 拷到 `orig_offset`，顺带修 PC 相对寻址）。

percpu 操作是同一机制的第二个用户（[percpu.h:73](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/percpu.h)、percpu.h:94）：

```c
// arch/arm64/include/asm/percpu.h:66（节选）
#define __PERCPU_OP_CASE(w, sfx, name, sz, op_llsc, op_lse)		\
static inline void							\
__percpu_##name##_case_##sz(void *ptr, unsigned long val)		\
{									\
	unsigned int loop;						\
	u##sz tmp;							\
									\
	asm volatile (ARM64_LSE_ATOMIC_INSN(				\
	/* LL/SC */							\
	"1:	ldxr" #sfx "\t%" #w "[tmp], %[ptr]\n"			\
		#op_llsc "\t%" #w "[tmp], %" #w "[tmp], %" #w "[val]\n"	\
	"	stxr" #sfx "\t%w[loop], %" #w "[tmp], %[ptr]\n"		\
	"	cbnz	%w[loop], 1b",					\
	/* LSE atomics */						\
		#op_lse "\t%" #w "[val], %" #w "[tmp], %[ptr]\n"	\
		__nops(3))						\
	: [loop] "=&r" (loop), [tmp] "=&r" (tmp),			\
	  [ptr] "+Q"(*(u##sz *)ptr)					\
	: [val] "r" ((u##sz)(val)));					\
}
```

第三个用户在 KVM 的 EL2 hyp 代码里——hyp 的自旋锁（票锁！）取号用 `ldadda`，解锁用 `staddlh`（[nvhe/spinlock.h:51](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kvm/hyp/include/nvhe/spinlock.h)、nvhe/spinlock.h:87）：

```c
// arch/arm64/kvm/hyp/include/nvhe/spinlock.h:49（节选取号部分）
	asm volatile(
	/* Atomically increment the next ticket. */
	ARM64_LSE_ATOMIC_INSN(
	/* LL/SC */
"	prfm	pstl1strm, %3\n"
"1:	ldaxr	%w0, %3\n"
"	add	%w1, %w0, #(1 << 16)\n"
"	stxr	%w2, %w1, %3\n"
"	cbnz	%w2, 1b\n",
	/* LSE atomics */
"	mov	%w2, #(1 << 16)\n"
"	ldadda	%w2, %w0, %3\n"
	__nops(3))
```

（解锁侧 LL/SC 三条 `ldrh/add/stlrh` ↔ LSE 一条 `staddlh`。）另外 KVM 地址翻译模拟里还有**无条件**直接用 LSE 的例子——[at.c:1714](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kvm/at.c) 的 `__lse_swap_desc()` 直接 `__LSE_PREAMBLE + cas` 访问用户页表项。

### 5.3 两套机制怎么分工

| | 机制一 `alternative_has_cap_likely` | 机制二 `ARM64_LSE_ATOMIC_INSN` |
| - | - | - |
| 形态 | C 层三目 `?:` + 一条可补丁的 `b` | 一个 asm 模板塞两段指令序列 |
| 补丁动作 | `b l_no` → NOP（`alt_cb_patch_nops`） | LSE 序列整段抄盖 LL/SC 序列（`patch_alternative`） |
| 长度约束 | 无（分支就一条） | 两段必须**等长**（`__nops` 凑齐 + `.org` 对齐） |
| 后端形态 | 两个完整 C 函数（`__lse_*` / `__ll_sc_*`），可用返回值、可含复杂 C 逻辑 | 纯指令序列，旧值/新值只能走寄存器约束 |
| 使用者 | atomic.h / cmpxchg（§3、§4.1-4.2） | xchg（cmpxchg.h:27）、percpu、hyp 票锁 |
| 每调用点开销 | 一条 NOP | 零（指令本身就是 LSE） |

一句话：**能写成"两个 C 函数"的用机制一（省心、表达力强）；必须在一个 asm 模板里表达输入输出约束的用机制二。** 两者共享同一张 `.altinstructions` 清单和同一个补丁循环。

### 5.4 补丁循环与启动时序

补丁循环核心（裁剪自 [alternative.c:142](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/alternative.c)）：

```c
// arch/arm64/kernel/alternative.c:142（节选）
static int __apply_alternatives(const struct alt_region *region,
				bool is_module,
				unsigned long *cpucap_mask)
{
	struct alt_instr *alt;
	__le32 *origptr, *updptr;
	alternative_cb_t alt_cb;

	for (alt = region->begin; alt < region->end; alt++) {
		int nr_inst;
		int cap = ALT_CAP(alt);

		if (!test_bit(cap, cpucap_mask))
			continue;
		if (!cpus_have_cap(cap))
			continue;
		...
		origptr = ALT_ORIG_PTR(alt);
		updptr = is_module ? origptr : lm_alias(origptr);
		nr_inst = alt->orig_len / AARCH64_INSN_SIZE;

		if (ALT_HAS_CB(alt)) {
			alt_cb  = ALT_REPL_PTR(alt);      // 机制一：回调 = 补 NOP
			...
		} else {
			alt_cb = patch_alternative;      // 机制二：抄写替换序列
		}

		alt_cb(alt, origptr, updptr, nr_inst);
		...
	}
	/* 补完刷 I-cache，再记录 applied_alternatives */
	dsb(ish);
	icache_inval_all_pou();
	isb();
	...
}
```

两阶段时序（谁在什么时候被改成什么）：

```
boot CPU                                          secondary CPUs
────────                                          ──────────────
start_kernel → ... → smp_prepare_boot_cpu()       （尚未上线）
  [smp.c:447]
  └─ setup_boot_cpu_features() [smp.c:457]
       ├─ update_cpu_capabilities(BOOT|LOCAL)
       │    LSE 是 SYSTEM 级能力（SCOPE_SYSTEM）：
       │    本轮不评估、不进 boot_cpucaps → 不补
       │    （boot_cpucaps 只收 SCOPE_BOOT_CPU 能力，
       │      cpufeature.c:3554）

          （LSE 不在此列：SYSTEM_FEATURE）

... smp_init：secondary_start_kernel() ──────────→ 各次级 CPU
   [smp.c:226] check_local_cpu_capabilities()        只校验能力一致性，
   （补丁统一由 boot CPU 做，避免并发改写）          不一致 → 拒绝上线

smp_cpus_done() [smp.c:438]
  └─ setup_system_capabilities() [cpufeature.c:3943]
       ├─ update_cpu_capabilities(SYSTEM)   ← LSE 能力位正式定盘
```

## 6. 微架构执行：Cortex-A725 的 near / far atomics

前面都是"软件视角"——代码补成 `stadd` 就完事了吗？一条 LSE 指令落到大核里到底**在哪执行**、争用时走哪条路？这正是 TRM 的职责范围。A725 TRM §8.3（p70）给出完整答案：

> "Atomic instructions to Cacheable memory can be performed as either **near atomics** or **far atomics**, the Cortex-A725 core performs these instructions as **near atomics by default**. Alternatively, IMP_CPUECTLR_EL1 can be programmed so that depending on the system behavior, some atomic instructions attempt to execute as far atomics. **When executed as far atomics, the atomic is passed on to the interconnect to perform the operation.** If the operation hits anywhere inside the cluster, or if an interconnect does not support atomics, then the **L3 memory system** performs the atomic operation. If the line is not already there, it allocates the line into the L3 cache. When Memory Tagging Extension (MTE) is enabled with precise checking, all checked atomics are performed near. The Cortex-A725 core supports atomics to Device or Non-cacheable memory, however this relies on the interconnect also supporting atomics. If such an atomic instruction is executed when the interconnect does not support them, then it results in an **abort**."
>
> 对 Cacheable 内存的原子指令可用 **near atomics**（本核就地执行）或 **far atomics**（交给互连执行）两种方式实现，A725 **默认 near**；可通过 IMP_CPUECTLR_EL1 编程让部分原子尝试 far。far 时原子操作被移交给互连执行；若操作命中簇内任意一级，或互连不支持原子，则由 **L3 内存系统**执行（行不在 L3 则分配进 L3）。MTE 精确检查开启时所有被检查的原子都 near 执行。A725 支持 Device/Non-cacheable 内存上的原子，但这依赖互连也支持原子——互连不支持时执行这类指令会产生 **abort**。

### 6.1 先摆好拓扑：一条原子指令能经过哪些站

A725 的内存系统层级（TRM §8/§9，p68/p73）：

```
                 簇（DynamIQ Shared Unit-120）
 ┌───────────────────────────────────────────────────────────┐
 │  ┌─────────┐   ┌─────────┐        ┌────────────────────┐  │
 │  │ CPU0    │   │ CPU1    │  ...   │  L3 缓存（共享）    │  │
 │  │ ┌─────┐ │   │ ┌─────┐ │        │  簇内一致性点       │  │
 │  │ │ L1D │ │   │ │ L1D │ │        └─────────▲──────────┘  │
 │  │ └──▲──┘ │   │ └──▲──┘ │                  │             │
 │  │    │私有 │   │    │私有 │   CPU bridge（CHI Issue E）  │
 │  │ ┌──┴──┐ │   │ ┌──┴──┐ │                  │             │
 │  │ │ L2  │ │   │ │ L2  │ │        ┌─────────┴──────────┐  │
 │  │ └──▲──┘ │   │ └──▲──┘ │        │  DSU-120 互连/SCU  │  │
 │  └────┼────┘   └────┼────┘        └─────────▲──────────┘  │
 └───────┼─────────────┼───────────────────────┼─────────────┘
         └─────────────┴───────────────────────┘
   · L1D 32/64KB 4 路 16 bank，64B 行，MESI（TRM p68-69）
   · L2 每核私有 128KB~1MB 8 路；L1D 与 L2 严格互斥（TRM p73）
     "Any data contained in the L1 data cache is never
      present in the L2 cache."
   · L2 经 CPU bridge（单条 CHI Issue E 接口）接 DSU-120 → L3
```

### 6.2 near atomic：默认路径，L1D 就地完成

行已在本地 L1D（Exclusive/Modified 态）时，整笔 RMW 在 **L1 数据缓存管线内**完成，不过桥、不惊动任何其他代理——这正是 [002 §4.2](./002.CAS实现原理.md) "行锁窗口内做完读→改→写"的最便宜形态：

```
      CPU0 (A725)                                     CPU1
 ┌─────────────────────────────────┐
 │ ldaddal w0, w1, [x2]            │
 │  │ 译码 → LSU → L1D 查找         │        （无任何总线事务，
 │  ▼                               │          对 CPU1 完全透明）
 │ L1D：line X = [Exclusive]        │
 │  ① 行锁：屏蔽对该行的 snoop      │
 │  ② 读旧值 old                    │
 │  ③ ALU: old + X0                 │
 │  ④ 写回，行转 Modified           │
 │  ⑤ old → W0（返回旧值）          │
 └─────────────────────────────────┘
   无争用时这是 L1 命中延迟量级——LL/SC 无争用时也是
   L1 上的环，两者差距很小（[004 §4] 边界）。
```

> 注：图中"① 行锁/屏蔽 snoop"是 [002 §4.2](./002.CAS实现原理.md) 架构层推理的执行形象——TRM 对 near atomic 只承诺"在 L1 数据内存系统中执行"，行锁的具体微操作是 IMPLEMENTATION DEFINED。

### 6.3 far atomic：把 RMW 推给一致性点排队

行不在本地（或按软件配置）时，原子可以作为 **far atomic** 下发——**整个 RMW 作为一个 CHI Atomic 事务**穿到互连/一致性点去执行，核**不取回独占行**：

```
      CPU0                    DSU-120/互连                 L3 / 其他 CPU
 ┌──────────────┐   CHI Atomic(RMW)  ┌──────────────┐   ┌──────────────┐
 │ ldaddal ...  │ ─────────────────→ │ 在一致性点     │   │ 不需要把行   │
 │ （不申请      │                    │ 排队定序执行： │   │ 迁给 CPU0    │
 │   独占行！）  │ ←───────────────── │  读→改→写     │   │ （仍可持有   │
 │              │   返回旧值+确认     │  一笔事务）    │   │   共享态）   │
 └──────────────┘                    └──────┬───────┘   └──────────────┘
                                            ▼
                            簇内任意级命中 → L3 内存系统就地执行
                            行不在 L3     → 分配进 L3 再执行
                            （TRM §8.3：far 原子的兜底规则）
```

为什么大系统偏爱这条路（[004 §4](./004.LLSC与LSE的区别.md) 的争用分析在此落地）：LL/SC 在 N 核争用下每轮 `LDXR` 都要把行拉成独占、行在核间乒乓；far atomic 用"所有请求到**同一个点排队**"取代"互踢"——每笔都算数、天然公平。AGI CPU（Neoverse V3 + CMN-700）在这条路上走得更远：原子事务可以 offload 到互连的 HN-F 一致性点定序，32 核对照图见 [031.AGI-SP113012 §5.3/§5.4](../../031.进程管理/008.进程调度/000.调度组与调度域/003.AGI-SP113012-层级架构-缓存一致性-原子操作.md)。

**两条边界规则**（TRM §8.3 原文）：

- **MTE 精确检查开启 → 所有 checked atomics 强制 near**（far 无法保证 tag 检查的精确性）；
- **Device / Non-cacheable 内存的原子依赖互连支持**，互连不支持则 **abort**——这正是 [002 §4.3](./002.CAS实现原理.md)（ARM ARM B2-249/250：架构只对 Shareable+Write-Back Normal 保证原子性）在具体微架构上的样子：非一致性内存没有缓存行可锁，只能指望互连/内存控制器提供原子事务，没有就翻异常。

### 6.4 软件开关：IMP_CPUECTLR2_EL1 的六个 near/far 旋钮

TRM §8.3 说的 "IMP_CPUECTLR_EL1 可编程"，具体字段全在 [IMP_CPUECTLR2_EL1](../../../007.BOOKs/arm_cortex_a725_core_trm_107652_0001_04_en.pdf)（TRM p202 起）：

| 位 | 字段（p204/p210/p211） | 语义 | 复位 |
| - | - | - | - |
| [45] | `sw_try_atomic_acquire_near` | miss 时也**尝试**以 acquire 语义 near 执行；行被逐出才转 far | 0b1 |
| [44] | `sw_try_atomic_release_near` | 同上，release 变体 | 0b1 |
| [3] | `sw_try_ld_atomic_near` | 原子**读**类（如 CAS 的读半）miss 时尝试 near | 0b0 |
| [2] | `sw_try_st_atomic_near` | 原子**写**类 miss 时尝试 near | 0b0 |
| [1] | `sw_force_st_atomic_near` | **强制**原子写 near（不走 far） | 0b0 |
| [0] | `sw_force_ld_atomic_near` | **强制**原子读 near | 0b0 |

（字段描述原文：*"Try atomic acquire as near even if misses in cache. If the line is evicted, move to far"* / *"Always execute atomic store in near mode"*。）

组合出三种策略：

```
默认（near 优先）      高争用调优（far 优先）      强隔离（绝不 far）
──────────────       ──────────────           ──────────────
try_* = 1 (acq/rel)   try_* = 0                force_* = 1
miss → 先试 L1D，      miss → 直接下发互连/       永远本核就地，
被逐出才转 far         L3 排队定序               哪怕更慢
```

这些是 IMPLEMENTATION DEFINED 的实现细节（固件/调优者用），Linux 内核**不触碰**它们——内核只负责"选哪条指令"，"在哪执行"交给微架构和固件。

### 6.5 和架构手册对齐：near/far 不违反架构中立

[002 §4.2.1](./002.CAS实现原理.md) 已核实：ARM ARM 是机制中立的（原子性由"PE 之外的内存系统"保证，B2-250）。A725 的 near/far 正是这句话的具体化——**架构只约束可观察行为**（读和写之间无人能改、只在一致性内存保证），**实现自由选择执行位置**：

```
架构契约（ARM ARM）                 实现选择（A725 TRM）
──────────────────────            ──────────────────────
读+写不可分割             ◄─────   三种执行位置都能满足：
只对 Shareable+WB 保证  ◄─────     ① near：L1D 行锁（§6.2）
保证者=PE 外的功能      ◄─────     ② far：互连原子事务（§6.3）
(B2-250)                         ③ far 兜底：L3 内存系统执行
Device/NC 不保证        ◄─────   互连不支持 → abort（§6.3 边界）
```

### 6.6 顺带对照：LL/SC 在 A725 上的"监视器"侧

同一颗核的 LL/SC 侧（TRM §8.4，p70-71）：内部独占监视器是 **2 态（open/exclusive）状态机**；`CTR_EL0` 定义的标记块为 **16 words = 一条 cache line（64B）**——这是 ERG（独占保留粒度）在 A725 上的实测值，伪共享问题与两级监视器的完整机制见 [003 §4.2/§4.5](./003.LLSC实现原理.md)。LSE 侧没有"标记块"概念，只原子更新所寻址的字节——[004 §2](./004.LLSC与LSE的区别.md) 对照表中"ERG 伪共享"一行的两边，在 A725 上分别是"64B 监视粒度"和"无"。

## 7. 边界与扩展：FEAT_LSE2 / FEAT_LSE128（简）

**FEAT_LSE2**（放宽原子/独占访问的对齐与原子性规则，A2.2 特性列表 A2-120）不改指令集，改"什么情况下允许原子访问"的规则。伪代码里最直观的一处在 `AArch64.UnalignedAccessFaults()`——判定未对齐访问是否产生 Alignment fault 的函数（J1-15833）：

```
elsif (accdesc.exclusive || accdesc.atomicop) then
    constant integer quantity = MemSingleGranule();
    return (!IsFeatureImplemented(FEAT_LSE2) ||
            !AllInAlignedQuantity(address, size, quantity));
```

对未对齐的 LL/SC（`exclusive`）或 LSE（`atomicop`）访问：**无 LSE2 → 一律 Alignment fault**（表达式恒真）；**有 LSE2 → 只要整个访问落在一个对齐的原子粒度（quantity）内即放行**。与此同时，内存属性派生伪代码里出现 `atomic = boolean IMPLEMENTATION_DEFINED "FEAT_LSE2: access is atomic"`（J1-15829~15831）——LSE2 之下"某类访问是否按原子对待"交由实现声明，呼应 §6.3 "Device/NC 原子依赖互连、不支持则 abort"的实现自由度。访问描述符里 LSE 原子访问有自己的类型位：`atomicop // FEAT_LSE: Atomic read-modify-write access`（J1-16318）。

**FEAT_LSE128**（ID 字段 0b0011，D24-9100）：在 0b0010 全家之上追加 128 位**算术/交换**族——LDCLRP、LDSETP、SWPP（A2-173，Armv9-A 扩展列表）。对内核的实际影响很小：128 位**比较交换**早已由 v8.1 的 `CASP` 覆盖（§4.2），7.1.3 的树里没有使用 LDSETP/SWPP 的路径。

## 9. 常见误区

1. **"开 LSE 要配 `CONFIG_ARM64_LSE_ATOMICS`"**——过时。7.1.3 树里该配置项已不存在（§8）；只要有 FEAT_LSE 的 CPU，启动期补丁自动生效。[README](./README.md) 附录的 Kconfig 片段是 5.9 时代的内容。
2. **"补丁 = static key"**——7.1.3 已换成 `alternative_has_cap_likely`（asm goto + NOP 补丁），与 `.altinstructions` 体系合流（§5.1）；5.9 的 `system_uses_lse_atomics()` 才是 static key。
3. **"LSE 单条一定更快"**——无争用时 near atomic 与 LL/SC 环都是 L1 量级；差距在众核争用下才拉开，且取决于 near/far 策略与互连能力（§6.3）。个别小核 LSE 反而更慢的工程经验与用户态 `-moutline-atomics` 见 [004 §6](./004.LLSC与LSE的区别.md)。
4. **"LSE 补丁完成前内核没有原子操作"**——有：全程 LL/SC 环兜底（§5.4 时序 + [003 §8](./003.LLSC实现原理.md) 保留地 4），这正是"LL/SC 是 Armv8.0 基线"的意义。
5. **"dec_if_positive 也在用 LSE，所以它没有环"**——反例见 §4.3：条件 RMW 在 LSE 路径下仍是乐观 CAS 重试环；"必成"说的是每笔 CAS 自身。
