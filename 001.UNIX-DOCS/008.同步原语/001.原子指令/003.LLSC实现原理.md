## 0. 一句话总结

**LL/SC 不用缓存行独占锁，也不用总线锁——它把"读"和"条件写"拆成两条指令，靠一组"独占监视器（Exclusive monitors）"状态机兑现原子性：`LDXR` 把目标地址登记到本地监视器（local monitor，共享内存时还登记全局监视器 global monitor）；任何观察者对该地址的成功写入都会清除登记；`STXR` 只在"登记仍有效（= 没人抢先写过）"时写成功并返回状态 0，否则返回 1，由软件循环重试。** 所以 LL/SC 的原子性本质是**检测性**的：它不把 read-modify-write 锁死成不可分割的一笔，而是保证"只要 LDXR 之后有别人写过，STXR 就一定失败"，从而让软件在"读→改→条件写"期间没有被别人插队。

> **依据**："原子性 = 监视器检测他人写入"这条叙述中，**前半句是手册原文**（B2-331 明确给出 LDXR/STXR 的配对模型），**后半句（监视器"看见"他人写入靠缓存一致性）是推断**——手册是机制中立的（IMPLEMENTATION DEFINED），但它对 global monitor 提了硬性要求：
> ① **B2-334** —— "Any successful write to the marked block by any other observer in the shareability domain … is **guaranteed** to clear the marking."（共享域内任何其他观察者对标记块的成功写入**必须**清除标记）；
> ② **B2-334** —— global monitor 在有些实现/内存类型上"require functionality **outside the PE**"；
> ③ **B2-334** —— "Any type of memory … that **does not support hardware cache coherency**" 上 global monitor 可能不实现。
> 完整推理链见 §4.3。

## 1. 指令本质：Load-Exclusive / Store-Exclusive 指令对

LL/SC（Load-Linked / Store-Conditional）在 AArch64 里对应 **Load-Exclusive / Store-Exclusive** 指令对（`LDXR`/`STXR`）。它是 **ARMv8 基础指令**（Armv8.0 就有，不属于 FEAT_LSE 扩展），是所有原子操作、自旋锁、信号量的底层地基。

B2-331 给出配对模型（**这是整篇文档的锚**）：

> "The model for the use of a Load-Exclusive/Store-Exclusive instruction pair accessing a non-aborting memory address x is:
> • The Load-Exclusive instruction reads a value from memory address x.
> • The corresponding Store-Exclusive instruction succeeds in writing back to memory address x **only if no other observer, process, or thread has performed a more recent store to address x**. The Store-Exclusive instruction returns a **status bit** that indicates whether the Write Memory succeeded."
>
> 对一个不产生 abort 的内存地址 x，LD/ST 独占指令对的模型是：
> - **LDXR** 从 x 读一个值；
> - **STXR** 只有**在 x 上没有其他观察者/进程/线程执行过更新（more recent）的写**时才写成功，并返回一个**状态位**表示这次写是否成功。

三个关键点：

1. **两条指令**：读（LDXR）和条件写（STXR）是分开的，中间可以插入计算（"读旧值 → 本地算新值 → 尝试条件写"）。
2. **条件写 + 状态位**：STXR 是"试探性"的——成功（status=0）或失败（status=1），失败时**不更新内存**，软件必须**重试**整个循环。
3. **判断依据**：成功与否取决于"这期间有没有人写过 x"——这正是监视器机制要回答的问题（§4）。

### 1.1 与 LSE CAS 的关系（概念分层）

| 概念 | 层次 | 是什么 |
| - | - | - |
| LDXR/STXR（LL/SC） | 指令级 | ARMv8.0 就有的**基础**原子原语（监视器机制） |
| LSE | 指令集层面（架构扩展） | ARMv8.1 引入的**一整族**原子指令 |
| CAS | 指令级 | LSE 家族里的一条指令（带"比较"语义） |
| 实现原理 | 微架构/内存系统层面 | 监视器状态机 vs 缓存一致性点上的原子 RMW——**两条不同的技术路线** |

LSE 官方定位就是**对 LL/SC 的替代**（CAS 文档 §1 已引 C3-393）。两者的根本差异：

| | LDXR/STXR（LL/SC，monitor） | LSE CAS（缓存行独占态 RMW） |
| - | - | - |
| 指令数 | **两条**（LDXR + STXR） | **一条** |
| 结果 | **条件成功**，可能失败，软件负责重试 | **无条件完成**，一次成功（否则异常） |
| 原子性保证机制 | 监视器"检测到别人写过就让它失败" | 一致性点把 RMW 锁成不可分割的一笔 |
| 状态位 | 有（`Ws` 返回 0/1） | 无（返回值永远是旧值） |
| 竞争时 | 反复重试，可能**活锁**（需要前瞻保证） | 不需要重试 |

一句话：**LSE 把"保证没人插队"从"事后检测 + 失败重试"升级成了"事前锁死"，用缓存一致性硬扛原子性，代价是必须独占缓存行；LL/SC 用监视器"事后检测"，代价是可能失败、需要循环。**

## 2. 指令族与编码

### 2.1 指令族（Table B2-3，B2-331）

| 事务大小 | 附加语义 | Load-Exclusive | Store-Exclusive | 其他 |
| - | - | - | - | - |
| 字节 | - | `LDXRB` | `STXRB` | - |
| 字节 | Load-Acquire/Store-Release | `LDAXRB` | `STLXRB` | - |
| 半字 | - | `LDXRH` | `STXRH` | - |
| 半字 | Load-Acquire/Store-Release | `LDAXRH` | `STLXRH` | - |
| 寄存器 | - | `LDXR` | `STXR` | - |
| 寄存器 | Load-Acquire/Store-Release | `LDAXR` | `STLXR` | - |
| 双字对 | - | `LDXP` | `STXP` | - |
| 双字对 | Load-Acquire/Store-Release | `LDAXP` | `STLXP` | - |
| 无 | 清除独占 | - | - | `CLREX` |

> 注："寄存器"变体访问 X 寄存器时是 64 位双字，访问 W 寄存器时是 32 位字；"对"变体访问两个寄存器。**CLREX 清本地监视器**（§4.6）。

### 2.2 编码：整个家族是**一条编码**，由字段区分

整个 LDXR/STXR 家族共享同一个主编码空间（C6.2.264 ~ C6.2.267、C6.2.448 ~ C6.2.451 等），由 `size`/`L`/`P`/`o0` 四个字段区分：

```
[31:30] [29:23]  [22] [21] [20:16] [15] [14:10] [9:5] [4:0]
  size   0010000   L    P     Rs     o0   Rt2     Rn    Rt
```

| 字段 | 位 | 含义 |
| - | - | - |
| `size` | [31:30] | 00=字节 / 01=半字 / 10=字(W) / 11=双字(X) |
| `L` | [22] | **1 = Load-Exclusive（LDXR）；0 = Store-Exclusive（STXR）** |
| `P` | [21] | **1 = 双字对（LDXP/STXP）；0 = 单寄存器** |
| `Rs` | [20:16] | Store：**状态寄存器 `Ws`**（0=成功/1=失败）；Load：固定 `11111`（忽略） |
| `o0` | [15] | **0 = 普通（LDXR/STXR）；1 = acquire/release（LDAXR/STLXR）** |
| `Rt2` | [14:10] | 双字对：第二个数据寄存器；单寄存器：固定 `11111` |
| `Rn` | [9:5] | 基址寄存器（唯一寻址模式：基址 + 立即数 0，无偏移） |
| `Rt` | [4:0] | 数据寄存器 |

**同一条编码、同一个字段位**的例子：

| 指令 | `size` | `L`[22] | `P`[21] | `Rs`[20:16] | `o0`[15] | `Rt2`[14:10] |
| - | - | - | - | - | - | - |
| `LDXR Wt,[Xn]` | 10 | 1 | 0 | 11111 | 0 | 11111 |
| `LDXP Xt1,Xt2,[Xn]` | 11 | 1 | 1 | 11111 | 0 | Rt2 |
| `STXR Ws,Wt,[Xn]` | 10 | 0 | 0 | Ws | 0 | 11111 |
| `STXP Ws,Xt1,Xt2,[Xn]` | 11 | 0 | 1 | Ws | 0 | Rt2 |
| `LDAXR Wt,[Xn]` | 10 | 1 | 0 | 11111 | **1** | 11111 |
| `STLXR Ws,Wt,[Xn]` | 10 | 0 | 0 | Ws | **1** | 11111 |

> **acquire/release 只是同一个字段的一个 bit**：`o0=1` 时，Load 侧变 LDAXR（带 acquire），Store 侧变 STLXR（带 release）——除此之外，编码、寻址、监视器机制**完全一样**。

## 3. 操作语义（架构伪代码层面）

### 3.1 LDXR Operation（C6-2386）

```
bits(64) address;
bits(elsize) data;
accdesc = CreateAccDescExLDST(MemOp_LOAD, acqrel, tagchecked, privileged, t);
...
address = X[n, 64];                         // 唯一寻址：基址寄存器
AArch64.SetExclusiveMonitors(address, dbytes, accdesc);   // ★ 标记
data = Mem[address, dbytes, accdesc];                    // 原子读
X[t, regsize] = ZeroExtend(data, regsize);
```

LDXR 的本质动作只有两个：**读 + 标记**。标记动作全在 `SetExclusiveMonitors` 里。

### 3.2 SetExclusiveMonitors（J1.1.3.40，J1-15805/6）——标记动作本体

```
AArch64.SetExclusiveMonitors(address, size, accdesc)
    memaddrdesc = AArch64.TranslateAddress(address, accdesc, aligned, size);
    // 内存/MMU 检查、对齐检查、地址翻译……
    if memaddrdesc.memattrs.shareability != Shareability_NSH then
        MarkExclusiveGlobal(memaddrdesc.paddress, ProcessorID(), size);   // ★ 共享内存才标 global
    MarkExclusiveLocal(memaddrdesc.paddress, ProcessorID(), size);        // ★ 一定标 local
    AArch64.MarkExclusiveVA(address, ProcessorID(), size);                // 可选 VA 记录
```

要点：
1. **local monitor 总是被标记**（无论共享与否）；
2. **global monitor 只在 Shareable 内存被标记**（`shareability != NSH`）——这是后面 §4 一切关于"全局监视器与共享域"讨论的入口；
3. 底层 `MarkExclusiveLocal/Global` 是 IMPLEMENTATION DEFINED 的"登记"动作（J1.3.3.106/107）。

### 3.3 STXR Operation（C6-2768）

```
bits(64) address;
data = X[t, elsize];
bit status = '1';                                   // ★ 默认失败
if AArch64.ExclusiveMonitorsPass(address, dbytes, accdesc) then
    // This atomic write will be rejected if it does not refer
    // to the same physical locations after address translation.
    Mem[address, dbytes, accdesc] = data;           // 条件写（原子）
    status = ExclusiveMonitorsStatus();             // ★ 翻译一致性复核
X[s, 32] = ZeroExtend(status, 32);                  // 状态位写回 Ws
```

关键注释原文：

> "This atomic write will be **rejected** if it does not refer to the same physical locations after address translation."
>
> 如果地址翻译后与标记的物理位置不一致，这次原子写会被**拒**。

要点：
1. `status` 初始化为 `'1'`（失败）——只有 `ExclusiveMonitorsPass` 通过才会被改写为 `'0'`；
2. 写动作通过 `Mem[]` 原子执行，但**是否算成功由监视器状态决定**；
3. `ExclusiveMonitorsStatus()` 做最后一道复核：如果 LDXR 和 STXR 之间 VA→PA 映射变了（如页表被改、break-before-make），即便监视器通过，翻译不一致仍判失败（§3.5）。

### 3.4 ExclusiveMonitorsPass（J1.1.3.37，J1-15804/5）——条件判断本体

```
boolean AArch64.ExclusiveMonitorsPass(address, size, accdesc)
    aligned = IsAligned(address, size);
    if !aligned && UnalignedAccessFaults(...) then AlignmentFault...
    if !IsExclusiveVA(address, ProcessorID(), size) then return FALSE;
    memaddrdesc = AArch64.TranslateAddress(address, accdesc, aligned, size);
    if IsFault(memaddrdesc) then Abort...
    passed = IsExclusiveLocal(memaddrdesc.paddress, ProcessorID(), size);
    ClearExclusiveLocal(ProcessorID());                          // ★ 本地监视器用完即清
    if passed && memaddrdesc.memattrs.shareability != Shareability_NSH then
        passed = IsExclusiveGlobal(memaddrdesc.paddress, ProcessorID(), size);  // ★ 共享内存再查全局
    return passed;
```

要点（这几乎是"STXR 的判定公式"）：
1. **本地监视器先查、且查完就清**（`ClearExclusiveLocal`）——STXR 每次尝试都会消费掉本 PE 的本地标记；
2. **共享内存才查全局监视器**；全局监视器**只查不清**（被清只能靠"别人写了标记块"这件事，§4.4）；
3. 返回 TRUE ⟺（local 通过）∧（共享时 global 也通过）→ 才允许写。

### 3.5 ExclusiveMonitorsStatus（J1.3.3.103，J1-16245）——翻译一致性复核

```
bit ExclusiveMonitorsStatus()
  Returns '0' to indicate success if the last memory write by this PE was to
  the same physical address region endorsed by ExclusiveMonitorsPass().
  Returns '1' to indicate failure if address translation resulted in a
  different physical address.
```

> 返回 '0'：本 PE 上一次内存写与 `ExclusiveMonitorsPass()` 认可的物理地址区间一致（成功）；
> 返回 '1'：地址翻译产生了不同的物理地址（失败）。

这是 LL/SC 对"VA 映射在 LDXR 与 STXR 之间被改"的最后一道防线：写动作按当前翻译落到一个新 PA，但 `ExclusiveMonitorsStatus` 发现它 ≠ 标记时的 PA，于是返回 1——软件看到 STXR 失败。这正是 B2-340 里 "If the mapping of the VA to PA is changed between the LoadExcl instruction and the StoreExcl instruction … the StoreExcl **will not pass its monitor check**" 的伪代码落地。

## 4. 原子性的实现原理（硬件层面）

### 4.1 架构契约（硬件必须兑现的几条）

1. **LDXR 的读是原子的** —— 单寄存器、按访问大小对齐的 load 是 single-copy atomic（B2-246）。LDXP 两个 32 位字、STXP 两个 32 位字也是 single-copy atomic；**成功的 64 位双字对 STXP 使整个 128 位内存位置单拷贝原子更新**（B2-246）。
2. **STXR 是条件写** —— "保证成功"仅当：访问的 PA 被本 PE 标记，且本地监视器 + 全局监视器都在 Exclusive Access 态（B2-335）。否则返回 1、不更新内存。
3. **STXR 一定返回状态位** —— 没有"不确定"的中间态；失败时 `Ws=1`，这是软件重试的驱动信号。

### 4.2 核心机制：两级监视器（local monitor + global monitor）

B2.12 把监视器分成两级，分别对付**非共享内存**和**共享内存**：

#### 本地监视器（local monitor）—— 每个 PE 一个（B2-332）

> "For memory locations for which the shareability attribute is Non-shareable, the exclusive access instructions rely on a **local Exclusives monitor**, or local monitor, that marks the address of the Explicit Memory Read effect generated by any Load-Exclusive instruction executed by the PE."
>
> 对 Non-shareable 内存，独占指令依赖**本地监视器**，它记录本 PE 执行 LDXR 产生的读效应地址。

- **LDXR**：读内存 + 把 PA 标记为 exclusive access，本地监视器进入 **Exclusive Access（置位 set）** 态。
- **STXR**（本地监视器为 Exclusive 时）：
  - 写地址 == 标记地址 → 写发生，status=0；
  - 写地址 ≠ 标记地址 → **IMPLEMENTATION DEFINED 是否写**；
  - 本地监视器无论成败都转 **Open Access（清除 clear）** 态。
- **STXR**（本地监视器为 Open 时）：不写，status=1，状态不变。

本地监视器状态机（Figure B2-4 的文字化）：

```
   Open Access ◄──────────────  Exclusive Access
     (clear)                        (set)
         │                            │ ▲
         │                            │ │ LDXR（本 PE）
         │                            ▼ │
         │       CLREX / STXR / 异常返回 / 写标记块(ID) / 投机原因(允许)
         └──────────────────────────────────┘
```

> 手册对本地监视器实现自由度的注（B2-333）：**本地监视器甚至可以不持有任何 PA**，只需把"任何 STXR 都当作匹配上一次 LDXR 的地址"来处理；它完全可以不知道其他 PE 的 LDXR/STXR。

#### 全局监视器（global monitor）—— 共享域内每个 PE 一个（B2-334）

> "For shareable memory locations, exclusive access instructions rely on: … A **global monitor** that marks a PA as exclusive access for a particular PE. … **Any successful write to the marked block by any other observer in the shareability domain of the memory location is guaranteed to clear the marking.**"
>
> 对共享内存位置，独占指令还依赖**全局监视器**：它为每个 PE 记录其标记的 PA。**共享域内任何其他观察者对标记块的成功写入，都必须清除该标记。**

全局监视器（PE(n)）状态机（Figure B2-5 的文字化）：

```
   Open Access ◄──────────────  Exclusive Access
     (clear)                        (set)
         │                            │ ▲
         │                            │ │ LDXR（PE(n)）
         │                            ▼ │
         │   ·其他观察者 !n 写标记块（必须清）
         │   ·STXR（PE(n) 成功/失败后终态 ID）
         │   ·CLREX（ID）/ 缓存维护（CU）/ 写 Non-shareable(ID)
         └──────────────────────────────────┘
```

要点（B2-335 ~ B2-336）：

1. **架构只为每个 PE 要求一个标记地址**——超过一个即 UNPREDICTABLE/CONSTRAINED UNPREDICTABLE（§6 的 C.U. 清单）。
2. 一个 PE 的 LDXR **不影响**其他 PE 的全局监视器状态。
3. **STXR 的"保证成功"条件**（B2-335 原文）：
   > "The store is guaranteed to succeed only if the PA accessed is marked as exclusive access for the requesting PE **and both the local monitor and the global monitor state machines for the requesting PE are in the Exclusive Access state**."
   >
   > 存储保证成功的条件 = 访问的 PA 已被本 PE 标记 **且** 本地监视器 **与** 全局监视器都在 Exclusive Access 态。
4. 若本 PE **没有标记任何地址** → 一定失败（status=1），全局监视器不受影响。
5. 若本 PE **标记了另一个 PA** → IMPLEMENTATION DEFINED 是否成功（B2-335：成功则 0，否则 1）。
6. 全局监视器**可以放在 PE 内，也可以作为内存接口处的二级监视器**（B2-334 note）；本地 + 全局**可以合并成同一个单元**，只要同时履行两者职责。

> 这两个状态机"动起来"什么样——监视器作为**部件部署在哪**（A.0 部署图）、**成功路径与双核互踢的逐帧时序**（每帧标注 local/global 状态迁移，A.1/A.2），见文末**附录 A**；软件环泳道版与失败原因全景见 [006.LLSC与LSE执行流程图 附录 A](./006.LLSC与LSE执行流程图.md)。

### 4.3 "谁保证原子性"的推理：监视器怎么"看见"别人的写入

**LL/SC 的原子性 = "STXR 成功 ⟺ LDXR 之后到 STXR 之前该地址没被任何人写过"。** 这个"有没有被写过"的判定，就是监视器机制。那么监视器凭什么知道别人写没写？

对**共享内存**，这条观察能力来自缓存一致性系统。推理链：

**前提①（B2-334）—— global monitor 必须"看到"共享域内所有其他观察者的写入：**
> "Any successful write to the marked block by any other observer in the shareability domain of the memory location is **guaranteed** to clear the marking."
>
> 共享域内任何其他观察者对标记块的成功写入，**必须**清除标记。

**前提②（B2-334）—— 这种观察能力可能只能由 PE 之外的功能提供：**
> "in some implementations and for some memory types, the properties of the global monitor **require functionality outside the PE**."
>
> 某些实现/内存类型下，全局监视器的性质需要 **PE 之外的功能**。

**前提③（B2-334）—— 没有硬件缓存一致性，就没有这个保证：**
> "Some system implementations might not implement this functionality for all locations of memory. In particular, this can apply to: **Any type of memory in the system implementation that does not support hardware cache coherency.**"
>
> 某些系统实现可能不为所有内存位置实现该功能，尤其对**不支持硬件缓存一致性的内存**。

**推理：**

```
① 必须观察到"共享域内其他观察者"对标记块的每一次成功写入
② 这种观察能力可能必须在 PE 之外实现
③ 不支持硬件缓存一致性的内存，该能力不保证存在
─────────────────────────────────────────────
⟹ 在"支持硬件缓存一致性的共享内存"上，唯一能同时满足①②③的机制，
  就是缓存一致性系统（一致性点/互连/二级监视器）
⟹ 全局监视器"看别人写没写"的能力，由缓存一致性系统兑现
```

**与 LSE 的对照（这条推理最值得体会的地方）**：LSE 的 CAS 需要一致性系统**主动把缓存行锁定到独占态、把 RMW 锁死**（CAS 文档 §4.2）；而 LL/SC 只需要一致性系统**被动广播/暴露"谁写了这行"**——它是**只读地借用一致性观察能力**，真正把原子性"兑现"出来的是监视器状态机和软件重试。这就是为什么 LL/SC 对一致性硬件的依赖比 LSE 更轻：**一致性系统在 LL/SC 里只是"看门狗"，在 LSE 里才是"锁"**。

**诚实标注**："全局监视器靠缓存一致性观察写入"这句话**没有哪份资料逐字写出**，它是推断。最接近的文本依据按可信度排序：

1. **ARM ARM B2-334** —— ①"必须清除标记" + ②"可能需要 PE 之外功能" + ③"不支持一致性则不保证"，三者合起来指向一致性系统。这是本文真正的**手册依据**。
2. **Arm Learn-the-Architecture** 及处理器 TRM —— 会描述 global monitor 在一致性域/内存接口的实际落点（如 Cortex/Neoverse TRM 里 L2 或内存接口的 exclusive monitor），供查阅。

### 4.4 内存类型限制

- **Non-shareable**（B2-332）：只用本地监视器，本 PE 自足，**不需要**任何共享域机制。这决定了对 Non-shareable 内存，LL/SC 只能保证"本 PE 内检测到改写"，**不能跨 PE 互斥**。
- **Shareable + cacheable**（B2-334）：本地 + 全局监视器，全局监视器观察共享域写入——这是**多核互斥唯一被架构保证的配置**。架构保证全局监视器实现的内存类型只有：
  > "Inner Shareable, Inner Write-Back, Outer Write-Back Normal memory" 和 "Outer Shareable, Inner Write-Back, Outer Write-Back Normal memory"。
- **Non-coherent / Non-cacheable**（B2-334）：全局监视器可能**根本不实现**。此时执行 LDXR/STXR 的后果（之一）：
  - 产生 External abort；
  - 产生 IMPLEMENTATION DEFINED MMU fault（`ESR_ELx.DFSC = 110101`）；
  - 当作 NOP；
  - LDXR 当作访问 Non-shareable，但本地监视器状态 UNKNOWN；STXR 类似，且双字对可能**非原子**；
  - STXR 结果寄存器 UNKNOWN。
- 这也是内核里对 non-cacheable 内存做同步要格外小心的原因（同 CAS 文档 §4.3）。

### 4.5 Exclusives reservation granule：标记粒度与"伪共享"

B2-337（标记与标记块大小）：

> "When a Load-Exclusive instruction is executed, a marked block of size **2ᵃ** bytes is created by ignoring the least significant bits of the memory address. … The size of the marked memory block is called the **Exclusives reservation granule**. The Exclusives reservation granule is **IMPLEMENTATION DEFINED in the range 4-512 words**."
>
> LDXR 通过忽略地址低位产生一个 **2ᵃ** 字节的标记块，其大小称为 **独占保留粒度（Exclusives reservation granule）**，IMPLEMENTATION DEFINED，范围 **4 ~ 512 字**（即 a ∈ [4, 11]）。

例子（B2-337）：a=4 时，对 0x341B4 成功的 LDXRB 会用地址 bits[47:4] 标记 0x341B0 ~ 0x341BF 四个字。

含义与后果：

1. **STXR 到标记块内任何地址都会清除标记**（B2-331）；
2. **任何其他观察者对标记块内任何地址的成功写入都会清除标记** → 别人写"相邻的字节/字"也会让你的 STXR 失败。**这就是 LL/SC 的"伪共享"损耗**——粒度越大，越容易被人误伤、越容易失败重试；
3. `CTR_EL0.ERG`（D24-8516）报告 `Log2(标记块字数)`；若实现不提供，**软件必须按最大 512 字假设**；
4. B2-339：架构对标记块大小设了 **2048 字节上限**；Arm 强烈建议被独占访问的对象按粒度**错开**（性能建议），并建议 LDXR 与 STXR 之间不超过 **128 字节**（越近越不容易被清标记）。

### 4.6 上下文切换 / 异常返回

B2-337（上下文切换支持）：

> "An **exception return clears the local monitor**. As a result, performing a CLREX instruction as part of a context switch is not required in most situations."
>
> **异常返回会清除本地监视器**。因此大多数情况下，上下文切换并不需要额外的 CLREX。

- 这也体现在伪代码里：`AArch64.ExceptionReturn()` 里第一条动作就是 `ClearExclusiveLocal(ProcessorID())`（J1-15804）。
- `CLREX` 指令本身（C6-1938）：唯一作用就是 `ClearExclusiveLocal(ProcessorID())`——清本 PE 的本地监视器。**它对全局监视器是否起作用是 IMPLEMENTATION DEFINED**（B2-337 note）。

### 4.7 WFE / SEV 集成：监视器被清 = 事件

B2-341：

> "In Armv8, when the global monitor for a PE changes from Exclusive Access state to **Open Access state, an event is generated**."
>
> 当某 PE 的全局监视器从 Exclusive Access 变到 Open Access 时，会**产生一个事件**。

> "This is equivalent to issuing an SEVL instruction on the PE … It **removes the need for spinlock code to include an SEV instruction** after clearing a spinlock."
>
> 这等价于对该 PE 执行 SEVL，**消除了自旋锁释放后还要显式发 SEV 的需要**。

自旋锁优化（B2.12.6、B2-341）：等待者用 `WFE` 睡下；持锁者释放锁（普通 STR 写标记块）→ 让等待者的全局监视器 Exclusive→Open → 产生事件 → 唤醒 WFE。这就是 Linux 自旋锁 `wfe` 提示背后的事件机制。

## 5. Acquire / Release 语义

`LDAXR`/`STLXR` 是 `LDXR`/`STXR` 的 `o0=1` 变体，语义规则（C6-2230、B2-302、B2-337/338 note）：

1. **LDAXR 的 acquire 是有条件的**：目标寄存器不是 WZR/XZR 时才有 acquire 语义（`acqrel = t != 31`，C6-2230）。这跟 CASA 里 `t != 31` 的规则同理（CAS 文档 §2）。
2. **STLXR 的 release 只在写成功时成立**（B2-302、C3-385）：
   > "A Store-Release Exclusive instruction has the **release semantics only if the store is successful**."
   >
   > STLXR 只有在**存储成功**时才具有 release 语义。
   ——与 CAS 文档 §5 引的 C3-397 是同一个道理：没有 store 就没有可 release 的东西。
3. **所有使用限制与原子性性质对 LDXR 的 acquire 变体同样适用**（B2-302 note）：
   > "Each Load-Acquire Exclusive and Store-Release Exclusive instruction is essentially a variant of the equivalent Load-Exclusive or Store-Exclusive instruction. All usage restrictions and single-copy atomicity properties that apply to the Load-Exclusive instructions also apply to the Load-Acquire Exclusive instructions…"
4. 它们支持 **RCsc**（Release Consistency sequentially consistent）模型（B2-301），可省掉显式 `DMB`。
5. `LDAXP`/`STLXP` 访问两个数据元素：双字对成功时产生 128 位 single-copy atomic 更新（C6-2674）。

## 6. LL/SC 的"坑"：使用限制与 CONSTRAINED UNPREDICTABLE

### 6.1 软件必须遵守的配对规则（B2.12.5，B2-338）

软件**能依赖** LDXR/STXR 循环"最终成功"的前提：

| 要求 | 违反后果（CONSTRAINED UNPREDICTABLE） |
| - | - |
| LDXR 与 STXR **同一 VA** | STXR 可能过/可能不过，status UNKNOWN，监视器状态 UNKNOWN，数据 UNKNOWN |
| **同一事务大小** | STXR 可能过/可能不过，status UNKNOWN，较大事务大小的数据块 UNKNOWN |
| **同一寄存器数量** | 行为 C.U.，枚举见 §6.2 |
| **Tag Checked 属性一致**（MTE） | STXR 可能过/可能不过，status UNKNOWN，数据 UNKNOWN |
| **内存属性一致** | STXR 可能过/可能不过，status UNKNOWN，STXR 数据 UNKNOWN |

### 6.2 寄存器数量不一致的 C.U. 枚举（B2-340）

LDXP/STXP 与 LDXR/STXR 混配（如 `LDXP` 两个 32 位量后跟 `STXR` 一个 64 位量）时，行为必须是以下**之一**：

1. 产生外部 Data Abort；
2. 产生 IMPLEMENTATION DEFINED MMU fault（`ESR_ELx.DFSC = 0b110101`）；
3. 总是失败（status=1）；
4. 总是成功（status=0）；
5. 与"使用正确大小和寄存器数量"时的成败行为相同。

### 6.3 前瞻（forward progress）保证与活锁

- **无条件要求**（B2-340）："In the event of repeatedly-contending LoadExcl/StoreExcl instruction sequences from multiple PEs, an implementation **must ensure that forward progress is made by at least one PE**."
- 没有 FEAT_LSE 时，LL/SC 循环**保证**前进的前提（B2-339，节选核心）：
  - LDXR 与 STXR 之间：没有显式内存效应、软件预取、系统寄存器写、地址翻译指令、缓存/TLB 维护、异常产生/返回、ISB、间接分支或 BL；
  - STXR 失败到重试 LDXR 之间：对保留粒度内地址无 store/PRFM/RPRFM、无不同 VA 别名的 load/预取、无其他 STXR、无系统寄存器写/翻译/维护/异常/间接分支/BL、所有 load/store 限于不超过 512 字节的连续虚拟内存块。
- 监视器**可以在任何时刻被清**（无应用原因），只要"不是系统地重复到阻止某个线程在有限时间内前进"（B2-339）。
- 别的 PE 在紧循环里反复对标记块做 store/带写意图的预取/DC clean/invalidate/IC invalidate/TLB 维护，可以**合法地**让你一直不前进——这是 LL/SC 竞争下的理论活锁来源，也是 LSE 要消灭的问题。
- 其他：**Data Abort 后监视器状态 UNKNOWN**（B2-339）；缓存维护指令对 Exclusive 态监视器的效果是 **CONSTRAINED UNPREDICTABLE**（可能清也可能不清，B2-340）；`PRFM PST*`/`RPRFM` 也可能清掉别的 PE 的标记（B2-340）。

## 7. 与 Linux 内核的对应

> 本节按 **5.9 树**（`CONFIG_ARM64_LSE_ATOMICS` 与 `__LL_SC_FALLBACK` 皆 5.9 时代机制）；7.1.3 的演进（配置项已删除、`alternative_has_cap_likely` 分支补 NOP 选路）见 [005.LSE内核实现 §5/§8](./005.LSE内核实现.md)。

内核把 LL/SC 实现放在 `arch/arm64/include/asm/atomic_ll_sc.h`（无 LSE 的 CPU 的主路径；启用 `CONFIG_ARM64_LSE_ATOMICS` 时经 `__LL_SC_FALLBACK` 变成 LSE 路径的**cold 回退**——宏把 LL/SC 序列挪进 `.subsection 1` 冷区，热区由 ALTERNATIVE 补成 LSE 指令，见 [atomic_ll_sc.h:20](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/arch/arm64/include/asm/atomic_ll_sc.h)）。

### 7.1 原子操作：LDXR → 运算 → STXR → 失败重试

```c
// atomic_ll_sc.h —— ATOMIC_OP 宏（示意）
"	prfm	pstl1strm, %2\n"      // 预取（性能）
"1:	ldxr	%w0, %2\n"            // LDXR  读旧值 + 标记
"	" #asm_op "	%w0, %w0, %w3\n"   // 本地运算（add/sub/…）
"	stxr	%w1, %w0, %2\n"        // STXR  条件写，状态进 %w1
"	cbnz	%w1, 1b\n"             // 失败(≠0) → 回到 1: 重试
```

这正对应手册模型：**LDXR 读 + 标记 → 本地算 → STXR 条件写 → 失败循环**。`_acquire`/`_release` 变体把指令换成 `ldaxr`/`stlxr`（§5 的 `o0=1` 变体）。

### 7.2 CAS：用 LL/SC 模拟"读-比较-写"

```c
// atomic_ll_sc.h —— __CMPXCHG_CASE 宏（示意，LL/SC 版 CAS）
"1:	ld" #acq "xr" #sfx "	%" #w "[oldval], %[v]\n"      // LDXR 读旧值
"	eor	%" #w "[tmp], %" #w "[oldval], %" #w "[old]\n"   // 旧值 ^ 期望值
"	cbnz	%" #w "[tmp], 2f\n"                             // ≠0 → 不等，跳走(返回旧值)
"	st" #rel "xr" #sfx "	%w[tmp], %" #w "[new], %[v]\n"  // STLXR 条件写新值
"	cbnz	%w[tmp], 1b\n"                                  // 写失败 → 重试
"2:"	                                                    // 比较失败出口
```

两层失败都要处理：
- **比较失败**（`eor+cbnz` → 跳到 `2:`）：不等，返回读到的旧值，不再写——对应"条件写"里的**比较**语义；
- **写失败**（`stxr` 状态 ≠0 → 跳回 `1:`）：监视器被清/被抢，重读重试——对应 LL/SC 的**重试**语义。

### 7.3 自旋锁与 WFE

> **勘误（5.9 与 7.1.3 实测）**：此前的表述"自旋锁用 `ldaxr`/`stlxr` 抢锁循环"描述的是 Linux ≤5.0 时代的 arm64 票锁，现已过时——两个树的 `arch/arm64/include/asm/spinlock.h` 里**没有**任何 `ldaxr`/`stlxr` 抢锁代码，只有 `#include <asm/qspinlock.h>` 与 `<asm/qrwlock.h>`。

主内核自旋锁是 **queued spinlock**，LL/SC 的存活位置如下：

- **快路径**：一条 CAS-acquire 抢 locked 位（`atomic_try_cmpxchg_acquire`，LSE 即 `casa`——[005 §4.1](./005.LSE内核实现.md)）；
- **慢路径**：排队后用 `smp_cond_load_relaxed()` 等待队首交接，落到 `__cmpwait`（`sevl/wfe/ldxr`，见 [005 §4.4](./005.LSE内核实现.md)）——`ldxr` 在这里是**事件登记**：释放者的 store 清掉等待者的全局监视器 → 产生事件唤醒 `wfe`（§4.7 的 B2-341 机制），因此不必显式 `sev`；
- **票锁形态**（`ldaxr/stxr` 取号环 + `wfe` 自旋）如今存活在 KVM nVHE 的 hyp 锁：[nvhe/spinlock.h](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kvm/hyp/include/nvhe/spinlock.h) 取号 `ldaxr/stxr`（或 LSE `ldadda`）、等待 `wfe/ldaxrh`（005 §5.2 有完整走读）。

## 8. LSE 时代的 LL/SC：替代与保留地

> 本节讲"怎么共存"；两条路线的全景区别总表见 [004.LLSC与LSE的区别.md](./004.LLSC与LSE的区别.md)。

FEAT_LSE（v8.0 起可选、**Armv8.1 起强制**，A2-97）把最常见的"读-改-写"做成了单条指令，本页的重试环大多能一一对应替换——且 LSE **没有 ERG 标记粒度/伪共享问题**（§4.5），**不受 B2.12.5 配对限制**（§6.1），也不需要前瞻保证（§6.3）：

| 本页的 LL/SC 重试环 | LSE 单条指令 | 语义 |
| - | - | - |
| §7.1 `ldxr`/`add`/`stxr` 循环 | `LDADD`（[atomic_lse.h:57](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/arch/arm64/include/asm/atomic_lse.h) `ATOMIC_FETCH_OPS(add, ldadd)`） | 原子加，返回旧值 |
| 同门 and/or/xor | `LDCLR` / `LDSET` / `LDEOR`（atomic_lse.h:54-56） | 原子位运算 |
| `__XCHG_CASE` 的交换环 | `SWP` | 原子交换（xchg） |
| §7.2 LL/SC 版 cmpxchg | `CAS` / `CASP`（128 位） | 比较-交换 |
| `ldaxr`/`stlxr`（§5 的 o0=1 变体） | A/L/AL 后缀（`LDADDA`/`SWPL`/`CASAL`…） | acquire/release 语义 |

内核（5.9）的落地是**编译期生成两份、启动期按 CPU 能力打补丁**：[lse.h:40](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/arch/arm64/include/asm/lse.h) 的 `ARM64_LSE_ATOMIC_INSN(llsc, lse)` = `ALTERNATIVE(llsc, __LSE_PREAMBLE lse, ARM64_HAS_LSE_ATOMICS)`——有 LSE 就把 LL/SC 内联 asm 原地补丁成 LSE 指令，没有就保留本页的重试环。

但 LSE 只覆盖**固定语义**的 RMW（Read-Modify-Write，读-改-写：读旧值→计算→写回，定义见 [README](./README.md)），LL/SC 并没有被淘汰，仍有四块保留地：

1. **等待（cmpwait）**：LSE 没有"等待"类指令，`smp_cond_load_*` 的 `sevl; wfe; ldxr` 序列至今仍用 `ldxr`（[cmpxchg.h:253](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/arch/arm64/include/asm/cmpxchg.h) `__CMPWAIT_CASE`）——靠"监视器被远端写清除 → 产生事件"唤醒 WFE（§4.7），LDXR 在这里是**事件登记**，不是原子读。
2. **中间夹任意计算**：LSE 每条指令语义固定（加/交换/比较…）；"读旧值 → 任意计算 → 条件写回"的非标准 RMW（如 `cmpxchg_double` 的 `LDXP/STXP` 实现，cmpxchg.h:137 `__CMPXCHG_DBL`）仍只能 LL/SC。
3. **128 位**：LSE 基础族最宽 64 位，FEAT_LSE128 之前的 128 位原子只能 `LDXP/STXP`（§2.1 双字对）。
4. **基线兼容**：LDXR/STXR/CLREX 是 Armv8.0 强制指令，LSE 到 Armv8.1 才强制（v8.0 世代核心如 Cortex-A53/A57 没有 LSE）——为 v8.0 编译的用户态代码、alternatives 补丁生效前的 early boot 代码，跑的仍是本页的 LL/SC 环。

> 一句话：**原子运算交给 LSE（单条、免重试、无 ERG 伪共享），两级监视器与 CLREX 退守"等待 / 非标准 RMW / 128 位 / 基线"四块保留地**——这就是"LSE 不用监视器 ≠ 监视器被淘汰"的准确边界（两级监视器与一致域的对齐视角见 [005.缓存一致性 附录 A.4](../../003.高速缓存/005.缓存一致性.md)）。

## 附录 A：逐帧时序——把两级监视器放进双核时间线

> §4.2 的两个状态机是"静"的；本附录把它们放进"动"的时间线，与 [002.CAS 附录 A](./002.CAS实现原理.md)（行锁窗口逐帧）同一套路、可直接对照。软件环×硬件泳道版、STXR 失败原因全景、总线事务视角在 [006.LLSC与LSE执行流程图 附录 A](./006.LLSC与LSE执行流程图.md)，此处不重复。

### A.0 独占监视器在哪：部署图（先认清"部件"，再看它动）

监视器不是一块独立芯片，而是**贴着一致性路径的一组状态**（每格即 §4.2 状态机里的一个 Open/Exclusive 位）：

```
 ┌────────── PE0 ──────────┐          ┌────────── PE1 ──────────┐
 │  L1 D-cache             │          │  L1 D-cache             │
 │  ┌────────────────────┐ │          │  ┌────────────────────┐ │
 │  │ local monitor (0)  │ │  每 PE   │  │ local monitor (1)  │ │ ← 只管本 PE 的
 │  │ [Open/Exclusive]   │ │  一个    │  │ [Open/Exclusive]   │ │   LDXR/STXR,
 │  │ (可不存 PA,B2-333) │ │          │  └────────────────────┘ │   看不见别人
 │  │ global(x):PE0      │ │  每 PE   │  │ global(x):PE1      │ │ ← 只登记"PE1 标
 │  │ [Open/Exclusive]   │ │  每地址  │  │ [Open/Exclusive]   │ │   记了 x",PE0 的
 │  │  ↑标记块=ERG 字节   │ │  一份    │  └────────────────────┘ │   LDXR 不影响它
 │  └─────────┬──────────┘ │          │  ┌────────────────────┐ │
 └────────────┼────────────┘          │  │ global(y):PE1 …    │ │
              │ ldxr/stxr/普通读写     │  └────────────────────┘ │
              ▼                        └────────────┬────────────┘
 ┌────────────────────────────────────────────────────────────────┐
 │  一致性系统（簇内 = DSU 的 SCU/L3；簇间 = 互连，分层见          │
 │  [005.缓存一致性 附录 A](../../003.高速缓存/005.缓存一致性.md)） │
 │                                                                │
 │   职责（B2-334 的观察能力，§4.3 推理链）：                       │
 │   把"谁写了标记块"广播给监视器 ⇒ 写 x 的事务经过这里时，         │
 │   顺手把 global(x):其他PE 清成 Open                             │
 │                                                                │
 │   实现自由（B2-334 note，§4.2 要点 6）：global monitor 的        │
 │   "每 PE 一份"状态也可以不放在各 PE 里，而做成内存接口/          │
 │   一致性点处的【二级监视器】（按 PA 记录"哪个 PE 标记了它"），    │
 │   local+global 甚至可合并为一个单元                              │
 └────────────────────────────────────────────────────────────────┘
```

读图三句：

1. **local 是"私表"**：每 PE 一份，只记自己（甚至可以不存地址，B2-333）；他人写内存**碰不到它**——所以共享内存上单靠 local 不够。
2. **global 是"公表"**：按"地址 × PE"登记（每 PE 每地址一份状态），谁都能通过一致性系统**改别人那一格**（写标记块必清，B2-334）——多核互斥全靠它。
3. **清除的通路**：PE1 的写 → 一致性系统（snoop/无效化事务）→ 顺路清 `global(x):PE0`。这就是 A.2 t6 那一格 `clear!` 的物理通路。

### A.1 成功路径：从 LDXR 到 STXR 全帧

```
  PE0（LL/SC 环）        local(0)  global(x):PE0  一致性系统
────────────────────────────────────────────────────────────────────
t0 ldxr w0,[x] ──读──►                             普通读:行以 S 态回填
t1  SetExclusiveMonitors:
    local 无条件置位            set ─┐
    共享内存 ⇒ global 也置位         └─► set(x)
t2 add w0,w0,w3        （窗口内无人动 x）
t3 stxr w1,w0,[x]
t4  ③ IsExclusiveLocal? Exclusive ✔
    查完即清(一次一消费)       clear
t5  ④ IsExclusiveGlobal?      Exclusive ✔(只查不清)
t6  ⑤ 真要写 ⇒ 此刻才"谈独占":                    SnpUnique 一族把行
    他核 S 副本退 I / 本地 S→E→M,                  谈成 PE0 可写,
    写入 newvalue              (随写清除)          然后写入
t7  w1=0,环退出               global(x):PE0 → Open(STXR 后终态,§4.2 Figure B2-5)
```

帧注：

- **t1 只需普通读**——LL/SC 的"拿独占"是**惰性的**：LDXR 只做登记（监视器置位），真正去一致性系统"谈独占"推迟到 t6 真要写的那一刻（对照 CAS：RMW 一进门就谈，002 附录 A.2 的 t1~t3）。这是两者对一致性硬件依赖轻重的根源（§4.3）。
- t4/t5 的**查/清不对称**（local 查完即清、global 只查不清）速查表见 006 A.4。
- t6 那一笔"谈独占 + 写"与 CAS 附录 A.2 的 t2~t7 完全同构——**STXR 成功的写，本质就是一次微缩 CAS**；差别只在 LL/SC 把"比较"环节交给了软件环。

### A.2 互踢路径：两个 PE 同时 LDXR 同一地址

手册允许——每 PE 一套 global 状态，**别人的 LDXR 不清你的标记**（B2-335，§4.2 要点 2）。于是经典"互踢"上演（泳道按 A.0 部署位画：监视器贴在各 PE 侧，一致性系统居中当"传令兵"）：

```
   PE0(软件)        监视器·PE0 侧       一致性系统             PE1(软件)        监视器·PE1 侧
                 local0    g[x]:PE0   (SCU/L3→互连)                        local1    g[x]:PE1
 ───────────────────────────────────────────────────────────────────────────────────────────
t0 ldxr w0,[x]
   └──登记──►      Exc       Exc      (普通读,行以 S 态回填;
                                        不谈独占,见 A.1 帧注)
t1                                      ◄── ldxr w9,[x] ──┐
                                         (普通读)          └──登记──►     Exc       Exc
   (PE1 的 LDXR 不碰 PE0 侧任何一格——每 PE 一套,B2-335)
t2 add w0,w0,#1                                           add w9,w9,#1
t3 stxr w1,w0,[x](先到)
t4  ├─③查 local0: Exc ✔──查完即清──►    Open
t5  ├─④查 g[x]:PE0: Exc ✔(只查不清)
t6  └─⑤写 x ─────► 谈独占+写(SnpUnique 一族):
                    g[x]:PE0 → Open(写后终态)
                    ───── 写事务 + "标记块被写"广播 ─────►
                                        PE1 若持 S 副本:退 I
                                        ─────────────────────────────────►  清! g[x]:PE1
                                                                              → Open
t7 w1=0 ✔ 环退出                                          stxr w2,w9,[x]
                                                          ├─③查 local1: Exc ✔──清──► Open
                                                          └─④查 g[x]:PE1: Open ✘
                                                           ⇒ 不写内存, w2=1
                                                           cbnz ⇒ 回 ldxr 重来
                                                           (重读到的 w9 已是 PE0 写后的新值)
```

帧注：

- **t6 是全局监视器"看见别人写"的兑现时刻**：PE0 的写经一致性系统广播，同时清掉 PE1 侧 `g[x]:PE1` 那一格——这条**清除通路**就是 A.0 读图第 3 句（写 → 一致性系统 → 顺路清别人那一格），观察能力来自一致性系统（§4.3 的推理链①②③）；
- 两人都 LL、一先一后 SC：**先到先得，后到被踢**——没有排队（对照 LSE 在一致性点/HN-F 的"排队串行化"，006 §5/§7）。这就是高争用下 LL/SC"互踢重试"损耗的来源，也是内核原子操作的 `-mtune` 里 LSE 优先的动因（§8）；
- **ERG 伪共享变体**（§4.5）：把 t6 里"PE1 持 S 副本"换成"PE1 写的是同标记块内的相邻变量"——标记按块清、不看地址相等，时序完全同上，PE0 照样被误伤。

### A.3 与 CAS 行锁窗口并排对照

| | CAS（[002 附录 A](./002.CAS实现原理.md)） | LL/SC（本附录） |
| - | - | - |
| 何时"谈独占" | RMW 一进门就谈（其 t1~t3） | **惰性**：LDXR 只登记，STXR 真要写才谈（A.1 t6） |
| 原子性载体 | 行锁窗口：在途事务占住该行修改权 | 监视器状态机：local + global 双 Exclusive |
| 别人插队会怎样 | 被行锁挡住（等待/重试），窗口外必见新值 | **不挡**——只把你的标记清掉 ⇒ 你的 STXR 失败 ⇒ 软件重试 |
| 失败语义 | 无失败态（要么完成、要么异常） | status=1；重试责任在软件（`cbnz` 环） |
| 并发同址两请求 | 在一致性点**排队串行化**（006 §7） | **互踢**：都标记、先后 SC、后到者被踢（A.2） |
| 对一致性系统的角色 | 主动借"**锁**"（行级修改权） | 只借"**看门狗**"（观察谁写了，§4.3） |
