## 0. 一句话总结

**CAS 不是靠 monitor，也不是靠总线锁——它把"读-比较-写"做成一笔缓存一致性事务，在缓存行的独占态上执行，由缓存一致性协议充当原子性的保证者。** 所以它只在 coherent cacheable 内存上被架构保证原子性，这也是 LSE 相比 LL/SC 无重试、可扩展的根源。

> **依据**："由缓存一致性协议充当原子性的保证者"**不是手册原文**（手册机制中立，IMPLEMENTATION DEFINED），而是手册三处约束的必然推论：
> ① **B2-249** —— 原子性只在 Shareable + Write-Back 的 Normal 可缓存内存被保证；
> ② **B2-249** —— "不支持硬件缓存一致性"的内存不保证原子性，且保证者来自 **PE 之外的内存系统**；
> ③ **B2-248** —— 手册把 single-copy atomicity 定义为一致性序（Coherence-after）上的性质。
> 完整推理链见 §4.2.1。

## 1. 指令本质：LSE 的"读-比较-写"原子操作

CAS 家族属于 **FEAT_LSE（Large System Extensions）**（ARMv8.1 引入）。它是对传统 LL/SC 对（`LDXR`/`STXR`）的替代：

> "The atomic instructions perform atomic read and write operations on a memory location such that the architecture guarantees that no modification of that memory location by another observer can occur between the read and the write."（C3-393）
>
> 原子指令会对内存位置执行原子的读和写操作。架构保证，在**读**和**写**之间，其他观察者（other observer）无法对该内存位置进行任何修改。

- LL/SC 需要"加载-尝试存储-失败重试"的循环，竞争激烈时反复回退；
- LSE CAS 是**单条指令**完成整个 read-modify-write（RMW），不需要重试。

### 1.1 CAS 与 LSE 的关系（概念分层）

"CAS 的实现原理"和"LSE"不是同一层面的概念，要分清三层：

| 概念 | 层次 | 是什么 |
| - | - | - |
| LSE | 指令集层面（架构扩展） | ARMv8.1 引入的**一整族**原子指令 |
| CAS | 指令级 | LSE 家族里的**一条指令**（带"比较"语义） |
| 实现原理 | 微架构/内存系统层面 | 一致性点上的原子 RMW——**整族共享** |

准确说法：**CAS 属于 LSE；所有 LSE 原子指令共享同一套实现原理（缓存一致性点上的原子 RMW，非 monitor、非总线锁），CAS 只是其中"比较-条件写"的一员。**

#### LSE 是一个"家族"，不只是 CAS
从 C3-393 的表 C3-48 可见，LSE 原子指令族包括（每个还有 acquire/release 变体）：

- `LDADD` / `LDCLR` / `LDEOR` / `LDSET` —— 算术/位操作
- `LDSMAX` / `LDSMIN` / `LDUMAX` / `LDUMIN` —— 最大/最小值
- `SWP` —— 交换
- `CAS` / `CASP` —— 比较并交换
- 不带返回值的 `ST<OP>` 版本（`STADD`、`STCLR`……）

以及后续扩展：**FEAT_LSE2**（放宽原子性规则）、**FEAT_LSE128**（128 位原子）。

#### CAS 相对其他 LSE 的"特殊之处"
它们共享实现原理（单笔一致性 RMW），区别在**语义**：

| | 其他 LSE（LDADD/SWP…） | CAS |
| - | - | - |
| 写内存 | **无条件**（一定写） | **条件**（相等才写新值；失败时是否写回旧值由实现决定，见 §3.4） |
| 核心逻辑 | 读 → 算 → 写 | 读 → **比较** → 条件写 |
| 伪代码 | `MemAtomicInt` 里 `result = op1 + op2` 等 | `CASCompare(op1, cmpop, op2)` |

CAS 是 LSE 里**唯一带条件写**的那一类（CASP 是它的双字对版本）。

## 2. 编码与四个变体

四个变体是**同一条编码**，由指令中的两个 bit（`L`、`o0`）区分：

```
[31:30] [29:23]  [22] [21]  [20:16] [15] [14:10] [9:5] [4:0]
   1x   0010001   L    1     Rs      o0   11111   Rn    Rt
```

- `Rs`（被比较并装载的寄存器）：比较值来源 + 旧值回写目标
- `Rt`（被条件存储的寄存器）：新值（newvalue）
- `Rn`：基址寄存器或 SP（唯一寻址模式：基址寄存器，无偏移）

| Mnemonic | `L` bit | `o0` bit | 内存序 |
| - | - | - | - |
| `CAS` | 0 | 0 | 无（plain） |
| `CASA` | 1 | 0 | acquire |
| `CASL` | 0 | 1 | release |
| `CASAL` | 1 | 1 | acquire + release |

Decode（C6-1871）直接给出语义开关：

```
acquire = L == '1' && t != 31;   // 只有 Rt 不是 WZR/XZR 才有 acquire
release = o0 == '1';
```

**关键点**：即便指令编码是 CASA（L=1），如果 `Rt` 写的是 `WZR/XZR`，就**没有 acquire 语义**。注意 gating 挂在 **Rt（新值寄存器）**上，而读出的旧值回写的是 Rs——手册 decode 原文如此（`acquire = L == '1' && t != 31`），勿按"旧值回写寄存器"直觉理解。另：这条"数据寄存器 = WZR ⇒ 无 acquire"是**全族规则**——LDADD/SWP 的 decode 同样带 `Rt != '11111'` 门控（C6-2199/2801），连裸 LDAR 也是 `t != 31`（C6-2222）。

## 3. 操作语义（架构伪代码层面）

### 3.1 指令 Operation（C6-1872）

```
comparevalue = X[s, datasize];      // 从 Rs 取比较值
newvalue     = X[t, datasize];      // 从 Rt 取新值
data = MemAtomic(address, comparevalue, newvalue, accdesc);
X[s, regsize] = ZeroExtend(data, regsize);   // 读到的旧值写回 Rs
```

指令只调用一个核心函数 `MemAtomic`，真正的原子性由它保证。

### 3.2 MemAtomic 核心伪代码（J1-15838）——原子性的关键

```
// 内存/MMU 检查、地址翻译、tag 检查……
if memaddrdesc.memattrs.shareability != Shareability_NSH then
    ClearExclusiveByAddress(...);          // 副作用：清掉独占监视器

// ★ 决定性注释：
// All observers in the shareability domain observe the following load and store atomically.
(memstatus, oldvalue) = PhysMemRead(memaddrdesc, bytes, accdesc);
...
(newvalue, cmpfail, retvalue) = MemAtomicInt(accdesc.modop, oldvalue, operand, cmpoperand);
//                                        └─ 对 CAS 而言即调用 CASCompare()

requirewrite = (!cmpfail || ConstrainUnpredictableBool(Unpredictable_WRITEFAILEDCAS));
...
if requirewrite then
    memstatus = PhysMemWrite(memaddrdesc, bytes, accdesc, newvalue);
    //                        └─ 落点=memaddrdesc,即 Xn 指向的那份内存本身;
    //                           此处形参名叫 newvalue,实际就是 CASCompare 的
    //                           memresult(见 §3.4 名字对照)
...
return retvalue;    // 返回操作前的旧值
```

要点：
1. **读和写对共享域内所有观察者原子可见** —— 架构层面的硬性保证。
2. 比较**成功**才一定写 `newvalue`；**失败**时是否写由 `Unpredictable_WRITEFAILEDCAS` 约束决定——实现可以不写、也可以把旧值写回原地址（详见 §3.4）。
3. 无论成败都返回旧值。
4. monitor（独占监视器）只被**清除**，不被查询、不参与保证原子性。

### 3.3 CASCompare 函数（J1-15834）——比较逻辑本体

```
CASCompare(oldvalue, comparevalue, newvalue):
    if oldvalue == comparevalue then
        cmpfail  = FALSE;
        memresult = newvalue;          // 相等 → 内存通道要写的值 = Rt 里的新值
        if !Unpredictable_CASRETURNOLDVALUE then regresult = comparevalue;
        else regresult = oldvalue;
    else
        cmpfail  = TRUE;
        memresult = oldvalue;          // 不相等 → 内存通道要写的值 = 刚原子读出的旧值
    return (memresult, cmpfail, regresult);   // 注意:这里只是"算出三个结果",
                                              //     写内存/写寄存器都不在本函数里
```

### 3.4 memresult 写回哪里、regresult 去哪——两条独立通道

`CASCompare` **只做比较、不落任何东西**；落点在调用方 `MemAtomic`（§3.2）与指令层（§3.1）。三处伪代码用了两套变量名，对照如下（重名正是歧义之源）：

```
 CASCompare 返回           MemAtomic 接包(§3.2,名字换了!)          最终落点
 ─────────────────────────────────────────────────────────────────────────
 memresult ───────────► newvalue ──► PhysMemWrite(memaddrdesc,…,newvalue)
                                    │ 落点 = Xn 指向的那份内存本身(同一地址!)
                                    │ ·比较成功: 写 Rt 的新值
                                    │ ·比较失败: 写回刚读出的 oldvalue——
                                    │  是否真写由 requirewrite 决定:
                                    │    requirewrite = !cmpfail ||
                                    │      ConstrainUnpredictableBool(
                                    │        Unpredictable_WRITEFAILEDCAS)
                                    │  失败时实现"写/不写"二选一,软件不可依赖
                                    └─ 不是写寄存器、不是写别处内存
 regresult ───────────► retvalue ──► MemAtomic 返回给指令层
                                    └► X[s] = ZeroExtend(data) (§3.1)
                                       落点 = Rs 寄存器,值 = 内存操作前的旧值
 cmpfail ─────────────► cmpfail ───► 只用于 requirewrite 判定,不暴露给软件
```

把"旧值写回"说清楚，就是三句话：

1. **写回哪里**：`memresult`（失败时 = oldvalue）唯一可能的落点是 **CAS 指令的内存操作数本身**——`Xn` 指向、经 `MemAtomic` 翻译出的那个地址。"写回"是**把刚原子读出的值再写回同一地址**（同值重写），不是写到 Rs、也不是写到其他位置。
2. **失败时到底写不写**：由 `requirewrite` 三态决定——成功：必写新值；失败：`Unpredictable_WRITEFAILEDCAS` 允许实现**二选一**（省掉写周期，或完成"写回旧值"的写周期）。手册这样写的原因：对 Normal 内存，**同值写回对任何观察者不可观测**（值没变），所以"失败也盲写"是最省硬件逻辑的 RMW 实现路径，架构索性放开；软件唯一能依赖的是**无论写没写，内存可见值都等于没写过**。
3. **别和寄存器通道混淆**：`regresult → X[s]` 这条线才是"旧值装进 **Rs** 寄存器"（§3.1 的 `X[s, regsize] = ZeroExtend(data)`），它**无条件**发生（无论成败，Rs 都得到内存操作前的旧值）。"旧值写回内存（失败时、可能）"与"旧值装入 Rs（总是）"是两个不同动作、不同目的地。

> 附带一个工程视角：对 Device 内存/MMIO，"写回同值"未必无副作用（某些寄存器写即触发动作）——所以手册把失败写回收进 Unpredictable 而不是规定"必须写"或"必须不写"；对 MMIO 用 CAS 本就不在架构保证范围内（§4.1 第 2 条），这里的辨析只是把伪代码读透。

## 4. 原子性的实现原理（硬件层面）

### 4.1 架构契约（硬件必须兑现的三条）

1. **读+写不可分割** —— `MemAtomic` 伪代码：所有共享域观察者原子可见，中间无缝隙。
2. **原子性只在 cacheable 内存上被保证**（B2-249）—— 理解实现原理的最重要一句话：
   > "The memory types for which it is architecturally guaranteed that the atomic instructions will be atomic are:
   > **Inner Shareable, Inner Write-Back, Outer Write-Back Normal memory**；
   > **Outer Shareable, Inner Write-Back, Outer Write-Back Normal memory**."
   >
   > 架构保证原子性的内存类型：Inner/Outer Shareable + Inner/Outer Write-Back 的 Normal 可缓存内存。
3. **无条件完成** —— 没有 STXR 那种"失败状态位"，CAS 要么完成，要么异常。

### 4.2 核心机制：在"缓存一致性点"上做原子 RMW

**原理：把 RMW 放到缓存行的"独占态"上执行，让缓存一致性协议充当"锁"。**

```
 核心 (PE)
 ┌──────────────────────────────────┐
 │ 译码 CAS                          │
 │  comparevalue ← X[Rs]            │  从寄存器取比较值/新值
 │  newvalue     ← X[t]             │
 │  计算地址 [Xn|SP]                 │
 │  下发"一笔原子请求"(不是load+store) │
 └──────────────┬───────────────────┘
                │ 单个原子 RMW 请求
                ▼
   内存系统（点对一致性 PoC）
 ┌──────────────────────────────────┐
 │ ① 定位 cache line                │
 │ ② 以独占态(Exclusive/Modified)持有│ ← 关键
 │ ③ 行锁: 阻塞该行的 snoop/一致性事务│ ← 期间无人能插
 │ ④ 读旧值 oldvalue                │
 │ ⑤ 比较 oldvalue == comparevalue  │
 │ ⑥ 相等→写 newvalue; 不等→可选写回 │
 │ ⑦ 返回 oldvalue                  │
 └──────────────┬───────────────────┘
                ▼
     X[Rs] ← oldvalue（返回旧值）
```

> 图中 **②"以独占态持有"和 ③"行锁"** 这两步是原子性的全部机关——独占怎么拿到（谁被无效化）、行锁到底锁住什么（别的核在窗口内会发生什么）、在哪一级缓存执行，逐帧展开见文末**附录 A**。

三个关键环节：

1. **一笔请求，而不是两次访存** —— CAS 在核心/互连层面是单个原子事务（如互连上的 "atomic RMW request"），不是一个 load 再跟一个 store。形式化内存模型 B2-257 专门定义这种配对：
   > "Successful Read-Modify-Write pair: E1 是 Memory Read Effect，E2 是 Memory Write Effect，同一 Location，且 **E1 和 E2 由同一条原子指令产生**。"
   >
   > 读效应和写效应在一致性顺序里被"绑定"成一笔，别的东西插不进来。

2. **独占态 + 行锁 = 不用总线锁** —— 一致性协议本身保证：对一行 cache line，任何时刻只有一个 agent 拥有修改权。CAS 只需把目标行拿到 Exclusive/Modified 态，在行锁窗口内做完读→比较→写，协议保证期间没有其他 agent 能合法碰这行。因此 CAS **不需要**锁总线/锁内存控制器，天然可扩展。

3. **RMW 在哪执行** ——
   - 行已在本地 L1（Exclusive/Modified）→ L1 缓存控制器就地原子执行（缓存管线内的原子 ALU）；
   - 行不在本地 → 原子请求沿一致性域送到该行所在的那级缓存（另一个核的 L1 / L2），在那边独占执行后把旧值带回来。

这正对应 B2-249 的论断：

> "In some implementations ... the properties of atomicity can be met **only by functionality outside the PE**."
>
> 某些实现里，原子性只能由 **PE 之外的功能（缓存一致性系统）** 来满足。

——原子性根本不在 CPU 执行核心里，而是**缓存一致性系统**给的。

#### 4.2.1 "由缓存一致性协议充当保证者"的结论来源与推理链

这句话**不是手册原文**，手册是机制中立的（IMPLEMENTATION DEFINED）。它由手册三处约束推出：

**前提①（B2-249，B2.2.6）—— 原子性只在"可缓存+可共享"内存被保证：**
> "The memory types for which it is architecturally guaranteed that the atomic instructions will be atomic are:
> **Inner Shareable, Inner Write-Back, Outer Write-Back Normal memory**；**Outer Shareable, Inner Write-Back, Outer Write-Back Normal memory**."
>
> 架构保证原子性的内存类型 = **Shareable + Write-Back 的 Normal 可缓存内存**。

**前提②（B2-249，B2.2.6）—— 无硬件缓存一致性的内存不保证原子性：**
> "In some implementations ... the properties of atomicity can be met **only by functionality outside the PE**. Some system implementations **might not support atomic instructions** for all regions of the memory. In particular, this can apply to: **Any type of memory in the system that does not support hardware cache coherency**."
>
> 原子性只能由 **PE 之外的功能**满足；对**不支持硬件缓存一致性**的内存，原子指令可能不被支持。

**前提③（B2-248，B2.2.2）—— 手册自己把"原子性"定义在一致性序上：**
> "A memory access instruction that is single-copy atomic has the following properties:
> 1. ... all of the overlapping writes generated by one of the stores are **Coherence-after** the corresponding overlapping writes generated by the other store. ..."
>
> 手册对 single-copy atomic 的定义本身就用 **Coherence-after（一致性先后序）** 表达。

**推理（把①②③合起来）：**
```
① 保证原子性 ⇔ 内存类型是 "Shareable + Write-Back cacheable"
② 不保证原子性 ⇔ "不支持硬件缓存一致性" 的内存
③ 原子性这个性质，手册自己是用"一致性序(Coherence-after)"定义的
＋ 保证者是 "PE 之外的内存系统"（不是 CPU 执行单元）
─────────────────────────────────────────────
⟹ 在"支持硬件缓存一致性的内存"上，唯一存在且同时缺失于
  "不支持一致性"的内存上的机制，就是缓存一致性协议
⟹ 所以原子性由缓存一致性机制兑现
```

**这是排除法/必要条件推理**：保证存在的场景 = 一致性存在的场景；保证缺失的场景 = 一致性缺失的场景。手册把两者绑死，又明说保证来自 PE 之外的内存系统，"保证者 = 缓存一致性协议"就是唯一自洽的结论。

**佐证与边界（诚实标注）**："由缓存一致性协议充当保证者"这句话**没有哪份资料逐字写出**，它是推断。最接近的文本依据按可信度排序：

1. **ARM ARM B2-249/250** —— 原子性只对 coherent cacheable 内存保证、无硬件缓存一致性不保证。这是本文真正且唯一的**手册依据**。
2. **Arm Learn-the-Architecture《Introduction to Large System Extensions》**（[链接](https://learn.arm.com/learning-paths/servers-and-cloud-computing/lse/intro/)）—— "atomic instructions provide a **non-interruptible read-modify-write sequence in a single instruction**"。只证明"单指令 RMW"，**未提**一致性协议。
3. **StackOverflow #75406033 答案**（[链接](https://stackoverflow.com/questions/75406033/how-is-aarch64-atomic-instructions-of-large-system-extensions-lse-implemented-in)）—— "Arm64 atomic instructions (LSE) are based on **cache-lock (MESI)**"。社区观点，score=1 未采纳，权威性低。
4. **处理器 TRM**（如 Cortex/Neoverse 技术参考手册）—— 通常会描述 LSE 在缓存一致性流水线中的实际实现（独占态 + 缓存控制器内原子 ALU），供查阅。

> ⚠️ **勘误**：此前曾把 **NVIDIA Grace 原子指令指南**（[链接](https://nvidia.github.io/grace-cpu-benchmarking-guide/developer/atomics.html)）列为佐证，**实为错误引用**——该页只讲 LSE 性能提升、Arm 弱内存模型与编译选项（`-mcpu=native`、`-moutline-atomics`、objdump 检查），**通篇没有**"缓存一致性协议充当原子性保证者"的表述，也不涉及缓存行独占态/行锁的实现细节。

### 4.3 内存类型限制

- CAS 只在 coherent cacheable Normal 内存上被架构保证。
- Device / Non-cacheable 内存**没有缓存行可锁**，一致性协议不生效：
  - 硬要做只能退到内存控制器层面加锁（慢得多）；
  - 很多实现干脆不接：可产生同步 External abort / SError / IMPLEMENTATION DEFINED MMU fault（ESR_ELx.DFSC=110101），或直接当 NOP（B2-250）。
- 这也是 Linux 内核里对 non-cacheable 内存做同步要格外小心的原因。

### 4.4 两个 CONSTRAINED UNPREDICTABLE = 实现的自由度

| 开关 | 含义 | 实现选择 |
| - | - | - |
| `Unpredictable_WRITEFAILEDCAS` | 比较失败时**是否写回旧值** | 可以"总是写"（流水线统一走写路径）；也可以"失败不写"（更快） |
| `Unpredictable_CASRETURNOLDVALUE` | 成功时返回**旧值**还是**比较值** | 可以不二次读内存 |

这解释了 CAS 描述里为什么是 "permitted to write the value read"（允许写回，不是必须）。

### 4.5 其他实现细节（C6-1870）

- **`Ws == Wt` 预热 hint**：当 `Rs` 与 `Rt` 指向同一寄存器，硬件被提示"同一地址后面很可能紧跟另一个 CAS"，可提前做缓存行预热/保持，让后续 CAS 更容易成功。ARM 建议配"预期比较会失败"的值使用（失败不写更快）。
- **同步 Data Abort**：`Ws`/`Xs` 被恢复到指令执行前的值。
- **清除独占监视器**：读即使比较失败，也允许清除该地址的独占监视器。

## 5. Acquire / Release 语义

- `CASA`/`CASAL` 的读部分按 **Load-Acquire** 排序；`CASL`/`CASAL` 的写部分按 **Store-Release** 排序，支持 **RCsc**（Release Consistency sequentially consistent）模型（B2-301）。
- **acquire**：该 Load-Acquire 访问必须先于程序序中其后的所有内存访问，被各 PE 观察到。
- **release**：程序序中该 Store-Release 之前的所有内存访问，必须先于该 release 访问被观察到。

**关键约束**（C3-398）：

> "If a compare and swap instruction **does not perform a store**, then the instruction **does not have release semantics**, regardless of the instruction ordering options."
>
> 如果比较失败、未发生写，则即便 CASL/CASAL 也没有 release 语义。

和 B2-302 "A Store-Release Exclusive instruction has the release semantics only if the store is successful" 是同一个道理：**没有 store 就没有可 release 的东西**。

## 6. CAS vs LDXR/STXR（monitor 机制）

monitor（独占监视器）是 **LDXR/STXR 专用**的机制，状态机只围绕 LDXR/STXR 工作（B2-335 ~ B2-336）：

- **LDXR**：把地址标记为本 PE 的 exclusive access（local + global monitor 进入 Exclusive Access 态）。
- **STXR**：**条件存储**——只有 monitor 仍处于 Exclusive Access 态才成功，失败要重试。

| | LDXR/STXR（monitor） | LSE CAS |
| - | - | - |
| 机制 | monitor 标记地址，条件写 | 缓存行独占态上的原子 RMW |
| 结果 | **条件成功**，可能失败，需软件重试 | **无条件完成**，一次成功（否则异常） |
| 状态寄存器 | 有（`Wt` 写状态） | 无（返回值永远是旧值） |
| 重试 | 软件负责 | 不需要 |
| 对 monitor | 依赖 | 只作为副作用**清除**（C6-1870、J1-15838） |

**架构上 CAS 不可能是 monitor 实现的逻辑**：CAS 必须"一定成功"，而 monitor 机制的本质是"条件成功"。所以 CAS 的原子 RMW 只能由一致性机制兑现。

> 补充：个别早期/低成本实现没有专门 LSE 原子硬件，**可能**在内部用独占序列甚至 trap 到固件来模拟 CAS——但那是 IMPLEMENTATION DEFINED 的翻译层，对外仍呈现"无条件一次完成"的架构语义，不属于 CAS 的原理。

## 7. 与 Linux 内核的对应

> 本节按 **5.9 时代**写法；7.1.3 已删除 `CONFIG_ARM64_LSE_ATOMICS`（LSE 路径无条件编译、启动期按 `ID_AA64ISAR0_EL1.Atomic` 探测后打补丁选路），完整演进与两套补丁机制见 [005.LSE内核实现 §5/§8](./005.LSE内核实现.md)。

内核开启 `CONFIG_ARM64_LSE_ATOMICS` 后：

- `atomic_cmpxchg` / `atomic_xchg` 等在 `arch/arm64/include/asm/cmpxchg.h`、`atomic_ll_sc.h` 直接内联发射 `casa`/`casal` 等单条指令；
- 替代 `LDXR/STXR` 重试循环，靠上面这套硬件原子性保证，**不需要软件层面的循环重试**；
- 没有 LSE 的 CPU 回退到 `atomic_ll_sc.h`（LL/SC 版本）。

```c
// arch/arm64/include/asm/cmpxchg.h（LSE 版，示意）
#define __CMPXCHG_CASE(w, sz, name, mb, acq, rel, cl)          \
    asm volatile(                                              \
        "	cas" #mb #acq #rel "	%" #w "[v], %" #w "[n], [%[a]]\n" \
        ...
        : [v] "+&r" (oldval) ...)
```

## 附录 A：②③两步的硬件展开——独占态怎么拿到、行锁锁住什么

> 回答 §4.2 流程图里被一句话带过的两步：②的"独占"是怎么**拿到**的（谁被无效化、走什么事务），③的"行锁"**锁的到底是什么**（别的 agent 在窗口内会发生什么）。MESI 状态表与"簇内 SCU / 簇间 CHI"的分层背景见 [003.高速缓存/005.缓存一致性](../../003.高速缓存/005.缓存一致性.md)。

### A.1 前提不变量：修改权唯一

MESI/MOESI 家族对每个 cache line 维护的不变量（状态表见 [005.缓存一致性 §2](../../003.高速缓存/005.缓存一致性.md)）：

| 状态 | 含义 | 可写 | 全系统同时几份 |
| - | - | - | - |
| **M**odified | 已改（脏，内存过期） | ✔ | **至多 1** |
| **E**xclusive | 独占干净 | ✔ | **至多 1** |
| **S**hared / **O**wned | 共享（干净 / 持有可回填的脏副本） | ✘ | 多份 |
| **I**nvalid | 无 | — | — |

**同一物理行，任意时刻至多一个 agent 持有"可写态"（M/E）**——这份"可写权"就是修改权。于是：

- **② = 把目标行谈成"只有我可写"**（自己进 E/M，别人全部退到 I）；
- **③ = 在读-比-写完成之前不交还这份修改权**。

> 注意：这里的"独占态"是**缓存行**的 MESI 状态（数据的修改权）；LL/SC 侧的监视器也有个 **Exclusive Access** 态，那是**登记标记**、与该行的 M/E/S/I 无关——两个"独占"的辨析见 [003 附录 A.0](./003.LLSC实现原理.md)。

### A.2 逐帧时序：独占怎么拿、行锁怎么挡

```
  核A（执行 CAS）        一致性点 PoC（如 DSU 的 SCU /                    核B（S 态副本）
                         互连 Home Node，见 A.4）
───────────────────────────────────────────────────────────────────────────────────
t0  译码 CAS，发起"一笔原子
    RMW 事务"（不是 load+store）──►
t1                        查该行目录：B 持有 S，A 无副本
t2                        发无效化（CHI 例：SnpUnique）──────────────►   S→I
                          ◄──────────────────── 无效化确认
t3                        授予 A 唯一态：行进 E
   ◄──── 独占到手 ────                                             ══ ②完成 ══
t4  ╔═③ 行锁窗口开始：该行的修改权被这笔在途事务占住 ═════════════════════╗
t5  ║  ④ 从行中读 oldvalue（缓存内读，不再过互连）                        ║
t6  ║  ⑤ 比较 oldvalue == comparevalue                                   ║
t7  ║  ⑥ 相等 → 写 newvalue，行 E→M；不等 →（可选）写回 oldvalue          ║
t8  ╚═③ 行锁窗口结束：事务完成，修改权随响应释放 ════════════════════════╝
   ◄──── 返回 oldvalue ────
                          B 若在 t4~t8 内对该行发起任何一致性事务
                          （读/snoop/也要独占）→ 与在途原子事务冲突，
                          被挡（重试/排在窗口之后），直到 t8 之后才被服务，
                          拿到的一定是 ⑥ 之后的值
t9                        B 后来读 → 回填 → 拿到新值
```

帧注：

- **t1~t3 只在"别处有副本 / 本地尚无独占"时发生**——行已在本核 L1 的 E/M 态时，直接从 t4 开始（这就是 §4.2 第 3 点的"快路径"，也解释了争用低时 CAS 几乎零额外开销）；
- "要独占"的一族事务，CHI 里叫 `ReadUnique` / `MakeUnique`，无效化别人叫 `SnpUnique`；这些事务响应回带的 UC/SC/UD/SD 字段就是行的新状态（[005.缓存一致性 附录 A.2](../../003.高速缓存/005.缓存一致性.md)）；
- 窗口 t4~t8 只是缓存控制器/一致性节点内部的几个周期，**不过互连、不碰主存**（除非行本就不在缓存，那属于 A.4 里"在更外层执行"的情形）。

### A.3 "行锁"锁的是什么（以及不是什么）

**是——该 cache line 的在途一致性事务互斥权**：一致性协议对同一行的并发事务必须仲裁出一个全局顺序；原子 RMW 作为一笔**未完成的事务**占着修改权，后来者的冲突事务只能等待或重试。锁的粒度 = 一个 cache line，锁的载体 = 一致性协议本身，不需要额外硬件"锁"。

**不是——**

| 常见误解 | 实际 |
| - | - |
| 锁总线（x86 LOCK# 时代做法） | 现代 ARM 系统无总线锁；别的行、别的事务完全不受影响 |
| 内存控制器/DDR 侧的锁 | 行通常在缓存内解决，根本到不了内存 |
| 软件可见的锁/状态位 | 没有任何软件可读状态；对比 LL/SC 的**独占监视器**是一个体系结构定义的状态机（见 [003.LLSC实现原理](./003.LLSC实现原理.md)）——同为"借协议当锁"，CAS 锁在**行**，LL/SC 锁在**监视器** |

与架构条款的对应：§4.2 第 1 点引的 B2-257"**RMW pair 绑定**"（E1 读效应与 E2 写效应由同一条指令产生、一致性顺序里相邻）是这件事的**架构表述**；A.2 的行锁窗口是它的**微架构落地**——"插不进 E1/E2 之间"在硬件上就是"窗口内在途事务占住修改权"。

顺手也解释了 §4.1 第 2 条为何 Device/不可缓存内存无原子保证：那里**没有带 M/E 语义的 cache line，没有修改权可借**，行锁无从谈起。

### A.4 在哪一级拿行锁——三个平台对照

"PoC 在哪一级"是 IMPLEMENTATION DEFINED；三个平台的典型分工（共同点：都是把读-比-写放进"修改权唯一"的窗口）：

| 平台 | 行已在本核 | 行在别处时的原子执行点 | 备注 |
| - | - | - | - |
| **Arm AGI CPU**（SP113012：Neoverse V3 ×136C 双 chiplet + CMN-700） | L1（核内）就地 | 本核私有 L2 可服务；再往外由 CMN-700 的 HN-F（SLC 侧）执行——CHI 的 **Atomic 事务（含 CompareSwap）可在家节点就地完成**，不必拆成读+写两笔 | 见 [Neoverse V3 TRM](../../../007.BOOKs/arm_neoverse_v3_core_technical_reference_manual_107734_0002_06_en.pdf)（Atomic operations 章）、[CMN-700 TRM](../../../007.BOOKs/arm_neoverse_cmn_700_trm_102308_0307_08_en.pdf)（Atomic/HA 相关章） |
| **Cortex-A725 + A520**（DSU-120 簇，异构 big.LITTLE） | L1 就地 | 簇内他核/共享 L3 → **DSU-120 的 SCU/L3 作为簇级 PoC**；跨簇再经互连 | DSU 结构见 [DynamIQ Shared Unit 笔记](../../../007.BOOKs/000.ARM资料库/000.DynamIQ%20Shared%20Unit.md) |
| **AMD EPYC 9996**（Zen 6c，16 CCX × 64MB L3） | L1/L2（每核私有）就地 | 同 CCX 他核 → CCD 内 L3 作为序列化点；跨 CCD → Infinity Fabric | MOESI 家族：L3 持有 Owned 副本，回填可免内存往返 |

（表中执行点为各体系结构的公开典型行为，具体截获级别以各家 TRM 为准。）

### A.5 一句话回收

**② = 谈成"全系统只有我可写"**（ReadUnique/SnpUnique 一族事务，别人的副本全部退 I）；**③ = 读-比-写完成前不交还修改权**，同行的其他一致性事务被协议仲裁挡在窗口外。借一致性协议当锁——锁的粒度是行，窗口是④⑤⑥三步。
