# KPROBE:kprobe / kretprobe / uprobe(BPF_PROG_TYPE_KPROBE)

> **函数级动态观测**:在任意内核函数(kprobe)/函数返回(kretprobe)/用户态函数(uprobe/uretprobe)入口插 BPF 程序。BCC 的 `funclatency`、`biolatency` 等大量工具的底层。枚举值 [bpf.h:1063](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/uapi/linux/bpf.h#L1063);ops 注册 [bpf_types.h:39](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/bpf_types.h#L39)。行号 = 仓库 7.1.3 树。

## 1. 使用场景

- 内核任意函数的入参/返回值/延迟统计(kprobe/kretprobe)
- 用户态库函数观测(uprobe,如 malloc/GC 耗时)
- 无源码二进制的"插桩"(只要符号表)
- 现代替代:多目标批量挂载(kprobe-multi)、session 模式(entry+exit 一次挂载),见 §3 方式③

## 2. 上下文与返回值

- 上下文 `struct pt_regs *`(寄存器现场):`PT_REGS_RC(ctx)` 取返回值,`bpf_probe_read_kernel()` 读指针参数
- uprobe/kretprobe 共用同一 prog type,挂载时由 perf event 类型区分
- helper 表:[kernel/trace/bpf_trace.c:1312 `kprobe_prog_func_proto`](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/trace/bpf_trace.c#L1312)(probe_read 系列、perf_event_output)

## 3. 如何生效(attach)——三条路

```
方式① 旧:perf_event_open + ioctl(BCC/bpftrace 经典路径)
  perf_event_open(kprobe:my_func)        → perf event fd
  ioctl(perf_fd, PERF_EVENT_IOC_SET_BPF, prog_fd)
    │ 调用点 kernel/events/core.c:6653
    ▼
  core.c:11704 perf_event_set_bpf_prog()
    └─ 11701 → kernel/trace/bpf_trace.c:1920 perf_event_attach_bpf_prog()
         ├─ 塞进 event->tp_event->prog_array(单点最多 64 个程序)
         └─ enable perf event ──【生效】

方式② 新 link:bpf(BPF_LINK_CREATE, attach_type=BPF_PERF_EVENT,
                   target_fd=perf_fd, prog_fd)
  └─ kernel/bpf/syscall.c:4191 bpf_perf_link_attach()
       └─ 4222 perf_event_set_bpf_prog()(后续同①)

方式③ kprobe-multi / session(一次挂 N 个函数,fprobe 实现)
  attach_type = BPF_TRACE_KPROBE_MULTI (bpf.h:1140) / KPROBE_SESSION (1154)
  uprobe 对应 BPF_TRACE_UPROBE_MULTI (1146) / UPROBE_SESSION (1155)
  └─ kernel/trace/bpf_trace.c:2734 bpf_kprobe_multi_link_attach()
       ├─ 2549 kprobe_multi_link_prog_run()    执行体
       ├─ 2592 kprobe_multi_link_handler()     entry handler
       └─ 2606 exit handler(session 模式)
  uprobe-multi:bpf_trace.c:3173 bpf_uprobe_multi_link_attach()
       (handler 3131 / ret_handler 3145)
```

## 4. 触发执行路径

```
kprobe(内核函数):
  断点命中(int3/brk)
    └─ kernel/trace/trace_kprobe.c:1825 kprobe_dispatcher()
         ├─ 1837 → 1683 kprobe_perf_func()
         │        └─ 1695 trace_call_bpf(call, regs)
         │             └─ kernel/trace/bpf_trace.c:109 trace_call_bpf()
         │                  └─ 145 bpf_prog_run_array(tp_event->prog_array)
         │                       → 逐个 bpf_prog_run() → JIT 本机码
         └─ kretprobe:1732 kretprobe_perf_func()(1741 同样 trace_call_bpf)

uprobe(用户函数):
  进程执行到插桩地址(断点)
    └─ kernel/trace/trace_uprobe.c:1526 uprobe_dispatcher()
         └─ 1553 → 1450 uprobe_perf_func() → 1386 __uprobe_perf_func()
              └─ 1405 bpf_prog_run_array_uprobe(array, regs, bpf_prog_run)
```

## 5. 如何卸载

```
方式①/②(挂在 perf event 上):
  close(perf event fd)
    └─ kernel/events/core.c:5828 perf_event_free()
         └─ 11718 perf_event_free_bpf_prog()
              └─ kernel/trace/bpf_trace.c:1964 perf_event_detach_bpf_prog()
                   (从 prog_array 移除,放掉引用)
  方式②的 link fd 也可以 close(等价触发)

方式③:
  close(link fd)
    ├─ bpf_trace.c:2382 bpf_kprobe_multi_link_release()
    └─ bpf_trace.c:2942 bpf_uprobe_multi_link_release()
```

prog fd 引用归零才真正释放(见 [002 §5](002.eBPF生命周期-加载生效卸载.md))。

## 6. 与同类钩子的对比

- vs [TRACING/fentry(024)](024.TRACING-fentry-fexit-fmod_ret.md):kprobe 是软件断点,开销高、无类型信息;fentry 是 ftrace direct 跳转,开销低、有 BTF 类型。能稳定用 fentry 就用 fentry
- vs [TRACEPOINT(021)](021.TRACEPOINT.md):tracepoint 是内核维护的稳定埋点,kprobe 可挂任意函数但随内核版本漂移
