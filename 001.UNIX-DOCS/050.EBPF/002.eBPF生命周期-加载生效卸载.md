# eBPF 生命周期:状态、如何生效、如何卸载

> 一个 eBPF 程序的一生:**编写 → 编译(.o) → 加载(验证+JIT,拿到 fd) → attach(生效) → 运行 → detach → 释放**。核心结论先记三条:
> 1. **拿到 fd ≠ 生效**:加载只说明"程序合法且在手",必须 attach 到钩子才运行;
> 2. **卸载 = 引用计数归零**:prog fd、挂载点、link fd、bpffs pin,任何一处还持有引用,程序就还活着;
> 3. **真正释放是延迟的**(work/RCU),因为其它 CPU 上可能正执行它的 JIT 代码。
>
> 源码行号 = 仓库 Linux 7.1.3 树。加载细节见 [000.从bpf系统调用来入门EBPF](000.从bpf系统调用来入门EBPF.md),各类型钩子细节见 010-034 各笔记。

## 1. 状态机全景

```
 用户态                                  内核态
 ──────                                 ──────
 .bpf.c 源码
   │ clang -target bpf
   ▼
 eBPF 字节码 .o  ──(状态①:还没进内核)
   │
   │ bpf(BPF_PROG_LOAD)  ← 见 000 笔记的下沉路径
   ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │ struct bpf_prog (include/linux/bpf.h:1777)                      │
 │ 已验证 + 已 JIT ──▶ bpf_prog_new_fd() (syscall.c:2519)          │
 │                                                                       │
 │ 状态②:已加载(prog fd 在手)——【不运行】                          │
 └─────────────────────────────────────────────────────────────────┘
   │ attach(按类型:BPF_LINK_CREATE / BPF_PROG_ATTACH / netlink /
   │        setsockopt / perf_event …,见各类型笔记)
   ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │ 状态③:已挂载 = 生效                                              │
 │ 钩子事件每次触发 → bpf_prog_run() → JIT 后的本机代码             │
 └─────────────────────────────────────────────────────────────────┘
   │
   ├─ 可选:BPF_OBJ_PIN 到 /sys/fs/bpf/*(见 §4)── 状态④:pinned
   │
   │ 卸载 = 把所有引用都放掉:
   │   close(prog fd) + 挂载点摘除(或 close(link fd)) + 无 pin
   ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │ 状态⑤:引用计数归零 → 延迟释放                                    │
 │ bpf_prog_release (syscall.c:2424)                                │
 │  └─ bpf_prog_put (2418) → __bpf_prog_put (2404)                 │
 │      └─ __bpf_prog_put_noref (2369):bpf_prog_free_id (2340)     │
 │         摘 ID/kallsyms,再 __bpf_prog_put_rcu (2358)             │
 │      └─▶ bpf_prog_free (kernel/bpf/core.c:3044,延迟 work)       │
 │             真正 free 内存 —— 因为可能正在别的 CPU 上执行        │
 └─────────────────────────────────────────────────────────────────┘
```

**哪些东西会持有一个 prog 的引用**:prog 自身的 fd、每个挂载点(attach 后内核在钩子上持有引用)、link 对象、bpffs 上的 pin 文件、被 `BPF_PROG_BIND_MAP` 绑定的 map。全部放掉才卸载。

## 2. "如何生效"的四种内核机制

attach 做的事,按钩子宿主分四类(具体到每种类型见各笔记):

| 机制 | 生效方式 | 代表类型 |
|-|-|-|
| **A. prog 数组/链表** | attach 把 prog 塞进宿主的 `bpf_prog_array`,事件路径上 `bpf_prog_run_array()` 遍历执行 | kprobe/tracepoint/perf_event([020](020.KPROBE与UPROBE.md)/[021](021.TRACEPOINT.md)/[023](023.PERF_EVENT.md))、cgroup([030](030.CGROUP系列.md))、raw tracepoint([022](022.RAW_TRACEPOINT.md)) |
| **B. 指针替换** | attach 直接改宿主结构里的函数指针/链表:XDP 改网卡 `xdp_state`、socket filter 换 `sk->filter`、TC 挂 cls 链表、struct_ops 填 ops 函数槽 | [010](010.XDP.md)/[011](011.TC-SCHED_CLS与SCHED_ACT.md)/[012](012.SOCKET_FILTER.md)/[032](032.STRUCT_OPS.md) |
| **C. ftrace direct + trampoline** | attach 生成一段本机跳板(trampoline),ftrace 把目标函数入口 patch 成 direct call 跳进跳板 | fentry/fexit/fmod_ret([024](024.TRACING-fentry-fexit-fmod_ret.md))、LSM([031](031.LSM.md))、EXT |
| **D. 不挂钩,显式调用** | 没有"生效"概念,由用户态 `BPF_PROG_TEST_RUN` 或内核 `kern_sys_bpf()` 触发 | SYSCALL([033](033.SYSCALL.md)) |

## 3. link:把"挂载关系"变成对象

老 `BPF_PROG_ATTACH` 挂上之后,挂载关系是钩子宿主的一部分;新 `BPF_LINK_CREATE` 则返回独立的 link fd:

- 创建:[kernel/bpf/syscall.c:5727 `link_create()`](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/bpf/syscall.c#L5727)(`case BPF_LINK_CREATE` 分支 6345),按 prog type/attach_type 分派到各类型的 attach 函数;link fd 经 [syscall.c:3480 `bpf_link_new_fd()`](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/bpf/syscall.c#L3480)(`"bpf-link"` anon inode)返回
- **detach 不等于销毁**:`BPF_LINK_DETACH`(处理 [syscall.c:5920 `link_detach()`](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/bpf/syscall.c#L5920))只把钩子摘下,link 对象还在——常配合 `BPF_LINK_UPDATE` 做原子换程序(旧程序被移走,不丢事件)
- close link fd → [syscall.c:3329 `bpf_link_release()`](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/bpf/syscall.c#L3329) → 类型自己的 release(摘钩子)→ [bpf_link_put](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/bpf/syscall.c#L3312)(3312)→ [bpf_link_free](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/bpf/syscall.c#L3266)(3266,先 3201 `bpf_link_free_id` 摘 ID)→ 放掉 prog 引用

## 4. pin:让程序活得比进程久

```
 bpf(BPF_OBJ_PIN, pathname="/sys/fs/bpf/my_prog", fd)
   │ syscall.c:6276 case 分支 → bpf_obj_pin (syscall.c:3139)
   ▼
 kernel/bpf/inode.c:431 bpf_obj_do_pin()
   └─ vfs_mkobj() 在 bpffs 上建文件
      (bpf_mkprog / bpf_mkmap / bpf_mklink 三种)
 bpffs 本身:bpf_fs_type (inode.c:1074),bpf_init (1083) 注册

 进程重启后取回:
 bpf(BPF_OBJ_GET, pathname)
   │ syscall.c:6279 → bpf_obj_get (syscall.c:3155)
   ▼
 inode.c:522 bpf_obj_get_user()
   └─ bpf_obj_do_get (490) 加引用
      → bpf_prog_new_fd / bpf_map_new_fd / bpf_link_new_fd 重开 fd
```

pin 之后即使所有 fd 关闭、进程退出,对象也活着(文件系统持有引用);`rm /sys/fs/bpf/my_prog` 或 `umount` 时才放掉最后引用。这是开机自启守护(如 Cilium agent 重启不中断数据面)的基础。

## 5. 卸载检查清单

以"完全卸载一个程序"为目标,依次确认:

1. **摘钩子**:detach(netlink 传 fd=-1 / `BPF_PROG_DETACH` / close link fd / `SO_DETACH_FILTER` / `tc filter del` …,每种类型见对应笔记)
2. **关 fd**:close prog fd(以及持有它的 map/link 对象的 fd)
3. **清 pin**:`rm /sys/fs/bpf/…`
4. 之后引用计数归零,内核经 RCU/work 延迟真正释放(§1 状态⑤)

观察工具:`bpftool prog show`(列 ID/类型/引用数/是否 pinned)、`ls /sys/fs/bpf/`、`bpf(BPF_PROG_GET_FD_BY_ID)` 可随时重新拿 fd。
