## 1. 为什么"装入驱动"是个问题

驱动是直接操作设备控制器寄存器的特权代码,必须运行在内核态(《现代操作系统》§5.3.2:设备驱动"normally has to be part of the operating system kernel",例外如 MINIX 3 把驱动放用户态)。但内核镜像在开机时一次性加载,此后新驱动怎么进入内核?《现代操作系统》§5.3.2(书页 361)总结了两个历史模型:

> **模型 A(静态编译)**:"In some systems, the operating system is a single binary program that contains all of the drivers it will need compiled into it. This scheme was the norm for years with UNIX systems... If a new device was added, the system administrator simply re-compiled the kernel with the new driver to build a new binary."
> (一些系统里,操作系统是单个二进制程序,所有需要的驱动都编译在里面。UNIX 多年如此——加新设备就得用新驱动重新编译内核。)
>
> **模型 B(动态加载)**:"With the advent of personal computers, with their myriad I/O devices, this model no longer worked... operating systems, starting with MS-DOS, went over to a model in which drivers were dynamically loaded into the system during execution. **Different systems handle loading drivers in different ways.**"
> (PC 时代设备五花八门,普通用户不可能重新编译内核。自 MS-DOS 起,操作系统转向运行时动态加载驱动。不同系统的加载方式各不相同。)

§10.5.5(书页 765)补了 Linux 的动机:"For decades, UNIX device drivers were statically linked into the kernel... With the arrival of Linux on the PC platform, suddenly all that changed. The number of I/O devices available on the PC is orders of magnitude larger than on any minicomputer."——**Linux 用可装载模块(loadable modules)解决了这个问题**:这些代码块可以在系统运行时装入内核,最常见的就是字符/块设备驱动,也可以是整个文件系统、网络协议等(§10.2,书页 723:"In addition to the static in-kernel components, Linux supports dynamically loadable modules")。

## 2. "三种装入方式"分析

《Linux 设备驱动开发》(参考文档)没有一句话直接列"三种方式",但把 §1.1.2(内核配置)、§2.5(构建)和 §2.1.3(模块的加载和卸载)合起来看,装入方式正好是三个:

| 方式 | 触发时机 | 谁触发 | 参考文档出处 | 《现代操作系统》对应 |
|-|-|-|-|-|
| ① **编译进内核**(built-in,静态链接) | 构建期 | 开发者(`make menuconfig` 选 `y`) | §1.1.2 内核配置、§2.5.2 内核树内构建 | 模型 A(单一二进制) |
| ② **手动动态加载** | 任意时刻 | root 用户(`insmod`/`modprobe`;`/etc/modules-load.d` 开机加载) | §2.1.3-1 手动加载 | 模型 B,用户显式触发 |
| ③ **自动/按需加载** | 设备出现/内核缺功能时 | 内核(`request_module`)或 udev 热插拔代理 | §2.1.3-2 自动加载 | 模型 B,按需触发(§1.7.1:"These components are loaded on demand",书页 64) |

参考文档 §2.1.3 的原文结构是:"模块要运行,应该先把它加载到内核"——其中 **1. 手动加载**(insmod 是开发期首选、modprobe 是生产首选,`/etc/modules-load.d/<name>.conf` 每行写一个模块名即可开机加载)和 **2. 自动加载**(depmod 生成 `modules.alias` 把设备映射到驱动;用户空间热插拔代理 udev/mdev 收到内核通知后调用 modprobe)。方式①则来自同一本书的内核配置部分:Kconfig 三态选项选 `y` 还是 `m`,就是"编译进内核"还是"编译成模块"的分叉点。

一句话概括:

- **①是模型 A**:驱动在构建期就死链接进 vmlinux,开机即存在,不可卸载;
- **②③是模型 B 的两个触发入口**:装的动作完全一样(都是模块装入),区别只是"人显式要装"还是"系统发现需要装"。

## 3. 《现代操作系统》对模块装入过程的总结

§10.5.5(书页 765)给出了模块装入时内核要做的五件事,这是理解 Linux 模块装载器(`kernel/module/main.c`)最好的框架:

> "When a module is loaded, several things have to happen. **First**, the module has to be **relocated on the fly**, during loading. **Second**, the system has to check to see if the **resources** the driver needs are available (e.g., interrupt request levels) and if so, mark them as in use. **Third**, any **interrupt vectors** that are needed must be set up. **Fourth**, the appropriate **driver switch table** has to be updated to handle the new major device type. **Finally**, the driver is allowed to **run** to perform any device-specific initialization it may need."
>
> (第一,装载时实时重定位;第二,检查驱动所需资源(如中断请求号)是否可用并标记占用;第三,建立所需的中断向量;第四,更新驱动开关表以处理新的主设备号;第五,让驱动运行,执行它自己的设备初始化。)

同节还有一个重要的安全警告(书页 766):

> "It is worth noting that **loadable modules are a security nightmare**... Loadable modules should only be fetched from a source known to be completely trustworthy."
> (可装载模块是安全噩梦——把未经审查、可能带漏洞和后门的外来代码放进内核风险极大;模块只能来自完全可信的来源。)

Linux 对这条警告的回应是模块签名验证(`CONFIG_MODULE_SIG`,`kernel/module/signing.c`)和 LSM 钩子(见 §4.3)。

## 4. Linux 是如何实现的(内核 7.1.3 逐条走读)

### 4.1 方式①:编译进内核——从 Kconfig 三态到 do_initcalls

**分叉点在配置阶段。** 每个 Kconfig 驱动选项是三态(tristate):`y` 编译进内核 / `m` 编译成模块 / `n` 不编译。以并口打印机驱动为例:

```text
drivers/char/Kconfig:34
config PRINTER
	tristate "Parallel printer support"
	depends on PARPORT
```

选 `y` 时,该驱动进入 `obj-y` 列表。内核构建系统把 `obj-y` 里的目标归档为 `built-in.a`,层层向上汇总,最终链接进 vmlinux:

```text
scripts/Makefile.build:75
obj-y := $(patsubst %/, %/built-in.a, $(obj-y))
```

选 `m` 时进入 `obj-m`,产物是独立的 `.ko` 文件(方式②③的原料)。

**驱动代码怎么感知自己是内置还是模块?** 同一个 `module_init()` 宏,在两种编译模式下展开完全不同——这是全篇最关键的一个宏:

```c
/* include/linux/module.h:80  内置路径(未定义 MODULE) */
#ifndef MODULE
/**
 * module_init() - driver initialization entry point
 * @x: function to be run at kernel boot time or module insertion
 *
 * module_init() will either be called during do_initcalls() (if
 * builtin) or at module insertion time (if a module).
 */
#define module_init(x)	__initcall(x);      // ← 展开成 initcall,放进内核镜像的 .initcall 段

/* include/linux/module.h:131  模块路径(定义了 MODULE) */
#else
/* Each module must use one module_init(). */
#define module_init(initfn)					\
	static inline initcall_t __maybe_unused __inittest(void)	\
	{ return initfn; }					\
	int init_module(void) __copy(initfn)			\
		__attribute__((alias(#initfn)));		\
	___ADDRESSABLE(init_module, __initdata);
```

- 内置时:`module_init(my_init)` 变成 `__initcall(my_init)`(`include/linux/init.h:277` 的 `__define_initcall` 按 early/core/subsys/device/late 等**级别**把函数指针收进 `.initcallN.init` 段)。
- 模块时:生成一个别名函数 `init_module` = `my_init`,它就是模块装入后被调用的入口(§4.2 末尾)。

**内置驱动的 init 何时执行?** 开机流程末尾:

<pre>
start_kernel → rest_init → kernel_init(内核线程)
  → kernel_init_freeable (init/main.c:1674)
      → do_basic_setup (init/main.c:1483)
          → do_initcalls (init/main.c:1457)          ← 内置驱动统一入口
              → do_initcall_level (init/main.c:1442)
                  for (fn = initcall_levels[level]; fn < initcall_levels[level+1]; fn++)
                      do_one_initcall(initcall_from_entry(fn));   // 逐级别逐函数执行
</pre>

`initcall_levels` 按级别(early→core→subsys→device→late,名字见 `initcall_level_names`,`init/main.c:1425`)排好了所有内置驱动 init 的执行顺序——这就是方式①"装入"的全部含义:**链接期已就位,开机时按级别调用一次 init,之后 init 代码段整体释放**。

注意:`module_exit()` 对内置驱动无意义(`include/linux/module.h:91` 注释:"If the driver is statically compiled into the kernel, module_exit() has no effect")——内置驱动不可卸载。启动早期就要用的驱动(如根文件系统所在的磁盘/控制器)必须走方式①,因为那时模块基础设施(`/lib/modules`、用户态)还没就绪。

### 4.2 方式②:手动加载——一次系统调用完成的"运行时链接"

`.ko` 文件本质是一个 **ELF 可重定位目标文件**(未完成连接的 `ET_REL`,带着 `.symtab`/重定位记录/`.modinfo` 元数据)。装入时,**内核自己充当链接器+加载器**,把这段代码"现场链接"进内核地址空间。这正是 Tanenbaum 五步里的第一步"relocated on the fly"。

用户态命令与系统调用的对应:`insmod`/`modprobe`(kmod 工具集)最终都落在:

```c
/* kernel/module/main.c:3634  insmod 走这里(传整个模块映像) */
SYSCALL_DEFINE3(init_module, void __user *, umod,
		unsigned long, len, const char __user *, uargs)

/* kernel/module/main.c:3799  modprobe/现代 kmod 走这里(传文件描述符,免双份拷贝) */
SYSCALL_DEFINE3(finit_module, int, fd, const char __user *, uargs, int, flags)
```

`finit_module` 校验 flags 后进入 `idempotent_init_module`(同名模块已在加载则直接等待其结果)→ `load_module`(`kernel/module/main.c:3422`)。装载主流程:

<pre>
load_module (kernel/module/main.c:3422)
  │ copy_module_from_user / fd          把 .ko 读进内核
  │ module_memory_alloc (main.c:1341)   按段分配可执行内存(见下)
  │ resolve_symbol (main.c:1260)        逐个解析未定义符号:查内核导出表
  │   └ check_version (main.c:1290)     CONFIG_MODVERSIONS 时核对符号 CRC
  │ simplify_symbols (main.c:1530)      符号定值(未解析的逐个 resolve_symbol)
  │ apply_relocations (main.c:1608)     现场重定位 ← "relocated on the fly"
  │ same_magic (main.c:2646)            校验 vermagic(内核版本/SMP/preempt 等指纹)
  │ 签名验证(CONFIG_MODULE_SIG, kernel/module/signing.c)
  │ mod_sysfs_setup (main.c:3561)       /sys/module/<name> 上线
  └ do_init_module (main.c:3077)
      └ do_one_initcall(mod->init) (main.c:3106)   ← 调用 init_module(即 module_init 注册的函数)
          之后释放模块的 .init* 段(内存用完即还)
</pre>

内存分配细节(7.1.3 较新变化):模块代码/数据段由 `module_memory_alloc` 申请,底层已从老的 `module_alloc()` 换成通用的 **execmem 机制**:

```c
/* kernel/module/main.c:1341 */
static int module_memory_alloc(struct module *mod, enum mod_mem_type type)
{
	...
	if (mod_mem_type_is_data(type))
		execmem_type = EXECMEM_MODULE_DATA;
	else
		execmem_type = EXECMEM_MODULE_TEXT;

	ptr = execmem_alloc_rw(execmem_type, size);   /* include/linux/execmem.h */
	...
}
```

**Tanenbaum 五步 vs Linux 实际**——Linux 没有把五步都塞进装载器,后三步被推给了驱动自己的 init/probe,由各子系统框架完成:

| 《现代操作系统》§10.5.5 五步 | Linux 7.1.3 实现 |
|-|-|
| 1. 装载时重定位 | `apply_relocations`(main.c:1608)+ `simplify_symbols`(main.c:1530) |
| 2. 检查并占用资源 | 驱动 init/probe 里 `request_region`/`request_mem_region`/`request_irq` 失败即回滚 |
| 3. 建立中断向量 | `request_irq`(devm_* 变体)注册中断处理程序 |
| 4. 更新驱动开关表 | `platform_driver_register`/`cdev_add`/`alloc_netdev`… 注册进 driver core(设备-驱动匹配的总线框架) |
| 5. 执行设备初始化 | `do_one_initcall(mod->init)`(main.c:3106)→ probe |

**insmod 与 modprobe 的区别**纯粹在用户态:modprobe 先解析 `modules.dep`(由 depmod 生成,参考文档 §2.1.2:"depmod 读取 /lib/modules/<kernel_release>/ 中的每个模块……结果写入 modules.dep")递归装入依赖,再装入目标;insmod 只做一次 `finit_module`。开机自动执行 modprobe 的机制是 `/etc/modules-load.d/<name>.conf`(每行一个模块名,由 systemd 逐行调 modprobe)——参考文档 §2.1.3-1。

前置条件:内核必须启用模块支持(`menuconfig MODULES`,`kernel/module/Kconfig:2`,即参考文档 §2.1.1 说的 `CONFIG_MODULES=y`);可卸载由 `CONFIG_MODULE_UNLOAD`(Kconfig:132)控制。

### 4.3 方式③:自动/按需加载——两条触发链,同一个 modprobe

两条链最终都汇到用户态的 modprobe,再走 §4.2 的系统调用。

#### 链 A:内核主动请求(request_module)

内核代码发现缺某个模块时,调 `request_module`(注意:它最终是**内核去执行用户态程序**):

```c
/* include/linux/kmod.h:22 */
#define request_module(mod...) __request_module(true, mod)
```

```c
/* kernel/module/kmod.c:132(节选) */
int __request_module(bool wait, const char *fmt, ...)
{
	char module_name[MODULE_NAME_LEN];
	...
	if (!modprobe_path[0])          /* modprobe_path 清空 = 内核侧自动加载被禁用 */
		return -ENOENT;
	...
	ret = security_kernel_module_request(module_name);   /* LSM 安全钩子 */
	...
	ret = call_modprobe(module_name, wait ? UMH_WAIT_PROC : UMH_WAIT_EXEC);
	...
}

/* kernel/module/kmod.c:72(节选):组装 /sbin/modprobe -q -- <模块名> */
static int call_modprobe(char *orig_module_name, int wait)
{
	...
	argv[0] = modprobe_path;    /* kmod.c:64: char modprobe_path[] = CONFIG_MODPROBE_PATH; */
	argv[1] = "-q";             /*       默认 "/sbin/modprobe"(kernel/module/Kconfig:419) */
	argv[2] = "--";             /*       运行时可经 /proc/sys/kernel/modprobe 修改 */
	argv[3] = module_name;
	argv[4] = NULL;

	info = call_usermodehelper_setup(modprobe_path, argv, envp, ...);
	ret = call_usermodehelper_exec(info, wait | UMH_KILLABLE);
	...
}
```

`call_usermodehelper`(`kernel/umh.c:482`)由内核工作线程 fork 出一个用户态进程执行 modprobe——modprobe 在用户态读 `.ko`、解依赖,再发起 `finit_module` 系统调用回到内核。**内核态发起、用户态干活、再回内核完成装入**,这是链 A 的完整闭环。

内核里典型的 request_module 触发点(网络子系统最多):

| 触发点 | 场景 |
|-|-|
| `net/core/dev_ioctl.c:674` `request_module("netdev-%s", name)` | 用户 `ifconfig eth0`/`ip link` 操作一个尚无驱动的网卡名 |
| `net/core/rtnetlink.c:4050` `request_module("rtnl-link-%s", kind)` | `ip link add type <kind>` 指定未知链路类型(如 vxlan) |
| `net/core/sock.c:4291` `request_module("net-pf-%d-proto-%d-type-%d", ...)` | `socket(AF_xxx,...)` 用到未加载的协议族/协议 |

#### 链 B:设备事件驱动(uevent → udev → modprobe)

这是"插上设备,驱动自动出现"的那条链,分**构建期准备**和**运行期触发**两半。

**构建期:驱动如何声明"我支持哪些设备"**

```c
/* include/linux/module.h:253 */
/* Creates an alias so file2alias.c can find device table. */
#define MODULE_DEVICE_TABLE(type, name)					\
static typeof(name) __mod_device_table(type, name)			\
  __attribute__ ((used, alias(__stringify(name))))
```

驱动用 `MODULE_DEVICE_TABLE(usb, my_id_table)` 暴露它的设备 ID 表(VID/PID 等)。构建时 modpost 的 file2alias 工具(`scripts/mod/file2alias.c`,自述:"Simple code to turn various tables in an ELF file into alias definitions")把这些 ID 表翻译成 `alias=usb:v0403pFF1Cd*...` 之类的**别名规则**,存进 `.ko` 的 `.modinfo` 段。`make modules_install` 末尾执行 depmod(`scripts/depmod.sh`,实际跑 `depmod -ae`)汇总所有模块的别名,生成参考文档 §2.1.3-2 展示的 `modules.alias`:

```text
alias usb:v0403pFF1Cd*dc*dsc*dp*ic*isc*ip*in*  ftdi_sio     ← FTDI USB 串口芯片
alias usb:v*p*d*dc*dsc*dp*ic01isc03ip*in*      snd_usb_audio ← 所有 USB 音频类设备
```

**运行期:设备出现 → 内核广播 uevent → udev 匹配别名 → modprobe**

以 USB 设备插入为例:

<pre>
USB 设备插入
  → USB 子系统枚举设备,注册进 driver core(无匹配驱动)
  → kobject_uevent_env (lib/kobject_uevent.c:476)
        action = KOBJ_ADD("add", uevent.c:51)
        总线 uevent 回调补环境变量:
            usb_if_uevent (drivers/usb/core/message.c:1881)
              "MODALIAS=usb:v%04Xp%04Xd%04Xdc%02X..." (message.c:1897)   ← 用真实 VID/PID 填充
            (platform 总线同理: platform_uevent, drivers/base/platform.c:1388/1402)
  → netlink_broadcast (uevent.c:735)   广播给用户态监听者
  → udevd(systemd) 收到 uevent
        取 MODALIAS 值查 modules.alias → 命中 ftdi_sio
        执行 modprobe ftdi_sio → (链路同方式②) finit_module → load_module
        → 驱动注册 → 总线匹配到该 USB 设备 → probe() → 设备可用
</pre>

```c
/* drivers/usb/core/message.c:1897  USB 设备的 MODALIAS 生成(节选) */
	if (add_uevent_var(env,
		   "MODALIAS=usb:"
		   "v%04Xp%04Xd%04Xdc%02Xdsc%02Xdp%02Xic%02Xisc%02Xip%02Xin%02X",

		   le16_to_cpu(usb_dev->descriptor.idProduct),

```

刚开机时 udevd 还会**重放**一遍所有已注册设备的 uevent(冷插拔 coldplug),让开机前就存在的设备也能按这条链把驱动装上。参考文档 §2.1.3-2 的描述与此完全一致:"udev……在内核中注册,以便在出现新设备时得到通知……守护进程再调用 modprobe,并向其传递设备描述信息。接下来,modprobe 解析 modules.alias 文件,匹配与该设备相关的驱动程序。"

《现代操作系统》§1.7.1(书页 64)把这归为按需加载的一般形态:"many operating systems support loadable extensions, such as I/O device drivers and file systems. These components are **loaded on demand**."

### 4.4 顺带:卸载

`rmmod` → `delete_module(2)` 系统调用(`kernel/module/main.c:804`)。内核为每个模块维护引用计数,模块被使用时拒绝卸载(参考文档 §2.1.3-3:"如果内核认为删除一个模块是不安全的,就不会删除它");`modprobe -r` 会额外卸载不再被依赖的相关模块。前提是 `CONFIG_MODULE_UNLOAD`(Kconfig:132)。内置驱动(方式①)没有卸载这条路。

## 5. 总结

| | ① 编译进内核 | ② 手动加载 | ③ 自动/按需加载 |
|-|-|-|-|
| 装入时机 | 构建期+开机 do_initcalls | 用户命令时 | 设备出现/内核缺功能时 |
| 触发者 | 开发者(配置 `y`) | root(insmod/modprobe/modules-load.d) | 内核 request_module / udevd |
| 内核机制 | `obj-y`→`built-in.a`→vmlinux;`module_init`→`__initcall` | `finit_module(2)`→`load_module` 现场链接 | 链 A:`__request_module`→`call_modprobe`→umh;链 B:uevent(MODALIAS)→udevd→modprobe |
| 能否卸载 | 否 | 能(rmmod/modprobe -r) | 能(同左) |
| 典型用途 | 启动早期必需(根盘/控制器)、始终在用的核心驱动 | 开发调试(insmod)、服务器手动装配 | 台式机/笔记本的海量即插即用设备 |

**一句话**:三条路殊途同归——最终都是让驱动的 init/probe 进入内核执行并注册进 driver core;《现代操作系统》的两个历史模型(静态单二进制/运行时动态加载)在 Linux 里分别落成方式①和方式②③,而方式②③又共享同一套模块装载机制,区别只在触发入口。Tanenbaum 的安全警告("loadable modules are a security nightmare")在 Linux 的回应是模块签名(`CONFIG_MODULE_SIG`)与 LSM 钩子(`security_kernel_module_request`,kmod.c:155)。
