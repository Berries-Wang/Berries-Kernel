## 0. 先建立全局观:一条连接的三种内核形态

读 TCP 连接管理的内核代码,最容易迷路的原因是:**同一条连接在不同阶段由三种不同的"套接字形态"承载**,它们形态不同、大小不同,却共用同一个四元组(源IP/源端口/目的IP/目的端口):

| 阶段 | 形态 | 分配点 | 归宿 |
|-|-|-|-|
| 握手中(服务端收到 SYN 后) | `struct request_sock` 迷你套接字(状态 `TCP_NEW_SYN_RECV`,挂在全局 ehash) | `inet_reqsk_alloc` (tcp_input.c:7628) | 收到第三次 ACK 后升级为完整 sock,或超时被 `reqsk_timer_handler` (inet_connection_sock.c:1024) 回收 |
| 稳定期(两端 ESTABLISHED) | `struct sock`/`struct tcp_sock` 完整套接字 | 客户端:socket() 时;服务端:`tcp_create_openreq_child` (tcp_minisocks.c:547) | 挥手到 CLOSED 时销毁 |
| TIME_WAIT 期(主动关闭方) | `struct inet_timewait_sock` 缩水套接字(只为回 ACK 而活) | `inet_twsk_alloc` (tcp_minisocks.c:333) | 60 秒后定时器到期销毁 |

> 为什么这样设计?**内存**。一个 `tcp_sock` 约 2KB+,一个 `request_sock` 只有百字节量级。SYN 洪水时攻击者可以伪造海量四元组,服务端绝不能为每个 SYN 就分配完整套接字。

发送/接收总入口(所有报文都要过这两道门):

<pre>
发送(本机协议栈发出): tcp_transmit_skb → __tcp_transmit_skb (tcp_output.c:1529) → IP层
接收(网卡上送):        ip_local_deliver_finish → tcp_v4_rcv (tcp_ipv4.c:2068) → 查哈希表分发
</pre>

### 1.2 第一步:客户端发出 SYN

应用层 `connect()` → `inet_stream_connect` → `tcp_v4_connect()`。三件事:**改状态、定身份、发 SYN**:

```c
/* tcp_ipv4.c:305-345 */
tcp_set_state(sk, TCP_SYN_SENT);            // 状态先于发包迁移
err = inet_hash_connect(tcp_death_row, sk); // 选源端口, 插入全局ehash
...
st = secure_tcp_seq_and_ts_off(net, ...);   // :328 基于四元组+时钟+密钥生成ISN
if (!tp->write_seq)
    WRITE_ONCE(tp->write_seq, st.seq);      // tp->write_seq = ISS
...
err = tcp_connect(sk);                      // :345
```

`tcp_connect()` (tcp_output.c:4293) 构造并发送 SYN:

```c
/* tcp_output.c:4351-4392 */
tcp_connect_init(sk);                       // 初始化序号空间与拥塞控制参数
buff = tcp_stream_alloc_skb(...);
tcp_init_nondata_skb(buff, sk, tp->write_seq, TCPHDR_SYN);  // :4365 seq=ISS, 仅SYN位
tcp_rbtree_insert(&sk->tcp_rtx_queue, buff);                // :4370 先进重传队列再发送
err = tcp_transmit_skb(sk, buff, 1, sk->sk_allocation);     // :4374 真正发出
WRITE_ONCE(tp->snd_nxt, tp->write_seq);     // :4381 snd_nxt = ISS+1 (SYN耗一个序号)
TCP_INC_STATS(sock_net(sk), TCP_MIB_ACTIVEOPENS);
/* Timer for repeating the SYN until an answer. */
tcp_reset_xmit_timer(sk, ICSK_TIME_RETRANS, inet_csk(sk)->icsk_rto, false);  // :4391
```

三个值得咀嚼的细节:
+ **SYN 占用一个序号**:`write_seq` 从 ISS 变为 ISS+1,所以后续第一个数据字节从 ISS+1 开始。这决定了报文(2)的 `ack=ISS+1` 和三次握手的 ACK 校验窗口 `(snd_una, snd_nxt]`。
+ **先入重传队列再发送**(`:4370` 在 `:4374` 之前):如果包在驱动层丢了呢?顺序保证"未确认的数据永远在队列里"。
+ **ISN 不是随机的随机**:`secure_tcp_seq_and_ts_off` 用四元组哈希 + 时钟 + 每引导随机密钥生成,递增且不可预测 —— 防旧连接的重复报文串门(RFC 793 要求 ISN 时钟递增),也防攻击者猜测序号伪造报文注入。

### 1.3 第二步:服务端收 SYN → 回 SYN+ACK

收包统一入口 `tcp_v4_rcv` (tcp_ipv4.c:2068) 第一件事是**用四元组查哈希表**(`__inet_lookup_skb`, :2112)。SYN 从 LISTEN 套接字的 ehash 桶里被找到,然后走 `tcp_v4_do_rcv → tcp_rcv_state_process` 的 `TCP_LISTEN` 分支:

```c
/* tcp_input.c:7133-7156 */
case TCP_LISTEN:
    if (th->ack) return SKB_DROP_REASON_TCP_FLAGS;  // LISTEN态收ACK = 异常
    if (th->rst)  { ... goto discard; }
    if (th->syn) {
        ...
        icsk->icsk_af_ops->conn_request(sk, skb);   // :7151 → tcp_v4_conn_request
```

`tcp_conn_request` (tcp_input.c:7587) 是服务端握手的核心,一条函数里完成了**防御、建迷你套接字、解析选项、选 ISN、入队、回包**:

```c
/* tcp_input.c:7587-7748 摘录 */
if (syncookies == 2 || inet_csk_reqsk_queue_is_full(sk)) {   // :7615 半连接队列满?
    want_cookie = tcp_syn_flood_action(sk, ...);             // → SYN cookie模式
    if (!want_cookie) goto drop;
}
if (sk_acceptq_is_full(sk)) {                                // :7623 全连接队列满?
    NET_INC_STATS(..., LINUX_MIB_LISTENOVERFLOWS);           // 计数器: ListenOverflows
    goto drop;
}
req = inet_reqsk_alloc(rsk_ops, sk, !want_cookie);           // :7628 迷你套接字诞生
tcp_parse_options(sock_net(sk), skb, &tmp_opt, 0, ...);      // :7643 MSS/时间戳/窗口因子
st = INDIRECT_CALL_INET(af_ops->init_seq_and_ts_off, ...);   // :7664 服务端ISN(IRS)
...
isn = st.seq;                                                // :7693
tcp_rsk(req)->snt_isn = isn;                                 // :7716 迷你套接字记住IRS
tcp_openreq_init_rwin(req, sk, dst);                         // :7719 初始接收窗
...
inet_csk_reqsk_queue_hash_add(sk, req);                      // :7740 半连接: 计数+插ehash
af_ops->send_synack(sk, dst, &fl, req, &foc,                 // :7745 回SYN+ACK
                    !want_cookie ? TCP_SYNACK_NORMAL : TCP_SYNACK_COOKIE, skb);
```

`tcp_v4_send_synack` (tcp_ipv4.c:1159) → `tcp_make_synack`(:1176,构造 seq=IRS, ack=ISS+1, 附 MSS/WS/TS 选项)→ `ip_build_and_send_pkt`(:1193)交 IP 层。

此刻服务端**没有**为它分配完整套接字,只有一个百字节量级的 `request_sock` 记着 `snt_isn=IRS`、`rcv_isn=ISS`、协商好的选项 —— 这就是"半连接"。SYN+ACK 的重传和超时由 `reqsk_timer_handler` (inet_connection_sock.c:1024) 负责。

### 1.4 第三步:客户端收 SYN+ACK → 发 ACK,ESTABLISHED

客户端的 SYN_SENT 套接字在 ehash 中被(2)命中,进入 `tcp_rcv_synsent_state_process` (tcp_input.c:6819)。这是把 RFC 793 "SYN-SENT 状态处理"逐条翻译成 C 的函数:

```c
/* tcp_input.c:6842-6969 摘录 */
if (!after(TCP_SKB_CB(skb)->ack_seq, tp->snd_una) ||        // :6842 ACK号必须落在
    after(TCP_SKB_CB(skb)->ack_seq, tp->snd_nxt)) {         //        (snd_una, snd_nxt]
    ... goto reset_and_undo;                                //        否则回RST
}
...
WRITE_ONCE(tp->rcv_nxt, TCP_SKB_CB(skb)->seq + 1);          // :6905 rcv_nxt = IRS+1
...
tcp_finish_connect(sk, skb);                                // :6942
...
if (!sock_flag(sk, SOCK_DEAD)) {
    sk->sk_state_change(sk);                                // :6948 唤醒connect()
    sk_wake_async(sk, SOCK_WAKE_IO, POLL_OUT);
}
...
tcp_send_ack_reflect_ect(sk, tcp_ecn_mode_accecn(tp));      // :6969 发出第三次握手的ACK
```

`tcp_finish_connect` (tcp_input.c:6700) 只做一件事的决定性一步:

```c
/* tcp_input.c:6705-6715 */
tcp_ao_finish_connect(sk, skb);
tcp_set_state(sk, TCP_ESTABLISHED);                 // :6706 ★客户端进入ESTABLISHED
...
tcp_init_transfer(sk, BPF_SOCK_OPS_ACTIVE_ESTABLISHED_CB, skb);  // :6715 拥塞控制初始化
```

注意顺序:**先 `tcp_finish_connect`(建连)再 `tcp_send_ack`(握手包)**。第三次握手的 ACK 里不能带数据?可以——Linux 支持,数据随 ACK 一起走(甚至 SYN 里就能带数据,即 TCP Fast Open,`:4373` 的 `tcp_send_syn_data` 分支)。

### 1.5 第四步:服务端收 ACK → 完整套接字诞生,accept() 返回

这是三次握手最精巧的一步。第三次 ACK 到达时,`__inet_lookup_skb` 命中的是**插在 ehash 里的迷你 req**(`TCP_NEW_SYN_RECV`,tcp_ipv4.c:2120),交给 `tcp_check_req` (tcp_minisocks.c:689) 裁决:

```c
/* tcp_minisocks.c:838-841, 920-944 摘录 */
if ((flg & TCP_FLAG_ACK) && !fastopen &&
    (TCP_SKB_CB(skb)->ack_seq != tcp_rsk(req)->snt_isn + 1))   // ACK必须精确==IRS+1
    return sk;                                                  // 否则走embryonic_reset伪造RST
...
/* OK, ACK is valid, create big socket and feed this segment to it. */
child = inet_csk(sk)->icsk_af_ops->syn_recv_sock(sk, skb, req, ...);  // :926 克隆完整sock
...
return inet_csk_complete_hashdance(sk, child, req, own_req);   // :944
```

两个关键动作:
+ `tcp_v4_syn_recv_sock` (tcp_ipv4.c:1671) → `tcp_create_openreq_child` (:1694):**从 LISTEN 套接字克隆**出一个完整的 `struct sock`,继承选项协商结果,状态置 `TCP_SYN_RECV`。
+ `inet_csk_complete_hashdance` (inet_connection_sock.c:1410) —— 名字直译"哈希之舞":迷你 req 从 ehash **摘下**(:1414),child **顶替**进去;`inet_csk_reqsk_queue_add`(:1444)把 child 挂到 LISTEN 套接字的**全连接队列**(`rskq_accept_head` 链表)。

最后 `tcp_child_process` (tcp_minisocks.c:990) 让 child 自己消化这个 ACK 报文:

```c
/* tcp_minisocks.c:1001-1005 */
if (!sock_owned_by_user(child)) {
    reason = tcp_rcv_state_process(child, skb);          // → case TCP_SYN_RECV :7218
    if (state == TCP_SYN_RECV && child->sk_state != state)
        READ_ONCE(parent->sk_data_ready)(parent);        // :1005 唤醒睡在accept()的进程
}
```

`tcp_rcv_state_process` 的 SYN_RECV 分支 (tcp_input.c:7218-7260) 把状态推向终点:

```c
/* tcp_input.c:7235-7237 */
tcp_ao_established(sk);
smp_mb();
tcp_set_state(sk, TCP_ESTABLISHED);      // :7237 ★服务端ESTABLISHED
```

而睡在 `accept()` 里的服务端进程由 `inet_csk_accept` (inet_connection_sock.c:649) 唤醒取货:

```c
/* inet_connection_sock.c:667-681 */
if (reqsk_queue_empty(queue)) {
    ...
    error = inet_csk_wait_for_connect(sk, timeo);   // :675 睡眠等待sk_data_ready
    ...
}
req = reqsk_queue_remove(queue, sk);                // :679 从全连接队列摘下child
newsk = req->sk;                                    // :681
```

### 1.6 两条队列与三种溢出

| 队列 | 内核位置 | 容量来源 | 溢出时的行为 |
|-|-|-|-|
| 半连接队列(SYN_RECV 迷你 req) | 挂全局 ehash,由 listener 的 `icsk_accept_queue.qlen` 计数 | `inet_csk_reqsk_queue_is_full` 对比 `listen()` 的 backlog(inet_connection_sock.h:290);`net.ipv4.tcp_max_syn_backlog` 参与 tcp_input.c:7677 的"最后 1/4 只留给已证实源"检查 | 触发 SYN cookie(tcp_input.c:7615):不再存状态,把状态编进 SYN+ACK 的序号里 |
| 全连接队列(等 accept 的 child) | `rskq_accept_head/tail` 链表(request_sock.h) | `listen(fd, backlog)`,受 `net.core.somaxconn` 封顶(socket.c:1982-1984) | 收第三次 ACK 时静默丢弃(tcp_minisocks.c:951,`tcp_abort_on_overflow=0` 时)或回 RST(:957);统计 `ListenOverflows` |

+ 全连接队列满时**丢的是第三次 ACK 而不是 SYN**:req 留在半连接队列,客户端以为建连成功开始发数据,服务端却不断重传 SYN+ACK——这是"客户端 ESTABLISHED 但服务端 accept 不出来"的经典线上问题的根源。
+ 观测:`netstat -s | grep -i listen` 或 `nstat -az | grep -i listen` 看 `ListenOverflows/ListenDrops`;`ss -lnt` 的 `Recv-Q/Send-Q` 列分别是当前全连接队列长度和容量。

### 1.7 SYN cookie 是怎么把状态"藏"进序号的

`tcp_conn_request` 里 `want_cookie=true` 时(tcp_input.c:7698-7702):`cookie_init_sequence`(:7699) 用**密钥对(四元组+时间片+MSS)做可逆编码**算出 IRS —— SYN+ACK 发出后 req 立即释放(`reqsk_free`, :7750),服务端零内存占用。第三次 ACK 到达时,ACK 号里携带的"IRS+1"被 `cookie_v4_check`(syncookies.c:184 `__cookie_v4_check`)反解出四元组与 MSS 合法性,合法就直接建连。代价:放弃保存协商选项(时间戳等),也是 `syncookies=2`(强制)不推荐常开的原因。

### 1.8 为什么必须是三次(内核视角)

三次的本质:**每一方都要把自己"发出去的序号"确认被对方收到,才能安全使用**。
+ 两次(去掉客户端的 ACK):服务端在(2)发出 SYN+ACK 后立即 ESTABLISHED —— 但这个 SYN+ACK 可能丢了、可能是历史重复 SYN 引发的。历史 SYN 迟到时,服务端会单方面建连、白占一个 `tcp_sock` 和全连接队列槽位,数据发过去也只有 RST 回来。有了第三次,`tcp_check_req:838` 用 `ack == snt_isn+1` 验证客户端**真的活着且看到了 IRS**,才付出克隆完整套接字的代价(`:926`)。**三次握手的每一步都在为"下一步要分配多少内存"做担保**。
+ 同时打开(crossed SYN):双方同时 connect,各收对方的裸 SYN。`tcp_rcv_synsent_state_process:6991` 识别后在 SYN_SENT 内直接回 SYN+ACK,双方都经历 SYN_SENT→SYN_RECV→ESTABLISHED,不需要 LISTEN —— TCP 本是对等协议,客户端/服务端只是角色约定。

### 2.2 第一步:A 调用 close() → FIN

`tcp_close` (tcp.c:3310) 只是加锁包装,真正逻辑在 `__tcp_close` (tcp.c:3138)。挥发的状态迁移不写 switch,而是查一张表:

```c
/* tcp.c:3039-3054 close()的状态迁移表 */
static const unsigned char new_state[16] = {
  [TCP_ESTABLISHED] = TCP_FIN_WAIT1 | TCP_ACTION_FIN,  // :3042 主动关闭第一站
  [TCP_CLOSE_WAIT]  = TCP_LAST_ACK  | TCP_ACTION_FIN,  // :3049 被动关闭者再close
  ...
};
/* tcp.c:3056-3063 */
static int tcp_close_state(struct sock *sk)
{
    int next = (int)new_state[sk->sk_state];
    int ns = next & TCP_STATE_MASK;
    tcp_set_state(sk, ns);            // 先迁移状态
    return next & TCP_ACTION_FIN;     // 再决定是否要发FIN
}
```

`tcp_send_fin` (tcp_output.c:3800) 的两个实现细节:

```c
/* tcp_output.c:3814-3843 摘录 */
if (tskb) {                                   // 发送队列尾部还有没发出去的skb?
    TCP_SKB_CB(tskb)->tcp_flags |= TCPHDR_FIN; // :3815 FIN捎带在最后一个数据包上
    TCP_SKB_CB(tskb)->end_seq++;               // :3816 FIN占一个序号
    tp->write_seq++;
    ...
} else {
    skb = alloc_skb_fclone(MAX_TCP_HEADER, ...);
    tcp_init_nondata_skb(skb, sk, tp->write_seq,
                         TCPHDR_ACK | TCPHDR_FIN);  // :3839 单独的纯FIN包
    tcp_queue_skb(sk, skb);
}
__tcp_push_pending_frames(sk, tcp_current_mss(sk), TCP_NAGLE_OFF);  // :3843 立即发出
```

+ **FIN 占一个序号**(`end_seq++`),所以 B 的 ACK 是 `F+1`,和 SYN 占序号完全对称。
+ `sock_orphan`(:3230):close() 返回后进程不再持有这个 fd,但 sock 不能立刻销毁——还要活着收发挥手剩余报文。它被打上 `SOCK_DEAD` 计入孤儿套接字,由内核继续守护到终态。这也解释了为什么 tcp_fin 里唤醒用的是 `if (!sock_flag(sk, SOCK_DEAD))`(:4950):主动关闭后进程已走,没人可唤醒。

### 2.3 第二步:B 收 FIN → ACK → CLOSE_WAIT

B 处于 ESTABLISHED,走收包快路径 `tcp_rcv_established` (tcp_input.c:6467) 的慢速分支 → `tcp_data_queue` (:5574)。**FIN 是被当作"半个数据"处理的**:

```c
/* tcp_input.c:5637-5641 */
eaten = tcp_queue_rcv(sk, skb, &fragstolen);      // 数据部分(可能为0字节)入接收队列
if (skb->len)
    tcp_event_data_recv(sk, skb);
if (TCP_SKB_CB(skb)->tcp_flags & TCPHDR_FIN)
    tcp_fin(sk);                                   // :5640 FIN标志 → 状态机
```

`tcp_fin` (tcp_input.c:4894) 是挥手阶段的"状态迁移枢纽",一个函数覆盖所有非同步状态:

```c
/* tcp_input.c:4898-4932 */
inet_csk_schedule_ack(sk);                              // :4898 排一个ACK(可能延迟合并)
WRITE_ONCE(sk->sk_shutdown, sk->sk_shutdown | RCV_SHUTDOWN);  // :4900 接收方向关闭
sock_set_flag(sk, SOCK_DONE);
switch (sk->sk_state) {
case TCP_SYN_RECV:
case TCP_ESTABLISHED:
    tcp_set_state(sk, TCP_CLOSE_WAIT);                  // :4907 ★ B进入CLOSE_WAIT
    inet_csk_enter_pingpong_mode(sk);
    break;
...
case TCP_FIN_WAIT1:                                     // :4921 同时关闭
    tcp_send_ack(sk);
    tcp_set_state(sk, TCP_CLOSING);
    break;
case TCP_FIN_WAIT2:                                     // :4929 主动关闭方等到了FIN
    tcp_send_ack(sk);                                   // :4931 挥手最后的ACK
    tcp_time_wait(sk, TCP_TIME_WAIT, 0);                // :4932 → TIME_WAIT
    break;
}
```

应用层视角:FIN 入接收队列后,`read()` 先把剩余数据读完,下一次 `read()` 返回 **0**——这就是 EOF 的内核来源(`sk_state_change`/`POLL_IN` 唤醒,:4950-4958)。

### 2.4 第三步:B 应用调用 close() → FIN(CLOSE_WAIT → LAST_ACK)

与第一步完全同路:`__tcp_close → tcp_close_state`,查表 `[TCP_CLOSE_WAIT] = TCP_LAST_ACK | TCP_ACTION_FIN`(tcp.c:3049)→ `tcp_send_fin`。

**为什么挥手是四次而握手是三次?** 因为 B 的 ACK(②,内核行为:tcp_fin 一收到 FIN 就排好了)和 B 的 FIN(③,要等 B 应用调 close)**分别由内核和应用程序发起,时间上可能隔任意久**。这个"间隔"就是 CLOSE_WAIT 状态存在的意义:内核已停收(收到 RCV_SHUTDOWN),但应用的发送方向还开着。若 B 应用 read 到 EOF 后立刻 close,②③会合并成一个 FIN+ACK,抓包上看就只有三个包。

### 2.5 第四步:A 的两跳 —— FIN_WAIT1 → FIN_WAIT2 → TIME_WAIT

**收到②(对 FIN 的 ACK)**:纯 ACK 不走 `tcp_rcv_established`(A 已不是 ESTABLISHED),由 `tcp_rcv_state_process` 的 step5 `tcp_ack()`(:7198)推进 `snd_una`,然后命中 FIN_WAIT1 分支:

```c
/* tcp_input.c:7266-7275 */
case TCP_FIN_WAIT1: {
    if (tp->snd_una != tp->write_seq)      // :7272 FIN(seq=F, 占到F+1)还没被确认?
        break;                              //   write_seq=F+1, snd_una要追到这里
    tcp_set_state(sk, TCP_FIN_WAIT2);      // :7275 ★ 半关闭: 我发完了, 还能收
    WRITE_ONCE(sk->sk_shutdown, sk->sk_shutdown | SEND_SHUTDOWN);
```

**收到③(B 的 FIN)**:注意 A 此刻是 FIN_WAIT2 而非 ESTABLISHED,所以不走 `tcp_rcv_established` 快路径,而是进 `tcp_rcv_state_process` 的 step7"处理段文本"——在 FIN_WAIT1/FIN_WAIT2/CLOSE_WAIT 等状态下数据仍要排队处理,此处调入 `tcp_data_queue`(tcp_input.c:7368)→ 发现 FIN 位(:5640)→ `tcp_fin` 命中 `:4929` 的 FIN_WAIT2 分支——`tcp_send_ack`(④)+ `tcp_time_wait`。对比第二步:同样收 FIN,B(ESTABLISHED)从 `tcp_rcv_established:6656` 进 `tcp_data_queue`,A(FIN_WAIT2)从 `tcp_rcv_state_process:7368` 进——**同一个 tcp_fin 枢纽,两条入口**。换装现场:

```c
/* tcp_minisocks.c:326-393 tcp_time_wait 摘录 */
tw = inet_twsk_alloc(sk, &net->ipv4.tcp_death_row, state);   // :333 分配timewait缩水套接字
tcptw->tw_rcv_nxt = tp->rcv_nxt;      // :344 只保留回ACK所需的最小状态
tcptw->tw_snd_nxt = tp->snd_nxt;
...
if (state == TCP_TIME_WAIT)
    timeo = TCP_TIMEWAIT_LEN;          // :377-378 60秒 (tcp.h:140)
inet_twsk_hashdance_schedule(tw, sk, ..., timeo);  // :383 tw顶替sock进ehash, 启动60s定时器
...
tcp_update_metrics(sk);
tcp_done(sk);                          // :393 原sock销毁
```

`TCP_TIMEWAIT_LEN = 60*HZ`(include/net/tcp.h:140)即 **60 秒** —— Linux 把 RFC 的 2×MSL 直接定值为 60s(MSL 按 30s 计),而非按 RTO 计算。

### 2.6 第五步:B 收最后的 ACK → CLOSED

```c
/* tcp_input.c:7326-7331 */
case TCP_LAST_ACK:
    if (tp->snd_una == tp->write_seq) {   // :7327 我的FIN(K→K+1)被确认
        tcp_update_metrics(sk);           // :7328 把本连接RTT等存入tcp_metrics, 造福同四元组重连
        tcp_done(sk);                     // :7329 → TCP_CLOSE + 销毁 (tcp.c:5082)
        goto consume;
    }
```

`tcp_done` (tcp.c:5082) 清定时器、清队列、置 `TCP_CLOSE`、释放 sock —— B 的终点。A 还要在 TIME_WAIT 里活满 60 秒才轮到。

### 2.7 TIME_WAIT 深挖:60 秒在等什么

TIME_WAIT 只在**主动关闭方**出现,两个使命:

1. **最后的 ACK(④)丢了要能重发**。若④丢失,B 的 LAST_ACK 等不到确认会重传③;A 的完整 sock 已销毁的话,一个新分配到相同四元组的连接会收到"来历不明的 FIN"而回 RST,B 永远困在 LAST_ACK。timewait 缩水套接字就是为这一刻准备的:
```c
/* tcp_minisocks.c:272-283 tcp_timewait_state_process 摘录 */
if (paws_reject || th->ack)
    inet_twsk_reschedule(tw, TCP_TIMEWAIT_LEN);   // :280 收到重传FIN → 重置60s计时
return tcp_timewait_check_oow_rate_limit(...);    // 未被限速则返回 TCP_TW_ACK_OOW
```
检查未被限速时返回 `TCP_TW_ACK_OOW`,由 `tcp_v4_rcv` 的 do_time_wait 分支调 `tcp_v4_timewait_ack` 重发那个 ACK(tcp_ipv4.c:2328-2329)。
2. **让本连接的旧重复报文在网络中自然死亡**,避免串进相同四元组的新连接(这也是 `tcp_done` 前调 `tcp_update_metrics` 存序号信息的原因之一)。

例外——TIME_WAIT 期间收到**序列号更大的合法 SYN**(RFC 1122 允许的 reincarnation):`tcp_timewait_state_process:253-261` 返回 `TCP_TW_SYN` 并算好新 ISN(`tw_snd_nxt + 65535 + 2`,:257)塞给 `tcp_conn_request`(它的第一个局部变量 `u32 isn = TCP_SKB_CB(skb)->tcp_tw_isn`,tcp_input.c:7592 就是干这个的)——允许**同一四元组原地复活**重连。

运维视角:TIME_WAIT 是**主动关闭方的正常形态**,高并发短连接服务端退出后大量 TIME_WAIT 属预期(`tcp_max_tw_buckets` 封顶,超了直接销毁不再警告)。端口复用有**两条独立的路径**,别混为一谈:
+ **被动复活**(上一段):SYN 打到存量 TIME_WAIT 上,`TCP_TW_SYN` 放行;
+ **主动复用**:客户端 connect 选源端口时,`__inet_check_established` 发现同四元组 TIME_WAIT(inet_hashtables.c:621-623),交给 `tcp_twsk_unique`(tcp_ipv4.c:118)裁决——`tcp_tw_reuse=1`(需时间戳)允许复用"年龄 ≥ `tcp_tw_reuse_delay`(默认 1s,:3453)"的 tw;`=2`(7.1.3 默认值,:3452)**仅对环回地址**开快速通道(:130-153),非环回等同 0。

`tcp_tw_recycle`(NAT 下有害)已在 4.12 移除。

### 2.8 挥手的变体与异常

+ **同时关闭**:A、B 同时 close → 双方都走 FIN_WAIT1,都会在 FIN_WAIT1 状态收到对方的 FIN。`tcp_fin:4921` 分支:回 ACK 并进 **CLOSING**;随后各自的 ACK 到达,`tcp_rcv_state_process:7319-7323` 的 CLOSING 分支把双方都送进 TIME_WAIT。TCP 允许两边同为"主动关闭方"。
+ **半关闭 shutdown()**:只关发送方向不关整个连接。`tcp_shutdown` (tcp.c:3071) 同样查表发 FIN,但**不置 SOCK_DEAD、不销毁**,此后仍可继续 `read()`。
+ **粗暴关闭 RST**:两种触发——① close() 时接收队列还有未读数据(`__tcp_close:3182-3187`,"数据都没读就想跑?复位");② `SO_LINGER` 且 linger 时间为 0(:3188-3191)。都走 `tcp_send_active_reset` (tcp_output.c:3851):发 RST、**不进 TIME_WAIT、不等对方**,对端 `tcp_reset()` 直接把连接杀到 CLOSE 并给应用报 `ECONNRESET`。
+ **FIN_WAIT2 的死等风险**:A 半关闭后若 B 永远不 close,A 的 sock 会一直挂在那。内核只对**孤儿**(close() 已返回、SOCK_DEAD)FIN_WAIT2 设防线,tmo = `tcp_fin_time()`(tcp.h:1878,取 max(linger2 或 `tcp_fin_timeout`, 3.5×RTO),`tcp_fin_timeout` 默认 60s,tcp_ipv4.c:3450):
  - 常见情形(tmo ≤ 60s 且进入 FIN_WAIT2 的报文没捎带 FIN):tcp_input.c:7313(close 时已处 FIN_WAIT2 则是 tcp.c:3272)**立即** `tcp_time_wait(sk, TCP_FIN_WAIT2, tmo)` 收编为 timewait 桶,原 sock 当场销毁;
  - tmo > 60s 或 ACK 里捎着 FIN:先挂 keepalive 定时器(tcp_input.c:7303/:7311、tcp.c:3268-3270),到期由 tcp_timer.c:801-812 裁决:linger2≥0 且剩余时间>60s → 收编(:806),否则 `tcp_send_active_reset`(:810) RST 了结;
  - linger2<0:立即 RST 兜底(tcp.c:3259-3264)。

  若 A 尚未 close(shutdown() 半关闭后继续 read),FIN_WAIT2 无限等待是应用自己的选择,内核不设防。

```
         │      │FIN_WAIT_1 │──────────────────────────────▶  │CLOSE_WAIT  │
         │      └─────┬─────┘                                 └─────┬──────┘
         │  收FIN未收ACK│ :4921→CLOSING(同时关闭)                   │应用close: tcp.c:3049
         │            ▼                                            ▼
         │      ┌───────────┐                                 ┌────────────┐
         │      │FIN_WAIT_2 │                                 │ LAST_ACK   │
         │      └─────┬─────┘                                 └─────┬──────┘
         │       收FIN:│ tcp_fin:4929-4932                      收ACK:│ tcp_input.c:7326-7331
         │            ▼                                            ▼ tcp_done:5082
         │      ┌───────────┐                                 ┌────────────┐
         │      │TIME_WAIT  │── 60s(tcp.h:140) ─────────────▶ │   CLOSED   │◀─┘
         │      └───────────┘   tcp_time_wait:326             └────────────┘
         │            ▲
         │            │ CLOSING收ACK: tcp_input.c:7319-7323
         │      ┌───────────┐
         └──────│  CLOSING  │ (同时关闭: 双方FIN_WAIT_1互收FIN, tcp_fin:4921-4927)
                └───────────┘
```

11 个状态中,`TCP_NEW_SYN_RECV`(tcp_states.h:24)是内核内部形态:迷你 req 在 ehash 里被查到时呈现的状态,升级为 child 后对外表现为 SYN_RECV。

## 6. 动手实验(把代码和系统状态对上)

```bash
# 1. 观察握手中间态: 终端A起服务, 终端B连接时立刻在C看状态
nc -l -p 9000 &                    # A: LISTEN
# C: ss -tan state syn-recv        # 半连接(迷你req) → SYN+ACK已发等第3次ACK
#    ss -tan state established     # 建连成功
#    ss -lnt sport = :9000         # Recv-Q=当前全连接队列长度, Send-Q=容量

# 2. 观察 TIME_WAIT (主动关闭方)
curl -s http://localhost:9000 >/dev/null; ss -tan state time-wait

# 3. 抓包验证序号语义 (SYN占一个序号: 第一个数据包seq == SYN的seq+1)
sudo tcpdump -i lo -nn 'tcp port 9000'

# 4. 用 kprobe 把报文和内核函数钉在一起 (bpftrace)
sudo bpftrace -e '
  kprobe:tcp_connect            { printf("SYN发出      %s\n", comm); }
  kprobe:tcp_conn_request       { printf("收到SYN      %s\n", comm); }
  kprobe:tcp_check_req          { printf("收到第3次ACK  %s\n", comm); }
  kprobe:tcp_send_fin           { printf("FIN发出      %s\n", comm); }
  kprobe:tcp_fin                { printf("收到FIN      %s\n", comm); }
  kprobe:tcp_time_wait          { printf("进入TIME_WAIT %s\n", comm); }'

# 5. 队列溢出计数 (全连接队列溢出会丢第3次ACK, 客户端重传)
nstat -az | grep -iE 'ListenOverflows|ListenDrops|SYNCookiesSent|EmbryonicRsts'

# 6. 相关sysctl
sysctl net.ipv4.tcp_syncookies net.ipv4.tcp_max_syn_backlog \
       net.core.somaxconn net.ipv4.tcp_fin_timeout \
       net.ipv4.tcp_max_tw_buckets net.ipv4.tcp_tw_reuse
```

## 7. 延伸学习路径

1. **本篇**之后自然的三站:**数据传输**(`tcp_rcv_established` 的快路径/慢路径预测机制,tcp_input.c:6467)、**拥塞控制**(`tcp_cong.c` + 算法族 `tcp_bbr.c`/`tcp_cubic.c`)、**定时器家族**(`tcp_timer.c`:重传/持久/保活/DELAYED ACK)。
2. 面试高频追问,本文都已给出代码级答案:为什么三次不是两次(§1.8)、为什么四次不是三次(§2.4)、TIME_WAIT 为什么 60s/能否缩短(§2.7)、CLOSE_WAIT 堆积说明什么(B 应用收了 EOF 却不 close,§2.4)、SYN cookie 原理(§1.7)。
3. 对照阅读:RFC 793 的状态图(FIG. 9)与本文 §3 —— Linux 并未逐字实现 RFC(例如 SYN_RECV 的处理在 `tcp_check_req` 的注释里被称作 "RFC793 DOES NOT describe SYN-RECV state",tcp_minisocks.c:738-742),实现与规范的差异本身就是最好的学习材料。
