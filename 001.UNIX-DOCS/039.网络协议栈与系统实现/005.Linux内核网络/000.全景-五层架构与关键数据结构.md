每两层之间都有一份"契约",内核网络代码的扩展点全部长在这些契约上:

|边界|契约(数据结构)|谁填、谁用|
|-|-|-|
|应用 ↔ socket 层|系统调用号 + fd|glibc 封装,`__sys_*` 入口(socket.c)|
|socket 层 ↔ 协议栈|`struct proto_ops`(操作函数集)+ `struct proto`(协议属性)|AF_INET 填 `inet_stream_ops`(af_inet.c:1062)与 `tcp_prot`(tcp_ipv4.c:3336)|
|协议栈 ↔ 设备层|`struct net_device` + `net_device_ops`(netdevice.h:1436)|驱动填回调,协议栈经 `dev_queue_xmit`/`netif_receive_skb` 调用|
|设备层 ↔ 驱动|`ndo_open/ndo_stop/ndo_start_xmit` 回调 + `napi_struct`|e1000e 填 `e1000e_netdev_ops`(netdev.c:7334)|
|驱动 ↔ 硬件|MMIO 寄存器(`regs.h` 偏移)+ DMA 描述符环 + 中断|e1000e 经 `er32/ew32`(e1000.h:607/611)读写|

> 一句话读图:**协议栈不懂网卡,网卡不懂协议栈,中间全靠 `net_device` 这个"插头"**。任何一块新网卡只要填好 `net_device_ops`,协议栈一行不改就能用——这就是抽象层存在的意义。

## 2. 四个核心对象与所属关系

一个 TCP 连接上的数据,内存里的"容器"是 `sk_buff`,而容器两侧分别是 **进程视角的 socket** 和 **硬件视角的网卡**:

<pre>
        进程视角                          硬件视角
   ┌──────────────┐   sk_buff    ┌──────────────────┐
   │ struct file  │              │ struct net_device │
   │  (fd=4)      │              │  "eth0"           │
   │   └─ socket  │◀── send/recv─│  netdev_ops ──────┼──▶ e1000e_netdev_ops
   │       └─ sock│   数据流      │  (netdevice.h:2124 struct net_device)│ (netdev.c:7334 e1000e_netdev_ops)
   │  struct sock │              │   └─ 环/队列        │
   │ (tcp_sock)   │              │      napi_struct   │──▶ napi_poll
   │ sk_receive_q │              │  tx_ring/rx_ring   │
   └──────────────┘              └──────────────────┘
          ▲                               ▲
          │ sk->sk_data_ready 唤醒         │ DMA 描述符指向同一块内存
          └────────── sk_buff ────────────┘
</pre>

|对象|定义|一句话职责|关键成员|
|-|-|-|-|

## 3. sk_buff:贯穿五层的集装箱

协议栈各层封装/解封装**不搬数据**,只移动 `sk_buff` 的指针。以一个 1460 字节 TCP 包为例:

<pre>
内存布局(线性区,skb_reserve 预留 2 字节给以太网头,skbuff.h:2942):
head                                                            end
 │                                                              │
 ▼                                                              ▼
 ┌───┬───┬────────┬──────┬──────┬─────────────────────────┬──────┐
 │pad│pad│Ethernet│  IP  │  TCP │        payload          │ FCS? │
 └───┴───┴────────┴──────┴──────┴─────────────────────────┴──────┘
         ▲        ▲      ▲      ▲                         ▲
         │        │      │      └─ data(收包时解封装逐层后移) │
         │        │      └─ transport_header                    │
         │        └─ network_header                             │
         └─ mac_header                                 tail ────┘

发送方向: data 从 payload 起点开始,每层 skb_push()(指针左移)加一个头
接收方向: data 从 Ethernet 头开始,每层 skb_pull()(指针右移)剥一个头
</pre>

- 发送方向加头:`eth_header`(eth.c:79)、`ip_queue_xmit` 填 IP 头、`__tcp_transmit_skb`(tcp_output.c:1529)填 TCP 头;
- 接收方向剥头:`eth_type_trans`(eth.c:155)设置 `skb->protocol` 并右移 data;`ip_rcv`→`tcp_v4_rcv` 逐层消费;
- 分片数据(SG/scatter-gather)在 `skb_shinfo(skb)->frags[]`,TSO 大包、sendfile 零拷贝都靠它。

## 4. 三种执行上下文:包在内核里"谁在跑"

网络代码最容易迷路的地方不是数据结构,而是**上下文**。同一块 e1000e 网卡,内核在三处不同现场处理它的包:

<pre>
上下文           触发者                     典型函数                              能否睡眠
────────────────────────────────────────────────────────────────────────────────────
进程上下文       应用程序 write/sendmsg      tcp_sendmsg_locked(tcp.c:1117)       ✔ 可睡眠
                应用程序 read/recvmsg       tcp_recvmsg_locked(tcp.c:2656)       (等发送缓冲/等数据)
                epoll_wait/io_uring_enter   ep_poll(eventpoll.c:1938)

硬中断上下文     网卡中断(收/发完成)          e1000_intr_msi(netdev.c:1751)        ✘ 不可睡眠
                (读了 ICR 就关本源中断)      → napi_schedule(:1801,:1806)         只做"预约轮询"

软中断上下文     NET_RX/NET_TX_SOFTIRQ       net_rx_action(dev.c:7914)            ✘ 不可睡眠
                (ksoftirqd 或中断退出时)     napi_poll(:7786)→ 驱动 poll 回调      有预算(quota)约束
                                            dev_queue_xmit(:4766)(发送侧)
</pre>

三条铁律,后续文档反复出现:

1. **硬中断里不做重活**:e1000e 的 ISR 只读 `ICR` 确认原因、调度 NAPI(`__napi_schedule`,netdev.c:1806),真正的收包在软中断里干;
2. **软中断有预算**:`net_rx_action` 每轮给固定 `budget`,超了就把 NAPI 重新挂回轮询链表等下一轮(dev.c:7914),防止软中断饿死进程;
3. **进程上下文才会睡眠**:`sk_stream_wait_memory`(stream.c:122)等发送缓冲、`sk_wait_data`(sock.h:1259)等收包数据,都是进程上下文的特权。

## 5. 两条主链路速览(编号即文档编号)

**发送**(应用 → 网线,详读 [008](008.发包全链路-从sk_buff到网线.md)):

<pre>
send() ─▶ __sys_sendto(socket.c:2231) ─▶ sock_sendmsg(:813) ─▶ tcp_sendmsg_locked(tcp.c:1117)
   ─▶ tcp_write_xmit(tcp_output.c:2963) ─▶ __tcp_transmit_skb(:1529) ─▶ ip_queue_xmit(ip_output.c:463)
   ─▶ ip_output(:428) ─▶ ip_finish_output2(:200) ─▶ neigh_resolve_output(neighbour.c:1599)
   ─▶ dev_queue_xmit(netdevice.h:3416) ─▶ qdisc(pfifo_fast_enqueue, sch_generic.c:757)
   ─▶ dev_hard_start_xmit(dev.c:3894) ─▶ e1000_xmit_frame(netdev.c:5803)
   ─▶ 写 TDT 门铃(writel, netdev.c:5942) ─▶ 硬件 DMA 读取描述符 → 上网线
完成侧: 硬件写回 DD 位 → 中断 → e1000_clean_tx_irq(netdev.c:1216) → 释放 skb → 唤醒 EPOLLOUT
</pre>

<pre>
网线 ─▶ PHY/MAC 校验 ─▶ DMA 写入 rx_ring 缓冲区 ─▶ 写回描述符 DD 位 ─▶ 置 ICR ─▶ 硬中断
   ─▶ e1000_intr_msi(netdev.c:1751) ─▶ __napi_schedule(:1806) ─▶ NET_RX_SOFTIRQ
   ─▶ net_rx_action(dev.c:7914) ─▶ e1000e_poll(netdev.c:2656) ─▶ e1000_clean_rx_irq(:915)
   ─▶ 构建 sk_buff(__netdev_alloc_skb, skbuff.c:759) ─▶ e1000_receive_skb(:553)
   ─▶ napi_gro_receive(netdevice.h:4286) ─▶ netif_receive_skb(dev.c:6454)
   ─▶ __netif_receive_skb_core(:5972) ─▶ ip_rcv(ip_input.c:603) ─▶ ip_local_deliver(:250)
   ─▶ tcp_v4_rcv(tcp_ipv4.c:2068) ─▶ tcp_data_queue(tcp_input.c:5574) ─▶ 入 sk_receive_queue
   ─▶ tcp_data_ready(tcp_input.c:5661) ─▶ sk_data_ready ─▶ sock_def_readable(sock.c:3614)
   ─▶ ep_poll_callback(eventpoll.c:1249)
   ─▶ epoll_wait/io_uring 返回 ─▶ 应用 recv()
</pre>
