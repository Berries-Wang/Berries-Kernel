## 2. 硬中断:ISR 的全部工作

```c
// drivers/net/ethernet/intel/e1000e/netdev.c:1751(节选)
static irqreturn_t e1000_intr_msi(int __always_unused irq, void *data)
{
	...
	u32 icr = er32(ICR);                     // :1756 读中断原因, 同时关本源中断(IAM)

	if (icr & E1000_ICR_LSC) { ... }         // 链路状态(网线插拔) → watchdog
	...
	if (napi_schedule_prep(&adapter->napi)) {             // :1801 CAS 置 NAPI_STATE_SCHED
		__napi_schedule(&adapter->napi);                  // :1806 → dev.c:6710
		...
	}
	return IRQ_HANDLED;
}
```

`__napi_schedule`(dev.c:6710)把 napi_struct 挂进**本 CPU** 的 `softnet_data.poll_list`,然后 `____napi_schedule`(:4957)末尾 `raise_softirq_irqoff(NET_RX_SOFTIRQ)`(:4990;若已处于 net_rx_action 内则仅入队)。软中断何时跑?中断返回路径(irq_exit)立即尝试;攒太多则唤醒 `ksoftirqd/N` 内核线程——这就是 `/proc/interrupts` 里 CPU 使用率与 ksoftirqd 的联动来源。

> **为什么关中断?** 读 ICR 即屏蔽(硬件行为),直到 NAPI 干完活 `napi_complete_done`(:6771)后驱动重写 IMS(e1000_irq_enable, :2685)才恢复。中断风暴被"进一次 ISR → 轮询一整批"的结构性设计压平——这就是 NAPI 的全部意义([004 §4](004.网络设备抽象层-net_device.md))。

## 3. 轮询:从描述符到 sk_buff

`e1000e_poll`(:2656)里 `adapter->clean_rx = e1000_clean_rx_irq`(:915)。每处理一个完成的描述符:

```c
// netdev.c:915(节选, 行号实测)
static bool e1000_clean_rx_irq(struct e1000_ring *rx_ring, int *work_done,   // :915
			       int work_to_do)
{
	...
	while (staterr & E1000_RXD_STAT_DD) {        // :935 硬件说"这个槽写完了"
		...
		staterr = le32_to_cpu(rx_desc->wb.upper.status_error);  // :932 状态区
		...
		dma_rmb();                               // :941 状态先于数据可见(弱内存序)
		...
		...   // ① 复用预映射的 skb(buffer_info 里躺着 §4 预分配的)
		skb = buffer_info->skb;                  // :943
		buffer_info->skb = NULL;
		...
		dma_unmap_single(&pdev->dev, buffer_info->dma, ...);    // :958 流式映射用完即拆
		length = le16_to_cpu(rx_desc->wb.upper.length);         // :962
		...
		skb_put(skb, length);                    // :1026 把有效长度划进数据区
		...
		e1000_rx_checksum(adapter, staterr, skb);// :1029 → :575 校验和卸载 → skb->ip_summed
		...
		e1000_receive_skb(adapter, netdev, skb, staterr,   // :1033
				  rx_desc->wb.upper.vlan);      // :1034
		...
		if (cleaned_count >= E1000_RX_BUFFER_WRITE)        // :1040 每 16 个批量补环
			adapter->alloc_rx_buf(rx_ring, cleaned_count,      // :1041 经函数指针补环
					      GFP_ATOMIC);
	}
	...
}

// netdev.c:553
static void e1000_receive_skb(...)
{
	e1000e_rx_hwtstamp(adapter, staterr, skb);
	skb->protocol = eth_type_trans(skb, netdev);   // eth.c:155: 剥以太头 + 设 protocol=ETH_P_IP
	if (staterr & E1000_RXD_STAT_VP)
		__vlan_hwaccel_put_tag(...);
	napi_gro_receive(&adapter->napi, skb);         // netdevice.h:4286 → 交给 GRO
}
```

`eth_type_trans`(eth.c:155)做三件事:`skb_pull` 掉 14 字节以太头、比较目的 MAC 决定 `PACKET_HOST/BROADCAST/OTHERHOST`、返回以太类型填 `skb->protocol`——正是 [002 §2](002.协议栈层-IP与协议分发.md) 里 `__netif_receive_skb_core` 用来二次分发的值。

## 4. 预映射与补环:性能的隐藏地基

§3 循环里"复用预映射的 skb"来自驱动持续维护的补给线 `e1000_alloc_rx_buffers`(:647):

```c
// netdev.c:647(节选)
	skb = __netdev_alloc_skb_ip_align(netdev, bufsz, gfp);   // :669 skbuff.c:759 带 2 字节对齐
	...
	buffer_info->dma = dma_map_single(&pdev->dev, skb->data, // :678 虚拟→总线地址(一次性)
						  adapter->rx_buffer_len,
						  DMA_FROM_DEVICE);
	...
	rx_desc = E1000_RX_DESC_EXT(*rx_ring, i);                // :688
	rx_desc->read.buffer_addr = cpu_to_le64(buffer_info->dma);
	...
	wmb();                                                   // :696
	writel(i, rx_ring->tail);                                // :700 RDT 门铃: 硬件可填到 i
```

设计精髓:**一次映射,反复使用**。`dma_map_single` 本身开销不小(可能刷 cache/改 IOMMU 页表),所以收包路径只在"补环"时映射,在"消费"时解绑;硬件持有的是同一批总线地址。环满(硬件 RDH 追上 RDT)会触发 `rx_missed_errors`——e1000e 只能丢包计数,这是"补环不及时"的经典症状([011 §6](011.调试方案-e1000e内核网络调试.md))。

## 5. GRO:软中断里的"大批量"

高频小包场景,每包一次协议栈分发太贵。`napi_gro_receive`(netdevice.h:4286)→ `dev_gro_receive`(gro.c:474)把**同流同特征**的段在 sk_buff 链上拼成大包再上送:

<pre>
网线: 1500B × 10 段(同一 TCP 流, 顺序)
GRO 前: 10 × [ip_rcv → tcp_v4_rcv → …]           = 10 次协议栈穿越
GRO 后: 1 × [合并后的 ~15KB skb → ip_rcv → …]    = 1 次协议栈穿越(TSO 反向)

  e1000_receive_skb(:553) ─▶ napi_gro_receive     netdevice.h:4286
                    └▶ dev_gro_receive(gro.c:474)
                          ├─ 同流?(MAC/IP/TCP 五元组+seq 连续) → skb 追加(frag_list)
                          └─ 不同流/超时 → gro_normal_list 直接上送
                    └▶ napi_gro_flush → netif_receive_skb(dev.c:6454)
</pre>

TCP 收到 GRO 合成大包后,配合 GSO/TSO(发送侧 [008 §3](008.发包全链路-从sk_buff到网线.md))使协议栈以"批"为单位运行。代价是**延迟**(攒包)与吞吐的权衡,`ethtool -k` 里 `gro on/off` 可切换。

## 7. 唤醒:到 epoll/io_uring 的三岔口

`sock_def_readable`(sock.c:3614)是三种 IO 模型的分岔口:

```c
// net/core/sock.c:3614(节选)
void sock_def_readable(struct sock *sk)
{
	struct socket_wq *wq;

	trace_sk_data_ready(sk);                    // tracepoint(011 §3 可直接用)

	rcu_read_lock();
	wq = rcu_dereference(sk->sk_wq);
	if (skwq_has_sleeper(wq))
		wake_up_interruptible_sync_poll(&wq->wait, EPOLLIN | EPOLLPRI |
						EPOLLRDNORM | EPOLLRDBAND);   // 唤醒等待者
	sk_wake_async_rcu(sk, SOCK_WAKE_WAITD, POLL_IN);       // SIGIO 异步通知
	rcu_read_unlock();
}
```

|等待者|被谁唤醒|后续|文档|
|-|-|-|-|
|阻塞 `recv()`|`wake_up_interruptible_sync_poll`|`tcp_recvmsg_locked`(:2656)恢复扫描队列|[001 §4](001.应用层-socket收发数据.md)|
|`epoll_wait` 进程|`ep_poll_callback`(eventpoll.c:1249)|epitem 挂就绪链表,epoll_wait 返回|[009 §3](009.epoll-事件驱动网络IO.md)|
|io_uring 提交的 recv|poll 唤醒 → `io_poll_task_func`(io_uring/poll.c:338)|完成入 CQE,multishot 重挂|[010 §4](010.io_uring-异步网络IO.md)|

<pre>
                sock_def_readable (sock.c:3614)
                          │ wake_up_interruptible_sync_poll
                          ▼
              sk->sk_wq->wait 等待队列(驱动/协议栈不关心上面是谁)
      ┌─────────────┬───────────────┬───────────────────┐
      ▼             ▼               ▼                   ▼
  recv()睡眠进程  ep_poll_callback   io_uring poll wait   sk_wake_async(SIGIO)
                  挂 rdllist→唤醒      → io_poll_task_func
                  epoll_wait           → CQE
</pre>

> **NAPI id 的伏笔**:`napi_gro_receive`/`netif_receive_skb` 沿途会把 `napi->napi_id`(netdevice.h:411)写进 `skb->napi_id`,`tcp_queue_rcv` 后落到 `sk->sk_napi_id`——epoll/io_uring 的 **busy-poll**([009 §6](009.epoll-事件驱动网络IO.md)/[010 §6](010.io_uring-异步网络IO.md))靠它找到"该轮询哪条 NAPI 环",把中断等待变成主动轮询。

## 8. 实测:一条命令看完收包全链路

```bash
# 1) ftrace 全链路(一次打开, 看 13 个函数的调用序列)
cd /sys/kernel/tracing
echo 1 > events/net/netif_rx/enable
echo 1 > events/net/netif_receive_skb/enable
echo 1 > events/napi/napi_poll/enable
echo 1 > events/sock/sk_data_ready/enable
echo 1 > tracing_on; ping -c1 10.0.2.2 >/dev/null; cat trace | head -40

# 2) bpftrace 端到端计时(硬件中断到 sk_data_ready)
sudo bpftrace -e '
  kprobe:e1000_intr_msi     { @t0 = nsecs; }
  kprobe:e1000_clean_rx_irq { @t1 = nsecs; }
  tracepoint:sock:sk_data_ready {
      printf("总延迟 ≈ %d us\n", (nsecs - @t0) / 1000);
  }'

# 3) 丢包在哪一环(计数器对账, 详见 011 §6)
ethtool -S eth0 | grep -E 'rx_missed|rx_no_buffer|rx_errors'
cat /proc/net/softnet_stat       # 第 2 列 dropped: backlog 满
nstat -az | grep -E 'TcpInErrs|IpInDiscards'
```
