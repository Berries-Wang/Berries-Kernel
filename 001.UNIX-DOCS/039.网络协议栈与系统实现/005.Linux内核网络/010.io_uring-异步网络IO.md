# 010.io_uring:异步网络 IO 与 NAPI busy-poll<sup>LINUX 7.1.3</sup>

> + 姊妹篇(通用机制/数据结构):[002.IO_Uring/README.md](../002.IO_Uring/README.md)——SQE/CQE/环布局/任务工作队列已在该文档细读
> + 本文定位:epoll 是"事件到了叫你",io_uring 是"操作我替你跑完,结果放 CQE"

io_uring 的网络命令**最终都落在 socket 层已有的函数上**(§2 会看到 `io_send` 调 `sock_sendmsg`)——它改变的不是收发路径,而是**提交与等待的组织方式**:一次 `io_uring_enter` 可以提交上千个 send/recv,收包事件由内核反向变成 CQE,应用零系统调用收结果。

## 2. io_send/io_recv:套在 socket 层外面的异步壳

```c
// io_uring/net.c:1180(节选, io_recv, 行号实测)
int io_recv(struct io_kiocb *req, unsigned int issue_flags)
{
	...
	sock = sock_from_file(req->file);            // io_kiocb.fd → struct socket
	if (unlikely(!sock))
		return -ENOTSOCK;
	...
retry_multishot:
	...
	if (io_do_buffer_select(req)) {              // PBUF 模式: 内核挑缓冲(§4)
		sel.val = sr->len;
		ret = io_recv_buf_select(req, kmsg, &sel, issue_flags);
		...
	}
	...
	ret = sock_recvmsg(sock, &kmsg->msg, flags);   // ★ socket.c:1156, 与阻塞 recv 同路!
	if (ret < min_ret) {
		if (ret == -EAGAIN && force_nonblock) {
			io_kbuf_recycle(req, sel.buf_list, issue_flags);
			return IOU_RETRY;                    // :1225 空转→上交, 由 poll 接管(io_uring.c:1572)
		}
		...
	}
	...
	sel.val = ret;
	if (!io_recv_finish(req, kmsg, &sel, mshot_finished, issue_flags))   // :854
		goto retry_multishot;                    // multishot: 不完成, 重挂继续收
	...
}
```

发送侧 `io_send`(:647)对称,调 `sock_sendmsg`(socket.c:813)。**收发下半场与 [001](001.应用层-socket收发数据.md)/[003](003.协议栈层-TCP数据面.md) 完全重合**——io_uring 只是把"谁在进程上下文里调这些函数"换了人:

|环节|阻塞 recv|epoll + recv|io_uring recv|
|-|-|-|---|
|系统调用次数|每包 2 次(1 阻塞 or 1 空转)|epoll_wait 1 + recv 1|提交批量 1 次,CQE 由内核推|
|数据拷贝位置|进程上下文 `tcp_recvmsg`|进程上下文(同左)|**内核线程/任务工作**(可能省一次上下文切换)|
|缓冲区来源|用户指定|用户指定|可由内核从 **PBUF 环**分配(§4)|
|就绪感知|睡 `sk_wait_data`|ep_poll_callback|poll 回调 → CQE(§3)|

提交侧入口(io_uring.c,行号实测):`io_uring_enter` SYSCALL :2609 → `io_submit_sqes` :2035 → 按 opcode 查 opdef → `io_send/io_recv` 的 prep+issue;完成侧 `io_req_task_complete` :1285 / `io_req_task_submit` :1060(任务工作队列,tctx 机制见 [002.IO_Uring README](../002.IO_Uring/README.md));阻塞等待 CQE:`io_cqring_wait`(wait.c:189)。

## 3. EAGAIN 之后:poll 回调接管

非阻塞语义下,提交 recv 时 socket 队列空,`sock_recvmsg` 返回 `-EAGAIN`。io_uring 不让应用空转重试,而是**改装成 poll 请求**:

```c
// io_uring/poll.c:705(io_arm_poll_handler, 节选, 行号实测)
int io_arm_poll_handler(struct io_kiocb *req, unsigned issue_flags)
{
	const struct io_issue_def *def = &io_issue_defs[req->opcode];
	__poll_t mask = POLLPRI | POLLERR;
	...
	if (def->pollin) {
		mask |= EPOLLIN | EPOLLRDNORM;      // 关心读事件(= tcp_poll 会报告的)
		...
	} else {
		mask |= EPOLLOUT | EPOLLWRNORM;
	}
	if (def->poll_exclusive)
		mask |= EPOLLEXCLUSIVE;

	return io_arm_apoll(req, issue_flags, mask);   // :727 → __io_arm_poll_handler :552
}
```

`__io_arm_poll_handler`(:552)内部经 `vfs_poll`(→ `sock_poll` → `tcp_poll` → `sock_poll_wait`,与 epoll 同一条回调安装路,见 [009 §2](009.epoll-事件驱动网络IO.md))把等待项挂上 `sk->sk_wq`。回调 `io_poll_wake`(poll.c:400)被 `sock_def_readable` 唤醒后 → `io_poll_task_func`(poll.c:338)在任务工作里重试 `io_recv` → 数据到手 → 填 CQE:

<pre>
提交: enter(SEND/RECV…) ─▶ io_submit_sqes(io_uring.c:2035) ─▶ prep/issue(net.c)
   │                                   │ 队列空 → -EAGAIN
   │                                   └▶ io_arm_poll_handler(poll.c:705)
   │                                        └▶ vfs_poll → tcp_poll → sock_poll_wait 装回调
   │   (内核收包: sock_def_readable, sock.c:3614 ← 007/009)
   │                                   ┌▶ io_poll_wake(poll.c:400) → 任务工作队列
   │                                   └▶ io_poll_task_func(poll.c:338) → 重试 io_recv → 成功
   └▶ io_req_task_complete(io_uring.c:1285) ─▶ CQE 入环 ─▶ (等待者 io_cqring_wait wait.c:189 醒)
</pre>

> **对比 epoll**:epoll 把"就绪"暴露给应用,recv 还是应用自己调;io_uring 把"就绪+收完"整个接管,应用只看 CQE。代价是请求生命周期管理(重挂/取消/生命周期引用)全部进内核——`io_poll_task_func`/multishot 机制因此比 epoll 复杂一个数量级。

## 4. multishot recv + 提供缓冲环(PBUF):一次提交收千万包

epoll 时代每个连接一次 `epoll_wait` + 一次 `recv` 的固定成本,在 io_uring 两个特性结合后趋近于零:

```c
// net.c:854(io_recv_finish, 节选, 行号实测)
static inline bool io_recv_finish(struct io_kiocb *req,       // :854
				  struct io_async_msghdr *kmsg,
				  struct io_br_sel *sel, bool mshot_finished,
				  unsigned issue_flags)
{
	...
		if (sr->nr_multishot_loops++ < MULTISHOT_MAX_RETRY &&
		    !(sr->flags & IORING_RECV_MSHOT_CAP)) {   // :916-917 重试上限
			return false;             // :918 返回 false = 请求不完成, 重新入队再收
		}
		/* mshot retries exceeded, force a requeue */   // :920
		...
		if (issue_flags & IO_URING_F_MULTISHOT)
			sel->val = IOU_REQUEUE;   // :924 超限强制重排队
	...
	/* Finish the request / stop multishot. */    // :929
finish:
	...
}
```

- **multishot recv**(`IORING_RECV_MULTISHOT`,uapi :438):提交一次,内核收到一个包填一个 CQE 并**自动重挂**自己,直到错误/用户取消;
- **提供缓冲环**(`IORING_REGISTER_PBUF_RING`,uapi :685):用户 mmap 一圈缓冲区交给内核,`io_recv` 不再要用户提供 buffer,而是 `io_buffer_select`(kbuf.c:226)从环里挑一个,数据直接 DMA 后由内核拷进(或与 zero-copy 配合),CQE 携带 buffer id,用户用完 `IORING_OP_...` 归还;

<pre>
用户态                          内核态
┌──────────────┐  mmap   ┌──────────────────────────────────┐
│ PBUF 环(共享)│◀═══════▶│ io_recv(io_uring/net.c:1180)     │
│ buf[0..N]    │         │   └▶ io_buffer_select(kbuf.c:226)│
└──────────────┘         │   └▶ io_ring_buffer_select :192  │
   ▲ CQE{buf_id}         └───┬──────────────────────────────┘
   │                         └▶ sock_recvmsg → tcp_recvmsg → sk_receive_queue
   │                             (socket 层以下与 001/003/007 全同)
   └── 应用处理完, 归还 buffer id, 循环继续
</pre>

这是 7.1.3 高性能网络服务的标准形态:**一个核一个 ring,multishot recv + PBUF,系统调用频率 → 0**。

## 5. 零拷贝发送(SEND_ZC)

`IORING_OP_SEND_ZC`(uapi :303,prep 为 `io_send_zc_prep`,net.c:1336):协议栈直接把**用户的页面挂进 skb 的 frags**(`skb_zcopy` 机制),DMA 引擎从用户内存读数据上网络——省掉 tcp_sendmsg 的那次大 memcpy。完成后 CQE 分两段:`NOTIFY` 确认数据真正发出(缓冲区可复用)。与 e1000e 的衔接:TX 描述符([008 §4](008.发包全链路-从sk_buff到网线.md))的 `buffer_addr` 直接指向用户页的总线地址,`e1000_tx_map` 的 `dma_map_page`(:5593 起,frag 路径)照常工作。

## 6. IORING_REGISTER_NAPI:io_uring 与 e1000e 的握手

io_uring 把 [009 §6](009.epoll-事件驱动网络IO.md) 的 busy-poll 思路内建:

```c
// io_uring/register.c:907
		...
		ret = io_register_napi(ctx, arg);       // IORING_REGISTER_NAPI (uapi:698)
		...

// io_uring/napi.c:41 起(行号实测)
int __io_napi_add_id(struct io_ring_ctx *ctx, unsigned int napi_id, ...)   // :41 记 napi_id
	...
static int io_napi_register_napi(struct io_ring_ctx *ctx, ...)             // :277 注册 busy-poll 参数
void io_napi_init(struct io_ring_ctx *ctx)                                 // :248
	...
__io_napi_do_busy_loop(struct io_ring_ctx *ctx, ...)                       // :201
```

工作方式(行号实测):应用注册后,`io_cqring_wait`(wait.c:189)在睡下去之前调 `__io_napi_busy_loop`(napi.h:21 声明)——按记录的 `napi_id`([004 §4](004.网络设备抽象层-net_device.md) netdevice.h:411)找到 e1000e 的 `napi_struct`,**主动调它的 poll 回调**(`e1000e_poll`,netdev.c:2656)把硬件环里已到的包立刻收完。`io_napi_sqpoll_busy_poll` 让 SQPOLL 内核线程 `io_sq_thread`(sqpoll.c:293)做同样的事。

<pre>
传统: 包到 → 中断 → NAPI → CQE → 唤醒应用            (中断延迟 + 调度延迟)
busy: 应用已在等 CQE → 主动轮询 RX 环(e1000e_poll) → 包立刻收 → CQE → 应用立刻醒
                                                    (省中断与唤醒, 花一个核)
</pre>

**napi_id 的传递链**(把三层连起来):驱动 `netif_napi_add`(:7463)分配 id → 收包时 `skb->napi_id`(GRO/netif_receive_skb 填)→ `tcp_queue_rcv` 落到 `sk->sk_napi_id` → `ep_set_busy_poll_napi_id`(eventpoll.c:465)/`__io_napi_add_id`(napi.c:41)各自记下 → busy-poll 逐 socket(或逐 ring)直达驱动环。

## 7. 三模型对比总表(结合本文集)

|维度|阻塞 IO|epoll([009](009.epoll-事件驱动网络IO.md))|io_uring(本文)|
|-|-|-|---|
|等待位置|`sk_wait_data`(sock.h:1259)|`ep_poll`(eventpoll.c:1938)|`io_cqring_wait`(wait.c:189)|
|唤醒回调|wait 队列直接醒|`ep_poll_callback`(:1249)|poll 回调 → 任务工作 → CQE|
|每事件系统调用|1(阻塞)|2(wait+recv)|0(批量提交+共享环)|
|数据拷贝|进程上下文|进程上下文|内核上下文(可再省一次切换)|
|缓冲区管理|应用|应用|可 PBUF 由内核管(:685)|
|发送背压|`sk_stream_wait_memory` 睡眠(stream.c:122)|EPOLLOUT 事件|SEND_CQE/重挂,可配合 ZC(IORING_OP_SEND_ZC :303)|
|主动轮询|`SO_BUSY_POLL`|同左(sk_busy_loop, socket.c:1497)|内建 REGISTER_NAPI(:698)|
|适合场景|连接数少逻辑简单|万级连接通用方案|百万 QPS/低 syscall/零拷贝需求|

## 8. 实测

```bash
# 1. 系统调用级(strace 5.19+ 原生解码)
strace -f -e trace=io_uring_setup,io_uring_enter,io_uring_register \
       -e signal=none ./your_io_uring_app

# 2. 内核路径打点(与本文行号对应)
sudo bpftrace -e '
  kprobe:io_submit_sqes       { @submit++; }
  kprobe:io_recv              { @io_recv++; }
  kprobe:sock_recvmsg         { @sock_recvmsg++; }   # 与普通 recv 汇合点
  kprobe:io_arm_poll_handler  { @eagain_poll++; }    # 空提交次数(包还没到)
  kprobe:io_poll_task_func    { @poll_wake++; }      # 被数据唤醒次数
  kprobe:io_cqring_wait       { @wait++; }           # 阻塞等 CQE 次数(busy-poll 在其内部)
  interval:s:1 { print(@submit); clear(@submit); }'

# 3. fdinfo 看 ring 状态(head/tail/SQ/CQ 水位)
ls /proc/$(pidof app)/fdinfo/; cat /proc/<pid>/fdinfo/<uring_fd>
```
