# 场景导入: 一个页面的一生

> 本文用一个**具体场景**串起 HMM 的所有关键机制, 先看懂本文, 再去读源码分析章节。
> 源码基线: Linux v6.8 (与本机 `/usr/src/linux-headers-6.8.0-138-generic` 一致)

---

## 1. 场景设定

一段典型的 **CUDA Managed Memory / ROCm HMM** 程序 (Linux 上分别由 `nvidia-uvm` / `amdkfd` / `nouveau` 驱动实现):

```c
float *p;
cudaMallocManaged(&p, 16 * 1024);   // UVM: 进程申请一段 VA, CPU 和 GPU 共用同一个虚拟地址
p[0] = 42.0f;                       // ① CPU 写 —— 数据落在系统内存 DDR
my_kernel<<<1, 32>>>(p, 16);        // ② GPU 读 —— GMMU 缺页 → HMM 镜像页表 → 数据迁移到显存 VRAM
float x = p[0];                     // ③ CPU 读 —— CPU 缺页 → 数据再迁回 DDR
```

三行代码, 触发了三种完全不同的内核路径。下面按硬件结构 + 页表状态逐阶段展开。

---

## 2. 硬件结构总览

```
                              ┌────────────── GPU (独立显卡) ────────────────┐
                              │  ┌──────────┐        ┌─────────────┐         │
                              │  │   GMMU   │        │ Copy Engine │         │
                              │  │ GPU 页表 │        │ (DMA 拷贝)  │         │
                              │  └──────────┘        └─────────────┘         │
                              │  ┌─────────────────────────────────┐         │
                              │  │     VRAM (HBM/GDDR, ~1TB/s)     │         │
                              │  └─────────────────────────────────┘         │
                              └───────────────────┬──────────────────────────┘
                                                  │ PCIe (~32GB/s, 非全缓存一致)
                                                  │ NVLink / C2C (一致性总线, 可选)
┌────────────────────────── 主机 Host ────────────┼──────────────────────────┐
│                                                 │                          │
│   ┌───────────┐     ┌─────────────┐  ┌──────────┴──────────┐               │
│   │ CPU core  │────►│    MMU      │  │      IOMMU          │               │
│   └───────────┘     │ VA→PA 翻译  │  │    (VT-d / SMMU)    │               │
│                     └─────┬───────┘  │    IOVA→PA 翻译     │               │
│                                      └──────────┬──────────┘               │
│                           │                     │                          │
│                           │        ┌────────────┴───────────┐              │
│                           └───────►│    DDR (System RAM)    │              │
│                                    │     ~100-300GB/s       │              │
│                                    └────────────────────────┘              │
└────────────────────────────────────────────────────────────────────────────┘
```

关键硬件事实 (决定了 HMM 的设计):

| 硬件事实 | 后果 |
|-|-|
| VRAM **不能**被 CPU 直接按页寻址 (只能通过很小的 BAR aperture 窥视) | 迁到 VRAM 的页, CPU 访问必须触发缺页迁回 |
| CPU→VRAM 无原子操作、常无缓存一致性 | VRAM 页不能当普通内存用, 需要 `struct page` 伪装 + 限制 |
| PCIe 带宽 ~32GB/s, 远低于 VRAM ~1TB/s | 数据要尽量搬到 GPU 正在用的地方 (迁移) |
| GPU 有自己的 MMU (GMMU) 和页表 | 内核需要一个机制把 CPU 页表"镜像"过去 → HMM |
| 设备 DMA 走 IOMMU, CPU 缺页有异常、IOMMU 缺页静默丢弃 | 需要软件握手: mmu_notifier + fault 机制 |

## 3. 主线大图: 一个页面在 DDR 和 VRAM 之间的四个人生阶段

图例:

```
DDR  = 系统内存物理页          VRAM = 显存物理页
VA   = 进程虚拟地址(CPU/GPU 同一份地址空间)
PTE  = CPU 页表项              GPTE = GPU 页表项
```

### 阶段 0: CPU 先写, 页在 DDR, GPU 还不认识这段 VA

```
   进程 VA 空间              CPU 页表 (MMU)                物理内存
  ┌────────────┐        ┌──────────────────┐        ┌─────────────────┐
  │  ...       │        │                  │        │  DDR            │
  │  p (VA=A)  │───────►│  A: PTE present  │───────►│  page #1234     │
  │  (16KB)    │ 读/写  │  权限 RW         │  PA    │ p[0]=42 就在这  │
  └────────────┘        └──────────────────┘        └─────────────────┘
                                                          ▲
                                                          │ PCIe 物理上可达
                              ┌──────────────────┐        │
                              │ GPU 页表 (GMMU)  │  <空>  │ ← GPU 还没有任何
                              └──────────────────┘        │   A 的映射
```

### 阶段 1: GPU 读 A → GMMU 缺页 → **hmm_range_fault** 镜像 CPU 页表

```
  GPU kernel 读 A
        │
        ▼ GMMU 查不到 A ──► GPU 把缺页记录写进硬件 fault buffer ──► 驱动中断
                                                                    │
  ┌───────────────────── 驱动缺页处理 (nouveau_svm_fault / uvm service) ──────────────┐
  │                                                                                   │
  │  1. mmu_interval_notifier_insert(A)     ← 向内核订阅: A 所在页表范围变了就通知我  │
  │  2. seq = mmu_interval_read_begin()     ← 记录 CPU 页表"版本号"                   │
  │  3. mmap_read_lock(mm)                                                            │
  │     hmm_range_fault(&range)            ← 核心! 遍历 CPU 页表:                     │
  │        · PTE 缺失 → handle_mm_fault() 强制 CPU 缺页补齐                           │
  │        · 结果填进 range.hmm_pfns[] = { pfn#1234 | VALID|WRITE|order }             │
  │  4. mmap_read_unlock(mm)                                                          │
  │  5. mmu_interval_read_retry(seq)?      ← 锁住驱动更新锁后复查"版本号"             │
  │        · 变了 → goto 2 重试 (和 CPU 线程并发竞争)                                 │
  │  6. 用 hmm_pfns[] 通过 ring buffer 命令更新 GPU 页表:                             │
  │        GPTE: A → pfn#1234 (经 IOMMU/ATS 翻译访问 DDR)                             │
  └───────────────────────────────────────────────────────────────────────────────────┘

   之后: GPU 经 PCIe/NVLink 直接访问 DDR 上的 page #1234 (带宽 ~32GB/s, 慢)
   CPU 页表不变, 数据仍在 DDR —— 这叫"页表镜像 (Address space mirroring)"

   进程 VA 空间         CPU 页表                DDR                 GPU 页表
  ┌────────────┐   ┌──────────────────┐   ┌───────────────┐   ┌────────────────┐
  │  p (VA=A)  │──►│ A: PTE present ──┼──►│ page #1234    │◄──┼─ A: GPTE ──────┤
  └────────────┘   └──────────────────┘   └───────────────┘   └────────────────┘
                          两张页表指向同一个物理页 = 镜像
```

### 阶段 2: 驱动策略迁移 CPU→VRAM → **migrate_vma** 三部曲

驱动发现这块数据 GPU 在高频访问 (fault 统计/access counter), 决定把它搬进显存:

```
  驱动调用 (核心 mm 提供, mm/migrate_device.c):

  ┌───────────────────────────────────────────────────────────────────┐
  │ migrate_vma_setup(&args)                                          │
  │   · 遍历 CPU 页表收集 src[], 锁定 + 隔离页面                      │
  │   · CPU PTE 换成 "migration swap entry", 页从所有 CPU 页表解除映射│
  │   · 期间 mmu_notifier 广播, 各设备摘掉相关映射(可跳过无关设备页)  │
  │                                                                   │
  │ [驱动回调部分]                                                    │
  │   · 在 VRAM 分配一页 → 得到 device-private page (有 struct page!) │
  │   · dst[i] = migrate_pfn(page_to_pfn(vram_page))                  │
  │   · 用 Copy Engine DMA: page#1234 ──► VRAM page#VR-5678           │
  │                                                                   │
  │ migrate_vma_pages()                                               │
  │   · 提交: 把 struct page 元数据从源页搬到目的页                   │
  │                                                                   │
  │ migrate_vma_finalize()                                            │
  │   · CPU 页表写上最终项, 释放源页引用                              │
  └───────────────────────────────────────────────────────────────────┘

  迁移完成后四方的状态:

   进程 VA 空间      CPU 页表                        DDR             VRAM
  ┌────────────┐  ┌─────────────────────────┐  ┌──────────┐   ┌──────────────┐
  │            │  │ A: swap entry           │  │          │   │ page#VR-5678 │
  │  p (VA=A)  │─►│ (device_private,        │  │ #1234    │   │  有 struct   │
  │            │  │  vram pfn)              │  │ 已释放   │   │  page        │
  └────────────┘  │ ← 伪装成"被换出到磁盘"  │  └──────────┘   └──────▲───────┘
                  └─────────────────────────┘                        │
                                    GPU 页表: A → VR-5678 ───────────┘
                                    GPU 全速访问 (~1TB/s)

  ★ 精髓: CPU 视角下"页在显存里" == "页被换出了" (swap entry 非 present)
    所以能 100% 复用内核既有的 swap/缺页/迁移机制, 不用改任何架构代码
```

### 阶段 3: CPU 又读 A → CPU 缺页 → **migrate_to_ram** 迁回

```
  CPU 读 A
     │
     ▼ MMU: PTE 非 present → 缺页异常 → do_swap_page()
            │
            │ pte 是 swap entry, 且 is_device_private_entry() == true
            ▼
      page->pgmap->ops->migrate_to_ram(vmf)          ← dev_pagemap 回调
            │ = nouveau_dmem_migrate_to_ram()
            │ = kfd 的 svm_migrate_to_ram()
            │ = (nvidia) uvm_hmm 的反向迁移路径
            ▼
      内部再次调用 migrate_vma 三部曲, 方向相反: VRAM → DDR
      [驱动] VRAM page#VR-5678 ──DMA──► 新分配的 DDR page#9999
            │
            ▼
   进程 VA 空间      CPU 页表                    DDR              VRAM
  ┌────────────┐  ┌──────────────────┐   ┌─────────────┐   ┌──────────────┐
  │  p (VA=A)  │─►│ A: PTE present   ├──►│ page#9999   │   │ page#VR-5678 │
  │            │  │ 权限 RW          │   │ p[0]=42     │   │ 已归还驱动   │
  └────────────┘  └──────────────────┘   └─────────────┘   └──────────────┘

  GPU 页表同时失效 (mmu_notifier), GPU 下次访问 A 会再走阶段 1 → 2
  页就这样随访问热度在 DDR ↔ VRAM 之间来回搬家, 进程毫无感知
```

## 4. 场景 → 内核函数 映射表

| 场景步骤 | 触发者 | 内核路径 | 核心源码 |
|-|-|-|-|
| ① CPU 写 | CPU MMU | 普通匿名缺页 `do_anonymous_page` | `mm/memory.c` |
| ② GPU 缺页(镜像) | GPU fault buffer 中断 | `mmu_interval_notifier_insert` → `hmm_range_fault` → 驱动填 GPTE | `mm/hmm.c` + `drivers/gpu/drm/nouveau/nouveau_svm.c` |
| ②→③ CPU→VRAM 迁移 | 驱动策略 | `migrate_vma_setup` → 驱动 DMA 拷贝 → `migrate_vma_pages` → `migrate_vma_finalize` | `mm/migrate_device.c` |
| ③ CPU 缺页(迁回) | CPU MMU | `do_swap_page` → `is_device_private_entry` → `pgmap->ops->migrate_to_ram` → 反向 migrate_vma | `mm/memory.c` + `nouveau_dmem.c` / `kfd_migrate.c` |
| 迁移的物理底座 | 驱动初始化 | `request_free_mem_region` + `memremap_pages` (ZONE_DEVICE 热插) | `mm/memremap.c` |

---

## 5. 一句话总结

> **HMM = 页表镜像 (让 GPU 看见进程的地址空间) + ZONE_DEVICE 设备页 (让显存拥有 struct page) + migrate_vma (让数据像 NUMA 迁移一样在 DDR/VRAM 间搬家)。**
> 对 CPU 而言, "页在显存" 和 "页被换出到磁盘" 是同一种东西 —— 一个特殊的 swap entry。
