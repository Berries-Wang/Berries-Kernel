# 001. 硬件背景: GPU 内存体系结构

> HMM 的每一个设计决定, 都是对硬件限制的妥协。读懂硬件, 源码就不用死记。

---

## 1. 独立显卡的内存拓扑

```
                       ┌───────────────── GPU ────────────────────┐
                       │                                          │
   GPU SM 核心 ───────►│  ┌─────┐                                 │
   (计算单元,上千个)   │  │SM...│──┐                              │
                       │  └─────┘  ▼                              │
                       │  ┌─────────────────┐                     │
                       │  │ GMMU (GPU MMU)  │◄─ GPU 页表          │
                       │  │ VA→PA 翻译      │  NVIDIA: 显存       │
                       │  └────────┬────────┘  AMD: 系统内存      │
                       │           ▼                              │
                       │  ┌───────────────────┐                   │
                       │  │ L2 缓存 (物理地址) │                  │
                       │  └─────────┬─────────┘                   │
                       │            ▼                             │
                       │  ┌─────────────────┐                     │
                       │  │ VRAM (HBM/GDDR) │                     │
                       │  │ ~1TB/s, 8-80GB  │                     │
                       │  └─────────────────┘                     │
                       │                                          │
                       │  Copy Engine (CE): 独立 DMA 引擎         │
                       │  fault buffer: GMMU 缺页记录环           │
                       └──────────────────┬───────────────────────┘
                                          │
                        PCIe x16 (~32GB/s)│  NVLink/C2C (一致性, 可选)
                                          │
┌─────────────────────── Host ────────────┼───────────────────────┐
│                                         │                       │
│  CPU core ──► MMU ──► 集成内存控制器(IMC) ──► DDR (System RAM)  │
│                                         │                       │
│  IOMMU (VT-d/SMMU): 设备 IOVA → PA, ATS 支持                    │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 关键硬件组件速查

| 组件 | 位置 | 作用 | 和 HMM 的关系 |
|-|-|-|-|
| DDR (System RAM) | 主机 | CPU 主存 | 页的"原生"住所 |
| VRAM (HBM/GDDR) | 显卡 | GPU 专用高带宽显存 | 迁移目的地; CPU 不能直接寻址 |
| CPU MMU + 页表 | CPU | VA→PA, 缺页异常 | `hmm_range_fault` 遍历/镜像的对象 |
| GMMU + GPU 页表 | 显卡 | GPU VA→PA, 记录缺页到 fault buffer | 镜像的"接收方" |
| IOMMU (VT-d/SMMU) | 主机 | 设备 DMA 地址翻译 + 保护 | GPU DMA 访问 DDR 的通道; 参见 [019.IOMMU](../019.IOMMU/README.md) |
| ATS/PRI | PCIe 扩展 | 设备发起地址翻译请求(缺页上报) | 硬件化页表镜像(较少用), HMM 是纯软件方案 |
| Copy Engine (CE) | 显卡 | 独立 DMA 拷贝引擎 | migrate_vma 时真正搬数据的硬件 |
| fault buffer | 显卡 | GMMU 缺页事件环形缓冲 | 驱动中断处理的输入(见 [006](./006.真实驱动实践-Nouveau-AMD-NVIDIA.md)) |
| NVLink / C2C | 总线 | CPU↔GPU 缓存一致性互连 | 使 `MEMORY_DEVICE_COHERENT` 成为可能 (Grace-Hopper) |

## 3. 三条 "CPU 摸不到显存" 的总线现实 (为什么必须迁移)

```
            CPU 读 VRAM                GPU 读 DDR              GPU 读 VRAM
          ┌────────────────┐        ┌────────────────┐       ┌────────────────┐
  带宽    │ BAR 窥视, 极慢 │        │ ~32GB/s (PCIe) │       │ ~1TB/s (HBM)   │
  原子操作│ ✗ 基本没有     │        │ 受限           │       │ ✓ 全套         │
  缓存一致│ ✗              │        │ PCIe 可选/弱   │       │ ✓              │
  按页映射│ ✗ 不能放页表   │        │ ✓ (经 IOMMU)   │       │ ✓ (GMMU)       │
          └────────────────┘        └────────────────┘       └────────────────┘
```

结论 (对应内核文档 *I/O bus, device memory characteristics* 一节):
1. **VRAM 不是"正常的内存"** → 不能直接进 buddy system, 只能以 ZONE_DEVICE 特殊类型存在;
2. **数据应该跟着使用者走** → 热数据迁移到 VRAM, 这就是 `migrate_vma` 的存在理由;
3. **CPU 访问迁走的页必须"缺页-迁回"** → 这就是 device-private swap entry 的设计。

## 4. 显存(CPU)的可见性: BAR aperture 与 Resizable BAR

VRAM 并非完全对 CPU 隐身: 显卡在 PCIe 枚举时报告 **BAR (Base Address Register)**, 映射出一小段 (传统 256MB, Resizable BAR 可开到全部显存) 的窗口:

```
   CPU 物理地址空间
  ┌────────────────────────────────────────────┐
  │  ...  System RAM (DDR) ...                 │
  ├────────────────────────────────────────────┤  ← BAR1 (VRAM aperture)
  │  GPU BAR: 窗口化直通 VRAM 的一段           │     CPU 可以 mmio 读写,
  │  (传统 256MB / ReBAR 最大 = 显存容量)      │     但慢且无一致性
  ├────────────────────────────────────────────┤  ← BAR2 (常为 doorbell/寄存器)
  │  ...                                       │
  └────────────────────────────────────────────┘
```

- BAR 窗口是给**驱动放 ring buffer/寄存器/小对象**用的, 不是给页表按页管理用的;
- HMM **不用** BAR 让 CPU 直接访问 VRAM 页 (MEMORY_DEVICE_PRIVATE 的页对 CPU 不可寻址), 而是选择"缺页→迁回"。

## 5. 设备侧地址翻译两条路: IOMMU 直通 vs GMMU 缺页

```
 路线A (传统): GPU 程序用设备虚拟地址, GMMU 查 GPU 页表
   ┌────────────────────────────────────────────────────────┐
   │ GPU VA ──► GMMU ──► VRAM PA (本地, 快)                 │
   │              │ miss?                                   │
   │              ▼ 写 fault buffer ──► 驱动中断 ──► HMM    │
   └────────────────────────────────────────────────────────┘

 路线B (GPU DMA 访问主机内存): 两种
   B1. 直通: 驱动把 CPU 页 DMA 映射(dma_map)后的总线地址 IOVA 填进 GPU 页表, DMA 经 IOMMU 翻译
      (nouveau: hmm PFN 先经 nvif/gp100_vmm_pgt_pfn 做 DMA map, 见 006 章)
   B2. ATS (Address Translation Services): GPU 向 IOMMU 发 ATS 翻译请求,
       IOMMU miss 时经 PRI 上报 → 但 Linux 主流路径仍是软件 HMM

 HMM 选 B1 + 软件镜像: 驱动调 hmm_range_fault() 拿到 CPU 页表快照(PFN 列表),
 再用自己的 ring buffer 命令批量写入 GPU 页表 → 与厂商硬件解耦, 通用性最好
```

## 6. 一致性总线: 从"不能"到"能" (C2C/CXL/NVLink-C2C)

| 平台 | 互连 | 效果 | 内核体现 |
|-|-|-|-|
| 传统 PCIe 显卡 | PCIe | GPU↔DDR 无强一致 | `MEMORY_DEVICE_PRIVATE` (VRAM 页 CPU 不可见, 必须迁移) |
| Grace-Hopper / Grace-Blackwell | NVLink-C2C | CPU↔GPU 内存**缓存一致**, CPU 可直接寻址显存 | `MEMORY_DEVICE_COHERENT` (VRAM 页可被 CPU 直接映射) |
| CXL 内存扩展 | CXL.mem | 设备内存挂到一致性域 | 同上 + `MEMORY_DEVICE_GENERIC` |

对应内核判断 (amdkfd 真实源码, `kfd_migrate.c::kgd2kfd_init_zone_device`):

```c
	if (adev->gmc.xgmi.connected_to_cpu) {          /* CPU 互连一致 (如 MI300A APU) */
		pgmap->range.start = adev->gmc.aper_base;
		pgmap->range.end = adev->gmc.aper_base + adev->gmc.aper_size - 1;
		pgmap->type = MEMORY_DEVICE_COHERENT;   /* 显存对 CPU 可见可映射 */
	} else {
		res = devm_request_free_mem_region(adev->dev, &iomem_resource, size);
		...
		pgmap->type = MEMORY_DEVICE_PRIVATE;    /* 显存 CPU 不可见, 只能迁移 */
	}
```

> 一句话: **总线的一致性能力, 决定了显存在内核里以哪种 memory_type 存在。**

## 7. 带宽/延迟数量级 (设计动机的量化)

```
 延迟 (数量级):
   GPU 访 VRAM     ~100ns 级
   GPU 访 DDR      ~1µs 级   (跨 PCIe, 高一个数量级)
   CPU 访 DDR      ~100ns 级
   CPU 访 VRAM     ✗ 常规不可达 (BAR 窥视 µs 级)

 带宽 (数量级):
   VRAM(HBM) ~1TB/s  >>  DDR 8通道 ~200GB/s  >>  PCIe4 x16 ~32GB/s
```

这就是为什么 UVM/ROCm 的策略引擎拼命让"谁在用数据, 数据就搬到谁身边"。
