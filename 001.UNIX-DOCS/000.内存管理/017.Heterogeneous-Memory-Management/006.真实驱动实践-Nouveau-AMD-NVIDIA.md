# 006. 真实驱动实践: Nouveau SVM / AMD KFD / NVIDIA UVM

> 三家 GPU 驱动, 同一套 HMM 概念, 三种实现深度:
> **nouveau** = 教科书式完整 HMM 用户 (in-tree) / **amdkfd** = ROCm 官方, HMM 重度用户 (in-tree) /
> **nvidia-uvm** = 闭源大厂自研, 正在向内核 HMM 迁移 (本机有源码可看)

---

## 1. 三家对照表

| | nouveau (NVIDIA 开源) | amdkfd (AMD ROCm) | nvidia-uvm (NVIDIA 闭源) |
|-|-|-|-|
| 用户态接口 | `/dev/nvidiactl` + nvif | `/dev/kfd` + thunk | `/dev/nvidia-uvm` + CUDA |
| 页表镜像 | `hmm_range_fault` (`nouveau_svm.c`) | `svm_range_get_pages` 等 | 自研镜像 + **正在切 HMM** (`uvm_hmm.c`) |
| 设备内存 | `nouveau_dmem.c` (MEMORY_DEVICE_PRIVATE) | `kfd_migrate.c` (PRIVATE/COHERENT) | 自研 VRAM 分配器 (`uvm_pmm_gpu.c`) |
| 迁移引擎 | CE (copy engine) + fence | sdma + fence | CE + semaphore tracker |
| 缺页入口 | GPU fault buffer → `nouveau_svm_fault` (workqueue) | GPU vm fault 中断 → `svm_migrate_to_ram` 等 | GPU fault buffer → `uvm_gpu_replayable_faults` |
| 策略 | 简单 (fault 即镜像) | + XGMI/NUMA 感知, prefetch | 最重: access counters/thrashing/prefetch/read-dup |

## 2. nouveau: 教科书式镜像路径 (`nouveau_svm.c`)

GPU 缺页的硬件起点: fault buffer (一个显存里的环形缓冲, GMMU miss 时硬件写入):

```
  GPU SM 访问 VA ──► GMMU miss ──► fault buffer 环形缓冲写入事件 ──► 中断/轮询
                                        │
                                        ▼
                    nouveau_svm_fault() (workqueue, 解析+排序 fault 项)
                                        │  按 GPU 上下文(instance)/地址排序, 合并处理
                                        ▼
                    nouveau_range_fault()  ──► hmm_range_fault()  (003 章)
                                        │  拿到 hmm_pfns[]
                                        ▼
                    nouveau_hmm_convert_pfn()  编码成 nouveau 自己的 PTE 格式
                                        │
                                        ▼
                    nvif_object_ioctl() ──► 内核侧再走 DMA map ──► 写 GPU 页表
                                        │
                                        ▼
                    重放 fault 的 GPU 访问 (replayable fault 机制)
```

### 驱动侧 hmm_range 的组装 (v6.8 真实源码)

```c
static int nouveau_range_fault(struct nouveau_svmm *svmm,
			       struct nouveau_drm *drm,
			       struct nouveau_pfnmap_args *args, u32 size,
			       unsigned long hmm_flags,
			       struct svm_notifier *notifier)
{
	unsigned long timeout =
		jiffies + msecs_to_jiffies(HMM_RANGE_DEFAULT_TIMEOUT);
	/* Have HMM fault pages within the fault window to the GPU. */
	unsigned long hmm_pfns[1];             /* GPU 一次缺页只请求 1 页 */
	struct hmm_range range = {
		.notifier = &notifier->notifier,
		.default_flags = hmm_flags,        /* HMM_PFN_REQ_FAULT (+WRITE) */
		.hmm_pfns = hmm_pfns,
		.dev_private_owner = drm->dev,     /* "显存页是我家的" */
	};
	struct mm_struct *mm = svmm->notifier.mm;
	int ret;

	ret = mmu_interval_notifier_insert(&notifier->notifier, mm,
					args->p.addr, args->p.size,
					&nouveau_svm_mni_ops);
	if (ret)
		return ret;

	range.start = notifier->notifier.interval_tree.start;
	range.end = notifier->notifier.interval_tree.last + 1;

	while (true) {
		if (time_after(jiffies, timeout)) {    /* 1s 超时防活锁 */
			ret = -EBUSY;
			goto out;
		}

		range.notifier_seq = mmu_interval_read_begin(range.notifier);
		mmap_read_lock(mm);
		ret = hmm_range_fault(&range);
		mmap_read_unlock(mm);
		if (ret) {
			if (ret == -EBUSY)
				continue;
			goto out;
		}

		mutex_lock(&svmm->mutex);
		if (mmu_interval_read_retry(range.notifier,
					    range.notifier_seq)) {
			mutex_unlock(&svmm->mutex);
			continue;                  /* 版本变了 → 重来 */
		}
		break;
	}

	nouveau_hmm_convert_pfn(drm, &range, args);

	ret = nvif_object_ioctl(&svmm->vmm->vmm.object, args, size, NULL);
	mutex_unlock(&svmm->mutex);

out:
	mmu_interval_notifier_remove(&notifier->notifier);
	return ret;
}
```

### invalidate 回调: CPU 页表一变, GPU 映射先摘

```c
static bool nouveau_svm_range_invalidate(struct mmu_interval_notifier *mni,
					 const struct mmu_notifier_range *range,
					 unsigned long cur_seq)
{
	struct svm_notifier *sn =
		container_of(mni, struct svm_notifier, notifier);
	...
	/*
	 * The overlapping device MMU mappings must be invalidated ...
	 * (硬件保证: invalidate 返回前 GPU 不能再访问旧映射)
	 */
	if (mmu_notifier_range_blockable(range))
		mutex_lock(&sn->svmm->mutex);
	else if (!mutex_trylock(&sn->svmm->mutex))
		return false;                /* 拿不到锁 → 告诉内核稍后再试 */

	mmu_interval_set_seq(mni, cur_seq);  /* 推进版本号 */

	if (mmu_notifier_range_blockable(range))
		mutex_unlock(&sn->svmm->mutex);
	return true;
}

static const struct mmu_interval_notifier_ops nouveau_svm_mni_ops = {
	.invalidate = nouveau_svm_range_invalidate,
};
```

> 镜像的一致性闭环 = `mmu_interval_read_begin/retry` (读侧版本号) +
> `invalidate` 回调里 `mmu_interval_set_seq` (写侧推进版本号) +
> 驱动自己的 `svmm->mutex` (GPU 页表更新与失效互斥)。

### convert: 把 HMM PFN 翻译成 GPU 页表项

```c
static void nouveau_hmm_convert_pfn(struct nouveau_drm *drm,
				    struct hmm_range *range,
				    struct nouveau_pfnmap_args *args)
{
	struct page *page;

	if (!(range->hmm_pfns[0] & HMM_PFN_VALID)) {
		args->p.phys[0] = 0;
		return;
	}

	page = hmm_pfn_to_page(range->hmm_pfns[0]);
	/* CPU 用大页映射时, GPU 也建大页表项 (省 TLB) */
	if (hmm_pfn_to_map_order(range->hmm_pfns[0])) {
		unsigned long addr = args->p.addr;

		args->p.page = hmm_pfn_to_map_order(range->hmm_pfns[0]) +
				PAGE_SHIFT;
		args->p.size = 1UL << args->p.page;
		args->p.addr &= ~(args->p.size - 1);
		page -= (addr - args->p.addr) >> PAGE_SHIFT;
	}
	if (is_device_private_page(page))
		args->p.phys[0] = nouveau_dmem_page_addr(page) |    /* 在显存 */
				NVIF_VMM_PFNMAP_V0_V |
				NVIF_VMM_PFNMAP_V0_VRAM;
	else
		args->p.phys[0] = page_to_phys(page) |              /* 在 DDR */
				NVIF_VMM_PFNMAP_V0_V |
				NVIF_VMM_PFNMAP_V0_HOST;
	if (range->hmm_pfns[0] & HMM_PFN_WRITE)
		args->p.phys[0] |= NVIF_VMM_PFNMAP_V0_W;
}
```

## 3. amdkfd: HMM 重度用户 (`kfd_migrate.c`)

ROCm 对 VRAM 的注册与双向迁移全部基于核心 HMM (源码已在 [005](./005.ZONE_DEVICE与devmap.md)/[004](./004.migrate_vma-双向迁移源码分析.md) 引用):

```c
static const struct dev_pagemap_ops svm_migrate_pgmap_ops = {
	.page_free		= svm_migrate_page_free,
	.migrate_to_ram		= svm_migrate_to_ram,   /* CPU 缺页 → VRAM 迁回 */
};

/* GPU 侧主动迁移 CPU→VRAM: svm_migrate_vma_to_vram() 真实序列 */
	r = migrate_vma_setup(&migrate);               /* migrate.flags = SELECT_SYSTEM */
	r = svm_migrate_copy_to_vram(node, prange, &migrate, &mfence, scratch, ...);
	migrate_vma_pages(&migrate);
	svm_migrate_copy_done(adev, mfence);           /* 等 SDMA 拷贝完成 */
	migrate_vma_finalize(&migrate);
```

特色: 迁移粒度对齐 (`prange->granularity`, 可以 2M)、SDMA 异步 + `mfence` 同步、
XGMI 多 GPU 路由选择、`KFD_MIGRATE_TRIGGER_PAGEFAULT_CPU/GPU/PREFETCH` 等
触发来源分类记账。

## 4. nvidia-uvm: 从自研镜像走向内核 HMM (本机源码 `/usr/src/nvidia-580.178.04/nvidia-uvm/`)

历史路径:

```
  ~2016: UVM 自研 "mirror" (自己的 mmu_notifier + 自有页表镜像)
    │
  ~2023: NVIDIA 开始把 UVM 迁到内核标准 HMM
    │     (上游 patchset: "nova core"/uvm+hmm; 新增 uvm_hmm.c)
    ▼
  580.178 (本机): 过渡态 ——
     uvm_hmm.h: 完整的 HMM 层接口 (34+ 个函数)
     uvm_hmm.c: 只有 module_param 开关 (实现体在闭源构建里/或被裁剪)
```

本机源码中的证据 (`uvm_hmm.c`, 仅 50 行):

```c
// Support for HMM ( https://docs.kernel.org/mm/hmm.html ):

#ifdef NVCPU_X86_64
static bool uvm_disable_hmm = false;
MODULE_PARM_DESC(uvm_disable_hmm,
                 "Force-disable HMM functionality in the UVM driver. "
                 "Default: false (HMM is enabled if possible). ...");
#else
// TODO: Bug 4103580: UVM: HMM: implement HMM support on ARM64 (aarch64)
// So far, we've only tested HMM on x86_64 and aarch64 and it is broken on
// aarch64 so disable it by default everywhere except x86_64.
static bool uvm_disable_hmm = true;
...
#endif

module_param(uvm_disable_hmm, bool, 0444);
```

`uvm_hmm.h` 暴露的接口面 (学习 NVIDIA 如何切分 HMM 层的极佳材料):

| 接口组 | 函数 | 对应本仓库章节 |
|-|-|-|
| va_space 生命周期 | `uvm_hmm_va_space_initialize/destroy` | [README](./README.md) |
| block 管理 | `uvm_hmm_va_block_find_create` / `split_tree` / `reclaim` | - |
| **GPU 缺页服务** | `uvm_hmm_va_block_service_locked` (内部会走 `hmm_range_fault`, 见 `uvm_hmm_va_block_update_residency_info` 注释) | [003](./003.hmm_range_fault-页表镜像源码分析.md) |
| **迁移** | `uvm_hmm_migrate_ranges` (UvmMigrate) / `uvm_hmm_va_block_migrate_locked` / `evict_chunks` | [004](./004.migrate_vma-双向迁移源码分析.md) |
| 策略 | `set_preferred_location` / `set_accessed_by` / thrashing / prefetch | - |
| 跨进程缺页 | `uvm_hmm_remote_cpu_fault` (别人家的进程碰到我家显存页) | [005](./005.ZONE_DEVICE与devmap.md) |

以及老的 mmu_notifier 关联逻辑 (`uvm_va_space_mm.c`):

```c
    if ((UVM_IS_CONFIG_HMM() || UVM_HMM_RANGE_FAULT_SUPPORTED()) &&
        uvm_va_space_pageable_mem_access_supported(va_space)) {
            ...
            // Initialize MMU interval notifiers for this process. This allows
            // mmu_interval_notifier_insert() to be called without holding the
            // mmap_lock for write.
            ret = __mmu_notifier_register(NULL, current->mm);
```

> 观察: UVM 的策略层(thrashing/access counter/read duplication) 远比内核 HMM 复杂 ——
> 印证了内核文档的分工: **HMM 只提供机制(mirror+migrate), 策略完全归驱动。**

## 5. 学习建议: 按什么顺序读源码

```
 ① 先读 in-tree 教科书 (小而完整):
    drivers/gpu/drm/nouveau/nouveau_svm.c   ← 镜像全流程 (~1000 行)
    drivers/gpu/drm/nouveau/nouveau_dmem.c  ← 设备内存全流程 (~900 行)
 ② 再读工业级 (特征丰富):
    drivers/gpu/drm/amd/amdkfd/kfd_migrate.c (~1000 行)
    drivers/gpu/drm/amd/amdkfd/kfd_svm.c     (range 管理, 大)
 ③ 最后看闭源过渡态:
    /usr/src/nvidia-580.178.04/nvidia-uvm/uvm_hmm.h  (只读接口, 理解分层)
 ④ 核心源码对照读:
    mm/hmm.c → mm/migrate_device.c → mm/memremap.c  (本仓库 003/004/005 章)
```
