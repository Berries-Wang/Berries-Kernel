# MMIO 的缺点:多总线路由问题与 ARM64 的处理

> 学习: <br/> - [现代操作系统（第4版）英文.pdf](../../../007.BOOKs/现代操作系统/现代操作系统（第4版）英文.pdf)#page:374-375 §5.1.3 Memory-Mapped I/O(以第4版页码为准) <br/> - [Modern Operating Systems 5th Edition](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf)#page:372-373 同节,仅两处措辞差异(见"与第5版的出入")

## 一、背景

第4版 §5.1.3 在讲完 MMIO 的三个优点(驱动可全部用 C 写、无需专门保护机制、所有可引用内存的指令都能操作设备寄存器)后,转向缺点。**"In computer design, practically everything involves trade-offs"** —— MMIO 的代价不在指令层面,而在系统结构层面:

- **缺点一:缓存/预取会干扰设备寄存器访问**(见 [003.CPU如何与IO设备交互](../../052.IO设备/003.CPU如何与IO设备交互.md) 第8行已有简记,本文补全原文)
- **缺点二:单一地址空间在多总线系统上的路由问题**(本文重点)

## 二、第4版原文(完整引用,PDF #page:374-375)

### 缺点一:缓存是灾难

> "First, most computers nowadays have some form of caching of memory words. Caching a device control register would be disastrous. Consider the assembly-code loop given above in the presence of caching. The first reference to PORT 4 would cause it to be cached. Subsequent references would just take the value from the cache and not even ask the device. Then when the device finally became ready, the software would have no way of finding out. Instead, the loop would go on forever."

中文对照:多数计算机都对内存字做某种形式的高速缓存,而**缓存一个设备控制寄存器将是灾难性的**——第一次引用 PORT 4 会被缓存,后续引用只从缓存取值、根本不问设备;等设备真正就绪时软件无从得知,轮询循环将永远转下去。

> "To prevent this situation with memory-mapped I/O, the hardware has to be able to selectively disable caching, for example, on a per-page basis. This feature adds extra complexity to both the hardware and the operating system, which has to manage the selective caching."

中文对照:硬件必须能**按页选择性地禁用缓存**,这给硬件和操作系统(需管理选择性缓存)都增加了额外复杂性。

### 缺点二:单一地址空间 + 多总线 → 设备看不见地址

> "Second, if there is only one address space, then all memory modules and all I/O devices must examine all memory references to see which ones to respond to. If the computer has a single bus, as in Fig. 5-3(a), having everyone look at every address is straightforward."

中文对照:**只有一个地址空间时,所有内存模块和所有 I/O 设备都必须检查每一次内存引用**,判断该不该由自己响应。单总线结构(图5-3a)下这很简单——人人都能看到每个地址。这句话是整个问题的出发点:统一地址空间隐含"全员地址解码义务"。

> "However, the trend in modern personal computers is to have a dedicated high-speed memory bus, as shown in Fig. 5-3(b). The bus is tailored to optimize memory performance, with no compromises for the sake of slow I/O devices. x86 systems can have multiple buses (memory, PCIe, SCSI, and USB), as shown in Fig. 1-12."

中文对照:现代 PC 的趋势是配备**专用高速内存总线**,纯粹为内存性能调优、不为慢速 I/O 设备做任何折中;x86 系统可以有多条总线(内存、PCIe、SCSI、USB)。图 1-12(大型 x86 系统的多总线结构)见第4版 **§1.3.5 Buses,PDF #page:63**。

> "The trouble with having a separate memory bus on memory-mapped machines is that the I/O devices have no way of seeing memory addresses as they go by on the memory bus, so they have no way of responding to them. Again, special measures have to be taken to make memory-mapped I/O work on a system with multiple buses."

中文对照:麻烦在于——**地址从内存总线上经过时,I/O 设备根本看不见,自然无从响应**。必须采取特殊措施才能让 MMIO 在多总线系统上工作。

图5-3 要点:
- (a) 单总线架构:所有地址(内存和 I/O)都走这一条总线;
- (b) 双总线架构:CPU 对内存的读写走高带宽内存总线,**另留一个内存端口让 I/O 设备访问内存**(该端口是为 DMA 方向准备的,不解决 CPU→设备方向的路由)。

### 三种解决方案

> "One possibility is to first send all memory references to the memory. If the memory fails to respond, then the CPU tries the other buses. This design can be made to work but requires additional hardware complexity."

中文对照:**试错法**——所有内存引用先发给内存,内存不应答(说明不是真内存地址)CPU 再试其他总线。能工作,但需要额外的硬件复杂性。

> "A second possible design is to put a snooping device on the memory bus to pass all addresses presented to potentially interested I/O devices. The problem here is that I/O devices may not be able to process requests at the speed the memory can."

中文对照:**snooping 设备旁听转发**——在内存总线上放一个监听设备,把呈现的地址传递给"可能感兴趣的"I/O 设备。问题:I/O 设备的处理速度可能跟不上内存总线的速度。

> "A third possible design, and one that would well match the design sketched in Fig. 1-12, is to filter addresses in the memory controller. In that case, the memory controller chip contains range registers that are preloaded at boot time. For example, 640K to 1M − 1 could be marked as a nonmemory range. Addresses that fall within one of the ranges marked as nonmemory are forwarded to devices instead of to memory. The disadvantage of this scheme is the need for figuring out at boot time which memory addresses are not really memory addresses."

中文对照:**内存控制器过滤**——内存控制器芯片里有**范围寄存器(range registers),引导时预装载**。例如 640K~1M−1 可标为"非内存"范围;落在非内存范围内的地址被**转发给设备而不是内存**(640K~1M 正是老 PC 里 VGA 显存/BIOS 所在的经典空洞)。缺点:必须在引导时就判定哪些地址不是真内存地址。
出处:第4版 §5.1.3 [PDF #page:375](../../../007.BOOKs/现代操作系统/现代操作系统（第4版）英文.pdf#page:375);第5版 §5.1.3 [PDF #page:373](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page:373) 同句,仅缺点句 "The disadvantage" → "The main disadvantage"。

> "Thus each scheme has arguments for and against it, so compromises and trade-offs are inevitable."

中文对照:每种方案各有支持与反对的理由,折中与权衡不可避免。

### 方案对比表

|方案|做法|代价|
|-|-|-|
|1. 试错|先发内存总线,无应答再试其他总线|额外硬件复杂性 + 未命中时的试错延迟|
|2. snoop 转发|内存总线上监听设备把地址传给可能感兴趣的设备|设备速度跟不上内存总线,拖慢总线|
|3. 范围寄存器过滤(内存控制器)|引导时预装范围寄存器,非内存范围地址转发给设备|必须在引导时判定哪些地址非真内存|

### 方案三的实现本质:可编程地址译码器

方案三与数字电路里的**地址译码器(Decoder)**是同一功能的不同形态——译码器是电路原语,范围寄存器是它的可编程升级:

| | 硬连线译码器 | 范围寄存器过滤(方案三) |
|---|---|---|
| 判断逻辑在哪|组合逻辑门,芯片设计时焊死|比较器 + 寄存器存上下界,引导时可改|
| 地址地图|设计定型后不可变|固件引导时装载/调整|
| 典型例子|74HC138 片选译码、单片机板级地址译码、外设接口内部"偏移→选哪个寄存器"|DMC-620 address region min/max、CMN-600 SAM_MEMREGION、x86 TOM/TOLUD/PCIEXBAR|

- 电路视角:**一个范围寄存器对(min/max)= 两个幅度比较器 + 一个与门**(地址 ≥ min 且 ≤ max 则命中)。原句 "range registers that are preloaded at boot time"(第4版 #page:375 / 第5版 #page:373)翻译成硬件语言就是:把译码阈值从逻辑门里搬进可编程寄存器,开机由固件写好;
- 实际芯片里两种形态**分层叠加**:入口是可编程译码(互连 SAM、内存控制器地址窗口),末端是硬连线译码(外设接口内部"偏移→选哪个寄存器"——最底层原语,焊死在 RTL 里,见下文 ARM64 小节);
- 译码器原语的图示与使能信号说明,见本目录 [README「MMIO工作原理·地址译码器模块」](README.md)。

## 三、逻辑链总结

MMIO 的代价不在 CPU 指令层面,而在系统结构层面——"用内存地址访问设备"要求整个地址通路(缓存、预取、总线路由)都配合:

1. **统一地址空间 → 全员解码义务**:每次内存引用都要有人决定谁响应;
2. **单总线**:广播即可,人人可见,MMIO 天然成立(图5-3a);
3. **内存专用总线**:地址旁路进内存总线,设备看不见 → MMIO 失效(图5-3b);
4. **解法**:让地址找到设备——试错(消极探测)/ snoop 转发(旁听抄送)/ 范围寄存器过滤(引导时建好路由表)。

## 四、ARM64 的处理方式

ARM64 是这套理论的现实标本:**PMIO 根本不存在,100% 依赖 MMIO;多总线路由用的是方案三(硬件地址过滤);缓存问题不用 MTRR 式范围寄存器,而是写进页表的内存属性。**

### 1. 路由:互连(fabric)的系统地址映射 —— 方案三的现实形态

- CPU、内存控制器、外设都挂在 AXI/CHI 互连上,**地址往哪个从设备端口送,由互连的系统地址映射解码决定**。CMN-600 TRM §2.1.9 System Address Map(PDF #page:39):
  > "All CHI commands must include a fully resolved network address. The address must include a source and target ID. Target IDs are acquired by passing a request address through a System Address Map (SAM). The SAM effectively maps a memory or I/O address to the target device."
- 大部分外设地址窗口是 SoC **设计时固化的**(每颗 ARM SoC 手册都有 memory map 一章,见 BCM2711 §1.2 Address map / §1.2.2 Full 35-bit address map,PDF #page:5-6;Zynq UltraScale+ UG585 Table: System-Level Address Map,PDF #page:78);少数窗口是**可配置寄存器,引导时由固件(TF-A/UEFI)装载**——如 DMC-620 内存控制器的 address region min/max 寄存器(`_next` 后缀,初始化提交生效,PDF #page:60-62)、PCIe RC 的 outbound 窗口把 CPU 物理地址翻译成 PCIe 事务。这正是书中所说的 *"range registers that are preloaded at boot time"*(第4版 #page:375 / 第5版 #page:373);
- 与 x86 时代不同,ARM SoC 没有 BIOS 式固定地图,**每颗 SoC 一张自己的图,靠设备树 `ranges`/ACPI 告诉软件**(`/proc/iomem` 可查)。

#### "Target IDs are acquired by passing a request address through a SAM" 逐句解读

**前置:mesh 网络只认"节点编号",不认地址。** CMN-600 是一张二维网格(mesh),每个组件有节点 ID:RN(请求节点,CPU 那侧)、HN-F(管某段 DDR 的一致性节点)、HN-D(管 I/O 设备)、SN(从节点,通向内存控制器)。CHI 协议规定每个事务的包必须带**源节点 ID + 目标节点 ID**,网格路由器按节点 ID 逐跳转发,**根本不看地址**。

**那句话的含义**:CPU 发请求时手里只有物理地址,目标节点 ID 是在事务进网格**之前**,用地址当 key 查 SAM 对照表查出来的("acquired" = 查表得出),查到后填进包的 tgtID 字段。
- 类比:城市路网只认路口编号、不认门牌号。出发前先查地图(SAM)把门牌号换算成"去几号路口",之后全程按路口编号走,路网自身不需要理解任何地址。

**一个请求的完整路由(两级 SAM)**:
1. **引导时**:固件把"地址区间 → 目标节点"的对应关系写进 SAM 寄存器——寄存器层证据:`por_hnf_sam_memregion0`,"Configures range-based memory region 0 in HN-F SAM",含 base_addr/valid 位(PDF #page:411)。这就是书中 *"range registers that are preloaded at boot time"*(第4版 #page:375 / 第5版 #page:373)的工程实体;
2. CPU(RN)发出读物理地址 0x8000_0000 的请求;
3. **RN SAM**(每个发起请求的部件都要有)用地址匹配区间 → 内存地址得到负责该段的 HN-F 节点 ID,I/O 地址可直接映射到 HN-D(RN SAM 可映射到 HN-F/HN-I/HN-D/HN-T);
4. CHI 请求包填上 srcID(自己)+ tgtID(查到的节点),进 mesh 逐跳路由到目标节点;
5. 到达 HN-F 后,由 **HN-F SAM** 再把地址映射成内存控制器(MC)目标 ID,经 SN 落到具体 DDR;range-based region 还能把一段地址交错(hash)到多个 HN-F 上分摊带宽。

**与教科书方案三的对应**:RN SAM 在入口决定"这块地址归谁"(内存→HN-F、设备→HN-D),等价于书里"非内存范围的地址转发给设备而不是内存";HN-F SAM 再决定"具体哪个内存控制器"。笔记前文说的"固件装载的可配置窗口",在 CMN-600 里的工程实体就是 SAM_MEMREGION 寄存器组——本质上是一组**可编程地址译码器**(见前文「方案三的实现本质」)。

参考: [CMN-600 TRM §2.1.9 System Address Map](../../../007.BOOKs/corelink_cmn600_technical_reference_manual_100180_0302_01_en.pdf)#page:39 <br/> [CMN-600 TRM por_hnf_sam_memregion 寄存器](../../../007.BOOKs/corelink_cmn600_technical_reference_manual_100180_0302_01_en.pdf)#page:411 <br/> [DMC-620 TRM 地址窗口寄存器](../../../007.BOOKs/corelink_dmc620_dynamic_memory_controller_technical_reference_manual_100568_0100_00_en.pdf)#page:60-62 <br/> [BCM2711 §1.2 Address map](../../../007.BOOKs/RP-008248-DS-1-bcm2711-peripherals.pdf)#page:5 <br/> [UG585 System-Level Address Map](../../../007.BOOKs/UG585.pdf)#page:78 <br/> 关联笔记: [000.ARM资料库/003.CMN-600](../../../007.BOOKs/000.ARM资料库/003.CMN-600.md)

### 2. 缓存/预取:页表里的 Device 内存属性 —— 缺点一的 ARM 解法

- x86 用 MTRR/PAT 按范围控制缓存;**ARM64 把内存属性编码在页表描述符里**:描述符的 AttrIndx 索引到 `MAIR_ELx` 属性表(Architecture guide:"MAIR_ELx Attr — Controls the Type and cacheability in Stage 1 table descriptors",[mm guide #page:28](../../../007.BOOKs/learn_the_architecture_aarch64_memory_management_guide_101811_0105_00_en.pdf#page:28)),设备页标记为 **Device memory**(最严格 `Device-nGnRnE`:不合并/不重排/不提前应答、禁止推测性访问),保证每次 `readl/writel` 真实抵达设备,永不缓存、无预取;RAM 映射为可缓存的 Normal memory;
- Linux 中 `ioremap()` 默认映射为 Device nGnRE,显存等可预取区域才用 `ioremap_wc()`。MAIR/AttrIndx 速查表见本目录 [README](README.md) "ARM64 关键内存属性速查"。

Device memory](../../../007.BOOKs/learn_the_architecture_-_aarch64_memory_attributes_and_properties_102376_0200_01_en.pdf)#page:15(§6.2 处理器对 nGnRnE/nGnRE 的真实行为 #page:18) <br/> [Arm ARM(A-profile)B2.10 Memory types and attributes](../../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf)#page:6(目录页,B2.10 起始页 manual p.312;在线版见 [该目录 README](../../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/README.md)) <br/> 本目录 [01-MMIO核心调用链](01-MMIO核心调用链.md)(ioremap→页表→MAIR 完整路径)

### 3. 没有 PMIO;两条 ARM64 特色通道

- **AArch64 没有 IN/OUT 指令**。为兼容 PCI 设备的 I/O BAR,内核在虚地址空间固定划一块(PCI I/O 区域,`PCI_IOBASE`)把设备 I/O 口**映射成内存地址**——`inb/outb` 在 arm64 上底层仍是 load/store。连"端口I/O"都被 MMIO 吸收,印证 MMIO 是唯一底座;
- **第三条通道:系统寄存器(MRS/MSR)**。CPU 内部"设备"——GICv3 的 CPU 接口(`ICC_*_EL1`)、通用定时器(`CNTV_*_EL0`)、PMU——不走总线内存地址,而用专门指令访问。这超出第4版 "MMIO vs PMIO" 的二分法;外部设备(如 GIC 的 distributor `GICD_*`/redistributor `GICR_*`)仍走 MMIO。GIC 规范 Table 1-3 列出了前缀与访问方式的对应(ICC_*=系统寄存器,GICD_*/GICR_*=内存映射)。

参考: [IHI0069H GIC 架构规范 Table 1-3 System registers](../../../007.BOOKs/IHI0069H_b_gic_architecture_specification.pdf)#page:28

### 4. DMA 方向:SMMU

设备主动访存(DMA)一侧,ARM64 用 **SMMU**(Arm 的 IOMMU,对标 Intel VT-d / AMD-Vi)做地址翻译和保护,DMA 地址不再直接等于物理地址——对应第4版 §5.1.4 Direct Memory Access(PDF #page:375 起)的现代延伸。SMMU 用 Stream table 按 StreamID 查 STE 定位翻译表结构。

参考: [SMMU software guide §4.2 Stream table](../../../007.BOOKs/learn_the_architecture_-_smmu_software_guide_109242_0100_01_en.pdf)#page:25 <br/> [AMD-48882_IOMMU](../../../007.BOOKs/AMD-48882_IOMMU.pdf)(x86 侧对照)

### 一句话总结

> MMIO 的代价不在指令层面而在系统结构层面——统一地址空间要求所有内存和设备都解码每次内存引用;当内存走专用总线后设备看不见地址,必须靠试错、snoop 转发或**内存控制器范围寄存器过滤**(现代 x86/ARM64 的共同选择,ARM64 中由互连的固化地址图 + 固件装载的可配置窗口实现)把地址送到设备面前;缓存问题则由页表 Device 内存属性(ARM64)或 MTRR/PAT(x86)解决。
