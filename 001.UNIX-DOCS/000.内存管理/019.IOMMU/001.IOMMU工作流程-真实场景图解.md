## 1. 平台总览:IOMMU 坐在哪

以 ARM64 + SMMUv3 为例(x86 上把 SMMU 换成 VT-d/AMD-Vi,拓扑同构):

**拓扑澄清**(为什么不是"MMU—SMMU 串联"也不是"MMU—DDR 直连";旧版简图把 MMU 的页表遍历画成了指向 SMMU 的线,是简画失误):

1. **MMU 与 SMMU 之间没有任何通路**。MMU 是 CPU 集群内部的部件(PTW 是它的一部分),SMMU 是设备侧入口的独立翻译器;SMMU 从不翻译 CPU 流量,MMU 从不翻译设备流量。唯一"沾边"的联系在软件层:SVA 场景下设备直接用进程 VA 时,CD 指向的页表与 CPU `TTBR0` 所指是同一份内存数据(见 [017.Heterogeneous-Memory-Management](../017.Heterogeneous-Memory-Management);5.9 的 arm-smmu-v3 驱动尚未实现 SVA,此为后续内核引入的能力)——是"读同一张表",不是硬件直连。
2. **MMU 与 DDR 之间也没有专线**:CPU 访存要过 DSU/L3 → 系统互联 → 内存控制器;页表遍历(PTW 的读)本身是带 cacheable 属性的内存访问,可能命中 L3 而根本不到 DDR。官方定义:[AArch64 memory management guide §5 #page:20](../../../007.BOOKs/learn_the_architecture_aarch64_memory_management_guide_101811_0105_00_en.pdf#page:20) —— MMU 内含 table walk unit("contains logic that reads the translation tables from memory"),其图 5-1 明确画出 PA 先过 **Caches** 再到 Memory,遍历读表走的就是普通访存路径。
3. **真正的汇聚点是系统互联**,MMU 与 SMMU 的差别只在位置:MMU 是"请求方内部"的翻译器——CPU 放上总线的已是 PA;SMMU 是"总线路口"的翻译器——设备放上总线的是 IOVA,SMMU 翻完才放行。双方各自的页表遍历(PTW/TTW)又都作为普通内存读回到同一根互联上。官方佐证:[SMMU Software Guide §5.1 #page:38](../../../007.BOOKs/learn_the_architecture_-_smmu_software_guide_109242_0100_01_en.pdf#page:38) —— SMMU 需要"提供正确一致性保证的互联端口(如 AMBA 互联上的 ACE-Lite port)";[Figure 5-1 #page:40](../../../007.BOOKs/learn_the_architecture_-_smmu_software_guide_109242_0100_01_en.pdf#page:40) 的系统拓扑即上图原型(PE 走 ACE、加速器经 SMMU 走 ACE-Lite,汇于同一条 ACE interconnect)。互联侧细节见仓库藏 [CMN-700 TRM](../../../007.BOOKs/arm_neoverse_cmn_700_trm_102308_0307_08_en.pdf):§2.1(#page:17) 列出兼容 IP 就是 DMC/GIC/**MMU** 三类、表 2-1(#page:18) 定义 RN-F(CPU 集群接入)/RN-I(代理一个或多个 **ACE-Lite** manager,设备与 SMMU 走的口)/HN-F(内存区域的 Home Node),§2.3(#page:20) 的 **System Address Map(SAM)** 即"按地址映射路由"的本体;另见 [CCI-550 TRM](../../../007.BOOKs/corelink_cci550_cache_coherent_interconnect_technical_reference_manual_100282_0100_01_en.pdf)、[DMC-620 TRM](../../../007.BOOKs/corelink_dmc620_dynamic_memory_controller_technical_reference_manual_100568_0100_00_en.pdf)。
4. 推论:翻译出的 PA **不一定进内存**——互联按地址映射路由,PA 可能落到 MMIO 窗口(见 [023.MMIO/006](../023.MMIO%28内存映射IO%29/006.MMIO的缺点-多总线路由与ARM64处理.md));官方图:[AArch64 memory management guide 图 3-1 #page:9](../../../007.BOOKs/learn_the_architecture_aarch64_memory_management_guide_101811_0105_00_en.pdf#page:9) 把 Physical Address Space 画成 DDR/**Peripherals**/Flash/SRAM/ROM 五类——DDR 只是其中之一。设备 DMA 翻出的 PA 同理,只是保留区/映射策略通常把设备挡在 MMIO 窗口外。
5. **DDR 在片外**(图已按此修正):DDR 颗粒物理上不属于 SoC die——DMC 经片内 **DFI** 接口(DDR PHY Interface,DMC-620 TRM "Additional reading" 列 DFI 3.1/4.0 规范,#page:9)连**片上** DDR PHY,PHY 驱动的 DRAM 通道引脚才是芯片边界,其后经 PCB 走线连到板上 DRAM(或 PoP 叠放在封装上)。常见框图(含本图旧版、SMMU Guide 图 2-2、MMU guide 图 5-1)把"内存"画进大框,那是"内存子系统"的逻辑视角,不是物理边界。两个特例照旧不改结论:①PoP/Apple Silicon 统一内存与 SoC **同封装**,但 DRAM die 仍不是 SoC die;②无 DDR 系统可用片上 OCM/SRAM(CMN-700 TRM §2.3 #page:21 明确支持无物理 DDR 的 CMN-700 系统)。**无论颗粒摆在哪,"翻译表/CMDQ/EVTQ 所在的内存"对 SMMU 而言都要经互联→DMC 这条路访问——逻辑关系与物理摆放无关**。

三个对照点(与 [011.MMU](../011.MMU(Memory%20Management%20Unit)/README.md) 一一对应):

1. **MMU 翻译的是 CPU 取的地址(VA→PA),IOMMU 翻译的是设备发出的地址(IOVA→PA)**;SMMUv3 的 stage 1 页表格式与 ARM MMU 相同(AArch64 LPAE),源码同源于 [io-pgtable-arm.c](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/io-pgtable-arm.c);
2. **MMU 缺页会陷入 CPU,IOMMU 翻译失败只记录事件、丢弃事务**——这正是 [README](README.md) 摘要引 AMD 规范说的"与 CPU MMU 的缺页机制形成鲜明对比",场景四专门画这条故障路径;
3. CPU 用 `TTBR0_EL1` 等寄存器指页表;SMMU 的页表指针存在**内存里的表**(Stream table/CD)中,所以 SMMU 多了两层"表中之表"的间接,见 [002 硬件架构 §2](002.SMMUv3硬件架构-StreamTable与命令队列.md#2-翻译数据结构总图stream-table--ste--cd--页表)。

### 2.2 图中三个"为什么"

1. **为什么②里还有一次 `page_to_phys()`?** `dma_map_page` 的入参是 `struct page`,OS 先把页转成物理地址([dma-mapping.h:227](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/include/linux/dma-mapping.h) `dma_map_page_attrs`)——[006.DMA 篇 §3.4](../006.DMA/001.DMA传送流程(重绘图5-4)与IOMMU地址翻译.md) 的结论"OS 必须先翻译"在这里依然成立;变的只是终点从"写进设备寄存器"变成"写进 IOMMU 页表"。
2. **为什么设备要 StreamID?** 同一根总线挂多个设备,各自映射不同。StreamID 是 SMMU 给每个"流"(通常一个 PCIe Function/一个 SoC 主设备)的编号,由硬件信号给出,IMPLEMENTATION DEFINED(Guide §3.3.1,#page:13)。PCIe 平台通常用 RequesterID 当 StreamID;设备树系统由 [arm-smmu-v3.c:3094](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c) `arm_smmu_of_xlate` 从 `iommu` 节点解析。
3. **④⑤为什么"每笔"都查表?** IOMMU TLB 只缓存最近翻译;冷 TLB 时每笔 DMA 都要完整走 STE→CD→页表遍历(可深至 4 级 × 每级一次内存读)。所以高频小包场景下,IOVA 局部性、`iommu.strict` 的取舍(见 [003 篇 §7](003.Linux内核IOMMU软件栈-从dma_map到SMMU页表.md#7-内核参数与性能权衡))都有实打实的性能含义。

### 2.3 软件侧分步对照(代码速览)

`dma-iommu.c:478-502`(本篇 §2.1 图②的核心,三步:领 IOVA → 建映射 → 返回 IOVA):

```c
/* drivers/iommu/dma-iommu.c:478-502(节选) */
static dma_addr_t __iommu_dma_map(struct device *dev, phys_addr_t phys,
		size_t size, int prot, u64 dma_mask)
{
	...
	size = iova_align(iovad, size + iova_off);        /* 对齐到 IOVA 粒度 */

	iova = iommu_dma_alloc_iova(domain, size, dma_mask, dev);   /* 1. 领 IOVA */
	if (!iova)
		return DMA_MAPPING_ERROR;

	if (iommu_map_atomic(domain, iova, phys - iova_off, size, prot)) {
		iommu_dma_free_iova(cookie, iova, size);
		return DMA_MAPPING_ERROR;                     /* 2. 建映射失败回滚 */
	}
	return iova + iova_off;                            /* 3. 给驱动的是 IOVA */
}
```

**无 IOMMU 平台对照**:同一驱动、同一行 `dma_map_page`,走 [006.DMA 篇 §3.3](../006.DMA/001.DMA传送流程(重绘图5-4)与IOMMU地址翻译.md) 的路径 A(`dma_direct_map_phys`,`phys_to_dma` 后直接当 DMA 地址)——两个世界的分岔点在 `dma_map_phys()`,不在驱动里。

## 3. 场景二:设备直通虚机(VFIO)

VFIO 把整块物理设备(如一块 NVMe)分配给虚机。虚机内核以为自己在操作真硬件,它的"物理地址"其实是 **GPA**(Guest Physical Address);把 GPA 翻成宿主 PA 的是 SMMU。**关键事实(2026-11 复核修正):5.9 的 arm-smmu-v3 默认把 VFIO 直通域实现为 S1 域——GPA 被当作 IOVA 用;本节旧版按"S2-only STE"画,不符合 5.9 默认行为**(证据见 §3.2 第 1 条)。

### 3.1 全流程图(5.9 默认路径:S1 域,GPA 当 IOVA)

```text
═══════════════════════════════════════════════════════════════════════════════
                                ①QEMU 建虚机时把 GPA→HPA 布局逐段
                                  经 VFIO_IOMMU_MAP_DMA 告诉内核;
                                  内核建 UNMANAGED 域并写入域页表。
                                  5.9 驱动把它实现为 S1 域
                                  (arm_smmu_domain_alloc :2400
                                   kzalloc → stage=0=S1;
                                   finalise_s1 :2473):
                                     STE.Config = S1(要配 CD!)
                                     CD.TTBR0 → 宿主内核建的 S1 页表
                                     表内容:GPA → HPA(GPA 当 IOVA)

 ②虚机内核加载驱动,dma_map_page
   ("PA"= GPA),把 GPA 写进设备 desc

 ③设备发 DMA,地址线 = GPA ─────►  StreamID ──► STE
                                  STE.Config = S1 ──► CD ──► S1 页表
                                  GPA ──► HPA(与场景一同一条翻译路径,
                                  只是 IOVA 的语义换成了 GPA)
                                            │
                                            ▼
                                  HPA → 宿主内存。设备被圈死在
                                  "该虚机 GPA 区间"内,越界即
                                  F_TRANSLATION 事件拦截(场景四)

 ④虚机收到中断(vGIC 注入)        宿主先收物理中断 → KVM/QEMU 注入
═══════════════════════════════════════════════════════════════════════════════
```

### 3.2 关键点

- **"GPA 当 IOVA 用",而不是"启 S2"**(2026-11 复核修正):虚机 CPU 侧确实有两级翻译(guest MMU:VA→GPA→HPA,stage 2 由 KVM 建);但设备侧在 5.9 默认只有**一级**——内核 VFIO 建的 S1 表直接做 GPA→HPA。代码证据:[`arm_smmu_domain_alloc`](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c#L2400)(:2400)对 UNMANAGED/DMA/IDENTITY 三种域一律 `kzalloc`(:2414),而枚举 `ARM_SMMU_DOMAIN_S1 = 0`(:698)——零值即 S1;`arm_smmu_domain_finalise`(:2549)仅在硬件**无 S1 能力**时才翻成 S2(:2568-2570)。所以"直通设备的 STE.Config = S2 only"并非 5.9 默认,而是下列形态。
- **S2 形态什么时候出现**:①**嵌套直通**(架构正位):虚机自管 S1(guest 写 CD/S1 表)、宿主用 S2 圈地——Guide #page:29 的分工("Stream table 与 stage 2 表由 hypervisor 管,CD 表与 stage 1 页表由 guest OS 管")描述的就是它。5.9 已留好口子:UNMANAGED 域可经 `DOMAIN_ATTR_NESTING` 置成 `ARM_SMMU_DOMAIN_NESTED`(:3061-3070),finalise 时 NESTED 与 S2 同走 `arm_smmu_domain_finalise_s2`(:2582-2587,:2523,内核代建 S2 表,STE 走 :1912-1923 的 S2VMID/S2TTB 字段);真正让虚机自管 S1 的 KVM 嵌套 SMMU 是后续内核(IOMMUFD 时代)的能力。②**硬件无 S1** 时的 fallback(:2568-2570)。③IDENTITY 域直接 BYPASS(:2563-2565),即 [003 篇 §7](003.Linux内核IOMMU软件栈-从dma_map到SMMU页表.md#7-内核参数与性能权衡) 的恒等域。
- **为什么没有 SMMU 直通不安全**:虚机驱动若被攻破,可以直接让设备 DMA 到宿主任意物理地址(设备眼中的地址根本不受控);直通映射(S1 表也好,S2 表也好)把设备的可访问范围严格限制在该虚机被分配的 GPA 区间内。这就是 [现代操作系统 5th §7.7 #page:526](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page:526) 说 IOMMU 是 I/O 虚拟化基础设施的原因。
- 内核侧入口:QEMU 经 VFIO 对每个直通设备调 `iommu_attach_device` → [arm-smmu-v3.c:2784](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c) `arm_smmu_attach_dev` → `arm_smmu_write_strtab_ent`(arm-smmu-v3.c:1803)装 STE。

## 4. 场景三:用户态驱动(DPDK)

DPDK 把网卡从内核手里拿走,轮询收发包。数据面完全在用户态,但**建映射仍要过一次内核**(VFIO ioctl),之后用户态自己管理 IOVA。

### 4.1 全流程图

```text
      用户态(DPDK 应用)             内核(VFIO+SMMU 驱动)              设备
═══════════════════════════════════════════════════════════════════════════════
 ①rte_eal_init: 大页 mmap 后,
   对每段内存发
   VFIO_IOMMU_MAP_DMA {vaddr,len,iova}
        │
        ▼
                                ②内核 vfio_iommu_type1:
                                  iommu_map(domain, iova, paddr, len, RW)
                                  ——与场景一同一个 iommu.c 入口,
                                   只是 IOVA 由用户态指定
                                  (域挂在 /dev/vfio/<group> 的
                                   container 上)
        │
        ▼
 ③用户态驱动直接写 NIC 的
   RX/TX 描述环(MMIO):
   desc.addr = IOVA ─────────────────────────────────────────► NIC 发 DMA(IOVA)
                                 ┌─────────────────────────────┐
                                 │ SMMU 同场景一⑤-⑧翻译         │
                                 └──────────────┬──────────────┘
                                                ▼
                                     大页物理内存 ←──► 收发数据
 ④数据面收发包: 纯用户态轮询,
   不再进内核(除非 TLB 未命中
   也不用内核——翻译全在硬件)
═══════════════════════════════════════════════════════════════════════════════
```

### 4.2 关键点

- **安全模型变了**:场景一的映射由内核逐笔把守(每次 map 都经过 `dma-iommu` 层的检查);DPDK 是用户态**批量**申请一大块 IOVA 区间,之后用户态自由使用——安全边界从"每笔 DMA"退到"每块内存注册"。这也是为什么 VFIO 必须依赖 IOMMU 隔离:没有 IOMMU 的机器上 VFIO 直接拒绝工作。
- 与场景一的对比一句话:**内核驱动 = 每包两次 ioctl 级别开销(所以不会这么做),DPDK = 每块内存一次 ioctl + 数据面零内核介入**。
- x86 上对应 VT-d + `vfio_iommu_type1`;ARM64 上 VFIO 同样落到 `iommu.c` 的通用 API,最终都是本篇 §2 那套页表。详见 [039.网络协议栈/000.软件加速-Intel DPDK](../../039.网络协议栈与系统实现/000.软件加速-Intel%20DPDK.md)。

## 5. 场景四:设备 DMA 打进未映射地址(故障路径)

恶意或失控的设备对任意 IOVA 发起 DMA——IOMMU 怎么办?这是 [README](README.md) 摘要那条 AMD 引文(“翻译失败不会向设备提供直接指示,与 CPU MMU 缺页机制形成鲜明对比”)的 ARM 侧完整答案。

### 5.1 故障流程图

```text
 设备 DMA(IOVA 无映射)                    软件
═══════════════════════════════════════════════════════════════════════════
 ①设备发起读/写,地址线 = 野 IOVA
        │
        ▼
 ┌─ SMMU ────────────────────────────────────────────────┐
 │ StreamID ──► STE →(按需)CD → 查页表                    │
 │ 查不到 / 权限不符 / STE 无效                            │
 │   ▼                                                    │
 │ ②把事件(Event)写进内存中的 Event Queue:                │
 │   F_TRANSLATION(翻译失败)/ C_BAD_STE(坏 STE)/          │
 │   F_CD_FETCH(CD 取不到)……分类见 Guide §4.9.1,#page:35 │
 │   事件记录 32 字节,SMMU 是生产者(Guide #page:34)       │
 │   ▼                                                    │
 │ ③该事务被 terminate with abort(Guide 图 3-3,#page:16) │
 │   ★ 不通知设备,不重试,不陷入 CPU —— 静默丢弃            │
 │   ▼                                                    │
 │ ④EVTQ 非空 → MSI 中断通知 CPU                          │
 └────────────────────────┬───────────────────────────────┘
                          ▼
 ⑤内核中断线程处理事件队列:
   arm-smmu-v3.c:1981 arm_smmu_evtq_thread
     while (!queue_remove_raw(q, evt))
         dev_info(smmu->dev, "event 0x%02x received:\n", id);
         ← 只打印!没有类似缺页的"补页重放"机制
   (EVTQ_ID 字段: arm-smmu-v3.c:390 EVTQ_0_ID)
═══════════════════════════════════════════════════════════════════════════
```

### 5.2 为什么不能像缺页那样处理

- CPU 缺页:**精确异常**——出错的指令现场可保存可恢复,OS 补页后重放该指令。
- 设备 DMA:**发出去就管不了**——设备是一个异步状态机,堵住它等软件补映射会拖死整条流水;SMMU 的选择是"记录、丢弃、中断",由软件事后处理(修配置、踢设备、或像 PRI 那样走 Page Request 协商,Guide §3.7 #page:20)。例外是 **Stall 模型**:STE 允许把出错事务"挂起"等软件续传(SMMU_CR0/STE.S1STALLD,驱动 `ARM_SMMU_FEAT_STALLS`,arm-smmu-v3.c:646),但这是可选项且性能代价高,内核默认不用。

### 5.3 实际意义

- **安全**:未映射 = 默认拒绝。旁路模式(无映射、直通)反而是显式配置项(`disable_bypass`,arm-smmu-v3.c:416)。攻击面收窄为"IOMMU 页表里的合法 IOVA 区间"。
- **调试**:线上看到 `arm-smmu-v3 <addr>: event 0x07 received:`(0x07=F_TRANSLATION)通常意味着驱动忘 map、map 后提前 unmap、或设备固件发了野地址。x86 VT-d 的对应物是 DMAR fault 记录(`DMAR: DRHD: handling fault...`)。
- 事件队列满会丢弃非挂起事件并报 `EVTQ overflow detected`(arm-smmu-v3.c:2005)——所以大量 DMA fault 时日志可能不全,这也是排查时要留意的。

## 6. 场景五:32 位设备访问 4GB 以上内存

老设备(或部分嵌入式 IP)DMA 引擎只有 32 位地址线,而 4GB 以上的物理地址它够不着。无 IOMMU 时只能 swiotlb 弹跳(双份拷贝);有 IOMMU 时 IOVA 重映射零拷贝解决。本篇只画差别,完整 swiotlb 对照见 [006.DMA 篇](../006.DMA/README.md)。

```text
   无 IOMMU(swiotlb bounce)                有 IOMMU(IOVA 重映射)
═══════════════════════════════════    ════════════════════════════════════
 设备只认 0~4GB                            设备只认 0~4GB(= IOVA 空间)
 DMA 目标缓冲在 8GB 处                      DMA 目标缓冲在 8GB 处
                                          
 swiotlb: 从低 4GB 控制台缓冲区            dma-iommu: alloc_iova_fast 限
   划一块 bounce buffer                    在 32 位以下领 IOVA
   (dma-iommu.c:429-431:                   (iommu_dma_alloc_iova:
    alloc_iova_fast(...,                     "Try to get PCI devices
    DMA_BIT_MASK(32) >> shift)               a SAC address")
 设备 ─DMA→ bounce(低地址)                 iommu_map(iova, phys@8GB)
 CPU memcpy bounce → 8GB 真实缓冲           设备 ─DMA(IOVA)→ SMMU → 8GB
   ★ 双份拷贝,CPU 参与搬运                  ★ 零拷贝,CPU 不参与
═══════════════════════════════════    ════════════════════════════════════
```

关键代码就在场景一那段 `iommu_dma_alloc_iova` 里(dma-iommu.c:428-435):凡是 64 位能力的 PCI 设备,分配器会**优先**在 32 位以下领 IOVA(`alloc_iova_fast(iovad, iova_len, DMA_BIT_MASK(32) >> shift, false)`,:429-431;失败再按 `dma_limit` 领,:433-435),不是只给"老设备"开的特例——这样设备固件、驱动、IOMMU 三方对"设备地址永远 32 位安全"的假设保持一致。

## 7. 总结:五个场景 = 一张表

|维度|①流式 DMA|②直通虚机|③DPDK|④故障|⑤32位重映射|
|---|---|---|---|---|---|
|IOVA 语义|内核分配的设备虚地址|GPA(当 IOVA 用)|用户态选定|任意|32 位以内|
|STE.Config|S1|**S1**(5.9 默认;S2 为嵌套/无S1 形态,§3.2)|S1|任意|S1|
|CD(进程上下文)|需要|**需要**(宿主内核写)|需要|——|需要|
|页表作者|内核 dma-iommu 层|宿主内核 VFIO(QEMU 发起)|内核(VFIO 代建)|——|内核 dma-iommu 层|
|翻译失败后果|不应发生(bug)|guest 不可访问宿主其他内存|用户态越界被拦|记录事件+abort|不应发生|
|性能敏感点|unmap 时 TLBI(strict)|直通映射 TLB 命中率|TLB 命中率+大页|——|低 IOVA 紧凑|
