## 0. 结论速览

|问题|答案|
|---|---|
|SMMUv3 怎么找到"这个设备用哪张页表"|StreamID → Stream table → **STE**(64B)→(S1 时)S1ContextPtr → **CD**(64B)→ TTBR → 页表;两级查表都在内存,硬件自动遍历|
|软件怎么"操纵" SMMU|不是直接写寄存器改页表,而是往内存中的**命令队列**发命令(CMD_SYNC/TLBI/CFGI);SMMU 出事则往**事件队列**投递 Event 并以 MSI 中断通知|
|S1 和 S2 是什么|Stage 1 = 设备自己的"VA"翻译(CD 管,虚机/进程视角);Stage 2 = IPA→PA 翻译(STE 管,Hypervisor 视角)。可单开、可级联|
|x86 对应物|VT-d 的 Root/Context Table ≈ Stream table/STE;AMD IOMMU Device Table ≈ 同;AMD 的 Command/Event Buffer ≈ CMDQ/EVTQ([AMD-48882](../../../007.BOOKs/AMD-48882_IOMMU.pdf) §2.2.2)|

## 2. 翻译数据结构总图:Stream table → STE → CD → 页表

重绘 Guide 图 4-5(#page:29,"Configuration structure example"),这是 SMMUv3 最核心的一张图:

```text
 设备事务(StreamID, SubstreamID?)
        │
        ▼
 ┌────────────────────┐   StreamID 作索引(线性表直接索引;
 │ Stream table        │   两级表先查 L1 描述符,见 §3)
 │ STRTAB_BASE 寄存器  │
 │ 指向(SMMU_STRTAB_BASE :80,驱动写于 reset)                  │
 └─────────┬──────────┘
           ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ STE(Stream Table Entry,64 字节,STRTAB_STE_DWORDS=8,:221)  │
 │                                                             │
 │ Config  : 0=abort 4=bypass 5=S1 6=S2 7=S1+S2 (:223-227)     │
 │ S1Fmt/S1CDMax/S1ContextPtr ──► stage 1 上下文(§5)           │
 │ VMID / VTCR / S2TTB ────────► stage 2 页表基址(§4)          │
 │ EATS/STRW/S1CIR·COR·CSH 等 ─► ATS、StreamWorld、表内存属性  │
 └──────┬──────────────────────────────────┬───────────────────┘
        │ Config 选 S1                     │ Config 选 S2
        ▼                                  ▼
 ┌──────────────────────┐          ┌──────────────────┐
 │ CD(Context Descriptor)│          │ S2 页表(IPA→PA)  │
 │ (64B;由 SubstreamID   │          │ 按 S2TTB 遍历     │
 │  在 CD 表中选中)      │          └────────┬─────────┘
 │  ASID   TTBR0 ───┐    │                   │
 │  TCR    MAIR     │    │                   │
 └──────────────────┼────┘                   │
                    ▼                        │
          ┌──────────────────┐               │
          │ S1 页表(VA→IPA/PA)│              │
          │ 格式=AArch64 LPAE │              │
          │(io-pgtable-arm.c) │              │
          └────────┬─────────┘               │
                   ▼                         ▼
              S1 输出 ────(S1+S2 时作为 IPA 再进 S2)───► PA
```

要点:

- **STE 是"设备级"条目,CD 是"进程/Substream 级"条目**(Guide §4.5,#page:28)。只有开 S1 才需要 CD;纯 S2 或 bypass 时 STE 一个就够。
- **SubstreamID ≈ PCIe 的 PASID**:同一设备多个"虚拟上下文"各用各的 S1(如一个 DMA 引擎多通道、或 SVA 场景下设备直接用进程 VA,参见 [017.Heterogeneous-Memory-Management](../017.Heterogeneous-Memory-Management))。
- 表格式与 CPU MMU 同源:S1 页表就是 AArch64 翻译表,驱动用 [io-pgtable-arm.c](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/io-pgtable-arm.c)(`arm_lpae_*`,格式 ARM_64K/ARM_16K/ARM_LPAE)生成,见 [003 篇 §3](003.Linux内核IOMMU软件栈-从dma_map到SMMU页表.md#3-一次-dma_map的完整软件流程)。

## 3. Stream table 的两种形态

Guide §4.2(#page:25-26),由 `SMMU_IDR0.ST_LEVEL` 报告支持哪种,软件用 `STRTAB_BASE_CFG` 选择:

**线性表**(图 4-2):连续数组,`STE_addr = STRTAB_BASE + StreamID × 64`,简单但 StreamID 位宽大时表巨大。

**两级表**(图 4-3,SPLIT=8):L1 表存 L1STD(L1 Stream Table Descriptor,L2Ptr + Span 字段,#page:27 图 4-4),按需挂 L2 子表——省内存且免大块连续分配:

```text
 STRTAB_BASE ──► ┌────────────┐
                 │ L1STD 0     │────► L2 表(StreamID 低 8 位索引): STE 0x000..0x0ff
                 │ L1STD 1     │────► L2 表: STE 0x100..0x1ff
                 │ (invalid)   │        (Span 未覆盖的 StreamID 视为无效)
                 │ L1STD 3     │────► ...单 STE 的退化情形也可以
                 └────────────┘
 L1STD_addr = STRTAB_BASE + StreamID[高n位] × 8
 STE_addr   = L1STD.L2Ptr + StreamID[低8位] × 64    (Guide #page:27)
```

驱动的选择在 [arm-smmu-v3.c:215 `STRTAB_SPLIT 8`](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c#L215):特性探测到 2L 支持即用两级表(`ARM_SMMU_FEAT_2_LVL_STRTAB`,:635),L1 固定,某 StreamID 第一次被用到时才在 [arm_smmu_init_l2_strtab](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c#L1952) 挂 L2——"按需分配"字面落地。

## 4. STE:设备上下文

STE 8 个 64 位字,驱动字段定义集中在 arm-smmu-v3.c:223-276。常用的四个字:

|字|关键字段|含义|驱动写入点|
|-|-|-|-|
|STE[0]|`Config`(3:1)|abort/bypass/S1/S2|`arm_smmu_write_strtab_ent` :1906-1909(S1)/:1925(S2)|
||`S1Fmt`(5:4)/`S1CDMax`(63:59)|CD 表格式与 Substream 位宽|同上(S1)|
||`S1ContextPtr`(51:6)|**CD 表基址**|`s1_cfg->cdcfg.cdtab_dma`|
|STE[1]|`S1CIR/S1COR/S1CSH`(CD 表内存属性)、`STRW`(StreamWorld)|S1 访问的 cacheability/安全态|:1895-1900|
||`EATS`(29:28)|PCIe ATS 允许|:1928-1930(master->ats_enabled)|
|STE[2]|`VMID`(15:0)/`VTCR`|S2 的虚机号与翻译控制|:1914-1916|
|STE[3]|`S2TTB`(51:4)|**S2 页表基址**|:1923|

安装/更新 STE 的铁律(函数头注释,arm-smmu-v3.c:1814-1820):SMMU 读 STE 无固定顺序且 8 字不能原子写,所以必须 **"先写 dword1..7 → sync → 再写 dword0(Config)→ sync"** 的两段式(`arm_smmu_sync_ste_for_sid`,两处调用 :1932/:1935,函数定义在 :1789,内含 CFGI_STE 命令,见 §6)。这一段是"软件如何安全地改硬件正在用的表"的教科书案例,与 MMU 侧更新 TTBR 的 DSB+ISB 节奏同理。

## 5. CD:进程(Substream)上下文

CD 同为 64B,字段宏在 arm-smmu-v3.c:293-314:`TCR_T0SZ/TG0/IPS`(与 CPU 侧 TCR_EL1 同义)、`ASID`(63:48)、`TTB0`(51:4)、`MAIR`。分配与填充全在 [arm_smmu_domain_finalise_s1](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c#L2473):

```c
/* arm-smmu-v3.c:2473-2510(节选)—— 一个 S1 域的 CD 内容 */
	ret = xa_alloc(&asid_xa, &asid, &cfg->cd,        /* 领一个 ASID */
		       XA_LIMIT(1, (1 << smmu->asid_bits) - 1), GFP_KERNEL);
	...
	cfg->cd.asid	= (u16)asid;
	cfg->cd.ttbr	= pgtbl_cfg->arm_lpae_s1_cfg.ttbr;  /* ← S1 页表基址 */
	cfg->cd.tcr	= FIELD_PREP(CTXDESC_CD_0_TCR_T0SZ, tcr->tsz) | ...
	cfg->cd.mair	= pgtbl_cfg->arm_lpae_s1_cfg.mair;
	...
	ret = arm_smmu_write_ctx_desc(smmu_domain, 0, &cfg->cd);  /* :1612,写入 CD 表 */
```

对照 CPU 侧:CD ≈ `TTBR0_EL1 + TCR_EL1 + MAIR_EL1 + ASID` 打包成一条 64B 内存记录;STE ≈ "选哪个进程"的路由器。SMMU 的页表遍历就是拿 CD.TTBR 当根、按 IOVA 逐级走,与 MMU 拿 TTBR 走 VA 完全同构——这也是 [io-pgtable-arm.c](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/io-pgtable-arm.c) 能与 CPU 页表共用格式宏的原因。

## 6. 命令队列 CMDQ:软件 → SMMU 的控制通道

SMMUv3 没有"写寄存器改页表缓存"的操作;**一切失效/预取/应答都经内存中的环形命令队列**(Guide §4.8,#page:32,图 4-8)。SMMU_CMDQ_BASE 给基址,`SMMU_CMDQ_PROD` 软件推进、`SMMU_CMDQ_CONS` SMMU 推进,方向与 EVTQ 相反:

```text
        软件写 CMD → 推进 PROD              SMMU 消费 → 推进 CONS
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │CMD│CMD│CMD│CMD│CMD│CMD│CMD│CMD│   每条命令 16 字节,小端
   └───┴───┴───┴───┴───┴───┴───┴───┘   满条件: 索引相等 且 WRAP 位不同
        ▲cons                ▲prod      空条件: 索引相等 且 WRAP 位相同
                                        (Guide #page:33)
   ◄──── 环形回绕(wrap 位) ────►
```

命令类(Guide §4.8.1 #page:33)与驱动 opcode 对照(arm-smmu-v3.c:459-514):

|类|opcode(驱动宏)|干什么|本目录笔记中的位置|
|-|-|-|-|
|Prefetch|`CMDQ_OP_PREFETCH_CFG` 0x1|预取 STE(5.9 驱动只实现这一种预取命令)|装完 STE 顺手预取(:1937-1939)|
|配置失效|`CMDQ_OP_CFGI_STE` 0x3 / `CMDQ_OP_CFGI_ALL` 0x4 / `CMDQ_OP_CFGI_CD` 0x5|失效缓存的 STE/CD|STE 两段式写、detach(:1792)|
|TLB 失效|`CMDQ_OP_TLBI_NH_ASID` 0x11 / `CMDQ_OP_TLBI_NH_VA` 0x12 / `CMDQ_OP_TLBI_S12_VMALL` 0x28 / `CMDQ_OP_TLBI_S2_IPA` 0x2a|失效 S1/S2 翻译缓存|[001 篇 §2.1 图⑩](001.IOMMU工作流程-真实场景图解.md)(unmap 路径 :2299)|
|ATC 失效|`CMDQ_OP_ATC_INV` 0x40|失效设备侧 ATS 缓存|ATS 场景|
|PRI 应答|`CMDQ_OP_PRI_RESP` 0x41|回应 Page Request|Guide §3.7|
|同步|`CMDQ_OP_CMD_SYNC` 0x46|**等待之前所有命令生效**|`arm_smmu_cmdq_issue_sync` :1508|

`CMD_SYNC` 是理解 CMDQ 的钥匙:CONS 推进只表示"命令被消费",不保证"效果可见"(Guide #page:33 的 `CMD_TLBI_EL3_ALL + CMD_SYNC` 例子)。所以驱动任何"必须立刻生效"的失效都以 SYNC 收尾,`arm_smmu_cmdq_issue_cmdlist`(:1374)一次锁住队列批量写入并按需追加 SYNC。队列满/卡死的全局错误走 **GERROR** 寄存器中断(`arm_smmu_gerror_handler`,:2076)。

## 7. 事件队列 EVTQ:SMMU → 软件的错误通道

结构同 CMDQ 但**生产者是 SMMU**(Guide §4.9,#page:34):翻译失败、配置错误、杂项各占一类,事件记录 32 字节,转入非空即发 MSI 中断。驱动处理线程 [arm_smmu_evtq_thread](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c#L1981) 简单到近乎"纯打印":

```c
/* arm-smmu-v3.c:1981-1996(节选) */
static irqreturn_t arm_smmu_evtq_thread(int irq, void *dev)
{
	...
	while (!queue_remove_raw(q, evt)) {
		u8 id = FIELD_GET(EVTQ_0_ID, evt[0]);       /* :390,ID 在 evt[0][7:0] */
		dev_info(smmu->dev, "event 0x%02x received:\n", id);
		for (i = 0; i < ARRAY_SIZE(evt); ++i)
			dev_info(smmu->dev, "\t0x%016llx\n", ...);
	}
```

Guide §4.9.1(#page:35) 给的事件样例:`CERROR_ILL`(非法命令)、`C_BAD_STREAMID`/`C_BAD_STE`(配置错误)、`F_TRANSLATION`(翻译失败)——前缀 `C_` = 配置错误,`F_` = 翻译过程故障。完整故障判定流见 Guide 图 3-3(#page:16):最终多数以 **terminate with an abort** 收场,事务静默丢弃——[001 篇 §5](001.IOMMU工作流程-真实场景图解.md#5-场景四设备-dma-打进未映射地址故障路径) 以场景方式展开过。队列溢出时,Stall 事务会被扣住、其余被丢弃(overflow 报错 :2005)。

## 8. PRI 队列与全局错误(一页带过)

- **PRIQ**:PCIe Page Request 的接收队列(Guide §3.7 #page:20,图 3-5 #page:21)。设备 ATS 翻译失败时可发 PPR 请求软件"把页弄好",软件处理后用 `CMDQ_OP_PRI_RESP` 回应——它是"把缺页语义引入 DMA"的尝试,5.9 驱动有 `ARM_SMMU_FEAT_PRI`(:639)支持但依赖设备侧 ATS,实用性有限。
- **GERROR**:命令队列卡死、队列内存访问 abort、MSI 写失败等**全局性**错误不进 EVTQ,走 `SMMU_GERROR` 寄存器 + 独立中断(Guide §4.10 #page:35;驱动 :2076)。EVTQ/GERROR 的关系相当于"每笔事务的错误"与"整个 SMMU 的错误"。

## 9. 上电序列:最小配置 ↔ 驱动 probe

Guide §4.11(#page:36-37) 的 7 步最小配置,逐条对到驱动 reset 路径 [arm_smmu_device_reset :3560](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c#L3560)(probe 入口 `arm_smmu_device_probe` :4020):

|#|Guide 最小配置|驱动代码|
|-|-|-|
|1|分配 Stream table、`STRTAB_BASE(_CFG)`、STE.V=0|`arm_smmu_init_strtab`(两级表 L1/L2 按需,bypass STE 全零)|
|2|分配 CMDQ/EVTQ,写 BASE/PROD/CONS|`arm_smmu_init_queues` :3207 → 基址写入 `ARM_SMMU_CMDQ_BASE` :3598、EVTQ :3626|
|3|设内存属性(`CMDQ_CR/…`)|队列描述符内嵌属性字段|
|4|使能 IRQ(IRQ_CTRL)|`arm_smmu_setup_irqs` :3508(EVTQ/PRIQ/GERROR 及 SYNC 的完成通知均走 MSI)|
|5|`CR0.CMDQEN=1` → 轮询 CR0ACK;`EVENTQEN=1` → 轮询|:3602 `enables = CR0_CMDQEN` → `arm_smmu_write_reg_sync`(:3359,写后轮询 ACK 的封装)|
|6|失效 TLB/CFG cache:CMD_TLBI_NSNH_ALL / CMD_CFGI_ALL / CMD_SYNC|reset 内部发全量失效命令|
|7|`CR0.SMMUEN=1` → 轮询|:3633 使能翻译(`CR0_SMMUEN`,:96)|

`arm_smmu_write_reg_sync`(写寄存器→轮询 ACK 寄存器相等)就是硬件手册里"改控制位必须等 CR0ACK"的驱动化表达。probe 完成后,`bus_set_iommu`([iommu.c:1817](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/iommu.c#L1817))把整个平台总线接进 IOMMU 框架,之后才是 [003 篇](003.Linux内核IOMMU软件栈-从dma_map到SMMU页表.md) 的设备接入与 dma_map 流程。

## 10. TLB 维护小结

SMMUv3 的缓存分层(STE/CD 缓存、S1/S2 翻译 TLB,Guide §4.7 #page:31)决定了两类失效:

- **改结构** → CFGI(STE/CD);**改映射** → TLBI(NH_ASID/NH_VA/S2_IPA/VMALL);两者都要 **CMD_SYNC** 收尾。
- [001 篇 §2.1](001.IOMMU工作流程-真实场景图解.md) 场景一的 unmap 是最常走的路:`iommu_unmap_fast` 拆页表 → 严格模式下 `iotlb_sync` → 驱动发 `TLBI_NH_VA`(:2299)+ SYNC。
- 多虚机时 TLB 条目带 VMID、S1 带 ASID,失效命令按 tag 精确打击,不必全清——与 CPU TLBI 的 ASID/VMID 机制同构。
