## 0. 结论速览

|问题|答案|
|---|---|
|驱动作者感知到 IOMMU 吗|**不**。驱动只调 DMA API(`dma_map_*`/`dma_alloc_coherent`),[dma-mapping.h:504](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/include/linux/dma-mapping.h);分派到直接映射还是 IOMMU 由 `dev->dma_ops` 决定(mapping.c:143)|
|`dma_map_single` 返回什么|挂 IOMMU 时是 **IOVA**;没挂时是物理地址(经 `phys_to_dma`)| 
|页表谁建|`iommu.c` 核心层 + 具体驱动 ops(`arm_smmu_map`)→ 页表格式由 `io-pgtable-*` 生成;dma-iommu 层只管 IOVA 分配与调度|
|IOVA 从哪来|`iova.c` 分配器:每 CPU 缓存(rcache)快路径 + 红黑树慢路径,从高地址向下找空洞|
|unmap 一定清 TLB 吗|严格模式(`iommu.strict=1`,默认)同步失效;**懒模式**(`iommu.strict=0`)挂进 flush queue 定时批量失效——吞吐换隔离|
|`iommu=pt` 是 ARM64 的吗|**不是**,5.9 里它标注 `[X86]`(kparams:1925);ARM64 等价物是 `iommu.passthrough=1`(kparams:1952,iommu.c:322)|

## 1. 软件栈分层总图

```text
 ┌──────────────────────────────────────────────────────────────────────────┐
 │ 驱动层     dma_map_single / dma_map_page / dma_alloc_coherent           │  只见 DMA API
 │            (include/linux/dma-mapping.h:504/607)                         │
 ├──────────────────────────────────────────────────────────────────────────┤
 │ DMA 映射层  get_dma_ops → dev->dma_ops 决定路线 (mapping.c:143)          │
 │    ├── 直接映射:  dma_direct_map_page  (kernel/dma/direct.h)            │ ← 无 IOMMU
 │    └── IOMMU 路线: iommu_dma_ops 表 (dma-iommu.c:1120)                  │ ← 有 IOMMU
 │         iommu_dma_map_page/map_sg/alloc,IOVA 分配,cache 同步            │
 ├──────────────────────────────────────────────────────────────────────────┤
 │ IOMMU 核心层  iommu.c:  iommu_map :2242 / __iommu_map :2182             │  与硬件无关
 │    domain/group 生命周期、attach、页大小拆分、resv region                  │
 ├──────────────────────────────────────────────────────────────────────────┤
 │ IOMMU 驱动层  arm-smmu-v3.c:  arm_smmu_map :2844 → 发 CMDQ 命令          │  一硬件一驱动
 │    (对照: intel/iommu.c、amd/iommu.c、virtio-iommu.c、tegra-smmu.c …)   │
 ├──────────────────────────────────────────────────────────────────────────┤
 │ 页表格式库  io-pgtable.c → io-pgtable-arm.c:  arm_lpae_map :460          │  S1 页表格式
 │    (io-pgtable-arm-v7s.c = 32 位 ARM SMMU;与 CPU 页表同格式)             │
 └──────────────────────────────────────────────────────────────────────────┘
```

对照记忆:上层(DMA API)是**设备视角**,中层(iommu.c)是**抽象域视角**,下层(arm-smmu-v3/io-pgtable)是**硬件视角**。[006.DMA 篇](../../052.INPUT_OUTPUT/006.DMA/README.md) 关注第一层,本篇关注第二、三层,002 篇关注第四层硬件。

## 2. 设备怎么挂上 IOMMU(probe 路径)

```text
 设备 probe(dts 里有 iommu 属性 / PCI 别名)
    │
    ├─ of_iommu.c: of_iommu_xlate → 驱动 of_xlate
    │    (arm-smmu-v3.c:3094,把 iommu 节点引用解析成 StreamID 存进 fwspec)
    ▼
 iommu.c:245  iommu_probe_device
    │  __iommu_probe_device :193 → 设备所属 IOMMU 实例 → iommu_group(最小隔离单元,
    │  PCI 别名/多路复用器后的设备共享一组)iommu_group_alloc :564
    ▼
 iommu.c:265  iommu_alloc_default_domain
    │  iommu.c:1502 → 依 iommu_def_domain_type:
    │    · IOMMU_DOMAIN_DMA     → 转译域(dma-iommu 层托管 IOVA)   ← 默认
    │    · IOMMU_DOMAIN_IDENTITY→ 恒等域(直通,见 §7 参数)
    ▼
 arm_smmu_attach_dev  arm-smmu-v3.c:2784
    │  arm_smmu_write_strtab_ent :1803 装 STE → 设备从此进入翻译世界
    ▼
 dma-iommu.c:302  iommu_dma_init_domain(转译域时)
    · 设定 IOVA 窗口(几何孔径)与粒度
    · fq(懒模式)惰性初始化::344-347 init_iova_flush_queue
```

要点:**域(domain)是页表 + 属性的容器,组(group)是不可拆分的设备集合**。同组设备共享一份映射——这就是为什么 VFIO 打不开"半个根端口后面的一组设备"。ARM64 上 `dev->dma_ops` 的挂接在 `arch_setup_dma_ops`([arch/arm64/mm/dma-mapping.c:40](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/arch/arm64/mm/dma-mapping.c#L40))→ `iommu_setup_dma_ops`,转译域时 `dev->dma_ops = &iommu_dma_ops`(dma-iommu.c:1156)。

## 3. 一次 dma_map 的完整软件流程

以流式映射 `dma_map_page` 为例(= 驱动 `dma_map_single` 的底层,场景见 [001 篇 §2](001.IOMMU工作流程-真实场景图解.md#2-场景一网卡收包流式-dma)):

```text
 dma_map_page(d, p, o, s, r)                    dma-mapping.h:607(宏)
   └─ dma_map_page_attrs                        mapping.c:139
        ├─ get_dma_ops(dev)                     dma-mapping.h:195
        ├─ dma_map_direct(dev, ops) ?           mapping.c:133
        │     ├─ 是 → dma_direct_map_page       (直接映射路线,006.DMA 篇)
        │     └─ 否 → ops->map_page             = iommu_dma_map_page(dma-iommu.c:1120 表)
        ▼
 iommu_dma_map_page                             dma-iommu.c:725
   phys = page_to_phys(page) + offset     ← ①OS 做 VA→PA(驱动给的 page)
   prot = dma_info_to_prot(dir, coherent) ← ②方向变权限(IOMMU_READ/WRITE)
   └─ __iommu_dma_map                           dma-iommu.c:478
        ├─ iommu_dma_deferred_attach            :356(懒 attach,首次 map 才挂)
        ├─ size = iova_align(…)                 ← ③对齐 IOVA 粒度
        ├─ iommu_dma_alloc_iova                 dma-iommu.c:400
        │    └─ alloc_iova_fast                 iova.c:412(§4)
        └─ iommu_map_atomic(domain, iova, phys, size, prot)
             └─ __iommu_map                     iommu.c:2182
                  ├─ 对齐检查: iova|paddr|size 须 ≥ 最小页粒度
                  ├─ while (size) 按 pgsize 逐段 ops->map  ← ④大页尽量合并
                  └─ ops->map = arm_smmu_map            arm-smmu-v3.c:2844
                       └─ ops->map = arm_lpae_map       io-pgtable-arm.c:460
                            └─ __arm_lpae_map           io-pgtable-arm.c:356
                                 └─ 自顶向下走 levels:
                                    无下级表 → __arm_lpae_alloc_pages
                                    arm_lpae_install_table :325 挂链
                                    叶级 → arm_lpae_init_pte 写 PTE  ← ⑤真正建映射
   arch_sync_dma_for_device(phys, size, dir)     dma-iommu.c:737
   ← ⑥非 I/O coherent 平台:CPU cache 维护(coherent 设备免)
        ▼
 返回给驱动 = iova + iova_off  (IOVA!写进设备描述符的就是它)
```

几个值得停下来想的地方:

1. **①和⑤是两次完全不同的"翻译"**:①是 CPU 侧软件翻译(page → PA),⑤是把映射**预写**进 SMMU 页表(此后每笔 DMA 由硬件翻译)。IOMMU 方案的本质是"软件预先协商,硬件逐笔执行"。
2. **④大页合并**:网络场景常见 4KB 缓冲连续分配,`__iommu_map` 按 `domain->pgsize_bitmap` 挑最大可行页;`__arm_lpae_map` 里 `size == block_size` 即装叶项(io-pgtable-arm.c:369-370),能省一级表与一次 walk。DPDK 用大页除了减少 TLB miss,也直接减少这里建的表项数。
3. **⑥cache 同步与 IOMMU 无关但总在附近出现**:非 coherent 设备(如部分 SoC 的 USB/DMA 引擎)每次 map/unmap 都要做 `arch_sync_dma_for_device/for_cpu`;SMMU 本身是否 coherent walk 由 `IDR0.COHACC`(arm-smmu-v3.c:55)探测、记为 `ARM_SMMU_FEAT_COHERENCY`(:643),并落到 `io_pgtable_cfg.coherent_walk`(arm-smmu-v3.c:2597);遍历属性据此在 [io-pgtable-arm.c:802-807](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/io-pgtable-arm.c)(S1)/:913-918(S2)配成 WBWA 或 NC,再经 CD.TCR 的 IRGN0/ORGN0(arm-smmu-v3.c:2498-2499)告知 SMMU 硬件——只影响**页表遍历**的走线,不影响设备数据的 coherency。
4. **一致性分配**(`dma_alloc_coherent`)走另一条:`iommu_dma_alloc`(dma-iommu.c:1022;页表属性可满足时转 `iommu_dma_alloc_remap` :582),IOVA 与内存一起分配、映射常驻——设备与 CPU 永久共享,生命周期到 `dma_free_coherent`。与流式映射的"用时映射"对比,即 DMA 经典二分法([006.DMA 篇](../../052.INPUT_OUTPUT/006.DMA/README.md))。

## 4. IOVA 分配器(iova.c):从高地址向下的"空洞查找"

IOVA 空间是块连续虚地址,分配器要在里面找空洞。数据结构两级:**每 CPU 缓存(rcache)+ 红黑树**。

```c
/* iova.c:412-438(节选)—— 快慢两路 */
unsigned long
alloc_iova_fast(struct iova_domain *iovad, unsigned long size,
		unsigned long limit_pfn, bool flush_rcache)
{
	iova_pfn = iova_rcache_get(iovad, size, limit_pfn + 1);   /* 快路:CPU 缓存 */
	if (iova_pfn)
		return iova_pfn;
retry:
	new_iova = alloc_iova(iovad, size, limit_pfn, true);      /* 慢路:红黑树 */
	if (!new_iova) {
		...
		for_each_online_cpu(cpu)
			free_cpu_cached_iovas(cpu, iovad);    /* 缓存耗尽→清缓存重试 */
		goto retry;
	}
	return new_iova->pfn_lo;
}
```

慢路径 [__alloc_and_insert_iova_range](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/iova.c#L180)(iova.c:180)从 `limit_pfn` **向下**walk 红黑树找第一个能容纳的空洞(:201-207)——从高地址向下分配是刻意的:留给 32 位设备整段低位空间(场景五,[001 篇 §6](001.IOMMU工作流程-真实场景图解.md#6-场景五32-位设备访问-4gb-以上内存))。快路径缓存按 2 的幂分级,`IOVA_RANGE_CACHE_MAX_SIZE = 6`([iova.h:28](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/include/linux/iova.h#L28)),即 1~32 页的块走缓存,更大的直接走树;`iommu_dma_alloc_iova` 里非 2 幂大小先 `roundup_pow_of_two`(dma-iommu.c:420-421)——**牺牲一点 IOVA 空间换缓存命中**,注释原话"会回来狠狠咬我们"。

释放侧与 TLB 策略绑定,分两派(dma-iommu.c:440-455 `iommu_dma_free_iova`):

```text
 严格模式(默认)                      懒模式(flush queue, fq)
─────────────────────────          ─────────────────────────────────
free_iova_fast (iova.c:450)        queue_iova   (iova.c:549)
  IOVA 立即回树/缓存                  IOVA + 失效任务挂 fq 定时器
iommu_tlb_sync → 硬件 TLBI            超时批量: iommu_dma_flush_iotlb_all
  (arm-smmu-v3.c:2299 TLBI_NH_VA)      (dma-iommu.c:276) 一次性批量失效
  ★ 每次都发 CMD_SYNC,贵             ★ unmap 便宜,但释放的页短时间
                                       仍可被设备旧 TLB 命中 → 隔离弱化
```

fq 的初始化点在 `iommu_dma_init_domain` 内(dma-iommu.c:344-347)。网络大流量场景下懒模式收益明显(unmap 在软中断里,省掉同步 TLBI 的等待),代价见 §7。

## 5. unmap 路径

```c
/* dma-iommu.c:741-749 —— 与 map 严格对称 */
static void iommu_dma_unmap_page(struct device *dev, dma_addr_t dma_handle,
		size_t size, enum dma_data_direction dir, unsigned long attrs)
{
	if (!(attrs & DMA_ATTR_SKIP_CPU_SYNC))
		iommu_dma_sync_single_for_cpu(dev, dma_handle, size, dir);  /* cache 归 CPU */
	__iommu_dma_unmap(dev, dma_handle, size);                           /* 拆映射 */
}
```

`__iommu_dma_unmap`(dma-iommu.c:456-477):对齐 → `iommu_unmap_fast` 拆页表(arm 侧 `arm_smmu_unmap` 收集 iotlb_gather)→ 非 fq 时 `iommu_tlb_sync` 立即发 TLBI → `iommu_dma_free_iova` 回收。**注意对称性里藏着的开销**:map 是"写页表(不动硬件)",unmap 在严格模式是"拆页表 + 打硬件 TLB + SYNC 等待"——这就是为什么高频短命映射(网络、块层)对 `iommu.strict` 参数敏感,也是 DPDK 干脆绕开整个问题的动因([001 篇 §4](001.IOMMU工作流程-真实场景图解.md#4-场景三用户态驱动dpdk))。

## 6. map_sg:网卡真实世界几乎都走这条路

收包路径一次映射一串缓冲(skb frags),`iommu_dma_map_sg`(dma-iommu.c:831)的技巧是**先在 scatterlist 上把各段对齐到 IOVA 粒度、累出一个总长度,再一次性领一块连续 IOVA、逐段填页表**:

```c
/* dma-iommu.c:889-900(节选) */
	iova = iommu_dma_alloc_iova(domain, iova_len, dma_get_mask(dev), dev);
	...
	if (iommu_map_sg_atomic(domain, iova, sg, nents, prot) < iova_len)
		goto out_free_iova;
	return __finalise_sg(dev, sg, nents, iova);   /* 把 IOVA 切片写回 sg_dma_address */
```

效果:物理上离散的 N 段缓冲,在设备眼里是**一段连续 IOVA**——设备侧描述符简单(有的硬件甚至只收"一个地址+总长"),代价是 IOVA 空间碎片化风险与每段的粒度对齐浪费。这与 CPU 侧"vmalloc 连续而物理不连续"是同一种思想:连续性是给"消费者"的视图,生产者(页表)负责兑现。

## 7. 内核参数与性能权衡

5.9 与 IOMMU 域策略直接相关的三组参数(kparams:1925-1958):

|参数|架构|语义|代码落点|
|---|---|---|---|
|`iommu=pt` / `nopt`|**X86**|默认域 = 恒等(直通),仍保留 IOMMU(中断重映射、resv)|kparams:1925-1939;ARM64 上写它无效果|
|`iommu.passthrough=`|ARM64, X86|`1` = 默认域用恒等(设备直通);`0` = 转译|kparams:1952-1958 → early_param [iommu.c:322](../../../000.SOURCE_CODE/000.LINUX-5.9/000.LINUX-5.9/drivers/iommu/iommu.c#L322) → `iommu_set_default_passthrough` :2568|
|`iommu.strict=`|ARM64|`1`(默认)= unmap 同步 TLBI;`0` = 懒模式 fq|kparams:1940-1951;fq 机制见 §4|
|`CONFIG_IOMMU_DEFAULT_PASSTHROUGH`|编译期|默认直通(iommu.c:134 读它)|`iommu.passthrough` 显式参数优先|
|`smmu40x…/arm-smmu-v3.disable_bypass`|模块参数|无映射设备是 abort(默认)还是 bypass|arm-smmu-v3.c:416-418,`BUG_ON(!disable_bypass)` :1863|

### 权衡表:什么时候关掉翻译

|配置|隔离|性能|适用|
|---|---|---|---|
|默认(转译 + strict)|★★★|unmap 有同步 TLBI 开销|通用、安全敏感|
|转译 + `iommu.strict=0`|★★(旧 TLB 残留窗口)|unmap 便宜,适合网络/存储大吞吐|吞吐敏感,且能接受弱化隔离|
|`iommu.passthrough=1`(恒等域)|★(仅剩中断重映射与保留区)|翻译旁路,无 map/unmap 软件开销|可信环境下追性能;或设备/IOMMU 兼容性差|
|无 IOMMU(硬件没有)|✗(设备可 DMA 全内存)|最直接|嵌入式裸设备;安全靠 swiotlb 兜底寻址能力|

三点补充:

1. **恒等域不是"关掉 IOMMU"**:设备仍挂组、仍受 resv region 与中断重映射约束;只是 IOVA≡PA,`iommu_dma_map_page` 这套软件开销消失。x86 的 `iommu=pt` 与 ARM64 的 `iommu.passthrough=1` 在"恒等域"这一步是同一个 `iommu_def_domain_type` 变量,只是命名与生效路径不同。
2. **strict 的"贵"具体在哪**:每次 unmap 都要往 CMDQ 塞 `TLBI_NH_VA` + `CMD_SYNC` 并等 CONS 推进(002 篇 §6);在软中断收包上下文里这是一段串行等待。懒模式把 N 次 TLBI 合成 1 次,把同步等待变成定时器异步。
3. **沙盒化 vs 直通的中间路线**:VFIO/DPDK 场景下,宿主用默认策略、仅对 VFIO 域开转译;`iommu.passthrough` 只影响**默认域**,按设备 per-domain 选择由驱动/VFIO 决定——"默认直通 + 关键设备转译"是常见的服务器折中。
