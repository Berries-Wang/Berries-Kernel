# arm64 系统下,为什么 CPU 的数据访问优先级通常低于 DMA?

## 0. 结论速览

"CPU 的数据访问优先级低于 DMA"不是某颗芯片的怪癖,而是**内存系统设计的一致取向**——从 Cortex-M3 的总线矩阵,到 arm64 SoC 的 AXI/CHI 互连 QoS,到 x86 服务器,都是同一判断:**DMA 等不起,CPU 等得起**。四条根因:

| # | 根因 | 一句话 |
|---|---|---|
| 1 | **DMA 有死线,溢出不可逆** | 外设 FIFO 满了数据就永久丢失——不是"慢",是"错" |
| 2 | **CPU 等得起** | 乱序流水线、Load/Store 队列、写缓冲、预取把几十周期的总线延迟吸收掉,程序只是慢一点 |
| 3 | **CPU 有替代通路,且可被"推迟"** | 取指走 I-Cache 预取、访存可乱序重排、写可进 Write Buffer;DMA 流水线上每个字都是串行依赖 |
| 4 | **固定优先级仲裁最简单且"刚好够用"** | 只要"延迟敏感者"排前面,无需抢占/轮转逻辑;arm64 上进一步演进为可编程 QoS(QPV/调节器) |

在 arm64(本仓库分析基座 AGI CPU = Neoverse V3 + CMN-700)上,"优先级"不再是总线矩阵里的静态线序,而是 **CHI/AXI 报文上的 QoS 字段 + 互连节点的仲裁策略 + QoS 调节器**——但四条根因原封不动,只是实现搬进了报文字段(§3)。

## 1. 教材原点:总线上的"周期窃取"与突发模式

MOS5 §5.1.4 在讲 DMA 时,已经把"谁让谁"写明白了——DMA 用**周期窃取**从 CPU 手里拿总线:

> In cycle stealing, ... the DMA controller requests the transfer of one word and gets it. If the CPU also wants the bus, it has to wait. The mechanism is called cycle stealing because the device controller sneaks in and steals an occasional bus cycle from the CPU once in a while, delaying it slightly.（在周期窃取方式下,DMA 控制器请求传送一个字并得到总线。如果 CPU 也要用总线,它就必须等待。这种机制之所以叫周期窃取,是因为设备控制器时不时"溜进来",从 CPU 手里偷走偶发的总线周期,让它稍微慢一点。）<sup>[Modern Operating Systems 5th, 书页 346(PDF 375)](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=375)</sup>

> The downside to burst mode is that it can block the CPU and other devices for a substantial period if a long burst is being transferred.（突发模式的缺点是:如果一个长突发正在传送,它可能把 CPU 和其他设备阻塞相当长一段时间。）<sup>[Modern Operating Systems 5th, 书页 346(PDF 375)](../../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=375)</sup>

教材语气已经预设:**"被偷"的一方是 CPU**——设备控制器对总线的请求天然排在 CPU 前,而"延迟它 slightly"被视为可接受的代价。为什么这个代价可接受?§2 的三条理由。

## 2. 三条硬理由

### 2.1 DMA 的死线:FIFO 溢出不可逆

DMA 不是自己想走——是外设的数据流"推着走":UART/SPI/音频 I2S/网卡收到的每个字节先进外设小 FIFO(几个字节到几 KB),必须**在下一次字节到达前**被搬进内存。搬晚了:

```text
 外设数据流(如 I2S 48kHz×2ch×16bit ≈ 每 20.8µs 一个样本),FIFO 深度 4:
   t0: 字节n   → [n]                (FIFO 1/4,DMA 请求已拉起)
   t1: 字节n+1 → [n][n+1]
   t2: 字节n+2 → [n][n+1][n+2]
   t3: 字节n+3 → [n][n+1][n+2][n+3]  (FIFO 满)
   t4: 字节n+4 到达,若 DMA 还没搬走任何一个 ─✗ 溢出
        ▲ DMA 每次搬运都要过总线仲裁:若被 CPU 密集访存连续压住,
          从"请求授权"到"落地内存"的延迟就是死线本身
   溢出 = 数据永久丢失:没有重传、没有恢复,音频炸音/网络丢包/传感器丢样
```

- CPU 的访存被延迟 N 周期 → 程序变慢 N 周期,数据一个不丢;
- DMA 的访存被延迟 N 周期 → 超过 FIFO 缓冲时限 → **数据物理性丢失**;
- **错误的代价不对称**:一个可挽回(慢),一个不可挽回(丢)。设计者必须把"不可逆"的一方排在前面。

### 2.2 CPU 为什么等得起:微架构里的"减震层"

Cortex-A 系核(如本仓库基座 Neoverse V3)的访存通路里塞满了吸收延迟的结构:

```text
 核内访存通路(简化,自上而下看"谁在等谁"):

   取指:  取指单元 ──► I-Cache(+预取器) ──miss──────────────┐
                                                            │
   访存:  Load/Store Unit ──Load──────────► L1 Data Cache ──┤(miss)
                 │                                          │
                 └─Store──► Store Buffer(进缓冲即"完成",     │
                            后续异步落 cache,不阻塞流水线)   │
                                                            ▼
                Load 未命中时:乱序机器挂起该 Load(MSHR 并发),
                核继续执行后续无关指令 ──► L2(私有) ─► DSU-120 L3 ─► CMN-700 mesh ─► 内存
                                          (L2/L3 各挂预取器提前填充)

   ▶ 几十个周期的总线延迟被四层机制摊平:在途请求并发(MSHR)+ 乱序 + 写缓冲 + 预取
   ▶ 一条 Load 停住,程序只是慢一点;Store 从不等总线——这就是"CPU 等得起"的微架构基础
```

- **写不必等**:Store 命中 Store Buffer 即可继续执行——CPU 的"写"本来就是异步落总线的;
- **读可以乱序等**:一个 Load miss 挂起,核继续执行后面的指令,直到数据真要被用;
- **取指有独立通路与预取**:I-Cache 未命中才上互连,且预取器提前填;
- 结论:CPU 是**延迟敏感**型(慢了性能掉),DMA 音视频流是**有界延迟**(bounded latency)型(慢了直接错)——两者对延迟的"容错语义"不同。

### 2.3 固定优先级"刚好够用"→ arm64 的可编程 QoS

在总线矩阵时代,这个判断被固化成静态优先级:延迟最敏感者(DMA)最高、CPU 次之、调试口最低——无需状态机、无需抢占。arm64 SoC 把同样的排序搬进了**报文字段**:AXI 的 `AxQOS[3:0]`、CHI 的 `QoS` 字段随每个请求流动,由互连在**每个仲裁点**裁决。

## 3. arm64 落地:CMN-700 的 QoS 设备分类(互连视角)

CMN-700 TRM §3.11 开宗明义按"延迟语义"给设备分类——**注意处理器只是"延迟敏感"类,而实时外设是"有界延迟"类**:

> The QoS device classes are: **Devices with bounded latency requirements** — These devices are primarily real-time or isochronous that require some or all of their transactions complete within a specific time period to meet overall system requirements. ... Examples of this class of device include networking I/O devices and display devices. **Latency-sensitive devices** — The performance of these devices is highly impacted by the response latency that is incurred by their transactions. Processors are traditionally highly latency-sensitive devices...（QoS 设备类别有:**有界延迟需求设备**——主要是实时或等时设备,要求其部分或全部事务在特定时限内完成以满足系统整体需求……这类设备的例子包括网络 I/O 设备和显示设备。**延迟敏感设备**——这类设备的性能深受其事务响应延迟的影响。处理器传统上是典型的延迟敏感设备……）<sup>[CMN-700 TRM §3.11, PDF 物理页 249](../../../007.BOOKs/arm_neoverse_cmn_700_trm_102308_0307_08_en.pdf#page=249)</sup>

```text
 CMN-700 QoS 设备分类(TRM §3.11)与仲裁含义:
   有界延迟(bounded latency)    网络I/O、显示  —— 慢了就错     ⇒ QoS 优先级必须高
   延迟敏感(latency-sensitive)  处理器         —— 慢了性能降   ⇒ 中等,可自我调制
   带宽敏感(bandwidth-sensitive) 视频编解码     —— 要保底带宽   ⇒ 长期带宽约束
   带宽饥饿(bandwidth-hungry)   GPU/大计算     —— 有多少用多少 ⇒ 最低,QoS 压低
```

优先级的载体与仲裁机制(TRM §3.11.1,PDF p249):

> The AMBA 5 CHI protocol includes a 4-bit QoS Priority Value (QPV) with all message flits. The QPV of the originating message must propagate for all messages in a transaction. The QPV is defined as higher values being higher priority and lower values being lower priority.（AMBA 5 CHI 协议在所有消息 flit 中携带 4 位 QoS 优先级值(QPV)。源发消息的 QPV 必须在该事务的所有后续消息中传递。QPV 值越高优先级越高,越低优先级越低。）<sup>[CMN-700 TRM §3.11.1, PDF 物理页 249](../../../007.BOOKs/arm_neoverse_cmn_700_trm_102308_0307_08_en.pdf#page=249)</sup>

> The QoS provision uses the QoS field in each RN request packet to influence arbitration priority at every QoS decision point.（QoS 机制利用每个 RN 请求包中的 QoS 字段,在每一个 QoS 决策点影响仲裁优先级。）<sup>[CMN-700 TRM §3.1.1.12, PDF 物理页 48](../../../007.BOOKs/arm_neoverse_cmn_700_trm_102308_0307_08_en.pdf#page=48)</sup>

两类典型端点:

- **DMA 类主设备(网卡/显示/视频编解码,多为 RN-I/RN-D)**:请求自带 QoS 字段,或挂一个 **QoS Regulator(QR)** 由互连代为调节——"A QoS Regulator (QR) provides an interstitial layer between an RN and the interconnect. The QR monitors how the bandwidth and latency requirements of the RN are met, and does in-line replacement of the RN-provided QoS field. The QR adjusts the QoS field upwards for higher priority in the system and downwards for lower priority."(§3.1.1.12,PDF p48;调节器两模式:latency regulation——"For every cycle that the latency of a transaction is more than the target latency, the QPV increases by a fractional amount." §3.11.2.2,PDF p251)
- **CPU(RN-F)**:同样受 QPV 约束。更直接的证据是 Cortex-A725 的**Cluster Bus QoS 寄存器**——CPU 侧的总线优先级是一个**可编程的 EL1 系统寄存器**,即"CPU 访存的 QoS 等级"本来就是被系统软件按需压低/抬高的对象:

> `IMP_CLUSTERBUSQOS_EL1` — 64-bit Cluster Bus QoS Control Register(64 位簇总线 QoS 控制寄存器)<sup>[Cortex-A725 Core TRM, PDF 物理页 167(寄存器总表);EL1 写入可被 `QOSEN` 陷阱位拦到 EL2/EL3,PDF 物理页 236](../../../007.BOOKs/arm_cortex_a725_core_trm_107652_0001_04_en.pdf#page=167)</sup>

还有一个容易误读的细节:CMN-700 的 **XP(Crosspoint)仲裁不用 QoS 值**——"Crosspoints (XPs) do not use the QoS value in its arbitration mechanism. Instead, XPs use Least Recently Granted policy."(§3.11.2 旁注,PDF p250)。即 mesh 内部靠"最近最少获准"公平轮转,而 QoS 在**端点准入/调节器/RN 侧**生效——"优先级"在 arm64 上是分层合成物:**设备侧 QPV 分类 + 调节器动态调制 + 互连 LRG 公平轮转**,而不是单点优先级比较器。

## 4. 内核证据:CPU 侧为 DMA 让路的四段代码

### 4.1 软件一致性:CPU 亲手为 DMA 清理缓存(非一致平台)

非一致 DMA 平台(arm64 SoC 常见)上,数据给设备前 CPU 必须 **clean 自己的 cache**,设备写完后 CPU 必须 **invalidate**——每一次 DMA 前后,都是"CPU 停下来伺候 DMA"的固定戏码:

```c
/* arch/arm64/mm/dma-mapping.c:15-30 —— 非 coherent 设备的 cache 维护 */
void arch_sync_dma_for_device(phys_addr_t paddr, size_t size,
			      enum dma_data_direction dir)
{
	unsigned long start = (unsigned long)phys_to_virt(paddr);

	dcache_clean_poc_nosync(start, start + size);   // 写方向:CPU clean,所有权交给设备
}

void arch_sync_dma_for_cpu(phys_addr_t paddr, size_t size,
			   enum dma_data_direction dir)
{
	unsigned long start = (unsigned long)phys_to_virt(paddr);

	if (dir == DMA_TO_DEVICE)
		return;

	dcache_inval_poc_nosync(start, start + size);   // 读方向:CPU invalidate,所有权收回
}
```

直连映射的两条路径都会走到它 <sub>[/kernel/dma/direct.h:64,124](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/dma/direct.h)</sub>;内核文档把这定义为 streaming DMA 的标准动作:

> `dma_sync_single_for_device(struct device *dev, dma_addr_t dma_handle, ...)` —— [Documentation/core-api/dma-api.rst:375-380](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/Documentation/core-api/dma-api.rst):"Before giving the memory to the device, dma_sync_single_for_device() needs [to be called]..."(:582)

(一致性互连平台上这层维护由硬件 snoop 完成——但"设备无碍直取内存、CPU 配合让路"的格局不变,见 [019.IOMMU](../019.IOMMU)。)

### 4.2 DMA 控制器驱动:通道优先级是显式可编程字段

```c
/* drivers/dma/tegra186-gpc-dma.c:893-895 */
	/* Configure default priority weight for the channel */
	csr |= FIELD_PREP(TEGRA_GPCDMA_CSR_WEIGHT, 1);
```

DMA 引擎的每个通道带硬件优先级/权重字段——同一颗 SoC 里,音频通道高权重、大块 memcpy 通道低权重,仲裁器照此排座。这说明"DMA 之间的相对优先级"尚需细分,而 **DMA 整体高于 CPU 访存**这一档通常在互连/总线矩阵的静态设计里就定了。

### 4.3 互连带宽 QoS 框架:drivers/interconnect

内核有专门的框架向互连声明带宽需求(设备 → 互连节点的 avg/peak 带宽约束,最终落到 SoC 互连的 QoS 寄存器):

```c
/* drivers/interconnect/core.c:680-694(icc_set_bw 注释为源码原文) */
 * icc_set_bw() - set bandwidth constraints on an interconnect path
 * @path: interconnect path
 * @avg_bw: average bandwidth in kilobytes per second
 * @peak_bw: peak bandwidth in kilobytes per second
 *
 * This function is used by an interconnect consumer to express its own needs
 * in terms of bandwidth for a previously requested path between two endpoints.
int icc_set_bw(struct icc_path *path, u32 avg_bw, u32 peak_bw)
```

显示/视频这类"死线型"消费者由此在互连上锁定带宽与时延,余量才轮到 CPU——内核软件栈与 §3 的硬件 QoS 分类一一对应。

### 4.4 反向印证:CPU 等 DMA 是常态

- `dma_sync_single_for_cpu()` 的语义就是"CPU 等 DMA 写完、放弃缓存所有权再读" <sub>[/Documentation/core-api/dma-api.rst:375](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/Documentation/core-api/dma-api.rst)</sub>;
- 网络/存储的完成路径全靠"DMA 完成中断唤醒 CPU"(收包 NAPI、块层 `bio_endio`,见 [051.AI-ASSISANT/001.CPU与DMA双向交互](../../051.AI-ASSISANT/001.CPU%E4%B8%8EDMA%E5%8F%8C%E5%90%91%E4%BA%A4%E4%BA%92%28%E7%BD%91%E7%BB%9C%E6%94%B6%E5%8C%85%E4%BA%8B%E4%BB%B6%E5%85%A8%E6%B5%81%E7%A8%8B%29.md));
- swiotlb 弹跳缓冲里"设备读写完 CPU 再拷贝"的两段式 <sub>[/kernel/dma/direct.h:110-112](../../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/dma/direct.h)</sub>(详见 [001.DMA传送流程](./001.DMA传送流程%28重绘图5-4%29与IOMMU地址翻译.md))——每次都是 CPU 多跑腿。

## 5. 三平台对照(按仓库 CPU 平台规范)

| 平台 | "CPU 低于 DMA"的体现 | 机制 |
|-|-|-|
| **Arm AGI CPU(Neoverse V3,本仓库基座)** | CPU 请求带 QPV 参与仲裁;实时外设经 QoS Regulator 被抬到更高优先级;XP 内部 LRG 公平轮转兜底 | CMN-700 QPV/QR(TRM §3.11) |
| **Cortex-A725 + A520(异构 SoC,附录)** | 簇级 `IMP_CLUSTERBUSQOS_EL1` 直接可编程压低/抬高 CPU 簇的 AXI QoS;DSP/ISP/显示控制器等 DMA 主设备在设备树/固件中静态配 QoS | A725 TRM 寄存器(PDF p167);DSU-120 簇级出口 |
| **AMD EPYC 9996(x86_64 对照)** | 同样成立:IOMMU(DMA 重映射)+ PCIe 的 VC/仲裁让出带宽;内存控制器对" IO 访存"与"核访存"分级调度;数据面网卡(DPDK 场景)带宽优先保障 | x86 QoS/MBA 与 PCIe 流控,机制不同、排序相同——**"谁等不起谁优先"跨 ISA 成立** |

**异构附录的量化直觉**(教学场景,数字见 [A725/A520 TRM](../../../007.BOOKs/arm_cortex_a725_core_trm_107652_0001_04_en.pdf)):A520(顺序核,访存一旦 miss 无别的事可做)对总线延迟其实**更敏感**,但其负载多为控制流;A725(乱序)靠 128KB~1MB 私有 L2 与窗口更大的访存并发把延迟藏起来——所以"压低 CPU QoS 换 DMA 通畅"在异构 SoC 上通常从小核簇/媒体路径开始做,大核簇保留较高 QoS 保交互延迟。

## 6. 回答与边界

1. **为什么"通常"低于?** 因为四条根因(死线不可逆/CPU 可吸收/有替代通路/固定优先级够用)在绝大多数工作负载下都成立;"通常"二字留出的例外是**交互延迟敏感的 CPU 路径**——所以现代方案不再是一刀切,而是 QPV+调节器按设备语义动态调制(§3)。
2. **代价是什么?** CPU 密集访存时有效带宽被 DMA 分走(极端情况近半);Store 进 buffer 后的落总线延迟不确定——用可测量的"慢"换不可逆的"不丢"。
3. **软件要做什么?** 4.1–4.3 的三件事:cache 维护让权、通道优先级编程、interconnect 带宽申请——内核把"谁优先"翻译成配置,而不是抢总线。
