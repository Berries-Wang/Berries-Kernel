# 从 C 到 Image：内核构建流水线

> **定位**：把 `make Image.gz` 拆开成一条可观测的流水线——每一步"用什么工具、吃进什么、吐出什么、由哪条规则驱动"，全部锚定 [003.LINUX-7.1.3](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3) 的真实构建文件（`file:line` 实测）。链接脚本深潜见 [002](./002.链接脚本走读：vmlinux.lds.S.md)，编译器扩展见 [003](./003.编译器扩展与内核：compiler.h深读.md)，理论坐标见 [README](./README.md)。
>
> 姊妹篇：[008.COMPUTER_SCIENCE 宏观系列](../../008.COMPUTER_SCIENCE/000.编译-汇编-链接/README.md)（流程/目标文件格式速览）。

## 0. 一句话总结

**教材里"编译器的阶段"（词法→语法→语义→中间代码→优化→代码生成，教材 p22-28）在内核里全部折叠进 `cmd_cc_o_c` 一条命令；构建系统真正显式展开的是"之后"的部分——汇编、部分链接（`ld -r`）、大链接（`vmlinux.lds.S`）、两遍 kallsyms 自举、压缩。** 所以看内核构建学的是**汇编之后、运行之前**的那半条编译流水线——恰好是教科书代码生成章（p365）的工程放大版。

## 1. 全景：一条产物的依赖链

```
 foo.c ──(cc1: 预处理+词法+语法+语义+优化+代码生成)── foo.s        教材 p22-28 的全部阶段
   │                                                        （构建系统只当它是"一条 CC 命令"）
   ▼
 foo.s ──(as: GNU 汇编器)── foo.o          ELF 目标文件（可重定位：留着重定位记录）
   │
   ├─ foo/ 子目录同样产出 → 归并
   ▼
 (若干 .o) ──(ld -r 部分链接)── foo/built-in.a      大目录的"打包层"
   │
   ▼ 逐级向上，最终：
 vmlinux.a + libs ──(ld -T vmlinux.lds.S + --gc-sections)── .tmp_vmlinux0
   │                    ↑ 没有符号表（kallsyms 还没生成）
   ▼ scripts/kallsyms 读出全部符号 → 生成一张汇编表 .tmp_vmlinux0.kallsyms.S → as → .o
 .tmp_vmlinux0 + kallsyms.o ──(再链接)── .tmp_vmlinux1        第一遍 kallsyms
   │  （地址又变了？再来一遍：kallsyms 是"链接后才存在、存在后又影响布局"的自举表）
   ▼
 vmlinux ──(objcopy / nm)── System.map
   │ ──(pahole)── BTF
   └──(objcopy -O binary)── Image ──(gzip)── Image.gz          arm64/Makefile:172
```

每一步的规则出处（下文逐个走读）：

| 步骤 | 工具 | 规则文件:行 | 详见 |
| - | - | - | - |
| `.c → .o` | cc（gcc/clang） | [scripts/Makefile.lib:253](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/scripts/Makefile.lib) `cmd_cc_o_c` | §2 |
| 目录归并 | `ld -r` | [scripts/Makefile.build:497](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/scripts/Makefile.build) `cmd_ld_multi_m` | §3 |
| 大链接 | `ld -T` | [scripts/link-vmlinux.sh:49](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/scripts/link-vmlinux.sh) `vmlinux_link()` | §4 |
| kallsyms | scripts/kallsyms + as + ld | link-vmlinux.sh:110-138 | §5 |
| 压缩镜像 | objcopy + gzip | [arch/arm64/Makefile:172](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/Makefile) | §6 |

## 2. 编译单元：cmd_cc_o_c——教材全部阶段折叠成一行

```make
# scripts/Makefile.lib:252（7.1.3 实测）
quiet_cmd_cc_o_c = CC $(quiet_modtag)  $@
      cmd_cc_o_c = $(CC) $(c_flags) -c -o $@ $<
```

- `$(c_flags)` 里除了 `-I` 包含路径（内核自带头文件树，不用系统 glibc 头），还有一批**直接改变代码生成**的开关：`-fno-PIE`（内核固定虚拟地址基址，见 [002 §2](./002.链接脚本走读：vmlinux.lds.S.md) 的 KIMAGE_VADDR）、`-fno-omit-frame-pointer`（栈回溯）、`-mstrict-align` 等——它们是"依赖机器的优化"（教材 p479）的调度旋钮；
- 教材的词法/语法/语义/优化/代码生成都在这一行的 cc1 内部发生，构建系统**不感知**；能从产物侧观察它们的窗口是 `foo.s`（`make foo.s`）与 `foo.o` 的重定位记录（[004 §3](./004.模块加载：运行期的链接器.md)）；
- 同一条流水线还有 `.S → .o` 的伴生规则（汇编源文件，`cmd_as_s_S`）——内核里手写汇编不少（`arch/arm64/kernel/head.S` 等），汇编器视角见 RISC-V 书第 5 章。

## 3. 归档层：`ld -r` 部分链接——"先缝成大块，重定位留到最后"

内核有几万个 `.o`，逐个交给最终链接会让命令行和依赖图爆炸，所以按目录树分层打包：

```make
# scripts/Makefile.build:476（7.1.3 实测）
$(obj)/built-in.a: $(real-obj-y) FORCE
	$(call if_changed,ar_builtin)

# scripts/Makefile.build:496
quiet_cmd_ld_multi_m = LD [M]  $@
      cmd_ld_multi_m = $(LD) $(ld_flags) -r -o $@ @$< $(cmd_objtool)
```

两个要点：

1. **`-r`（--relocatable）**：合并输入段的同名段（所有 `.text` 并成一个 `.text`）、解析**文件间**符号引用，但**不**做最终地址分配——重定位记录被保留/合并，留给大链接（教材 p365"代码生成"章的重定位小节：重定位可以推迟到"地址确定的那一刻"，这里推迟了两级）；
2. 顶层 Makefile 把 `obj-y` 里的目录替换成它的 `built-in.a`（[Makefile.build:75](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/scripts/Makefile.build)：`obj-y := $(patsubst %/, %/built-in.a, $(obj-y))`）——目录树 = 归档树。

```
 drivers/net/built-in.a ──┐
 mm/built-in.a ───────────┤            （逐级 ld -r）
 kernel/built-in.a ───────┼──► vmlinux.a（顶层大归档）
 arch/arm64/built-in.a ───┘
```

## 4. 大链接：vmlinux_link() 与 --gc-sections

```sh
# scripts/link-vmlinux.sh:49（函数开头；:106 为实际链接行）
# ${LD} ${KBUILD_LDFLAGS} -T ${kallsymso}... ${btf_vmlinux_bin_o} ...
```

关键开关：

- **`-T arch/arm64/kernel/vmlinux.lds.S`（预处理后成 .lds）**：布局的总指挥——入口、段顺序、地址、合成符号、断言，逐段走读见 [002](./002.链接脚本走读：vmlinux.lds.S.md)；
- **`--gc-sections`**（[顶层 Makefile:1058](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/Makefile)：`LDFLAGS_vmlinux += --gc-sections`）：**链接期死代码消除**——每个函数/数据在自己的小节里（见 [003 §1](./003.编译器扩展与内核：compiler.h深读.md) 的 `__section`/`-ffunction-sections`），链接器从入口/保留符号出发做可达性分析，不可达的整节丢掉。这就是为什么 lds 里到处是 `KEEP()`——被 KEEP 的段豁免回收（如 initcall 表：它不被调用链引用，却是启动的根）；
- **LTO 变体**（[Makefile:1073](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/Makefile) `--lto-whole-program-visibility`）：链接时优化把"优化"阶段从 cc1 搬到 ld——教材"独立于机器的优化"（p402）的工程极限形态。

## 5. kallsyms：一张"自举"的符号表（两遍链接）

问题：内核想在运行期打印栈回溯/`/proc/kallsyms`，就需要全部符号表；但符号表本身放进镜像会**改变后面所有符号的地址**——鸡生蛋。解法是迭代到收敛：

```sh
# scripts/link-vmlinux.sh:110（节选，逻辑同构）
kallsyms()          # 调 scripts/kallsyms 从 nm 输出生成 .S 汇编表
sysmap_and_kallsyms()  # :133 —— 一遍"链接+取符号+生成表"
# :198  第一遍: .tmp_vmlinux0 → .tmp_vmlinux0.kallsyms
#        第二遍: .tmp_vmlinux1（若地址仍漂移则再来一次 → .tmp_vmlinux2）
```

```
 第 0 遍链接: .tmp_vmlinux0（无 kallsyms 段，地址是"少了表"的布局）
      │ nm 提取符号
      ▼ scripts/kallsyms 生成 .tmp_vmlinux0.kallsyms.S ──as──► .o
 第 1 遍链接: .tmp_vmlinux1 = vmlinux + 表（布局变了，表里的地址可能过期）
      │ 若表内容与上遍不同 → 第 2 遍（:198 附近的循环），通常两遍收敛
      ▼
 最终 vmlinux（表内地址 = 表自身所在布局的真实地址）
```

消费方：`kernel/kallsyms.c`（运行期查表）。教材对应"符号表管理"（p27）——只是内核把它做成了**自引用数据结构**。

## 6. 收尾：objcopy、BTF 与压缩

- **System.map**：`nm vmlinux` 的文本快照（静态符号表，见 [008.CS 宏观系列](../../008.COMPUTER_SCIENCE/000.编译-汇编-链接/README.md) 的目标文件六大部分）；
- **BTF**：`pahole` 从 DWARF 蒸馏出紧凑类型信息（link-vmlinux.sh:218 的 `.tmp_vmlinux1.btf.o`）——CO-RE/eBPF 的类型地基，"调试信息反哺运行时"的代表；
- **Image / Image.gz**：`objcopy -O binary` 剥掉 ELF 外壳得纯二进制 `Image`，再 gzip 成默认目标 `Image.gz`（[arch/arm64/Makefile:172](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/Makefile) `KBUILD_IMAGE := $(boot)/Image.gz`）——此时"加载器"是内核自己的解压头（arch/arm64/boot/compressed/），ELF 的加载职责由启动代码接管。
