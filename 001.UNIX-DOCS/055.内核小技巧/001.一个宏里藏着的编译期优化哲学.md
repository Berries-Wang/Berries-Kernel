# 一个宏里藏着的编译期优化哲学 —— `___wait_is_interruptible`

> **代码基线**: 本文内核代码全部取自本地内核树 [003.LINUX-7.1.3](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3), 所有 `file:line` 引用均已在 7.1.3 树逐条核实
> **编译验证**: macOS arm64 / Apple clang -O2, 见 [§6](#6-本地验证clang--o2-复刻实验)

---

## 0. TL;DR

`___wait_is_interruptible` ([include/linux/wait.h:284](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/wait.h)) 用 `!__builtin_constant_p(state) ||` 这个看似多余的前缀, 让同一个 `if` 在三种场景下坍缩成最优代码:

| state 的性质 | 宏折叠结果 | `if (宏 && __int)` 坍缩为 |
|-|-|-|
| 编译期常量, **不可**中断(如 `wait_event` 的 `TASK_UNINTERRUPTIBLE`) | `0` | 整个分支被编译器**删除**(死代码剪除) |
| 编译期常量, **可**中断(如 `wait_event_interruptible` 的 `TASK_INTERRUPTIBLE`) | `1` | `if (__int)`(常量折叠) |
| 运行时变量 | `1`(短路) | `if (__int)`(**检查合并**: 掩码判断被省掉, 完全委托给 `__int`) |

正确性不丢的原因: 变量场景下"是否可中断"的判断并没有消失, 而是已经包含在 `prepare_to_wait_event` 的返回值 `__int` 里(经 `signal_pending_state` 用**同一个掩码**在运行时兜底, [signal.h:411](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/sched/signal.h))。**一份契约, 两处执行**: 编译期能定的就地折叠, 定不了的交给运行时的同一判断。

## 1. 引子: 一行让人停下来的代码

读内核源码时, 最让人惊艳的瞬间往往不是宏大的架构设计, 而是藏在角落、让人忍不住停下来琢磨的两行代码。在等待队列的头文件里就有这么一个:

```c
// include/linux/wait.h:284
#define ___wait_is_interruptible(state)						\
	(!__builtin_constant_p(state) ||					\
	 (state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))
```

初看有两个疑问:

1. `!__builtin_constant_p(state) ||` 这一前缀在逻辑上很"怪": 如果 state 不是常量就直接返回真? 那后面的掩码判断还有什么意义?
2. 这个宏的用途显然是判断"进程睡眠状态是否可被信号打断", 为什么不直接写 `(state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL))`?

答案藏在它的**调用点**和**编译器视角**里。

## 2. 宏本身: 三种输入, 三种输出

`__builtin_constant_p(expr)` 是 GCC/Clang 内建函数: `expr` 能在编译期求值则返回 `1`, 否则返回 `0`。它让同一个宏在预处理后走向完全不同的优化路径:

- **state 是运行时变量** → `__builtin_constant_p(state)` 为 `0`, `!0` 短路求值为真 → 宏整体为 `1`;
- **state 是编译期常量且含可中断位** → 前缀为 `0`, 取掩码分支 → `state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)` 非 `0` → 宏为 `1`;
- **state 是编译期常量且不含可中断位** → 掩码分支折叠为 `0` → 宏为 `0`。

掩码中两个状态位的定义(任务状态位完整定义见 [include/linux/sched.h:106](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/sched.h)):

| 状态 | 值 | 定义处 | 睡眠中能否被信号打断 |
|-|-|-|-|
| `TASK_INTERRUPTIBLE` | `0x00000001` | sched.h:108 | 任意信号 |
| `TASK_UNINTERRUPTIBLE` | `0x00000002` | sched.h:109 | 不能 |
| `TASK_WAKEKILL` | `0x00000100` | sched.h:119 | 修饰位: 仅致命信号可唤醒 |
| `TASK_KILLABLE` | `TASK_WAKEKILL \| TASK_UNINTERRUPTIBLE` = `0x102` | sched.h:137 | 仅致命信号(`kill -9`) |
| `TASK_IDLE` | `TASK_UNINTERRUPTIBLE \| TASK_NOLOAD` = `0x402` | sched.h:141 | 不能(`ps` 显示 `D` 但不计入 load) |

```c
// include/linux/sched.h:106-141 (节选)
#define TASK_RUNNING			0x00000000
#define TASK_INTERRUPTIBLE		0x00000001
#define TASK_UNINTERRUPTIBLE		0x00000002
...
#define TASK_WAKEKILL			0x00000100
...
/* Convenience macros for the sake of set_current_state: */
#define TASK_KILLABLE			(TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)
...
#define TASK_IDLE			(TASK_UNINTERRUPTIBLE | TASK_NOLOAD)
```

所以"可中断"在这里的含义是: **状态掩码与 `(TASK_INTERRUPTIBLE | TASK_WAKEKILL)` 有交集** —— 要么任意信号可打断, 要么至少致命信号可打断。`TASK_KILLABLE` 虽以 `TASK_UNINTERRUPTIBLE` 为基底, 因为带 `TASK_WAKEKILL` 位, 也算"可中断"。

## 3. 主调用点: `___wait_event` 模板

该宏在 7.1.3 全树共有 **3 个调用点**, 三套等待队列实现各自复制了同一句 `if (___wait_is_interruptible(state) && __int)`, 模式一字不差:

- [wait.h:315](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/wait.h) — `___wait_event`(常规等待队列, 所有 `wait_event*` 的公共模板)
- [swait.h:171](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/swait.h) — `___swait_event`(简单等待队列, swait.h:157 注释自述 "as per `___wait_event()` but for swait")
- [wait_bit.h:269](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/wait_bit.h) — `___wait_var_event`(按变量地址等待, `wait_var_event*` 的模板)

三处的剪枝逻辑完全相同(后两处的顶层宏同样喂常量 state)。下文以最常用的 `___wait_event` 为例(7.1.3 完整代码):

```c
// include/linux/wait.h:302
#define ___wait_event(wq_head, condition, state, exclusive, ret, cmd)		\
({										\
	__label__ __out;							\
	struct wait_queue_entry __wq_entry;					\
	long __ret = ret;	/* explicit shadow */				\
										\
	init_wait_entry(&__wq_entry, exclusive ? WQ_FLAG_EXCLUSIVE : 0);	\
	for (;;) {								\
		long __int = prepare_to_wait_event(&wq_head, &__wq_entry, state);\
										\
		if (condition)							\
			break;							\
										\
		if (___wait_is_interruptible(state) && __int) {			\
			__ret = __int;						\
			goto __out;						\
		}								\
										\
		cmd;								\
										\
		if (condition)							\
			break;							\
	}									\
	finish_wait(&wq_head, &__wq_entry);					\
__out:	__ret;									\
})
```

循环每轮做四件事:

1. **`prepare_to_wait_event`**(wait.h:310): 把 `__wq_entry` 挂上等待队列、把当前进程置为 `state`, 并把"信号检查结果"作为返回值存入 `__int`;
2. 条件已成立则直接退出(wait.h:312);
3. **关键行**(wait.h:315): 若 `___wait_is_interruptible(state) && __int` —— "这个睡眠可被打断, 且确实有信号来了" —— 就带着 `__int` 提前退出等待;
4. 否则执行 `cmd`(通常是 `schedule()`), 让出 CPU 睡眠, 醒来后再查条件。

`__int` 的取值只有两种(见 §4): `0` 表示可以继续睡; `-ERESTARTSYS` 表示有待处理信号、等待应当被打断。

## 4. 运行时的另一半: `prepare_to_wait_event` 与 `signal_pending_state`

宏的另一半逻辑在运行时。`prepare_to_wait_event` 位于 [kernel/sched/wait.c:289](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/kernel/sched/wait.c):

```c
// kernel/sched/wait.c:289
long prepare_to_wait_event(struct wait_queue_head *wq_head, struct wait_queue_entry *wq_entry, int state)
{
	unsigned long flags;
	long ret = 0;

	spin_lock_irqsave(&wq_head->lock, flags);
	if (signal_pending_state(state, current)) {
		/*
		 * Exclusive waiter must not fail if it was selected by wakeup,
		 * it should "consume" the condition we were waiting for.
		 *
		 * The caller will recheck the condition and return success if
		 * we were already woken up, we can not miss the event because
		 * wakeup locks/unlocks the same wq_head->lock.
		 *
		 * But we need to ensure that set-condition + wakeup after that
		 * can't see us, it should wake up another exclusive waiter if
		 * we fail.
		 */
		list_del_init(&wq_entry->entry);
		ret = -ERESTARTSYS;
	} else {
		if (list_empty(&wq_entry->entry)) {
			if (wq_entry->flags & WQ_FLAG_EXCLUSIVE)
				__add_wait_queue_entry_tail(wq_head, wq_entry);
			else
				__add_wait_queue(wq_head, wq_entry);
		}
		set_current_state(state);
	}
	spin_unlock_irqrestore(&wq_head->lock, flags);

	return ret;
}
EXPORT_SYMBOL(prepare_to_wait_event);
```

而它调用的 `signal_pending_state`([include/linux/sched/signal.h:409](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/include/linux/sched/signal.h))藏着本篇最关键的一行:

```c
// include/linux/sched/signal.h:409
static inline int signal_pending_state(unsigned int state, struct task_struct *p)
{
	if (!(state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))	// <-- 就是同一个掩码!
		return 0;
	if (!signal_pending(p))
		return 0;

	return (state & TASK_INTERRUPTIBLE) || __fatal_signal_pending(p);
}
```

第一行(wait.h 的宏在 signal.h:411 找到了运行时的孪生兄弟): **如果 state 不含可中断位, 无论有没有信号, 直接返回 0** —— 于是 `prepare_to_wait_event` 走 `else` 分支正常入队睡眠, `__int = 0`, wait.h:315 的条件不成立, 等待绝不会被打断。

由此得出全文最重要的事实:

> 当 state 是**运行时变量**时, `__int` 是否非零已经**完整编码**了"这次等待是否该被信号打断"(可中断性检查 + 信号检查都在里面)。此时 `___wait_is_interruptible` 再去做一次 `state & MASK` 的位测试是纯重复劳动 —— 所以它干脆短路返回 `1`, 让 `if (1 && __int)` 被优化成 `if (__int)`, 一次多余的位测试都不留。

## 5. 编译器视角: 三种坍缩

把 §2 的真值表代入 wait.h:315, 整个 `if` 在编译期的决策如下:

```
                 ___wait_is_interruptible(state)
                               │
           ┌───────────────────┴────────────────────┐
           │ state 是编译期常量?  (__builtin_constant_p)
           └───────────────────┬────────────────────┘
              否 (运行时变量)   │   是
                    ▼          ▼
                 返回 1     (state & (TASK_INTERRUPTIBLE|TASK_WAKEKILL))
                    │          │
                    │     ┌────┴─────────────┐
                    │   = 0              ≠ 0
                    │  (TASK_             (TASK_INTERRUPTIBLE
                    │   UNINTERRUPTIBLE   / TASK_KILLABLE
                    │   / TASK_IDLE)      / ...含可中断位)
                    ▼     ▼                  ▼
              if (1 && __int)        if (0 && __int)
                    │                      │
                    ▼                      ▼
               if (__int)          分支整体删除 (死代码剪除)
```

上层 `wait_event*` 宏传入的 state 都是**字面常量**, 逐一对应:

| 上层宏 | 传入的 state(常量) | 掩码折叠 | wait.h:315 最终形态 |
|-|-|-|-|
| `wait_event`(wait.h:329) | `TASK_UNINTERRUPTIBLE` = `0x2` | `0x2 & 0x101 = 0` | **分支删除** |
| `wait_event_interruptible`(wait.h:482) | `TASK_INTERRUPTIBLE` = `0x1` | `0x1 & 0x101 = 1` | `if (__int)` |
| `wait_event_killable`(wait.h:913) | `TASK_KILLABLE` = `0x102` | `0x102 & 0x101 = 0x100 ≠ 0` | `if (__int)` |
| `wait_event_freezable`(wait.h:368) | `TASK_INTERRUPTIBLE\|TASK_FREEZABLE` | ≠ `0` | `if (__int)` |
| 内部调用(state 为变量) | 变量 | 短路 `1` | `if (__int)` |

```c
// 四个上层宏如何把常量 state 喂给 ___wait_event:

// include/linux/wait.h:329
#define __wait_event(wq_head, condition)					\
	(void)___wait_event(wq_head, condition, TASK_UNINTERRUPTIBLE, 0, 0,	\
			    schedule())

// include/linux/wait.h:368
#define __wait_event_freezable(wq_head, condition)				\
	___wait_event(wq_head, condition, (TASK_INTERRUPTIBLE|TASK_FREEZABLE),	\
			0, 0, schedule())

// include/linux/wait.h:482
#define __wait_event_interruptible(wq_head, condition)				\
	___wait_event(wq_head, condition, TASK_INTERRUPTIBLE, 0, 0,		\
		      schedule())

// include/linux/wait.h:913
#define __wait_event_killable(wq, condition)					\
	___wait_event(wq, condition, TASK_KILLABLE, 0, 0, schedule())
```

于是同一个 `___wait_event` 模板展开出两代代码:

- **`wait_event()` 路径**(不可中断): `if (0 && __int)` 连同 `__ret = __int; goto __out;` 分支体一起被编译器删除。这条路径上连"信号"的概念都不存在, 运行时零开销 —— 内核里成千上万个 `wait_event()` 调用点, 每个都免费享受了这次剪枝;
- **其余路径**: `if (1 && __int)` → `if (__int)`, 运行时只做一次 `__int` 非零判断, 掩码位测试一次都不多做。

这就是"为什么不直接写 `(state & MASK)`": 变量场景下那样写会多生成一次运行时的 `and` + `tst`(见 §6 的对照组 `variant_d`), 而加上 `!__builtin_constant_p(state) ||` 前缀后, 掩码判断**要么在编译期消失(常量), 要么被 `1` 短路跳过(变量)**, 两种情况都不进热路径。

## 6. 本地验证: clang -O2 复刻实验

把宏从内核语境中剥离出来, 用四个函数复刻三种场景 + 一个对照组:

```c
/* 复刻 include/linux/wait.h:284 的 ___wait_is_interruptible。
 * 分支体返回 -ERESTARTSYS, 与 ___wait_event 的中断退出语义一致。 */
#define TASK_INTERRUPTIBLE   0x00000001
#define TASK_UNINTERRUPTIBLE 0x00000002
#define TASK_WAKEKILL        0x00000100
#define __ERESTARTSYS        (-13L)

#define ___wait_is_interruptible(state)            \
	(!__builtin_constant_p(state) ||            \
	 (state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))

extern void branch_deleted(void);

/* 场景A: wait_event() 传入常量 TASK_UNINTERRUPTIBLE */
long variant_a(long __int)
{
	if (___wait_is_interruptible(TASK_UNINTERRUPTIBLE) && __int) {
		branch_deleted();		/* 期望: 整个调用被编译器删除 */
		return __ERESTARTSYS;
	}
	return 0;
}

/* 场景B: wait_event_interruptible() 传入常量 TASK_INTERRUPTIBLE */
long variant_b(long __int)
{
	if (___wait_is_interruptible(TASK_INTERRUPTIBLE) && __int)
		return __ERESTARTSYS;
	return 0;
}

/* 场景C: state 为运行时变量 */
long variant_c(int state, long __int)
{
	if (___wait_is_interruptible(state) && __int)
		return __ERESTARTSYS;
	return 0;
}

/* 对照组: 不用 __builtin_constant_p, 只写位掩码 */
long variant_d(int state, long __int)
{
	if ((state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)) && __int)
		return __ERESTARTSYS;
	return 0;
}
```

`clang -O2 -S` 在 arm64 (Apple clang, macOS) 上的实测输出(已去掉无关伪指令):

```asm
_variant_a:                     ; 场景A: 常量不可中断
        mov     x0, #0          ; 整个函数坍缩为 return 0
        ret                     ; branch_deleted() 调用彻底消失 ← 死代码剪除

_variant_b:                     ; 场景B: 常量可中断
        mov     x8, #-13
        cmp     x0, #0          ; 只比较 __int, 没有 state 掩码测试 ← 常量折叠
        csel    x0, xzr, x8, eq
        ret

_variant_c:                     ; 场景C: state 为运行时变量(第一个参数在 w0, __int 在 x1)
        mov     x8, #-13
        cmp     x1, #0          ; 只比较 __int; w0(state) 全程未被碰过! ← 检查合并
        csel    x0, xzr, x8, eq
        ret

_variant_d:                     ; 对照组: 直接写位掩码
        mov     w8, #257        ; 掩码 0x101 装入寄存器
        and     w8, w0, w8      ; 运行时位测试 state & MASK
        cmp     x1, #0
        ccmp    w8, #0, #4, ne  ; 两次判断串联
        mov     x8, #-13
        csel    x0, x8, xzr, ne
        ret                     ; 比场景C多 3 条指令, 全在热路径上
```

四个函数恰好对应三种坍缩和反例:

| 变体 | 场景 | 结果 |
|-|-|-|
| `variant_a` | 常量 `TASK_UNINTERRUPTIBLE` | 函数体坍缩为 `return 0`, 连外部函数调用 `branch_deleted()` 都被删除 |
| `variant_b` | 常量 `TASK_INTERRUPTIBLE` | 只测 `__int`, 掩码在编译期折成 `1` |
| `variant_c` | state 为变量 | **`state` 参数(w0)在生成的指令里完全没有出现** —— 证明掩码判断被 `!__builtin_constant_p` 短路省掉 |
| `variant_d` | 直接写位掩码(对照组) | 多出掩码装载 + `and` + `ccmp` 三条指令, 变量场景的代价一目了然 |

真实内核里 `if` 的两个分支是 `__ret = __int; goto __out;` 与 `schedule()` 循环, 比这里复杂, 但坍缩规律完全相同 —— GCC 对内核正式构建做的正是这三类优化: **检查合并**(`1 && x` → `x`)、**死代码剪除**(`0 && x` → 删除)、**常量传播**(`__builtin_constant_p` 分流)。

## 7. 哲学总结: 一份契约, 两处执行

把 §4 和 §5 合起来看, 同一个掩码 `(TASK_INTERRUPTIBLE | TASK_WAKEKILL)` 在两个世界各出现一次:

```
   编译期 (wait.h:286)                          运行时 (signal.h:411)
   ___wait_is_interruptible(state)              signal_pending_state(state, p)
          │                                            │
   state 是常量?                                if (!(state & MASK)) return 0;
   ├─ 是 → 掩码折叠成 0/1,                       state 是变量时的兜底:
   │        分支删除或化为 if (__int)             同一掩码在运行时再判一次,
   └─ 否 → 短路成 1, 完全委托 __int               结果编码进 __int 交回调用者
```

这十几行代码浓缩了内核工程里三条很"哲学"的原则:

1. **编译期与运行时的分界**: 能在编译期定下来的, 绝不留给运行时; 编译期定不下来的, 要保证运行时已有人兜底, 而不是重复检查。两层用的是**同一份掩码契约**, 一处剪枝、一处兜底, 互为保险。
2. **热路径零成本**: `wait_event` 家族是内核调用密度最高的基础设施之一。一次看似可有可无的位测试, 乘以数万个调用点、每秒百万次睡眠唤醒, 就是可观的浪费。`if (0 && __int)` 让不可中断路径上连"信号"二字都不存在于指令流中。
3. **上下文即契约**: 这个宏**单独看是不完备的** —— 变量场景它恒返回 1, "是否可中断"的判断完全依赖 `prepare_to_wait_event` 内部已经用同一掩码检查过。它的正确性建立在对调用链上下游的精确理解之上。读内核代码时, 任何一行"看不懂"的写法, 答案往往不在这行本身, 而在它的上下文里。
