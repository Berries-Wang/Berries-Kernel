## 指令

书籍表 1.15 补全——LDTR/STTR 族与对应 LDR/STR 语法相同，语义差异只有一条：**按"非特权（unprivileged）访问级别"做权限检查**：

|指令|描述|指令|描述|
|--|--|--|--|
|LDTR|非特权加载，8 字节|STTR|非特权存储，8 字节|
|LDTRB/LDTRSB|1 字节 / 有符号 1 字节|STTRB|1 字节|
|LDTRH/LDTRSH|2 字节 / 有符号 2 字节|STTRH|2 字节|
|LDTRSW|有符号 4 字节|—|—|

**为什么内核需要它**：EL1 跑内核、EL0 跑用户。arm64 开 PAN（PSTATE.PAN，Privileged Access Never）后，内核**普通** load/store 访问用户态地址会被硬件拒绝——逼着所有"碰用户内存"的路径要么临时关 PAN，要么用 LDTR/STTR（它们按 EL0 权限检查，PAN 不拦）。UAO（ARMv8.2，书籍提到的扩展）是个开关：UAO=0（内核常态）时 LDTR/STTR 严格按 EL0 检查；UAO=1 时反转，LDTR/STTR 在 EL1 执行的效果等同普通 LDR/STR（按 EL1 权限检查）。指令页原文（[C6-2340](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=2340)）：

> "Explicit Memory effects produced by the instruction behave **as if the instruction was executed at EL0 if the Effective value of PSTATE.UAO is 0** and either: The instruction is executed at EL1. …"
>
> 当 PSTATE.UAO 的有效值为 0 且在 EL1（或 HCR_EL2.{E2H,TGE}={1,1} 的 EL2）执行时，本指令的显式内存效果**等效于在 EL0 执行**。

## 内核实例：LDTR/STTR 就是 arm64 的 `get_user/put_user`

**① 汇编宏**——[arch/arm64/include/asm/asm-uaccess.h:68-84](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/asm-uaccess.h)：

```asm
/*
 * Generate the assembly for LDTR/STTR with exception table entries.
 * This is complicated as there is no post-increment or pair versions of the
 * unprivileged instructions, and USER() only works for single instructions.
 */
	.macro user_ldp l, reg1, reg2, addr, post_inc
8888:		ldtr	\reg1, [\addr];
8889:		ldtr	\reg2, [\addr, #8];
		add	\addr, \addr, \post_inc;	// 没有后变基版本，手动推进

		_asm_extable_uaccess	8888b, \l;	// 访问出错 → 跳修复标号
		_asm_extable_uaccess	8889b, \l;
	.endm
```

**② C 侧的统一入口**——[arch/arm64/include/asm/uaccess.h:239,337](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/uaccess.h)：

```c
#define raw_get_user __raw_get_mem("ldtr", ...)		// get_user → ldtr
#define raw_put_user __raw_put_mem("sttr", ...)		// put_user → sttr
```

两个细节值得咀嚼（都写在 ① 的注释里）：
1. **LDTR/STTR 没有后变基、没有 pair 版本**——`user_ldp` 拷 16 字节要两条 `ldtr` + 一条手动 `add`，异常表也得登记两条（8888/8889 两个标号）；
2. **异常表（extable）** 是 LDTR 生效的另一半：用户指针非法时硬件抛访问权限异常，内核查 `__ex_table` 找到 `8888b` 对应的修复点跳过去返回 `-EFAULT`——"把错误变成控制流"。

**③ MTE 检查路径**——[arch/arm64/lib/mte.S:96,123](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/lib/mte.S)：`USER(2f, ldtrb w4, [x1])` 逐字节非特权读，探测用户缓冲区的 tag——LDTRB 的窄宽度正合适。

## QA

##### 1. 内核直接用 LDR 读用户态地址行不行？

开 PAN 后直接硬件异常（这本身就是安全特性：防止内核被诱导读写用户内存的提权攻击）；关 PAN 又失掉保护。正确姿势只有 LDTR/STTR（或 KPTI/UAO 方案下的组合）。书籍说"当 PSTATE.UAO=1 时在 EL1/EL2 执行这些非特权指令的效果和特权指令一样"——反过来说就是 UAO=0（内核常态）时 LDTR/STTR 严格按 EL0 权限检查，PAN 与之兼容。

##### 2. `get_user` 返回 `-EFAULT` 的机制链是什么？

`ldtr` 抛权限异常 → 异常向量表入口 → `do_page_fault` → 查 `__ex_table`（`_asm_extable_uaccess` 登记的 修复地址）→ 回到内核标注的失败标号。汇编宏里的 `8888:` 标号 + `extable` 条目 = 把"硬件异常"包装成"函数返回错误码"。全流程深潜见 [../009.中断与异常/002.异常发生后的处理.md](../009.中断与异常/002.异常发生后的处理.md)。
