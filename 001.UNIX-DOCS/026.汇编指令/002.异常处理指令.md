## 0. 一句话总结

A64 的"异常处理指令"分两半：**三个异常生成指令** `SVC/HVC/SMC` 分别把控制权向上交给 EL1（内核）、EL2（Hypervisor）、EL3（Secure Monitor）——Linux 的系统调用、KVM 的 hypercall、PSCI/TF-A 请求全靠它们；**异常返回指令** `ERET` 把 `PC←ELR_ELx`、`PSTATE←SPSR_ELx` 一步还原回去。

## 异常生成指令

书籍表 1.20 补全：

|指令|目标 EL|功能|备注|内核实例|
|--|--|--|--|--|
|SVC|EL1（从 EL0 发起时）|系统调用指令，`SVC #imm`，允许应用程序自陷到操作系统|Linux/AArch64 调用约定：**系统调用号放 x8**，参数 x0-x5，立即数恒为 `#0`|vDSO 信号返回桩，[arch/arm64/kernel/vdso/sigreturn.S:73-75](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/vdso/sigreturn.S)|
|HVC|EL2|虚拟化系统调用指令，`HVC #imm`，允许主机操作系统自陷到 hypervisor|KVM：`kvm_call_hyp()`；固件调用：SMCCC 的 HVC conduit|SMCCC 宏，[arch/arm64/kernel/smccc-call.S:11-13](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/smccc-call.S)；hyp-stub 处理端 [arch/arm64/kernel/hyp-stub.S:62-78](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/hyp-stub.S)|
|SMC|EL3|安全监控系统调用指令，`SMC #imm`，允许 OS/hypervisor 自陷到 secure monitor|只在 EL1/EL2 可用；ATF/TF-A 提供 EL3 固件服务（PSCI、SDEI…）|`__arm_smccc_smc`，[arch/arm64/kernel/smccc-call.S:31-34](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/smccc-call.S)|

SVC 指令页原文说清了"立即数去哪了"（[C6-2799](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=2799)）：

> "On executing an SVC instruction, the PE records the exception as a Supervisor Call exception in **ESR_ELx**, using the **EC syndrome value 0x15**, and **the value of the immediate argument**."
>
> 执行 SVC 时，PE 把异常记录为 Supervisor Call 异常写入 ESR_ELx，EC 综合码为 0x15，**立即数的值**也随之记录（AArch64 下在 ESR_ELx.ISS<15:0>）。

三者层层向上的关系（异常只能**向更高 EL** 走）：

```
EL0 应用 ──SVC──► EL1 内核 ──HVC──► EL2 KVM/Hypervisor ──SMC──► EL3 Secure Monitor
   ▲                 ▲                    ▲                        ▲
   └─────────────────┴────────────────────┴──── ERET 逐级返回 ─────┘
```

## 内核实例

**① SVC：vDSO 信号返回桩**（用户态唯一还在内核里"种"的 SVC）——[arch/arm64/kernel/vdso/sigreturn.S:73-75](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/vdso/sigreturn.S)：

```asm
SYM_CODE_START(__kernel_rt_sigreturn)
//	PLEASE DO NOT MODIFY
	mov	x8, #__NR_rt_sigreturn		// 系统调用号 → x8
//	PLEASE DO NOT MODIFY
	svc	#0
```

信号处理函数返回时跳进 vDSO 这段代码，`x8` 放调用号、`svc #0` 自陷进内核——AArch64 Linux 的标准系统调用形状（glibc 走的 `syscall()` 同理，只是那段在 libc 里）。异常向量入口见 [arch/arm64/kernel/entry.S:517](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/entry.S) 的 `vectors` 表（EL0/EL1 × 64/32 位分组）。

**② HVC：一条宏通吃 SMC/HVC**——[arch/arm64/kernel/smccc-call.S:11-13, 31-44](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/smccc-call.S)：

```asm
	.macro SMCCC instr
	\instr	#0				// smc #0 或 hvc #0
	ldr	x4, [sp]
	stp	x0, x1, [x4, #ARM_SMCCC_RES_X0_OFFS]	// 回填 x0-x3 到结果结构体
	...
1:	ret
	.endm

SYM_FUNC_START(__arm_smccc_smc)
	SMCCC	smc
SYM_FUNC_END(__arm_smccc_smc)

SYM_FUNC_START(__arm_smccc_hvc)
	SMCCC	hvc
SYM_FUNC_END(__arm_smccc_hvc)
```

参数 x0-x7 按寄存器原样传给固件（SMCCC 规范的调用约定），返回后把 x0-x3 存回 `struct arm_smccc_res`。PSCI（CPU on/off/suspend）、SDEI 等都从这里进固件，走哪条指令由设备树的 `conduit` 属性决定。

**③ HVC 的内核侧接收端：hyp-stub**——[arch/arm64/kernel/hyp-stub.S:62-78](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/hyp-stub.S)：

```asm
2:	cmp	x0, #HVC_SOFT_RESTART
	b.ne	3f
	...
3:	cmp	x0, #HVC_RESET_VECTORS
	beq	9f				// Nothing to reset!
	/* Someone called kvm_call_hyp() against the hyp-stub... */
	mov_q	x0, HVC_STUB_ERR
	eret					// ← 这就是异常返回
9:	mov	x0, xzr
	eret
```

HVC 自陷进 EL2 后，hyp-stub 按 x0 里的 function id 分发；注意**返回全靠 `eret`**——x0 同时是请求参数和返回值（in/out 同寄存器，SMCCC 约定）。

## 异常返回：ERET / DRPS

书籍表 1.20 只列了三个"进"指令，配套的"出"指令一并补全：

|指令|功能|备注|
|--|--|--|
|ERET|从当前 EL 的异常返回：`PC ← ELR_ELx`，`PSTATE ← SPSR_ELx`（NZCV/DAIF/SP/EL 整体还原）|指令页原文："Returns from an exception, to an EL and execution state that is determined by the SPSR…"（[C6-2171](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=2171)）|
|ERETAA/ERETAB|带指针认证的 ERET（验证 PAC 后返回，FEAT_PAuth）|内核 `__ptrauth` 路径|
|DRPS|调试恢复返回（Debug Restore state），调试器场景，内核常规路径不用|—|

**内核实例：一条 `eret` 完成 EL1 首次进入**——[arch/arm64/kernel/head.S:270-284](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/head.S)：

```asm
SYM_FUNC_START(init_kernel_el)
	mrs	x1, CurrentEL
	cmp	x1, #CurrentEL_EL2
	b.eq	init_el2

SYM_INNER_LABEL(init_el1, SYM_L_LOCAL)
	...
	msr	spsr_el1, x0			// 目标 PSTATE（EL1h + DAIF 屏蔽）
	msr	elr_el1, lr			// 目标 PC = 返回地址
	mov	w0, #BOOT_CPU_MODE_EL1
	eret					// PC←ELR_EL1, PSTATE←SPSR_EL1
```

启动代码把 `spsr_el1/elr_el1` 当"返程票"填好，一条 `eret` 就降回 EL1 继续执行——异常返回的全部语义就这两行 MSR + 一条 ERET。异常出口的常规路径 `kernel_exit` 的最后一条指令同样是 `eret`（[arch/arm64/kernel/entry.S:459](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/entry.S)），前面紧跟一条 `dmb sy`（见 [000.内存屏障指令简介.md](./000.内存屏障指令简介.md) 实例①）。

## QA

##### 1. `SVC #imm` 的 imm 到底给谁用？为什么 Linux 恒写 `#0`？

立即数被记录进 `ESR_ELx.ISS<15:0>`（见上文指令页原文），异常处理程序读 ESR 就能拿到。但 AArch64 Linux 的系统调用号走 **x8 寄存器**传（glibc/vDSO 约定），ESR 里的 imm 被忽略，所以 ABI 固定写 `#0`。它真正被用起来的是 AArch32 兼容态（32 位程序 `svc #__NR_compat_sigreturn` 之类）和某些 RTOS（直接用 imm 区分服务）。

##### 2. HVC 和 SMC 都是"陷进固件"，区别在哪？

陷进的 EL 不同、信任域不同：HVC 进 **EL2**（KVM/hypervisor 的地盘，可被 EL3 屏蔽），SMC 进 **EL3**（Secure Monitor，最高权限）。同一个 PSCI 请求，固件 conduit 是 "hvc" 就走 `hvc #0`（EL2 转发），是 "smc" 就直通 EL3——见 `drivers/firmware/psci/psci.c` 的 `__invoke_psci_fn_hvc/__invoke_psci_fn_smc`（[drivers/firmware/psci/psci.c:113](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/drivers/firmware/psci/psci.c)）。

##### 3. SVC 从 EL1 发起会怎样？

异常"向更高或同 EL"发生：EL1 发 SVC 仍进 EL1（同一异常向量表的不同组——`vectors` 里 EL1h 组与 EL0 组的区别，见 [arch/arm64/kernel/entry.S:517-533](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/entry.S)）。内核自己的 `BUG()/WARN()` 用同一族的 `brk` 指令自陷（`brk BUG_BRK_IMM`，[arch/arm64/include/asm/asm-bug.h:45,65](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/asm-bug.h)）——都是"异常生成类指令"在内核态的用法。
