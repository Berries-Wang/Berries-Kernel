## 0. 一句话总结

ARMv8 是弱一致性内存模型：**跨地址**的访存可见顺序没有任何保证（缓存一致性只管同一地址，见深潜笔记 §1.1 的 MP litmus）。屏障就是把顺序"补上"的指令——三档强度递增：`DMB` 管顺序、`DSB` 在顺序之上再管完成、`ISB` 管取指（上下文同步）；第四种现代形态 `LDAR/STLR` 把单向顺序直接焊进访存指令本身。

## 内存屏障指令

书籍表 1.16 补全（功能/格式/内核典型用法）：

|指令|功能|格式|内核典型用法|
|--|--|--|--|
|数据存储屏障（Data Memory Barrier，DMB）|保证屏障**前后的访存之间的相对顺序**（观察序不乱），**不保证完成**——前面的写可以还没到达，后面的访存不能越过它|`DMB <domain>{,<direction>}` 如 `dmb ish`、`dmb ishst`|`smp_mb()/smp_wmb()/smp_rmb()` 在 arm64 的展开，见 [arch/arm64/include/asm/barrier.h:126-128](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)|
|数据同步屏障（Data Synchronization Barrier，DSB）|比 DMB 强一档：屏障**之前的访存必须全部完成**（到达观察点）后，DSB 本身才算完成，之后的指令才能继续|`DSB <domain>{,<direction>}` 如 `dsb sy`、`dsb st`|`mb()/wmb()/rmb()`（驱动 MMIO 写序、DMA）、TLB/缓存维护指令之后，见 [arch/arm64/include/asm/barrier.h:63-65](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)|
|指令同步屏障（Instruction Synchronization Barrier，ISB）|**上下文同步**：ISB 之后的指令在 ISB 完成后才重新取指，冲掉流水线里预取的旧指令——让之前的系统寄存器/TLB/缓存控制写入"生效"|`ISB <option>`（option 通常为 `#0x3` 即 `sy`，汇编可不写）|改 SCTLR/TTBR/系统寄存器之后；MMU 开关处，见 [arch/arm64/kernel/head.S:278-279](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/head.S)|

ARM ARM 把这三种能力开宗明义（B2-295 原文）：

> "The memory barriers defined by the Arm architecture provide a range of functionality, including: **Ordering** of load/store instructions. **Completion** of load/store instructions. **Context synchronization**."
>
> Arm 架构定义的内存屏障覆盖三类功能：访存的**排序**、访存的**完成**、**上下文同步**。

### 域与方向变体：`dmb ish` 里的两个后缀是什么

DMB/DSB 都带 **域（domain）** 和 **方向（direction）** 两个可选后缀，选得越窄开销越小（选项编码见 [C6-2157](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=2157)）：

| 后缀 | 含义 | 什么时候用 |
|--|--|--|
| 域 `SY` | 全系统（ Inner+Outer+Device 全部观察者） | 默认/最强，`mb()` |
| 域 `ISH` | **Inner Shareable**——本 Inner Shareable 域内的核（多核内核态同步的常规范围） | `smp_mb()` 等核间同步 |
| 域 `NSH` | 仅本核（Non-shareable） | 单核内自约束（如旁路 speculative load 修复） |
| 域 `OSH` | Outer Shareable——跨集群/到设备侧 | DMA 一致性屏障 |
| 方向（无后缀） | 读+写都管 | `dmb ish` |
| 方向 `ST` | 只管**写**的顺序（写序屏障） | `smp_wmb()` → `dmb ishst` |
| 方向 `LD` | 只管**读**的顺序（读序屏障） | `smp_rmb()` → `dmb ishld` |

内核里的对应关系（全部实测于 [arch/arm64/include/asm/barrier.h](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)）：

```c
// arch/arm64/include/asm/barrier.h:63-65   强屏障：DSB
#define __mb()          dsb(sy)
#define __rmb()         dsb(ld)
#define __wmb()         dsb(st)

// arch/arm64/include/asm/barrier.h:67-69   DMA 侧：Outer Shareable 域
#define __dma_mb()      dmb(osh)
#define __dma_rmb()     dmb(oshld)
#define __dma_wmb()     dmb(oshst)

// arch/arm64/include/asm/barrier.h:126-128  核间同步：Inner Shareable 域
#define __smp_mb()      dmb(ish)
#define __smp_rmb()     dmb(ishld)
#define __smp_wmb()     dmb(ishst)
```

一眼看出分层：**核间同步用 DMB（顺序就够），跨观察点/设备侧用 DSB（要完成），`mb()` 系（驱动物理设备、体系结构敏感路径）一律 DSB**。

## 单向屏障：LDAR / STLR

书籍表 1.17——把 acquire/release 语义直接编进访存指令，不再单独插屏障：

|指令|功能|备注|
|--|--|--|
|LDAR|加载-获取（load-acquire）：**本指令之后的**读写不得提前到它之前|对应 `smp_load_acquire()` 的 arm64 展开；带 `L` 后缀的 LDAPR 是弱化版（RCpc，FEAT_LRCPC），对应 `smp_load_acquire()` 的 io-acquire 语义|
|STLR|存储-释放（store-release）：**本指令之前的**读写不得推迟到它之后|对应 `smp_store_release()` 的 arm64 展开|

对应内核宏同样在 barrier.h（`__smp_store_release`/`__smp_load_acquire`，[barrier.h:130,165](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)，展开为 `stlr`/`ldar`，详见深潜笔记 §3）。它们与独占访问的 acquire/release 变体 `LDAXR/STLXR`（自旋锁用的就是这对）是同一套单向语义，互链：[001.独占内存访问指令/](./001.独占内存访问指令/001.README.md)、[../008.同步原语/001.原子指令/](../008.同步原语/001.原子指令/README.md)。

## QA

##### 1. 内存屏障指令和 `#define barrier() __asm__ __volatile__("" : : : "memory")` 有啥区别和联系呢?

**完全不同的两层：`barrier()` 是编译器屏障，一条指令都不生成；DMB/DSB/ISB 是 CPU 屏障，是真实的指令。**

```c
// include/linux/compiler.h:85
# define barrier() __asm__ __volatile__("" : : : "memory")
```

`"memory"` clobber 告诉编译器：这段空汇编可能读写内存——于是编译器**自己**（①）不敢把屏障两侧的访存对调，**也**（②）不敢把寄存器里缓存的值跨屏障使用（必须真的读写内存）。它只约束**编译器在生成代码时的重排**，对 CPU 硬件的乱序执行、多核可见顺序**毫无约束**——CPU 看到的只是一条普通指令，照常乱序。

| | 编译器屏障 `barrier()` | CPU 屏障 `dmb/dsb/isb` |
|--|--|--|
| 约束谁 | 只约束编译器（代码生成阶段） | 约束 CPU 硬件（执行阶段） |
| 生成的指令 | 零指令（空的内联汇编） | 真实指令，有流水线/访存开销 |
| 防什么 | 编译器重排、寄存器缓存跨点失效 | CPU 乱序、其他核观察顺序错乱 |
| 内核对应 | `barrier()`（compiler.h:85） | `mb()`→`dsb sy`、`smp_mb()`→`dmb ish` |

联系：内核 API 是**两层叠加**的——`smp_mb()` 之类的宏展开成内联汇编时都带 `"memory"` clobber（如上面 barrier.h 的 `dmb(opt)` 定义），**编译器屏障是 CPU 屏障宏的必要组成部分**：光插 `dmb` 不够，还得先阻止编译器把访存对调到屏障外面去。为什么单核只需要编译器屏障不需要 CPU 屏障？因为单核内 CPU 自己维持程序序的假象（同核的访存依赖自洽），会被重排的只有编译器——这就是 `barrier()` 在 UP 配置下当 `smp_mb()` 用的原因（内核 memory-barriers.txt 的 UP 变换规则）。

##### 2. DSB 的方向变体（`dsb st`/`dsb ld`）"完成"的是什么?

`dsb st` 只要求屏障前的**写**全部完成（写序：前面的 store 到达观察点后 DSB 才完成，前面的 load 无所谓）；`dsb ld` 反之。`__wmb()` 选 `dsb(st)`（[barrier.h:65](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/barrier.h)）——写侧只关心写到达设备的顺序，等读完成是白白多等。

##### 3. 改了系统寄存器为什么必须 `isb`，`dsb` 不行吗?

不行，作用点不同。改页表基址/SCTLR 这类"上下文"时，流水线里可能已经预取了一堆按**旧**上下文翻译/取指的指令；`dsb` 只等访存完成，管不到取指流。`isb` 强制**之后的指令重新取指**（B2.6.1 ISB 指令同步屏障原文："all instructions that come after the ISB instruction in program order are fetched from the cache or memory after the ISB instruction has completed"，[B2-295](../../007.BOOKs/Arm%20Architecture%20Reference%20Manual%20for%20A-profile%20architecture/DDI0487_M_a_a_a-profile_architecture_reference_manual-1-3000.pdf#page=295)），旧的预取全部作废。实例：[arch/arm64/kernel/head.S:278-284](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/head.S) `msr sctlr_el1, x0; isb; ... eret`。

## 内核实例

**① 异常返回前的 DMB**——[arch/arm64/kernel/entry.S:455-459](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/entry.S)（`kernel_exit` 宏尾部）：

```asm
	/* Ensure any device/NC reads complete */
	alternative_insn nop, "dmb sy", ARM64_WORKAROUND_1508412

	eret
```

返回用户态前用全系统域的 `dmb sy` 保证对 Device/Non-cacheable 内存的读已完成——erratum 1508412（Cortex-A77/A76 类核心的缓解措施）。

**② TLB 失效后的 DSB**——[arch/arm64/include/asm/tlbflush.h:104](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/include/asm/tlbflush.h)：

```c
	__tlbi_level(vale1is, ...);
	dsb(ish);
```

`tlbi` 广播到共享域的各核是异步的，`dsb ish` 等它**完成**（不只是"已发出"）——这就是"顺序 vs 完成"的区别落到实处的样子。

**③ 开 MMU 后的 ISB**——[arch/arm64/kernel/head.S:278-279](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/arch/arm64/kernel/head.S)：`msr sctlr_el1`（开 MMU）→ `isb` → 后续代码在 MMU 开启后的取指流里重新取指，见 §QA 3。
