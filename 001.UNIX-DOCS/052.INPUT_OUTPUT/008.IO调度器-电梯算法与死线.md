## 1. 原文:为什么需要 I/O 调度器

> "In order to reduce the latency of repetitive disk-head movements, or of random I/O accesses in general, Linux relies on an I/O scheduler. Its purpose is to reorder or bundle read/write requests to block devices. There are many scheduler variants, optimized for different types of workloads. The basic Linux scheduler is based on the original Linux elevator scheduler."（为了减少重复的磁头移动——或者更一般地，随机 I/O 访问——的延迟，Linux 依靠一个 I/O 调度器。它的目的是对发往块设备的读/写请求进行重排或捆绑。调度器有许多变体，针对不同类型的工作负载做了优化。基本的 Linux 调度器以最初的 Linux 电梯调度器为基础。）<sup>[Modern Operating Systems 5th, 书页 767(PDF 792)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=792)</sup>

### 1.1 电梯调度器(elevator)

> "The operations of the elevator scheduler can be summarized as follows: Disk operations are sorted in a doubly linked list, ordered by the address of the sector of the disk request. New requests are inserted in this list in a sorted manner. This prevents repeated costly disk-head movements. The request list is subsequently merged so that adjacent operations are issued via a single disk request."（电梯调度器的操作可以概括如下：磁盘操作在一个双向链表中按磁盘请求的扇区地址排序；新请求以有序方式插入该链表，从而避免反复的高昂磁头移动；请求链表随后进行合并，使相邻的操作经由单次磁盘请求发出。）<sup>[书页 767(PDF 792)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=792)</sup>

ASCII 重绘(电梯:沿一个方向"扫"过盘面,类电梯只上不下):

```text
 磁头位置 →                 扇区地址增大 ──────────────────────────►
    100    [130]   [180]   [220]   [260]   [300]     (排序后的双向链表)
     │        │       │       │       │       │
 请求到达顺序 7,3,1,9,5 …──► 按 sector 排序插入 + 相邻请求合并(elv_merge)
```

内核中的合并入口至今保留在 [block/elevator.c](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/elevator.c):`elv_merge()`(elevator.c:268,尝试向前/向后合并)、`elv_attempt_insert_merge()`(elevator.c:324,插入时顺带合并)。

### 1.2 死线调度器(deadline):给电梯加两张"截止时间表"

> "The basic elevator scheduler can lead to starvation. Therefore, the revised version of the Linux disk scheduler includes two additional lists, maintaining read or write operations ordered by their deadlines. The default deadlines are 0.5 sec for reads and 5 sec for writes. If a system-defined deadline for the oldest write operation is about to expire, that write request will be serviced before any of the requests on the main doubly linked list."（基本的电梯调度器可能导致饥饿。因此，修订版的 Linux 磁盘调度器增加了两个额外链表，分别按截止时间维护读操作或写操作。默认期限是读 0.5 秒、写 5 秒。如果最老写请求的系统定义期限即将到期，该写请求将在主双向链表上的任何请求之前得到服务。）<sup>[书页 767-768(PDF 792)](../../007.BOOKs/现代操作系统/Modern%20Operating%20Systems%205th%20Edition-PDF-01.pdf#page=792)</sup>

```text
                    ┌──────────────────────────────────────┐
 新请求 ──► elv_merge尝试合并 ──否──► 按扇区排序插入 sort_list(RB树)   │ 主链:电梯(防寻道)
                    │                    (read_tree / write_tree)    │
                    │                                                 │
                    └──► 同时挂入 FIFO 链表(按到期时间)                  │ 辅链:防饥饿
                             fifo_list[READ]  死线 0.5s (HZ/2)         │
                             fifo_list[WRITE] 死线 5s   (5*HZ)         │
                                                  │
 派发 dd_dispatch_request(): 先查 FIFO 是否有请求死线将到 → 有则优先派发该请求
                            → 否则按电梯顺序从 sort_list 取
```

**内核数字与原文逐字对应**(Linux 7.1.3 [block/mq-deadline.c](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/mq-deadline.c)):

```c
// block/mq-deadline.c —— 与书中默认死线完全一致
static const int read_expire  = HZ / 2;   /* :30  读死线 0.5 秒 */
static const int write_expire = 5 * HZ;   /* :31  写死线 5 秒   */
static const int writes_starved = 2;      /* :37  读最多连续饿写2轮后放行一次写 */
static const int fifo_batch   = 16;       /* :38  一批最多连续派发16个顺序请求 */

struct deadline_data {
	struct rb_root sort_list[DD_DIR_COUNT]; /* :74 按扇区排序的读/写两棵红黑树 */
	struct list_head fifo_list[DD_DIR_COUNT]; /* FIFO:按死线到期先后 */
	int batching, starved, ...;
};
```

- 派发逻辑:`dd_dispatch_request()`(mq-deadline.c:452)先扫描两棵 sort_list 非空的 FIFO,检查 `deadline_check_fifo`(即将到期的写/读请求则优先);`dd->batching < dd->fifo_batch` 内成批派发顺序请求(mq-deadline.c:338)。
- 读写不对称的原因:读是同步的(进程在等),写可先攒(页缓存);所以读死线短、写死线长,`writes_starved` 再防写饿死。

### 1.3 多队列(multi-queue)时代的三个调度器

内核 7.1.3 的 `block/` 下提供三个可插拔调度器<sup>[block/Kconfig.iosched](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/Kconfig.iosched)</sup>:

| 调度器 | 配置项 | 设计目标 | 源码 |
|-|-|-|---|
| mq-deadline | `CONFIG_MQ_IOSCHED_DEADLINE`(default y) | 上述电梯+死线的多队列版,对 NVMe/SCSI 单队列语义友好 | [block/mq-deadline.c](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/mq-deadline.c) |
| kyber | `CONFIG_MQ_IOSCHED_KYBER`(default y) | 低开销,面向多队列/快速设备:按读与同步写的**目标延迟**自调队列深度 | [block/kyber-iosched.c](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/kyber-iosched.c) |
| bfq | `CONFIG_IOSCHED_BFQ` | 按权重在进程间分配设备带宽,保证交互式/软实时低延迟 | [block/bfq-iosched.c](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/bfq-iosched.c) |

```text
 电梯(legacy,单队列时代) ──blk-mq重构──► mq-deadline(多队列死线)
      │                                        ┆ 机械盘: mq-deadline 常为默认
      ├──► kyber: 目标延迟自调深度(SSD/NVMe)    ┆
      └──► bfq:   按权重分带宽(交互/软实时)     ┆ NVMe 盘也可 none(硬件内部足够深)
```

查询与切换:`/sys/block/<dev>/queue/scheduler`(如 `none mq-deadline kyber bfq`);内核侧调度器经 `elevator` 接口挂接<sup>[block/elevator.h](../../000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3/block/elevator.h)</sup>。

## 2. 与 Professional Linux Kernel Architecture #6.5.8 的互参

PLKA(基于 2.6 时代)描述了 noop/anticipatory/cfq/deadline 四调度器与 `elv_next_request` 等旧接口;演进到今天的对应关系:

| PLKA 时代 | 现今(7.1.3) | 说明 |
|-|-|---|
| noop | `none` | 多队列后基本直通(合并仍做,排序交给硬件) |
| deadline | mq-deadline | 算法不变,挂到 blk-mq |
| anticipatory(预期) | 已删除 | 被 CFQ→BFQ 演进替代 |
| cfq(完全公平) | bfq | 同一思想(按权重分带宽)的现代实现 |

## 3. 小结

- 调度器存在的根本理由:**磁头寻道贵**(机械盘);SSD 时代退化成"防饥饿 + 合并 + 目标延迟控制"。
- 书中电梯/死线描述与内核 `mq-deadline.c` 的参数逐字对得上(0.5s/5s 死线)。
- 从 Fig 10-22 看,调度器夹在"通用块层"与"块设备驱动"之间;完整路径见 [000.块设备/000.块设备的操作](000.块设备/000.块设备的操作.md)。
