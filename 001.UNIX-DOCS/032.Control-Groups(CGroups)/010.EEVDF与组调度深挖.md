# EEVDF 与组调度深挖：cpu.weight 到底怎么改变分配（Linux 7.1.3 源码走读）

> 源码树：`000.SOURCE_CODE/003.LINUX-7.1.3/000.LINUX-7.1.3`，所有 `文件:行号` 逐条核实。
> [004](./004.CGroup如何影响CPU调度.md) §3 只用一句"权重高 → vruntime 涨得慢"带过了 cpu.weight 的生效机理；本文把 EEVDF（Earliest Eligible Virtual Deadline First，6.6 起替代 CFS 的公平调度算法）与组调度的交界面完整走一遍，这是"cgroup 影响调度"最深的最后一层。
> 前置知识：`task_group`/`cfs_rq` 分层结构（[004 §1.2](./004.CGroup如何影响CPU调度.md)）。

---

## 0. EEVDF 三句话

1. 每个实体（任务或**组**）有**虚拟运行时间** `vruntime`：物理时间除以自身权重（跑同样的 1ms，权重 1024 的任务 vruntime 涨 1ms，权重 5120 的只涨 0.2ms）；
2. 谁该跑由两个条件决定：**eligible**（拿到的服务少于应得，即 lag ≥ 0）且 **virtual deadline 最早**（deadline = vruntime + slice/权重）；
3. 权重同时影响 ①②：权重高 → vruntime 涨得慢 → 长期 eligible；虚拟 deadline 也排得更远 → 一旦 eligible 就能连跑更久。**双重放大，这就是 weight 是"乘性"而非"加性"的原因。**

## 1. 数据结构：sched_entity 里 EEVDF 需要的字段

```c
/* include/linux/sched.h:575 (节选: 省略 PELT sched_avg 等与本问无关字段) */
struct sched_entity {
	struct load_weight		load;       // 权重 (cpu.weight 的落点)
	u64				deadline;       // 虚拟截止时间 vd_i
	u64				vruntime;           // 虚拟运行时间 ve_i
	s64				vlag;               // 虚拟滞后 (virtual lag), 近似 lag_i/weight
	u64				vprot;              // "保护期"截止, 防止刚上机就被抢 (7.1.3)
	u64				slice;              // 本次服务请求 r_i (物理量, 默认 0.7ms)

#ifdef CONFIG_FAIR_GROUP_SCHED
	int				depth;
	struct sched_entity	*parent;         // ← 上一层实体 (组实体挂父组 cfs_rq)
	struct cfs_rq		*cfs_rq;             // 我挂在哪个队列
	struct cfs_rq		*my_q;               // 我拥有的队列 (任务为 NULL, 组非 NULL)
	unsigned long			runnable_weight;
#endif
	...
};
```

`my_q` 是否为 NULL 是区分**任务实体**与**组实体**的判据（`entity_is_task()`）。每个 `cfs_rq` 维护聚合量：

- `cfs_rq->sum_weight` / `sum_w_vruntime`：所有权重的和、Σw·v（算平均值用的分子分母）；
- `cfs_rq->zero_vruntime`：把 Σw·v 拉回原点附近的基准（7.1.3 防溢出的手段）；
- `tasks_timeline`：按 **deadline 排序**的红黑树，同时增广存储子树的 `min_vruntime`（最小 vruntime），用于 O(log n) 剪枝。

## 2. 记账：update_curr() 同时推进三件事

```c
/* kernel/sched/fair.c:1407 完整函数体 (cpu.stat 记账在调用者 update_curr_fair():1377) */
static void update_curr(struct cfs_rq *cfs_rq)
{
	/*
	 * Note: cfs_rq->curr corresponds to the task picked to
	 * run (ie: rq->donor.se) which due to proxy-exec may
	 * not necessarily be the actual task running
	 * (rq->curr.se). This is easy to confuse!
	 */
	struct sched_entity *curr = cfs_rq->curr;
	struct rq *rq = rq_of(cfs_rq);
	s64 delta_exec;
	bool resched;

	if (unlikely(!curr))
		return;

	delta_exec = update_se(rq, curr);              // 物理运行时长 Δt
	if (unlikely(delta_exec <= 0))
		return;

	curr->vruntime += calc_delta_fair(delta_exec, curr);   // ① vruntime += Δt/w (fair.c:297)
	resched = update_deadline(cfs_rq, curr);              // ② 到期检查 (§4.3)

	if (entity_is_task(curr)) {
		/*
		 * If the fair_server is active, we need to account for the
		 * fair_server time whether or not the task is running on
		 * behalf of fair_server or not: ...
		 */
		dl_server_update(&rq->fair_server, delta_exec);
	}

	account_cfs_rq_runtime(cfs_rq, delta_exec);           // ③ cpu.max 记账 (004 §4.3)

	if (cfs_rq->nr_queued == 1)
		return;

	if (resched || !protect_slice(curr)) {
		resched_curr_lazy(rq);                     // ④ 到期/失去保护 → 要求重调度
		clear_buddies(cfs_rq, curr);
	}
}
```

`calc_delta_fair()`（fair.c:297）就是乘性换算 `Δt * 1024 / weight`。

### 2.1 lag 的维护

vruntime 只涨不回；"欠了多少"由 **vlag** 表达，在出队/切换时校准：

```c
/* kernel/sched/fair.c:830 entity_lag() 完整函数体 */
static s64 entity_lag(struct cfs_rq *cfs_rq, struct sched_entity *se, u64 avruntime)
{
	u64 max_slice = cfs_rq_max_slice(cfs_rq) + TICK_NSEC;
	s64 vlag, limit;

	vlag = avruntime - se->vruntime;               // vlag = V - v_i
	limit = calc_delta_fair(max_slice, se);

	return clamp(vlag, -limit, limit);             // 防止睡很久的任务积累天量 lag
}

/* kernel/sched/fair.c:859 update_entity_lag() 完整函数体 */
bool update_entity_lag(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	u64 avruntime = avg_vruntime(cfs_rq);
	s64 vlag = entity_lag(cfs_rq, se, avruntime);
	...
	se->vlag = vlag;
	...
}
```

`avg_vruntime()`（fair.c:780）计算加权平均 V = Σw·v / Σw——EEVDF 的"当前时刻"，也是 eligible 判断的基准。

### 2.2 eligible 判定：不除法的技巧

```c
/* kernel/sched/fair.c:895 完整函数体 */
static int vruntime_eligible(struct cfs_rq *cfs_rq, u64 vruntime)
{
	struct sched_entity *curr = cfs_rq->curr;
	s64 key, avg = cfs_rq->sum_w_vruntime;
	long load = cfs_rq->sum_weight;

	if (curr && curr->on_rq) {                       // curr 也参与平均
		unsigned long weight = avg_vruntime_weight(cfs_rq, curr->load.weight);

		avg += entity_key(cfs_rq, curr) * weight;
		load += weight;
	}

	key = vruntime_op(vruntime, "-", cfs_rq->zero_vruntime);
	...
	return avg >= (__int128)key * load;              // 交叉相乘代替除法, 保精度
}

int entity_eligible(struct cfs_rq *cfs_rq, struct sched_entity *se)   /* :939 */
{
	return vruntime_eligible(cfs_rq, se->vruntime);
}
```

**含义**：v_i 比"加权平均 V"小（欠账）→ eligible。睡醒的任务 vruntime 落后 → 立即 eligible；刚跑完的权重小的任务 vruntime 领先 → 暂时不 eligible，只能等别人把平均拉上来。

## 3. 选中：pick_eevdf() 的 O(log n) 双条件搜索

```c
/* kernel/sched/fair.c:1136 完整函数体 (注释块与 PICK_BUDDY 分支保留) */
static struct sched_entity *pick_eevdf(struct cfs_rq *cfs_rq, bool protect)
{
	struct rb_node *node = cfs_rq->tasks_timeline.rb_root.rb_node;
	struct sched_entity *se = __pick_first_entity(cfs_rq);
	struct sched_entity *curr = cfs_rq->curr;
	struct sched_entity *best = NULL;

	/*
	 * We can safely skip eligibility check if there is only one entity
	 * in this cfs_rq, saving some cycles.
	 */
	if (cfs_rq->nr_queued == 1)
		return curr && curr->on_rq ? curr : se;

	/*
	 * Picking the ->next buddy will affect latency but not fairness.
	 */
	if (sched_feat(PICK_BUDDY) && protect &&
	    cfs_rq->next && entity_eligible(cfs_rq, cfs_rq->next)) {
		/* ->next will never be delayed */
		WARN_ON_ONCE(cfs_rq->next->sched_delayed);
		return cfs_rq->next;
	}

	if (curr && (!curr->on_rq || !entity_eligible(cfs_rq, curr)))
		curr = NULL;                             // curr 不 eligible: 排除

	if (curr && protect && protect_slice(curr))
		return curr;                             // 还在保护期内: 不换人

	/* Pick the leftmost entity if it's eligible */
	if (se && entity_eligible(cfs_rq, se)) {         // 最左(deadline最早)的先试
		best = se;
		goto found;
	}

	/* Heap search for the EEVD entity */
	while (node) {
		struct rb_node *left = node->rb_left;

		/*
		 * Eligible entities in left subtree are always better
		 * choices, since they have earlier deadlines.
		 */
		if (left && vruntime_eligible(cfs_rq,
				__node_2_se(left)->min_vruntime)) {  // 左子树可能含 eligible 实体?
			node = left;                         // 树按 deadline 排, 左边 deadline 更早
			continue;
		}

		se = __node_2_se(node);
		if (entity_eligible(cfs_rq, se)) {          // 左子树无 eligible → 检查当前节点
			best = se;
			break;
		}
		node = node->rb_right;                      // 否则只能往右
	}
found:
	if (!best || (curr && entity_before(curr, best)))
		best = curr;
	return best;
}
```

被 `pick_next_entity()`（fair.c:5781）包住、再被 `pick_task_fair()`（fair.c:9197）逐层下钻调用（[004 §4.4](./004.CGroup如何影响CPU调度.md) 的 pick 循环）。**组调度在这里现形**：在父 cfs_rq 上，一个 task_group 就是一个 se——它 compete、被选中后下钻进 `my_q` 继续 pick，直到叶子任务。父层的 eligible/deadline 竞争，用的正是该组实体的 `vruntime/vlag/deadline`，而这些量由组内所有任务的活动汇聚而成。

7.1.3 还加了"保护期"机制：刚被选中的实体在 `vprot` 之前不被抢占（`set_protect_slice()` fair.c:1085、`protect_slice()` :1105），保证最小量子、防止高频互抢。

## 4. 放置：入队时 vruntime 与 deadline 的初始化

### 4.1 place_entity()：lag 保持的数学

任务唤醒/迁移入队时不能简单放 `vruntime = V`——那会把睡眠攒的 lag 清零。EEVDF 用**放置策略**补偿（注释原文给出了完整推导）：

```c
/* kernel/sched/fair.c:5381 完整函数体 (PLACE_LAG 注释中的推导是理解 EEVDF 的钥匙, 原样保留) */
static void
place_entity(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
	u64 vslice, vruntime = avg_vruntime(cfs_rq);
	bool update_zero = false;
	s64 lag = 0;

	if (!se->custom_slice)
		se->slice = sysctl_sched_base_slice;            // 默认 r_i = 0.7ms (fair.c:79)
	vslice = calc_delta_fair(se->slice, se);            // 虚拟 slice = r_i / w_i

	/*
	 * Due to how V is constructed as the weighted average of entities,
	 * adding tasks with positive lag, or removing tasks with negative lag
	 * will move 'time' backwards, this can screw around with the lag of
	 * other tasks.
	 *
	 * EEVDF: placement strategy #1 / #2
	 */
	if (sched_feat(PLACE_LAG) && cfs_rq->nr_queued && se->vlag) {
		struct sched_entity *curr = cfs_rq->curr;
		long load, weight;

		lag = se->vlag;

		/*
		 * If we want to place a task and preserve lag, we have to
		 * consider the effect of the new entity on the weighted
		 * average and compensate for this, otherwise lag can quickly
		 * evaporate.
		 *
		 * Lag is defined as:
		 *
		 *   lag_i = S - s_i = w_i * (V - v_i)
		 *
		 * To avoid the 'w_i' term all over the place, we only track
		 * the virtual lag:
		 *
		 *   vl_i = V - v_i <=> v_i = V - vl_i
		 *
		 * And we take V to be the weighted average of all v:
		 *
		 *   V = (\Sum w_j*v_j) / W
		 *
		 * Where W is: \Sum w_j
		 *
		 * Then, the weighted average after adding an entity with lag
		 * vl_i is given by:
		 *
		 *   V' = (\Sum w_j*v_j + w_i*v_i) / (W + w_i)
		 *      = (W*V + w_i*(V - vl_i)) / (W + w_i)
		 *      = (W*V + w_i*V - w_i*vl_i) / (W + w_i)
		 *      = (V*(W + w_i) - w_i*vl_i) / (W + w_i)
		 *      = V - w_i*vl_i / (W + w_i)
		 *
		 * And the actual lag after adding an entity with vl_i is:
		 *
		 *   vl'_i = V' - v_i
		 *         = V - w_i*vl_i / (W + w_i) - (V - vl_i)
		 *         = vl_i - w_i*vl_i / (W + w_i)
		 *
		 * Which is strictly less than vl_i. So in order to preserve lag
		 * we should inflate the lag before placement such that the
		 * effective lag after placement is the lag
		 * we computed before dequeue.
		 *
		 * As such, invert the above relation for vl'_i to get the vl_i
		 * we need to use such that the lag after placement is the lag
		 * we computed before dequeue.
		 *
		 *   vl'_i = vl_i - w_i*vl_i / (W + w_i)
		 *         = ((W + w_i)*vl_i - w_i*vl_i) / (W + w_i)
		 *
		 *   (W + w_i)*vl'_i = (W + w_i)*vl_i - w_i*vl_i
		 *                   = W*vl_i
		 *
		 *   vl_i = (W + w_i)*vl'_i / W
		 */
		load = cfs_rq->sum_weight;
		if (curr && curr->on_rq)
			load += avg_vruntime_weight(cfs_rq, curr->load.weight);

		weight = avg_vruntime_weight(cfs_rq, se->load.weight);
		lag *= load + weight;                       // 膨胀 lag, 抵消新实体加入
		if (WARN_ON_ONCE(!load))
			load = 1;
		lag = div64_long(lag, load);                // 对加权平均 V 的稀释
		...
		if (weight > load)
			update_zero = true;                 // 重实体: 移动 zero_vruntime 基准防溢出
	}

	se->vruntime = vruntime - lag;                     // 放置: v_i = V - lag

	if (update_zero)
		update_zero_vruntime(cfs_rq, -lag);

	if (sched_feat(PLACE_REL_DEADLINE) && se->rel_deadline) {
		se->deadline += se->vruntime;              // 唤醒保留旧 deadline (延迟敏感)
		se->rel_deadline = 0;
		return;
	}

	/*
	 * When joining the competition; the existing tasks will be,
	 * on average, halfway through their slice, as such start tasks
	 * off with half a slice to ease into the competition.
	 */
	if (sched_feat(PLACE_DEADLINE_INITIAL) && (flags & ENQUEUE_INITIAL))
		vslice /= 2;                                   // 新任务半 slice 优待 (降首响延迟)

	/*
	 * EEVDF: vd_i = ve_i + r_i/w_i
	 */
	se->deadline = se->vruntime + vslice;
}
```

### 4.2 入队路径与组实体

```c
/* kernel/sched/fair.c:5523 完整函数体 */
static void
enqueue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
	bool curr = cfs_rq->curr == se;

	/*
	 * If we're the current task, we must renormalise before calling
	 * update_curr().
	 */
	if (curr)
		place_entity(cfs_rq, se, flags);

	update_curr(cfs_rq);

	/*
	 * When enqueuing a sched_entity, we must:
	 *   - Update loads to have both entity and cfs_rq synced with now.
	 *   - For group_entity, update its runnable_weight to reflect the new
	 *     h_nr_runnable of its group cfs_rq.
	 *   - For group_entity, update its weight to reflect the new share of
	 *     its group cfs_rq
	 *   - Add its new weight to cfs_rq->load.weight
	 */
	update_load_avg(cfs_rq, se, UPDATE_TG | DO_ATTACH);   // PELT 负载跟踪
	se_update_runnable(se);
	/*
	 * XXX update_load_avg() above will have attached us to the pelt sum;
	 * but update_cfs_group() here will re-adjust the weight and have to
	 * undo/redo all that. Seems wasteful.
	 */
	update_cfs_group(se);                                  // ← 组实体: 按组内负载重设权重 (§5)

	/*
	 * XXX now that the entity has been re-weighted, and it's lag adjusted,
	 * we can place the entity.
	 */
	if (!curr)
		place_entity(cfs_rq, se, flags);               // 放置

	account_entity_enqueue(cfs_rq, se);

	/* Entity has migrated, no longer consider this task hot */
	if (flags & ENQUEUE_MIGRATED)
		se->exec_start = 0;

	check_schedstat_required();
	update_stats_enqueue_fair(cfs_rq, se, flags);
	if (!curr)
		__enqueue_entity(cfs_rq, se);                  // 挂入 deadline 红黑树
	se->on_rq = 1;

	if (cfs_rq->nr_queued == 1) {
		check_enqueue_throttle(cfs_rq);             // ★ cpu.max 检查 (004 §4.4)
		list_add_leaf_cfs_rq(cfs_rq);
#ifdef CONFIG_CFS_BANDWIDTH
		if (cfs_rq->pelt_clock_throttled) {         // 解限后恢复 PELT 时钟
			struct rq *rq = rq_of(cfs_rq);

			cfs_rq->throttled_clock_pelt_time += rq_clock_pelt(rq) -
				cfs_rq->throttled_clock_pelt;
			cfs_rq->pelt_clock_throttled = 0;
		}
#endif
	}
}
```

`enqueue_task_fair()`（fair.c:7197）随后用 `for_each_sched_entity(se)`（fair.c:314）**沿 parent 链逐层向上**把每个组实体也入队并更新 `h_nr_queued` 计数——任务醒来会"点亮"它所有祖先组实体。

### 4.3 到期与抢占

```c
/* kernel/sched/fair.c:1238 完整函数体 */
static bool update_deadline(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	if (vruntime_cmp(se->vruntime, "<", se->deadline))
		return false;                            // 还没到 deadline: 继续

	/*
	 * For EEVDF the virtual time slope is determined by w_i (iow.
	 * nice) while the request time r_i is determined by
	 * sysctl_sched_base_slice.
	 */
	if (!se->custom_slice)
		se->slice = sysctl_sched_base_slice;

	/*
	 * EEVDF: vd_i = ve_i + r_i / w_i
	 */
	se->deadline = se->vruntime + calc_delta_fair(se->slice, se);   // 续期
	avg_vruntime(cfs_rq);

	/*
	 * The task has consumed its request, reschedule.
	 */
	return true;                                 // → resched_curr: 回到 pick_eevdf 重选
}
```

即：一个实体最多连跑一个 slice（默认 0.7ms 物理时间，高权重者的**虚拟** slice 更短但**物理**更长），到期就重新竞争。

## 5. 组实体的权重：shares 如何流到每个 CPU 的 se

`cpu.weight` 写的是 `tg->shares`（总量），而**每个 CPU 上的组实体各有自己的权重**，按该 CPU 上组的实际负载比例分配：

```c
/* kernel/sched/fair.c:4205 完整函数体 */
static long calc_group_shares(struct cfs_rq *cfs_rq)
{
	long tg_weight, tg_shares, load, shares;
	struct task_group *tg = cfs_rq->tg;

	tg_shares = READ_ONCE(tg->shares);                  // cpu.weight 设置的总量

	load = max(scale_load_down(cfs_rq->load.weight),    // 该 CPU 上组的实际负载
		   cfs_rq->avg.load_avg);                   //   (瞬时权重与 PELT 平均取大)
	...
	shares = (tg_shares * load);
	if (tg_weight)
		shares /= tg_weight;                        // 按负载占比切分 tg_shares

	return clamp_t(long, shares, MIN_SHARES, tg_shares);
}
```

调用点是每次组实体入队/权重更新时的 `update_cfs_group()`：

```c
/* kernel/sched/fair.c:4243 完整函数体 */
static void update_cfs_group(struct sched_entity *se)
{
	struct cfs_rq *gcfs_rq = group_cfs_rq(se);
	long shares;
	...
	shares = calc_group_shares(gcfs_rq);
	if (unlikely(se->load.weight != shares))
		reweight_entity(cfs_rq_of(se), se, shares);     // 改权重并重算 vruntime 缩放
}
```

**效果**：4 核上 `cpu.weight 4000` 的组，若负载集中在 1 个核，那个核的组实体拿走全部 4000 与其他单核组竞争；4 个核都有负载则各拿 1000。层级嵌套时逐层重复该分配——子组在父组内的占比由子组 `se` 的 shares 决定。

进程换组时的调度器侧迁移（`sched_move_task` → 公平类回调）：


## 6. 把三个角色拼起来：一次 0.7ms 的生命周期

```
任务 T (w=1024) 在组 G (cpu.weight=10000) 中, G 与任务 S (w=1024) 竞争根队列

  t0  pick_task_fair() 在根 cfs_rq:
        候选: se(G)(w=10240) vs se(S)(w=1024)
        se(G) 的 vruntime 涨速 = 1024/10240 = S 的 1/10
        → se(G) 长期 vruntime 更小 → eligible 且 deadline 更近(虚拟量)
      选中 se(G) → 下钻 G->cfs_rq[cpu] → pick_eevdf 选出 T
  t0  T 运行: update_curr() 每 tick/切换:
        ① T 的 vruntime += Δt/1024 (fair.c:1427)
        ② G 的 se 在父层的记账: 由 enqueue 时的 shares 与 PELT 聚合,
           calc_group_shares 把 G 的整体虚拟消耗折算到 se(G)
        ③ G->cfs_rq 的 account_cfs_rq_runtime() 同步扣 cpu.max 配额 (004 §4.3)
  t0+0.7ms  update_deadline() 到期 → resched
        回到根 cfs_rq 重新 pick: se(S) 若已 eligible(欠账) 则这轮轮到 S
  ...      两者按 10:1 的 vruntime 涨速比例轮流, 稳态即 cpu.weight 的 10000:1024 分配
        (G 若撞 cpu.max 配额 → throttle, 整条下钻路径被冻结, 004 §4.4)
```

## 7. 常见问题对照表

| 现象 | 机理落点 |
|---|---|
| 两个组 weight 100:10000，轻负载时轻组也能跑满 | weight 只在**竞争**时起作用（eligible 判定与虚拟 deadline），CPU 空闲时人人 eligible、人人能跑（`pick_eevdf` 无竞争者直接选中） |
| 睡了很久的任务醒来立即抢到 CPU | `place_entity()` 的 PLACE_LAG：vlag 保留（clamp 限幅），放置 vruntime = V - lag → 立即 eligible（fair.c:5491） |
| 新进程首跑延迟不错 | PLACE_DEADLINE_INITIAL：首个 vslice 减半 → deadline 更近（fair.c:5508） |
| 改了 cpu.weight 立即生效 | `__sched_group_set_shares()` 逐 CPU `update_cfs_group()` → `reweight_entity()` 重缩放（fair.c:14071，[004 §3.1](./004.CGroup如何影响CPU调度.md)） |
| 高负载下 weight 大的组尾延迟更好 | 双重机制：虚拟 slice = r/w → 物理连续运行时间 ≈ 0.7ms * w/1024 更长；且长期 eligible |
| `sched_delayed`（延迟出队） | 7.1.3 默认特性：睡眠任务先留在树上给个"悔改"机会，减少 wakeup 抖动（`update_entity_lag()` 的 sched_delayed 分支 fair.c:866） |
