# CGroup 日常排查与实战（配合 004/006/007 源码走读使用）

> 前三篇是"内核为什么"（[004 CPU](./004.CGroup如何影响CPU调度.md)｜[006 内存](./006.CGroup如何影响内存分配.md)｜[007 IO与其他](./007.CGroup如何影响IO与其他系统行为.md)），本篇是"用户态怎么办"：日常用什么命令、出问题看哪个文件、常见场景的配方。
> 实验环境请用 Linux 主机/虚机（macOS 无 cgroup）。示例默认 cgroup v2（`stat -fc %T /sys/fs/cgroup` 返回 `cgroup2fs` 即 v2）。

---

## 1. 三种使用方式，选哪种

| 方式 | 适用 | 说明 |
|---|---|---|
| **systemd（推荐）** | 常驻服务、登录会话 | 一切 unit 都天然在 cgroup 里；改属性即改 cgroup 文件，重启不丢 |
| `systemd-run` | 临时/一次性任务 | 一条命令起一个受控 scope，最省事 |
| 手写 cgroupfs | 学习、内核实验 | 直接 `mkdir`/`echo`，理解最深（见 [003.DEMO](./003.DEMO/000.memory.max.md)） |
| libcgroup 工具（cgcreate 等） | 无 systemd 的老系统 | v2 支持一般，新系统不推荐 |

### 1.1 systemd 的 slice 层级

```
/sys/fs/cgroup/
├── init.scope                      # PID 1 自己
├── user.slice/                     # 所有用户登录会话
├── system.slice/                   # 系统服务, 每个服务一个目录
│   ├── nginx.service/
│   └── ssh.service/
└── machine.slice/                  # 虚拟机/容器 (systemd-nspawn/docker+systemd)
```

unit 与 cgroup 文件的映射（写属性 = 写文件）：

| systemd 属性 | cgroup 文件 | 内核入口（详见 004/006） |
|---|---|---|
| `CPUWeight=` | cpu.weight | `sched_group_set_shares()` fair.c:14107 |
| `CPUQuota=50%` | cpu.max `"50000 100000"` | `tg_set_cfs_bandwidth()` core.c:9807 |
| `AllowedCPUs=` | cpuset.cpus | `update_cpumask()` cpuset.c:2392 |
| `MemoryMin=` / `MemoryLow=` | memory.min / memory.low | `page_counter_set_min/low()` |
| `MemoryHigh=` | memory.high | 罚睡机制（006 §5） |
| `MemoryMax=` | memory.max | memcg OOM（006 §6） |
| `TasksMax=` | pids.max | `pids_try_charge()` pids.c:166 |
| `IOReadBandwidthMax=` | io.max | `tg_set_limit()` blk-throttle.c:1527 |

### 1.2 一次性任务的三个例子

```bash
# 限制批处理脚本: 最多 1.5 核、2G 内存
systemd-run --scope -p CPUQuota=150% -p MemoryMax=2G \
    ./train.sh

# 备份限速 10MB/s, 防止占满磁盘带宽 (259:0 换成 lsblk 的主:次号)
systemd-run --scope -p 'IOReadBandwidthMax=/dev/sda 10M' \
    -p 'IOWriteBandwidthMax=/dev/sda 10M' rsync -a /data /backup

# 把已有 PID 10086 放进受控组
mkdir -p /sys/fs/cgroup/batch
echo "+cpu +memory" > /sys/fs/cgroup/cgroup.subtree_control
echo 10086 > /sys/fs/cgroup/batch/cgroup.procs
```

容器场景：`docker run --cpus=1.5 --memory=512m` 即 `cpu.max "150000 100000"` + `memory.max 536870912`；K8s 的 CPU limits/requests 分别映射 cpu.max/cpu.weight。**排查容器资源问题，本质上就是去 `/sys/fs/cgroup/<容器组>` 读下述文件。**

## 2. 排查 Playbook：现象 → 看哪里

### 2.1 "进程 CPU 用不上去 / 延迟毛刺" —— 先查 CPU 限流

```bash
cat /sys/fs/cgroup/<组>/cpu.stat
# usage_usec 100000000
# nr_periods 10000        ← 经过的周期数 (每 100ms 一个)
# nr_throttled 3200       ← 撞上限的周期数
# throttled_usec 41200000 ← 累计被"停车"的时长
```

判读与处置：
- `nr_throttled/nr_periods` 持续 >5% 且业务有周期性毛刺 → CPU 配额不足。毛刺机理见 [004 §4.4](./004.CGroup如何影响CPU调度.md)：整组任务被停到下个周期，单次可停近百毫秒；
- 处置三板斧：① 调大 `cpu.max`；② 缩短 period（`echo "50000 50000" > cpu.max`，限制粒度更细、毛刺更短）；③ 对毛刺敏感的服务改用 `cpu.weight`（软限制，不限硬顶）+ `cpu.max.burst` 容忍突发；
- 多核注意：quota 是**全组合计**。`cpu.max 100000 100000` + 4 个满载线程 ≠ 每核 25%，而是全组轮转 1 核总量，竞争会放大尾延迟。
- 区分"限流慢"与"就绪但没跑"：`pidstat -wt 1` 看 `%wait`；再对比宿主机 `mpstat 1` 是否本身空闲。

### 2.2 "进程被杀 / malloc 失败" —— 查 memcg OOM

```bash
# ① 确认是被 memcg 杀的 (而非系统级 OOM)
dmesg -T | grep -i "memory cgroup out of memory"
# Memory cgroup out of memory: Killed process 10086 (app) ...

# ② 事件计数
cat /sys/fs/cgroup/<组>/memory.events
# low 0
# high 0        ← 触发过减速带 (006 §5)
# max 123       ← 撞墙次数 (每次 charge 失败 +1)
# oom 3         ← 进入 OOM 流程次数
# oom_kill 3    ← 实际杀掉的进程数

# ③ 用量构成: 到底是什么占的
cat /sys/fs/cgroup/<组>/memory.stat | head
# anon 409600        ← 匿名页(堆/栈), 只能 swap 或杀
# file 204800        ← page cache, 可直接回收
# slab_reclaimable ...
# pgfault / pgmajfault ...
```

处置：
- `memory.current` 贴着 `memory.max` 且 `anon` 占大头 → 真用超了：加限额，或修应用的内存泄漏；
- `file` 占大头 → 多半不用管（cache 可回收）；若想让它别顶爆 max，可设 `memory.high`（在 max 之下留缓冲，靠减速带提前触发回收）；
- 一杀就杀到关键进程：给关键进程设 `oom_score_adj = -1000`（memcg OOM 同样按 oom_score 选 victim），或容器场景开 `memory.oom.group=1` 让整组死透后由上层重启；
- `memory.events` 的 `max` 涨但没 OOM：说明回收救回来了，进程当时只是慢（同步回收卡住分配者）——若频繁出现，考虑提高 max 或设 `memory.high` 平滑化。

### 2.3 "整机没缺内存，进程却很卡" —— memory.high 减速 / PSI

```bash
cat /sys/fs/cgroup/<组>/memory.pressure
# some avg10=85.50 avg60=... total=...      ← 有任务在等内存 (回收/罚睡)
# full avg10=40.20 ...                       ← 全组非中断停等
```
`some` 高而系统空闲内存充足 → 该组被 `memory.high`/`memory.max` 卡住（对照 006 §5 的罚睡：越超越多罚得越重）。处置：放宽 high/max，或降低组内消耗。`full` 持续非零通常意味着全组进入直接回收，性能悬崖。

### 2.4 "fork: retry: Resource temporarily unavailable"

```bash
cat /sys/fs/cgroup/<组>/pids.current /sys/fs/cgroup/<组>/pids.max
cat /sys/fs/cgroup/<组>/pids.events    # max 1 = 撞过限额
```
哪个组的 `pids.current == pids.max`，哪个组就是元凶（注意层级：父组限额也会拦住子组，见 [007 §2](./007.CGroup如何影响IO与其他系统行为.md) 的层级记账）。常见于 systemd 的 `TasksMax=`——user.slice 默认约为全局上限的 15%（`DefaultTasksMax=15%`），编译任务/线程池很容易触顶。

### 2.5 "磁盘 IO 慢"

```bash
cat /sys/fs/cgroup/<组>/io.stat        # 每设备 字节/IO 数, 差分得速率
cat /sys/fs/cgroup/<组>/io.pressure    # IO 等待压力
iostat -x 1                            # 对照设备级 util/await
```
设备 util 高但组内 IO 少 → 是**别人**在吃盘，给自己的组设 `io.max` 保底，或给吃盘的组限速（见 §3 配方）。

### 2.6 定位"进程到底在哪个组"

```bash
cat /proc/<PID>/cgroup
# 0::/system.slice/nginx.service      ← v2 路径
ls /sys/fs/cgroup/system.slice/nginx.service/
```

## 3. 实战配方

### 3.1 批处理任务限流，保护在线服务
```bash
systemd-run --scope -p CPUWeight=20 -p MemoryMax=4G \
    -p IOWeight=10 ./batch_job
```
在线服务不设硬限额（或设很宽的 cpu.max），批任务用**低权重**抢剩余资源——CPU 空闲时批任务也能跑满，忙时自动让位（weight 语义见 [004 §3](./004.CGroup如何影响CPU调度.md)）。

### 3.2 关键服务的内存保护（别人缺页时别动我）
```bash
systemctl set-property mydb.service MemoryLow=8G
# 全局回收按比例绕开受保护组 (vmscan.c:2424 apply_proportional_protection)
# 7.1.3 起保护是按比例缩放而非硬跳过, 设成工作集大小的 50-100% 均可试验
```

### 3.3 暂停进程组（比 SIGSTOP 安全）
```bash
echo 1 > /sys/fs/cgroup/<组>/cgroup.freeze
cat /sys/fs/cgroup/<组>/cgroup.events    # frozen 1 = 全组已冻结
echo 0 > /sys/fs/cgroup/<组>/cgroup.freeze
```
冻结发生在系统调用边界（[007 §4](./007.CGroup如何影响IO与其他系统行为.md)），不会把进程冻在持锁中途——做快照、迁移、排查快照级一致性问题都用它。

### 3.4 防 fork 炸弹
```bash
systemctl set-property user-1000.slice TasksMax=512
# 登录会话再失控也炸不穿系统; 系统级兜底:
sysctl kernel.threads-max=4194304    # 全局线程上限(非 cgroup, 但值得一并设)
```

### 3.5 绑核隔离（低延迟服务）
```bash
# ① 建一个组并成为"分区根", CPU 2-3 随之退出全局负载均衡
mkdir /sys/fs/cgroup/rt
echo 2-3 > /sys/fs/cgroup/rt/cpuset.cpus
echo root > /sys/fs/cgroup/rt/cpuset.cpus.partition
cat /sys/fs/cgroup/rt/cpuset.cpus.effective   # 确认生效
# ② 服务绑到同一批 CPU
systemctl set-property myrt.service AllowedCPUs=2-3
```
partition 语义与调度域重建见 [004 §5.3](./004.CGroup如何影响CPU调度.md)。

### 3.6 手动强制回收（在线缓解内存压力）
```bash
echo 512M > /sys/fs/cgroup/<组>/memory.reclaim   # 让内核立刻从该组回收 512M
```
该文件直达 `try_to_free_mem_cgroup_pages()`（[006 §3](./006.CGroup如何影响内存分配.md)），不用等水位触发。

## 4. 观测速查表

| 想知道 | 命令/文件 |
|---|---|
| 进程属于哪个组 | `cat /proc/PID/cgroup` |
| 组内有哪些进程 | `cat <组>/cgroup.procs`；systemd 下 `systemd-cgls`/`systemd-cgtop` |
| CPU 是否被限流 | `<组>/cpu.stat` 的 `nr_throttled`、`throttled_usec`（差分） |
| 内存用量构成 | `<组>/memory.stat`；总量 `memory.current`；峰值 `memory.peak` |
| 内存事件（撞墙/OOM） | `<组>/memory.events`（含祖先）/ `memory.events.local`（仅本组） |
| 内存/IO 压力 | `<组>/memory.pressure`、`io.pressure`（PSI） |
| IO 速率与限额 | `<组>/io.stat`、`io.max` |
| 进程数限额 | `<组>/pids.{current,max,events}` |
| 组是否被冻结 | `<组>/cgroup.events` 的 `frozen` |
| cgroup 版本 | `stat -fc %T /sys/fs/cgroup`（`cgroup2fs`=v2，`tmpfs`=v1） |
| 内核侧限流机理 | 回到 [004](./004.CGroup如何影响CPU调度.md)/[006](./006.CGroup如何影响内存分配.md)/[007](./007.CGroup如何影响IO与其他系统行为.md) 对照函数 |

## 5. 一个综合案例：K8s Pod 周期性超时

现象：某 Pod（容器组 `/sys/fs/cgroup/kubepods/pod xxx/`）P99 延迟每 100ms 出现毛刺。

1. `cpu.stat`：`nr_throttled/nr_periods` ≈ 95% → CPU limit 撞顶；
2. 对照 [004 §4](./004.CGroup如何影响CPU调度.md)：quota 按周期补给（`sched_cfs_period_timer`），超限任务被停车到下个周期——毛刺周期 100ms 与 limit period 吻合，实锤；
3. `memory.pressure` 正常 → 排除内存；
4. 处置：提高 CPU limit；或应用侧降低并发；或改 CPU burst（`cpu.max.burst`）容忍突发。

整个排查没有用任何"玄学"，每一步都能在内核源码里指出是哪个函数在计数/执行——这就是把 004/006/007 读完后应有的状态。
